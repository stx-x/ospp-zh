<div class="chap-en">The Programming Interface</div>
<blockquote class="epigraph">从程序员的视角来看，用户就是一个外设——当你发出读请求时，它才会敲字。——<strong>彼得·威廉斯（Peter Williams）</strong></blockquote>

上一章讨论了操作系统内核为实现进程抽象所需的机制。进程是程序的一个实例——内核提供一个高效的沙箱，让不可信的代码以用户级身份直接运行在处理器上。

本章讨论我们如何选择使用进程抽象：操作系统为应用程序提供哪些功能？这些功能又应该放在哪里——哪些应该放进操作系统内核，哪些应该放进用户级库？操作系统本身又应该如何组织？

这个问题有多少种操作系统，就有多少种答案。即便只是描述某一个操作系统的完整编程接口和内部组织，也足以写成一整本书。因此，本章只探讨 UNIX 编程接口的一个子集——UNIX 是 Linux、MacOS、iOS 和 Android 的基石。我们也会谈及 Windows 如何处理同样的问题。

首先，我们需要回答“是什么”——操作系统需要为应用程序提供哪些功能？

- **进程管理。** 程序能否创建另一个程序的实例？能否等待它完成？能否停止或恢复另一个正在运行的程序？能否向它发送异步事件？

- **输入/输出。** 进程如何与连接到计算机的设备通信，并借助设备与物理世界交互？进程之间能否互相通信？

- **线程管理。** 我们能否在一个进程内创建共享内存或其他资源的多个活动或线程？能否停止和启动线程？如何同步它们对共享数据结构的使用？

- **内存管理。** 进程能否申请更多（或更少）的内存空间？能否与其他进程共享同一块物理内存区域？

- **文件系统与存储。** 进程如何持久地存储用户数据，使其在机器崩溃和磁盘故障后依然幸存？用户如何命名和组织自己的数据？

- **网络与分布式系统。** 进程如何与其他计算机上的进程通信？不同计算机上的进程如何在机器崩溃和网络故障的情况下协调各自的行为？

- **图形与窗口管理。** 进程如何控制屏幕上属于自己那部分的像素？进程如何利用图形加速器？

- **认证与安全。** 用户或程序拥有哪些权限？这些权限如何保持最新？我们依据什么来确认用户（或程序）就是其声称的那个身份？

本章只聚焦其中前两个主题：进程管理和输入/输出。线程管理、内存管理和文件系统将在本书后面的章节中详细讨论。

令人惊叹的是，仅用十几个系统调用，我们就能描述进程管理和输入/输出的功能接口；再增加十几个，就能覆盖其余的系统调用接口。更令人惊叹的是，这些调用与最初的 UNIX 设计相比几乎没有变化。尽管它们早在 20 世纪 70 年代初就被设计和实现，其中大多数调用至今仍在各种系统中广泛使用！

其次，我们需要回答“在哪里”——对于操作系统提供给用户程序的每一项功能，都有若干可选的安放位置，如图 3.1 所示：

- 可以把功能放在用户级程序中。例如在 Windows 和 UNIX 中，都有一个管理用户登录的用户程序，以及另一个管理用户进程的用户程序。

- 可以把功能放在与每个应用程序链接在一起的用户级库中。在 Windows 和 MacOS 中，用户界面控件就是用户级库的一部分，由需要它们的应用程序包含进来。

- 可以把功能放在操作系统内核中，通过系统调用访问。在 Windows 和 UNIX 中，低层进程管理、文件系统和网络协议栈都实现在内核中。

- 可以通过系统调用访问某个功能，但该功能由内核调用的一个独立服务器进程来实现。在许多系统中，窗口管理器就是一个独立的服务器进程。

我们如何做这个选择？重要的是要认识到，这个选择对用户和应用程序员来说（基本上）是透明的。用户想要一个好用的系统；程序员想要一个干净、便利、能完成任务的接口。只要操作系统提供了这样的接口，每个功能具体在哪里实现就由操作系统自行决定，需要在灵活性、可靠性、性能和安全性之间加以权衡。

- **灵活性。** 修改位于内核之外的操作系统代码要容易得多，而且不会破坏使用旧接口的应用程序。如果我们创建了一个新版本的库，只需把它与新应用程序链接在一起，再随时间推移把旧应用程序逐步迁移到新接口即可。然而，如果要修改系统调用接口，我们要么同时修改内核和所有应用程序，要么就必须同时支持新旧两个版本，直到所有旧应用程序都完成迁移。许多应用程序由第三方开发者编写，操作系统厂商无法控制他们。因此，修改系统调用接口是重大的一步，往往需要多家公司协同配合。

UNIX 成功的一个关键思想，就是把它的系统调用接口设计得简洁而强大，这样一来，系统中几乎所有的创新都可以发生在用户代码中，而无须更改操作系统的接口。UNIX 系统调用接口还具有高度的可移植性——操作系统可以移植到新硬件上，而无须重写应用程序代码。如图 3.2 所示，内核可以看作一个“细腰”，它让应用层和硬件层都能各自创新，而不需要同时改动系统的其他部分。

**互联网与“细腰”。** 互联网是另一个体现“简洁且可移植的接口带来好处”的例子。互联网定义了一种分组级协议，它几乎可以运行在任何类型的网络硬件之上，也几乎能支持任何类型的网络应用。万维网的诞生没有要求对互联网的分组传送机制做任何修改；同样，无线网络的引入需要改动硬件设备和操作系统，但网络应用无须任何变化。互联网的“细腰”有时确实会导致低效，但其好处是把一方的变化与另一方的变化解耦，从而同时促进应用和硬件两个层面的创新。

- **安全性。** 不过，资源管理和保护是操作系统内核的职责。正如第 2 章所解释的，保护检查不能实现在用户级库中，因为应用程序代码可以绕过库所做的任何检查。

- **可靠性。** 提高可靠性是让操作系统内核保持精简的另一个理由。内核代码需要拥有配置硬件设备（如磁盘）以及控制应用程序之间保护边界的权力。然而，内核模块彼此之间通常不受保护，因此内核代码中的一个 bug（无论是否涉及敏感操作）都可能破坏用户数据或内核数据。这促使一些系统奉行一种理念：“凡是能放在用户级的东西，就应该放在用户级。”这一理念的一个极端版本，是把操作系统中特权高但不那么关键的部分（如文件系统或窗口系统）与内核的其余部分隔离开来。这称为**微内核**（microkernel）设计。在微内核中，内核本身保持很小，传统操作系统内核的大部分功能则被放进一组用户级进程（即服务器）中，用户应用通过进程间通信来访问它们。

- **性能。** 最后，把控制权转入内核的开销比调用库函数的一次过程调用更高，而经由内核把控制权转交给用户级文件系统服务器的代价还要更高。硬件设计者曾尝试降低这类跨界切换的成本，但其性能仍然是个问题。Windows 7 的前身 Microsoft Windows NT 最初按微内核设计，但出于性能方面的考虑，它的许多功能后来被逐渐迁移回了内核。

::: tip 应用级沙箱与操作系统功能
支持在受限沙箱中执行第三方代码或脚本的应用程序，必须回答许多与上述相同的问题，此时沙箱扮演着操作系统内核的角色。就功能而言：脚本代码能否启动自身的新实例？能否进行输入/输出？能否在后台执行工作？能否持久地存储数据？如果能，它如何为这些数据命名？能否通过网络传输数据？它如何对操作进行认证？

以网页浏览器为例，HTML5 不仅允许脚本在屏幕上绘图、与服务器通信、保存和读取 cookie，近来还增加了用于离线存储和跨文档通信的编程接口。Flash 媒体播放器则为脚本提供了异步操作、文件存储、网络通信、内存管理和认证等能力。

与系统调用一样，这些接口必须经过精心设计，做到对恶意使用无懈可击。十年前，电子邮件病毒之所以泛滥，是因为脚本可以被嵌入文档中，并在文档打开时执行；这些脚本的编程接口允许它们获取当前邮件用户所知的联系人列表并向他们发送邮件，从而只需一次点击就能传播并扩散病毒。接口的功能越丰富，对开发者就越便利，接口的某一方面被黑客滥用的可能性也就越大。
:::

## 3.1　进程管理

在现代计算机上，当用户点击一个文件或应用程序图标时，该应用程序便启动了。这是怎么发生的？被调用的是谁？当然，我们可以把所有需要发生的事情都实现在内核中——为文件系统中的每个条目绘制图标，把鼠标位置映射到目标图标，捕捉鼠标点击，然后启动进程。在早期的批处理系统中，内核不得不掌控一切：用户提交作业，剩下的工作全部由操作系统接管，在作业该运行的时候实例化进程。

另一种做法是允许用户程序创建并管理自己的进程。这催生了铺天盖地的创新。如今，创建和管理进程的程序包括窗口管理器、Web 服务器、Web 浏览器、外壳命令行解释器、源码控制系统、数据库、编译器和文档排版系统。我们还可以继续列举下去，但你已经明白意思了。如果创建进程是一件进程自己就能做的事，那么任何人都可以构建这些应用程序中任意一个的新版本，而无须重新编译内核，也不必强迫其他人使用它。

用户级进程管理的一个早期动机，是允许开发者编写自己的外壳命令行解释器。**外壳**（shell）是一个作业控制系统；Windows 和 UNIX 都有外壳。许多任务都包含完成某件事的一系列步骤，其中每一步都可以是一个独立的程序。借助外壳，你可以把这些步骤写下来，作为一组依序运行的程序，每个程序完成一步。因此，你可以把它看作一个非常早期的脚本系统。

例如，要从多个源文件编译一个 C 程序，可以输入：

```c
cc -c sourcefile1.c
cc -c sourcefile2.c
ln -o program sourcefile1.o sourcefile2.o
```

如果我们把这些命令放进一个文件，外壳就会读取并执行该文件，依次创建一个进程来编译 sourcefile1.c，一个进程来编译 sourcefile2，再创建一个进程把它们链接在一起。外壳脚本一旦本身成为程序，我们就可以通过组合脚本来创建出别的程序。事实上，在 UNIX 上，C 编译器本身就是一个外壳程序！编译器首先调用一个进程来展开头文件包含，然后调用一个单独的进程来解析其输出，再用另一个进程生成（文本形式的）汇编代码，最后还要用一个进程把汇编代码转换为可执行的机器指令。

::: tip 凡事皆有其应用
用户级进程管理是“凡事皆有其应用”（there is an app for that）的另一种说法。我们不必用一个程序包揽一切，而是可以为每项任务编写专门的程序，并按需自由组合。本书的排版系统就使用了五十多个独立的程序。

万维网是把复杂应用由更专门的服务组合而成的绝佳例子。一个网页不必事事亲为：它可以糅合许多不同网页的结果，也可以在本地服务器上调用进程创建来生成页面的一部分。创建进程的灵活性在万维网发展的早期极其重要。HTML 起初只是一种描述静态信息排版格式的方式，但它包含了一种“逃逸”到进程的途径，例如在数据库中做查询，或对用户进行认证。随着时间推移，HTML 增加了对许多不同特性的支持，而这些特性最初都是通过由单独进程执行来做出原型的。当然，对于标准不支持的任何格式，HTML 至今仍然可以执行一个进程来处理。
:::

### 3.1.1　Windows 进程管理

进程管理的一种做法是：只添加一个创建进程的系统调用，再用其他系统调用来完成其余的进程操作。这在理论上简单，在实践中却很复杂。Windows 中有一个例程，名字毫不出人意料，就叫 CreateProcess，其简化形式如下：

```c
boolean CreateProcess(char *prog, char *args);
```

我们把创建进程的一方称为**父进程**（parent），被创建的进程称为**子进程**（child）。

CreateProcess 要执行哪些步骤？正如上一章所解释的，内核需要：

- 在内核中创建并初始化进程控制块（PCB）。

- 创建并初始化一个新的地址空间。

- 把程序 prog 装载到地址空间中。

- 把参数 args 复制到地址空间的内存中。

- 初始化硬件上下文，使其从“start”处开始执行。

- 通知调度器，新进程已就绪，可以运行。

遗憾的是，进程有不少方面是父进程想要控制的，例如：子进程的权限、它的输入和输出发往何处、文件应存放在哪里、用什么作为调度优先级，等等。我们不能信任子进程自己去设置自己的权限和优先级，而指望每个应用程序都自带代码来弄清自己的上下文也很不方便。因此，CreateProcess 的真实接口在实践中要复杂得多，如图 3.3 所示。

<div class="code-cap"><span class="code-label">图 3.3</span>使用 Windows CreateProcess 系统调用的示例节选。前两个参数指定程序及其参数；其余参数涉及进程运行时环境的方方面面。</div>

```c
// Start the child process
if (!CreateProcess(NULL,   // No module name (use command line)
    argv[1],        // Command line
    NULL,           // Process handle not inheritable
    NULL,           // Thread handle not inheritable
    FALSE,          // Set handle inheritance to FALSE
    0,              // No creation flags
    NULL,           // Use parent’s environment block
    NULL,           // Use parent’s starting directory
    &si,            // Pointer to STARTUPINFO structure
    &pi )           // Pointer to PROCESS_INFORMATION structure
)
```

### 3.1.2　UNIX 进程管理

UNIX 采取了另一种进程管理思路，一种在理论上复杂、在实践中简单的方式。UNIX 把 CreateProcess 拆分为两个步骤，称为 fork 和 exec，如图 3.4 所示。

<figure class="book-figure">
<img src="/figures/vol1/image00208.png" alt="图 3.4" loading="lazy">
<figcaption><span class="fig-label">图 3.4</span>UNIX 的 fork 与 exec 系统调用的操作过程。UNIX fork 复制出父进程的一个副本；UNIX exec 让子进程改而运行新程序。</figcaption>
</figure>

**UNIX fork** 创建父进程的一份完整副本，只有一个关键例外。（我们需要某种办法来区分哪个副本是父进程、哪个是子进程。）子进程为即将启动的程序设置权限、优先级和 I/O，例如关闭一些文件、打开另一些文件，如果它要在后台运行就降低自己的优先级，等等。由于子进程运行的代码与父进程完全相同，因此可以信任它会为新程序正确地设置好上下文。

上下文一旦设置好，子进程就调用 **UNIX exec**。UNIX exec 把新的可执行映像装入内存并开始运行。先完整复制一份父进程，随后又在用 exec 把新可执行映像装入内存时覆盖这份副本，这看起来似乎很浪费。事实表明，fork 和 exec 可以借助第 8 章将介绍的一组技术高效地实现。

采用这一设计，UNIX fork 不带任何参数，返回一个整数；UNIX exec 接受两个参数（要运行的程序名和一个传给程序的参数数组）。这取代了 CreateProcess 所需的十个参数。部分由于 UNIX fork 和 exec 的简洁，这套接口自 20 世纪 70 年代初 UNIX 诞生以来几乎从未改变。（虽然接口没有变，但 fork 一词如今已有些歧义：它既用于创建 UNIX 进程的副本，也在线程系统中用于创建新线程。为避免混淆，我们在指 UNIX 的复制进程系统调用时，始终使用“UNIX fork”这一说法。）

#### UNIX fork

在内核中实现 UNIX fork 的步骤是：

- 在内核中创建并初始化进程控制块（PCB）。

- 创建一个新的地址空间。

- 用父进程地址空间的全部内容的副本初始化这个新地址空间。

- 继承父进程的执行上下文（例如所有打开的文件）。

- 通知调度器，新进程已就绪，可以运行。

UNIX fork 有一个奇特之处：这个系统调用会返回**两次**——一次返回到父进程，一次返回到子进程。对父进程，UNIX 返回子进程的进程 ID；对子进程，它返回零以表示成功。就像你克隆了自己，就需要某种办法来分辨谁是克隆、谁是本体一样，UNIX 用 fork 的返回值来区分这两个副本。图 3.5 给出了调用 fork 的示例代码。

<div class="code-cap"><span class="code-label">图 3.5</span>UNIX 中 fork 一个进程的示例代码，以及运行该代码可能得到的输出。getpid 是获取当前进程 ID 的系统调用。</div>

```c
int child_pid = fork();

if (child_pid == 0) {   // I’m the child process.
    printf("I am process \#%d\n", getpid());
    return 0;
} else {                // I’m the parent process.
    printf("I am the parent of process \#%d\n", child_pid);
    return 0;
}

Possible output:
    I am the parent of process 495
    I am process 495

Another less likely but still possible output:
    I am process 456
    I am the parent of process 456
```

如果我们运行图 3.5 中的程序，会发生什么？如果你手头有一台 UNIX 系统，可以亲自试一试。UNIX fork 返回两次：一次在子进程中，返回值为零；一次在父进程中，返回值为子进程的进程 ID。然而，我们无法预知接下来运行的是父进程还是子进程。父进程一直在运行，所以它很可能会先执行到打印语句。但是，在父进程完成 fork 之后、执行到打印语句之前，可能插入一次时钟中断，使处理器被重新分配给子进程；或者我们可能运行在多核系统上，父进程和子进程同时在运行。无论哪种情况，子进程都可能先于父进程打印输出。关于并发执行的不同次序会带来什么影响，我们将在下一章更深入地讨论。

::: tip UNIX fork 与 Chrome 网页浏览器
虽然 UNIX fork 通常与 exec 搭配使用，但在某些情况下，UNIX fork 单独使用也很有用。一个特别有趣的例子是 Google 的 Chrome 网页浏览器。当用户点击一个链接时，Chrome 会 fork 一个进程，在浏览器的新标签页中抓取并渲染该链接指向的网页。父进程继续显示原来的引荐网页，而子进程运行同样的浏览器程序，但运行在自己的地址空间和保护边界之内。这样设计的动机是隔离新链接：即使该网站感染了病毒，也不会传染给浏览器的其余部分。关闭被感染的浏览器标签页，就能把链接和病毒一并从系统中清除。

一些安全研究者把这一思路更进一步。他们把浏览器和邮件系统配置为每打开一个新链接就创建一台新的**虚拟机**（virtual machine），并在每台虚拟机中运行浏览器的一个副本；即使网站带有病毒、破坏了虚拟机中运行的客户操作系统，系统的其余部分也不会受到影响。这时，关闭虚拟机就清除了系统中的病毒。

有趣的是，在 Windows 上，Google Chrome 并不使用 CreateProcess 来按需 fork 浏览器的新副本。困难在于：如果 Chrome 在运行期间被更新，CreateProcess 将创建新版本的副本，它可能与旧版本无法正确互操作。因此，Chrome 会创建一个辅助进程池，让它们在后台等待渲染新的链接。
:::

#### UNIX exec 与 wait

UNIX 的系统调用 exec 完成启动运行一个新程序所需的其余步骤。子进程通常在从 UNIX fork 返回并为新进程配置好执行环境之后，调用 UNIX exec。关于它的工作机制，我们将在下一节讨论 UNIX 管道时进一步介绍。

UNIX exec 执行以下步骤：

- 把程序 prog 装载到当前地址空间中。

- 把参数 args 复制到地址空间的内存中。

- 初始化硬件上下文，使其从“start”处开始执行。

注意，exec 并不创建新进程！

另一方面，父进程常常需要暂停，等待子进程完成，例如下一步操作依赖上一步的输出时。在本章开头的外壳示例中，必须等两次编译都完成，才能安全地启动链接器。

UNIX 有一个系统调用，名字起得再自然不过，就叫 **wait**，它会暂停父进程，直到子进程完成、崩溃或被终止。由于父进程可能创建了很多子进程，wait 需要用子进程的进程 ID 作为参数。有了 wait，外壳就可以创建一个新进程来执行其指令序列中的某一步，然后暂停，等这一步完成后再继续下一步。如果没有 wait，很难构建出一个可用的外壳。

不过，在 UNIX 中调用 wait 是可选的。例如，Chrome 浏览器不需要等待它 fork 出的克隆完成。同样，大多数 UNIX 外壳都提供在后台运行操作的选项，只需在命令行末尾附加“&”。（与 fork 一样，wait 一词如今也有些歧义：它既用于暂停当前 UNIX 进程以等待另一个进程完成，也用于线程同步中在条件变量上等待。为避免混淆，我们在指 UNIX 的 wait 系统调用时，始终使用“UNIX wait”这一说法。有点奇怪的是，等待一个线程完成反而被称为“thread join”（线程汇合），尽管它与 UNIX wait 最为相似。Windows 则更简单，只提供一个名为“WaitForSingleObject”的函数，既可以等待进程完成、线程完成，也可以在条件变量上等待。）

::: tip 内核句柄与垃圾回收
正如上一章讨论的，UNIX 进程结束时，会调用系统调用 exit。exit 可以释放与进程相关的各种资源，例如用户栈、堆和代码段。然而，它在回收进程控制块（PCB）时必须谨慎：即使子进程已经结束，如果它删除了 PCB，那么父进程稍后调用 UNIX wait 时就会拿到一个悬空指针。当然，我们无法确定父进程是否真的会调用 wait，所以保险起见，只有当父进程和子进程都已结束或崩溃时，才能回收 PCB。

推广开来说，Windows 和 UNIX 都有若干系统调用会返回指向某个内核对象的句柄；这些句柄在后续调用中作为 ID 使用。UNIX fork 返回的进程 ID 在后续调用 UNIX wait 时使用；下面我们将看到，UNIX open 返回一个文件描述符，供其他系统调用使用。重要的是要认识到，这些句柄**不是**指向内核数据结构的指针；否则，一个出错的用户程序就可以用伪造的句柄发起系统调用，在内核中大肆破坏。实际上，句柄是特定于进程的，并且在每次使用时都会检查其有效性。

此外，在 Windows 和 UNIX 中，句柄都是引用计数的。内核每返回一个句柄，就把引用计数加一；进程每释放一个句柄（或退出），引用计数就减一。UNIX fork 把进程 ID 的引用计数设为 2，父进程和子进程各占一个。只有当引用计数降到零——即父进程和子进程都已终止——底层数据结构 PCB 才会被回收。
:::

最后，正如上一章概述的，UNIX 提供了一种机制，让一个进程向另一个进程发送即时通知，即**上调**（upcall）。在 UNIX 中，通知通过调用 **signal** 来发送。信号用于终止应用程序、为调试而暂时挂起它、从挂起中恢复、定时器到期，以及许多其他用途。在默认情况下——接收方应用程序没有指定信号处理程序时——内核会代为实现一个标准的信号处理程序。

## 3.2　输入/输出

计算机系统拥有种类繁多、形态各异的输入和输出设备：键盘、鼠标、磁盘、USB 端口、以太网、WiFi、显示器、硬件定时器、麦克风、摄像头、加速度计和 GPS，等等，不一而足。

为了应对这种多样性，我们本来可以为每种设备量身定制一套应用程序编程接口，让它贴合该设备的具体特性。毕竟，磁盘设备与网络截然不同，两者又都与键盘截然不同：磁盘按固定大小的数据块寻址，网络收发的是长度可变的数据包流，而键盘则随着按键被按下逐个返回字符。磁盘只在被问到时才返回数据，网络和键盘却会主动送来数据。早期的计算机系统采取的就是这种让接口去适配设备的做法，但它有一个显著的缺点：每当发明出一种新型硬件设备，系统调用接口就必须升级才能支持它。

UNIX 的主要创新之一，是把所有设备的输入和输出都规整到同一个通用接口之后。事实上，UNIX 在这条路上又向前迈了一大步：它用同一个接口来读写文件，也用它来实现进程间通信。这种做法极为成功，以至于今天的系统几乎无一例外地沿袭了它。本节先勾勒这个接口，下一节再说明如何用它来构建一个外壳。

UNIX 的 I/O 接口包含以下几条基本思想：

- **一致性。** 所有设备 I/O、文件操作和进程间通信都使用同一组系统调用：`open`、`close`、`read` 和 `write`。

- **使用前先打开。** 应用程序做 I/O 之前，必须先对设备、文件或通信通道调用 `open`。这给了操作系统一个机会去检查访问权限，并建立所需的内部簿记数据结构。某些设备（例如打印机）一次只允许一个应用程序访问——如果设备正被占用，`open` 调用可以返回一个错误。`open` 返回一个句柄，供后续的 `read`、`write` 和 `close` 调用用来标识文件、设备或通道；这个句柄被称为**文件描述符**（file descriptor），这个名字多少有些误导，因为即使它指向的是设备或通道、压根儿没有文件牵涉其中，照样也这么叫。为了方便起见，UNIX 外壳在启动应用程序时，就已经为其打开了用于读写终端的文件描述符。

- **面向字节。** 所有设备，哪怕是那些以固定大小数据块传输数据的设备，都用字节数组来访问。同样，文件和通信通道的访问也以字节为单位，尽管我们在文件中存放的是数据结构、在通道上发送的也是数据结构。

- **内核缓冲的读。** 流式数据（例如来自网络或键盘的数据）先存放在内核缓冲区中，再按请求返回给应用程序。这使得 UNIX 的 `read` 系统调用接口对流式读的设备和以块为单位读的设备（如磁盘和闪存）可以保持一致。在这两种情况下，如果没有数据可以立刻返回，`read` 调用就会阻塞直到数据到来，期间还可能把处理器让给其他有待处理工作的任务。

- **内核缓冲的写。** 同样，待发出的数据也先存放在内核缓冲区中，等设备可用时再传输出去。在通常情况下，`write` 系统调用把数据复制进内核缓冲区之后立即返回。这把应用程序和设备解耦开来，使双方都可以各按自己的步调运行。如果应用程序产生数据的速度快于设备接收的速度（把数据排队送打印机输出时很常见），`write` 系统调用就会在内核中阻塞，直到缓冲区腾出足够空间来容纳新数据。

- **显式关闭。** 应用程序用完设备或文件后，就调用 `close`。这向操作系统发出信号：可以减少该设备上的引用计数，并回收任何不再使用的内核数据结构。

::: tip open 与 creat 与 stat
默认情况下，如果应用程序试图打开一个并不存在的文件，UNIX 的 `open` 系统调用会返回错误；作为一个可选项（上面并未列出），应用程序可以通过一个参数告诉内核：若文件不存在则改为把它创建出来。既然 UNIX 另外还提供了用于创建文件的系统调用（`creat`）和用于检测文件是否存在的系统调用（`stat`），那么看起来似乎可以把 `open` 简化成总是假定文件已经存在。

然而，UNIX 常常运行在多用户、多应用程序的环境中，在这种场合下，系统调用设计的问题会变得微妙得多。假设我们不用 UNIX 的这套接口，而是用三个完全独立的函数，分别用来检测文件是否存在、创建文件、打开文件。假定用户拥有检测、打开或创建该文件的权限，下面这段代码能正确工作吗？

```c
    if (!exists(file)) {    // If the file doesn’t exist create it.
    // Are we guaranteed the file doesn’t exist?
        create(file);
    }
    // Are we guaranteed the file does exist?
    open(file);

```

问题在于，在多用户系统上，可能有别的用户在"检测文件是否存在"的调用与"创建文件"的调用之间抢先创建了这个文件。因此，创建文件的调用本身也必须检测文件是否存在。同样地，也可能有别的用户在"创建文件"的调用与"打开文件"的调用之间删掉了这个文件。所以 `open` 同样需要具备判断文件是否还在的能力，并且能在它不在时把它创建出来（如果这正是用户的意图）。

UNIX 用一个全能的、原子的 `open` 来解决这个问题：先检测文件是否存在，可选地在它不存在时创建它，然后打开它。由于系统调用是在内核中实现的，操作系统可以使 `open`（以及所有其他 I/O 系统调用）相对于其他系统调用而言不可被打断。如果另一个用户在内核正对同一个文件执行 `open` 系统调用期间试图删除该文件，那么删除操作会被推迟到 `open` 完成为止。`open` 会返回一个文件描述符，它会一直有效，直到应用程序关闭该文件的那一刻。删除操作会把文件从文件系统中移除，但在文件被关闭之前，文件系统并不会真正回收它的磁盘块。
:::

- **管道。** **UNIX 管道**是一个带有两个文件描述符的内核缓冲区，一个用于写（把数据放进管道），一个用于读（把数据从管道中取出），如图 3.6 所示。读取数据的顺序与写入的顺序完全一致，但由于数据经过缓冲，生产者和消费者的执行得以解耦，从而在通常情况下减少等待。任一端点关闭管道或退出时，管道即告终止。因特网上有一种与 UNIX 管道类似的设施，叫做 TCP（传输控制协议，Transmission Control Protocol）。UNIX 管道连接的是同一台机器上的进程，而 TCP 则在运行于不同机器上的两个进程之间提供一条双向管道。在 TCP 中，数据在一台机器上按字节序列写入，在另一台机器上以同样的序列被读出。

- **替换文件描述符。** 通过操纵子进程的文件描述符，外壳可以让子进程改为从文件或管道读取输入，或者把输出送往文件或管道，而不是从键盘读入、输出到屏幕。这样一来，子进程就不必知道是谁在提供或消费它的 I/O。外壳用一个名为 `dup2(from, to)` 的特殊系统调用来完成这种重定向，它用 `from` 文件描述符的一份副本替换掉 `to` 文件描述符。

- **等待多路读。** 在客户—服务器计算中，一台服务器可能同时与多个客户进程各有一条管道处于打开状态。通常，没有数据可读时 `read` 会阻塞，而让服务器轮流轮询每条管道、查看是否有活儿要干，效率实在太低。UNIX 系统调用 `select(fd[], number)` 就是解决这个问题的。`select` 让服务器等待一组文件描述符中任意一个的输入；它返回那个有数据的文件描述符，但并不读出数据。Windows 中有一个等价的函数，叫做 `WaitForMultipleObjects`。

## 3.3　案例研究：实现一个外壳

图 3.7 中列出的这十来个 UNIX 系统调用，足以构建出一个灵活而强大的命令行外壳，而且它完全运行在用户级，不需要任何特殊权限。正如前面提到的，创建外壳的那个进程负责为它提供一个已经打开的文件描述符，供它读取作为输入的命令（例如从键盘读入），称为 **stdin**；还要提供一个用于写出结果的文件描述符（例如送往显示器），称为 **stdout**。

<div class="code-cap"><span class="code-label">图 3.8</span>一个简单 UNIX 外壳的示例代码。</div>

```c

 main() {
     char *prog = NULL;
     char **args = NULL;

     // Read the input a line at a time, and parse each line into the program
     // name and its arguments. End loop if we’ve reached the end of the input.
     while (readAndParseCmdLine(&prog, &args)) {

         // Create a child process to run the command.
         int child_pid = fork();

         if (child_pid == 0) {
             // I’m the child process.
             // Run program with the parent’s input and output.
             exec(prog, args);
             // NOT REACHED
         } else {
             // I’m the parent; wait for the child to complete.
             wait(child_pid);
             return 0;
         }
     }
 }

```

图 3.8 给出了外壳基本操作的代码。外壳从输入中读取一个命令行，然后分叉出一个进程来执行该命令。UNIX 的 `fork` 会自动复制父进程中所有已打开的文件描述符，并递增内核对这些描述符的引用计数，因此子进程的输入和输出与父进程相同。父进程要等子进程运行结束之后，才去读取下一条待执行的命令。

因为无论一个已打开的文件描述符代表的是键盘、屏幕、文件、设备还是管道，对它进行读写的命令都是一样的，所以 UNIX 程序不需要知道自己的输入来自何处、输出去向何方。这在许多方面都很有用：

- **程序可以是一份命令文件。** 程序通常是一组机器指令，但在 UNIX 上，程序也可以是一个包含若干命令、交由外壳逐条解释执行的文件。为了消除歧义，UNIX 中的外壳程序在文件的首行写上 "#! interpreter" 来表明自己的身份，其中 "interpreter" 是外壳可执行文件的名字。UNIX 的 C 编译器就是这么工作的。当它被 exec 执行时，内核把它识别为一个外壳文件，于是启动解释器，并把该文件作为输入传给解释器。外壳把这个文件当作一张命令清单读入，依次调用预处理器、语法分析器、代码生成器和汇编器，恰好像它正在从键盘读入文本一样。当最后一条命令完成时，外壳解释器调用 `exit`，通知内核该程序已经结束。

- **程序可以把自己的输出送往文件。** 通过改动子进程中的 stdout 文件描述符，外壳就可以把子进程的输出重定向到一个文件中。在标准的 UNIX 外壳中，这用一个"大于"符号来表示。因此，"ls > tmp" 把当前目录的内容列进文件 "tmp" 里。在 `fork` 之后、`exec` 之前，外壳可以用 `dup2` 替换子进程的 stdout 文件描述符。由于子进程是从父进程克隆出来的，改动子进程的 stdout 不会影响父进程。

- **程序可以从文件读取自己的输入。** 同样地，通过用 `dup2` 改动 stdin 文件描述符，外壳可以让子进程从文件中读取输入。在标准的 UNIX 外壳中，这用一个"小于"符号来表示。因此，"zork < solution" 玩名为 "zork" 的游戏，而操作指令来自文件 "solution" 中存放的一串命令。

- **一个程序的输出可以成为另一个程序的输入。** 外壳可以用管道把两个程序连接起来，使一个的输出成为另一个的输入。这称为**生产者—消费者**（producer-consumer）关系。举例来说，在 C 编译器中，预处理器的输出被送往语法分析器，语法分析器的输出被送往代码生成器，然后再送往汇编器。在标准的 UNIX 外壳中，连接两个程序的管道用 "|" 符号表示，例如："cpp file.c | cparse | cgen | as > file.o"。在这种情况下，外壳会创建四个独立的子进程，每一个都通过管道与它的前驱和后继相连。各个阶段可以并行运行，父进程则等待它们全部完成。

## 3.4　案例研究：进程间通信

出于与"用较简单的模块构建复杂应用程序"大体相同的理由，让每个应用程序专注于一项特定任务、再把这些应用程序组合成更复杂的结构，往往也是合理的做法。前面我们已经用 C 编译器举过一个例子，而操作系统的许多部分也是这样组织起来的。举例来说，与其让每个程序都必须懂得如何协调对打印机的访问，UNIX 干脆提供一个打印服务器——一个专门管理打印队列的程序。

要让这套做法行得通，我们需要一种让进程彼此通信的手段。三种被广泛使用的**进程间通信**（interprocess communication）形式是：

- **生产者—消费者。** 在这种模型中，程序被组织成可以接受其他程序输出作为自己输入的形式。通信是单向的：生产者只写，消费者只读。正如我们前面所讲的，这使得串联成为可能：一个消费者又可以作为另一个进程的生产者。UNIX 的成功在很大程度上要归功于它能以这种方式把许多不同的程序轻松地组合在一起。

- **客户—服务器。** 另一种模型是允许进程之间双向通信，客户—服务器计算就是如此。服务器实现某种专门的任务，例如管理打印队列或者管理显示器。客户向服务器发送请求，让它做某件事；操作完成后，服务器再把结果回复给客户。

- **文件系统。** 把程序连接起来的又一种方式是通过读写文件。一个文本编辑器可以导入由某个绘图程序生成的图片，而这个编辑器又可以写出一个 HTML 文件，供 Web 服务器读取，从而知道如何显示一个网页。与前两种模式的一个关键区别在于：通过文件系统进行的通信可以在**时间**上分离——写文件的一方不必与读文件的一方同时在运行。因此，数据需要持久地存放在磁盘或其他稳定存储上，而且数据需要有名字，以便你日后需要时能找到这个文件。

这三种模型无论是在单个系统上还是在网络上都得到了广泛使用。举例来说，Google 的 MapReduce 工具就是以生产者—消费者的方式在网络上工作的：map 函数的输出被送到运行 reduce 函数的那些机器上。Web 是客户—服务器计算的一个例子；许多企业和大学则运行集中式文件服务器，把一台计算机上的文本编辑器与运行在另一台计算机上的编译器连接起来。

由于持久存储、文件命名和分布式计算各自都是足以独立成章的复杂主题，我们把对这些主题的讨论推迟到后面的章节。这里聚焦于进程间通信，即两个进程在同一台机器上同时运行的情形。

### 3.4.1　生产者—消费者通信

<figure class="book-figure">
<img src="/figures/vol1/image00210.png" alt="图 3.9" loading="lazy">
<figcaption><span class="fig-label">图 3.9</span>生产者应用程序与消费者之间的进程间通信。生产者用 <code>write</code> 系统调用把数据放入缓冲区；消费者用 <code>read</code> 系统调用把数据从缓冲区中取出。</figcaption>
</figure>

图 3.9 说明了处于生产者—消费者关系中的两个进程如何经由操作系统进行通信。通过外壳，我们在生产者与消费者之间建立一条管道。一个进程一边计算、一边产出输出数据流，它就在管道上发出一串 `write` 系统调用，把数据送进内核。每次写入的数据量可以各不相同。只要内核缓冲区里还有空间，内核就把数据复制进缓冲区，然后立即返回生产者。

稍后某个时刻，操作系统会调度消费者进程运行。（在多核系统上，生产者和消费者可以同时运行。）消费者发出一串 `read` 调用。由于管道只不过是一个字节流，消费者可以用任意方便的块大小把数据读出来——消费者可以按 1 KB 的块读取，而生产者却是以 4 KB 的块写入的，反过来也一样。消费者每做一次 `read` 系统调用，就从内核缓冲区中取回紧接其后的下一块数据。消费者进程随后可以对自己的输入进行计算，把输出送往显示器、文件，或者下一个消费者。

内核缓冲区允许每个进程按自己的节奏运行，并不要求两个进程有等量的工作要做。如果生产者比消费者快，内核缓冲区就会被填满，当生产者试图向一个已满的缓冲区写入时，内核就让该进程停顿下来，直到有空间存放数据为止。反过来，如果消费者比生产者快，缓冲区就会被读空，下一次 `read` 请求也会停顿下来，直到生产者产出更多数据为止。

在 UNIX 中，生产者完成时关闭自己那一侧的管道，但内核中可能仍有数据在排队等待消费者。最终，消费者读完了最后的数据，此时 `read` 系统调用会返回一个"文件结束"标记。因此，对消费者而言，从管道读和从文件读并无区别。

用内核缓冲区来解耦生产者和消费者的执行，可以减少上下文切换的次数与开销。现代计算机大量使用硬件缓存来提升性能，但如果一个程序只运行很短一段时间就必须把处理器让给另一个任务，缓存就发挥不了作用。内核缓冲区让操作系统可以把每个进程运行得足够久，从而受益于缓存复用，而不必在每次系统调用时在生产者与消费者之间来回切换。

### 3.4.2　客户—服务器通信

<figure class="book-figure">
<img src="/figures/vol1/image00211.png" alt="图 3.10" loading="lazy">
<figcaption><span class="fig-label">图 3.10</span>客户进程与服务器进程之间的进程间通信。客户和服务器一旦建立连接，客户就把请求写进一个内核缓冲区来发送给服务器。服务器把请求从缓冲区中读出，并把结果写进另一个缓冲区返回，供客户读取。</figcaption>
</figure>

我们可以把上面的情形一般化，用来说明客户—服务器通信，如图 3.10 所示。这里不再只用一条管道，而是创建两条，每个方向一条。客户发出请求时，把数据写进其中一条管道，并从另一条管道读取应答。服务器的做法正好相反：它从第一条管道读取请求，执行被请求的动作（前提是客户拥有发出该请求的权限），然后把应答写到第二条管道上。

客户和服务器的代码见图 3.11。为了简化代码，我们假定请求和应答都是固定大小的。

<div class="code-cap"><span class="code-label">图 3.11</span>客户—服务器交互的示例代码。</div>

```c

 Client:
     char request[RequestSize];
     char reply[ReplySize]

     // ..compute..

     // Put the request into the buffer.

     // Send the buffer to the server.
     write(output, request, RequestSize);

     // Wait for response.
     read(input, reply, ReplySize);

     // ..compute..

 Server:
     char request[RequestSize];
     char reply[ReplySize];

     // Loop waiting for requests.
     while (1) {
         // Read incoming command.
         read(input, request, RequestSize);

         // Do operation.

         // Send result.
         write(output, reply, ReplySize);
     }

```

::: tip 精简客户—服务器通信
客户—服务器通信是许多系统中常见的模式，因此人们不免要问：怎样才能提高它的性能？第一步是认识到，客户和服务器都是先发出一次 `write`，紧接着再发出一次 `read`，以等待对方应答；以增加一次系统调用为代价，可以把这两个调用合并起来，从而省掉每一轮往返中的两次内核穿越。此外，客户总是需要等待服务器，因此让它把自己的处理器让给服务器代码去运行是合理的，这可以缩短延迟。微软在 20 世纪 90 年代初把 Windows 改为微内核设计时（本章稍后会解释），就为 Windows 加入了这种优化。然而，正如我们前面提到的，现代计算机体系结构大量依赖缓存，因此要想让这种做法奏效，客户和服务器的代码与数据必须能同时待在缓存里。我们将在后面某一章讨论实现这一点的机制。

我们还可以把这种精简再往前推进一步。在多核系统上，客户和服务器很可能各自拥有一个处理器。如果内核建立起一块共享内存区，使客户和服务器都能访问、而其他进程都不能访问，那么客户和服务器就可以（安全地）以内存系统所允许的最快速度来回传递请求和应答，全程不必进入内核、也不必放弃各自的处理器。
:::

我们经常希望允许多个客户与同一台服务器对话。举例来说，管理打印队列的服务器只有一台，但想要打印的进程却可以有很多。为此，服务器使用 `select` 系统调用来识别出包含请求的那条管道，如图 3.12 所示。客户的代码则无须改动。

<div class="code-cap"><span class="code-label">图 3.12</span>与多个客户通信的服务器代码。</div>

```c

 Server:
     char request[RequestSize];
     char reply[ReplySize];
     FileDescriptor clientInput[NumClients];
     FileDescriptor clientOutput[NumClients];

     // Loop waiting for a request from any client.
     while (fd = select(clientInput, NumClients) {

         // Read incoming command from a specific client.
         read(clientInput[fd], request, RequestSize);

         // Do operation.

         // Send result.
         write(clientOutput[fd], reply, ReplySize);
     }

```

## 3.5　操作系统结构

我们在本章开头列出了用户和应用程序需要从操作系统获得的功能。我们已经看到，通过精心设计系统调用接口，可以把操作系统的一部分工作卸载给用户程序，例如交给外壳或者打印服务器。

在本章余下的部分，我们要问的是：操作系统剩下的那些部分应当如何组织。操作系统内部各模块之间存在许多依赖关系，这些模块之间的交互也往往相当频繁：

- 操作系统的许多部分都依赖同步原语，用以协调内核中对共享数据结构的访问。

- 虚拟内存系统依赖底层的地址转换硬件支持，而这种支持是特定于某一种处理器体系结构的。

- 文件系统和虚拟内存系统共享同一个物理内存块池。它们也都要依赖磁盘设备驱动程序。

- 如果磁盘在物理上位于另一台机器上，文件系统就可能依赖网络协议栈。

这使得操作系统设计者不得不在一个根本性的权衡中反复掂量：把功能集中到内核里，性能得以提升，也更容易让内核模块之间实现紧密集成；然而，由此得到的系统灵活性更差、更难改动，也更难适应用户或应用程序的需求。我们通过描述操作系统体系结构的几种可选方案来讨论这些权衡。

### 3.5.1　宏内核

<figure class="book-figure">
<img src="/figures/vol1/image00212.png" alt="图 3.13" loading="lazy">
<figcaption><span class="fig-label">图 3.13</span>在宏内核操作系统中，操作系统的大部分功能都被链接在一起，置于内核之内。内核模块直接调用其他内核模块来完成所需的功能。例如，虚拟内存系统会用到缓冲区管理、同步机制以及硬件抽象层。</figcaption>
</figure>

几乎所有被广泛使用的商用操作系统，例如 Windows、MacOS 和 Linux，在内核体系结构上都采取了类似的方案——宏内核设计。如图 3.13 所示，在**宏内核**（monolithic kernel）中，操作系统的大部分功能都运行在操作系统内核之内。说实话，这个术语多少有点名不副实，因为即便在所谓的宏内核系统中，用户心目中"操作系统"的很大一部分也常常运行在内核之外：要么作为外壳这样的实用程序，要么存在于系统库中，例如管理用户界面的那些库。

在宏内核内部，操作系统设计者可以自由地开发出任何合理的模块间接口，因此这些内部结构在不同操作系统之间差异相当大。不过，各系统之间还是浮现出两个共同的主题：为了提高可移植性，几乎所有现代操作系统都同时具备硬件抽象层和动态加载的设备驱动程序。

#### 硬件抽象层

操作系统的一项关键目标是能够在多种多样的硬件平台之间移植。要做到这一点，尤其是在宏内核系统中，需要精心设计**硬件抽象层**。硬件抽象层（HAL）是内核中面向机器配置和处理器特定操作的一套可移植接口。举例来说，在同一个处理器系列（例如 Intel x86）内部，不同的计算机制造商会需要各自不同的机器相关代码来配置和管理中断与硬件定时器。

能够跨处理器系列移植的操作系统，比如在 ARM 与 x86 之间、或者在 32 位与 64 位 x86 之间，会需要用于进程和线程上下文切换的处理器特定代码。中断、处理器异常和系统调用**陷阱**的处理同样是处理器相关的；所有系统都有这些功能，但具体实现各不相同。我们将在第 8 章看到，各种机器在管理虚拟地址空间的体系结构上差异相当大；大多数内核都在这些机器相关的例程之上提供可移植的抽象，例如把虚拟地址转换为物理地址，或者在应用程序内存与内核内存之间来回复制数据。

有了定义良好的硬件抽象层，操作系统的绝大部分就与机器和处理器无关了。于是，把操作系统移植到一台新计算机上，就只是为这些底层的 HAL 例程编写新的实现、再重新链接一遍的事情。

::: tip Windows 中的硬件抽象层
举一个具体的例子，Windows 为提高可移植性采取了两管齐下的策略。为了让同一个 Windows 内核二进制文件能用于不同厂商制造的个人计算机，内核在引导时与一组专门针对每种硬件配置编写的库例程动态链接。这就把内核与主板硬件的具体细节隔离开来。

Windows 还运行在若干种不同的处理器体系结构上。通常，每种处理器都会生成各自的内核二进制文件，其中包含所需的处理器特定代码；有时也会采用条件执行的办法，让一个内核二进制文件能在关系密切的几种处理器设计之间共享。
:::

#### 动态安装的设备驱动程序

类似的考量催生了能够轻松容纳种类繁多的物理 I/O 设备的操作系统。虽然当今广泛使用的指令集体系结构只有寥寥几种，但物理 I/O 设备的类型却多得惊人，由数量众多的公司制造。设备的硬件接口、以及管理设备的硬件芯片组，都呈现出高度的多样性。最近的一项调查发现，Linux 内核中大约 70% 的代码是设备相关的软件。

为了让操作系统内核的其余部分保持可移植，我们希望把操作系统源代码与每种设备的具体细节解耦开来。举例来说，假设某家制造商推出了一款新的打印机——操作系统厂商需要采取哪些步骤来适应这一变化？

如今被广泛采用的关键创新是**动态可加载设备驱动程序**。动态可加载设备驱动程序是用于管理某个特定设备、接口或芯片组的软件，它在内核开始运行之后才被加入操作系统内核，用以处理某台机器上实际存在的设备。设备制造商通常使用内核所支持的标准接口来提供驱动程序代码。操作系统内核每当需要向设备读写数据时，就调用驱动程序。

操作系统引导时只带少量设备驱动程序——例如磁盘的驱动程序（用于把操作系统二进制文件读进内存）。对于物理连接到计算机上的设备，计算机制造商把这些驱动程序打包进一个文件，与引导加载程序存放在一起。操作系统启动时，会查询 I/O 总线以了解计算机上连接了哪些设备，然后从磁盘上的这个文件中加载相应的驱动程序。最后，对于任何网络连接型设备（例如网络打印机），操作系统可以通过因特网加载它们的驱动程序。

动态可加载设备驱动程序在解决一个问题的同时，又带来了另一个问题。设备驱动程序中的错误可能破坏操作系统内核和应用程序的数据结构；就像普通程序一样，这类错误未必会立刻暴露，因此用户可能并不知道自己的数据正在被悄悄改动。更糟的是，恶意攻击者可以利用设备驱动程序把计算机病毒引入操作系统内核，从而悄无声息地控制整台计算机。近期的研究发现，所有系统崩溃中有 90% 是由设备驱动程序中的缺陷造成的，而不是操作系统本身的问题。

操作系统开发者采取了五种办法来应对这个问题：

- **代码审查。** 操作系统厂商通常要求所有设备驱动程序代码在获准进入内核之前，必须事先提交接受审查和测试。

- **缺陷追踪。** 每次系统崩溃之后，操作系统可以收集有关系统配置和当前内核栈的信息，并把这些信息送回一个中央数据库用于分析。微软就在大规模地这样做。由于装机量数以亿计，即便故障率很低，每天也能产生数以百万计的缺陷报告。许多崩溃发生在设备驱动程序内部，但即便不是如此，有时也能追查下去。举例来说，如果故障与某个特定设备驱动程序的存在相关，或者在该驱动程序的新版本发布之后数量上升，那就可能指示出问题的根源。

- **用户级设备驱动程序。** 苹果和微软都大力鼓励新的设备驱动程序运行在用户级，而不是内核中。每个设备驱动程序运行在一个独立的用户级进程里，通过系统调用来操纵物理设备。这样一来，有缺陷的驱动程序只能影响它自己的内部数据结构，而不会波及操作系统内核的其他部分；如果设备驱动程序崩溃，内核可以轻易地重启它。尽管用户级设备驱动程序正变得越来越普遍，但把现有的设备驱动程序移植到用户级运行可能颇为费时。遗憾的是，现存的大量设备驱动程序代码会直接访问内核内部的数据结构；为这些驱动程序划出一条边界已被证明相当困难。当然，随着智能手机和平板电脑这类全新的硬件与操作系统平台被开发出来，支持遗留驱动程序的问题就不那么突出了。

- **虚拟机设备驱动程序。** 为了处理遗留设备驱动程序，一种已经获得一定认可的做法是：把设备驱动程序代码运行在虚拟机内的一个客户操作系统中，如图 3.14 所示。客户操作系统加载这些设备驱动程序，就像自己直接运行在真实硬件上一样；但当这些设备试图访问物理硬件时，底层的虚拟机监视器会重新取得控制权，以确保安全。设备驱动程序仍然可能有缺陷，但它们只能破坏客户操作系统，而不能破坏运行在底层虚拟机监视器上的其他应用程序。

- **驱动程序沙箱。** 用户级设备驱动程序和虚拟机驱动程序都还面临一个进一步的挑战，那就是性能。有些设备驱动程序需要与硬件以及内核的其余部分频繁交互。一些研究者提出，让设备驱动程序运行在内核中属于它们自己的受限执行环境里。这就需要轻量级的沙箱技术，我们将在第 8 章末尾回到这个话题。

### 3.5.2　微内核

与宏内核方案相对的另一种选择，是把尽可能多的操作系统功能放到一个或多个用户级服务器中运行。大多数操作系统上的窗口管理器就是这样工作的：各个应用程序通过向窗口管理器发送请求，在属于自己的那部分屏幕上绘制图元。窗口管理器对屏幕上的每个像素裁定哪个应用程序窗口在前、哪个在后，然后把结果渲染出来。如果系统中配有硬件图形加速器，窗口管理器就可以用它来更快地渲染图元。有些系统已经把操作系统的其他部分也搬进了用户级服务器：网络协议栈、文件系统、设备驱动程序，等等。

宏内核设计与微内核设计之间的差别，对应用程序员来说往往是透明的。服务所处的位置可以隐藏在一个用户级库中——调用先进入该库，由库把这些请求要么转化为系统调用，要么转化为通过管道对服务器的读写。服务器的位置也可以隐藏在内核内部——应用程序调用内核，就好像该服务是由内核实现的一样，但内核实际上把请求重新打包成一条管道，供服务器读取。

微内核设计为操作系统开发者带来了相当大的好处，因为用户级服务比内核代码更容易模块化、也更容易调试。然而，除了可能带来可靠性上的提升之外，微内核对最终用户几乎没有什么看得见的好处，而且由于在应用程序与它所需的服务之间插入了额外的步骤，还可能拖慢整体性能。因此，在实践中，大多数系统采取一种混合模型：一部分操作系统服务运行在用户级，另一部分放在内核中，具体取舍取决于代码复杂度与性能之间的权衡。

## 3.6　小结与未来方向

在本章中，我们看到了应用程序如何使用系统调用来创建和管理进程、执行 I/O，以及与其他进程通信。每个操作系统都有自己独特的系统调用接口；即便要把其中某一个接口深入地讲清楚，也超出了本书的范围。本章之所以聚焦于 UNIX 接口的一部分内容，是因为它既紧凑又强大。UNIX 接口的一个关键之处在于：创建进程（用 `fork`）与在该进程中开始运行一个程序（用 `exec`）是分开的；另一个关键特征是它用内核缓冲区来解耦经由内核进行的读写。

操作系统利用系统调用接口向应用程序提供服务，也用它来辅助操作系统自身的内部构造。当今几乎所有通用计算机系统都有一个用户级外壳和/或窗口管理器，可以代表用户启动和管理应用程序。许多系统还把操作系统的一部分实现为通过内核管道访问的用户级服务。

正如我们所指出的，一个趋势是应用程序本身正在变成小型操作系统，具备多用户、资源共享与分配、不可信的第三方代码、处理器和内存管理等等。Windows 和 UNIX 的系统调用接口在设计时并没有考虑到这一点，一个有意思的问题是：它们将如何演进，以适应这种强大的"元应用程序"的未来。

除了我们在上一章末尾描述的细粒度沙箱与进程创建之外，还有一个趋势是重构系统调用接口，使资源分配决策变得明确、并对应用程序可见。传统上，操作系统在应用程序毫无察觉的情况下做出资源分配决策——何时调度一个进程或一个线程、给某个应用程序分配多少内存、在何时何地存放它的磁盘块、何时发送它的网络数据包——其目标是改善最终用户和整个系统的性能。应用程序并不知道自己拥有多少资源，看上去像是自己在独自运行，被隔离在属于自己的（虚拟）机器上。

当然，现实往往大相径庭。另一种模型是：操作系统在应用程序之间划分资源，然后让每个应用程序自行决定怎样最好地使用这些资源。可以把这看作一种联邦制。如果操作系统和应用程序都是各自做资源分配的政府，那么稍有不慎就会互相掣肘。举个简单的例子，考虑垃圾回收器是如何工作的：它假定自己管理着固定数量的内存。然而，随着其他应用程序启动或停止，它可能获得或失去内存；如果操作系统以透明的方式进行这种重新分配，垃圾回收器就根本没有希望去适应。我们会在操作系统设计的许多不同领域看到同样的设计模式。
