# 第 1 章　引论

<div class="chap-en">Introduction</div>

<blockquote class="epigraph">我在幼儿园里学到了真正需要知道的一切。——<strong>罗伯特·富尔格姆（Robert Fulgham）</strong></blockquote>

我们如何构建可靠、可移植、高效且安全的计算机系统？一个关键组成部分是计算机的**操作系统**（operating system）——即管理计算机资源的软件。

先说坏消息：操作系统的概念是计算机科学中最复杂的概念之一。一个现代的通用操作系统可以超过 5000 万行代码，换句话说，比这本教科书长一千多倍。新的操作系统还在不断涌现：如果你使用电子书阅读器、平板电脑或智能手机，就有一个操作系统在管理你的设备。鉴于这种固有的复杂性，我们把注意力集中在每一位计算机科学家都应该掌握的核心概念上。

再说好消息：操作系统的概念同时也是计算机科学中最容易亲近的概念之一。本书的许多话题对你来说都会显得似曾相识——如果你曾经试图同时做两件事，或在杂货店排错了队，或想防止室友或兄弟姐妹乱动你的东西，或成功策划过一次愚人节恶作剧。这些活动中的每一项在操作系统中都有对应的原型。正是这种熟悉感让我们有信心在一本教科书中讲清楚操作系统的工作原理。我们对读者唯一的要求，是对计算机基本工作原理有初步了解，并且能够读懂伪代码。

我们相信，对于任何有兴趣构建现代计算机系统的学生来说，理解操作系统的工作原理都是必不可少的。当然，每个使用计算机或智能手机——甚至现代烤面包机——的人都在使用操作系统，因此理解操作系统的功能对大多数计算机科学家都有用。本书的目标则要深入得多：解释那些我们每天都在依赖却从未察觉的操作系统内部机制。

软件工程师在构建其他复杂系统时，使用的许多技术与设计模式和操作系统中的如出一辙。无论你的目标是钻研操作系统内核的内部实现，还是为云计算、安全的网页浏览器、游戏主机、图形用户界面、媒体播放器、数据库或多核软件开发下一代软件——可靠、可移植、高效且安全的软件所需要的概念与抽象都是大体相同的。根据我们的经验，学习这些概念的最好方式，就是研究它们在操作系统中是如何被使用的；我们也希望你能把它们应用到远比操作系统广泛的各类计算机系统中去。

作为开始，请看图 1.1 中的 Web 服务器。它的行为简单得出奇：它从网络接收一个包含网页名称的数据包，即一个 HTTP GET 请求；Web 服务器解析这个数据包，从磁盘读取文件，再把文件的内容通过网络发送回用户的机器。

操作系统的一部分职责，就是让编写像 Web 服务器这样的应用变得容易。但再稍微深究一下，这个简单的故事在解答问题的同时，又引出了同样多的问题：

- 许多 Web 请求既涉及数据也涉及计算。例如，Google 首页只呈现一个简单的文本框，但在这个框中输入的每一次搜索查询，都要访问分布在许多机器上的数据。为了让软件易于管理，Web 服务器常常会调用辅助应用（helper application）来承担实际的搜索功能。主 Web 服务器必须能够与这些辅助应用通信，这一切才能运转起来。那么，操作系统如何让多个应用彼此通信？

- 如果两个用户（或者一百万个用户）同时向服务器请求一个网页会怎样？一种简单的做法是逐个处理请求。但如果某个请求耗时很长，其他所有请求都必须等待它完成。一种更快但更复杂的方案是**多任务处理**（multitask）：同时周旋于多个请求的处理之间。在现代多核计算机上，多任务处理尤其重要，因为每个处理器可以同时处理不同的请求。那么，操作系统如何让应用同时做多件事？

- 为了获得更好的性能，Web 服务器可能想保存最近请求过的页面的副本，有时称为**缓存**（cache）。这样，当多个用户请求同一个页面时，服务器对后续请求可以直接从缓存更快地做出响应，而不必每次从头开始。这就要求 Web 服务器对缓存的数据结构的访问进行协调，或者说**同步**（synchronize）——可能同时有成千上万个 Web 请求在访问。那么，操作系统如何同步应用对共享数据的访问？

- 为了定制和丰富用户体验，Web 服务器通常会在网页内容之外向客户端发送脚本代码。但这意味着，点击一个链接就可能让别人的代码在你的计算机上运行。那么，客户端操作系统如何保护自己不被悄悄嵌入脚本代码中的计算机病毒所侵害？

- 假设网站管理员用编辑器更新了网页，Web 服务器必须能够读取这个文件。那么，操作系统如何把字节存储到磁盘上，才能让 Web 服务器找到并读取它们？

- 更进一步，管理员可能希望对网站进行一组一致的修改，使得嵌入的链接不会（哪怕只是暂时地）悬空指向不存在的页面。那么，操作系统如何让用户对网站做出一组修改，使得请求要么看到旧页面、要么看到新页面，而不会看到两者的混合？

- 当客户端浏览器与 Web 服务器的运行速度不一致时会发生什么？如果服务器向客户端发送网页的速度快于客户端把页面呈现在屏幕上的速度，那么文件内容在此期间存放在哪里？操作系统能否把客户端与服务器解耦，让二者各自按自己的速度运行而互不拖累？

- 随着 Web 服务器的负载增长，管理员可能需要迁移到更强的硬件上：更多内存、更多处理器、更快的网络设备和更快的磁盘。为了利用新硬件，Web 服务器是否每次都得重写？还是可以写成与硬件无关的形式？操作系统又如何——它是否必须为每一件新硬件重写？

我们可以继续列下去，但你应该已经领会到意思了。本书将帮助你理解这些问题以及更多问题的答案。

## 1.1　什么是操作系统？

**操作系统**（operating system, OS）是这样一层软件：它为计算机的用户及其应用管理计算机的资源。操作系统运行在种类繁多的计算机系统上。它们可能对最终用户完全不可见，控制着嵌入式设备——烤面包机、游戏机，以及现代汽车和飞机内部的众多计算机。它们对智能手机、桌面电脑和服务器等更通用的系统同样不可或缺。

我们的讨论将聚焦于通用操作系统，因为它们所需的技术是嵌入式系统所需技术的一个超集。为通用计算开发的操作系统技术，如今正越来越多地迁移到嵌入式领域。例如，早期的移动电话只有简单的操作系统，用来管理硬件并运行少数几个原始的应用。今天，智能手机——能够运行独立第三方应用的手机——已成为移动电话业务中增长最快的部分。这些设备需要完善得多的操作系统，具备精密的资源管理、多任务处理、安全性以及故障隔离能力。

类似地，汽车正日益由软件控制，由此带来一连串操作系统层面的问题。任何人都能为你的汽车编写软件吗？如果软件在你行驶在高速公路上时出了故障怎么办？汽车的操作系统会被计算机病毒劫持吗？这听起来也许牵强，但研究人员最近演示了他们如何通过一个被攻破的车载收音机，把计算机病毒植入车载计算机，从而远程关闭汽车的刹车系统。本书的一个目标，就是解释如何在各种情境下构建更可靠、更安全的计算机系统。

</figure>

+ **裁判。** 操作系统管理同一台物理机器上运行的多个不同应用之间共享的资源。例如，操作系统可以停止一个程序并启动另一个。操作系统把应用彼此隔离开，使得一个应用中的缺陷不会破坏同一台机器上运行的其他应用。操作系统还必须保护自身和其他应用免受恶意计算机病毒的侵害。而且，由于应用共享物理资源，操作系统需要决定哪个应用在何时获得哪些资源。

+ **魔术师。** 操作系统提供对物理硬件的抽象，以简化应用的设计。要写一个“Hello world!”程序，你不需要（也不想要！）考虑系统有多少物理内存，或者还有多少其他程序在共享计算机的资源。操作系统提供的幻象是：尽管物理内存有限，你却拥有近乎无限的内存；同样，它们还营造出每个程序独占计算机处理器的假象。显然，实际情况大相径庭！这些幻象让你编写应用时无需关心系统的物理内存有多少、物理处理器有几个。由于应用是面向更高层抽象编写的，操作系统可以悄悄改变分配给每个应用的资源数量。

+ **粘合剂。** 操作系统提供一组公共服务，方便应用之间的共享。这样一来，剪切和粘贴在整个系统上行为一致；一个应用写下的文件可以被另一个应用读取。许多操作系统还提供公共的用户界面例程，使应用拥有一致的“外观与感觉”。也许最重要的是，操作系统提供了一层把应用与硬件输入/输出（I/O）设备隔开的抽象，使应用可以独立于某台具体计算机上实际使用的键盘、鼠标和磁盘驱动器来编写。

接下来我们更详细地讨论这三种角色。

### 1.1.1　资源共享：作为裁判的操作系统

共享是计算机大多数用法的核心。此刻，我的笔记本电脑正运行着浏览器、播客库、文本编辑器、电子邮件程序、文档查看器和电子报纸。操作系统必须设法把这些活动彼此分开，同时在其他程序没有运行时让每个程序都能用上机器的全部能力。至少，当一个程序停止运行时，操作系统应当让我能运行另一个程序。更好的做法是，操作系统能让多个应用同时运行，这样我就可以在下载系统安全补丁的同时阅读电子邮件。

即便是单个应用，也可以一次执行多项任务。例如，Web 服务器如果并发地处理多个请求，而不是等前一个完成再开始下一个，其响应能力就会提高。浏览器也是如此——能在页面其余部分还在传输时就开始渲染，它会显得更加流畅。在多处理器上，并行应用内部的计算可以拆分成若干可独立运行的单元，从而更快地执行。操作系统本身就是为一次执行多项任务而编写的软件的一个例子。正如我们将在全书各处展示的，操作系统是它自身抽象的用户。

共享给操作系统带来了几个挑战：

- **资源分配。** 操作系统必须让所有同时进行的活动互不干扰，并按需为每个活动分配资源。一台计算机通常只有少数几个处理器，以及有限的内存、网络带宽和磁盘空间。当同时有多项任务要做时，操作系统应该如何决定给每项任务多少资源？资源分配方式上看似微不足道的差异，就可能影响用户感受到的性能。正如我们将在第 9 章看到的，给某个程序分配太少内存的操作系统，不仅拖慢那个程序，还常常拖慢其他应用。为了说明在物理机器上执行与在操作系统提供的抽象机器上执行的区别，不妨想想：如果一个应用执行了一个无限循环 `while (true) {; }`，会发生什么？如果程序直接运行在裸硬件上，这段代码会让计算机死锁，对用户输入完全失去响应。而如果操作系统确保每个程序都分得计算机资源的一份切片，那么某个具体应用可能卡死，但其他程序仍能不受阻碍地继续运行；此外，用户还可以要求操作系统强制退出那个陷入死循环的程序。

- **隔离。** 一个应用中的错误不应影响其他应用，甚至不应影响操作系统本身。这称为**故障隔离**（fault isolation）。任何上过计算机科学导论课的人都知道，一个能保护自身和其他应用免受程序员缺陷伤害的操作系统多么有价值。如果一个程序中的错误会破坏其他应用中的数据结构，调试将变得困难得多。同样，下载并安装一个屏幕保护程序或其他应用，不应该让无关的程序崩溃，不应该为恶意攻击者悄悄安装计算机病毒提供可乘之机，也不应该让一个用户在未经许可的情况下访问或篡改另一个用户的数据。故障隔离要求把应用的行为限制在低于底层硬件全部能力的水准上。否则，任何从网上下载的应用，或任何嵌入网页的脚本，都可能完全控制这台机器。任何应用都可以在操作系统中植入间谍软件，记录你敲下的每一个按键，或者窃取你访问的每一个网站的密码。没有操作系统提供的故障隔离，任何程序中的任何错误都可能不可挽回地毁掉磁盘。容易出错或心怀恶意的应用可能造成各种各样的破坏。

- **通信。** 隔离的另一面，是不同应用、不同用户之间需要通信。例如，一个网站可能由一组相互协作的应用共同实现：一个负责挑选广告，一个负责缓存最近的结果，另一个负责从磁盘读取并合并数据，还有几个协同扫描 Web 以寻找待索引的新内容。要让这一切运转起来，这些程序必须彼此通信。如果操作系统阻止缺陷、恶意用户和应用影响其他用户及其应用，那它又如何支持共享结果的通信呢？在设立边界的同时，操作系统还必须允许在需要时以受到严格管控的方式跨越这些边界。

作为裁判，操作系统有点像一位格外有耐心的幼儿园老师。它权衡需求、分开冲突、促成共享。不应允许任何一个用户垄断系统资源，或在未经许可的情况下访问、破坏另一个用户的文件；一个有缺陷的应用不应能搞垮操作系统或其他不相干的应用；然而，应用之间又必须协同工作。维护并平衡这些关注点，正是操作系统的核心角色。

### 1.1.2　掩盖局限：作为魔术师的操作系统

操作系统的第二个重要角色，是掩盖计算机硬件固有的限制。物理约束限制了硬件资源——一台计算机只有有限数量的处理器、有限的物理内存、网络带宽和磁盘。而且，由于操作系统必须决定如何在各个时刻运行的应用之间分配这些固定资源，同一个应用即使运行在相同的硬件上，在不同时刻可获得的资源也可能不同。虽然有些应用的设计就是要利用计算机特定的硬件配置和资源分配，但大多数程序员更愿意使用更高层次的抽象。

**虚拟化**（virtualization）为应用提供了一种并不实际存在的资源的幻象。例如，操作系统可以提供这样的抽象：每个应用都拥有一台专属的处理器，尽管在物理层面可能只有一个处理器，由计算机上运行的所有应用共享。

只要硬件和操作系统支持得当，大多数物理资源都可以被虚拟化。例如，硬件只提供少量有限的内存，而操作系统向应用提供近乎无限的**虚拟内存**（virtual memory）幻象。无线网络会丢失或损坏数据包，操作系统掩盖这些故障，提供可靠服务的幻象。在物理层面，磁盘和闪存支持按块读写，块的大小取决于物理设备特性，并通过设备相关的块号来寻址；而大多数程序员更愿意处理按名称组织到层次目录中的、按字节寻址的文件。甚至连处理器的类型也可以被虚拟化，让同一个未经修改的应用能够运行在智能手机、平板电脑和笔记本电脑上。

再前进一步，有些操作系统把整台计算机都虚拟化了，让一个操作系统作为应用运行在另一个操作系统之上（见图 1.4）。这称为创建**虚拟机**（virtual machine）。运行在虚拟机中的操作系统称为**客户操作系统**（guest operating system），它以为自己运行在一台真实的物理机器上，但这只是底下那个真正的操作系统呈现出来的幻象。

虚拟机的一个好处是应用可移植性。如果某个程序只能运行在操作系统的旧版本上，它可以借助新系统上运行的虚拟机继续工作——虚拟机在新系统之上承载旧操作系统，并在其上运行该应用。虚拟机还有助于调试。如果一个操作系统能作为应用运行，那么它的开发者就可以像调试应用那样设置断点、停下内核、单步执行自己的代码。

在本书中，我们将讨论操作系统用来实现这些幻象（以及其他幻象）的技术。在每一种情况下，操作系统提供的编程抽象都比底层硬件提供的更便利、更灵活。

### 1.1.3　提供公共服务：作为粘合剂的操作系统

操作系统扮演的第三个关键角色，是向应用提供一组通用的标准服务，以简化并规范应用的设计。本章前面描述的 Web 服务器就是一例。操作系统隐藏了网络设备和磁盘设备工作方式的细节，提供一个更简单的抽象——收发可靠的字节流、读写按名称组织的文件。这让 Web 服务器可以专注于它的核心任务——解析并响应传入的请求——而不必操心把数据格式化成一个个网络分组和磁盘块。

操作系统之所以要提供公共服务，而不是让每个应用各写一套，一个重要原因就是便于应用之间共享。Web 服务器必须能够读取文本编辑器写下的文件。要让应用共享文件，文件就必须以标准格式存储，并有一套标准的文件目录管理体系。大多数操作系统还提供了应用之间传递消息和共享内存的标准方式。

操作系统应提供哪些服务，往往需要斟酌取舍。例如，计算机可能装配了五花八门的设备：不同的图形协处理器和像素格式，不同的网络接口（WiFi、以太网、蓝牙），不同的磁盘驱动器（SCSI、IDE），不同的设备接口（USB、FireWire），以及不同的传感器（GPS、加速度计），更别提每一种又有不同版本。大多数应用只需使用操作系统提供的通用接口，就可以忽略这些差异。但对另一些应用（比如数据库）来说，具体是哪块磁盘驱动器可能相当要紧。对于能在更高抽象层次上运作的应用，操作系统充当互操作层，让应用与设备得以各自独立地演进。

大多数现代操作系统的另一项标准服务是图形用户界面库。微软和苹果的操作系统都提供一组标准的用户界面控件。这为用户带来一致的“外观与感觉”，使高频操作——如下拉菜单、“剪切”和“粘贴”命令——在各个应用中得到一致的处理。

操作系统中的大部分代码都在实现这些公共服务。然而，操作系统复杂性的很大一部分来自资源共享和对硬件限制的掩盖。由于公共服务代码建立在另外两种角色所提供的抽象之上，本书将主要聚焦于作为裁判和作为魔术师的操作系统。

### 1.1.4　操作系统设计模式

操作系统所应对的挑战并非独一无二——它们出现在许多不同的计算机领域。许多复杂的软件系统拥有多个用户，运行第三方开发者编写的程序，并且/或者需要协调大量同时进行的活动。这些都会引出资源分配、故障隔离、通信、物理硬件抽象，以及如何为软件开发者提供一套好用的公共服务等问题。不仅挑战相同，解决方案往往也相同：这些系统使用的许多设计模式和技术，正是本书所要描述的。

- **Web 浏览器**（图 1.6），如 Chrome、Internet Explorer、Firefox 和 Safari，扮演着与操作系统类似的角色。浏览器加载并显示网页，但正如我们前面提到的，许多网页内嵌了浏览器必须执行的脚本程序。这些脚本可能有缺陷，也可能怀有恶意；黑客已经利用它们接管了数量庞大的家用计算机。像操作系统一样，浏览器必须把用户、其他网站乃至浏览器自身，与这些脚本的错误或恶意行为隔离开。类似地，大多数浏览器都有支持扩展的插件架构，这些扩展同样必须被隔离，以防造成危害。**裁判。** 当用户同时打开多个标签页、每个标签页都运行着来自不同网站的脚本时，浏览器如何保证响应能力？我们如何限制网页脚本和插件，防止有缺陷的脚本搞垮浏览器、防止恶意脚本访问敏感的用户数据？**魔术师。** 许多 Web 服务在地理上分布部署，以改善用户体验。这不仅让服务器离用户更近，而且当某台服务器崩溃或其网络连接出现问题时，浏览器可以连接到另一个站点。用户在多数情况下察觉不到差别，即便他正在更新购物车或网页表单。浏览器如何让服务器的变化对用户透明？**粘合剂。** 浏览器如何为脚本提供一个跨操作系统、跨硬件平台都行为一致的可移植执行环境？

- **媒体播放器**，如 Flash 和 Silverlight，常常以浏览器插件的形式发布，但它们本身也为脚本程序提供执行环境。因此，这些系统面临许多与浏览器以及它们所运行的操作系统相同的问题：隔离有缺陷或恶意的代码、并发的后台与前台任务，以及插件架构。**裁判。** 媒体播放器常因暴露于某种新的恶意攻击而登上新闻。媒体播放器应当如何对恶意或有缺陷的脚本进行沙箱隔离，以防它们破坏宿主机？**魔术师。** 媒体应用往往既计算密集又高度交互。它们如何协调前台与后台活动以保持响应能力？**粘合剂。** 高性能图形硬件随着电子游戏市场的需求迅速演进。媒体播放器如何提供一组标准 API，让脚本能在多种多样的图形加速器上工作？

- **多人游戏**常常带有可扩展性 API，允许第三方软件厂商以可观的方式扩展游戏。这些扩展本身往往就是一个小型游戏，但同时又必须防止它们破坏游戏的整体规则。**裁判。** 许多游戏试图把工作下放到客户端机器上，以减轻服务器负载、提高响应速度，但这也让游戏面临玩家安装专用扩展以谋取不正当优势的威胁。游戏设计者如何为扩展和玩家设定限制，以保证公平竞技？**魔术师。** 如果游戏中的对象分布在客户端与服务器两端，这一区别对扩展代码是否可见，还是接口处于更高层次？**粘合剂。** 最成功的游戏拥有大量扩展；游戏设计者应当如何搭建他们的 API，才能更容易地培育出一个开发者社区？

- **多用户数据库系统**（图 1.7），如 Oracle 和微软的 SQL Server，允许大型组织存储、查询和更新大型数据集，例如亚马逊或沃尔玛有史以来每一笔采购的详细记录。大规模数据分析能极大优化业务运营，但也因此，数据库面临许多与操作系统相同的挑战。它们被位于许多不同地点的许多不同用户同时访问，因此必须在不同的用户请求之间分配资源，隔离对共享数据的并发更新，并确保数据一致地存储在磁盘上。事实上，我们在第 14 章讨论的几种技术，最初就是为数据库系统开发的。**裁判。** 数据库的各个用户之间应如何分配资源？数据库如何实施数据隐私保护，使只有经过授权的用户才能访问相关数据？**魔术师。** 数据库如何掩盖机器故障，使得无论故障何时发生，数据总是被一致地存储？**粘合剂。** 哪些公共服务能让数据库应用的开发更轻松？

- **并行应用**是为利用单台计算机上的多个处理器而设计的程序。每个应用把工作划分到固定数量的处理器上，并且必须确保对共享数据结构的访问得到协调以维持一致性。有些并行程序直接使用底层操作系统提供的服务，另一些则需要细致控制工作到处理器的分配才能获得良好性能。这些系统在操作系统之上插入一个运行时系统来管理用户级并行，实质上是在底层操作系统之上再构建一个小型操作系统。**裁判。** 当要执行的任务多于处理器时，运行时系统如何决定先执行哪些任务？**魔术师。** 运行时系统如何向程序员隐藏硬件的物理细节，比如处理器的数量或处理器间的通信延迟？**粘合剂。** 高并发数据结构可以让人更容易写出高效的并行程序；我们要如何对树、哈希表和链表编程，才能让它们被多个处理器同时使用？

这些系统中的许多都使用与操作系统相同的技术和设计模式。研究操作系统是理解这些其他系统如何工作的绝佳途径。少数情况下，达成同一目标会采用不同的机制，但即便如此，边界也是模糊的。例如，浏览器常常使用编译期检查来防止脚本取得对浏览器的控制，而大多数操作系统使用基于硬件的保护来限制应用程序接管机器。不过近年来，一些智能手机操作系统已经开始采用与浏览器相同的编译期技术来防范恶意移动应用；反过来，一些浏览器也开始借助操作系统基于硬件的保护来增强它们提供的隔离。

为了避免把讨论铺得太开，本书聚焦于操作系统是如何工作的。正如在精通第一门编程语言之后再学第二门会容易得多，在一种情境中看清操作系统原理如何运用之后，再去学习它们在其他场景中的应用也会更好。不过，我们希望也期待你能把本书中的概念应用到比操作系统设计更广阔的天地。

## 1.2　操作系统的评价

在明确了操作系统的职责之后，我们该如何在各种备选设计之间做出选择？下面讨论评价操作系统的几条理想标准：

- **可靠性与可用性**（reliability and availability）。操作系统是否做到了你希望它做的事？

- **安全性**（security）。操作系统会不会被攻击者破坏？

- **可移植性**（portability）。操作系统是否容易迁移到新的硬件平台？

- **性能**（performance）。用户界面是否响应及时，还是说操作系统带来了过多的开销？

- **采用率**（adoption）。使用这个操作系统的用户有多少？

在很多情况下，这些标准之间的权衡不可避免——在一个维度上改进系统，可能会在另一个维度上损害它。本节末尾会给出一些具体的设计权衡实例。

### 1.2.1　可靠性与可用性

也许操作系统最重要的特性就是它的可靠性。**可靠性**是指系统严格做到它被设计出来要做的事。作为系统上运行的最低层软件，操作系统的错误可能产生毁灭性且不易察觉的后果。如果操作系统坏掉，你可能就没法完成工作，有时甚至会丢失此前的工作成果，比如故障损坏了磁盘上的文件。相比之下，应用程序的失败往往要无害得多，这正是因为操作系统提供了故障隔离，以及在出错之后快速而干净的重启。

让操作系统变得可靠并不容易。操作系统常常运行在充满敌意的环境中：计算机病毒和其他恶意代码试图利用操作系统防御机制在设计或实现上的缺陷，来夺取系统的控制权。

遗憾的是，提高软件可靠性最常用的那些手段——比如针对常见代码路径运行测试用例——用在操作系统上效果要差得多。由于恶意攻击可以精确瞄准某个特定漏洞，迫使执行流程走上一条罕见的代码路径，因此操作系统要可靠，就必须保证每一处都正确。即使没有蓄意的恶意攻击，极其罕见的边角情况也会经常发生：对一个拥有百万用户的操作系统来说，十亿分之一概率的事件终究会在某个用户身上出现。

一个相关的概念是**可用性**，即系统处于可用状态的时间百分比。一个毛病很多、频繁崩溃并丢失用户工作的操作系统，既不可靠也不可用。一个频繁崩溃、但从不丢失用户工作、也不会被恶意攻击颠覆的操作系统，是可靠但不可用的。而一个已经被颠覆、却仍表现得运行正常、同时在暗中记录用户按键的操作系统，则是不可靠但可用的。

因此，可靠性**和**可用性两者都值得追求。可用性受两个因素影响：故障发生的频率，用**平均无故障时间（MTTF）**衡量；以及发生故障后把系统恢复到工作状态所需的时间（例如重启），称为**平均修复时间（MTTR）**。要提高可用性，可以增大 MTTF，或者减小 MTTR。

在本书中，我们会介绍各种提高操作系统可靠性和可用性的方法。很多时候，这些抽象初看起来似乎过于死板、过于程式化。重要的是要认识到，这是有意为之！只有精确的抽象，才能为构建可靠且可用的系统提供基础。

### 1.2.2　安全性

与可靠性密切相关的两个概念是安全性和隐私性。**安全性**是指计算机的运行不会被恶意攻击者破坏。**隐私性**是安全性的一个方面：计算机上存储的数据只有被授权的用户才能访问。

可惜，没有任何有用的计算机是绝对安全的！任何复杂的软件都有缺陷，而看似无害的缺陷也可能被攻击者利用来夺取系统控制权。或者，计算机硬件可能被做了手脚，为攻击者提供进入系统的途径。或者，计算机的管理员不可信，利用自己的权限窃取用户数据。又或者，操作系统的软件开发者不可信，在系统中植入后门，让攻击者得以进入。

尽管如此，操作系统可以、而且也应该被设计成把受攻击的可能性降到最低。例如，强故障隔离可以阻止第三方应用接管系统。下载并安装一个屏幕保护程序或其他应用，不应该给攻击者提供在系统中偷偷植入**计算机病毒**的机会。计算机病毒是一种计算机程序，它在计算机所有者不知情或未许可的情况下修改操作系统或应用程序，从而把自己从一台计算机复制到另一台。一旦装入计算机，病毒往往让攻击者得以控制系统的资源或数据。计算机病毒的一个例子是键盘记录器（keylogger）：它修改操作系统，记录用户敲下的每一次按键，并把这些内容发回攻击者的机器。这样一来，攻击者就能拿到用户的口令、银行账号以及其他私密信息。同样，一个恶意的屏幕保护程序也可能偷偷扫描磁盘上含有个人信息的文件，或者把系统变成一台垃圾邮件发送服务器。

即使有很强的故障隔离，如果应用程序本身不是为安全而设计的，系统仍然可能是不安全的。例如，互联网电子邮件标准并不能强有力地保证发件人的身份；完全可以构造出这样一封邮件，在“发件人”字段里填上任何人的地址，而不一定是真正的发件人。于是，一封邮件可以看起来来自某个人（也许是你信任的人），而实际上它来自攻击者，并且带有一个恶意病毒附件，一旦打开附件就会接管计算机。到如今，希望你点击任何邮件附件时都会心存警惕。退一步看，这个问题可以视为电子邮件系统与操作系统之间交互方式的一种局限。如果操作系统能提供一种廉价而简便的方式，让附件在一个能力受限的隔离执行环境中得到处理，那么即使附件中含有病毒也造不成危害。

更麻烦的是，操作系统不仅必须阻止对共享数据的非预期访问，在很多情况下还必须**允许**访问。用户和程序必须能够彼此交互，以便在不同应用之间剪切和粘贴文本，共享写到磁盘上或通过网络传来的数据。如果每个程序都完全独立、从不需要与任何别的程序交互，那么单靠故障隔离就够了。然而，我们不仅希望把程序彼此隔离开，还希望在程序之间、用户之间方便地共享数据。

因此，操作系统既需要一套强制实施机制，也需要一个安全策略。**强制实施**是操作系统用来确保只允许被许可操作的手段。**安全策略**则定义了什么是被许可的——谁可以访问哪些数据，谁可以执行哪些操作。

恶意攻击者既可以针对强制实施机制中的漏洞，也可以针对安全策略中的漏洞。强制实施上的错误会让攻击者得以绕过策略；策略上的错误则会让攻击者获得本应被禁止的访问权限。

### 1.2.3　可移植性

所有操作系统都为应用程序提供了底层计算机硬件的一种抽象；所谓**可移植的**抽象，是指它不随硬件的改变而改变。为微软 Windows 8 编写的程序，无论使用的是哪一款具体显卡，无论持久存储由闪存还是旋转磁盘提供，无论网络是蓝牙、WiFi 还是千兆以太网，都应该能正确运行。

可移植性也适用于操作系统本身。正如我们前面提到的，操作系统是有史以来最复杂的软件系统之一，因此每当有新硬件问世或有新应用开发出来，就从头重写一遍是不现实的。相反，新的操作系统往往至少在一定程度上是从旧系统衍生而来的。举个例子，iPhone 和 iPad 的操作系统 iOS 就是从 MacOS X 的代码库衍生出来的。

因此，大多数成功的操作系统寿命都以数十年计。微软 Windows 8 最初的源头是 1988 年启动的 Windows NT 开发。那时，典型的计算机在计算能力上比今天弱一万倍，内存和磁盘容量也只有今天的一万分之一。能延续几十年的操作系统并不罕见。微软此前的操作系统 MS/DOS 于 1981 年推出，后来演化为 Microsoft Windows 的早期版本，直到 2000 年前后才最终退出历史舞台。

这意味着操作系统必须被设计成能够支持尚未写出的应用，能够运行在尚未开发出的硬件上。同样，开发者也不希望操作系统从一台机器移植到另一台机器时还得重写应用。有时候，“让操作系统面向未来”这件事的重要性只有事后才会被发现。微软的第一个操作系统 MS/DOS 于 1981 年设计时，假定个人计算机的内存永远不会超过 640 KB。这个限制在当时可以接受，但今天连手机的内存都比它高出几个数量级。

那么，我们该如何设计操作系统来实现可移植性？正如前面图 1.3 所示，为应用提供一种与操作系统交互的简单而标准的方式会很有帮助，这就是**抽象虚拟机（AVM）**。它是操作系统向应用程序提供的接口，包括：（i）**应用程序接口（API）**，即操作系统提供给应用的函数调用清单；（ii）内存访问模型；（iii）哪些指令可以合法执行。例如，有一条指令用来切换硬件当前执行的是可信的操作系统代码还是不可信的应用代码，它必须对操作系统可用，而对应用程序不可用。

设计良好的操作系统 AVM 提供了一个固定支点，使应用代码和硬件可以在它的两侧各自独立演化。这与网络领域中互联网协议（IP）标准的作用类似。用 IP 编写的分布式应用，比如电子邮件和万维网，与底层网络技术（以太网、WiFi、光纤）的变化隔离开来。同样重要的是，应用的变化——从电子邮件到即时消息再到文件共享——并不要求底层硬件同时做出改变。

这种可移植硬件抽象的思想非常强大，以至于操作系统在内部也使用同样的做法：操作系统本身在很大程度上可以独立于具体硬件来实现。使这一点成为可能的接口称为**硬件抽象层（HAL）**。看起来，操作系统的 AVM 与操作系统的 HAL 似乎应该完全相同或者几乎相同——毕竟两者都是为了隐藏硬件细节而设计的可移植层。然而，AVM 必须做得更多。正如我们所指出的，应用程序运行在受限的、虚拟化的上下文中，并且可以访问高层的通用服务；而操作系统本身使用的则是更贴近实际硬件的过程式抽象。

今天，Linux 是高度可移植的操作系统的一个范例。它已被用作 Web 服务器、个人计算机、平板电脑、上网本、电子书阅读器、智能手机、机顶盒、路由器、WiFi 接入点和游戏机的操作系统。Linux 源自一个名为 UNIX 的操作系统，后者最初开发于 1970 年代早期。UNIX 由一个小型开发团队编写，其设计目标是紧凑、易于编程和高度可移植，代价是性能上有所损失。多年以来，UNIX 与 Linux 的可移植性以及便利的编程抽象，一直是它们取得成功的关键。

### 1.2.4　性能

操作系统的可移植性要随着时间的推移才会显现出来，而它的性能往往立刻就能被用户察觉。虽然我们常把性能与单个应用联系在一起，但操作系统的设计会极大地影响应用所表现出来的性能。操作系统决定一个应用何时可以运行、可以使用多少内存、它的文件是被缓存在内存中还是在磁盘上高效地聚簇存放。操作系统还居中调解应用对内存、网络和磁盘的访问。它必须避免拖慢关键路径，同时仍要在应用之间提供所需的故障隔离和资源共享。

性能并不是一个单一的指标，而是可以从几个不同的角度来度量。一个性能指标是**开销**，即为实现呈现给应用的某种抽象而额外付出的资源成本。与之相关的概念是**效率**，即抽象中没有多余的开销。度量开销（或者说反过来度量效率）的一种方法，是看这种抽象在多大程度上妨碍了应用性能。假设你可以让应用直接运行在底层硬件上、不必承担操作系统抽象带来的开销，那么应用的性能能提高多少？

操作系统还需要在各个应用之间分配资源，而这会影响最终用户所感受到的系统性能。其中一个问题是同一台机器上不同用户或不同应用之间的**公平性**。资源应该在不同用户或应用之间平均分配，还是有些应该得到优待？如果是后者，操作系统又如何决定哪些任务优先？

另外两个相关的概念是响应时间和吞吐量。**响应时间**，有时也称为**延迟**，是一个任务从开始到完成所用的时间。举例来说，台式机上一个非常显眼的响应时间，是从用户移动鼠标到屏幕上的指针反映出这一动作之间的时间。响应时间很差的操作系统可能会让人根本没法用。**吞吐量**是系统完成任务的速率。吞吐量衡量的是一组任务、而不是单个任务的效率。看起来，能改善响应时间的设计必然也会改善吞吐量，但事实并非如此，我们将在第 7 章讨论这一点。

一个相关的考量是**性能可预测性**：系统的响应时间或其他指标是否随时间保持一致。可预测性往往比平均性能更重要。如果一个用户操作有时瞬间完成、有时却要等很久，用户可能很难适应。举例来说，考虑两个系统。在其中一个系统里，每次按键通常都是即时的，但有 1% 的情况下要花 10 秒才生效。在另一个系统里，一次按键总是恰好花 0.1 秒显示到屏幕上。两个系统的平均响应时间相同，但后者更可预测。你认为哪一个对用户更友好？

::: info 例
为了说明效率、开销、公平性、响应时间、吞吐量和可预测性这些概念，考虑一辆汽车驶向目的地的情形。如果道路上从来没有别的汽车和行人，这辆车可以开得相当快，永远不必为红绿灯减速。停车标志和红绿灯让多辆车得以共享道路，代价是每个司机都要多付出一些开销、多承受一些响应时间上的损失。随着系统变得拥堵，可预测性会变差。拼车可以提高系统的吞吐量。如果设有专用拼车车道，即使拼车的人得先协调彼此的接送，拼车甚至还能减少延迟。放弃小汽车、改建公共交通，则可以同时改善可预测性、吞吐量和公平性。
:::

### 1.2.5　采用率

除了可靠性、可移植性和性能之外，操作系统的成功还取决于两个不受它直接控制的因素：移植到该操作系统上的应用是否丰富，以及它能够支持的硬件是否丰富。iPhone 运行 iOS，但如果没有预装的应用和 App Store 中的内容，iPhone 也不过就是又一部手机而已。

**网络效应**是指某种技术的价值不仅取决于它的固有功能，还取决于有多少其他人采用了它。应用和硬件的设计者会把精力投入到用户最多的那些操作系统平台上，而用户则偏爱应用最好或者硬件最便宜的那些操作系统。如果这听起来像是循环论证，那它确实是！用户越多意味着应用越多、硬件越便宜；应用越多、硬件越便宜又意味着用户越多，从而形成一个良性循环。

考虑一下你会如何设计一个操作系统，才能利用网络效应，或者至少不被它压垮。显而易见的一步是：让系统易于接纳新硬件，并让应用易于在同一操作系统的不同版本之间移植。

一个更微妙的问题是选择：操作系统的编程接口（API），或者操作系统源代码本身，是开放的还是专有的。**专有系统**由单一公司掌控，提供方可以随时修改它以满足客户的需要。**开放系统**则是指系统源代码公开，任何人都可以查看和修改代码。开放系统的 API 通常只有在公开标准组织达成一致时才能修改。遵循标准为应用开发者提供了保证：除非经过普遍同意，API 不会被改动；另一方面，标准组织也可能使得快速加入人们想要的新特性变得困难。

开放与专有本身并没有哪一种更利于被采用。Windows 8 和 MacOS 是专有操作系统；Linux 是开放操作系统。三者都被广泛使用。开放系统更容易适配各种各样的硬件平台，但它们有分裂成多个版本的风险，从而削弱网络效应。专有操作系统的提供者则主张，他们的系统更可靠，也更能贴合客户的需要。如果同一家公司同时掌控硬件和软件，互操作性问题可以减少；但把操作系统限定在单一硬件平台上，会削弱网络效应，并有疏远消费者的风险。

让应用易于从现有系统移植到一个新操作系统，可以帮助新系统站稳脚跟；反过来，设计一套让应用难以移植走的操作系统 API，则有助于阻止竞争对手立足。因此，商业压力常常促使操作系统接口变得五花八门、各行其是。本书通篇都在概念层面上讨论操作系统问题，但要记住，由于这些重要但有时相当混乱的商业利益，任何具体操作系统在细节上都可能相差很大。

### 1.2.6　设计权衡

大多数实用的操作系统设计，都在可靠性、安全性、可移植性、性能和采用率这些目标之间取得平衡。那些改善可移植性的设计选择——例如保留遗留接口——往往会让整个系统变得更不可靠、更不安全。类似地，打破某个抽象往往可以提升系统性能。然而，这类性能优化可能会增加复杂度，进而潜在地损害可靠性。操作系统的设计者必须仔细权衡这些相互竞争的目标。

::: info 例
为了说明性能与复杂度之间的权衡，来看下面这个真实的故事。1980 年代后期开发的一个研究型操作系统使用了类型安全语言，以减少程序员出错的概率。为了速度，操作系统核心中最频繁使用的那些例程是用汇编代码实现的。在其中某个例程里，实现团队决定采用一段指令序列，它能在一条极频繁执行的代码路径上省掉一条指令，但代价是当操作系统的规模超过某个特定大小时有时会出错。当时，操作系统的规模离这个上限还很远。然而在投入生产使用几年之后，系统开始神秘地崩溃，看起来毫无规律，而且总是在连续运行很多天之后才出现。经过数星期艰苦的排查，问题才水落石出：操作系统的规模已经长到了超出汇编代码实现所假定的上限。一旦找到问题，修复很容易，但问题是：你觉得当初那次优化值得冒这个风险吗？
:::

过去五十年计算技术的发展中，最引人注目的一点是摩尔定律（Moore's Law）的累积效应，以及存储器、磁盘等相关技术的同步进步。**摩尔定律**说的是晶体管密度随时间呈指数增长；许多其他元器件技术也出现了类似的指数式改进。表 1.8 概括了过去三十年间计算机硬件技术的演进。在此期间，计算和内存的成本下降了近六个数量级，磁盘容量的成本则下降了七个数量级。并非所有技术的改进步伐都一样快：磁盘延迟（表中未列出）虽有改善，却远比磁盘容量慢得多。这些相对变化彻底改变了计算机的使用方式，也改变了操作系统设计者所面临的取舍。

很难想象当年的情形是什么样子。今天，你口袋里很可能揣着一部智能手机，里面是一台性能惊人的计算机。成千上万台服务器计算机耐心地等待你键入一条搜索查询；查询一到，它们就能在不到一秒的时间里合成答复。然而在计算发展的早期，计算机比使用它们的人的薪水还要贵。用户常常要排上几天的队，才能轮到自己运行程序。在过去一百年里，电话也经历了类似从昂贵到便宜的过程。最初电话线路极其昂贵，整个街区的人共用一条线路。当然，随着时间推移，计算机和电话都变得足够便宜，可以一直闲置着，直到我们需要时才拿出来用。

尽管发生了这些变化，操作系统今天面对的概念性挑战与五十年前并无二致。为了替应用程序和用户管理计算机资源，它们仍必须在应用程序之间分配资源、提供故障隔离和通信服务、屏蔽硬件限制，如此等等。我们在提高操作系统的可靠性、安全性、效率和可移植性方面已经取得了巨大进展，但还有大量工作要做。虽然我们无法精确预知未来 10～20 年计算技术或应用需求将如何演变，但这些操作系统层面的根本挑战极有可能继续存在。

### 1.3.2　早期操作系统

最早的操作系统其实是运行时库，目的是简化早期计算机系统的编程工作。最早的计算机完全不像今天这样小巧廉价却极度复杂，它们往往占满仓库的整整一层楼，耗资数百万美元，却一次只能供一个人使用。用户先要重启计算机，再用开关把程序一位一位地拨入系统，然后按下“运行”，产生的输出只能在下一个用户的时间段里慢慢琢磨。如果程序有错，用户就得等着试下一次运行，往往要等到第二天。

看起来这种场景下似乎并不需要操作系统。然而计算机贵得惊人，因此减少程序员出错的可能性就成了头等大事。最早的操作系统正是作为提供一组标准公共服务、借以减少错误的手段而开发出来的。例如，早期操作系统提供标准的输入/输出（I/O）例程，每个用户都可以把它链接进自己的程序。有了这些服务，用户的程序更有可能产生有用的输出。

尽管最初的操作系统已经是巨大进步，结果仍然极其低效。也正是在那个年代，IBM 的首席执行官做出了那个著名的预言：全世界只需要五台计算机。如果今天的计算机每台还得花数百万美元、一次只能让一个人跑几个小型应用，他也许是对的。

### 1.3.3　多用户操作系统

再往前的一步是共享，它带来了我们在今天的操作系统中看到的许多优势，也带来了许多挑战。当处理器时间十分宝贵时，把系统限制为一次只服务一个用户是极大的浪费。例如，在早期系统中，用户装载程序的那段时间里处理器一直空闲着，哪怕外面还有一长串人排队等着轮到自己。

**批处理操作系统**（batch operating system）处理的是一个任务队列。它运行一个简单的循环：依次装载、运行、卸载每个作业。当一个作业正在运行时，操作系统会安排 I/O 设备为上一个/下一个作业进行后台传输，这一过程称为**直接内存访问**（direct memory access，DMA）。借助 DMA，I/O 设备把数据直接传送到内存中由操作系统指定的位置。传输结束后，硬件中断处理器，把控制权交给操作系统的中断处理程序。操作系统启动下一次 DMA 传输，然后恢复应用程序的执行。对应用程序而言，这次中断好像根本没有发生过，只是在两条指令之间多了一些延迟。

批处理操作系统很快被扩展成可以同时运行多个应用程序，这就是**多任务**（multitasking），有时也叫**多道程序设计**（multiprogramming）。多个程序同时装入内存，只要前一个任务因某种原因需要暂停（例如要读取更多输入或产生输出），其中每一个都随时可以使用处理器。多任务能把处理器效率提高到接近 100%；只要任务队列足够长，又有足够多的 I/O 设备不断给处理器供料，处理器就没有等待的必要。

然而，共享处理器也提出了程序隔离的需求，需要限制一个程序中的错误导致另一个程序崩溃或数据被破坏。在此期间，计算机设计者为硬件增加了内存保护机制，以降低故障隔离的开销。

不过，批处理计算有一个实际困难：如何调试操作系统本身。与应用程序不同，批处理操作系统假定自己直接掌管硬件。要测试新版本，只能停下所有应用程序并重新启动系统，这实质上又把计算机变回了单用户系统。不用说，这是一项代价高昂的操作，通常要安排在深夜进行。

虚拟机解决了这一限制（见图 1.4）。虚拟机不是直接在硬件上运行待测操作系统，而是把一个**操作系统**当作应用程序来运行。**宿主操作系统**（host operating system），又称**虚拟机监视器**（virtual machine monitor），对外呈现的是一个与底层硬件完全相同的抽象虚拟机（abstract virtual machine，AVM）。运行在虚拟机之上的待测操作系统不必知道自己身处虚拟环境——它执行指令、访问硬件设备、在中断之后恢复应用程序状态，一切都和在真实硬件上运行一模一样。

如今虚拟机被广泛用于操作系统开发、向后兼容和跨平台支持。那些只能在旧版操作系统上运行的应用程序，可以与全新的应用程序共享同一套硬件。虚拟机监视器同时运行两个虚拟机——一个供当前应用程序在新操作系统上运行，另一个单独供遗留应用程序使用。再举一个例子，需要运行 Windows 或 Linux 应用程序的 MacOS 用户，也可以把这些程序放进虚拟机里运行。

最终，摩尔定律的累积效应让计算成本下降到这样一个水平：系统可以围绕用户来优化，而不必一味追求高效的处理器利用率。例如，UNIX 就是 70 年代初在一台当时没人使用的闲置计算机上开发出来的。UNIX 后来成了 Apple MacOS X、Linux、VMware（一种被广泛使用的虚拟机监视器）和 Google Android 的基础。图 1.9 追溯了这些操作系统的谱系。

**分时操作系统**（time-sharing operating system）——例如 Windows、MacOS 或 Linux——旨在支持对计算机的交互式使用，而不是早期系统那种批处理模式。在分时系统中，用户通过与计算机直接相连的键盘或其他输入设备输入信息。每一次击键或鼠标动作都会引发一次处理器中断来报告该事件；中断处理程序从设备读出事件，并把它排入操作系统内部的队列。当用户的文字处理程序、游戏或其他应用程序恢复运行时，它从操作系统取出事件，进行处理，相应地改变显示内容，然后取出下一个事件。每秒可以处理数百甚至数千个这样的事件，这就要求操作系统和应用程序都必须按照频繁、极短的活动突发来设计，而不是按照批处理那种持续执行的模型。

Web 服务器的基本运作方式与分时系统相似。Web 服务器等待数据包的到来，请求的是网页、Web 搜索或图书购买。网络硬件通过 DMA 把到达的数据包复制进内存。一旦传输完成，硬件便中断处理器，告知数据包已经到达。这会触发服务器去执行所请求的任务。同样地，网页的每一个数据块从磁盘读入内存时，处理器也会被中断。与分时系统一样，服务器操作系统必须设计成每秒能够处理数量极大的短促操作。

最早的分时系统支持许多同时在线的用户，但这同样只是一个阶段。最终计算机变得足够便宜，人们买得起属于自己的专用“个人”计算机，这些计算机在一天的大部分时间里都会安安静静地闲置着。对共享数据的访问变得至关重要，由此确立了向客户机-服务器计算的转变。

### 1.3.5　现代操作系统

今天，我们面对种类繁多的计算设备，其上运行的操作系统也各不相同。操作系统设计者所面对的取舍，取决于硬件的物理能力以及应用和用户的需求。以下是几个你最近可能使用过的操作系统的例子：

- **台式机、笔记本电脑和上网本操作系统。** 例如 Windows 8、MacOS X 和 Linux。这些系统是单用户的，可以同时运行许多应用程序，配有各种各样的 I/O 设备。有人也许以为，既然只有一个用户，就没有必要把系统设计成支持共享，早期的个人计算机操作系统走的就是这条路子。它们几乎没有把系统各个部分彼此隔离的能力。然而随着时间推移，人们逐渐认识到，要提升系统可靠性、增强抵御计算机病毒的能力，就需要更严格的故障隔离。这类系统的其他关键设计目标还包括采用率（adoption，以支持丰富的应用程序）和交互性能。

- **智能手机操作系统。** 智能手机是一种手机，内置嵌入式计算机，能够运行第三方应用程序。智能手机操作系统的例子包括 iOS、Android、Symbian、WebOS、Blackberry OS 和 Windows Phone。智能手机虽然只有一个用户，却必须支持许多应用程序。关键设计目标包括响应速度、对种类繁多应用程序的支持，以及高效利用电池。另一个设计目标是用户隐私。由于第三方应用程序可能会为了营销目的偷偷收集用户的联系人名单之类的私密数据，操作系统必须设计成能够限制对受保护用户数据的访问。

- **服务器操作系统。** 搜索引擎、网络媒体、电子商务网站和电子邮件系统都托管在数据中心里的计算机上；这些计算机各自运行一个操作系统，通常是上述桌面系统的某个工业级强化版本。通常每台机器只运行一个应用程序（例如 Web 服务器），但操作系统必须协调成千上万个同时到达的网络连接。以每秒处理大量请求的吞吐量为核心设计目标。与此同时，响应速度也极为重要：Amazon 和 Google 都报告说，即使每个 Web 请求只增加 100 毫秒的延迟，也会显著影响营业收入。服务器还运行在充满敌意的环境中，恶意攻击者可能试图颠覆或阻断服务，因此抗攻击能力是一项基本要求。

- **虚拟机。** 如前所述，虚拟机监视器是这样一种操作系统，它能把另一个操作系统像普通应用程序那样运行起来，使之看上去如同运行在真实硬件之上。例子包括 VMWare、Xen 和 Windows Virtual PC。虚拟机监视器面临许多与其他操作系统相同的挑战，此外还有“协调一众协调者”带来的额外难题。运行在虚拟机内部的客户操作系统在做出资源分配和故障隔离的决策时，表现得就好像它完全掌控着自己名下的资源，而实际上它正与其他操作系统和应用程序共享这台机器。虚拟机在商业上的一项重要用途，是让单台服务器机器运行一组彼此独立的服务。每个虚拟机都可以按各自服务的需要进行配置。举例来说，这样就能让多个互不相关的 Web 服务器共享同一套物理硬件。因此，虚拟机的首要设计目标就是高效率和低开销。

- **嵌入式系统。** 随着时间推移，计算机已经便宜到可以集成进五花八门的消费设备中，从有线电视机顶盒，到微波炉、汽车和飞机的控制系统、乐高机器人，再到核磁共振（MRI）设备和基于 WiFi 的静脉输液滴定系统等医疗设备。嵌入式设备通常运行一个定制操作系统，与控制设备的专用软件捆绑在一起。你也许以为这些系统太过简单，不值得多花心思，但其中的软件错误可能造成灾难性后果。一个例子是 Therac-25，这是一种早期的计算机控制放射治疗设备。操作系统代码中的编程错误导致系统发生故障，造成数名病人死亡。

- **服务器集群。** 出于容错、规模和响应速度的考虑，网站越来越多地构建在分布式计算机集群之上，这些集群安置在一个或多个靠近用户、地理位置分散的数据中心里。如果一台计算机因硬件故障、软件崩溃或断电而失效，另一台计算机可以接管它的角色。如果网站的需求量超出单台计算机所能承受的范围，就可以把 Web 请求分摊到多台机器上。与普通操作系统一样，服务器集群的应用程序运行在抽象的集群接口之上，把应用与硬件变化隔离开来，也把一个应用的故障与同一数据中心里的其他应用隔离开来。同样地，资源还可以在两类对象之间共享：(1) 同一个网站上的各种应用（如 Google Search、Google Earth 和 Gmail），以及 (2) 托管在同一集群硬件上的多个网站（例如 Amazon 的 Elastic Compute Cloud 或 Google 的 Compute Engine）。

### 1.3.6　未来的操作系统

未来十年操作系统将走向何方？操作系统在抵御恶意攻击方面已经有了长足进步，但仍有相当长的路要走。只要能够克服安全性和可靠性方面的挑战，让计算机紧密控制和协调物理基础设施——例如电网、电话网络，以及医院的医疗设备和病历系统——将会带来巨大的潜在收益。每年有成千上万条生命因交通事故而逝去，而借助计算机控制汽车，这些事故本有可能避免。如果我们要把关键系统托付给计算机，就需要更大的把握确认操作系统胜任这项工作。

其次，底层硬件的变化往往会引发操作系统设计中的新工作。操作系统的未来也就是硬件的未来：

- **超大规模数据中心。** 操作系统需要协调数据中心里成千上万乃至数百万台计算机，以支撑必不可少的在线服务。

- **超大规模多核系统。** 计算机体系结构目前已经在一块芯片上集成多个处理器；这一趋势还将延续，最终会出现每台机器拥有数百个、甚至数千个处理器的系统。

- **无处不在的便携计算设备。** 随着智能手机、平板电脑和电子书阅读器的出现，计算机及其操作系统将摆脱键盘和屏幕的束缚，转而去响应语音、手势，甚至也许是脑电波。

- **高度异构的系统。** 当每一种设备都变得可编程之后，就必须为大到超级计算机、小到冰箱乃至单个电灯开关的形形色色设备提供操作系统。

- **超大规模存储。** 凡能存储的数据，最终都会被存储；操作系统需要可靠地保存海量数据，使之在任何时候都能够被取回，哪怕是在几十年之后。

管理好这一切，正是操作系统的职责所在。

+ 现在假设该计算机系统需要支持故障隔离。你认为需要哪些硬件支持和/或操作系统支持，才能实现以下几点：保护应用程序在内存中的数据结构不被其他应用程序破坏；保护某个用户的磁盘文件不被另一个用户访问或破坏；保护网络免受病毒的侵害，这种病毒企图利用你的计算机发送垃圾邮件。
+ 操作系统应当如何支持应用程序之间的通信？请说明你的理由。借助文件系统？借助在应用程序之间传递消息？借助应用程序之间共享的内存区域？以上全部？还是以上皆非？
