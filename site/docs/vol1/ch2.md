# 第 2 章　内核抽象

<div class="chap-en">The Kernel Abstraction</div>

<blockquote class="epigraph">好篱笆造就好邻居。——<strong>17 世纪谚语</strong></blockquote>

操作系统的一个核心作用是**保护**（protection）——把可能行为不端的应用程序和用户隔离起来，使它们不至于破坏其他应用程序或操作系统自身。对于实现上一章提到的若干操作系统目标而言，保护是必不可少的：

- **可靠性。** 保护能阻止一个程序中的缺陷导致其他程序或操作系统崩溃。在用户看来，系统崩溃总是操作系统的错，哪怕问题的根源其实是某个应用程序或用户的意外行为。因此，要实现高系统可靠性，操作系统必须把自己锤炼得刀枪不入，无论应用程序或用户做出什么举动，它都能正确运行。

- **安全性。** 系统上的某些用户或应用程序未必完全可信；因此，操作系统必须限制它们所能触及的范围。没有保护，恶意用户就可能悄悄篡改应用程序文件，甚至篡改操作系统本身，而用户却浑然不觉。举例来说，如果一个恶意应用程序能够直接写磁盘，它就可以修改存放操作系统代码的文件；下一次系统启动时，被篡改过的操作系统就会被引导起来，装上间谍软件并关掉病毒防护。出于安全考虑，操作系统必须阻止不可信代码修改系统状态。

- **隐私性。** 在多用户系统上，每个用户都只能访问她被允许访问的那部分数据。没有操作系统提供的保护，系统上的任何用户或应用程序都能在数据所有者不知情、未许可的情况下访问任何人的数据。例如，黑客常常利用热门应用程序——例如游戏或屏幕保护程序——作为跳板，去获取保存在智能手机或笔记本电脑上的个人电子邮件、电话号码和信用卡数据。出于隐私考虑，操作系统必须阻止不可信代码访问未经授权的数据。

- **公平的资源分配。** 有效的资源分配同样离不开保护。没有保护，一个应用程序就可以随心所欲地占用任意多的处理器时间、内存或磁盘空间。在单用户系统上，一个有缺陷的应用程序可能让其他应用程序无法运行，或者慢得像是卡死了。在多用户系统上，某个用户可能把系统资源一抢而空。因此，出于效率与公平的考虑，操作系统必须能够限制分配给每个应用程序或用户的资源量。

实现保护是**操作系统内核**（operating system kernel）的职责。内核是系统上运行的软件的最低层，可以完全访问机器的所有硬件。内核必然是**可信的**，可以对硬件做任何事。其余的一切——也就是系统上运行的不可信软件——则运行在受限环境中，无法完全施展硬件的全部能力。图 2.1 展示了内核级执行与用户级执行之间的这一区别。

反过来，应用程序自身也常常需要安全地执行不可信的第三方代码。一个例子是 Web 浏览器执行嵌入的 JavaScript 来绘制网页。没有保护，一段嵌有病毒的脚本就能控制浏览器，让用户以为自己在直接与 Web 交互，而实际上他们的 Web 口令正被转发给攻击者。

这种设计模式——可扩展的应用程序运行第三方脚本——出现在许多不同的领域。如果第三方开发者和用户能够对应用程序进行定制，应用程序就会变得更强大、应用得更广，但这样做也引出了一个问题：如何保护应用程序本身免受失控扩展的侵害。本章聚焦于操作系统如何保护内核不受不可信应用程序的侵害，但这些原则同样适用于应用程序层面。

**进程**是以受限权限执行应用程序的过程；进程是操作系统内核提供的、用于受保护执行的抽象。进程在访问任何其他进程的内存之前、在读写磁盘之前、在修改硬件设置之前，都需要获得操作系统内核的许可，如此等等。换句话说，操作系统内核对每个进程的硬件访问进行中介与检查。本章讲解进程的概念，以及内核如何实现进程隔离。

一个关键考虑是：既要提供保护，又要让应用程序代码高速运行。操作系统内核直接运行在处理器上，拥有不受限制的权限，可以执行硬件支持的任何操作。那么应用程序呢？它们需要在处理器上运行，同时禁用所有潜在的危险操作。要做到这一点，硬件需要提供一点帮助，我们稍后就会说明。全书中有不少类似的例子，说明经过精心设计的少量硬件支持，可以大大简化操作系统提供用户所需功能的工作。

当然，操作系统内核和以受限权限运行的应用程序进程实际上共享着同一台机器——同一个处理器、同一份内存、同一个磁盘。阅读本章时，请把这两个视角记在心里：当我们运行操作系统内核时，它可以做任何事；当我们代表用户运行应用程序进程时，进程的行为是受限的。

因此，运行操作系统的处理器有点像一个有人格分裂的人。运行操作系统内核时，处理器像是一座精神病院里掌管一切的看守，可以完全接触一切。而在其他时候，处理器在进程中运行应用程序代码——处理器变成了囚犯，被看守穿上约束衣、锁进软壁病房，以防它伤害别人。当然，这两种情况下是同一个处理器，有时完全可信，有时又完全不可信。

## 2.1　进程抽象

在图 2.2 所示这个你可能已经熟悉的模型中，程序员用某种高级语言键入代码。编译器把这些代码转换成一串机器指令，并把这些指令存放在一个文件中，称为程序的**可执行映像**（executable image）。编译器还定义程序所需的任何静态数据及其初始值，并把它们一并放进可执行映像。

要运行这个程序，操作系统把指令和数据从可执行映像复制到物理内存中。操作系统划出一块内存区域，即**执行栈**（execution stack），用来保存过程调用期间局部变量的状态。操作系统还划出一块内存区域，称为**堆**（heap），供程序可能需要的任何动态分配的数据结构使用。当然，为了把程序复制进内存，操作系统自身必须已经装入内存，并拥有自己的栈和堆。

暂且把保护放在一边，一旦程序装入内存，操作系统就可以通过设置栈指针、跳转到程序的第一条指令来启动它运行。编译器本身也不过是另一个程序：操作系统把编译器的可执行映像复制进内存、跳转到它的第一条指令，就这样启动了编译器。

要运行同一个程序的多个副本，操作系统可以在内存中为该程序的指令、静态数据、堆和栈各制作多份副本。正如我们将在第 8 章讲到的，大多数操作系统会尽可能复用内存：当同一个程序的多个副本同时执行时，它们只保存程序指令的一份副本。即便如此，程序的数据、堆和栈仍各需一份副本。眼下我们把事情简化，假定操作系统为每个进程都制作整个程序的一份独立副本。

因此，进程是程序的一个**实例**，正如在面向对象编程中对象是类的一个实例。每个程序可以有零个、一个或多个正在执行它的进程。对程序的每一个实例，都有一个进程，在内存中拥有该程序自己的一份副本。

操作系统用一种称为**进程控制块**（process control block，PCB）的数据结构来跟踪计算机上的各个进程。PCB 存放着操作系统关于某个特定进程所需的全部信息：它存放在内存的什么位置、它的可执行映像驻留在磁盘的什么位置、是哪个用户要求执行它的、该进程拥有哪些特权，如此等等。

前面我们把进程定义为以受限权限执行的程序实例。这两个角色——执行与保护——每一个都重要到足以占用好几章的篇幅。

本章聚焦保护，因此我们把讨论限定在简单进程上：每个进程只有一个程序计数器，以及代码、数据、堆和栈。

有些程序由多个并发活动（即线程）组成。例如，一个 Web 浏览器可能需要在绘制屏幕或接收网络输入的同时接收用户输入。这些彼此独立的活动各有自己的程序计数器和栈，但操作的是与其他线程相同的代码和数据。操作系统在一个进程中运行多个线程，与它在物理内存中运行多个进程的方式大体相同。我们在第 4 章推广进程抽象，以便在同一保护域内支持多个活动。

::: tip 进程、轻量级进程与线程
和计算机科学中的许多术语一样，“进程”这个词的含义也随时间发生了变化。词语的演变有时会绊倒毫不知情的人——在不同年代构建出来的系统，会以显著不同的方式使用同一个词。

“进程”最初被创造出来时，指的正是今天所说的“线程”——执行操作系统代码或应用程序代码的一条逻辑指令序列。进程这一概念的发展，是为了简化早期操作系统的正确构造，那些系统在应用程序之间根本不提供保护。

把操作系统组织成一组相互协作的进程，被证明极为成功，很快几乎所有新的操作系统都按这种方式构建，其中也包括那些同时还能防范恶意或有缺陷用户程序的系统。当时，几乎所有的用户程序都是简单的单线程程序，只有一个程序计数器和一个栈，因此并不存在混淆。运行一个程序需要一个进程，也就是一条带有保护边界的单一顺序执行流。

然而，随着并行计算机日益流行，我们再次需要一个词来表示一条逻辑指令序列。一个多处理器程序可以有多条指令序列并行运行，各有自己的程序计数器，但都在同一个保护边界内协作。有一段时间，它们被称为“轻量级进程”（每一个都是在保护边界内协作的一条指令序列），但最终“线程”这个词用得更为广泛。

这就形成了几乎所有现代操作系统都在使用的当前命名约定：一个进程执行一个程序，由在同一个保护边界内运行的一个或多个线程构成。
:::

## 2.2　双模式操作

程序被装入内存、操作系统启动进程之后，处理器便依次取指，然后译码并执行每一条指令。有些指令负责计算数值，比如把两个寄存器相乘、把结果放进另一个寄存器；有些指令读写内存单元；还有些指令（如分支或过程调用）改变程序计数器，从而决定下一条要执行哪条指令。图 2.3 示意了处理器的基本工作原理。

操作系统内核如何阻止一个进程去伤害其他进程，或者伤害操作系统自身？毕竟，当多个程序同时装入内存时，是什么东西阻止某个进程覆盖另一个进程的数据结构，甚至覆盖存放在磁盘上的操作系统映像？

如果不去考虑性能，有一种非常简单、安全、但纯属假想的做法：让操作系统内核一步一步地模拟每个用户进程中的每一条指令。不再由处理器直接执行指令，而是由一个软件解释器依次取指、译码并执行用户程序的每条指令。在执行每条指令之前，解释器可以检查该进程是否有权限做这项操作：它引用的是自己的内存，还是别人的内存？它是不是想跳进别人的代码？它是在直接访问磁盘，还是通过操作系统中正确的例程去访问？解释器可以放行所有合法操作，同时终止任何越了界的应用程序。

现在假设我们想给这个假想的模拟器加速。绝大多数指令是完全安全的，比如把两个寄存器相加、把结果存入第三个寄存器。我们能不能对处理器做些改动，让安全的指令直接在硬件上执行？

为此，我们把假想解释器里的那些检查如法炮制，只不过用硬件而不是软件来实现。这就是**双模式操作**（*dual-mode operation*），它由处理器状态寄存器中的一位表示，用来指示处理器当前所处的模式。在**用户模式**（*user mode*，也称用户态）下，处理器在执行每条指令之前先做检查，以确认该指令确实允许被这个进程执行（具体的检查内容我们接下来介绍）。在**内核模式**（*kernel mode*，也称内核态）下，操作系统运行时保护检查是关闭的。

::: tip 内核与操作系统的其余部分
操作系统内核是操作系统中至关重要的一块，但它只是整个操作系统的一部分。在大多数现代操作系统中，操作系统的一部分以用户模式运行，作为链接进每个应用程序的库。一个例子是管理应用程序菜单按钮的库代码。为了鼓励各个应用程序采用统一的用户界面，大多数操作系统都提供一个用户界面控件（widget）库。应用程序当然可以自己编写界面例程，但大多数开发者选择复用操作系统提供的那些例程。这段代码可以放进内核，但并没有这个必要。如果应用程序崩溃了，那个应用程序的菜单按钮失灵也无关紧要。库代码（而不是操作系统内核）与应用程序的其他部分**命运与共**：一方出问题，其影响和另一方出问题完全一样。

同样，操作系统的某些部分也可以运行在各自的用户级进程中。窗口管理器就是一个例子。窗口管理器把发生在某个窗口内的鼠标动作和键盘输入导向正确的应用程序，同时还确保每个应用程序只修改屏幕上属于自己的那一部分，而不是操作系统的菜单栏或其他任何应用程序的窗口。没有这条限制，恶意应用程序就有可能夺取整台机器的控制权。举例来说，病毒可以弹出一个和系统登录界面一模一样的登录提示，诱使用户把自己的密码透露给攻击者。

那为什么不把整个操作系统——库代码加上所有用户级进程——都放进内核里？这样做看起来似乎更合乎逻辑，但有一个理由是：调试用户级代码往往比调试内核代码容易得多。内核可以利用底层硬件，为应用程序代码提供断点和单步执行的调试支持；而要单步跟踪内核，就需要一个运行在内核之下的、更底层的调试器。调试操作系统内核的困难，正是当年开发虚拟机的最初动因。

更重要的是，内核必须是可信的，因为它完全掌控着硬件。内核中的任何错误都可能破坏磁盘、破坏某个毫不相干的应用程序的内存，或者干脆让系统崩溃。把不必待在内核里的代码分离出去，操作系统就能变得更可靠——窗口系统里有个 bug 已经够糟了，要是这个 bug 还能破坏磁盘，那就更糟了。这体现了**最小特权原则**（principle of least privilege）：如果系统的每一部分都恰好只拥有完成其工作所必需的那些特权，不多也不少，那么安全性和可靠性都会得到提升。
:::

要让操作系统内核既能够保护应用程序和用户彼此不受侵害，又能够让用户代码直接在处理器上运行，需要什么样的硬件？至少，硬件必须支持三样东西：

- **特权指令。** 在用户模式下执行时，所有可能不安全的指令都被禁止。（2.2.1 节）

- **内存保护。** 在用户模式下执行时，所有超出进程合法内存区域的内存访问都被禁止。（2.2.2 节）

- **定时器中断。** 无论进程在做什么，内核都必须有办法周期性地从当前进程手中收回控制权。（2.2.3 节）

此外，硬件还必须提供一种在用户模式与内核模式之间安全转移控制权的方法。由于实现这一点的机制相对复杂，我们把相关讨论推迟到 2.3 节和 2.4 节。

::: tip 处理器状态寄存器与特权级
从概念上讲，内核/用户模式就是一个一位的寄存器。置为 1 时，处理器处于内核模式，可以为所欲为；置为 0 时，处理器处于用户模式，受到限制。在大多数处理器上，内核/用户模式存放在**处理器状态寄存器**中。这个寄存器含有若干控制处理器运作的标志位，应用程序代码通常不能直接访问它。这些标志位是作为执行指令的副产品被置位或清零的。例如，中断发生时硬件会自动把状态寄存器保存到内存中，否则中断处理程序的代码会在不知不觉中覆盖掉它的内容。

内核/用户模式位是处理器状态寄存器中的一个标志位：每次进入内核时置位，每次内核切换回用户模式时清零。其他标志位包括**条件码**（condition code），它们是算术运算的副产品，用来让条件分支指令的编码更加紧凑。还有一些标志位可以指明处理器当前是以 16 位、32 位还是 64 位地址在执行。处理器状态寄存器的具体构成取决于处理器体系结构。

包括 Intel x86 在内的一些处理器体系结构，在处理器状态寄存器中支持两个以上的特权级（x86 支持四个特权级）。最初的动机是让操作系统内核可以分成两层：(i) 可以无限制访问机器的核心层；(ii) 被禁止执行某些操作、但权力又比完全无特权的应用代码更大的外层。这样一来，操作系统内核某一部分的 bug 也许就不会拖垮整个系统。然而，据我们所知，MacOS、Windows 和 Linux 都没有使用这一特性。

多特权级一个潜在的未来用途，是简化“把一个操作系统当作应用程序（即虚拟机）运行在另一个操作系统之上”这件事。运行在虚拟机操作系统之上的应用程序跑在用户级；虚拟机跑在某个中间级；真正的内核跑在内核模式。当然，只有四级的话，“虚拟机上再跑虚拟机上再跑虚拟机”就行不通了。在本书的讨论中，我们假定采用更简单也更普遍的情形：两级硬件保护。
:::

### 2.2.1　特权指令

只有当存在某种办法限制用户模式下运行的程序直接改变自己的特权级时，进程隔离才成为可能。我们将在 2.3 节讨论：进程可以通过执行一条称为**系统调用**（system call）的特殊指令间接地改变自己的特权级，把控制权转移到由操作系统定义的、内核中某个固定的位置。除了在这些固定位置把控制权交给操作系统内核（也就是实际上变成内核）之外，应用程序进程无法改变自己的特权级。

另一些指令也仅限于内核代码使用。不能允许应用程序去改变它可以访问的内存位置集合；我们将在 2.2.2 节讨论，把应用程序限制为只能访问自己的内存，对于防止它有意或无意地破坏、滥用其他应用程序或操作系统的数据与代码，是至关重要的。此外，应用程序也不能关闭处理器中断，这一点我们会在 2.2.3 节解释。

在内核模式下可用、而在用户模式下不可用的指令称为**特权指令**（privileged instruction）。操作系统内核必须能够执行这些指令才能完成自己的工作——它需要改变特权级、调整内存访问权限、关闭和打开中断。如果这些指令对应用程序开放，那么一个恶意应用程序实际上就拥有了操作系统内核的权力。

因此，应用程序只能使用完整指令集的一个子集，而操作系统以内核模式运行，拥有硬件的全部能力。

如果应用程序试图访问受限内存，或者试图改变自己的特权级，会发生什么？这类动作会引发一次**处理器异常**（processor exception）。与编程语言中由语言运行时和用户代码来处理的“抛出异常”不同，处理器异常会让处理器把控制权转交给操作系统内核中的异常处理程序。通常，内核在发现特权违规之后只是简单地终止该进程。

::: info 例
如果允许应用程序跳转到内核中的任意位置进入内核模式，可能会发生什么？
:::

::: warning 答
表面上看，最坏的情况无非是操作系统崩溃（这已经够糟了！），但这还可能让恶意应用程序获得对特权数据的访问，甚至可能取得整台机器的控制权。操作系统内核代表应用程序实现了一组特权服务。通常情况下，内核例程最先做的几步就包括核实用户是否有权限执行该操作；例如，文件系统在返回数据之前会检查用户是否有读该文件的权限。如果应用程序能够跳过权限检查，它就有可能绕开内核的安全限制。□
:::

### 2.2.2　内存保护

要运行一个应用程序进程，操作系统和应用程序必须同时驻留在内存中。应用程序必须在内存中才能执行，而操作系统也必须在内存中，才能启动程序，并处理程序运行期间发生的任何中断、处理器异常或系统调用。此外，内存中还可能存放着其他应用程序进程；例如，你可以一边读邮件、一边下载歌曲、一边用 Skype、一边发即时消息、一边浏览网页。

为了让内存共享变得安全，操作系统必须能够配置硬件，使得每个应用程序进程只能读写自己的内存，而不是操作系统或任何其他应用程序的内存。否则，应用程序就可以修改操作系统内核的代码或数据来夺取系统的控制权。举例来说，应用程序可以把登录程序改成给攻击者完整的系统管理员权限。虽然看上去只读访问内存似乎无害，但别忘了操作系统既要提供安全性，也要提供隐私性。内核数据结构——例如文件系统缓冲区——可能含有用户的私密数据。同样，用户密码在被核验期间也可能存放在内核内存中。

::: tip MS/DOS 与内存保护
作为内存保护威力的一个例证，MS/DOS 是微软早期的一个操作系统，它就没有提供内存保护。相反，用户程序可以读取和修改系统中的任何内存位置，包括操作系统的数据结构。对于一台一次只由一个人使用的个人计算机来说，这看似可以接受，但它有不少弊端。一个明显的问题是系统可靠性：应用程序的 bug 频繁地让操作系统崩溃或破坏其他应用程序。缺少内存保护也使系统更容易受到计算机病毒的攻击。

随着时间推移，一些应用程序利用了“能够修改操作系统数据结构”这一能力，例如去改动某些控制参数，或者直接操纵用于控制显示的帧缓冲。结果，改动操作系统变得相当困难：要么新版本跑不了旧的应用程序，从而限制它的吸引力；要么它必须把这些数据结构留在与旧版本完全相同的位置上。换句话说，内存保护不仅有助于提高可靠性和安全性，它还有助于在应用程序与操作系统内核之间强制形成一个定义良好的接口，从而为日后的可演进性和可移植性提供便利。
:::

操作系统如何阻止用户程序访问物理内存的某些部分？我们在第 8 章会讨论多种不同的做法，不过早期计算机开创了一种提供保护的简单机制。我们现在就介绍它，以说明其中的一般原理。

按照这种做法，处理器增设了两个寄存器，称为**基址寄存器和界限寄存器**（base and bound）。基址给出进程内存区域在物理内存中的起点，界限给出它的终点（图 2.5）。这两个寄存器只能由特权指令修改，也就是只能由以内核模式运行的操作系统来修改，用户级代码无法改变它们的值。

处理器每取一条指令，都要检查程序计数器的地址是否落在基址与界限寄存器之间。如果是，就允许这次取指继续进行；否则，硬件就引发一次异常，挂起程序并把控制权交还给操作系统内核。虽然每执行一条指令都要多做两次比较看上去有些奢侈，但内存保护值这个代价。事实上，我们在第 8 章还会讨论复杂得多、“奢侈”得多的内存保护方案。

同样，对于读写内存的指令，处理器会把每一次内存引用与基址和界限寄存器进行比对，一旦越界就产生一次处理器异常。复杂的指令（比如块复制指令）必须检查该指令所触及的每一个位置，以确保应用程序不会无意或恶意地读写这样一个缓冲区：它起始于自己的区域，却延伸进了内核的区域。否则，应用程序就能读取或覆盖操作系统代码或数据的关键部分，进而夺取系统的控制权。

操作系统内核的执行不受基址和界限寄存器的约束，因此它可以访问系统上的任何内存——内核自己的内存，或者系统上运行的任何应用程序进程的内存。由于应用程序只碰自己的内存，内核必须显式地把任何输入或输出复制进、或复制出应用程序的内存区域。例如，一个简单的程序可能会打印 “hello world”，内核就必须把这个字符串从应用程序的内存区域复制到屏幕缓冲区中。

用基址和界限寄存器做内存分配很简单，类似于堆内存的分配。程序启动时，内核找一块足够大的连续空闲物理内存块，用来存放整个程序、它的数据、堆和执行栈。如果这块空闲区域比需要的大，内核就把剩余部分归还给堆，以便分配给别的进程。

::: tip 内存映射设备
在大多数计算机上，操作系统通过读写特殊的内存位置来控制输入/输出设备——例如磁盘、网络或键盘。每个设备监视内存总线上分配给自己的地址，一旦看到自己的地址，就触发相应的 I/O 操作。

操作系统可以利用内存保护来阻止用户级进程访问这些特殊的内存位置。于是，内存保护还带来一项额外好处：限制用户代码直接访问输入/输出设备。通过把每个进程限制在它自己的内存位置范围内，内核阻止了进程直接读写磁盘控制器或其他设备。如此一来，有 bug 的或恶意的应用程序就无法修改存放在磁盘上的操作系统映像，用户也无法在不先经由操作系统检查文件权限的情况下访问另一个用户的文件。
:::

使用物理寻址的基址和界限寄存器能够提供保护，但它无法提供以下几项重要特性：

- **可扩展的堆和栈。** 每个进程只有一对基址和界限寄存器，程序启动时分配给它的内存量就固定下来了。虽然操作系统可以改变界限，但大多数程序有两个（或更多）需要根据程序行为独立扩展的内存区域。执行栈存放过程的局部变量，随着过程调用图的深度而增长；堆存放动态分配的对象。今天的大多数系统让堆和栈从程序内存的两端相向生长；这很难用一对基址和界限寄存器来配合。

- **内存共享。** 基址和界限寄存器不允许在不同进程之间共享内存，而共享内存在“多个运行同一程序或使用同一个库的进程之间共享代码”时是很有用的。

- **物理内存地址。** 程序在编译和链接时，其过程和全局变量的地址是相对于可执行文件开头设定的，也就是从零开始。用我们刚才描述的基址和界限寄存器机制，每个程序在运行时被装入物理内存，并且必须使用那些物理内存地址。由于一个程序可能因同时运行的其他程序不同而被装到不同的位置，内核必须在每次程序装入内存时，修改每一条引用全局地址的指令和每一个数据位置。

- **内存碎片。** 程序一旦启动，几乎就不可能再搬动它。程序可能把指针存放在寄存器里或执行栈上（例如过程返回时要用的程序计数器），要搬动程序到物理内存的其他区域，就得修改这些指针。随着时间推移，由于应用程序启动和结束的时间参差不齐，内存会变得越来越碎片化。碎片化有可能严重到这样的地步：尽管总的空闲内存是够的，却没有足够大的连续空间来启动一个新进程。

由于这些原因，大多数现代处理器引入了一层间接寻址，称为**虚拟地址**（virtual address）。有了虚拟地址，每个进程的内存都从同一个地方开始，比如零。每个进程都以为自己独占了整台机器，尽管现实中显然并非如此。硬件把这些虚拟地址翻译为物理内存位置。一种简单的算法就是把基址寄存器加到每个虚拟地址上，这样进程就可以使用从零开始的虚拟地址。

实践中，现代系统在虚拟地址和物理地址之间做转换时用的是复杂得多的算法。虚拟地址提供的这层间接性，赋予操作系统极大的灵活性去高效管理物理内存。例如，许多采用虚拟地址的系统以固定大小而不是可变大小的块来分配物理内存，以减少碎片。

虚拟地址还能让堆和栈分别从虚拟地址空间的两端起步，从而按程序需要各自增长（图 2.6）。如果栈或堆的增长超出了最初分配给它的区域，操作系统可以把它搬到物理内存中另一个更大的区域，却让它的虚拟地址保持不变。这种扩展对用户进程来说是完全透明的。我们将在第 8 章更深入地讨论虚拟地址。

<div class="code-cap"><span class="code-label">图 2.7</span>一个简单的 C 程序，其输出说明了在物理内存中执行与在虚拟内存中执行的区别。同时运行这个程序的多个副本时，输出不会改变。</div>

```c
int staticVar = 0;    // a static variable
main() {
    staticVar += 1;

    // sleep causes the program to wait for x seconds
    sleep(10);
    printf ("Address: %x; Value: %d\n", &staticVar, staticVar);
}

Produces:
    Address: 5328; Value: 1
```

有了虚拟地址，如果同时运行这个程序的多个副本，每个副本都会打印出完全相同的结果。如果每个副本都在直接寻址物理内存位置，这是不可能的。换句话说，程序的每个实例看起来都运行在自己那份完整的内存副本中：当它向某个内存位置存值时，只有它自己看得到对这个位置的改动，其他进程改动的是它们各自的那份内存位置。这样一来，一个进程无法改动任何其他进程的内存，因为它根本没有办法引用其他进程的内存；只有内核才能读写自身以外的进程的内存。

::: tip 地址随机化
计算机病毒常常通过攻击操作系统和服务器代码中隐藏的漏洞来得手。例如，如果操作系统开发者在把用户字符串复制进一个缓冲区之前忘了检查它的长度，这次复制就会覆盖紧随该缓冲区之后存放的数据。如果该缓冲区位于栈上，恶意用户就有可能覆盖过程的返回程序计数器；攻击者随后就可以让服务器跳转到任意位置（例如跳进嵌入在字符串里的代码）。当一个程序每次运行时都为同样的变量使用同样的位置时，这类攻击就更容易得手。

大多数操作系统（如 Linux、MacOS 和 Windows）通过对程序每次运行时所使用的虚拟地址做（小范围内的）随机化来对抗病毒。这称为**地址空间布局随机化**（address space layout randomization）。一种常见做法是为每次执行的堆和栈选取略微不同的起始地址。因此，在图 2.7 中，如果我们改为打印一个过程局部变量的地址，那么这个地址每次运行可能都不一样，尽管变量的值仍然是 1。

一些系统已经开始对过程和静态变量的位置，以及栈上相邻过程记录之间的偏移量也做随机化，以增大迫使系统跳转到攻击者代码的难度。尽管如此，每个进程看起来仍然拥有自己的一份内存，与所有其他进程互不相交。
:::

这非常像一组电视节目：每一部都占据着自己的世界，尽管它们都出现在同一台电视机上。一部剧里发生的事件（通常）不会影响其他剧的情节线。情景喜剧里的人物浑然不知 Jack Bauer 刚刚把世界从核毁灭中拯救了出来。当然，正如电视节目偶尔可以共用角色一样，只要内核允许，进程之间也可以通信。我们将在第 3 章讨论这一点是如何实现的。

::: info 例
假设我们有一种“完美的”面向对象语言和编译器，其中只有某个对象的方法才能访问该对象内部的数据。如果操作系统只运行用这种语言编写的程序，它还需要硬件的内存地址保护吗？
:::

::: warning 答
理论上不需要，但实践中需要。编译器要负责确保没有任何应用程序读写自己对象之外的数据。这就要求，举例来说，语言运行时必须做垃圾回收：一旦一个对象被释放回堆（并可能被其他应用程序复用），应用程序就不能再继续持有指向该对象的指针。

在实践中，这种做法意味着系统安全不仅要依赖操作系统内核的正确运作，还要依赖编译器的正确运作。编译器或语言运行时中的任何 bug 都可能成为攻击者夺取机器控制权的途径。许多语言带有庞大的运行时库，以简化用该语言编写程序的工作；这些库往往为了性能而用更接近硬件的语言（比如 C）写成。库例程中的任何 bug 同样可能成为攻击者夺取控制权的手段。

尽管看起来有些冗余，许多系统还是同时采用语言级保护和进程级保护。例如，Google 的 Chrome 浏览器会创建独立的进程（比如每个浏览器标签页一个）来解释网页上的 HTML、Javascript 或 Java。这样，恶意攻击者必须同时攻破语言运行时和操作系统进程边界，才能控制客户端机器。□
:::

### 2.2.3　定时器中断

进程隔离还要求硬件提供一种方式，让操作系统内核周期性地收回处理器的控制权。当操作系统启动一个用户级程序时，该进程可以自由地执行它想执行的任何用户级（非特权）指令，调用其内存区域内的任何函数，对自己的内存加载或存储任何值，如此等等。在用户程序看来，它似乎在自己内存区域的范围内完全掌控着硬件。

然而，这也只是一种假象。如果应用程序进入了死循环，或者用户单纯是不耐烦了、想让系统停掉这个应用程序，操作系统就必须能够收回控制权。当然，操作系统需要执行指令才能判断是否应该停掉这个应用程序，可如果处理器被应用程序占着，那么操作系统按定义就没有在那个处理器上运行。

在正常运作中，操作系统同样需要收回处理器的控制权。假设你一边在电脑上听音乐，一边下载文件，一边打字。为了流畅地播放音乐、并及时响应用户输入，操作系统必须能够收回控制权，以便切换到新的任务上去。

::: tip MacOS 与抢占式调度
在 2002 年之前，Apple 的 MacOS 不具备强制进程把处理器交还内核的能力。相反，所有应用程序员都被要求把自己的系统设计成周期性地调用操作系统，检查是否有别的工作要做。操作系统随后保存原进程的状态，把控制权切换给另一个应用程序，并且只在又轮到原进程时才返回。这有个缺点：如果某个进程没能主动让出处理器（例如因为有 bug 而陷入死循环），操作系统内核就无计可施。用户只能重启机器，才能把控制权交还给操作系统。这种情况发生得相当频繁，以至于有了专门的名字：“死亡转圈光标”（spinning cursor of death）。
:::

几乎所有计算机系统都包含一个称为**硬件定时器**（hardware timer）的设备，它可以被设定为在指定的延时之后中断处理器（延时可以按时间计，也可以按已经执行的指令条数计）。每个定时器只中断一个处理器，所以多处理器通常为每一个 CPU 配备一个单独的定时器。操作系统可能会把每个定时器设定为每隔几毫秒到期一次，而人的反应时间是几百毫秒。重置定时器是一项特权操作，只能在内核中完成，这样用户级进程就无法无意或恶意地关掉定时器。

定时器中断发生时，硬件把控制权从用户进程转移给以内核模式运行的内核。其他硬件中断（例如告知处理器某个 I/O 设备已经完成工作）同样把控制权从用户进程转移给内核。定时器中断或其他中断并不意味着程序出了错；在大多数情况下，操作系统重置定时器之后就恢复该进程的执行，把模式、程序计数器和寄存器恢复为中断发生前一刻的值。我们会在 2.4 节讨论实现中断的硬件与内核机制。

::: info 例
内核如何知道一个应用程序是否陷入了死循环？
:::

::: warning 答
它并不知道。典型情况下，操作系统只在用户或系统管理员要求时才终止一个进程，例如因为该应用程序已经不再响应用户输入。操作系统需要能够收回控制权，才有可能去询问用户是否想关掉某个特定的进程。□

## 2.3　模式切换的类型

内核把用户进程放进精心构造的沙箱之后，接下来的问题是：如何安全地从执行用户进程切换到执行内核，以及反过来如何切换回去。这类切换并不罕见。举例来说，一台高性能 Web 服务器每秒可能在用户模式和内核模式之间往返数千次。因此，这套机制必须既快又安全，不给恶意的或有缺陷的程序留下任何破坏内核的余地——无论它是蓄意为之还是无心之失。

### 2.3.1　用户模式到内核模式

我们先关注从用户模式到内核模式的切换；后面会看到，反方向的切换其实就是“撤销”用户进程进入内核时所做的那一套动作。

内核从用户进程手中接管控制权，有三类原因：中断、处理器异常和系统调用。中断是异步发生的——也就是说，它由外部事件触发，并且可以在任意一条用户模式指令之后引发向内核模式的转移。

处理器异常和系统调用则是由进程执行触发的同步事件。我们用**陷阱**（trap）一词指代任何从用户模式到内核模式的同步控制权转移；有些系统把这个词用得更宽泛，泛指任何从较低特权级向较高特权级的控制权转移。

- **中断。** **中断**是发给处理器的一个异步信号，告知某个可能需要处理器关注的外部事件已经发生。处理器执行指令时会检查是否有中断到达。如果有，它会把正在执行中的指令完成或者暂停下来。此时处理器硬件不再去取下一条指令，而是保存当前的执行状态，并转到内核中一个专门设定的中断处理程序开始执行。在多处理器上，中断只会在其中一个处理器上被接收，其余处理器照常继续执行，仿佛什么都没有发生。每一种不同类型的中断都需要各自的处理程序。对于时钟中断，处理程序会检查当前进程是否仍在响应用户输入，据此判断进程是否陷入了死循环。时钟处理程序也可以切换去执行另一个进程，以保证每个进程都能轮到一次。如果不需要做任何改变，时钟处理程序就在被中断的那条指令处恢复执行，整个过程对用户进程是透明的。中断也被用来通知内核 I/O 请求已经完成。例如，用户每次移动或点击鼠标，鼠标设备硬件都会触发一次中断。内核接着通知相应的用户进程——也就是用户正“划过”其窗口的那个进程。几乎每一种 I/O 设备——以太网、WiFi、硬盘、U 盘、键盘、鼠标——只要有输入送达处理器，或者有请求完成，都会产生一次中断。中断之外的另一种做法是**轮询**（polling）：内核循环检查每一个输入/输出设备，看是否发生了需要处理的事件。不用说，内核一旦忙于轮询，就没法再去跑用户级代码了。处理器间中断是中断的另一个来源。一个处理器可以向其他任何一个处理器发送中断。内核用这类中断来协调多处理器上的动作；例如，当一个并行程序退出时，内核就发出中断，阻止该程序继续在其他处理器上运行。**缓冲区描述符与高性能 I/O** 在早期的计算机系统中，获得良好性能的关键是让处理器保持忙碌；而在今天，尤其是对服务器而言，关键变成了让网络和磁盘等 I/O 设备保持忙碌。过去四十年里，互联网带宽和磁盘带宽都没有跟上处理器性能的飞速提升，这使得它们相对于 CPU 而言对系统性能更为重要。设计操作系统软件来管理 I/O 设备的一种简单但低效的做法，是任一时刻只允许对该设备发起一次 I/O 操作。在这种情况下，中断处理本身就可能成为性能的瓶颈：设备完成一个请求后就发出中断，让设备中断处理程序运行起来；处理程序再向硬件发出下一个待处理的请求。而在处理器处理中断的这段时间里，设备是空闲的。为了获得更高的性能，操作系统为每个设备建立一个循环的请求队列。（网络接口会有两个队列：一个用于入站数据包，一个用于出站数据包。）队列中的每一项称为一个**缓冲区描述符**（buffer descriptor），它描述一次 I/O 操作：所请求的操作（例如磁盘读或写）以及存放数据的缓冲区位置。设备硬件读取缓冲区描述符，据此决定要执行哪些操作。只要缓冲区描述符队列是满的，设备就可以在操作系统处理上一个操作的同时着手下一个操作。缓冲区描述符存放在内存中，设备通过 DMA（直接内存访问）来访问它。由此带来的一个结果是：每一次逻辑 I/O 操作可能涉及多次 DMA 请求——先把缓冲区描述符从内存下载到设备，然后拷贝数据进出，最后再把操作的成功/失败写回缓冲区描述符。

- **处理器异常。** **处理器异常**是由用户程序行为引起的硬件事件，它会导致控制权转移给内核。与中断一样，硬件会先完成此前的所有指令，保存当前执行状态，然后转到内核中专门设定的异常处理程序开始运行。例如，当进程试图执行一条特权指令，或者访问自己内存区域之外的内存时，就会发生处理器异常。其他处理器异常还包括：进程用整数除以零、用非对齐的地址访问内存字、试图写入只读内存，等等。在这些情况下，操作系统通常直接终止该进程，并向用户返回一个错误码。在多处理器上，异常只会停止触发该异常的那个处理器上的执行；内核随后需要发送处理器间中断，以停止该并行程序在其他处理器上的执行。处理器异常也会由一些更为无害的程序事件引发。例如，为了在程序中设置断点，内核会把内存中那条机器指令替换成一条特殊的指令，该指令会触发一次陷阱。当程序执行到那个位置时，硬件就切换到内核模式。内核恢复原来的指令，并把控制权交给调试器。调试器随后可以检查程序的变量、设置新的断点，并在引发异常的那条指令处恢复程序的运行。**处理器异常与虚拟化** 处理器异常是虚拟化——即仿真实际上并不存在的硬件——特别有力的工具。举一个例子：同一处理器体系结构家族的不同版本支持指令集的某些部分而不支持另一些部分，这是很常见的事，比如某个廉价、低功耗的处理器不支持浮点运算。操作系统可以借助处理器异常把这种差异对用户进程完全隐藏起来，代价是性能上有所损失。当程序发出一条浮点指令时，就会引发异常，陷入操作系统内核。操作系统不必终止该进程，而是可以**仿真**这条缺失的指令，并在完成后返回到用户进程中引发异常的那条指令之后的那条指令。这样一来，同一份程序二进制代码就能在不同版本的处理器上运行。更一般地，处理器异常被用来透明地仿真虚拟机。当客户操作系统作为一个用户级进程运行在某个操作系统之上时，它会像运行在物理硬件上那样尝试执行特权指令。这些指令会引发处理器异常，陷入宿主操作系统的内核。为了维持物理硬件的假象，宿主内核会代表这个用户级虚拟机去执行所请求的指令，并在引发异常的那条指令之后重新启动客户操作系统。再举最后一个例子：处理器异常是内存管理的关键基石。对于大多数虚拟寻址方式，可以把处理器设置成在读写某个特定虚拟地址范围时触发异常。这使得内核能够把内存当作**虚拟**的——程序内存的一部分可以存放在磁盘上，而不是放在物理内存中。当程序访问到一个缺失的地址时，操作系统的异常处理程序会先从磁盘把数据填进来，再恢复程序运行。这样，操作系统就能运行那些所需内存超过机器当前可容纳量的程序。

- **系统调用。** 用户进程也可以主动切入操作系统内核，请求内核代表自己执行某项操作。**系统调用**是内核提供的、可以从用户级调用的任何过程。大多数处理器用一条特殊的 `trap` 或 `syscall` 指令来实现系统调用。不过，专用指令并非严格必需；在某些系统上，进程通过执行一条带有特定非法操作码的指令来触发系统调用。与中断或处理器异常一样，陷阱指令把处理器模式从用户模式改为内核模式，并从内核中一个预先定义好的处理程序开始执行。为了保护内核免受行为不当的用户程序侵害，硬件在系统调用时必须把控制权转移到一个预先定义好的地址——绝**不能**允许用户进程跳到内核中的任意位置。操作系统可以提供任意数量的系统调用，例如：建立与 Web 服务器的连接、通过网络发送或接收数据包、创建或删除文件、向文件读写数据、创建新的用户进程，等等。对用户程序来说，这些调用就像普通过程一样，有参数也有返回值。调用者只需要关心接口，不必知道这个例程实际上是由内核实现的。内核负责处理参数检查与拷贝、执行操作、以及把返回值拷回进程内存这些细节。内核完成系统调用后，会在陷阱指令之后的那条指令处恢复用户级的执行。

### 2.3.2　内核模式到用户模式

正如从用户模式到内核模式有若干种不同类型的转移，从内核模式到用户模式也有若干种：

- **新建进程。** 要启动一个新进程，内核把程序复制进内存，把程序计数器设置为进程的第一条指令，把栈指针设置为用户栈的栈底，然后切换到用户模式。

- **中断、处理器异常或系统调用之后的恢复。** 内核处理完请求后，通过恢复被中断进程的程序计数器（如果是系统调用，则是陷阱之后的那条指令）、恢复它的寄存器、并把模式改回用户级，来恢复该进程的执行。

- **切换到另一个进程。** 在某些情况下，比如在时钟中断时，内核会切换到与中断之前正在运行的那个进程不同的另一个进程。由于内核最终还要恢复原来的进程，它需要把该进程的状态——程序计数器、寄存器等等——保存到该进程的控制块中。之后，内核可以通过把另一个进程的状态——程序计数器、寄存器等等——从它的控制块装入处理器，再切换到用户模式，从而恢复它的运行。

- **用户级向上调用。** 许多操作系统为用户程序提供接收事件异步通知的能力。我们在 2.8 节描述这一机制，它类似于内核的中断处理，只不过发生在用户级。

## 2.4　实现安全的模式切换

无论从用户模式切换到内核模式，还是反方向切换，都必须小心确保有缺陷的或恶意的用户程序无法破坏内核。基本思路虽然简单，底层实现却可能相当棘手：处理器必须一边保存自己的状态、切换正在做的事情，**同时**又在执行着那些可能改变它正在保存的状态的指令。这就好比给一辆以每小时 60 英里疾驰的汽车重建变速箱。

上下文切换代码必须精心编写，而且它依赖硬件的支持。为了避免混乱、减少出错的可能，大多数操作系统在进入内核时——无论是因为中断、处理器异常还是系统调用——都使用同一段公共的指令序列，返回用户级时也是如此，同样不问原因。

这段公共指令序列至少必须提供下列保证：

- **受限的内核入口。** 要把控制权交给操作系统内核，硬件必须确保进入内核的入口点是由内核自己设定的。不能允许用户程序跳到内核中的任意位置。举例来说，处理“读文件”系统调用的内核代码会先检查用户程序是否有权限这样做；如果没有，内核就应当返回一个错误。倘若内核没有受限的入口点，恶意程序就可以直接跳到执行检查的那段代码之后，从而得以访问任何人的文件。

- **处理器状态的原子性改变。** 在用户模式下，程序计数器和栈指向用户进程内存中的位置；内存保护阻止用户进程访问其区域之外的任何内存。在内核模式下，程序计数器和栈指向内核内存中的位置；内存保护被改变，使内核既能访问自己的数据，也能访问用户进程的数据。两者之间的切换是原子的——模式、程序计数器、栈和内存保护全部同时改变。

- **透明、可重启的执行。** 某个事件可能在任意时刻、任意两条指令之间打断一个用户级进程。例如，处理器可能已经算出了一个内存地址、把它装进了寄存器，正准备把一个值存到那个地址。操作系统必须能够把用户程序的状态恢复到中断发生之前一模一样的样子。对用户进程来说，中断是不可见的，唯一的差别只是程序暂时变慢了一点。一个 “hello world” 程序写的时候根本没考虑过中断，但中断仍然可能在它运行期间发生。发生中断时，处理器把当前状态保存到内存，暂时推迟后续事件，切换到内核模式，然后跳转到中断或异常处理程序。处理程序结束后，这些步骤被反向执行：处理器状态从保存它的位置恢复，被中断的程序对此毫不知情。

有了这些背景，我们现在来描述处理中断、处理器异常或系统调用的软硬件机制。稍后，我们会把这套基本机制当作构件加以复用，用来实现用户级信号。

### 2.4.1　中断向量表

当中断、处理器异常或系统调用陷阱发生时，操作系统必须根据事件类型的不同而采取不同的动作：是除零异常，是读文件系统调用，还是时钟中断。处理器怎么知道该运行哪段代码呢？

如图 2.8 所示，处理器有一个特殊的寄存器，指向内核内存中一块称为**中断向量表**的区域。中断向量表是一个指针数组，每一项指向内核中某个不同处理程序过程的第一条指令。**中断处理程序**指的是发生中断时内核所调用的那个过程。

中断向量表的格式因处理器而异。例如在 x86 上，中断向量表的第 0～31 项对应不同类型的处理器异常（如除零），第 32～255 项对应不同类型的中断（时钟、键盘等等）；按惯例，第 64 项指向系统调用陷阱处理程序。硬件会判断是哪个硬件设备引发了中断、是否执行了陷阱指令、或者发生了什么异常条件。因此，硬件能够从中断向量表中选出正确的表项，并调用相应的处理程序。

另一些处理器的入口点数量要少得多，它们改为把一个指示中断原因的编码放进某个特殊的硬件寄存器。这种情况下，由操作系统软件用这个编码去索引中断向量表。

如果中断向量表可以被应用程序代码修改，那么应用程序就有可能把所有的网络中断都导向自己的代码，从而劫持网络。同样地，指向中断向量表的那个硬件寄存器也必须是受保护寄存器，只有在内核模式下才能设置。□
:::

::: tip 多处理器与中断路由
在多处理器上，各种各样的中断应该由哪一个处理器来接收？一些早期的多处理器指定一个处理器（“0 号处理器”）来处理所有外部中断。如果某个事件需要改变其他某个处理器正在做的事情，0 号处理器就可以发送一个处理器间中断，触发那个处理器切换到新的进程。

对于需要大量输入输出的系统，比如 Web 服务器，把所有 I/O 都导向单个处理器会成为瓶颈。在现代系统中，中断路由越来越可编程，由内核掌控。每个处理器通常都有自己的硬件定时器。同样地，磁盘 I/O 事件可以直接发送给当初发出该 I/O 操作的处理器，而不是随机发给某一个处理器。如果数据已经装入处理器自己的高速缓存，现代处理器的运行速度会比代码和数据放在别的处理器缓存里时快得多。

网络 I/O 数据包的高效投递更加棘手。一台高性能服务器每秒可能收发数万个数据包，涉及数千条不同的连接。从处理的角度看，最好把入站数据包投递给负责该连接的那个处理器；这就要求网络接口硬件根据数据包首部的内容（例如客户端的 IP 地址和端口号）来重定向入站数据包。较新的网络控制器为此支持为同一设备配备多个缓冲区描述符环，并依据到达数据包的首部来选择使用哪一个环——进而也就决定了去中断哪一个处理器。
:::

### 2.4.2　中断栈

被中断进程的状态应该保存在哪里？内核的代码又应该用哪一个栈？

在大多数处理器上，有一个特殊的特权硬件寄存器指向内核内存中一块称为**中断栈**的区域。当中断、处理器异常或系统调用陷阱导致上下文切换进入内核时，硬件把栈指针改为指向内核中断栈的栈底。在调用内核的处理程序之前，硬件会自动把被中断进程的一部分寄存器压入中断栈，从而把它们保存下来。

内核处理程序运行时，会先把剩余的寄存器压入栈，然后才开始自己的工作。从中断、处理器异常或系统调用陷阱返回时，过程正好相反：先由处理程序弹出它所保存的寄存器，再由硬件恢复它自己保存的那些寄存器，返回到进程被中断的那个点。从系统调用返回时，必须把保存的程序计数器的值加上一个增量，这样硬件才能返回到引发陷阱的那条指令之**后**的那条指令。

你也许以为可以用进程的用户级栈来保存它的状态。然而，出于两点理由，需要一个独立的内核级中断栈。

- **可靠性。** 进程的用户级栈指针可能不是合法的内存地址（比如程序有 bug 的时候），但内核处理程序必须继续正常工作。

- **安全性。** 在多处理器上，同一进程中的其他线程可能在系统调用进行期间修改用户内存。如果内核处理程序把局部变量存放在用户级栈上，用户程序就有可能修改内核的返回地址，进而有可能让内核跳转到任意代码。

在多处理器上，每个处理器都需要有自己的中断栈，这样内核才能同时处理多个处理器上发生的系统调用和异常。内核会为每个处理器分配一块独立的内存区域，作为该处理器的中断栈。

### 2.4.3　每个进程两个栈

大多数操作系统内核更进一步，为每一个用户级进程（以及第 4 章中会讨论的每一个执行用户代码的线程）分配一个内核中断栈。当某个用户级进程正在运行时，硬件中断栈就指向该进程的内核栈。注意：当进程在用户级运行时，它并不在内核中执行，因此它的内核栈是空的。

为每个进程分配一个内核栈，可以让中断或系统调用处理程序更容易地切换到新的进程。例如，时钟中断处理程序可能决定把处理器让给另一个进程。同样地，某个系统调用可能需要等待一次 I/O 操作完成；在等待期间，应该让别的进程运行。有了每进程栈，要挂起一个进程，就把指向它内核栈的指针存入进程控制块，然后切换到新进程的栈。我们在第 4 章会更详细地描述这一机制。

<figcaption><span class="fig-label">图 2.9</span>在大多数操作系统中，一个进程有两个栈：一个用于执行用户代码，一个用于执行内核代码。图中展示了进程在各种状态下的内核栈与用户栈。当进程在用户模式下运行时，它的内核栈是空的。当进程被抢占（处于就绪但未运行）时，它的内核栈中保存着用户进程被中断那一刻的用户级处理器状态。当进程正在系统调用中等待 I/O 时，内核栈中保存的是 I/O 完成后要恢复的上下文，而用户栈中保存的是系统调用返回后要恢复的上下文。</figcaption>

图 2.9 概括了一个进程的用户栈和内核栈在各种状态下的情形：

- 如果进程正在处理器上以内核模式运行——无论是因为中断、处理器异常还是系统调用——它的内核栈正在被使用，其中既保存着被挂起的用户级计算的寄存器，也保存着内核处理程序的当前状态。

- 如果进程可以运行，但正在排队等待轮到自己使用处理器，它的内核栈中保存着该进程恢复运行时需要恢复的寄存器和状态。

- 如果进程正在等待某个 I/O 事件完成，它的内核栈中保存着 I/O 完成后要恢复的那个被挂起的计算。

::: tip UNIX 与内核栈
在 UNIX 最初的实现中，内核内存极为宝贵；当时主存每字节的价格大约是今天的百万倍。最初的系统只需要 50KB 主存就能运行。UNIX 没有为每个进程分配一整个中断栈，而是在进程控制块中只分配刚好够存放一次模式切换时保存下来的用户级寄存器的内存。这样，UNIX 就能以最少的内存挂起一个用户级进程。UNIX 仍然需要少量几个内核栈：一个用于运行中断处理程序，另加一个供每一个正在等待 I/O 事件完成的系统调用使用；但这远比每个进程一个要少得多。

当然，如今内存便宜得多，大多数系统就图省事，给每个进程或线程分配一个内核栈。
:::

### 2.4.4　中断屏蔽

中断是异步到达的；中断到达时，处理器可能正在执行用户代码，也可能正在执行内核代码。在内核的某些区域——例如中断处理程序自身内部，或者 CPU 调度器内部——接收中断会造成混乱。如果一个中断处理程序自己又被中断，我们就不能把栈指针重新指向内核中断栈的栈底——那样做会把第一个处理程序的状态抹掉。

为了简化内核设计，硬件提供了一条特权指令，用于把中断的投递暂时推迟到安全的时候。在 x86 和其他若干处理器上，这条指令叫做**关中断**（disable interrupts）。不过这个名目其实并不准确：中断只是被推迟（屏蔽）了，并没有被丢弃。一旦执行了相应的**开中断**（enable interrupts）指令，所有挂起的中断就会被投递给处理器。屏蔽和解除屏蔽中断的指令必须是特权指令；否则，用户代码就可能因无意或恶意而关掉硬件定时器，让机器彻底卡死。

如果在关中断期间有多个中断到达，硬件会在中断重新开启后依次把它们投递出来。不过，由于硬件为挂起中断提供的缓冲有限，如果关中断的时间过长，某些中断就可能丢失。通常硬件为每种类型缓冲一个中断；中断处理程序负责检查设备硬件，看是否有多个待处理的 I/O 事件需要处理。

::: tip 中断处理程序：上半部与下半部
当机器因为某个硬件事件发生（如定时器到期、按下一个键、一个网络数据包到达，或者一次磁盘 I/O 完成）而调用中断处理程序时，处理器硬件通常会在中断处理程序执行期间屏蔽中断。在中断被屏蔽期间，另一个硬件事件不会再次触发中断处理程序的调用，直到中断被重新开启。

有些中断会引发大量的处理工作，让中断长时间处于屏蔽状态是不可取的。硬件 I/O 设备的缓冲空间有限，如果中断不能及时处理，就可能导致事件丢失。例如，键盘缓冲区满了之后，键盘硬件就会丢弃击键。因此，中断处理程序被分成**上半部**（top half）和**下半部**（bottom half）。遗憾的是，这套术语在不同系统之间略有出入；在 Linux 中，上下半部的含义正好相反。本书采用更常见的（非 Linux）用法。

中断处理程序的下半部由硬件调用，在执行时中断是被屏蔽的。它被设计成能够快速完成。下半部通常保存硬件设备的状态，把设备复位以便接收新的事件，并通知调度程序上半部需要运行。到此下半部就完成了，它可以重新开启中断并返回被中断的任务，或者（如果该事件优先级较高）切换到上半部，但此时中断是开启的。上半部运行时可以做更一般的内核任务，例如解析到达的数据包、把它投递给正确的用户级进程、发送确认，等等。上半部还可以执行那些需要内核等待以独占访问共享内核数据结构的操作，这是第 5 章的主题。
:::

如果处理器在内核模式下、且中断处于开启状态时接收到一个中断，那么沿用当前的栈指针、而不把它重置为中断栈的栈底就是安全的。这种做法可以把一系列处理程序的状态递归地压入栈；随后每当一个处理程序完成，它的状态就从栈中弹出，先前的那个处理程序便从它中断的地方继续运行。

### 2.4.5　保存与恢复寄存器的硬件支持

被中断进程的寄存器必须被保存，这样该进程才能从它中断的地方原样重启。由于处理程序在运行过程中可能会改变这些寄存器里的值，状态必须在处理程序运行**之前**就保存好。而由于大多数指令都会修改寄存器的内容，硬件通常会提供专门的指令，使保存和恢复用户状态变得容易一些。

为了说得具体些，我们来看 x86 体系结构。当中断或陷阱发生时，硬件并不把全部工作都丢给处理程序软件去做，而是：

- 如果处理器处于用户模式，x86 把被中断进程的栈指针压入内核的中断栈，并切换到内核栈。

- x86 把被中断进程的指令指针压入栈。

- x86 把 x86 的**处理器状态字**（processor status word）压入栈。处理器状态字中包含一些控制位，例如被中断代码中最近一次算术运算的结果是正、是负还是零。为了让后续的条件分支指令能够正确执行，这些位必须被保存和恢复。

硬件在通过中断向量表跳转到中断处理程序**之前**，就把栈指针、程序计数器和处理器状态字的值保存好了。一旦处理程序开始运行，这些值就变成处理程序的了，而不再属于被中断的进程。

处理程序开始运行后，可以用 `pushad`（“push all double”）指令把其余的寄存器保存到栈上。这条指令保存全部 32 位 x86 整数寄存器。在 16 位 x86 上则改用 `pusha`。由于内核通常不执行浮点运算，除非内核要切换到另一个进程，否则这些寄存器不需要保存。

x86 体系结构还提供了配套的恢复状态的手段：`popad` 指令把栈上的一组整数寄存器值弹回寄存器；`iret`（从中断返回）指令把栈上的栈指针、指令指针和处理器状态字装入相应的处理器寄存器。

::: tip 快速模式切换的体系结构支持
有些处理器体系结构能够非常高效地执行用户模式和内核模式之间的切换，而另一些体系结构做这类切换则要慢得多。

SPARC 体系结构属于前者。SPARC 定义了一组**寄存器窗口**（register windows），其行为就像一个硬件栈。每个寄存器窗口都包含 SPARC 指令集所定义的一整套寄存器。当处理器执行过程调用时，就切换到一个新的窗口，于是编译器根本不需要在过程调用前后保存和恢复寄存器，过程调用因此相当快。（在递归足够深的时候，SPARC 会用光它的寄存器窗口；这时会触发一次异常，保存一半的窗口并继续执行。当处理器弹出它的最后一个窗口时又会发生一次异常，让内核重新装入已保存的窗口。）

在 SPARC 上，模式切换可以相当快。模式切换时，处理器切换到一个不同的寄存器窗口。内核处理程序随后就能运行，使用新窗口中的寄存器，而不会打扰被中断进程那份寄存器副本中的值。遗憾的是，这是有代价的：在 SPARC 上，不同进程之间的切换相当昂贵，因为内核需要保存和恢复每一个活动窗口的整个寄存器集合。

Motorola 88000 属于后者。88000 是一种早期的流水线体系结构；如今几乎所有现代计算机都采用流水线。为了提高性能，流水线体系结构同时执行多条指令。例如，一条指令正在取指，另一条正在译码，第三条正在完成一次浮点运算，第四条正在完成一次内存存储。当 88000 上发生中断或处理器异常时，流水线的操作被暂停，操作系统内核必须保存和恢复流水线的整个状态，才能维持对用户代码的透明性。

而大多数具有深度执行流水线的现代处理器，例如 x86，提供的是**精确中断**（precise interrupts）：硬件先按程序顺序完成被中断指令之前的所有指令；硬件会作废按程序顺序位于中断或陷阱之后的所有指令，即使处理器检测到中断时那条指令正在执行中。
:::

## 2.5　综合实例：x86 上的模式切换

处理中断、处理器异常或系统调用所需的高层步骤很简单，但其中的细节需要格外小心。

为了具体说明这种“精心设计”的代码是如何工作的，我们现在描述在 x86 体系结构上实现由中断触发的模式切换的一种方法。x86 上不同的操作系统遵循的都是这一基本思路，尽管细节各有差异。同样地，不同的体系结构要处理的是同一类问题，但它们可以借助不同的硬件支持来做到这一点。

首先，我们交代一些 x86 体系结构的背景知识。x86 采用分段机制，因此指针由两部分组成：(i) 段（segment），即一段内存区域，比如代码、数据或栈；(ii) 段内的偏移量（offset）。当前的用户级指令由代码段（`cs` 寄存器）加上指令指针（`eip` 寄存器）组合而成。类似地，当前的栈位置由栈段（`ss`）与栈段内的栈指针（`esp`）组合而成。当前的特权级存放在 `cs` 寄存器的低位，而不是存放在处理器状态字（`eflags` 寄存器）中。`eflags` 寄存器中含有若干条件码，它们作为指令执行的副产品被修改；`eflags` 寄存器还有另一些标志位用来控制处理器的行为，例如中断是否被屏蔽。

+ **屏蔽中断。** 硬件首先做的是：在处理器从用户模式切换到内核模式的过程中，阻止任何中断发生。

+ **保存三个关键值。** 硬件把栈指针（x86 的 `esp` 和 `ss` 寄存器）、执行标志（x86 的 `eflags` 寄存器）和指令指针（x86 的 `eip` 和 `cs` 寄存器）的值，保存到内部的临时硬件寄存器中。

+ **切换到内核中断栈。** 硬件随后把栈段/栈指针切换到内核中断栈的栈底，其位置由一个特殊的硬件寄存器指定。

+ **把三个关键值压入新栈。** 接着，硬件把内部保存的这些值存放到栈上。

+ **可选地保存错误码。** 某些类型的异常（例如缺页异常）会产生一个错误码，以提供关于该事件的更多信息；对于这些异常，硬件把这个错误码压入栈中，使它成为栈顶元素。对于其他类型的事件，软件中断处理程序则把一个哑值压入栈中，使得两种情况下的栈格式完全一致。

+ **调用中断处理程序。** 最后，硬件把代码段/程序计数器改为中断处理程序的入口地址。处理器中有一个特殊寄存器，其中存放着中断向量表在内核内存中的位置，这个寄存器只能由内核修改。中断类型被映射到该数组中的某个索引，代码段/程序计数器就被设置为该索引处的值。

至此，处理程序软件开始运行。

处理程序必须首先保存被中断进程其余的状态——在修改这些寄存器之前，它得先把它们保存下来！处理程序使用 x86 的 `pushad` 指令，把其余寄存器（包括当前栈指针）压入栈中。

<figcaption><span class="fig-label">图 2.12</span>在 x86 体系结构上，中断处理程序开始执行之后系统的状态。处理程序首先保存处理器寄存器的当前状态，因为它可能会覆盖这些寄存器。注意，栈指针被保存了两次：先是用户栈指针，然后是内核栈指针。</figcaption>
</figure>

如图 2.12 所示，此时内核的中断栈中保存着：(1) 由硬件保存的栈指针、执行标志和程序计数器；(2) 一个错误码或哑值；(3) 所有通用寄存器的一份副本（包括栈指针，但不包括指令指针和 `eflags` 寄存器）。

一旦处理程序把被中断线程的状态保存到栈上，它就可以随意使用这些寄存器，也可以往栈上压入更多的项。于是，处理程序现在可以去做它需要做的任何工作。

处理程序完成之后，就可以恢复被中断的进程。为此，处理程序把保存在栈上的寄存器弹出，这会恢复除执行标志、程序计数器和栈指针以外的所有寄存器。在 x86 指令集上，通常使用 `popad` 指令来完成。处理程序还要把那个错误值从栈上弹出。

最后，处理程序执行 x86 的 `iret` 指令，从内核的中断栈中恢复代码段、程序计数器、执行标志、栈段和栈指针。

这就把进程状态恢复到中断发生之前的确切状态，进程继续往下执行，就像什么都没有发生过一样。

当硬件产生异常以便在内核中模拟某条指令时（例如缺少浮点硬件），会出现一个细小却很重要的细节。如果处理程序返回到引发异常的那条指令，异常会立刻再次发生！为了防止陷入无限循环，异常处理程序会修改保存在栈底的程序计数器，使它指向引发模式切换的那条指令之后紧邻的那条指令。这样，`iret` 指令就能返回到用户进程中的正确位置。

对于系统调用陷阱，Intel x86 硬件在保存用户级状态时就完成了这个递增，陷阱之后那条指令的程序计数器被保存在内核的中断栈上。

## 2.6　实现安全的系统调用

操作系统内核为进程执行构造出一个受限环境，以限制错误程序和恶意程序对系统可靠性的影响。任何时候，只要进程需要执行超出其保护域的动作——创建新进程、从键盘读入、或者写一个磁盘块——它都必须通过系统调用，请求操作系统代为执行这个动作。

系统调用营造出这样一种假象：操作系统内核不过是一组供用户程序使用的库例程。对用户程序而言，内核提供了一组系统调用过程，每个都有自己的参数和返回值，可以像其他任何例程一样被调用。用户程序不必关心内核是如何实现这些调用的。

实现系统调用，要求操作系统定义一套**调用约定**（calling convention）——如何命名系统调用、如何传递参数，以及如何跨用户/内核边界接收返回值。通常，操作系统采用的约定与编译器用于普通过程的约定相同——即通过寄存器和执行栈传递参数的某种组合。

一旦参数被摆放成正确的格式，用户级程序就可以执行陷阱指令来发起系统调用，把控制权转交给内核。系统调用与中断、处理器异常一样，共用同一套在用户模式和内核模式之间切换的机制。事实上，x86 上用于因系统调用而陷入内核的指令就叫 `int`，意为“软件中断”。

在内核内部，每个系统调用由一个过程来实现。这个过程的行为与在内核内部发起调用时完全一样，但有一个显著区别：内核在实现系统调用时，必须保护自己免受可能因接口被误用而发起的一切错误和攻击。当然，绝大多数应用程序会正确地使用接口！但是，应用程序中的错误决不能让内核崩溃，计算机病毒也决不能借助系统调用接口来夺取内核的控制权。可以把它看作防御性编程的一个极端版本：内核应当始终假定，传给系统调用的参数是被刻意设计得尽可能恶意的。

我们用一对存根把这两种视角——用户程序调用系统调用，以及内核实现系统调用——连接起来。**一对存根**是指在两个环境之间居中调解的一对过程，这里就是在用户程序与内核之间居中调解。存根也用于调解分布式系统中计算机之间的过程调用。

图 2.13 展示了系统调用所涉及的这一连串步骤：

+ 用户程序以正常方式调用用户存根，并不知道这个过程的实现其实位于内核之中。

+ 用户存根填入该系统调用的代码，并执行陷阱指令。

+ 硬件把控制权转交给内核，通过中断向量表跳转到系统调用处理程序。该处理程序充当内核一侧的存根，复制并检查参数，然后调用该系统调用的内核实现。

+ 系统调用完成之后，返回到处理程序。

+ 处理程序返回到用户级，即存根中的下一条指令处。

+ 存根返回给调用者。

```asm
 // using the standard calling convention for the x86.

 open:
 // Put the code for the system call we want into %eax.
     movl #SysCallOpen, %eax

 // Trap into the kernel.
     int #TrapCode

 // Return to the caller; the kernel puts the return value in %eax.
     ret

```

下面我们更详细地描述这些步骤。图 2.14 展示了 x86 上用户级存根的行为。操作系统为每个系统调用提供一个库例程，它接收参数，按照调用约定重新组织它们，然后执行陷阱指令。内核返回时，存根把内核给出的结果返回。当然，用户程序并非非得使用这个库例程——它完全可以直接陷入内核；反过来，内核必须保护自己免受那些不按格式摆放参数的恶意程序的侵害。

系统调用的调用约定是人为约定的。在图 2.14 中，代码把参数放在用户栈上，并把系统调用代码存入 `%eax` 寄存器。返回值同样通过 `%eax` 传回，因此返回时不需要再做任何工作。

`int` 指令在通过中断向量表跳转到系统调用处理程序之前，先把程序计数器、栈指针和 eflags 保存到内核栈上。内核处理程序接着保存所有在函数调用期间必须保持不变的其他寄存器。然后，它检查 `%eax` 中的系统调用整数代码，确认它是一个合法的操作码，再调用该系统调用对应的存根。

内核存根有四项任务：

- **定位系统调用参数。** 与普通的内核过程不同，系统调用的参数存放在用户内存中，通常位于用户栈上。当然，用户栈指针可能是被破坏过的！即使它有效，它也是一个虚拟地址，而不是物理地址。如果系统调用带有指针参数（例如文件名或缓冲区），存根必须检查该地址，确认它是用户域内的合法地址。如果合法，存根就把它转换成物理地址，以便内核能够安全地使用它。在图 2.14 中，指向表示文件名的字符串的指针存放在栈上；因此，存根必须同时检查和转换栈地址与字符串指针这两者。

- **校验参数。** 内核还必须保护自己，免受参数在格式或内容上的恶意或意外错误。文件名通常是一个以零结尾的字符串，但内核不能相信用户代码总会正确工作。文件名可能已经被破坏；它可能指向应用程序区域之外的内存；它可能起始于应用程序的内存区域之内、却延伸到区域之外；应用程序可能没有访问该文件的权限；该文件可能并不存在；如此等等。如果检测到错误，内核就把它返回给用户程序；否则，内核代表应用程序执行该操作。

- **先复制后检查。** 在大多数情况下，内核在执行必要检查之前，先把系统调用参数复制到内核内存中。这样做是为了防止应用程序在存根检查完某个值**之后**、但在该参数被例程的实际实现使用**之前**修改它。这称为**检查时与使用时的时间差**（time of check vs. time of use，TOCTOU）攻击。举例来说，应用程序可以用一个合法的文件名调用 `open`，但在检查之后，把字符串的内容改成一个不同的名字，比如指向包含另一个用户私密数据的文件。TOCTOU 并不是什么新攻击——最早的案例可以追溯至 1960 年代中期。尽管看起来进程一旦执行系统调用就必然会停下来，但情况并非总是如此。例如，如果一个进程与另一个进程共享内存区域，那么这两个进程协同配合就可以发起 TOCTOU 攻击。类似地，运行在两个处理器上的并行程序也可以发起 TOCTOU 攻击：一个处理器陷入内核，而另一个在恰好合适（或者说最不合适）的时刻修改这个字符串。请注意，内核必须在每一种情况下都正确无误，而攻击者却可以反复尝试任意多次，直到成功为止。

- **复制回任何结果。** 为了让用户程序能够访问系统调用的结果，存根必须把结果从内核复制到用户内存中。同样，内核在执行复制之前，必须先检查用户地址，并把它转换为内核地址。

综合起来，图 2.15 给出了 `open` 系统调用的内核存根。在这种情况下，返回值可以放进一个寄存器，因此存根可以直接返回；而在其他情况下，例如文件读操作，存根就需要把数据复制回用户级缓冲区。

<div class="code-cap"><span class="code-label">图 2.15</span>内核中 <code>open</code> 系统调用的存根例程。内核在使用系统调用的所有参数之前，必须先校验它们。</div>

```c
 int KernelStub_Open() {
     char *localCopy[MaxFileNameSize + 1];

 // Check that the stack pointer is valid and that the arguments are stored at
 // valid addresses.

     if (!validUserAddressRange(userStackPointer, userStackPointer + size of arguments))
         return error_code;

 // Fetch pointer to file name from user stack and convert it to a kernel pointer.

     filename = VirtualToKernel(userStackPointer);

 // Make a local copy of the filename.  This prevents the application
 // from changing the name surreptitiously.

 // The string copy needs to check each address in the string before use to make sure
 // it is valid.

 // The string copy terminates after it copies MaxFileNameSize to ensure we
 // do not overwrite our internal buffer.

     if (!VirtualToKernelStringCopy(filename, localCopy, MaxFileNameSize))
         return error_code;

 // Make sure the local copy of the file name is null terminated.

     localCopy[MaxFileNameSize] = 0;

     if (!UserFileAccessPermitted(localCopy, current_process)
         return error_code;

 // Finally, call the actual routine to open the file.  This returns a file

 }

```

系统调用完成之后，处理程序弹出所有已保存的寄存器（`%eax` 除外），并用 `iret` 指令返回到陷阱之后紧邻的用户存根，使用户存根得以返回到用户程序。

## 2.7　启动一个新进程

到目前为止，我们已经说明了在发生中断、处理器异常或系统调用时，如何把控制权从用户级进程转交给内核，以及内核做完工作之后如何在用户级恢复执行。

现在我们来看，最初究竟是怎样在用户级开始运行的。内核必须：

- 分配并初始化进程控制块。

- 为进程分配内存。

- 把程序从磁盘复制到新分配的内存中。

- 为用户级执行分配一个用户级栈。

- 为处理系统调用、中断和处理器异常分配一个内核级栈。

要让程序开始运行，内核还必须：

- **把参数复制到用户内存中。** 启动一个程序时，用户可以给它传入参数，这很像调用一个过程。举例来说，当你在 MacOS 或 Windows 中点击某个文件图标时，窗口管理器会请求内核启动与该文件相关联的应用程序，并把要打开的文件名传给它。内核把这个文件名从窗口管理器进程的内存中，复制到新进程内存中一块特殊的区域。按照惯例，传给进程的参数被复制到用户级栈的栈底，用户栈指针随之递增，这样程序开始运行时这些地址就不会被覆盖。

- **把控制权转移到用户模式。** 新进程启动时，并没有任何已保存的状态可供恢复。虽然可以为这种情况专门写一段代码，但大多数操作系统会复用同一段退出内核的代码，既用来启动新进程，也用来从系统调用返回。创建新进程时，我们为它分配一个内核栈，并在内核栈底部预留空间，用来存放其用户空间寄存器、程序计数器、栈指针和处理器状态字的初始值。要启动新程序，我们随后切换到这个新栈，并跳转到中断处理程序的末尾。当处理程序执行 `popad` 和 `iret` 时，处理器就“返回”到用户程序的开头。

最后，虽然你可以把用户程序看作是从调用 `main` 开始的，但实际上编译器插入了一层间接。它在进程内存中内核将要跳转进来的那个位置放了一个存根。存根的任务是调用 `main`，然后在 `main` 返回时调用 `exit`——即终止进程的系统调用。如果没有这个存根，从 `main` 返回的用户程序会试图弹出返回程序计数器，而栈上并没有这样的地址，处理器就会开始执行随机的代码。

```c
    start(arg1, arg2) {
        main(arg1, arg2);  // Call program main.
        exit();     // If main returns, call exit.
    }

```

## 2.8　实现上调

应用程序与操作系统内核之间的绝大部分通信，都可以用系统调用来完成。当程序需要执行某个受保护的操作时，它可以陷入内核，请内核代为执行。同样地，如果应用程序需要内核内部的数据，也可以用系统调用把它取回来。

但要让应用程序能够实现类似操作系统的功能，我们还需要更多东西。内核之所以需要基于中断的事件传递，是出于种种理由；出于同样的许多理由，应用程序也能从“被告知发生了需要立刻处理的事件”中获益。在本书中，我们会反复看到这样一种模式：需要把内核的某个部分**虚拟化**，好让应用程序的行为更像操作系统。我们把被虚拟化的中断和异常称为**上调**（upcall）。在 UNIX 中它们叫做**信号**（signal）；在 Windows 中它们是**异步事件**（asynchronous event）。

用上调来立即传递事件，有若干用途：

- **抢占式用户级线程。** 正如操作系统内核在单个处理器上运行多个进程一样，一个应用程序也可以在一个进程中运行多个任务，或者说线程。用户级线程包可以把周期性的定时器上调当作触发器来切换任务，从而在用户级任务之间更均匀地分享处理器，或者用来制止某个失控的任务——例如，网页浏览器需要终止一个嵌入的第三方脚本。

- **异步 I/O 通知。** 大多数系统调用会一直等到所请求的操作完成才返回。如果进程在这段时间里还有其他工作要做，那该怎么办？一种做法是**异步 I/O**：系统调用发起请求后立即返回。之后，应用程序可以轮询内核，查询 I/O 是否完成；也可以在 I/O 完成时，通过一个上调向应用程序发出单独的通知。

- **进程间通信。** 大多数进程间通信都可以用系统调用来处理——一个进程写入数据，另一个进程稍后再把它读出来。但如果某个进程产生的事件需要另一个进程立刻关注，那就需要内核上调。举例来说，当调试器想要挂起或恢复某个进程时，UNIX 会发送一个上调来通知它。另一个用途是注销登录——通知各个应用程序：它们应当保存文件数据并干净地终止。

- **用户级异常处理。** 前面我们讲过这样一种机制：诸如除零错误之类的处理器异常由内核来处理。然而，许多应用程序有自己的异常处理例程，例如用来确保应用程序在关闭之前把文件保存好。为此，操作系统在收到处理器异常时必须通知应用程序，好让应用程序的运行时、而不是内核来处理这个事件。

- **用户级资源分配。** 操作系统负责分配资源——决定哪些用户和进程应当得到多少 CPU 时间、多少内存，如此等等。反过来，许多应用程序是资源自适应的——能够针对不同的 CPU 时间或内存数量来优化自身的行为。Java 的垃圾回收就是一个例子。在一定限度内，Java 进程可以通过改变垃圾回收器的运行频率，来适应不同的可用内存量：内存越多，Java 运行回收器所需的时间就越少，执行也就越快。为此，操作系统必须在进程所分得的资源发生变化时通知它——例如，因为某个其他进程需要更多或更少的内存。

从内核发往用户进程的上调并非总是必需的。许多应用程序采用事件循环的结构反而更简单：轮询事件，然后逐个处理每个事件。在这种模型中，内核可以通过向进程发送那些不需要立即处理的事件来传递数据。事实上，直到最近，Windows 一直都缺乏把上调立即投递到用户级程序的支持。

- **信号的类型。** 内核定义了数量有限的若干种信号类型供进程接收，以此取代由硬件定义的中断和处理器异常。

- **处理程序。** 每个进程为每种信号类型定义自己的处理程序，这很像内核定义自己的中断向量表。如果进程没有为某个特定信号定义处理程序，内核就改去调用一个默认的处理程序。

- **信号栈。** 应用程序可以选择让 UNIX 信号处理程序运行在进程正常的执行栈上，也可以运行在由用户进程在用户内存中分配的一个专门的信号栈上。在正常栈上运行信号处理程序，会使信号处理程序更难操纵栈——例如，当运行时需要抛出一个语言级异常的时候。

- **信号屏蔽。** 对于在针对某类事件的信号处理程序执行期间所发生的事件，UNIX 会推迟其信号；相反，一旦处理程序返回内核，该信号就被投递出去。UNIX 还提供了一个系统调用，让应用程序按需屏蔽信号。

- **处理器状态。** 内核把程序停止处的程序计数器、栈指针和通用寄存器的已保存状态复制到信号栈上。通常，信号处理程序返回时，内核把这些保存的状态重新装入处理器，以恢复程序执行。信号处理程序也可以修改这些保存的状态——例如，让内核在处理程序返回时恢复执行另一个用户级任务。

把 UNIX 信号投递给用户进程的机制，只需要对前面已经讲过的、跨越内核/用户边界转交控制权的那些技术做一点小小的改动。举例来说，发生定时器中断时，硬件和内核中断处理程序会保存用户级计算的状态。要把这个定时器中断投递到用户级，内核就把那份已保存的状态复制到信号栈底部，把保存的状态重置为指向信号处理程序和信号栈，然后退出内核处理程序。随后 `iret` 指令就在信号处理程序处恢复用户级执行。信号处理程序返回时，这些步骤被逆向展开：处理器状态从信号处理程序复制回内核内存，`iret` 则返回到原来的计算。

## 2.9　案例研究：引导操作系统内核

计算机引导时，会把机器的程序计数器设置为从内存中一个预先确定的位置开始执行。由于计算机此时还没有运行起来，最初的机器指令必须在电源刚一接通、系统还来不及初始化自己的 DRAM 之前就立刻取指并执行。因此，系统通常使用一种特殊的只读硬件存储器（**引导 ROM**，Boot ROM）来存放引导指令。在大多数 x86 个人计算机上，这个引导程序叫做 BIOS，即“基本输入输出系统”（Basic Input/Output System）。

试图把整个内核都塞进 ROM 有若干弊端。最严重的问题是操作系统会很难更新：ROM 中的指令在计算机出厂时就已经固定，（除极少数情况外）永远不会改变。如果更新 BIOS 的过程中出错，机器就可能陷入永久不可用的状态——既无法引导，又无法完成 BIOS 的更新。

相比之下，操作系统需要频繁更新，因为不断有缺陷和安全漏洞被发现并修复。这一点，再加上 ROM 存储相对较慢且较贵的事实，都说明应当只在 BIOS 中放入少量的代码。

于是，BIOS 提供了一层间接，如图 2.18 所示。BIOS 从磁盘（或闪存）上一个固定的位置，把一块固定大小的字节读入内存。这块字节称为**引导加载程序**（bootloader）。一旦 BIOS 把引导加载程序复制进内存，它就跳转到这块代码的第一条指令。在一些较新的机器上，BIOS 还会检查引导加载程序没有被计算机病毒篡改过。（如果病毒能够修改引导加载程序并让 BIOS 跳转到它，那么病毒就控制了这台机器。）作为检查手段，引导加载程序在存储时会附上一个**加密签名**（cryptographic signature）——它是文件中各个字节与一个私有加密密钥的一个经过特殊设计的函数，使得持有相应公开密钥的人能够验证该文件确实是由某个被授权的实体生成的。对于一个没有私有密钥的攻击者来说，要另外造出一个带有合法签名的不同文件，在计算上是不可行的。BIOS 检查引导加载程序的代码与签名是否匹配，以此验证它的真实性。

引导加载程序接着把内核装入内存，并跳转到它。同样，引导加载程序可以检查操作系统的加密签名，以验证它没有被病毒篡改过。内核的可执行映像通常存放在文件系统中。因此，BIOS 要找到引导加载程序，只需从磁盘读出一块原始字节；而引导加载程序则必须知道如何从文件系统中读取，才能找到并读出操作系统映像。

内核开始运行后，就可以初始化自己的数据结构，包括建立中断向量表，使之指向各个中断、处理器异常和系统调用的处理程序。随后内核启动第一个进程，通常是用户登录页面。为了运行这个进程，操作系统把登录程序的代码从它在磁盘上的位置读进来，并用前面讲过的启动进程的过程，跳转到该程序的第一条指令。登录进程在需要内核服务时（例如在屏幕上渲染登录提示符），又可以通过系统调用陷入内核。第 3 章我们会讨论进程要做有用的工作所需的那些系统调用。

## 2.10　案例研究：虚拟机

有些操作系统内核在用户级提供一整台**虚拟机**（virtual machine）的抽象。在这种情形下，中断、处理器异常和系统调用又是如何工作的呢？为了避免在讨论虚拟机时产生混淆，我们先回顾一下第 1 章引入的几个术语。提供虚拟机抽象的那个操作系统称为**宿主操作系统**（host operating system）；运行在虚拟机内部的那个操作系统称为**客户操作系统**（guest operating system）。

宿主操作系统营造出客户内核运行在真实硬件上的假象。举例来说，为了给客户机提供一块磁盘，宿主内核把一块虚拟磁盘模拟成物理磁盘上的一个文件；为了让客户内核能够访问网络，宿主内核用物理网络数据包模拟出一张虚拟网卡。同样地，宿主内核必须管理内存，以营造出“客户内核在管理自己的内存保护”的假象，尽管它运行时使用的是虚拟地址。我们将在第 10 章更详细地讨论虚拟机的地址转换问题。

宿主内核是如何管理客户进程与客户内核之间的模式切换的呢？在引导期间，宿主内核会初始化自己的中断向量表，使其指向宿主内核内存中的中断处理程序。当宿主内核启动虚拟机时，客户内核开始运行，就像它正在被引导一样：

+ 宿主从虚拟磁盘上装入客户引导程序，并启动它运行。

+ 客户引导程序从虚拟磁盘上把客户内核装入内存，并启动它运行。

+ 客户内核随即初始化自己的中断向量表，使其指向客户中断处理程序。

+ 客户内核从虚拟磁盘上把一个进程装入客户内存。

+ 为了启动一个进程，客户内核发出指令，要求在用户级恢复执行，例如在 x86 上使用 `iret`。由于改变特权级属于特权操作，这条指令会陷入宿主内核。

+ 宿主内核模拟所请求的这次模式切换，就像处理器直接执行了它一样。它把程序计数器、栈指针和处理器状态字恢复成客户操作系统所期望的那样。注意，宿主内核必须保护自己免受客户操作系统中缺陷的影响，因此它还必须检查这次模式切换的合法性——确保客户内核不是在偷偷地试图让宿主内核“切换”到内核代码中的某个任意位置。

接着考虑当客户用户进程执行系统调用时会发生什么，如图 2.19 所示。对硬件而言，只存在一个内核，那就是宿主操作系统。因此，陷阱指令会陷入宿主内核的系统调用处理程序。当然，这个系统调用本来并不是发给宿主的！宿主内核要模拟的是：假如这条系统调用指令发生在运行客户操作系统的真实硬件上，本来会发生的一切：

+ 宿主内核把指令计数器、处理器状态寄存器和用户栈指针保存到客户操作系统的中断栈上。

+ 宿主内核把控制权转交给客户内核的中断处理程序入口，但客户内核此时是以用户模式的特权级运行的。

+ 客户内核执行这个系统调用——保存用户状态并检查参数。

+ 当客户内核试图从系统调用返回到用户级时，这会引发一次处理器异常，重新落回宿主内核。

+ 宿主内核随后恢复该用户进程的状态，使其在用户级继续运行，就好像客户操作系统能够直接返回到那里一样。

宿主内核以类似的方式处理处理器异常，但有一点需要特别注意。虚拟机产生的某些异常来自用户进程，宿主内核把这些异常转发给客户内核去处理；另一些异常则是由客户内核自身产生的（例如当它试图执行特权指令时），这些异常由宿主内核自己来模拟。因此，宿主内核必须跟踪虚拟机当前是运行在虚拟用户模式还是虚拟内核模式。

硬件把中断向量送到宿主内核。定时器中断需要特殊处理，因为时间在宿主中可能已经流逝，而在客户中却尚未流逝。当定时器中断发生时，可能已经过去了足够多的虚拟时间，客户内核的定时器中断也该到期了。如果是这样，宿主内核就从这次中断返回到客户内核的中断处理程序。客户内核又可能切换客户进程；它的 `iret` 会引发一次处理器异常，返回到宿主内核，宿主内核随后再恢复正确的那个客户进程。

处理 I/O 中断则简单一些：虚拟设备的模拟完全不必真的像一台设备。当客户内核向虚拟磁盘发出请求时，内核把指令写入该磁盘设备的缓冲区描述符环；宿主内核把这些指令翻译成对虚拟磁盘的操作。宿主内核可以随心所欲地模拟这个磁盘请求——例如通过普通的文件读写，再把结果复制到客户内核内存中，就好像真的存在 DMA 硬件一样。客户内核预期在虚拟磁盘完成工作时收到一个中断；这个中断可以由定时器中断触发，但被向量到客户磁盘中断处理程序，而不是客户定时器中断处理程序。

::: tip 操作系统的硬件支持
我们已经介绍了若干支持操作系统的硬件机制：

- **特权级**：用户级与内核级。

- **特权指令**：只能在内核模式下使用的指令。

- **内存转换**：阻止用户程序访问内核的数据结构，并有助于内存管理。

- **处理器异常**：在发生特权违例或其他意外事件时陷入内核。

- **定时器中断**：在时间到期时把控制权交还给内核。

- **设备中断**：把控制权交还给内核，以通知 I/O 完成。

- **处理器间中断**：促使另一个处理器把控制权交还给内核。

- **中断屏蔽**：阻止中断在不合时宜的时刻被投递。

- **系统调用**：陷入内核，代表用户程序执行某个特权动作。

- **从中断返回**：从内核模式切换到用户模式，并切换到用户进程中的某个特定位置。

- **引导 ROM**：把磁盘上的启动例程装入内存的代码。

为了支持线程，我们还需要另外一种机制，将在第 5 章介绍：

- **原子读—改—写指令**：用于在多线程程序中实现同步。
:::

## 2.11　总结与未来方向

进程这一概念——即以受限权限执行任意用户程序的能力——已经取得了引人注目的成功。除了一次只运行单个应用的设备（例如嵌入式系统和游戏机）之外，每一个获得商业成功的操作系统都提供了进程隔离。

这一成功的原因显而易见。倘若没有进程隔离，计算机系统会脆弱得多，也更不安全。就在大约十年前，个人计算机每天崩溃一次还是司空见惯的事。如今，笔记本电脑可以连续工作数周而无需重启。而与此同时，这些系统上的操作系统和应用软件反而变得更加复杂。尽管其中一部分改善要归功于硬件可靠性的提高和自动化的缺陷追踪，进程隔离一直是构建更可靠的系统软件所依托的一项关键技术。

进程隔离对于构建更安全的计算机系统同样不可或缺。倘若没有隔离，计算机用户就不得不信任装入计算机的每一个应用程序，而不仅仅是信任操作系统代码。然而在实践中，完全的进程隔离至今仍更像是一种追求，而非既成事实。大多数操作系统在面对恶意应用时依然脆弱，因为攻击者可以利用内核实现中的任何一处漏洞。哪怕内核中只有一个缺陷，也足以让整个系统暴露在风险之下。及时为系统打上最新的补丁可以提供一定程度的防护，但从网上下载并安装来历不明的软件依然是不可取的。

在未来，我们很可能会看到三种互为补充的发展趋势：

- **操作系统对细粒度保护的支持。** 进程隔离正变得更加灵活、更加细粒度，以反映不同应用程序所具有的不同信任等级。今天，典型的情况是：一个用户应用拥有该用户所拥有的全部权限。这就使得一个伪装成屏幕保护程序的病毒，能够窃取或破坏该用户的数据，而无须先攻陷操作系统。智能手机操作系统已经开始加入更完善的控制机制，阻止那些并无“知情必要”的应用程序访问敏感信息，例如手机所在的位置或者经常拨打的电话号码列表。

- **应用层沙箱。** 越来越多的应用程序本身正在变成小型的操作系统，能够安全地执行第三方软件，以扩展和改善用户体验。精巧的脚本可以定制网站的行为；Web 浏览器必须高效且彻底地隔离这些脚本，使它们无法窃取用户的数据或破坏浏览器。其他一些应用——例如数据库和桌面出版系统——也在朝着需要应用层沙箱的方向发展。Google 的 Native Client 和微软的应用程序域（Application Domains）就是两个例子，它们在用户级提供了通用的、安全的第三方代码执行环境。

- **面向虚拟化的硬件支持。** 虚拟机在操作系统之下又提供了一层保护。即使虚拟机上由客户操作系统运行的某个恶意进程能够破坏其内核，影响范围也仅限于那台虚拟机。在虚拟机接口之下，宿主操作系统需要在不同虚拟机之间提供隔离；这在实践中要容易得多，因为虚拟机接口比内核的系统调用接口简单得多。例如，在数据中心里，虚拟机让用户得以灵活运行任何应用，同时不会危及数据中心的运转。计算机制造商正在重新设计处理器体系结构，以降低运行虚拟机的代价。例如，在某些新型处理器上，客户操作系统可以直接处理自己的中断、处理器异常和系统调用，而不必由宿主操作系统来居中调解。同样地，I/O 设备制造商也在重新设计接口，使之能够与客户操作系统之间直接传输数据，而无须经由宿主内核。
