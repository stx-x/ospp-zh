虚拟现实的愿景令人神往。谁不想拥有这样一种能力：不必离开全息甲板（holodeck），就能去任何地方旅行？当然，这一愿景离成为现实还差得很远。理论上，只要针对你的动作去调整输入到你每一种感官的信号，虚拟现实系统就能完美地布置出场景。然而，你的感官并不那么容易被控制。也许我们很快就能为视觉提供沉浸式的环境，但平衡感、听觉、味觉和嗅觉还需要长得多的时间。触觉、本体感受（prioperception，即感到自己靠近另一物体的感觉）以及 G 力（g-forces）则更加遥远。这些当中只要有一样出了错，幻觉就消失了。

我们能否为计算机程序营造一个虚拟现实的环境？在 UNIX 的 I/O 接口中，我们已经见过这样的例子：程序并不需要知道——有时也无法分辨——它的输入和输出究竟是文件、设备，还是其他进程。

在接下来的三章里，我们要把这个想法大大推进一步。只要让操作系统掌管*地址转换*（address translation），也就是把程序自以为正在引用的那个内存地址，转换成该内存单元在物理内存中的实际位置，就能实现数量惊人的高级系统特性。从程序员的角度看，地址转换是透明地发生的——尽管程序的内存实际存放的位置与它所以为的位置完全不同，程序的行为依然正确。

你大概在早年的某门编程课上听老师说过：内存地址就只是一个地址。链表中的指针里存放的，是它所指向对象的真实内存地址；一条跳转指令里包含的，是下一条要执行指令的真实内存地址。这是一种有用的虚构！程序员往往最好不要去想每一次内存引用是如何被转换成它所引用的数据或指令的。而在实践中，幕布之下发生着相当多的活动。

地址转换是一个简单的概念，但它最终被证明强大得不可思议。操作系统能用地址转换做些什么？下面这份清单并不完整：

- **进程隔离**。正如我们在第 2 章所讨论的，要保护操作系统内核和其他应用不被有缺陷或恶意的代码破坏，就需要有能力限制应用的内存引用。同样，应用也可以利用地址转换，为第三方扩展构造安全的执行沙箱（sandbox）。

- **进程间通信**。进程常常需要彼此协调，而一种高效的做法是让这些进程共享一块公共的内存区域。

- **共享代码段**。同一个程序的多个实例可以共享该程序的指令，从而减小它们占用的内存，并让处理器高速缓存更有效率。同样，不同的程序也可以共享公共库。

- **程序初始化**。借助地址转换，我们可以在程序的所有代码尚未从磁盘装入内存之前，就让它开始运行。

- **高效的动态内存分配**。当进程扩大自己的堆、或线程扩大自己的栈时，我们可以利用地址转换陷入内核，只在真正需要时才为这些用途分配内存。

- **高速缓存管理**。正如我们将在下一章解释的，操作系统可以通过一种称为页着色（page coloring）的机制，安排程序在物理内存中的位置，从而提高高速缓存的效率。

- **程序调试**。操作系统可以利用内存转换，防止有缺陷的程序覆写自己的代码区；通过在更早的阶段捕获指针错误，调试起来会容易得多。调试器也利用地址转换来设置数据断点，在程序引用某个特定内存位置时让它停下来。

- **高效的 I/O**。服务器操作系统常常受限于它们与磁盘和网络之间传输数据的速率。地址转换使得数据可以在用户态应用与 I/O 设备之间安全地直接传输。

- **内存映射文件**。对许多应用来说，一种方便而高效的抽象是把文件映射到地址空间里，这样文件的内容就可以用程序指令直接引用。

- **虚拟内存**。操作系统可以为应用提供这样一种抽象：它可以使用的内存比某台具体计算机上实际安装的物理内存更多。

- **检查点与重启**。长期运行的程序，其状态可以被定期做成检查点（checkpoint），这样一旦程序或系统崩溃，就可以从保存的状态重新启动。关键的挑战在于，要在程序继续运行的同时，为它的数据生成一份内部一致的检查点。

- **持久数据结构**。操作系统可以提供一块持久内存区域的抽象，对该区域中数据结构的修改能够在程序崩溃和系统崩溃之后依然保留。

- **进程迁移**。一个正在执行的程序可以被透明地从一台服务器搬到另一台服务器，例如为了负载均衡。

- **信息流控制**。在安全上再加一层，是核实程序没有把你的私人数据发送给第三方；例如，一个智能手机应用可能需要访问你的通讯录，但不应该被允许把这些数据传出去。地址转换可以作为管控信息进出系统的基础。

- **分布式共享内存**。利用地址转换，我们可以透明地把一个服务器集群变成一台大规模的共享内存并行计算机。

本章聚焦于实现地址转换所需的机制，因为它是上述所有服务的基础。在接下来的两章里，我们将讨论操作系统和应用如何利用这些机制来提供这些服务。

为了提高运行时的效率，大多数系统都有专门的硬件来完成地址转换，这些硬件由操作系统内核管理。不过，在某些系统中，转换是由可信的编译器、链接器或字节码解释器提供的；在另一些系统中，则由应用自己完成指针转换，以此管理自身数据结构的状态；还有一些系统采用混合模式，地址同时在软件和硬件中转换。这种选择通常是在性能、灵活性和成本之间做出的工程权衡。不过，无论采用哪种机制来实现转换，所提供的功能往往是一样的。本章将涵盖一系列硬件与软件机制。

**本章导读：**

- **地址转换的概念**。我们先给出一个概念框架，用以理解硬件和软件的地址转换。（8.1 节）

- **灵活的地址转换**。我们首先关注硬件地址转换：我们问，怎样才能把硬件设计得给操作系统内核提供最大的灵活性？（8.2 节）

- **高效的地址转换**。我们给出的方案看起来灵活，却慢得可怕。接下来讨论在不牺牲灵活性的前提下让地址转换高效得多的机制。（8.3 节）

- **软件保护**。越来越多的软件编译器和运行时解释器正在利用地址转换技术来实现操作系统的功能。当转换由软件而不是硬件完成时，会发生哪些变化？（8.4 节）

## 8.1　地址转换的概念

<figure class="book-figure">
<img src="/figures/vol3/image00283.png" alt="图 8.1" loading="lazy">
<figcaption><span class="fig-label">图 8.1</span>地址转换的抽象表示。转换器把程序产生的（虚拟）内存地址转换为物理内存地址。</figcaption>
</figure>

把地址转换看成一个黑箱，它就是一个简单的函数，如图 8.1 所示。转换器接收进程产生的每一次指令内存引用和数据内存引用，检查该地址是否合法，再把它转换成一个物理内存地址，用来取指令、取数据或存数据。数据本身——也就是内存中存放的内容——原样返回，不做任何变换。转换通常由硬件实现，而操作系统内核通过配置这些硬件来达成自己的目标。

本章的任务，就是把这个黑箱内部如何工作讲清楚。如果现在就问你打算怎样实现它，你最初的几个猜测很可能就八九不离十。如果你说可以用数组、树或哈希表，那你就说对了——这些做法都曾被真实的系统采用过。

既然可以有多种不同的实现，我们该如何评价这些备选方案？下面是我们可能希望一个转换黑箱达到的一些目标；我们最终得到的设计，取决于我们如何在众多目标之间取得平衡。

- **内存保护**。我们需要有能力限制进程对某些内存区域的访问，例如阻止它访问不属于该进程的内存。不过，我们也常常希望限制程序对自身内存的访问，例如防止指针错误覆写代码区，或者在程序引用某个特定数据位置时陷入调试器。

- **内存共享**。我们希望允许多个进程共享选定的内存区域。这些共享区域可能很大（例如在多个执行同一程序的进程之间共享该程序的代码段），也可能相对较小（例如共享一个公共库、一个文件或一个共享的数据结构）。

- **灵活的内存放置**。我们希望让操作系统能够灵活地把一个进程（以及进程的各个部分）放到物理内存中的任意位置；这样我们就能更紧凑地使用物理内存。正如我们将在下一章看到的，把进程数据分配到物理内存位置上的这种灵活性，还能让我们更有效地利用片上高速缓存。

- **稀疏地址**。许多程序都有多个动态内存区域，它们会在程序执行过程中改变大小：存放数据对象的堆、每个线程的栈，以及内存映射文件。现代处理器具有 64 位地址空间，使每个动态对象都有充足的空间按需增长，但这会让转换函数变得更复杂。

- **运行时查找的效率**。每一次取指令、每一次数据装入和存储都会发生硬件地址转换。如果一次查找平均而言比指令本身的执行还要慢得多，那就不切实际了。起初，我们要讨论的许多方案看起来会显得极不实用！我们将讨论一些方法，让即便最迂回的转换系统也能高效运转。

- **紧凑的转换表**。我们还希望转换在空间上的开销尽可能小；我们需要的任何数据结构，相对于所管理的物理内存量都应当很小。

- **可移植性**。不同的硬件体系结构在如何实现转换上做出不同的选择；如果操作系统内核要能容易地移植到多种处理器体系结构上，它就必须能够把自己（与硬件无关）的数据结构映射到每种体系结构的具体能力上。

我们最终会得到一个相当复杂的地址转换机制，因此讨论将从最简单的机制开始，只在需要时才添加功能。在讨论过程中，请始终牢记内存的两种视图，这会有帮助：进程看到的是它自己的内存，用的是它自己的地址。我们把这类地址称为*虚拟地址*（virtual address），因为它们未必对应任何物理上的真实位置。相反，对内存系统而言，只有*物理地址*（physical address）——内存中的真实位置。从内存系统的角度看，它拿到的是物理地址，据此查找并存入数值。转换机制就是在两种视图之间做转换：从虚拟地址转换为物理内存地址。

::: tip 链接器与加载器中的地址转换
即使没有内核与用户之间的边界，多道程序设计也需要某种形式的地址转换。在多道程序系统上，编译一个程序时，编译器并不知道其他应用会占用物理内存的哪些区域；它无法控制程序会落在物理内存的什么位置。程序的机器指令中既有相对地址也有绝对地址；相对地址（例如向前或向后跳若干条指令）无论程序位于内存何处都能正常工作。但有些指令包含绝对地址，例如装入一个全局变量，或跳转到某个过程的开头。除非程序被装入到编译器所期望的那个确切位置，这些指令就会失效。

在硬件转换普及之前，早期的操作系统用*重定位加载器*（relocating loader）把程序复制到内存中，以此解决这个问题。操作系统为程序选定一块空闲的物理内存区域之后，加载器会修改程序中所有用到绝对地址的指令。为了简化实现，可执行映像的开头有一张表，列出程序中用到的所有绝对地址。在现代系统中，这张表称为*符号表*（symbol table）。

今天，我们仍然有类似的东西。复杂的程序往往包含多个文件，每个文件都可以独立编译，然后再*链接*（link）到一起，形成可执行映像。编译器为单个文件生成机器指令时，并不知道这个文件在可执行文件中会落在什么位置。于是，编译器在每个被编译文件的开头生成一张符号表，指明当各个文件被组装到一起时，哪些值需要修改。

如今大多数商用操作系统都支持动态链接这一选项，它把重定位加载器的思想又向前推进了一步。使用动态链接库（DLL）时，库是在程序第一次调用它的时候按需链接进正在运行的程序中的。稍后我们会解释 DLL 的代码如何能在多个不同进程之间共享，但链接过程本身很直接：编译器保存一张表，列出 DLL 的有效入口点；调用程序通过这张表间接跳转，到达库中的例程。
:::

## 8.2　走向灵活的地址转换

我们对硬件地址转换的讨论分两步进行。首先，把查找效率的问题放在一边，转而考虑如何最好地实现前面列出的其他目标：灵活的内存分配、空间效率、细粒度的保护与共享，等等。等我们得到了想要的功能，再补上各种机制，把查找效率赢回来。

<figure class="book-figure">
<img src="/figures/vol3/image00284.png" alt="图 8.2" loading="lazy">
<figcaption><span class="fig-label">图 8.2</span>用基址与界限寄存器进行地址转换。虚拟地址与基址相加得到物理地址；界限寄存器拿虚拟地址来做检查，以防止进程读写超出分配给它的内存区域。</figcaption>
</figure>

第 2 章中，我们用所能想象的最简单的硬件——基址与界限——说明了硬件内存保护的概念。这个转换黑箱由每个进程的两个额外寄存器构成。**基址**（base）寄存器指明该进程在物理内存中那块区域的起点；**界限**（bound）寄存器指明这块区域的长度。如果把基址寄存器加到程序产生的每一个地址上，我们就不再需要重定位加载器了——程序的虚拟地址从 0 开始、到 bound 结束，物理地址则从 base 开始、到 base + bound 结束。图 8.2 给出了一个基址与界限转换的例子。由于物理内存中可以容纳多个进程，内核在每次进程上下文切换时，都要把基址与界限寄存器的内容重设为该进程对应的值。

基址与界限转换既简单又快速，但它缺少支持现代程序所需的许多特性。基址与界限转换只支持整个进程这一级的粗粒度保护；例如，它无法阻止一个程序覆写自己的代码。要在两个进程之间共享内存区域也很困难。由于一个进程的内存必须是连续的，支持动态内存区域——例如堆、线程栈或内存映射文件——就变得困难，甚至不可能。

### 8.2.1　分段内存

<figure class="book-figure">
<img src="/figures/vol3/image00285.png" alt="图 8.3" loading="lazy">
<figcaption><span class="fig-label">图 8.3</span>用段表进行地址转换。虚拟地址由两部分组成：段号和段内偏移量。段号索引段表，以定位该段在物理内存中的起点。界限寄存器拿段内偏移量来做检查，以防止进程读写超出分配给它的内存区域。进程对某些段可以只有受限的权限，例如防止对代码段进行写操作。</figcaption>
</figure>

基址与界限转换的许多局限，只需一点小改动就能补救：硬件不再为每个进程只保留一对基址与界限寄存器，而是支持一个由基址与界限寄存器对组成的数组。这称为*分段*（segmentation）。数组中的每一项控制虚拟地址空间的一部分，即一个*段*（segment）。每个段的物理内存连续存放，但不同的段可以存放在不同的位置。图 8.3 展示了段转换的工作过程。虚拟地址的高位用来索引这个数组；地址的其余部分则按上面的方式处理——与基址相加，并与存放在该索引处的界限相比较。此外，操作系统还可以给不同的段赋予不同的权限，例如允许对代码段只执行访问、对数据段读写访问。图中虽然画出了四个段，但一般来说，段的数目由虚拟地址中为段号预留的位数决定。

分段内存中存在空洞，这一点在你看来大概有些奇怪：程序的内存不再是一个连续区域，而是一组区域。每个不同的段都从一个新的段边界开始。例如，代码和数据无论在虚拟地址空间还是物理地址空间中，都不彼此紧邻。

如果程序跳转进这些空洞，或者试图从空洞中装载数据，会怎么样？硬件会产生一个异常（exception），陷入操作系统内核。在 UNIX 系统上，这仍然称为*段错误*（segmentation fault），也就是引用落在了某个合法内存段之外。程序怎样才能避免误入这些空洞呢？正确的程序不会产生指向合法内存之外的引用。换个说法，试图执行并不存在的代码、或读取并不存在的数据，多半说明程序本身有缺陷。

<img src="/figures/vol3/image00286.png" alt="图 8.4" loading="lazy">
<figcaption><span class="fig-label">图 8.4</span>两个进程共享一个代码段，但数据段和栈段各自独立。在这个例子中，两个进程使用相同的虚拟地址，但这些虚拟地址或者映射到同一块物理内存（若是代码），或者映射到不同的物理内存区域（若是数据）。</figcaption>
</figure>

分段内存实现和管理都很简单，却出人意料地强大，并被广泛使用。例如，x86 体系结构就是分段的（它还带有一些增强，我们稍后介绍）。有了段，操作系统就可以让进程共享某些内存区域，同时让另一些区域保持受保护。例如，两个进程要共享一个代码段，只需在各自的段表中设置一项，指向同一块物理内存——也就是使用相同的基址与界限。两个进程可以使用相同的代码、却在不同的数据上工作，办法是让段表把数据段指向不同的物理内存区域。图 8.4 展示了这一点。

同样，共享的库例程（例如一个图形库）也可以放进一个段，在进程之间共享。与前面一样，库的数据会放在另一个不共享的段里。现代操作系统中的动态链接库就经常这样做。一个实际的问题是，不同的进程可能装入数目不同的库，因而可能给同一个库分配不同的段号。只要库的代码使用*段内地址*（segment-local addresses），也就是相对于当前段的地址，那么视处理器体系结构的不同，共享仍然可以工作。

::: tip UNIX 的 fork 与写时复制
第 3 章中，我们介绍了 UNIX 的 fork 系统调用。UNIX 通过完整复制父进程来创建新进程；除了 fork 的返回值之外，父子进程完全相同。随后子进程可以设置自己的 I/O，并最终用 UNIX 的 exec 系统调用运行一个新程序。当时我们承诺过要解释如何高效地做到这一点。

有了段，这件事就可以实现了。要 fork 一个进程，我们只需复制父进程的段表；父进程物理内存中的*任何*内容都无需复制。当然，我们希望子进程是父进程的一份副本，而不只是指向父进程的同一块内存。如果子进程修改了某些数据，它应该只改动自己的副本，而不改动父进程的数据。另一方面，在大多数情况下，UNIX fork 出的子进程紧接着就调用 UNIX exec；共享数据在那里只是为了编程上的方便。

我们可以借助一个称为*写时复制*（copy-on-write，COW）的想法，高效地做到这一点。在 fork 期间，父子进程之间共享的所有段，在双方的段表中都被标记为“只读”。只要任何一方修改了某个段中的数据，就会触发异常，此时再对该段做一次完整的内存复制。在常见情形下，子进程在调用 UNIX exec 之前只修改自己的栈，如果是这样，就只需要物理复制栈。
:::

我们也可以用段来实现进程间通信，只要给进程以对同一个段的读、写权限。Multics 是 20 世纪 60 年代的一个操作系统，如今我们在 Microsoft 的 Windows 7、Apple 的 Mac OS X 和 Linux 中看到的许多思想，它早已具备；它大量使用分段内存来做进程间共享。在 Multics 中，每个数据结构都分配一个段，从而在进程之间实现细粒度的保护与共享。当然，这使段表变得相当大！较现代的系统倾向于只把段用于粒度较粗的内存区域，例如整个共享库的代码和数据，而不是库内的每一个数据结构。

作为段的能力的最后一个例子，它能对动态分配的内存做高效管理。当操作系统重用以前用过的内存或磁盘空间时，必须先把内存或磁盘的内容清零。否则，一个应用的私有数据就可能无意中泄露给另一个应用——而后者可能是恶意的。例如，你可能在某个网站（比如一家银行）上输入了密码，然后关掉浏览器。然而，如果浏览器用过的物理内存随后被重新分配给一个新进程，这个密码就可能泄露给一个恶意网站。

当然，我们只希望在内存确实会被用到时才付出清零的开销。对于堆和栈上动态分配的内存，这一点尤其成问题。程序启动时，并不清楚它会用多少内存；视程序而定，堆可能只有几 KB，也可能有几个 GB。操作系统可以用*引用时清零*（zero-on-reference）来应对这个问题。采用引用时清零时，操作系统为堆分配一块内存区域，但只把最前面的几 KB 清零。取而代之，它设置段表中的界限寄存器，把程序限制在已清零的那部分内存内。如果程序扩大自己的堆，就会触发异常，操作系统内核可以在恢复执行之前，再把更多的内存清零。

既然有这么多好处，为什么不就此打住呢？分段的主要缺点在于管理大量大小可变、动态增长的内存段所带来的开销。随着时间的推移，进程不断被创建和结束，物理内存会被分成正在使用的区域和未被使用的区域，也就是可以分配给新进程的区域。这些空闲区域大小各不相同。当我们创建一个新段时，需要为它找一块空闲的地方。我们应该把它放进容得下它的最小空闲区域，还是最大的空闲区域？

然而，无论我们怎样放置新段，随着被分配的内存越来越多，操作系统都可能遇到这样的情况：空闲空间的总量足以容纳一个新段，但这些空闲空间并不连续。这称为*外部碎片*（external fragmentation）。操作系统可以自由地整理内存来腾出空间，而不影响应用程序，因为当我们在物理内存中移动一个段时，虚拟地址并没有改变。即便如此，整理内存的处理器开销也可能很高：一台典型的服务器配置大约需要一秒才能完成一次内存整理。

当内存段还能增长时，这一切会变得更加复杂。我们应该为一个程序的堆预留多少内存？如果把堆段放在物理内存中空间充裕的地方，而该程序最终只需要一个小堆，那我们就浪费了内存。如果反过来——把堆段放进物理内存中一小块地方——那么一旦它改变大小，我们就需要把它复制到别处。

### 8.2.2　分页内存

分段内存之外的另一条路是*分页内存*（paged memory）。采用分页时，内存被划分为固定大小的块，称为*页框*（page frame）。地址转换与分段时的做法类似：不再用一张表项指向大小可变段的段表，而是为每个进程准备一张页表，其表项指向页框。由于页框是固定大小、且为 2 的幂，页表项只需给出页框地址的高位，因而更为紧凑。偏移量上也不需要“界限”，因为物理内存中的整页是作为一个单位分配的。图 8.6 展示了分页内存的地址转换过程。

分页让人觉得奇怪、也许还觉得挺妙的一点是：程序以为自己的内存是线性的，但实际上它的内存可以、而且通常确实是像一幅抽象拼贴画那样散布在整个物理内存中。处理器用虚拟地址一条接一条地执行指令，它的虚拟地址仍然是线性的；但是位于一页末尾的那条指令，与位于下一页开头的那条指令，会被放在物理内存中完全不同的区域。数据结构在虚拟地址看来是连续的，而一个大矩阵却可能散布在许多物理页框里。

一个贴切的类比是把几副牌洗在一起。一个进程在自己的虚拟地址空间里，看到的是单独一副牌，顺序井然；另一个进程看到的是完全不同的另一副牌，但它同样有序。然而在物理内存中，当前运行的所有进程的牌都被混洗在一起，看上去杂乱无章。页表就是魔术师的助手：能在洗乱的牌堆里瞬间找出红桃 Q。

分页解决了分段的主要局限：空闲空间的分配非常直接。操作系统可以把物理内存表示成一张位图（bit map），每一位代表一个物理页框是空闲还是已用。找一个空闲页框，只需求出一个为空的位。

进程之间共享内存也很方便：只要让每个共享某一页的进程，其页表项都指向同一个物理页框。对于跨越多个页框的大块共享区域（例如一个共享库），这可能需要设置许多个页表项。由于进程结束时需要知道何时该释放内存，共享内存还需要额外的簿记，用来跟踪共享页是否仍在使用。用于此目的的数据结构称为*核心映射表*（core map），它记录每个物理页框的信息，例如有哪些页表项指向它。

我们在分段一节中讨论过的许多优化，用分页同样可以做。对于写时复制，我们需要复制页表项并把它们置为只读；一旦有人向其中某一页写入，就可以先对底层的页框做一次真正的复制，再恢复进程的执行。同样，对于引用时清零，我们可以把栈顶的页表项置为无效，从而触发一次陷入内核；这样就可以按需扩展栈。

页表还允许加入其他特性。例如，一个程序的代码和数据尚未全部装入内存，就可以先让它跑起来。起初，操作系统把新进程的所有页表项都标记为无效；随着各页从磁盘读入，再把这些页分别标记为只读（代码页）或读写（数据页）。一旦最前面的几页进入内存，操作系统就可以在用户态启动程序的执行，同时内核在后台继续传输程序其余的代码。程序启动过程中，如果恰好跳到一个尚未装入的位置，硬件会产生异常，内核可以让程序停顿，直到该页可用为止。更进一步，编译器可以重新组织可执行文件以获得更高效的启动：把各初始化页合并到程序开头的少数几页里，从而让初始化与从磁盘装入程序这两件事重叠起来。

再举一例。*数据断点*（data breakpoint）要求程序在引用或修改某个特定内存位置时停止执行。调试时，知道某个数据结构何时被改动是很有帮助的，追踪指针错误时尤其如此。数据断点有时靠专门的硬件支持来实现，但也可以用页表实现：把包含该位置的页表项标记为只读。这样一来，进程每次改动该页都会陷入操作系统；操作系统再检查引起异常的那条指令是否真的影响了那个特定位置。

分页的一个缺点是：物理内存的管理变简单了，虚拟地址空间的管理却变得更棘手。编译器通常期望执行栈在（虚拟地址上）连续、且大小任意；每次新的过程调用都假定栈的内存已经就绪。同样，动态内存分配的运行时库通常也期望有一个连续的堆。在单线程进程中，我们可以把栈和堆放在虚拟地址空间的两端，让它们相向生长，如图 8.5 所示。然而一个进程若有多个线程，就需要多个线程栈，而且每个栈都要有生长的余地。

在 64 位虚拟地址空间下，这个问题更加突出。页表的大小与虚拟地址空间的大小成正比，而与物理内存的大小无关。虚拟地址空间越稀疏，页表所需的空间开销就越大。大多数表项都是无效的，代表虚拟地址空间中尚未使用的部分，但所有这些页表项仍然要占用物理内存。

我们可以通过选择更大的页框来减少页表占用的空间。页框该有多大？如果一个进程没有用满页框内的全部内存，大页框就会浪费空间，这称为*内部碎片*（internal fragmentation）。固定大小的块易于分配，但只要整块没被用完就会浪费空间。不幸的是，这意味着采用分页时，要么页很大（因内部碎片而浪费空间），要么页表很大（浪费空间），要么两者兼有。例如，若页大小为 16 KB、虚拟地址空间为 64 位，我们可能需要 $2^{50}$ 个页表项！

### 8.2.3　多级转换

如果要设计一个在稀疏键空间上高效查找的系统，你大概不会选一个简单的数组。树或者哈希表更合适；事实上，现代系统两者都用。本小节我们集中讨论树，之后再讨论哈希表。

许多系统采用基于树的地址转换，尽管各系统的细节不同，术语也有些容易混淆。差别虽多，我们即将描述的那些系统却有相近的性质：它们支持粗粒度与细粒度的内存保护和内存共享、灵活的内存放置、高效的内存分配，以及在稀疏地址空间上（即便是 64 位机器）的高效查找。

几乎所有多级地址转换系统都把分页作为树的最底层。系统之间的主要差别，在于如何抵达树叶处的页表——是用分段加分页，还是用多级分页，还是用分段加多级分页。这样做有几个理由：

- **高效的内存分配。** 以固定大小的页框来分配物理内存，空闲空间的管理只需一张简单的位图。

- **高效的磁盘传输。** 硬件磁盘被划分为固定大小的区域，称为扇区；磁盘扇区必须整块读出或写入。让页大小成为磁盘扇区的整数倍，就简化了内存与磁盘之间的传输——无论是把程序装入内存、读写文件，还是用磁盘模拟出比机器上实际物理内存更大的内存。

- **高效的查找。** 下一节我们将介绍如何用一个称为转换后备缓冲区（TLB）的高速缓存，使常见情形下的查找变得很快；这个转换缓冲区以页为单位缓存查找结果。分页还使查找表可以更紧凑，这一点在树的最底层尤其重要。

- **高效的反向查找。** 使用固定大小的页框还便于实现核心映射表，从物理页框出发找到共享该页框的那组虚拟地址。下一章要造出“无限虚拟内存”的假象时，这一点至关重要。

- **页粒度的保护与共享。** 通常，树中每一层的每一个表项都有自己的访问权限，因而既能做粗粒度、也能做细粒度的共享，最细可到单个页框。

#### 分页分段

让我们先从一个只有两层的树开始。采用*分页分段*（paged segmentation）时，内存仍是分段的，但每个段表项不再直接指向物理内存中一块连续区域，而是指向一个页表，再由页表指向该段背后的内存。段表项中的“界限”描述页表的长度，也就是该段有多少页。由于最底层采用分页，所有段的长度都是页大小的某个整数倍。图 8.7 展示了分页分段的转换过程。

段表有时存放在专用的硬件寄存器中，但各段的页表合起来要大得多，所以通常存放在物理内存里。为保持内存分配器的简单，最大段长通常选得能让每个段的页表恰好是页大小的一个小整数倍。

例如，在 32 位虚拟地址、4 KB 页的情况下，我们可以把高 10 位留给段号，紧接着的 10 位作为页号，剩下 12 位作为页内偏移量。这时若每个页表项占 4 字节，每个段的页表就恰好能放进一个物理页框。

与分页分段几乎等价的做法是使用多级页表。以 Sun Microsystems 的 SPARC 处理器为例，它有三层页表。如图 8.8 所示，顶层页表包含若干表项，每个表项指向一个二级页表，而二级页表的表项又是指向页表的指针。与大多数使用多级页表的系统一样，SPARC 上每一层页表都被设计成恰好放得进一个物理页框。只有顶层页表必须完整填入；树的更低层，只有在虚拟地址空间的相应部分被某个进程使用时才分配。访问权限可以在每一层指定，因此进程之间的共享在每一层都可以实现。

#### 多级分页分段

把这两种做法结合起来，就是用分段内存，而每个段由一个多级页表来管理。x86 的 32 位与 64 位寻址模式都采用这种做法。

先说 32 位的情形。x86 的术语与我们这里用的略有不同。x86 有一个每进程的*全局描述符表*（Global Descriptor Table，GDT），相当于段表。GDT 存放在内存中；每个表项（描述符）指向该段的（多级）页表，同时给出段长和段的访问权限。要启动一个进程，操作系统建立 GDT，并初始化一个寄存器——*全局描述符表寄存器*（Global Descriptor Table Register，GDTR），其中存放 GDT 的地址和长度。

由于历史原因，x86 用彼此独立的处理器寄存器来指定段号（即 GDT 中的索引）和供每条指令使用的虚拟地址。例如在“32 位”x86 上，既有段号，又有一个 32 位的段内虚拟地址；在 64 位 x86 上，段内虚拟地址扩展到 64 位。不过大多数应用只用少数几个段，所以每进程的段表通常很短。操作系统内核有自己的段表；这张表的设置使内核能够用虚拟地址访问系统上所有的每进程段和共享段。

为了编码效率，段寄存器常常隐含在指令之中。例如 x86 的 `push`、`pop` 等栈指令默认使用栈段（索引存放在栈段寄存器中），分支指令默认使用代码段（索引存放在代码段寄存器中），如此等等。作为一项优化，x86 每次初始化代码段、栈段或数据段寄存器时，还会把对应的 GDT 表项（即顶层页表指针和访问权限）读进处理器，这样处理器在每次引用时就能直接找到页表。

许多指令还提供了显式指定段索引的选项。例如 `ljmp`（长跳转）指令会把程序计数器改到新的段号以及该段内的偏移量。

对于 32 位 x86，一个段内的虚拟地址空间使用两级页表。虚拟地址的前 10 位索引顶层页表，这张表称为*页目录*（page directory）；接下来的 10 位索引二级页表；最后 12 位是页内偏移量。每个页表项占 4 字节，页大小为 4 KB，因此顶层页表和每一个二级页表都恰好放得进一个物理页。需要多少个二级页表取决于段的长度；虚拟地址空间中的空白区域不需要二级页表。顶层与二级页表项都带权限，因此在一个段内部也能做细粒度的保护和共享。

今天，一台计算机的内存容量往往远远超出 32 位所能寻址的范围；例如一台高端服务器可以有 2 TB 物理内存。对于 64 位 x86，段内虚拟地址最长可达 64 位。不过为了简化地址转换，目前的处理器只允许使用 48 位虚拟地址；这已经足以用四级页表映射 128 TB。页表树的更低层，只有在虚拟地址空间的相应部分被使用时才会填入。

作为一项优化，64 位 x86 可以选择省掉一级或两级页表。x86 的每个物理页框都是 4 KB。四级页表的每一页映射 2 MB 数据，三级页表的每一页映射 1 GB 数据。如果操作系统在放置数据时，让四级页表所覆盖的整整 2 MB 在物理内存中连续分配，那么上一层的页表项就可以标记为直接指向这块区域，而不指向一个页表。同样，如果操作系统为进程分配了 1 GB 的一块物理内存，三级页表的一页也可以省掉。除了节省页表映射所需的空间，这还提高了转换缓冲区的效率——这一点我们将在下一节详细讨论。

### 8.2.4　可移植性

地址转换机制的多样性，给操作系统设计者带来了挑战。为了让系统得到广泛使用，我们希望操作系统能够容易地移植到各种各样的处理器体系结构上。即便在同一个处理器系列之内（例如 x86），操作系统也可能需要支持若干种不同的变体。主存的密度在增长，物理地址空间与虚拟地址空间几乎每年都要增加一位。换句话说，要想让多级页表能够映射全部内存，每过十年就得给页表增加一级，才能跟上主存容量的增长。

另一个挑战是，操作系统常常需要为地址转换维护两套账。一套是硬件视角的账——处理器查询一组段表和多级页表，以便正确、安全地执行指令、读写数据。另一套是操作系统视角的虚拟地址空间账。为了支持写时复制、引用时清零、引用时装入等特性，以及后面几章将要介绍的其他应用，操作系统除了硬件页表中保存的信息之外，还必须记录每个虚拟页的额外信息。

这些软件的内存管理数据结构与硬件结构互为镜像，但并不完全相同，由三部分组成：

- **内存对象清单。** 内存对象即逻辑段。无论底层硬件是否分段，内核内存管理器都需要记录哪些内存区域代表哪些底层数据，例如程序代码、库代码、两个或多个进程之间共享的数据、写时复制区域，或者内存映射文件。例如，进程启动时，内核可以查一查对象清单，看看该代码是否已经在内存中；同样，进程打开一个库时，可以检查它是否已被别的进程链接过。类似地，内核可以维护引用计数，以确定进程退出时应当回收哪些内存区域。

- **虚拟地址到物理地址的转换。** 发生异常时，以及在复制系统调用的参数时，内核需要能够把进程的虚拟地址转换为其物理位置。内核固然可以使用硬件页表来完成这件事，但内核还需要弄清：一个无效页是真的无效，还是只是尚未装入（在引用时装入的情形下）；一个只读页是真的只读，还是只是在模拟数据断点或写时复制页。

- **物理地址到虚拟地址的反向转换。** 我们在前面把它称为*核心映射表*（core map）。操作系统需要记录哪些进程映射到某个特定的物理内存位置，以确保内核在更新某一页的状态时，也能更新指向该物理页的每一个页表项。

这其中最有趣的是用于虚拟地址到物理地址转换的那些数据结构。对于软件页表，我们在分段和多级分页方面拥有与前面完全相同的一组选择，此外还有一些别的选择。软件页表不必采用与底层硬件页表相同的结构；事实上，如果希望操作系统易于移植，软件数据结构完全可以与底层硬件大不相同。

Linux 让操作系统内部的地址转换数据结构仿照 x86 的“分段加多级页表”体系结构来设计。这使得把 Linux 移植到新的 x86 体系结构上相对容易，但移植到其他体系结构上就多少困难一些。

另一种做法最早出现在一个名为 Mach 的研究系统中，后来又被 Apple OS X 采用：软件转换数据不用树，而用哈希表（hash table）。由于历史原因，用哈希表来做分页地址转换被称为*反向页表*（inverted page table）。尤其是当我们走向更深的多级页表时，用哈希表做转换可以加快转换速度。

采用反向页表时，虚拟页号被哈希到一张大小与物理页框数成正比的表中。哈希表的每个表项保存形如下式的元组（在图中，物理页是隐含的）：

```text
    inverted page table entry = {
        process or memory object ID,
        virtual page number,
        physical page frame number,
        access permissions
    }
```

如图 8.9 所示，如果虚拟页号和进程 ID 都匹配，这次转换就是有效的。有些系统采用两级查找：先把虚拟地址映射为内存对象 ID，再针对该内存对象内的相对虚拟地址做哈希表查找。如果内存大部分是共享的，这样做既能节省哈希表空间，又不会过分拖慢转换。

反向页表确实需要某种办法来处理哈希冲突，即两个虚拟地址映射到同一个哈希表项的情形。标准的做法——例如链地址法或再哈希——都可以用来处理冲突。

为内存管理设置一个可移植层，有一个特别有用的结果：硬件多级转换表的内容可以被当作*线索*（hint）来看待。线索是某次计算的结果，它可能已经不再有效，但使用失效的线索会触发异常。

有了可移植层，软件页表才是真正的事实依据，硬件页表只是线索。只要硬件页表中的转换和权限是软件页表中转换的**子集**，就可以放心地使用硬件页表。

::: tip 反向页表就够了吗？
反向页表的概念引出一个有趣的问题：我们真的需要在硬件里放多级页表吗？假设我们在硬件中对虚拟地址做哈希。但不去用哈希值到一张表里查出物理页框在哪里，而是假设我们直接把哈希值*当作*物理页。要让这个办法成立，哈希表的大小必须恰好等于物理内存的页框数，这样哈希表项与页框之间才能一一对应。

我们仍然需要一张表来保存权限，并指明每个表项里存的是哪个虚拟页；如果进程没有权限访问该页，或者两个虚拟页哈希到同一个物理页，我们需要能够检测出来并陷入操作系统内核来处理。这正是用于管理内存的哈希表常被称为*反向页表*的原因：表里存的是虚拟页号，而不是物理页号；物理页号就是该虚拟页在表中的位置。

这种做法的缺点呢？处理哈希冲突变得困难得多。如果两个页哈希到同一个表项，只有一个能存进那个物理页框。另一个必须放在别处——要么放进哈希表的另一个表项，要么存到磁盘上。把新页复制进来需要时间，而如果程序不幸恰好需要同时访问两个哈希到同一物理页的虚拟页，系统还会进一步变慢。因此，在现代系统中，反向页表通常用在软件里以改善可移植性，而不是用在硬件里以省掉多级页表。
:::

## 8.3　走向高效的地址转换

读到这里，你大概已经有点坐不住了。毕竟我们前面描述的硬件机制，在每条指令上都要至少两次、多则四次额外的内存引用，才终于到达想要访问的物理内存位置！让处理器在每次取指令时都做若干次内存查找，而且对每条读写数据的指令还要做得更多，这看起来完全不切实际。

本节我们将讨论如何在不改变地址转换逻辑行为的前提下提高其性能。换句话说，尽管做了优化，每个虚拟地址仍然被转换到完全相同的物理内存位置，每次权限异常仍然会触发陷入，与没有做性能优化时完全一样。

为此，我们要使用*高速缓存*（cache），即某份数据的一份副本，访问它比访问原始数据更快。本节关心的是如何用高速缓存来提升转换性能。高速缓存广泛用于计算机体系结构、操作系统、分布式系统以及许多其他系统；下一章我们会更一般地讨论高速缓存何时有效、何时无效。不过眼下，我们只关注用高速缓存来降低地址转换的开销。这样安排是有原因的：最早的一批硬件高速缓存，正是用来提升转换性能的。

### 8.3.1　转换后备缓冲区

想一想处理器在带地址转换的情况下如何执行指令，就能找到一些明显的性能改进办法。毕竟处理器通常是一条接一条地按顺序执行指令：

```text
    ...
    add r1, r2
    mult r1, 2
    ...
```

硬件会先转换 `add` 指令的程序计数器，遍历多级转换表，找出存放这条 `add` 指令的物理内存。程序计数器递增之后，处理器又必须再走一遍多级表，找出存放 `mult` 指令的物理内存。如果这两条指令在虚拟地址空间中位于同一页，那么它们在物理内存中也位于同一页。处理器只是把同样的工作重复一遍——页表遍历完全一样，再下一条指令、再下一条，都是如此。

*转换后备缓冲区*（translation lookaside buffer，TLB）是一张很小的硬件表，保存最近若干次地址转换的结果。TLB 的每个表项把一个虚拟页映射到一个物理页：

```text
    TLB entry = {
        virtual page number,
        physical page frame number,
        access permissions
    }
```

TLB 硬件（通常）不再靠多级查找或哈希来找到相关表项，而是把所有表项同时与虚拟页比较。如果匹配，处理器就用该表项构成物理地址，跳过地址转换余下的步骤。这称为*TLB 命中*（TLB hit）。TLB 命中时，硬件仍然需要检查权限，以防万一——例如程序试图写一个只含代码的页，或者操作系统需要对写时复制页上的写指令陷入。

如果 TLB 中没有任何表项匹配，就发生了*TLB 未命中*（TLB miss）。此时硬件按前面描述的方式做完整的地址转换。转换完成后，用得到的物理页构成物理地址，并把这次转换装入 TLB 的某个表项，替换掉一个已有的表项。通常被替换的是最近没有用过的表项。

图 8.10 展示了 TLB 的查找过程，图 8.11 则展示了 TLB 如何嵌入整个地址转换系统。

TLB 的硬件成本乍看可能不小，但与它在处理器性能上能带来的潜在收益相比，并不算大。为了有用，TLB 查找必须比做一次完整地址转换快得多；因此，TLB 表项用非常快的片上静态存储器实现，并且就放在处理器附近。事实上，为了保持查找速度，现在许多系统都包含多级 TLB。一般来说，存储器越小，查找越快。所以第一级 TLB 很小、紧靠处理器（并且出于工程上的原因，常常拆成两个：一个用于指令查找，一个用于数据查找）。如果第一级 TLB 中没有这次转换，就去查更大的第二级 TLB；只有当两级都未命中时，才去做完整转换。为简单起见，我们的讨论假定只有一级 TLB。

TLB 还需要为每个表项配一个地址比较器，以便并行检查是否匹配。为了降低这一成本，有些 TLB 采用*组相联*（set associative）结构。与全相联 TLB 相比，组相联 TLB 需要更少的比较器，但未命中率可能更高。我们将在下一章讨论组相联以及它对操作系统设计的影响。

带 TLB 的地址转换开销有多大？有两个因素。无论地址是否在 TLB 中，我们都要付出 TLB 查找的开销；而在 TLB 查找不成功时，还要再付出完整转换的开销。设 P(hit) 为 TLB 中已经缓存该表项的概率：

$$
\text{地址转换开销} = \text{TLB 查找开销} + \text{完整转换开销} \times (1 - P_{\text{命中}})
$$

换句话说，处理器设计者必须把 TLB 做得足够大，使程序产生的大多数地址都能在 TLB 中命中，从而让做完整转换成为罕见事件。即便如此，对许多应用来说，TLB 未命中仍是一项可观的开销。

::: tip 软件装入的 TLB
如果 TLB 能有效地把一次完整地址转换的开销分摊到许多次内存引用上，我们就可以提出一个激进的问题：TLB 未命中时，还需要硬件做多级页表查找吗？这就是软件装入的 TLB（software-loaded TLB）背后的想法。TLB 命中与以前一样工作，作为快速路径。TLB 未命中时，处理器不是去做硬件地址转换，而是陷入操作系统内核。在陷入处理程序中，由内核负责做地址查找、把新的转换装入 TLB，并重新启动应用。

这种做法极大地简化了操作系统的设计，因为操作系统不再需要维护两套页表——一套给硬件，一套给自己。TLB 未命中时，操作系统可以查询自己那套可移植的数据结构，确定应当往 TLB 中装入什么。

软件装入的 TLB 虽然给操作系统带来了方便，但对执行应用来说要慢一些，因为陷入内核的开销远大于做一次硬件地址转换。下一章我们将看到，页表项的内容可以存放在片上硬件高速缓存中；这意味着即使在 TLB 未命中时，硬件通常也能发现多级页表的每一级都已经存放在片上高速缓存里，只是不在 TLB 里。例如，在现代 x86 上，一次 TLB 未命中在最好情况下相当于 17 条指令就能完成。相比之下，陷入操作系统内核即使在最好情况下也要几百到几千条指令才能处理完。
:::

### 8.3.2　超级页

提高 TLB 命中率的一种办法，是使用一个称为*超级页*的概念。超级页（superpage）是物理内存中一组连续的页，它们映射虚拟内存中一段连续的区域，并且这些页按边界对齐，从而共享相同的高位（超级页）地址。例如，一个 8 KB 的超级页由两个相邻的 4 KB 页组成，这两个页在虚拟内存和物理内存中都落在 8 KB 的边界上。是否使用超级页由操作系统自行决定——那些受益于较小页大小的短小程序或内存段，仍然可以使用标准的、较小的页大小。

超级页给操作系统的内存分配带来了麻烦，因为系统必须以不同的尺寸分配内存块。但好处是，映射一大段连续内存所需的 TLB 表项数量可以大幅减少。TLB 的每个表项都有一个标志位，指明该表项是一个页还是一个超级页。对于超级页，TLB 匹配的是超级页号，也就是说，它忽略虚拟地址中表示超级页内部页号的那一部分。图 8.12 展示了这一点。

具体来说，当有一段 2 MB 或 1 GB 的物理内存作为一个整体被映射时，x86 会跳过一级或两级页表。处理器引用这些区域时，只需要往 TLB 中装入一个表项。在查找与超级页的匹配时，TLB 只考虑地址的高位，忽略超级页内部的偏移量。对于 2 MB 的超级页，偏移量是虚拟地址最低的 21 位；对于 1 GB 的超级页，则是最低的 30 位。

<figcaption><span class="fig-label">图 8.13</span>高分辨率帧缓冲区在物理内存中的布局。显示的每一行像素都可能占据整整一页，因此在垂直方向上相邻的像素位于不同的页上。</figcaption>
</figure>

超级页的一个常见用途，是为计算机显示器映射帧缓冲区。重画屏幕时，处理器可能要访问每一个像素；对于高分辨率显示器，这涉及遍历好几兆字节的内存。如果每个 TLB 表项只映射一个 4 KB 页，那么即便是拥有 256 个表项的大容量片上 TLB，同一时刻也只能容纳 1 MB 帧缓冲区的映射。于是，处理器在内存中前进时，TLB 就得反复做页表查找，以便装入新的 TLB 表项。画一条竖线时情况更糟。帧缓冲区是按行优先顺序存放的二维数组，因此显示器的每一行水平像素都位于单独的一页上。这样一来，修改竖线上的每一个像素，都需要装入一个单独的 TLB 表项！有了超级页，整个帧缓冲区可以用一个 TLB 表项映射，从而为应用程序需要的其他页留出更多空间。

科学计算代码中的大型矩阵也有类似的问题。

### 8.3.3　TLB 一致性

每当我们在系统中引入高速缓存，都必须考虑表项被修改时如何保证缓存与原始数据一致。TLB 也不例外。为了让程序安全、正确地执行，操作系统必须确保每个程序看到的只是自己的内存，而不是别人的内存。TLB、硬件多级转换表和可移植的操作系统层之间任何不一致，都是潜在的正确性与安全性缺陷。

需要考虑三个问题：

<figure class="book-figure">
<img src="/figures/vol3/image00296.png" alt="图 8.14" loading="lazy">
<figcaption><span class="fig-label">图 8.14</span>带进程 ID 的转换后备缓冲区的操作。TLB 中包含多个进程的表项，但只有当前进程的表项是有效的。操作系统内核在进程之间做上下文切换时，必须修改当前进程 ID。</figcaption>
</figure>

- **进程上下文切换。** 进程上下文切换时会发生什么？旧进程的虚拟地址对新进程来说不再有效，也不应当有效。否则，新进程就能读取旧进程的数据结构，轻则使新进程崩溃，重则可能让它捞取到内存中存放的密码之类的敏感信息。做上下文切换时，我们需要修改硬件页表寄存器，使其指向新进程的页表。然而，TLB 中也保存着旧进程的页转换和权限的副本。一种办法是在每次上下文切换时*冲刷*（flush）TLB，即丢弃它的全部内容。由于清空缓存会带来性能损失，现代处理器采用了*带标记的 TLB*（tagged TLB），如图 8.14 所示。带标记 TLB 中的表项包含产生该转换的进程 ID：

```text
      tagged TLB entry = {
          process ID,
          virtual page number,
          physical page frame number,
          access permissions
      }
```

  采用带标记的 TLB 后，操作系统在每次上下文切换时把当前进程 ID 写入一个硬件寄存器。做查找时，硬件忽略其他进程的 TLB 表项，但可以复用它上次运行当前进程时留下的任何 TLB 表项。

- **权限缩减。** 操作系统修改页表中的一个表项时会发生什么？对于处理器缓存主存数据的普通数据高速缓存，专用硬件会保持缓存数据与内存中的数据一致。但 TLB 通常不提供硬件一致性，让 TLB 与页表保持一致是操作系统内核的责任。之所以需要软件介入，有几个原因。第一，页表项可以在进程之间共享，因此一次修改可能影响多个 TLB 表项（例如共享该页的每个进程各有一个）。第二，TLB 只保存虚拟页到物理页的映射，并不记录该映射来自哪个地址，因此它无法判断对内存的一次写操作是否会影响某个 TLB 表项。即使它真的记录了这些信息，大多数对内存的写操作也不影响页表，所以每次写内存都去检查是否会影响某个 TLB 表项，会带来大量而几乎总是用不上的开销。因此，操作系统在修改页表时，要确保 TLB 中不含有错误的映射。当操作系统为虚拟地址空间的某一部分*增加权限*时，什么也不用做。例如，操作系统可能通过分配物理内存、把无效的页表项改为指向新内存，来动态扩展堆或栈；也可能把某一页从只读改为可读写。在这些情况下，TLB 可以不去动它，因为任何需要新权限的引用要么会让硬件装入新表项，要么会触发异常，从而让操作系统装入新表项。但是，如果操作系统需要*缩减*某一页的权限，那么内核在恢复该进程运行之前，必须确保 TLB 中没有旧转换的副本。如果该页是共享的，内核还需要确保，对于那些可能引用过该页的进程 ID，TLB 中都没有副本。例如，要把某段内存标记为写时复制，操作系统必须把该区域的权限缩减为只读，并且必须从 TLB 中删除该区域的所有表项，因为旧的 TLB 表项仍然是可读写的。早期的计算机只要页表发生变化，就丢弃 TLB 的全部内容；而更现代的体系结构（包括 x86 和 ARM）支持删除单个 TLB 表项。

<figure class="book-figure">
<img src="/figures/vol3/image00297.png" alt="图 8.15" loading="lazy">
<figcaption><span class="fig-label">图 8.15</span>为保持正确的转换行为而需要 TLB 击落的示例。处理器 1 要把进程 0 中页 <code>0x53</code> 的转换改为只读，就必须从自己的 TLB 中删除该表项，并且必须确保没有其他处理器的 TLB 中还保留着旧转换。为此，它向每个处理器发送一个处理器间中断，请求对方删除旧转换。操作系统并不知道某个 TLB 中是否存在该表项（例如处理器 3 的 TLB 中就没有页 <code>0x53</code>），因此必须从所有 TLB 中删除。只有当所有处理器都确认旧转换已被删除，击落才算完成。</figcaption>
</figure>

- **TLB 击落。** 在多处理器上还有一个额外的麻烦。系统中的任何处理器都可能在自己的 TLB 中缓存了某个转换的副本。因此，为了安全、正确，每当修改一个页表项时，都必须先丢弃*每个*处理器 TLB 中对应的表项，修改才会生效。通常只有当前处理器能使自己的 TLB 失效，所以要把表项从系统的所有处理器中删除，操作系统必须中断每个处理器，请求它从自己的 TLB 中删除该表项。这一重量级操作有自己的名字：*TLB 击落*（TLB shootdown），如图 8.15 所示。操作系统先修改页表，然后向所有其他处理器发送 TLB 击落请求。其他处理器在确认自己的 TLB 已清除旧表项之后，就可以继续运行。最初的处理器只有在*所有*处理器都确认已从各自的 TLB 中删除旧表项之后，才能继续。由于 TLB 击落的开销随系统中处理器数量线性增长，许多操作系统会把 TLB 击落请求批量处理，以减少处理器间中断的次数，代价是完成击落的延迟有所增加。

### 8.3.4　虚拟地址缓存

<figure class="book-figure">
<img src="/figures/vol3/image00298.png" alt="图 8.16" loading="lazy">
<figcaption><span class="fig-label">图 8.16</span>虚拟地址缓存、转换后备缓冲区与硬件页表的协同工作。</figcaption>
</figure>

提高地址转换性能的又一步，是在查询 TLB *之前*先经过一个虚拟地址缓存（virtually addressed cache），如图 8.16 所示。虚拟地址缓存保存物理内存内容的副本，以虚拟地址为索引。一旦命中，处理器就可以立即使用数据，不必等待 TLB 查找或页表转换产生物理地址，也不必等待从主存取回数据。几乎所有现代多核芯片都在每个处理器核附近包含一个小容量、按虚拟地址寻址的片上缓存。通常，与 TLB 一样，虚拟地址缓存也会一分为二：一个用于取指令，一个用于数据。

适用于 TLB 的一致性问题，同样适用于虚拟地址缓存：

- **进程上下文切换。** 虚拟地址缓存中的表项要么必须与进程 ID 一起标记，要么必须在上下文切换时失效，以防止新进程访问旧进程的数据。

- **权限缩减与击落。** 当操作系统修改页表中某一页的权限时，虚拟地址缓存不会反映这一变化。要使受影响的缓存表项失效，要么冲刷整个缓存，要么找出缓存中存放在该受影响页上的所有内存位置，两者都是相当重量级的操作。因此，大多数带虚拟地址缓存的系统都把虚拟地址缓存与 TLB 配合使用。每个虚拟地址同时在这两者中查找；TLB 指明应当使用什么权限，而缓存在访问被允许时提供数据。这样一来，只需要让 TLB 的权限保持最新。TLB 与虚拟地址缓存是协同设计的，两者完成一次查找所花的时间相同，因此处理器不会因为等待 TLB 而停顿。

进一步的问题是别名。许多操作系统允许共享内存的进程用不同的虚拟地址引用同一个内存位置。这称为*内存地址别名*（memory address alias）。每个进程都会为该内存拥有自己的 TLB 表项，虚拟地址缓存也可能为每个进程各存一份该内存的副本。问题出现在某个进程修改了自己的副本时：系统怎么知道要去更新另一份副本？

解决这个问题最常见的办法，是在虚拟地址缓存中把物理地址与虚拟地址一起保存。在与虚拟地址缓存查找并行的同时，查询 TLB 以产生物理地址和页权限。当一条存储指令修改虚拟地址缓存中的数据时，系统可以做一次反向查找，找出所有匹配同一物理地址的表项，从而更新这些表项。

### 8.3.5　物理地址缓存

<figure class="book-figure">
<img src="/figures/vol3/image00299.png" alt="图 8.17" loading="lazy">
<figcaption><span class="fig-label">图 8.17</span>虚拟地址缓存、转换后备缓冲区、硬件页表与物理地址缓存的协同工作。</figcaption>
</figure>

许多处理器体系结构还包含一个物理地址缓存（physically addressed cache），它作为第二级缓存，在虚拟地址缓存和 TLB 之后、主存之前被访问。图 8.17 展示了这一点。一旦通过 TLB 查找形成内存位置的物理地址，就去查询第二级缓存。如果命中，该位置保存的值可以直接返回给处理器，无需访问主存。

以今天的芯片密度，片上物理地址缓存可以做得相当大。事实上，许多系统同时包含第二级和第三级物理地址缓存。通常，第二级缓存是每核私有的，并针对延迟进行优化，典型容量为 256 KB。第三级缓存由同一芯片上的所有核共享，针对容量进行优化，在现代芯片上可达 2 MB。换句话说，70 年代整个 UNIX 操作系统及其全部应用程序，都可以装进一块现代芯片里，完全不需要访问主存。

这些物理地址缓存合起来有两个作用：

- **更快的内存引用。** 片上物理地址缓存的查找延迟比主存快 10 倍（第二级）或 3 倍（第三级）。

- **更快的 TLB 未命中。** 发生 TLB 未命中时，硬件要沿着多级页表依次查找。由于页表存放在物理内存中，它们也可以被缓存。因此，即使是一次 TLB 未命中加上页表查找，也可能完全在片上处理完毕。

## 8.4　软件保护

越来越多的系统在基于硬件的地址转换之外，辅以基于软件的保护机制。显然，只靠软件实现保护是可行的。用软件实现的机器码解释器，可以模拟硬件保护的确切行为。解释器可以逐条取出指令、加以解释，在页表中查找每个地址以判断该指令是否被允许，若允许再执行这条指令。当然，这样做会非常慢！

在本节中我们要问：是否存在实用的软件技术，可以在不依赖硬件地址转换的前提下，把代码限制在一个受限的域内执行？讨论的重点放在用软件提供高效的保护边界，以此改善计算机的安全性。不过，我们描述的技术也可以用来提供其他操作系统服务，例如写时复制、栈的可扩展性、可恢复内存以及用户级虚拟机。一旦有了重新解释对代码和数据位置之引用的基础设施——无论用软件还是用硬件实现——许多服务就都成为可能。

硬件保护在现代计算机上几乎无处不在，所以很自然地要问：为什么我们还需要用软件来实现保护？

- **简化硬件。** 一个目标纯粹出于好奇。我们真的需要硬件地址转换吗，还是说它只是一项工程折衷？如果软件能够提供高效的保护，我们就可以从计算机中去掉大量硬件复杂性和运行时开销，同时大幅提高灵活性。

- **应用级保护。** 即使我们需要硬件地址转换来保护操作系统免受行为不当的应用程序侵害，我们也常常希望在一个应用程序内部运行不可信的代码。网页浏览器就是一例：网页可以包含代码，用来为某个网站配置显示，但浏览器需要保护自身，免受网站提供的恶意或有缺陷代码的侵害。

- **内核内部的保护。** 有时我们还需要在内核中运行不可信的、或者至少可信度较低的代码。例子包括第三方设备驱动程序和代表应用程序定制操作系统行为的代码。由于内核是以整台机器的全部能力运行的，任何在内核中运行的用户代码都必须用软件而非硬件来保护。

- **可移植的安全性。** 消费类设备的激增给应用程序的可移植性带来了挑战。没有任何一个操作系统能运行在每一种嵌入式传感器、智能手机、平板电脑、上网本、笔记本电脑、台式机和服务器上。希望跨多种设备运行的应用程序，需要一个公共的运行时环境，把应用程序与底层操作系统和硬件设备的具体细节隔离开来。把保护作为运行时系统的一部分提供，意味着用户可以下载并运行应用程序，而不必担心该程序会破坏底层的操作系统。

<img src="/figures/vol3/image00300.png" alt="图 8.18" loading="lazy">
<figcaption><span class="fig-label">图 8.18</span>在可信代码的区域内执行不可信代码。可信区域可以是一个进程，例如正在执行不可信 JavaScript 的浏览器；也可以就是操作系统内核，例如正在执行不可信分组过滤器或设备驱动程序的场景。</figcaption>

对软件保护的需求相当普遍，以至于它有了专门的名称：我们如何为执行不可信代码提供一个软件*沙箱*（sandbox），使它既能完成自己的工作，又不对系统其余部分造成危害？

### 8.4.1　单一语言操作系统

一种非常简单的软件保护办法，是要求所有应用程序都用同一种经过精心设计的编程语言编写。如果这种语言及其环境只允许表达安全的程序，并且编译器和运行时系统是可信的，那么就不需要硬件保护。

<figure class="book-figure">
<img src="/figures/vol3/image00301.png" alt="图 8.19" loading="lazy">
<figcaption><span class="fig-label">图 8.19</span>在内核中执行分组过滤器。网络调试器可以装入一个分组过滤器，以便针对特定用户或应用程序跟踪分组。与过滤条件匹配的分组首部被复制给调试器，而正常的分组处理不受影响。</figcaption>
</figure>

这种方法有一个至今仍被广泛使用的实例：UNIX 分组过滤器（packet filter），如图 8.19 所示。UNIX 分组过滤器允许用户把代码下载到操作系统内核中，以定制内核的网络处理。例如，可以在内核中装入一个分组过滤器，把某个特定连接到达的分组首部复制一份，并发送给用户级调试器。

UNIX 分组过滤器通常只有很少量的代码，但由于它需要在内核态运行，系统不能依靠硬件保护来阻止行为不当的分组过滤器对无关应用程序造成破坏。于是，系统改为限制分组过滤器的语言，只允许表达安全的分组过滤器。例如，过滤器只能根据分组的内容做分支，不允许使用循环。由于过滤器通常很短，使用解释型语言带来的开销并不算过分。

<figure class="book-figure">
<img src="/figures/vol3/image00302.png" alt="图 8.20" loading="lazy">
<figcaption><span class="fig-label">图 8.20</span>在现代网页浏览器中执行 JavaScript 程序。JavaScript 解释器负责把 JavaScript 程序的影响限制在它所属的那个页面上。JavaScript 程序可以调用浏览器中一大组例程，因此这些例程也必须受到保护，以抵御恶意的 JavaScript 程序。</figcaption>
</figure>

同一思路的另一个例子，是现代网页浏览器中对 JavaScript 的使用，如图 8.20 所示。JavaScript 程序定制网站的用户界面与呈现方式；它由网站提供，却在客户机的浏览器内部执行。因此，JavaScript 的浏览器执行环境必须防止恶意的 JavaScript 程序夺取浏览器的控制权，乃至控制客户机的其余部分。由于 JavaScript 程序往往相对较短，它们通常被解释执行；JavaScript 还可以调用一组预先定义的库例程。如果 JavaScript 程序试图调用一个并不存在的例程，或者引用任意内存位置，解释器就会产生一个运行时异常，并在造成任何损害之前终止该程序。

早期有几款个人计算机就是单一语言系统，保护用软件而非硬件实现。最著名的是 Xerox Alto 研究样机，它使用软件保护而不是硬件保护；Alto 启发了 Apple Macintosh，而它所用的语言 Mesa 则是 Java 的前身。其他系统包括 Lisp 机器——一种只执行用 Lisp 编写的程序的计算机——以及只执行 Smalltalk（Python 的前身）的计算机。

::: tip 语言保护与垃圾回收
JavaScript、Lisp 和 Smalltalk 都为动态创建的数据结构提供了内存压缩式垃圾回收。这样做的一个动机是方便程序员，并减少本可避免的程序员错误。不过，软件保护与垃圾回收之间有着密切的关系。垃圾回收要求运行时系统跟踪程序中可见的所有有效指针，这样才能在不影响程序行为的前提下搬移数据结构。用这种语言能够表达的程序，无法指向或跳转到任意内存位置，否则垃圾回收器就会改变程序的行为。程序生成的每一个地址必然落在该应用程序代码所在的区域内，每一条装入和存储指令访问的都是本程序的数据，而不是别人的数据。换句话说，这恰恰就是软件保护所需要的东西！
:::

遗憾的是，基于语言的软件保护有一些实际局限，因此在现代系统中，它往往与硬件保护配合使用，而不是取代硬件保护。使用解释型语言看起来是个安全的选择，但它要求同时信任解释器及其运行时库。解释器是一个复杂的软件，其中的任何缺陷都可能为恶意程序提供夺取进程控制权、也就是逃出其保护边界的途径。这类攻击在运行 JavaScript 的浏览器上很常见，不过随着时间的推移，JavaScript 解释器对付这类攻击已经变得更为健壮。

更糟的是，由于解释执行代码往往很慢，许多解释型系统把大部分功能放进可以编译成机器码、直接在处理器上运行的系统库中。例如，商业网页浏览器为 JavaScript 程序提供了数量庞大的用户界面对象，于是被解释的代码只是少量的“胶水”。遗憾的是，这扩大了攻击面——任何没有完全防范恶意使用的库例程，都可能成为程序逃出保护边界的通道。例如，JavaScript 程序可以设法让某个库例程越过缓冲区末尾写入，视内存中存放的内容而定，这可能为 JavaScript 程序提供控制系统的途径。针对 JavaScript 运行时库的这类攻击十分普遍。

这就使得大多数系统同时使用硬件保护和软件保护。例如，Microsoft Windows 在一个权限受限的特殊进程中运行其网页浏览器。这样，如果系统管理员访问了含有恶意 JavaScript 程序的网站，即使该程序接管了浏览器，它也无法保存文件，或执行系统管理员通常可以执行的其他操作。我们认识一位计算机安全专家，他把每个新网页都放在单独的虚拟机中运行；即使网页中含有接管浏览器的病毒，而浏览器又能够接管操作系统，也可以靠重置虚拟机把原来未被感染的系统自动恢复出来。

::: tip 跨站脚本
另一种 JavaScript 攻击利用的是提供给 JavaScript 程序的存储接口。为了便于 JavaScript 程序彼此通信，它们可以把数据存放在浏览器的 cookie 中。对某些网站来说，这些 cookie 可能含有敏感信息，例如用户的登录认证信息。能够访问用户 cookie 的 JavaScript 程序，有可能冒充该用户，从而访问用户存放在服务器上的敏感数据。如果一个网站被攻破，它可能被修改为提供含有 JavaScript 程序的页面，由该程序收集并利用用户的敏感数据。这类攻击称为*跨站脚本攻击*（cross-site scripting attack），十分普遍。
:::

还有一种相关的做法：把系统上的全部软件都用同一种安全的语言编写，然后把代码编译成直接在处理器上执行的机器指令。与解释型语言不同，库本身也可以用这种安全语言编写。Xerox Alto 采用的就是这种做法：应用程序和整个操作系统都用同一种语言 Mesa 编写。与 Java 一样，Mesa 把对线程同步的支持直接内建在语言之中。然而即便如此，仍然存在实际问题。你仍然需要在信任边界上做防御性编程——一边是不可信的应用代码（用安全语言编写），另一边是可信的操作系统代码（同样用安全语言编写）。你还需要能够信任编译器生成强制执行保护的、正确的代码；编译器中的任何弱点，都可能让一个有缺陷的程序使系统崩溃。Alto 的设计者构建了一个后继系统，称为 Digital Equipment Firefly，它使用 Mesa 的后继语言 Modula-2 来实现应用程序和操作系统。不过，为了多一层保护，Firefly 还使用硬件保护把应用程序与操作系统内核隔离开来。

### 8.4.2　与语言无关的软件故障隔离

信任某种语言及其解释器或编译器来提供安全性，有一个局限：许多程序员都很看重自行选择编程语言的灵活性。例如，有人用 Ruby 来配置 Web 服务器，有人用 Matlab 或 Python 编写科学计算代码，还有人用 C++ 承担大型软件工程。

既然让操作系统去信任每一种语言的每一个编译器并不现实，那么我们能否以与编程语言无关的方式，在没有硬件支持的情况下用软件高效地隔离应用程序代码？

考虑这件事的原因之一是，很多场合下系统需要在进程内部再加一层保护。我们已经见过一例：网页浏览器需要安全地执行 JavaScript 程序，但类似的例子还有很多。有了软件保护，我们就可以像分组过滤器那样把代码下载到内核中，让用户定制操作系统，只是范围可以更广泛。事实表明，内核设备驱动程序是导致操作系统崩溃的首要原因；如果内核能够在一个受限环境中执行设备驱动程序，就有可能减轻这类故障的严重程度。同样，许多复杂的软件包——数据库、电子表格、桌面出版系统、计算机辅助设计系统——都允许用户把代码下载到系统中，以定制和配置系统的行为，满足自己的特定需求。如果这些下载来的代码导致系统崩溃，用户无法分辨究竟是谁的过错，最后多半会归咎于厂商。

当然，办法之一就是依靠 JavaScript 解释器。已经有一些工具可以把用 C 或 C++ 之类语言编写的代码编译成 JavaScript，使这些语言编写的应用能够运行在任何支持 JavaScript 的浏览器上。如果执行 JavaScript 既安全又足够快，我们就可以宣布大功告成了。

本节讨论另一条途径：我们能否取出任意一段机器指令，对它加以修改，确保这段代码不会触碰自己数据区域之外的任何内存？这样一来，代码可以用任何语言编写、由任何编译器编译，并以处理器的全速直接执行。

Google 和 Microsoft 都有实现这一点的产品：一个能运行任何编程语言所写代码、并在进程内部安全执行的沙箱。Google 的产品叫 Native Client，Microsoft 的叫 Application Domains。这些实现都很高效：据 Google 报告，在沙箱内安全执行代码的运行时开销不到 10%。

为使讨论简单，我们假定沙箱的内存区域是连续的，也就是说，沙箱有一个需要在软件中强制实施的基址与界限。既然我们可以禁止执行明显恶意的代码，就可以先检查沙箱中的代码没有使用自修改指令或特权指令。

我们的做法分两步。第一步，把机器指令插入可执行代码，完成硬件保护本来会做的事，即检查每个地址是否合法地落在基址与界限所规定的区域内，若不合法则抛出异常。第二步，用控制流和数据流分析删去那些对沙箱正确性并非严格必需的检查。这与我们在硬件地址转换中的做法如出一辙——先设计一个通用而灵活的机制，再说明如何用 TLB 对它进行优化，使得不必在每条指令上都执行完整的转换机制。

为每条装入和存储指令添加的指令很简单：只需增加一项检查，确认该装入或存储指令要使用的地址落在正确的数据区域内。下面的代码中，`r1` 是一个机器寄存器。

```text
  test r1, data.base
  if less-than, branch to exception
  test r1, data.bound
  if greater-than, branch to exception
  store data at r1
```

注意，存储指令必须被限制在沙箱的数据区域之内；否则一条存储指令就可能修改指令序列，例如造成一次跳出受保护区域的跳转。

我们还需要检查间接分支指令。必须确保程序无法分支到沙箱之外，只允许跳到预定义的入口点和出口点。相对分支和具名过程调用可以直接验证。间接分支和过程返回则会跳转到存放在寄存器或内存中的位置，因此使用该地址之前必须先做检查。

```text
  test r1, code.base
  if less-than, branch to exception
  test r1, code.bound
  if greater-than, branch to exception
  jump to r1
```

最后一个细节：上面的代码只是验证间接分支指令停留在代码区域之内。事实证明，这对于保护来说还不够，原因有两个。第一，x86 代码按字节编址，如果允许跳转到一条指令的中间，就无法保证代码会做什么。特别是，一个有错误或恶意的程序可能跳到某条指令的中间，而那条指令的字节会让处理器跳出受保护区域。这看起来似乎不太可能，但请记住，攻击者占据优势：攻击者可以尝试各种代码序列，看哪一种能逃出沙箱。第二个问题是，间接分支可能跳过对装入或存储指令的保护检查。要防止这两种情况，可以让所有间接跳转都通过一张只包含合法代码入口点的表来完成；当然，这张表也必须受到保护，不能被沙箱中的代码修改。

现在逻辑上已经正确，我们就可以运行控制流和数据流分析，在能够证明某些插入的指令并不需要时，把许多多余的指令删除。可行的优化包括：

- **循环不变式。** 如果循环以固定步长遍历内存，沙箱或许能在循环开始处用一次简单的检查证明：循环中的所有内存访问都落在受保护区域内。

- **返回值。** 如果对过程进行静态代码分析能够证明该过程不会修改栈上保存的返回程序计数器，那么返回时无需再做检查即可安全完成。

- **跨过程检查。** 如果代码分析能够证明某个参数在作为实参传给子例程之前总是已经检查过，那么在该过程内部使用它时就不必再检查。

::: tip 无内核支持的虚拟机
修改机器码以透明地改变程序行为，同时仍然实施保护，这一技术还可以用于其他目的。一个应用是在没有内核支持的情况下，在用户级进程内部透明地执行客户操作系统。

通常，当我们在虚拟机中运行客户操作系统时，客户内核执行任何特权指令都会被硬件捕获并陷入宿主内核。宿主内核模拟这些指令，然后把控制权返回到客户内核中紧跟硬件异常之后的那条指令。这样，宿主内核就能模拟特权级、中断、异常以及对硬件页表的内核管理。

如果我们运行在一个不支持虚拟机的操作系统之上，情况会怎样？我们仍然可以通过修改客户操作系统内核的机器码来模拟一台虚拟机。例如，可以把开中断和关中断的指令改成空操作。可以把启动用户程序的指令改成：取出应用程序内存的内容，把这些内容重新写入一个用户级沙箱，然后让它开始执行。从客户内核的角度看，应用程序的执行一切正常；正是沙箱在阻止应用程序破坏内核的数据结构，并在应用程序发出系统调用时把控制权交给客户内核。

由于虚拟机的广泛使用，一些硬件体系结构已经开始增加支持，使得无需内核支持即可在用户态直接执行客户操作系统。我们将在后面一章回到这个问题，因为它与可堆叠虚拟机这一主题密切相关：当客户操作系统本身就是一个运行虚拟机的虚拟机监控器时，我们该如何操纵页表来处理这种情况。
:::

### 8.4.3　通过中间代码实现沙箱

为了提高可移植性，Microsoft 和 Google 都可以用编译器生成的中间代码来构造各自的沙箱。这样系统就更容易完成实施沙箱所需的代码修改和数据流分析。各种编译器不直接生成 x86 或 ARM 代码，而是用中间语言生成代码，再由沙箱运行时把它转换成特定处理器体系结构上的沙箱化代码。

中间表示可以看作一台指令集更简单的虚拟机。从编译器的角度看，为这台虚拟机生成代码与直接生成 x86 或 ARM 指令一样容易。不过从沙箱的角度看，用虚拟机作为中间表示要简单得多。中间代码可以带有标注，说明哪些指针能够被证明是安全的、哪些在使用前必须检查。例如，C 程序中的指针需要运行时检查，而 Java 程序中的内存引用或许可以根据代码结构静态地证明是安全的。

Microsoft 几乎为每一种有商业价值的编程语言都提供了编译器。为了避免把所有编译器的可信性都押在系统安全上，运行时系统负责验证为沙箱高效生成代码所需的任何类型信息。通常，验证静态分析的正确性要比最初生成这些分析结果简单得多。

Java 虚拟机（JVM）也是一种沙箱；Java 代码被翻译成中间字节码指令，这些指令可以在运行时被验证为安全地包含在沙箱之内。已经有好几种语言可以编译成 Java 字节码，例如 Python、Ruby 和 JavaScript。因此，JVM 也可以看作一个与语言无关的沙箱。不过，由于 Java 中间表示的结构所限，要为 C 或 Fortran 之类的语言生成正确的 Java 字节码则比较困难。

## 8.5　小结与未来方向

地址转换是一个强大的抽象，使各种各样的操作系统服务成为可能。它最初的设计目的是在进程之间提供隔离，并保护操作系统内核免受行为不当的应用程序侵害，但它的适用范围要广得多。如今它被用来简化内存管理、加速进程间通信、提供高效的共享库、把文件直接映射到内存，以及许多其他用途。

有效实施硬件地址转换的一大挑战，是数十年摩尔定律的累积效应：今天无论是服务器还是台式机都包含海量内存。进程现在可以把代码、数据、堆、共享库和文件直接映射到内存中。这些段每一个都可能是动态的；它们可以在进程之间共享，也可以是某个进程私有的。为应对这些需求，硬件系统已经收敛到一种两级结构：用多级段表和页表提供非常灵活但节省空间的查找，用 TLB 为同一页的重复转换提供时间上高效的查找。

凡是硬件能做的事，很多也能用软件来做；硬件保护与软件保护的结合在许多场合都被证明很有吸引力。现代网页浏览器把嵌入网页中的代码放在软件沙箱里执行，使这些代码无法感染浏览器；操作系统则使用硬件保护，在浏览器自身被攻破时提供另一层防御。

未来的趋势很清晰：

- **超大的内存系统。** 每 GB 内存的价格很可能继续暴跌，使越来越大的内存系统变得可行。过去几十年里，每台机器的内存容量几乎每年翻一番。我们日后回看今天的计算机，多半会奇怪：当年只有 1 GB DRAM 怎么够用！这些巨大的内存将需要越来越深的多级页表。幸运的是，使得建造超大内存成为可能的同一趋势，也使得设计非常大的 TLB 成为可能，从而掩盖查找树不断增加的深度。

- **多处理器。** 另一方面，多处理器意味着维护 TLB 一致性将变得越来越昂贵。用页表保护硬件实现写时复制和按需填页（fill-on-demand）的一个关键假设是，修改页表项的代价不大。一种可能是，在硬件中增加功能，使 TLB 击落成为代价低得多的操作，例如让 TLB 保持缓存一致性。另一种可能是顺应软件沙箱的趋势。如果 TLB 击落依然昂贵，我们可能开始看到写时复制和其他特性改由软件而不是硬件实现。

- **用户级沙箱。** 像浏览器这样运行不可信代码的应用程序正变得越来越普遍。操作系统只是最近才开始认识到需要支持这类应用。软件保护已经变得常见，既有语言层面的 JavaScript，也有运行时系统中的 Native Client 和 Application Domains。随着这些技术得到更广泛的使用，我们似乎很可能把硬件支持引向应用级保护——允许每个应用建立自己的受保护执行环境，但由硬件来实施。若果真如此，我们也许会把许多应用看作自带嵌入式操作系统，而把底层的操作系统内核看作这些操作系统之间的中介。
