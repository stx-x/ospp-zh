# 第 10 章　高级内存管理

<div class="chap-en">Advanced Memory Management</div>

在抽象层面，操作系统为应用进程提供一种执行上下文，包括：对特权指令的限制、进程的内存区域、一组系统调用，以及操作系统周期性重新取得处理器控制权的方式。通过在这个接口上进行介入（interpose）——最常见的是捕获并转换系统调用或内存引用——操作系统可以透明地插入新功能，以提升系统的性能、可靠性和安全性。

介入系统调用是直截了当的。内核用一次表查找来确定应用程序所调用的每个系统调用该转去哪个例程。内核只需修改表项，就能把一个系统调用重定向到一个新的增强例程。

更有趣的情形是内存系统。地址转换硬件为操作系统提供了一种高效的手段，让它可以监视并控制对特定内存区域的每一次引用，同时让其他内存引用不受影响地继续执行。（与之等价的是，基于软件的故障隔离也提供了许多类似的钩子，只是在介入程度与执行速度之间有着不同的取舍。）这使得地址转换成为操作系统向应用引入新的、高级服务的有力工具。我们已经展示过如何用地址转换来实现：

- <strong>保护。</strong> 操作系统利用地址转换硬件，加上段表和页表权限，来限制应用对内核等特权内存位置的访问。

- <strong>按需填充/按需置零。</strong> 把某些页表权限置为无效，内核就可以在进程的全部代码和数据都装入内存之前就开始执行该进程；如果进程在数据就绪之前就引用了它，硬件会陷入内核。同样，内核可以在后台把数据和堆页置零，依靠页引用故障来捕获应用第一次使用空页的时机。内核也可以只为内核栈和用户栈按需分配内存。把未使用的栈页标记为无效，内核就只在程序执行了深层的过程调用链时才需要分配这些页。

- <strong>写时复制。</strong> 写时复制允许多个进程拥有逻辑上相互独立的、同一内存区域的副本，而这些副本在内存中只由一份物理副本支撑。该区域中的每一页在每个进程里都被映射为只读；只有在一页被修改时（且仅当被修改时），操作系统才做出一份物理副本。

- <strong>内存映射文件。</strong> 磁盘文件可以成为进程虚拟地址空间的一部分，让进程用普通的处理器指令来访问文件中的数据。当内存映射文件的一页首次被访问时，一次保护故障会陷入操作系统，好让它把该页从磁盘调入内存。对文件块的第一次写也能被捕获，从而把这个块标记为需要写回磁盘。

- <strong>按需调页的虚拟内存。</strong> 操作系统可以运行那些使用的内存超过计算机物理内存的程序，办法是捕获对不在物理内存中的页的引用，并从磁盘或集群内存填充它们。

在本章中，我们探讨如何通过捕获并重新解释内存引用和系统调用，来构造若干其他高级的操作系统服务。

## 10.1　零拷贝 I/O

<figure class="book-figure">
<img src="/figures/vol3/image00320.png" alt="图 10.1" loading="lazy" decoding="async">
<figcaption><span class="fig-label">图 10.1</span>一个 Web 服务器从网络收到请求。服务器首先要求内核把被请求的文件从磁盘或其文件缓冲区复制到服务器的地址空间；然后服务器要求内核把文件内容再复制回网络。</figcaption>
</figure>

操作系统的一项常见任务，是在用户级程序与物理设备（如磁盘和网络硬件）之间流式传输数据。然而，如果数据在跨越保护边界时被复制，这种流式传输在处理时间上可能代价高昂。一个网络数据包需要从网络接口硬件进入内核内存，再到用户级；而响应则需要从用户级返回内核内存，再从内核内存到网络硬件。

考虑图 10.1 所示的 Web 服务器操作。几乎所有的 Web 服务器都实现为用户级程序。这样一来，重新配置服务器行为就很容易，而且服务器实现中的缺陷也未必会危及系统安全。

一个 Web 服务器要响应一次 Web 请求，需要经过一系列步骤。在这个例子里，假设客户端与服务器之间的连接已经建立，为每个客户端连接分配了一个服务器线程，并且我们使用显式的读写系统调用而不是内存映射文件。

- <strong>服务器从网络读取。</strong> 服务器线程调用内核，等待到达的请求。

- <strong>数据包到达。</strong> Web 请求从网络到达；网络硬件用 DMA 把数据包数据复制到内核缓冲区。

- <strong>把数据包数据复制到用户级。</strong> 操作系统解析数据包头，确定由哪个用户进程接收这个 Web 请求。内核把数据复制到服务器线程提供的用户级缓冲区，然后返回用户级。

- <strong>服务器读取文件。</strong> 服务器解析 Web 请求中的数据，确定请求的是哪个文件。它向内核发出一次文件读系统调用，并提供一个用户级缓冲区来存放文件内容。

- <strong>数据到达。</strong> 内核发出磁盘请求，磁盘控制器把数据从磁盘复制到内核缓冲区。如果文件数据已经在文件缓冲区缓存里——对于热门 Web 请求常常如此——就跳过这一步。

- <strong>把文件数据复制到用户级。</strong> 内核把数据复制到用户进程提供的缓冲区，然后返回用户级。

- <strong>服务器写向网络。</strong> 服务器转过身来，把存放文件数据的缓冲区交回内核，让它发送到网络。

- <strong>把数据复制到内核。</strong> 内核把数据从用户级缓冲区复制到内核缓冲区，格式化数据包，然后向网络硬件发出请求。

- <strong>数据发送。</strong> 硬件用 DMA 把数据从内核缓冲区复制到网络。

虽然我们用 Web 服务器来举例说明，但对于任何把数据流式传入或传出计算机的应用，都会发生类似的过程。例子包括 Web 客户端、在线视频或音乐服务、BitTorrent、网络文件系统，甚至软件下载。对其中每一种应用，数据都是从硬件复制进内核、再进入用户空间，或者反过来。

我们可以把这些应用都移进内核，从而消除跨内核-用户边界的额外复制。但这不现实，因为它要求把操作系统的全部权力托付给这些应用。另一种办法是修改系统调用接口，让应用能直接操作存放在内核缓冲区里的数据，而不必先把数据复制到用户内存。但这也不是通用的解决方案；如果应用需要对缓冲区做任何处理，而不仅仅是把它从一个硬件设备传输到另一个，这个办法就行不通。

实际上，有*零拷贝 I/O*的两种解决方案投入使用。两者都消除了大块数据跨内核-用户边界的复制；而对于小块数据，额外复制不会损害性能。

更广泛使用的那种方法，是操纵进程页表来模拟一次复制。要让这个方法生效，应用必须先把它的用户级缓冲区对齐到页边界。用户级缓冲区在读写系统调用时提供给内核，其对齐方式和大小由应用决定。

关键思想在于：用户空间到内核空间（或反过来）的页到页复制，可以通过改变页表指针来模拟，而不必真正地复制内存。

对于从用户空间到内核的复制（例如网络或文件系统写），内核改变用户级缓冲区页表项的权限，防止它被修改。内核还必须*钉住*（pin）这个页，防止它被虚拟内存管理器逐出。在常见情况下，这就足够了——在 I/O 请求进行期间，这个页通常不会被修改。如果用户程序确实试图修改该页，程序会陷入内核，内核可以在那一刻做一次显式复制。

<figcaption><span class="fig-label">图 10.2</span>在内核通过交换页表项、让它指向内核缓冲区，从而把数据“复制”到用户级之前与之后，页表的内容。</figcaption>

在另一个方向，一旦数据进入了内核缓冲区，操作系统就可以通过切换页表中的指针来模拟一次向用户空间的复制，如图 10.2 所示。进程页表原本指向存放（空的）用户缓冲区的页框；现在它指向存放（满的）内核缓冲区的页框。对用户程序来说，数据正好出现在它所期待的位置！内核可以回收那个空缓冲区背后的任何物理内存。

近来，一些硬件 I/O 设备被设计成能够向虚拟地址、而不只是向物理地址传输数据。内核把用户级缓冲区的虚拟地址交给硬件设备。由硬件设备（而不是内核）去遍历多级页表，确定用哪个物理页框进行设备传输。传输完成时，数据自动到达它该在的位置，内核无需再做任何额外工作。对于传入的网络数据包，这个过程要稍微复杂一些，因为“哪个进程该接收哪个数据包”是由数据包头的内容决定的。因此，网络接口硬件必须解析传入的数据包，把数据投递给合适的进程。

## 10.2　虚拟机

虚拟机是一种让宿主操作系统把客户操作系统当作一个应用进程来运行的方式。宿主模拟一台物理机器的行为，使得客户系统表现得就像运行在真实硬件上一样。虚拟机在客户端机器上被广泛用于运行那些并非当前操作系统版本原生的应用。它们也被广泛用于数据中心，让一台物理机器能在多个相互独立的用途之间共享，其中每个用途都可以被编写得如同对整台（虚拟）机器拥有系统管理员控制权一样。例如，多个代表不同网站的 Web 服务器可以托管在同一台物理机器上，只要它们各自运行在独立的虚拟机里。

地址转换给实现虚拟机这一挑战带来了一个麻烦，但它同时也打开了提高效率和提供新服务的机会。

### 10.2.1　虚拟机页表

采用虚拟机后，我们有了两套页表，而不是一套，如图 10.3 所示：

- <strong>客户物理内存到主机物理内存。</strong> 宿主操作系统提供一组页表，用来约束客户操作系统内核的执行。客户内核以为自己在真实的物理内存上运行，但实际上它的地址是虚拟的。硬件页表在检查过客户对每个位置的读写权限之后，把客户操作系统的每一次内存引用转换为一个物理内存位置。这样，宿主操作系统就能防止客户操作系统中的缺陷覆写宿主的内存，就像客户是一个普通的用户级进程一样。

- <strong>客户用户内存到客户物理内存。</strong> 反过来，客户操作系统为它的客户进程管理页表，就像客户内核运行在真实硬件上一样。由于客户内核对宿主内核分配给它的物理页框一无所知，这些页表把客户进程地址转换为客户操作系统内核地址。

首先，考虑宿主操作系统把控制权转移给客户内核时会发生什么。一切都按预期运行。客户操作系统可以读写它的内存，硬件页表提供了一种假象：客户内核直接运行在物理内存上。

现在考虑客户操作系统把控制权转移给客户进程时会发生什么。客户内核运行在用户级，因此它转移控制权的尝试是一条特权指令。于是，硬件处理器会先陷入宿主。宿主内核随后可以模拟这条转移指令，把控制权交给用户进程。

然而，在这种情况下我们该用哪张页表呢？不能用客户操作系统建立的页表，因为客户操作系统以为自己在物理内存中运行，但它实际使用的是虚拟地址。也不能用宿主操作系统建立的页表，因为那会授予客户进程访问并修改客户内核数据结构的权限。如果我们把客户内核内存的访问权授予客户进程，虚拟机的行为就会受到破坏。

<img src="/figures/vol3/image00323.png" alt="图 10.4" loading="lazy" decoding="async">
<figcaption><span class="fig-label">图 10.4</span>为了运行一个客户进程，宿主操作系统构造一张影子页表，由两张页表的内容复合而成。</figcaption>
</figure>

相反，我们需要构造一张复合页表，称为*影子页表*（shadow page table），它代表客户页表与宿主页表的复合，如图 10.4 所示。当客户内核把控制权转移给客户进程时，宿主内核取得控制权，把页表换成影子版本。

为了让影子页表保持最新，宿主操作系统需要跟踪客户或宿主操作系统对自己页表所做的改动。对宿主操作系统来说这很容易——在改动页表项之前，它可以检查是否有影子页表需要更新。

然而，要跟踪客户操作系统对自己页表所做的改动，就需要多做一些工作。宿主操作系统把客户页表的内存设为只读。这保证客户操作系统每次试图改动页表项时都会陷入宿主。宿主利用这次陷入，同时改动客户页表和对应的影子页表，然后再恢复客户操作系统的执行（页表仍保持只读）。

::: tip 半虚拟化
让虚拟机运行得更快的一种办法，是假定客户操作系统被*移植*（ported）到了虚拟机上。依赖硬件的底层，被替换成理解虚拟机的代码。这被称为半虚拟化（paravirtualization），因为这样得到的客户操作系统与运行在真实物理硬件上的系统几乎、但并不完全一样。

半虚拟化在几个方面有帮助。也许最重要的是处理空闲循环。当客户操作系统没有线程可运行时应发生什么？如果客户相信自己在物理硬件上运行，那么什么都不发生——客户原地空转、等待更多工作，也许还会把自己置于低功耗模式。最终硬件会引发一次定时器中断，把控制权转移给宿主操作系统。宿主随后可以决定是恢复这个虚拟机，还是运行其他线程（甚至其他虚拟机）。

而采用半虚拟化，空闲循环可以更高效。实现空闲循环的硬件相关软件可以陷入宿主内核，立即把处理器让给其他用途。

同样，采用半虚拟化，客户操作系统内部依赖硬件的代码可以对宿主内核发起显式调用以修改自己的页表，从而免除宿主模拟客户页表管理的需要。
:::

Intel 架构最近为虚拟机中页表的复合增加了直接的硬件支持。硬件可以不是只设置一张页表，而是设置两张页表，一张给宿主、一张给客户操作系统。当运行一个客户进程时，在 TLB 未命中时，硬件用客户页表把虚拟地址转换为客户物理页框，然后再用宿主页表把客户物理页框转换为主机物理页框。换句话说，TLB 中含有两张页表的复合，就像宿主维护了一张显式的影子页表一样。当然，如果客户操作系统自己又把一个虚拟机作为客户用户进程来托管，那么客户内核就必须构造影子页表。

虽然这种硬件支持简化了虚拟机的构造，但它能否提升性能尚不明确。TLB 未命中的处理变慢了，因为宿主操作系统必须查两张页表而不是一张；但对客户页表的改动更快了，因为宿主无需维护影子页表。这一取舍在实践中是否有用，还有待观察。

### 10.2.2　透明内存压缩

贯穿本书的一个主题，是复用复用器的困难。采用虚拟机后，宿主操作系统和客户操作系统都在尝试做同一件事：把一组任务高效地复用到有限的内存上。客户操作系统为管理自己的内存所做的决策，可能与宿主操作系统为管理自己的内存所做的决策背道而驰。

内存的高效使用在数据中心里可能尤为重要。数据中心里的一台物理机器，常常被配置成同时运行许多虚拟机。例如，一台机器可以托管许多不同的网站，其中每个网站都太小，不值得独占一台专用机器。

要让这种方案行得通，系统需要足够的内存，才能同时运行许多不同的操作系统。宿主操作系统可以通过在客户内核之间共享内存来帮忙，例如，如果它运行的两个客户内核用的是同一个可执行内核映像。同样，客户操作系统可以通过在客户应用之间共享内存来帮忙，例如，如果它运行的是同一个程序的两份副本。然而，如果不同的客户内核都运行同一个用户进程的一份副本（例如都运行 Apache Web 服务器），或者使用同一个库，宿主内核就没有（直接的）办法在这两个实例之间共享页。

另一个例子出现在客户进程退出时。客户操作系统把退出进程的页框放到空闲链表上，以便重新分配给其他进程。任何数据页的内容都不会再被用到；事实上，客户内核在重新分配这些页之前还需要把它们置零。然而，宿主操作系统没有（直接的）办法知道这一点。最终这些页会被宿主逐出，例如当它们成为最近最少使用的时候。但在此期间，宿主操作系统可能已经逐出了客户里那些仍然活跃的页。

一种解决办法是更紧密地协调客户与宿主的内存管理器，让双方都了解对方在做什么。我们在本章后面会详细讨论这一点。

商业虚拟机的实现采取不同的方法，利用硬件地址保护来管理虚拟机之间公共页的共享。这些系统在后台运行一个清扫器，寻找可以在虚拟机之间共享的页。一旦识别出一个公共页，宿主内核就操纵页表指针，制造出“每个客户都拥有该页自己的一份副本”的假象，即便物理表示更为紧凑。

<img src="/figures/vol3/image00324.png" alt="图 10.5" loading="lazy" decoding="async">
<figcaption><span class="fig-label">图 10.5</span>当宿主内核运行多个虚拟机时，它可以通过存放对现有页（页 A）的增量、以及对同一页的多份副本（页 B）使用同一个物理页框来节省空间。</figcaption>
</figure>

需要考虑两种情形，如图 10.5 所示：

- <strong>同一页的多份副本。</strong> 两个不同的虚拟机常常会有内容相同的页。一个明显的例子是置零页：每个内核都维护一个已经置零、随时可以分配给新进程的页池。如果每个客户操作系统各自运行在自己的机器上，保持这个页池待命几乎没什么代价，因为除了内核之外没有人能使用那段内存。然而，当物理机器在虚拟机之间共享时，让每个客户都保留自己的零页池就是一种浪费。相反，宿主可以在物理内存中为所有这些实例分配一个单一的零页。所有指向该页的指针都被设为只读，因此任何试图修改该页的操作都会陷入宿主内核；内核随后可以为这一用途分配一个新的（置零的）物理页，就像写时复制一样。当然，客户内核在创建零页时不需要告诉任何人，所以宿主内核在后台运行一个清扫器，在客户内存中寻找零页。当它找到一个时，就回收那个物理页，把页表指针改为指向共享零页，并赋予只读权限。清扫器对其他共享页框也可以做同样的事。应用和共享库的代码段与数据段，即便跨越不同的操作系统，也往往是相同的或相当相似的。像 Apache Web 服务器这样的应用，不会为每一个不同的操作系统从头重写；相反，会加入一些操作系统相关的粘合代码，把应用的可移植部分与它的特定环境对接起来。

- <strong>未使用页的压缩。</strong> 即便某个页不同，它也可能与另一个虚拟机里的某个页很接近。例如，不同版本的操作系统可能只在某些细小的方面有差异。这为宿主内核提供了一个机会，即在存储层次中引入一个新层以节省空间。操作系统可以不去逐出一个相对未使用的页，而是把它压缩起来。如果这个页是某个现有页的增量，那么压缩后的版本可能相当小。内核操纵页表权限，维持“这个增量是一个真实页”的假象。页的完整副本被标记为只读；增量被标记为无效。如果增量被引用，它被重新构成为完整页的速度比存放在磁盘上更快。如果原页被修改，增量可以根据需要重新压缩或逐出。

## 10.3　容错

一切系统都会出故障。尽管我们竭尽全力，应用代码仍可能有缺陷，导致进程突然退出。操作系统代码可能有缺陷，导致机器停机并重启。电源故障和硬件错误也会让系统毫无征兆地停止。

大多数应用的结构都会针对这类事件，周期性地把用户数据保存到磁盘。当操作系统或应用重启时，程序可以从磁盘读出已保存的数据，让用户得以继续他们的工作。

在本节中，我们更进一步，看看能否管理内存，让应用的数据结构（而不只是用户的文件数据）在故障后得到恢复。

### 10.3.1　检查点与重启

我们可能想要恢复应用数据的一个原因，是程序运行时间很长。如果对未来全球气候的模拟要计算一个星期，我们可不想每次遇到电源毛刺都从头再来。如果涉及的机器足够多、计算时间足够长，那么在计算过程中至少有一台机器会在某个时刻遇到故障，这是很可能的。

当然，程序可以写成把自己的内部数据当作珍宝——周期性地把部分结果保存到文件。为确保数据内部一致，程序需要一些自然的停止点；例如，程序可以在进入 2051 年气候的计算之前，先保存预测出的 2050 年气候。

一种更通用的办法，是让操作系统利用虚拟内存系统，把应用恢复作为一项服务来提供。如果我们能保存进程的状态，就能在电源故障时透明地重启它，恰好从它中断的地方继续，用户浑然不觉。

<figure class="book-figure">
<img src="/figures/vol3/image00325.png" alt="图 10.6" loading="lazy" decoding="async">
<figcaption><span class="fig-label">图 10.6</span>通过对进程状态做检查点，我们可以在故障后通过恢复保存的副本，来恢复进程已保存的状态。</figcaption>
</figure>

要让这套机制运转起来，我们首先需要挂起进程中的每个线程，把它的状态——程序计数器、栈指针和寄存器——保存到应用内存中。一旦所有线程都被挂起，我们就可以把应用内存内容的一份副本存到磁盘上。这被称为一个*检查点*（checkpoint）或快照，如图 10.6 所示。在故障之后，我们可以通过从检查点恢复内存内容、并从我们停止它们的那个确切位置恢复每个线程，来继续执行。这被称为应用*重启*（restart）。

如果我们在把内存内容保存到磁盘的同时允许线程继续运行，会发生什么？在复制期间会有一个竞态条件：某些页可能在某个线程修改它们之前就被保存，而另一些页则可能在被同一个线程修改之后才被保存。当我们试图重启应用时，它的数据结构可能看起来已经被损坏。程序的行为可能与没有发生故障时应有的行为不同。

幸运的是，我们可以利用地址转换，把检查点期间系统必须停顿的时间降到最低。我们不必把内存内容复制到磁盘，而是可以把应用的页标记为写时复制。此时，我们就可以重启程序的线程了。当每一页到达磁盘后，我们就把该页的保护重置为读写。当程序试图修改一个尚未到达磁盘的页时，硬件会引发异常，内核就可以复制这个页——一份保存到磁盘，一份给正在运行的程序用。

我们可以用同样的方式对操作系统本身做检查点。如果操作系统运行在虚拟机里，这就最容易做到。宿主可以通过停止虚拟机、保存处理器状态、并把（宿主页表中的）页表保护改为只读，来做一个检查点。此后虚拟机就可以安全地重启，而宿主在后台把检查点写到磁盘。

::: tip 检查点与系统调用
检查点/重启的一个实现挑战，是正确处理任何正在进行中的系统调用。程序的状态不仅仅是它的用户级内存；它还包括正在内核中执行的任何线程的状态，以及内核为进程维护的任何每进程状态，比如它的打开文件描述符。虽然有些操作系统被设计成允许把进程的内核状态作为检查点的一部分捕获下来，但更常见的做法是只在虚拟机层支持检查点。一个虚拟机在内核中没有状态，只有它的内存内容和处理器寄存器。如果我们需要在某个陷入处理程序进行到一半时做检查点，那么直接重启这个处理程序即可。
:::

*进程迁移*（process migration）是指在一台系统上取一个正在运行的程序、停止它的执行、然后在另一台机器上恢复它的能力。检查点与重启为透明的进程迁移提供了基础。例如，如今在数据中心内部对整台虚拟机做检查点并迁移，已经成为平衡负载的一种常见做法。如果一台系统托管着两个 Web 服务器，而两者都变得负载很重，我们就可以停掉其中一个、把它移到另一台机器上，让两者都能获得更好的性能。

### 10.3.2　可恢复虚拟内存

对进程或虚拟机做一次完整的检查点是重量级的操作，因此实际上只能比较罕见地做一次。我们可以在开始检查点后，用写时复制的页保护来恢复进程，但完成检查点仍需要相当长的时间，因为我们要把内存内容复制到磁盘。

我们能否给应用提供一种“持久内存”的假象，让内存内容恢复到故障前不久的某个点？具备这种能力被称为*可恢复虚拟内存*（recoverable virtual memory）。我们可能想要可恢复虚拟内存的一个例子是电子邮件客户端；当你阅读、回复和删除邮件时，你不希望系统崩溃时自己的工作丢失。

如果我们把效率放在一边，可恢复虚拟内存是可行的。首先，我们做一个检查点，让应用数据的某个一致版本落到磁盘上。接下来，我们记录应用对内存所做的每一次更新，形成一个有序序列，即*日志*（log）。一旦日志写到磁盘上，我们就能在故障后通过读取检查点、再应用日志中的改动来恢复。

这正是大多数文本编辑器保存备份的方式，好让它们在机器或应用故障后能恢复未提交的用户编辑。文本编辑器可以反复地把文件的完整副本写到一个备份，但这样很慢，对大文件尤其如此。相反，文本编辑器会先写文件的一个版本，然后追加用户对该版本所做每一次改动的序列。为了避免把每个键入的字符都单独写到磁盘，编辑器会批量处理改动，例如把用户在过去 100 毫秒里所做的全部改动作为一个单元写到磁盘。即便最新的一批改动还没有写到磁盘，用户通常也能恢复到机器崩溃前几乎那一瞬间的文件状态。

这个算法对文本编辑器有一个缺点：它可能导致信息在文件当前版本不可见的情况下泄露出去。文本编辑器有时在用户点击“保存”时也使用同样的方法——只追加上一版本以来的改动，而不是重写整个文件的崭新副本。这意味着文件的旧版本仍可能从文件中恢复出来。所以，如果你写了一份辱骂老板的备忘录，后来又编辑它、把语气缓和下来，那么最好在发送之前另存一份全新的文件版本！

这个方法对持久内存行得通吗？对进程里每个内存位置的每一次改动都记日志，会太慢。我们得在每条存储指令上陷入，并把值保存到磁盘。换句话说，我们就会以陷入处理程序的速度、而不是处理器的速度运行。

不过，我们可以很接近这个目标。在做检查点时，我们把所有页都标记为只读，以确保检查点包含进程内存状态的一份一致快照。然后，我们对每一页的第一次存储指令陷入内核，让内核做一次写时复制。内核把该页重置为读写，好让对同一页的后续存储指令全速运行，但它也可以记录下该页已被修改。

<figure class="book-figure">
<img src="/figures/vol3/image00326.png" alt="图 10.7" loading="lazy" decoding="async">
<figcaption><span class="fig-label">图 10.7</span>通过保存一串增量检查点，操作系统可以在崩溃后恢复内存段的状态。</figcaption>
</figure>

我们可以通过停止程序、并保存自上一个检查点以来被修改过的任何页的副本来做一次*增量检查点*（incremental checkpoint）。一旦把这些页改回只读，我们就可以重启程序，等一会儿，再做一次增量检查点。崩溃之后，我们可以通过读入第一个检查点、再依次应用每一个增量检查点，来恢复最近的内存，如图 10.7 所示。

机器崩溃时我们会损失多少工作，取决于我们把一次增量检查点完全写到磁盘的速度。这受应用产生新数据的速率支配。为降低增量检查点的成本，需要可恢复虚拟内存的应用会指定一个特定的内存段为持久段。崩溃之后，该内存会被恢复到最新的增量检查点，让程序能迅速继续它的工作。

### 10.3.3　确定性调试

构建可靠的系统软件，一个关键是当问题确实发生时能够定位并修复它。调试顺序程序相对容易：如果你给它相同的输入，它就会以相同的顺序执行相同的代码，并产生相同的输出。

调试并发程序要难得多：程序的行为可能随操作系统所选择的精确调度顺序而变化。如果程序是正确的，那么对相同的输入应当产生相同的输出。然而，如果我们在调试一个程序，它大概是不正确的。相反，程序的精确行为可能随每次运行而异，取决于哪些线程先被调度。

调试操作系统就更难了：操作系统不仅大量使用并发，而且有时很难说清它的“输入”和“输出”是什么。

然而，事实证明，我们可以用虚拟机抽象为操作系统提供一个可重复的调试环境，进而用它为并发应用提供可重复的调试环境。

在单处理器上最容易看清这一点。一个运行在虚拟机里的操作系统的执行，只可能受三个因素影响：它的初始状态、它的 I/O 设备提供的输入数据、以及中断的精确时机。

由于宿主内核为虚拟机居中调度这三者中的每一项，它可以在调试期间记录它们并回放。只要宿主精确地复现它第一次所做的一切，客户操作系统的行为就会相同，而运行在客户操作系统之上的所有应用的行为也会相同。

回放输入很容易，但我们如何回放中断的精确时机呢？大多数现代计算机架构在处理器上有一个计数器，用来测量执行的指令数。宿主操作系统可以用它来测量：从宿主把处理器控制权交给客户、到因中断或陷入而把控制权归还内核，这期间客户操作系统（或客户应用）执行了多少条指令。

要回放一次异步中断的精确时机，宿主内核在中断交付给客户的那一刻，记录下客户的程序计数器和指令计数。回放时，宿主内核可以在包含下一次中断将要发生的那个程序计数器的页上设置一个陷阱。由于客户可能多次访问同一个程序计数器，宿主内核用指令计数来确定哪一次访问对应着中断交付的那一次。（有些系统让这件事更简单，允许内核请求在指令计数达到某个值时触发一次陷阱。）

此外，如果我们想跳到某个已知的好的中间点，可以做一个检查点，然后从那里开始向前回放中断序列和输入数据。这一点很重要，因为有时操作系统中的缺陷要数周才会显现；如果我们每次都需要从启动开始回放一切，调试过程会麻烦得多。

在多核系统上事情更复杂，因为客户操作系统和客户应用的精确行为，都取决于指令在不同处理器之间的精确顺序。如何在这种场景下最好地提供确定性执行，是一个正在进行的研究领域。只要被调试的程序没有竞态条件——也就是没有在临界区之外对共享内存的访问——那么它的行为在多一条信息的情况下就会是确定性的。除了初始状态、输入和异步中断之外，我们还需要记录哪个线程以何种顺序获取每个临界区。如果我们按那个顺序回放线程、精确地交付中断、并提供相同的设备输入，行为就会相同。这是否是一个实用的解决方案，仍然是一个悬而未决的问题。

## 10.4　安全

硬件或软件的地址转换为执行不可信的应用代码提供了基础，让操作系统内核能够保护自己和其它应用，免受恶意或有缺陷的实现之害。

然而，一台现代智能手机或平板电脑，可以安装的应用实际上有数十万个。其中许多、甚至大多数都是完全可信的，但另一些则是专门设计来窃取或破坏本地数据的，手段是利用底层操作系统的弱点，或是利用人类天生倾向信任技术这一点。用户该如何分辨哪些可信、哪些不可信呢？网络上存在类似的情形：即便大多数网站都是无害的，仍有一些网站嵌入了利用浏览器防御中已知漏洞的代码。

如果我们无法限制自己对潜在恶意应用的暴露，还能做些什么？重要的一步是让系统软件保持最新。恶意代码的作者也认识到这一点：最近一项调查显示，最可能携带病毒的网站，是那些面向最新手用户的网站，例如屏保和儿童游戏。

在本节中，我们讨论是否还有其它办法，能用虚拟机来限制恶意应用的影响范围。

假设你想下载一个新应用，或者访问一个新网站。它有某种可能按广告所说的那样工作，也有某种可能携带病毒。有没有什么办法，能限制这个新软件利用你的操作系统或浏览器中某个未知漏洞的能力？

一种有趣的办法，是把你的操作系统克隆到一个新的虚拟机里，并在克隆中、而不是在原生的操作系统上运行该应用。为执行可疑代码而构造的虚拟机，称为*虚拟机蜜罐*（virtual machine honeypot）。借助虚拟机，如果代码最终证明是恶意的，我们就可以删除这个虚拟机，让底层操作系统保持在我们试图运行该应用之前的状态。

为执行一个新应用而创建一台虚拟机，可能显得铺张。然而，在本章前面，我们讨论过各种让它更高效的办法：影子页表、内存压缩、高效的检查点与重启，以及写时复制。而且，在系统感染病毒之后重装系统，当然更慢！

研究者和商用反病毒软件的厂商都大量使用虚拟机蜜罐来检测和理解病毒。例如，一种常见的技巧是创建一组虚拟机，每个装不同版本的操作系统。把潜在的病毒加载进每一个虚拟机，再模拟用户行为，我们就能更容易地判断哪些软件版本易受攻击、哪些不易受攻击。

一个局限是，我们需要能够判断运行在虚拟机蜜罐里的浏览器或操作系统是否已被破坏。病毒常常是即时行动的：试图安装日志软件，或扫描磁盘寻找信用卡号之类的敏感信息。没有什么能阻止病毒潜伏等待；近来这种情况越来越常见，尤其是那些为军事或商业间谍活动设计的病毒。

另一个局限是，病毒可能被设计成同时感染克隆中运行的客户操作系统、以及实现虚拟机的宿主内核。（在网络的情形下，病毒必须感染浏览器、客户操作系统和宿主。）只要系统软件保持最新，只有当病毒能够利用客户操作系统中某个未知弱点、并利用宿主虚拟机实现中另一个独立的未知弱点时，系统才会被攻破。这就提供了*纵深防御*（defense in depth），通过多层保护提升安全性。

## 10.5　用户级内存管理

随着应用及其运行时系统日益复杂，大多数广泛使用的操作系统都引入了让应用管理自己内存的钩子。虽然各系统接口的细节不同，但这些钩子都保留了内核在进程之间分配资源、以及阻止对特权内存的访问这两项职责。不过，一旦一个页框被分配给某个进程，内核就可以让该进程自己决定如何处置这一资源。

操作系统可以让应用在以下方面自主决策：

- <strong>从哪里获取缺失的页。</strong> 正如我们在上一章指出的，现代存储层次又深又复杂：本地磁盘、本地非易失内存、数据中心内部的远端内存，或者远端磁盘。把控制权交给应用，内核就能让自己的存储层次保持简单、本地化，同时仍允许复杂的应用在网络资源可用时利用它们，即便这些资源位于运行着完全不同操作系统的机器上。

- <strong>哪些页可以被访问。</strong> 许多应用，比如浏览器和数据库，需要建立自己的应用级沙箱来执行不可信代码。今天，这是通过软硬件技术的结合来完成的，正如我们在第 8 章描述的。对缺页处理更细粒度的控制，可以实现更精细的模型，来管理不可信代码各区域之间的共享。

- <strong>哪些页应当被逐出。</strong> 应用常常比操作系统更清楚它在不久的将来会引用哪些页。

许多应用都能让自己的工作集大小适应内核提供的资源，但只要出现失配，它们的性能就会变差。

- <strong>垃圾回收程序。</strong> 考虑一个自己做垃圾回收的程序。启动时，它在自己的虚拟地址空间里分配一块内存作为堆。周期性地，程序扫描堆、压缩它的数据结构，为更多数据结构腾出空间。这会让所有页都显得“近期使用”，从而迷惑内核的内存管理器。反过来，应用知道最该置换的页是最近刚清空应用数据的那个页。对应用来说，这同样令人困惑。垃圾回收器怎么知道该为堆分配多少内存呢？理想情况下，垃圾回收器应当恰好使用内核所能提供的那么多内存，不多也不少。如果运行时堆太小，程序就不得不做垃圾回收，尽管还有更多可用的页框；如果堆太大，内核就会把堆的一部分调页到磁盘，而不是让应用以更低的压缩开销来付出代价。

- <strong>数据库。</strong> 数据库和其它数据处理系统常常操作必须从磁盘流式读入内存的庞大数据集。正如我们在第 9 章指出的，针对大数据的算法如果根据可用物理内存的量来定制，就会更高效。如果操作系统逐出了数据库预期在内存中的页，这些算法的运行就会慢得多。

- <strong>虚拟机。</strong> 虚拟机也存在类似的问题。运行在虚拟机内部的客户操作系统，以为它有一组物理页框，可以把它们分配给虚拟机中应用的虚拟页。然而实际上，客户操作系统中的页框是虚拟的，可以被宿主操作系统调页到磁盘。如果宿主操作系统能在需要夺取一个页框（或捐赠一个页框）时告知客户操作系统，那么客户就能确切地知道有多少页框可供分配给它的应用。

在上述每一种情形中，如果一个资源管理器运行在虚拟化、而非物理的资源之上，它的性能都可能受损。所需要的，是操作系统内核把分配给进程或虚拟机的内存量传达出来，好让应用去做自己的内存管理。随着进程的启动和完成，可用物理内存的量会变化，因此分配给每个应用的量也会变化。

为应对这些需求，大多数操作系统提供某种程度的应用内存控制。出现了两种模型：

- <strong>钉住的页。</strong> 一种简单且广泛可用的模型，是允许应用把虚拟内存页*钉住*（pin）到物理页框上，除非绝对必要，否则防止这些页被逐出。一旦钉住，应用就可以随心所欲地管理它的内存，例如显式地把数据在磁盘之间来回搬运。

- <strong>用户级调页器。</strong> 一种更通用的方案，是让应用为某个内存段指定一个*用户级页处理程序*（user-level page handler）。发生缺页或保护违例时，内核的陷入处理程序被调用。内核不是自己处理故障，而是把控制权交给用户级处理程序，就像 UNIX 信号处理程序那样。用户级处理程序随后可以决定如何处置这次陷入：从哪里获取缺失的页、如果应用是沙箱该采取什么行动、以及置换哪一个页。为避免无限递归，用户级页处理程序本身必须存放在被钉住的内存中。

## 10.6　小结与未来方向

在本章中，我们论证了地址转换是操作系统向应用提供一组高级服务、以提升系统性能、可靠性和安全性的有力工具。检查点、可恢复内存、确定性调试和蜜罐等服务，如今已在虚拟机层得到广泛支持，我们相信它们也将在大多数操作系统中成为标配。

展望未来，很明显，高级服务对内存管理系统的需求将会增加。不仅存储层次日益复杂，内存管理系统所提供服务的多样性也增添了更多的复杂性。

操作系统常常经历这样的循环：复杂性逐渐增加，随后又迅速回归简单。近来业界对虚拟机的兴趣，可能通过减少内核对“任何应用可能需要的每项服务”的提供，带来向更简单内存管理的回归。处理器架构现在直接支持用户级页表。对于本身就是微型操作系统的那些应用，这可能开启一个全新的领域，实现更复杂的运行时系统，同时内核得到简化的机会。有了恰当的操作系统支持，应用将能够直接建立和管理自己的页表，实现自己的用户级进程抽象，并对内存段提供自己的透明检查点与恢复。
