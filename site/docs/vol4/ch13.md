# 第 13 章　文件与目录

<div class="chap-en">Files and Directories</div>

<blockquote class="epigraph">名字算什么？我们叫作玫瑰的那种花，换个名字，芬芳依旧。——《罗密欧与朱丽叶》第二幕第二场（莎士比亚）</blockquote>

回顾第 11 章：文件系统用目录来提供按层次命名的文件，而每个文件都包含元数据和一串数据字节。然而，正如第 12 章所讨论的，存储设备提供的抽象层次要低得多——大片的数据库块数组。因此，要实现文件系统，我们必须解决一个转换问题：怎样从文件名和偏移量得到块号？

一个简单的答案是：文件系统实现了一张字典，把键（文件名和偏移量）映射到值（设备上的块号）。我们已经有多种用于实现字典的数据结构，包括哈希表、树和跳表，那么也许直接挑一种来用就可以了？

不幸的是，答案并没有这么简单。文件系统的设计者面临四个重大挑战：

- **性能。** 文件系统需要在应对底层存储设备局限的同时提供良好的性能。在实践中，这意味着文件系统要努力保证良好的**空间局部性**：被一起访问的块存放在彼此邻近的位置，最好就落在连续的存储块中。

- **灵活性。** 文件系统的一个主要用途是让应用程序共享数据，因此它必须是“多面手”。如果大文件顺序读要用一种文件系统，很少写入的小文件要用另一种，大文件随机访问再用一种，短命文件还得再换一种，依此类推，那文件系统就没什么用了。

- **持久性。** 文件系统必须把用户数据和自己的内部数据结构都维护、更新在持久存储设备上，使这一切都能在操作系统崩溃和断电之后幸存。

- **可靠性。** 文件系统必须能够长期保存重要数据，即使更新过程中机器崩溃，或者系统的某些存储硬件发生故障。

本章讨论文件系统在组织上如何应对前三个挑战，第 14 章讨论可靠性。

## 13.1　实现概述

文件系统必须把文件名和偏移量映射到物理存储块，并且这种映射要支持高效的访问。尽管存在许多不同的文件系统，大多数实现都建立在四个关键思想之上：目录、索引结构、空闲空间映射表和局部性启发式策略。

<figure class="book-figure">
<img src="/figures/vol4/image00314.png" alt="图 13.1" loading="lazy">
<figcaption><span class="fig-label">图 13.1</span>文件系统分两步把文件名和文件偏移量映射到存储块。首先，它们用目录把名字映射到文件号；然后，它们用一种持久存储的树那样的索引结构，找出存放该文件任意特定偏移量处数据的块。</figcaption>
</figure>

**目录与索引结构。** 如图 13.1 所示，文件系统分两步把文件名和文件偏移量映射到特定的存储块。

第一步，它们用**目录**把人类可读的文件名映射到文件号。目录通常就是一种特殊文件，其中存放着一串**文件名** →**文件号**的映射。

第二步，文件名被转换成文件号之后，文件系统用一个持久存储的**索引结构**来定位该文件的各个块。索引结构可以是任何能把文件号和偏移量映射到存储块的持久数据结构。为了高效支持各种大小的文件和访问模式，索引结构往往取某种树的形式。

**空闲空间映射表。** 文件系统实现**空闲空间映射表**，随着文件的增长和收缩，记录哪些存储块空闲、哪些正在使用。最低限度上，文件系统的空闲空间映射表必须让文件系统在文件需要增长时找到一个空闲块；但由于空间局部性很重要，大多数现代文件系统的空闲空间映射表还能让它们在期望位置附近找到空闲块。例如，许多文件系统把空闲空间映射表实现为持久存储上的位图。

**局部性启发式策略。** 目录和索引结构让文件系统无论文件数据与元数据存放在哪里都能找到它们，空闲空间映射表则让文件系统能在持久存储设备上任何位置附近找到空闲空间。这些**机制**使文件系统可以运用各种**策略**，决定某个文件的某个块应当存放在何处。

这些策略体现在把数据分组以优化性能的**局部性启发式策略**之中。例如，有些文件系统把每个目录下的文件集中存放，但把不同的目录分散到存储设备的不同区域。有些文件系统则定期**碎片整理**，重写已有文件，使每个文件都存放在连续的存储块中，同时让设备上出现大段连续的空闲空间，从而可以顺序写入新文件。还有些文件系统优先优化写而非读，把一切数据都顺序写入，不论这一批写入里包含的是对一个文件的更新还是对许多不同文件的更新。

**实现细节。** 本章先讨论目录是如何实现的。然后，我们考察具体文件系统如何通过实现不同的索引结构、空闲空间映射表和局部性启发式策略，来处理在持久存储中放置和查找数据的种种细节。

## 13.2　目录：为数据命名

如图 13.1 所示，要访问一个文件，文件系统首先要把它名字转换成文件号。例如，名为 `/home/tom/foo.txt` 的文件，在内部可能被称为文件 66212871。文件系统用目录来存放从人类可读名字到内部文件号的映射，并把这些目录按层次组织起来，使用户能够把相关的文件和目录归在一起。

<figure class="book-figure">
<img src="/figures/vol4/image00315.png" alt="图 13.2" loading="lazy">
<figcaption><span class="fig-label">图 13.2</span>目录是一个文件，其中存放着一组文件名 → 文件号映射。</figcaption>
</figure>

用文件来存放目录，是实现提供层次化“名字到编号”映射的目录的简单办法。于是，若系统需要确定某个文件的编号，它只需打开相应的目录文件，逐项扫描文件名/文件号对，直到找到正确的那一项。

例如，图 13.2 展示了单个目录文件的内容。要打开文件 foo.txt，文件系统会扫描这个目录文件，找到 foo.txt 这一项，从而看到文件 foo.txt 的文件号是 66212871。

<figure class="book-figure">
<img src="/figures/vol4/image00316.png" alt="图 13.3" loading="lazy">
<figcaption><span class="fig-label">图 13.3</span>让一个目录包含另一个目录的文件名 → 文件号映射，就可以把目录按层次组织起来。</figcaption>
</figure>

当然，如果我们用文件来存放 `/home/tom` 这类目录的内容，就仍然存在如何找到这些目录文件本身的问题。如图 13.3 所示，目录 `/home/tom` 的文件号可以通过在目录 `/home` 中查找名字 tom 得到，而目录 `/home` 的文件号可以通过在根目录 `/` 中查找名字 home 得到。

递归算法需要有一个基准情形——我们无法通过查看别的目录来得到根目录的文件号。解决办法是事先约定根目录的文件号。例如，Unix 快速文件系统（FFS）以及许多其他 Unix 和 Linux 文件系统，都用 2 作为文件系统根目录的预定义文件号。

于是，要读取图 13.3 中的文件 `/home/tom/foo.txt`，我们首先读取那个众所周知的根编号 2 所对应的文件，从而读出根目录。在这个文件中查找名字 home，发现目录 `/home` 存放在文件 88026158 中。读取文件 88026158 并查找名字 tom，得知目录 `/home/tom` 存放在文件 5268830 中。最后，读取文件 5268830 并查找名字 foo.txt，得知 `/home/tom/foo.txt` 的文件号是 66212871。

尽管查找一个文件的编号可能需要好几步，但我们预期其中存在局部性（例如，访问一个目录中的某个文件时，该目录中的其他文件往往很快也会被访问），因此可以指望高速缓存减少大多数查找所需的磁盘访问次数。

**目录的 API。** 既然文件系统用文件来存放目录信息，那我们能不能直接用标准的 open/close/read/write API 来访问它们呢？

不能。目录使用一套专门的 API，因为它们必须控制这些文件的内容。例如，文件系统必须防止应用程序破坏**名字** →**文件号**映射表，否则可能导致操作系统无法执行查找或更新。再比如，文件系统应当维护这样一条不变式：合法目录项中的每个文件号都指向一个确实存在的文件。

因此，文件系统为修改目录文件提供专门的系统调用。例如，应用程序不用标准的 write 系统调用把新文件的目录项加入目录，而是使用 create 调用。通过限制更新方式，这些调用保证目录文件始终能被操作系统解析。这些调用还把文件的创建或删除与它的目录项绑定在一起，使目录项始终指向真实存在的文件，并且每个文件至少有一个目录项。

在第 11 章描述的 API 中，其他会修改目录文件的调用是 mkdir、link、unlink 和 rmdir。

举例来说，对于图 13.3 所示的文件系统，Tom 可以在自己的主目录中把 foo.txt 改名为 hw1.txt，办法是运行一个执行下面两个系统调用的进程：

```c
link("foo.txt", "hw1.txt");
unlink("foo.txt");
```

进程可以直接用标准的 read 调用读取目录文件。

::: info 例
**读取目录。** 对程序来说，能够取得一个目录中所有文件名的列表是很有用的，例如从某一点开始递归遍历整个层次结构。然而，第 11 章描述的文件系统 API 并没有专门用于读取目录的调用。

仅凭那张图中的系统调用 API，进程怎样才能知道它当前工作目录中有哪些文件名？
:::

::: warning 答
**进程可以使用读取“普通”文件内容的标准文件 read 系统调用，读取目录文件的内容。**

尽管操作系统必须限制对目录文件的写入以保证目录结构的不变式，但不必限制应用程序读取（它有权读取的）目录文件的内容。为简便起见，应用程序可以通过一个标准库来使用这一功能，该库同时提供解析目录文件的例程。□
:::

尽管为读取目录设置专门的系统调用并非根本必要，但这样做很方便。例如，Linux 提供了 `getdents`（“get directory entries”）系统调用，可以从一个已打开的文件中读取指定数量的目录项。

**目录的内部结构。** 许多早期实现只是在目录文件中线性存放**文件名**、**文件号**对的列表。例如，在 Linux ext2 文件系统最初的版本中，每个目录文件都存放一个目录项的链表，如图 13.4 所示。

<figure class="book-figure">
<img src="/figures/vol4/image00317.png" alt="图 13.4" loading="lazy">
<figcaption><span class="fig-label">图 13.4</span>目录的链表实现。这个例子展示了一个包含五个目录项的目录文件：Music、Work、foo.txt，以及 .（当前目录）和 ..（父目录）。</figcaption>
</figure>

当目录项数量较少时，简单的链表工作得很好，而这正是许多早期文件系统所预期的情况；但系统偶尔会遇到在单个目录中生成数千个文件的负载。一旦目录里有几千个目录项，基于简单列表的目录就会变得迟钝。

为了高效支持含有大量目录项的目录，许多较新的文件系统——包括 Linux XFS、微软 NTFS 和 Oracle ZFS——都把目录的内容组织成一棵树。同样，较新版本的 ext2 在底层链表之外又增加了一个基于哈希的结构，以加快查找。

<figure class="book-figure">
<img src="/figures/vol4/fig13_5.png" alt="图 13.5" loading="lazy">
<figcaption><span class="fig-label">图 13.5</span>与 Linux XFS 文件系统所用结构类似的基于树的目录结构。</figcaption>
</figure>

例如，图 13.5（a）展示了一个与 Linux XFS 所用结构类似的基于树的目录结构，图 13.5（b）展示了这些记录在目录文件中的物理排布方式。

在这个例子中，把文件名映射到文件号的目录记录存放在一棵 B+ 树中，该树以每个文件名的哈希值为索引。要找出某个文件名（例如 out2）对应的文件号，文件系统先计算该名字的哈希值（例如 0x0000c194），然后以该哈希值作为键在树中查找目录项：从文件某个已知偏移处的 B+ 树根节点（`BTREE_ROOT_PTR`）开始，经由 B+ 树的内部节点一路走到叶节点。在每一层，树节点都包含一个**（哈希键，文件偏移量）**对的数组，每个对表示一个指向子节点的指针，该子节点中包含键值小于**哈希键**、但大于前一项**哈希键**的那些项。文件系统在节点中查找第一个**哈希键**值超过目标键的项，然后顺着相应的**文件偏移量**指针走到正确的子节点。叶节点记录中的**文件偏移量**指针则指向目标目录项。

在 XFS 的实现中，目录项存放在目录文件的前部。B+ 树的根位于文件中某个已知偏移处（例如 `BTREE_ROOT_PTR`）。大小固定的内部节点和叶节点存放在根节点之后，而大小可变的目录项存放在文件开头。从根开始，每个树节点都包含指向其子节点在文件中存放位置的指针。

**硬链接与软链接。** 许多文件系统允许一个文件拥有多个名字。例如，`/home/tom/Work/Classes/OS/hw1.txt` 和 `/home/tom/todo/hw1.txt` 可能指向同一个文件，如图 13.6 所示。

<figure class="book-figure">
<img src="/figures/vol4/image00320.png" alt="图 13.6" loading="lazy">
<figcaption><span class="fig-label">图 13.6</span>带有多个指向同一文件的硬链接的有向无环图目录组织示例（此图重印自第 11 章）。</figcaption>
</figure>

**硬链接**是多个把不同路径名映射到同一文件号的目录项。由于一个文件号可以出现在多个目录中，文件系统必须保证：只有当指向某个文件的最后一个硬链接被删除之后，该文件才会被删除。

为了正确实现垃圾回收，文件系统在每个文件上记录指向它的硬链接数量，即引用计数。文件刚创建时引用计数为 1，此后每增加一个指向该文件的硬链接（例如 `link(existingName, newName)`），引用计数就加 1。反过来，每次调用 `unlink(name)` 都会把文件的引用计数减 1，当引用计数降为零时，底层文件被删除，它占用的资源被标记为空闲。

**软链接**（或称**符号链接**）并非把文件名映射到文件号，而是把某个名字映射到另一个名字的目录项。

<figure class="book-figure">
<img src="/figures/vol4/image00321.png" alt="图 13.7" loading="lazy">
<figcaption><span class="fig-label">图 13.7</span>在这个目录中，硬链接 foo.txt 和 bar.txt 以及软链接 baz.txt 都指向同一个文件。</figcaption>
</figure>

例如，图 13.7 展示了一个目录，其中三个名字都指向同一个文件。foo.txt 和 bar.txt 两项是指向同一文件——文件号 66212871——的硬链接，baz.txt 则是指向 foo.txt 的软链接。

请注意，如果我们用 unlink 系统调用从这个目录中删除 foo.txt 这一项，该文件仍然可以用名字 bar.txt 打开，但如果试图用名字 baz.txt 打开它，就会失败。

::: info 例
**文件的元数据。** 大多数文件系统把文件的元数据（例如文件的访问时间、所有者标识、权限和大小）存放在一个文件头中，而这个文件头可以用文件号找到。可以设想改把这些元数据存放在文件的目录项里。为什么很少有人这样做？
:::

::: warning 答
**在支持硬链接的文件系统中，把文件元数据存放在目录项里会带来问题。** 例如，每当文件的大小之类的属性发生变化，都必须找出并更新该文件的所有目录项。再比如，如果元数据存放在目录项中，就难以维护文件的引用计数，从而难以做到当且仅当指向该文件的最后一个硬链接被删除时才释放该文件的资源。

历史悠久的微软 FAT 文件系统把文件元数据存放在目录项中，但它不支持硬链接。□
:::

## 13.3　文件：查找数据

文件系统用目录把文件名翻译成文件号之后，还必须能够找到属于该文件的那些块。除这一功能上的要求之外，文件的实现通常还追求另外五个目标：

- 支持数据按顺序放置，以最大化顺序文件访问的性能

- 提供对任意文件块的高效随机访问

- 把开销限制在较低水平，使实现对小文件也高效

- 具备可扩展性，以支持大文件

- 提供一个位置来存放每文件的元数据，例如文件的引用计数、所有者、访问控制表、大小和访问时间

文件系统设计者在达成这些目标时拥有很大的自由度。回顾 13.1 节：

- 文件的**索引结构**提供了定位文件每个块的办法。为了可扩展性并支持局部性，索引结构通常是某种树。

- 文件系统的**空闲空间映射表**提供了把空闲块分配给文件、使文件得以增长的办法。文件增长时，选用哪些空闲块对获得良好的局部性至关重要。因此，文件系统的空闲空间映射表常常实现为位图，以便容易地在期望位置附近找到所需数量的连续空闲块。

- 文件系统的**局部性启发式策略**规定文件系统如何在存储中把数据分组，以最大化访问性能。

在这一框架之内，文件系统的设计空间非常大。为了理解其中的权衡、也理解常见文件系统的工作方式，我们将考察四个案例研究设计，它们展示了重要的实现技术，也代表了当今广泛使用的几种方案。

- **FAT。** 微软的文件分配表文件系统可追溯到 20 世纪 70 年代末。*技术：* FAT 文件系统使用一种极其简单的索引结构——**链表**，因此很适合作为我们讨论实现技术的起点。*今天：* 在闪存盘和数码相机这类把简单性与互操作性放在首位的设备中，FAT 文件系统仍被广泛使用。

- **FFS。** Unix 快速文件系统（FFS）于 20 世纪 80 年代中期发布，它保留了 Ritchie 和 Thompson 在 70 年代初的原始 Unix 文件系统中的许多数据结构。*技术：* FFS 的索引结构采用**基于树的多级索引**以提高随机访问的效率，并用一组**局部性启发式策略**为各种负载取得良好的空间局部性。*今天：* 在 Linux 中，流行的 ext2 和 ext3 文件系统都基于 FFS 的设计。

- **NTFS。** 微软新技术文件系统（NTFS）于 20 世纪 90 年代初推出，用以取代 FAT 文件系统。*技术：* 与 FFS 一样，NTFS 使用基于树的索引结构，但这棵树**比 FFS 的固定树更灵活**。此外，NTFS 通过索引变长的**区段**而不是单个块，使索引结构针对顺序文件布局做了优化。*今天：* NTFS 仍是 Windows 7 等微软操作系统的主要文件系统。此外，灵活的树和区段技术也代表了若干广泛使用的文件系统，例如 Linux 的 ext4、XFS 和 Reiser4，AIX/Linux 日志文件系统（JFS），以及苹果的分层文件系统（HFS 和 HFS+）。

- **COW/ZFS。** 写时复制（COW）文件系统通过把新版本写到空闲磁盘块来更新已有的数据和元数据块。这种方案优化了写性能：由于任何数据或元数据都可以写到磁盘上任何空闲空间，文件系统能够把原本随机的写入归并成大规模的、顺序的成组写入。为了看清这些思想如何实现，我们将考察开源的 ZFS——一个著名的写时复制文件系统，由 Sun Microsystems 于 2000 年代初推出。ZFS 的设计目标是扩展到跨越大量磁盘的文件系统、提供强大的数据完整性保证，并优化写性能。

图 13.8 汇总了这些系统中的关键思想，我们将在后续各节中详述。

::: tip 扇区与页；块与簇；区段与运行
尽管存储硬件以*扇区*（对磁盘）或*页*（对闪存）为单位组织数据，文件系统却常常把固定数目的磁盘扇区或闪存页合在一起，构成一个更大的分配单位，称为*块*。例如，我们可能把一个运行在 512 字节扇区磁盘上的文件系统格式化为使用 4 KB 的块。把多个扇区聚合为一个块可以减少分配、跟踪和回收块的开销，但可能略微增加空间开销。

FAT 和 NTFS 把块称为*簇*，但为统一起见，我们在讨论中使用“块”这一术语。

最后，NTFS、ext4 和 btrfs 等一些文件系统把数据存放在变长的连续磁道数组中，这种数组在多数文件系统中称为*区段*，在 NTFS 中称为*运行*。为统一起见，我们在讨论中使用“区段”这一术语。
:::

### 13.3.1　FAT：链表

微软的文件分配表文件系统最早于 20 世纪 70 年代末实现，是 MS-DOS 和早期微软 Windows 的主要文件系统。多年来，FAT 文件系统在许多方面得到了增强。我们的讨论将聚焦于最新的版本 FAT-32，它支持最多 $2^(28)$ 个块的卷，以及最大 $2^(32) - 1$ 字节的文件。

**索引结构。** FAT 文件系统因其**文件分配表**而得名，它是位于卷中保留区域的一个 32 位表项数组。系统中的每个文件对应 FAT 表项的一条链表，每个 FAT 表项包含一个指向该文件下一个 FAT 表项的指针（或者一个特殊的“文件结束”值）。FAT 为卷中的每个块设一个表项，文件的块就是与该文件的 FAT 表项相对应的那些块：若 FAT 表项 $i$ 是某文件的第 $j$ 个 FAT 表项，则存储块 $i$ 就是该文件的第 $j$ 个数据块。

<figcaption><span class="fig-label">图 13.9</span>一个 FAT 文件系统，其中有一个 5 块的文件和一个 2 块的文件。</figcaption>
</figure>

图 13.9 展示了一个含有两个文件的 FAT 文件系统。第一个文件从块 9 开始，包含 5 个块。第二个文件从块 12 开始，包含 2 个块。

目录把文件名映射到文件号，而在 FAT 文件系统中，文件的编号就是该文件在 FAT 中第一个表项的下标。于是，已知文件的编号，我们就能找到该文件的第一个 FAT 表项和第一个块；而已知第一个 FAT 表项，我们就能找到该文件其余的 FAT 表项和块。

**空闲空间跟踪。** FAT 也用于跟踪空闲空间。如果数据块 $i$ 空闲，则 `FAT[i]` 为 0。因此，文件系统只要扫描 FAT、找到一个值为零的表项，就能找到一个空闲块。

**局部性启发式策略。** FAT 的不同实现可能采用不同的分配策略，但这些策略通常都很简单。例如，有些实现使用*下次适配*（next fit）算法：它从上次分配的表项开始顺序扫描 FAT，返回找到的下一个空闲表项。

像这样简单的分配策略可能使文件碎片化，把文件的块散布到整个卷上，而不是得到所期望的顺序布局。为提高性能，用户可以运行*碎片整理*（defragmentation）工具，它把文件从现有位置读出，再写到空间局部性更好的新位置。例如，Windows XP 中的 FAT 碎片整理程序会试图把散布在多个区段上的每个文件的块，复制到一段容纳该文件全部块的、连续的区段中。

**讨论。** FAT 文件系统之所以被广泛使用，是因为它简单，并得到许多操作系统的支持。例如，许多闪存 U 盘和相机存储卡都使用 FAT 文件系统，从而使几乎任何一台运行现代操作系统的计算机都能读写它们。

FAT 文件系统的变体甚至被应用程序用来组织单个文件内部的数据。例如，1997 年到 2007 年间各版本 Microsoft Word 生成的 Microsoft `.doc` 文件，实际上是包含许多内部片段的复合文档。`.doc` 格式在 `.doc` 文件内部建立了一个类 FAT 的文件系统，用来管理该文件中的各个对象。

然而，FAT 文件系统在许多方面存在局限。例如，

- **局部性差。** FAT 实现通常使用下次适配之类的简单分配策略。这可能造成文件严重碎片化。

- **随机访问差。** 要在文件内随机访问，必须顺序遍历该文件的 FAT 表项，直到抵达所需的块。

- **文件元数据和访问控制有限。** 每个文件的元数据包含文件名、大小和创建时间等信息，但不包含文件所有者或组标识这类访问控制信息，因此任何用户都能读写 FAT 文件系统中的任何文件。

- **不支持硬链接。** FAT 把每个文件表示为文件分配表中一串 32 位表项构成的链表。这种表示没有为其他文件元数据留出空间，于是文件元数据改为与文件名一起存放在目录项中。这种做法要求每个文件只能通过恰好一个目录项访问，从而排除了指向同一文件的多个硬链接。

- **卷和文件大小受限。** FAT 表项是 32 位的，但最高的 4 位被保留。因此一个 FAT 卷最多只能有 $2^(28)$ 个块。以 4 KB 的块计算，最大卷容量十分有限（例如 $2^(28)$ 块/卷 × $2^(12)$ 字节/块 = $2^(40)$ 字节/卷 = 1 TB）。系统虽支持最大 256 KB 的块，但由于内部碎片，这样做可能浪费大量磁盘空间。同样，文件大小用 32 位编码，所以任何文件都不能大于 $2^(32) - 1$ 字节（略小于 4 GB）。

- **不支持现代可靠性技术。** 虽然我们要到第 14 章才讨论可靠性，但这里先指出：FAT 不支持现代文件系统用来避免数据损坏的那些事务式更新技术——当计算机在写存储的过程中崩溃时，这些技术可保护关键数据结构。

### 13.3.2　FFS：固定树

Unix 快速文件系统（FFS）展示了两个方面的关键思想：如何为文件的块建立索引以便快速定位，以及如何在磁盘上放置数据以获得良好的局部性。

具体而言，FFS 的索引结构称为**多级索引**（multi-level index），它是一棵精心构造的树，使 FFS 能定位文件的任意一个块，并且对大文件和小文件都高效。

得益于多级索引带来的灵活性，FFS 采用两种局部性启发式策略——**块组放置**与**预留空间**——二者结合通常能给出良好的磁盘布局。

**索引结构。** 为了跟踪属于每个文件的数据块，FFS 使用一棵固定、非对称的树，称为**多级索引**，如图 13.10 所示。

<figure class="book-figure">
<img src="/figures/vol4/image00323.png" alt="图 13.10" loading="lazy">
<figcaption><span class="fig-label">图 13.10</span>FFS 的索引节点是一棵非对称树的根，树的叶子是文件的数据块。</figcaption>
</figure>

每个文件都是一棵树，叶子是大小固定的数据块（例如 4 KB）。每个文件的树以**索引节点（inode）**为根，索引节点中存放该文件的元数据（例如文件的所有者、访问控制权限、创建时间、最后修改时间，以及该文件是否为目录）。

::: tip FFS 的访问控制
FFS 的索引节点中包含用于控制文件访问的信息。访问控制可以针对三类人分别指定：

- **用户（所有者）。** 拥有该文件的用户。

- **组。** 属于某个指定 Unix 组的那些人。每个 Unix 组在别处用一个组名和该组用户的列表来定义。

- **其他人。** 所有其他用户。

访问控制按三类活动来指定：

- **读。** 读取该普通文件或目录。

- **写。** 修改该普通文件或目录。

- **执行。** 执行该普通文件，或穿过该目录去访问其中的文件或子目录。

每个文件的索引节点既存放该文件的用户（所有者）和组的标识，也存放 9 个基本访问控制位，用来指定文件用户（所有者）、组和其他人各自的读/写/执行权限。例如，命令 `ls -ld /` 显示根目录的访问控制信息：

```text
ls -ld /
drwxr-xr-x 40 root wheel 1428 Feb 2 13:39 /
```

这表示该文件是一个目录（d），它的所有者是用户 root，所属组是 wheel。根目录可以被所有者读写和执行（穿越）（rwx），可以被 wheel 组的成员以及其他所有用户读取和执行（穿越），但不能被他们写入（r-x）。
:::

::: tip setuid 与 setgid 程序
除 9 个基本访问控制位之外，FFS 的索引节点还存放两个重要的附加位：

- **Setuid。** 当任何用户（具有执行权限）执行该文件时，它将以文件所有者（而不是该用户）的权限运行。例如，`lprm` 程序允许用户从打印队列中删除一个作业。打印队列实现为一个包含待打印文件的目录；由于我们不希望用户能够删除其他用户的作业，这个目录归 root 用户所有，并且只能由 root 修改。于是，`lprm` 程序归 root 用户所有并设置了 setuid 位。任何用户都可以执行它，但它运行时具有 root 权限，因此能够修改打印队列目录。例如：`-rwsr-xr-x 1 root root 507674 2010-07-05 12:39 /usr/bin/lprm`。

  当然，把一个程序设为 setuid 是有潜在危险的。例如在这里，我们依赖 `lprm` 程序去核实真正的用户删除的是自己的打印作业，而不是别人的。`lprm` 中的一个缺陷可能让一个用户删掉另一个用户的打印作业。更糟的是，如果这个缺陷让攻击者得以执行恶意代码（例如通过缓冲区溢出攻击），那么 `lprm` 中的缺陷就可能让攻击者完全控制这台机器。http://www.linuxjournal.com/article/6701

- **Setgid。** setgid 位与 setuid 位相似，区别在于文件以文件所属组的权限运行。例如在某些机器上，`sendmail` 以组 smmsp 成员的身份运行，以便访问对 smmsp 组可访问的邮件队列文件。例如：`-r-xr-sr-x 1 root smmsp 2264923 2011-06-23 14:51 /usr/opt/sendmail-8.14.4/lib/mail/sendmail`。
:::

文件的索引节点（根）中还包含一个指针数组，用来定位文件的数据块（叶子）。其中一些指针直接指向树的数据叶子，另一些则指向树中的内部节点。典型情况下，一个索引节点包含 15 个指针。前 12 个指针是**直接指针**，直接指向文件的前 12 个数据块。

第 13 个指针是一个**间接指针**，它指向树中一个称为**间接块**的内部节点；间接块是一个普通的存储块，其中存放一个直接指针数组。要读取文件的第 13 个块，先读索引节点取得间接指针，再读间接块取得直接指针，然后读数据块。在块大小为 4 KB、块指针为 4 字节的情况下，一个间接块最多可容纳 1024 个直接指针，因此可以支持略大于 4 MB 的文件。

第 14 个指针是一个**双重间接指针**，它指向树中一个称为**双重间接块**的内部节点；双重间接块是一个间接指针数组，其中每个指针都指向一个间接块。在块大小为 4 KB、块指针为 4 字节的情况下，一个双重间接块最多可容纳 1024 个间接指针。于是，一个双重间接指针最多可以索引 $1024^{2}$ 个数据块。

最后，第 15 个指针是一个**三重间接指针**，它指向一个**三重间接块**，其中存放一个双重间接指针数组。在块大小为 4 KB、块指针为 4 字节的情况下，一个三重间接指针最多可以索引 $1024^{3}$ 个数据块，共包含 $4 space \text{KB} \times 1024^{3} = 2^{12} \times 2^{30} = 2^{42}$ 字节（4 TB）。

文件系统的所有索引节点都放在一个**索引节点数组**中，该数组存储在磁盘上的固定位置。文件的文件号在 FFS 中称为 `inumber`，它是索引节点数组的下标：要打开一个文件（例如 `foo.txt`），我们先在文件所属的目录中查找它的 `inumber`（例如 91854），再到索引节点数组的相应表项（例如第 91854 项）中查找它的元数据。

FFS 的多级索引有四个重要特征：

+ **树结构。** 每个文件都表示为一棵树，这使文件系统能够高效地找到文件的任意一个块。

+ **高度数。** 与内存数据结构中常用的二叉树相比，FFS 的树使用有很多孩子的内部节点（即内部节点的**度**（degree）或**扇出**（fan out）很高）。例如，若文件块为 4 KB、块号为 4 字节，则每个间接块可以容纳指向 1024 个块的指针。高度数节点对磁盘上的数据结构是合理的，因为（1）我们希望尽量减少寻道次数，（2）读取几千字节顺序数据的代价并不比读取第一个字节高多少，（3）数据至少要以扇区为单位读写。高度数节点还提高了顺序读写效率——一旦读入一个间接块，就可以在需要下一个间接块之前读入数百个数据块。两次读取双重间接块之间的连续数据长度还要更长。

+ **固定结构。** FFS 的树具有固定结构。对于 FFS 的给定配置，最前面的 $d$ 个指针始终指向文件的前 $d$ 个块；接下来的指针是间接指针，指向一个间接块；依此类推。与那种随文件增长而在某个块之上增加间接层级的动态树相比，固定结构的主要优点是实现简单。

+ **非对称。** 为了用固定的树结构同时高效支持大文件和小文件，FFS 的树结构是非对称的。FFS 并不把每个数据块都放在同一深度，而是把相继的若干组块放在逐渐增加的深度上，使小文件存放在浅树中、中等文件的大部分存放在中等深度的树中、大文件的大部分存放在更深的树中。例如，图 13.11 展示了一个只有 4 个块的小文件，其索引节点中包含指向它全部块的直接指针。反过来，对于图 13.10 所示的大文件，大部分块必须通过三重间接指针访问。

<figure class="book-figure">
<img src="/figures/vol4/image00324.png" alt="图 13.11" loading="lazy">
<figcaption><span class="fig-label">图 13.11</span>一个小的 FFS 文件，其所有块都可通过索引节点中的直接指针到达。</figcaption>
</figure>

  相比之下，如果采用固定深度的树，又希望支持相当大的文件，小文件就要承担很高的开销。采用三重间接指针和 4 KB 块时，存储一个 4 KB 的文件会消耗 16 KB 以上（4 KB 数据、小小的索引节点，以及 3 层各 4 KB 的间接块），而读取该文件需要读取五个块来遍历这棵树。

FFS 的这些原则是通用的；许多文件系统都在其基本方法之上做了各种变体。

::: info 例
**FFS 的变体。** 假设 BigFS 是 FFS 的一个变体，其每个索引节点包含 12 个直接指针、1 个间接指针、1 个双重间接指针、1 个三重间接指针和 1 个**四重间接指针**。假定块大小为 4 KB、指针为 8 字节，这种索引结构最多能支持多大的文件？
:::

::: warning 答
12 个直接指针可以索引 $12 \times 4 space \text{KB} = 48 space \text{KB}$。

作为内部节点使用时，每个存储块最多可以容纳 $4 space \text{KB} div 8 space \text{bytes} = 512$ 个指针，即每块 $2^{9}$ 个指针。

因此，间接指针指向一个含 $2^{9}$ 个指针的间接块，最多引用 $2^{9} \times 2^{12} = 2^{21}$ 字节，即 2 MB。

类似地，双重间接指针最多引用 $2^{9} \times 2^{9} \times 2^{12} = 2^{30}$ 字节（1 GB），三重间接指针最多引用 $2^{9} \times 2^{9} \times 2^{9} \times 2^{12} = 2^{39}$ 字节（512 GB），四重间接指针最多引用 $2^{9} \times 2^{9} \times 2^{9} \times 2^{9} \times 2^{12} = 2^{48}$ 字节（256 TB）。

于是，**BigFS 可以支持略大于 256.5 TB 的文件。** □
:::

**稀疏文件。** 诸如 FFS 所用的这种基于树的索引结构可以支持**稀疏文件**（sparse file），即一段或多段由文件数据包围起来的空白区域；这些空白区域不占用任何磁盘空间。

例如，若我们创建一个新文件，在偏移量 0 处写入 4 KB，定位到偏移量 $2^{30}$ 处，再写入 4 KB，如图 13.12 所示，则一个块大小为 4 KB 的 FFS 系统只会占用 16 KB——两个数据块、一个双重间接块和一个单重间接块。

<figure class="book-figure">
<img src="/figures/vol4/image00325.png" alt="图 13.12" loading="lazy">
<figcaption><span class="fig-label">图 13.12</span>一个稀疏的 FFS 文件，其中有两个 4 KB 的块，一个位于偏移量 0，一个位于偏移量 \(2^{30}\)。</figcaption>
</figure>

在这种情况下，如果我们用 `ls` 命令列出**文件的大小**，会看到文件大小为 1.1 GB。但是，如果我们用 `du` 命令检查**文件占用的空间**，会看到它只占用 16 KB 的存储空间。

```text
ls -lgGh sparse.dat
-rwx------ 1 1.1G 2012-01-31 08:45 sparse.dat
du -hs sparse.dat
16K  sparse.dat
```

如果从空洞中读取，文件系统会产生一个填满零的缓冲区。如果向空洞中写入，文件系统会为数据以及所需的各层间接块分配存储块。

与高效支持稀疏的虚拟内存地址空间类似，高效支持稀疏文件有利于给应用程序在文件中放置数据时提供最大的灵活性。例如，数据库可以把它的表存放在文件开头，把索引存放在文件的 1 GB 处，把日志存放在 2 GB 处，把额外的元数据存放在 4 GB 处。

稀疏文件有两个重要局限。第一，并非所有文件系统都支持稀疏文件，因此依赖稀疏文件支持的应用程序可能无法移植。第二，并非所有工具程序都能正确处理稀疏文件，这可能带来意想不到的后果。例如，如果我从头到尾读一个稀疏文件，并把每个字节写到另一个文件中，就会观察到对应于空洞的、填满零的缓冲区，并把那些填零的区域写入新文件。结果得到一个新的非稀疏文件，它占用的空间与其大小相当。

```text
cat sparse.dat > /tmp/notSparse.dat
ls -lgGh /tmp/notSparse.dat
-rw-r--r-- 1 1.1G 2012-01-31 08:54 /tmp/notSparse.dat
du -hs /tmp/notSparse.dat
1.1G  /tmp/notSparse.dat
```

**空闲空间管理。** FFS 的空闲空间管理很简单。FFS 分配一个**位图**（bitmap），每个存储块对应一位。位图中的第 $i$ 位表示第 $i$ 个块是空闲还是已使用。FFS 位图的位置在文件系统格式化时就已固定，因此很容易找到位图中标识任意位置附近空闲块的那一部分。

**局部性启发式策略。** FFS 使用两种重要的局部性启发式策略，以便在许多负载下取得良好性能：**块组放置**与**预留空间**。

**块组放置。** FFS 的数据放置针对常见情形做了优化：同一文件的数据块、同一文件的数据与元数据，以及同一目录下的不同文件，往往会被一起访问。

反过来说，由于不可能让所有东西都彼此靠近，FFS 允许不同目录的文件相距较远。

<img src="/figures/vol4/image00326.png" alt="图 13.13" loading="lazy">
<figcaption><span class="fig-label">图 13.13</span>FFS 把磁盘划分为块组，把空闲空间与索引节点元数据分散到各块组，并把同一目录下文件的数据块放在同一个块组中。</figcaption>

这种放置启发式策略包含四个部分：

- **把磁盘划分为块组。** 如图 13.13 所示，FFS 把磁盘划分为一组组相邻磁道，称为**块组**（block group）。同一块组内任意两块之间的寻道时间都很短。

- **分散元数据。** 早期的多级索引文件系统把索引节点数组和空闲空间位图放在磁盘上一段连续的区域里。在这种集中的元数据布局中，磁头常常必须在文件的数据与其元数据之间来回寻道。在 FFS 中，索引节点数组和空闲空间位图在概念上仍然是记录数组，每个数组表项仍存放在一个位置已知、易于计算的地方，但这个数组现在被切成若干片，分散到整个磁盘上。具体来说，每个块组各存放这些元数据结构的一部分，如图 13.13 所示。例如，若磁盘有 100 个块组，则每个块组存放文件系统 1% 的索引节点，以及位图中跟踪该块组内数据块状态的那 1% 部分。

- **把文件放进块组。** FFS 把一个目录和它的文件放在同一个块组中：创建新文件时，FFS 知道新文件所属目录的 `inumber`，由此可以确定同一块组内 `inumber` 的范围。若该组中有空闲的索引节点，FFS 就从该组中选一个；否则，FFS 放弃局部性，从另一个块组中选择一个 `inumber`。与普通文件不同，FFS 创建新目录时会从另一个块组中选择 `inumber`。尽管我们可能期望子目录与它的父目录有一定局部性，但把所有子目录都放进同一个块组会很快把它填满，从而使我们想在目录内部获得局部性的努力落空。图 13.13 展示了 FFS 可能如何把不同目录的文件归入不同的块组。

- **放置数据块。** 在块组内部，FFS 使用首次适配式的启发式策略。写入文件的一个新块时，FFS 把该块写到该文件所属块组中的第一个空闲块。这种策略在短期可能牺牲局部性，但这样做是为了在长期改善局部性。在短期内，它可能把一连串写入分散到块组开头附近的若干小空洞中，而不是把它们聚集到别处的某段连续空闲块上。然而这种短期牺牲带来长期收益：碎片减少了，该块末尾往往还会跟着一段较长的空闲空间，后续写入更可能是顺序的。直观地看，一个给定的块组通常会在开头附近的若干块中散落着几个空洞，而在块组末尾保留一段较长的空闲空间。于是，若创建一个小文件，它的块很可能落进那几个小空洞，这虽不理想，但对小文件来说可以接受。反过来说，若创建一个大文件并从开头写到结尾，它的前几个块往往会散落在块组前段的那些空洞中，而它的大部分数据会顺序地写在块组末尾。如果一个块组用尽了空闲块，FFS 就另选一个块组，并用同样的策略在那里分配块。

<figcaption><span class="fig-label">图 13.14</span>FFS 的块放置启发式策略是：把每个新文件块放入该文件所属块组中的第一个空闲块。</figcaption>

**预留空间。** 块组启发式策略虽然可能有效，但它依赖于磁盘上存在相当多的空闲空间。特别是当磁盘几乎写满时，文件系统就几乎没有优化局部性的余地。例如，若磁盘上只剩几千字节的空闲扇区，大多数块组都会是满的，其余的也只剩下几个空闲块；新的写入只能或多或少随机地散布到磁盘各处。

因此，FFS 预留磁盘空间的一部分（例如 10%），并向应用程序呈现略小一些的磁盘容量。如果磁盘上的实际空闲空间降到预留比例以下，FFS 就把磁盘视为已满。例如，当除预留空间之外的空间都已消耗完时，若用户的应用程序试图在文件中写入一个新块，这次写入就会失败。当除预留空间之外的空间都已满时，超级用户的进程仍然可以分配新块，这便于管理员登录进来做些清理工作。

考虑到磁盘技术的趋势，预留空间的做法是有效的。它牺牲少量磁盘容量——这是一种近几十年来进步迅速的硬件资源——来缩短寻道时间，而这是一项进步缓慢的硬件特性。

### 13.3.3　NTFS：带区段的灵活树

微软的新技术文件系统（NTFS）于 1993 年发布，它在微软 FAT 文件系统的基础上增加了许多新特性，包括用于提升性能的新索引结构、更灵活的文件元数据、更强的安全性和更高的可靠性。

我们将在第 14 章讨论 NTFS 的一部分可靠性特性。这里只关注 NTFS 如何存储数据和元数据。

**索引结构。** FFS 用固定的树跟踪文件块，而 NTFS 以及 Linux ext4、btrfs 等许多较新的文件系统则用**灵活的树**（flexible tree）跟踪**区段**。

- **区段。** NTFS 并不跟踪单个文件块，而是跟踪**区段**，即文件中大小可变、各自存放在存储设备上一段连续区域的片段。

- **灵活的树与主文件表。** NTFS 中的每个文件都用一棵深度可变的树表示。即使文件本身很大，只要它的区段数目不多，其区段指针就可以存放在一棵很浅的树中。只有当文件碎片化严重时，才需要更深的树。

这些树的根存放在一张主文件表中，它与 FFS 的索引节点数组类似。NTFS 的**主文件表（MFT）**存储一个由 1 KB 的 MFT 记录组成的数组，每条记录存放一串大小可变的**属性记录**（attribute record）。NTFS 用属性记录同时存储数据和元数据——二者都只被视为文件的属性。

有些属性可能大到装不进一条 MFT 记录（例如数据区段），有些则小到足以装下（例如文件的最后修改时间）。因此属性可以是**驻留的**（resident），也可以是**非驻留的**（non-resident）。**驻留属性**把内容直接存放在 MFT 记录中，**非驻留属性**则把区段指针存放在 MFT 记录中，并把内容存放在这些区段里。

MFT 记录采用灵活的格式，可以包含各种不同的属性。除数据属性之外，三种常见的元数据属性类型是：

- **标准信息。** 该属性存放所有文件都需要的标准信息。字段包括文件的创建时间、修改时间、访问时间、所有者标识和安全说明符。其中还包括一组标志位，用来表示一些基本信息，例如该文件是只读文件、隐藏文件还是系统文件。

- **文件名。** 该属性存放文件名及其父目录的文件号。由于一个文件可以有多个名字（例如该文件有多个硬链接），它的 MFT 记录中可能有多个文件名属性。

- **属性列表。** 由于文件的元数据可能包含数目不定的、大小可变的属性，文件的元数据可能超出单条 MFT 记录所能容纳的大小。出现这种情况时，NTFS 把属性存放在多条 MFT 记录中，并在第一条记录中放入一个属性列表。属性列表若存在，就指明哪些属性存放在哪些 MFT 记录中。例如，图 13.17 展示了两条文件的 MFT 记录：一个文件的属性都放在一条 MFT 记录中，另一个文件则有属性跨越两条 MFT 记录。

**元数据文件。** NTFS 并不为零星空间位图之类的文件系统元数据临时分配磁盘上的特殊区域，而是把几乎全部元数据存放在十几个文件号很低、且为众所知的普通文件中。例如，文件号 5 是根目录，文件号 6 是空闲空间位图，文件号 8 包含该卷的坏块列表。

文件号 9 名为 `$Secure`，存放安全与访问控制信息。NTFS 有一个灵活的安全模型，一个文件可以关联一组用户和组，并为列出的每个主体（principal）指定具体的访问控制设置。在早期版本的 NTFS 中，这样的访问控制列表随每个文件一起存放，但这些列表占用相当可观的空间，而且许多列表的内容完全相同。因此，当前的 NTFS 实现把每个唯一的访问控制列表只在特殊的 `$Secure` 文件中存放一次，并用一个定长的唯一键为其建立索引。每个文件只需在自己的 MFT 记录中存放相应的定长键，NTFS 便可用该文件的安全键在 `$Secure` 文件中找到对应的访问控制列表。

甚至主文件表本身也作为一个文件存放，其文件号为 0，名为 `$MFT`。于是，要读取 MFT，我们得先找到 MFT 的第一条表项！为了定位 MFT，NTFS 卷的第一个扇区中包含一个指向 MFT 第一条表项的指针。

把 MFT 存放在文件中，就不必在预定位置以固定数组的形式静态分配全部 MFT 表项。NTFS 从一个小的 MFT 开始，随着新文件的创建和新表项的需要而增长。

**局部性启发式策略。**

大多数 NTFS 实现采用**最佳适配**（best fit）的一种变体，即系统尽量把新分配的文件放进足以容纳它的最小空闲区域。在 NTFS 的变体中，系统并不把整个磁盘的分配位图都保存在内存中，而是缓存磁盘上一块较小区域的分配状态，并优先搜索该区域。如果位图缓存保存的是最近发生写入的区域的信息，那么时间上相伴发生的写入往往会聚集在一起。

NTFS 为优化其最佳适配放置而提供的一项重要特性是 `SetEndOfFile()` 接口，它允许应用程序在创建文件时指定文件的预期大小。相比之下，FFS 是在写入时才分配文件块，并不知道文件最终会长到多大。

为避免主文件表文件（`$MFT`）变得碎片化，NTFS 在卷的开头预留一部分空间（例如卷的前 12.5%）供 MFT 扩展使用。在非预留区域写满之前，NTFS 不会把文件块放进 MFT 预留区；写满之后，它把 MFT 预留区的大小减半，然后继续。随着卷不断被填满，NTFS 不断把预留区减半，直到剩余的预留区已超过半满为止。

最后，带 NTFS 的微软操作系统中包含一个碎片整理工具，它把碎片化的文件取出，重写到磁盘上的连续区域。

### 13.3.4　写时复制文件系统

在更新已有文件时，**写时复制（COW）文件系统**并不覆盖原有的数据或元数据，而是把新版本写到新的位置。

<figure class="book-figure">
<img src="/figures/vol4/image00332.png" alt="图 13.19" loading="lazy">
<figcaption><span class="fig-label">图 13.19</span>原地更新的文件系统（左）在原位置更新数据和元数据，而写时复制文件系统（右）在每次更新时都为数据和元数据制作新副本。</figcaption>
</figure>

COW 文件系统这样做是为了优化写入，把随机的 I/O 更新转化为顺序更新。例如，向文件追加一个块时，传统的原地更新文件系统可能要寻道去更新空闲空间位图、索引节点数组中该文件的索引节点、该文件的间接块以及该文件的数据块。相比之下，COW 文件系统可能只需找到一段连续的空闲空间，把新的位图、索引节点、间接块和数据块都写在那里，如图 13.19 所示。

若干技术趋势推动了 COW 文件系统的广泛采用：

- **小写入昂贵。** 大块顺序写入的磁盘性能远好于小的随机写入。这一差距很可能继续扩大，因为带宽通常比寻道时间或旋转延迟改善得更快：即使转速不提高，提高存储密度也能提升带宽。因此，把小随机写入转化为大顺序写入的收益很大，而且还在增大。

- **小写入在 RAID 上尤其昂贵。** 独立磁盘冗余阵列（RAID）常被用来提高存储可靠性。然而，正如我们将在下一章讨论的，在以奇偶校验方式存储的 RAID 上更新单个块需要四次磁盘 I/O：读旧数据、读旧奇偶校验、写新数据、写新奇偶校验。相比之下，当整个条带——所有共用同一个奇偶校验块的块——被一次更新时，RAID 是高效的。这时无需任何读操作，每个新数据块被写入，奇偶校验的更新分摊到条带中的各数据块上。RAID 的广泛使用放大了把随机写入转化为顺序写入的好处。

- **高速缓存过滤了读。** 对许多负载而言，大容量 DRAM 高速缓存几乎可以处理全部文件系统读。但我们用 DRAM 缓冲写的能力受限于数据写入后必须尽快持久保存这一要求。因此，写的开销常常主导性能，那些优化写性能的技术也就颇具吸引力。

- **闪存的广泛采用。** 闪存有两个特性使 COW 技术变得重要。第一，要写入一个小（例如 4 KB）的闪存页，必须先擦除它所在的大（例如 512 KB）擦除块。第二，每个闪存存储单元在磨损失效之前能承受有限次数的写-擦循环，因此**磨损均衡**——把写入均匀分散到所有单元——对于最大化闪存寿命很重要。闪存盘的闪存转换层使用 COW 技术来虚拟化块地址，使它能够对外提供按逻辑页读写的标准接口，同时在内部把写入重定向到已擦除擦除块上的页，并把现有数据搬到新的物理页，以便它们当前的擦除块可以被擦除、供将来写入使用。注意，闪存盘的闪存转换层工作在文件系统之下——在它之上仍然使用标准的原地更新或 COW 文件系统。但闪存转换层的构造原理与这里讨论的 COW 文件系统相同。

- **容量增长使版本化成为可能。** 大容量存储使得文件系统提供让用户访问文件旧版本的接口变得有吸引力。由于 COW 系统中的更新不会用新数据覆盖旧数据，支持版本化相对直接，我们将在下面讨论。

<figcaption><span class="fig-label">图 13.20</span>传统的原地更新文件系统，例如 FFS。</figcaption>

**实现原理。** 图 13.20 和图 13.21 通过把一个传统文件系统（这里是 FFS）与使用相同基本索引结构的 COW 实现作对比，说明了 COW 文件系统的核心思想。

在传统系统（图 13.20）中，文件的间接节点和数据块可以位于磁盘上的任何位置；给定文件的 `inumber`，我们就能在磁盘上的固定位置找到它的索引节点。

在 COW 版本（图 13.21）中，我们不希望原地覆盖索引节点，因此必须让它们可移动。一个简单的办法是把它们存放在一个文件中，而不是放在固定数组里。当然，事情还没有完——我们仍然需要能够找到索引节点文件的索引节点，它称为**根索引节点**（root inode）。

最简单的做法是把根索引节点存放在固定位置。这样一来，我们就可以用根索引节点从索引节点文件中计算出的偏移量处读取，从而找到任意文件的索引节点，再由该索引节点找到它的块。

然而，把根索引节点也做成写时复制是有好处的。例如，我们不希望在写入根索引节点的过程中发生崩溃，从而冒着丢失它的风险。一个解决办法是在根索引节点中放入单调递增的版本号和校验和，并维护一个保存当前及近期根索引节点的小槽位数组，每次写入时更新其中最旧的一个。崩溃之后，我们扫描所有槽位，找出校验和正确且最新的那个根索引节点。

**ZFS 的索引结构。** 为了更好地理解写时复制文件系统是如何实现的，我们来看开源的 ZFS 文件系统。

如图 13.23 所示，ZFS 存储系统的根称为**uberblock**。ZFS 在固定的存储位置保存一个含 256 个 uberblock 的数组，并把相继的版本轮换着写在其中。重启时，ZFS 扫描这个 uberblock 数组，选用校验和有效且序列号最大的那一个。

当前的 uberblock 在概念上包含一个指向当前根 dnode 的指针，根 dnode 保存 ZFS 文件系统的 dnode 数组。（我们说“在概念上”，是因为这里做了些简化。读完这段描述之后，若想了解其中繁复的细节，请看边栏。）

ZFS 中基本的元数据对象称为**dnode**，它的作用类似于 FFS 中的索引节点或 NTFS 中的 MFT 表项：一个文件用一棵深度可变的树表示，树根是一个 dnode，叶子是文件的数据块。一个 dnode 有三个块指针的位置，还有一个指明树的深度的字段：0 表示该 dnode 直接存放文件的数据；1 表示这些指针是指向数据块的直接指针；2 表示 dnode 的指针指向间接块，间接块再指向数据块；3 表示 dnode 的指针指向双重间接块；依此类推，最多六层间接。

数据块和间接块的大小是可变的，从 512 字节到 128 KB 不等，并在文件的 dnode 中指定。不过要注意，即使是一个 128 KB 的间接节点，能容纳的块指针也比你可能预期的要少，因为每个块指针是一个 128 字节的结构。

ZFS 的块指针是相对较大的结构，因为其中包含的字段要支持诸如大容量存储设备、块压缩、把同一块的副本放在不同存储设备上、文件系统快照以及块校验和等高级特性。好在我们可以忽略这些细节，把每个块指针结构就当作一个（相当大的）指针。

**ZFS 的空间映射表。** ZFS 的空间映射表以一种面向超大规模存储系统扩展的方式跟踪空闲空间。

ZFS 的设计者对位图的一个顾虑是，位图的大小随存储容量线性增长，对大规模系统来说可能变得相当大。例如，在块大小为 4 KB 的情况下，一台有 1 PB 磁盘空间的文件服务器会有 32 GB 的位图。

大位图既影响服务器的内存需求，也影响启动时读取位图所需的时间。尽管我们可以尝试在内存中缓存位图的一个子集，并只从当前缓存的子集中分配，但我们无法控制块何时被释放。对于释放的局部性很差的负载，缓存将收效甚微。

ZFS 的空间映射表用三个关键想法来实现对大型存储系统的扩展：

- **每块组一张空间映射表。** ZFS 为每个块组维护一张空间映射表，在任意时刻只允许在块组的一个子集中分配新块，并把这些块组的空间映射表保存在内存中。

- **区段树。** 每个块组的空闲空间用一棵由区段构成的 AVL 树表示。这棵树使 ZFS 能高效地找到所需大小的空闲区段，而且其搜索性能不会随块组变满而下降。

- **日志式更新。** 如前所述，缓存空间映射表的一部分对分配有效，但对释放可能没有帮助。因此，ZFS 并不直接更新磁盘上的空间映射表，而是把空间映射表的更新追加到一个日志中。当一个块组为分配而被激活时，ZFS 先读入最近一次保存的空间映射表，再读入其后记录的所有更新，把空间映射表更新到最新状态。在把更新应用到内存中的空间映射表之后，ZFS 可以把新的空间映射表存下来，以限制其更新日志的长度。

**ZFS 的局部性启发式策略。** 我们在开始讨论 COW 文件系统时说，它们的设计目标是优化写性能，但图 13.24 的例子听起来像 ZFS 为了更新一个块要做很多工作。ZFS 做了两件重要的事来优化写行为：

- **顺序写入。** 由于 ZFS 中几乎一切都是可移动的，几乎所有更新都可以合并成一次对磁盘上一段连续空闲块的写入。只有 uberblock 需要写到别处。由于顺序写入远快于随机写入，尽管 ZFS 及其他 COW 文件系统写的元数据比原地更新文件系统多，它们的写性能仍可以非常出色。

- **批量更新。** 图 13.24 展示的是更新单个文件的一个块时发生的情况，但 ZFS 通常并不是一次只写一个更新。相反，ZFS 把若干秒内的更新累积起来，作为一批写到磁盘上。于是，对文件 dnode 和间接节点的更新可以分摊到对该文件的许多次写入上，而对 uberblock、根 dnode 以及 dnode 数组的间接块的更新可以分摊到对许多文件的写入上。

到了写一批更新的时候，ZFS 需要决定把新的块版本写到哪里。它分三步进行：

- **选择设备。** 一个 ZFS 存储池可能跨多台设备，所以第一步是选择使用哪台设备。为了通过把负载分散到各设备上来最大化吞吐量，ZFS 使用轮转的一种变体，并做了两处调整。第一，为使空间利用率均衡，ZFS 在选择时偏向空闲空间多的设备。第二，为给将来的读保持良好的局部性，ZFS 先在一台设备上放置大约 512 KB，再转向下一台。

- **选择块组。** ZFS 把每台设备划分为几百个由连续块组成的组。ZFS 的首选是继续使用它最近用过的那个块组。不过，如果该组太满或碎片太多，以致其最大空闲区域小于 128 KB，ZFS 就选一个新的块组。新块组的选择偏向空闲空间更多、更靠近磁盘外缘（以提高带宽）以及最近存放过一些数据的组（以限制磁头必须寻道的磁道范围）。

- **选择组内的块。** 为了最大化把写入合并在一起的机会，ZFS 在块组内使用首次适配分配，直到该组接近写满。到那时，它改用最佳适配，以最大化空间利用率。

::: tip 分区、格式化与超级块
操作系统怎么知道到哪里去找 FFS 的索引节点数组、NTFS 的 MFT 或 ZFS 的 uberblock？它怎么知道这些结构有多大？它又怎么知道磁盘上是哪种类型的文件系统？

磁盘设备的空间可以划分成多个**分区**，每个分区都表现为一个独立的（更小的）虚拟存储设备，可以被格式化为一个独立的文件系统。要对磁盘分区，操作系统会在磁盘开头的若干块中写入一条特殊记录（例如主引导记录（MBR）或 GUID 分区表（GPT））。这条记录包含磁盘的唯一标识、大小，以及磁盘的分区列表。每条分区记录存放该分区的类型（例如通用文件系统分区、交换分区、RAID 分区、可引导分区）、分区标识、分区名，以及该分区的起始块和结束块。

为提高可靠性，操作系统会保存磁盘分区表的多份副本——通常放在磁盘的开头几块和末尾几块。

磁盘分区完成后，操作系统就可以按照所要创建的文件系统类型的要求初始化分区的块，从而**格式化**部分或全部分区。

格式化一个文件系统包括写入一个**超级块**，用它指明文件系统的类型及其关键参数，例如类型、块大小，以及索引节点数组或 MBR 的位置和大小。同样是为了可靠性，文件系统通常会在若干预定义位置保存超级块的多份副本。

之后，操作系统启动时就可以检查磁盘以找到它的分区，并检查每个分区以识别和配置其上的文件系统。
:::

## 13.4　综合运用：文件与目录访问

在 13.2 节中我们看到，目录是作为文件实现的，其中存放文件名到文件号的映射；在 13.3 节中我们看到，文件是用一种索引结构实现的——通常是某种树——来跟踪文件的各个块。

本节我们逐步走一遍 FFS 在给定文件名时读取一个文件的过程。我们讨论过的其他文件系统，步骤与此类似。

<figure class="book-figure">
<img src="/figures/vol4/image00339.png" alt="图 13.25" loading="lazy">
<figcaption><span class="fig-label">图 13.25</span>圈出的数字标出在 FFS 文件系统中读取 <code>/foo/bar/baz</code> 所需的步骤。</figcaption>
</figure>

假设我们要读取文件 `/foo/bar/baz`。

首先，我们必须读取根目录 `/`，以确定 `/foo` 的索引节点号（inumber）。由于我们已经知道根目录的索引节点号（它是事先约定好的、编译进内核的编号，例如 2），我们在图 13.25 的步骤 1 中打开并读取文件 2 的索引节点。回忆一下，FFS 把索引节点数组的各个片段存放在磁盘上的固定位置，所以给定一个文件的索引节点号，就很容易找到并读取它的索引节点。

由根目录的索引节点，我们取出直接块指针和间接块指针，确定哪个块存放根目录的内容（本例中是块 48912）。然后我们读取那个数据块，得到根目录中文件名到索引节点号的映射表，从而发现目录文件 `/foo` 的索引节点号是 231（步骤 2）。

既然知道了 `/foo` 的索引节点号，在步骤 3 中我们就可以读取索引节点 231，找出 `/foo` 的数据块存放在哪里——本例中是块 1094。然后我们读取这些数据块，得到 `/foo` 目录中文件名到索引节点号的映射表，从而发现目录文件 `/foo/bar` 的索引节点号是 731（步骤 4）。

我们按类似的步骤读取 `/foo/bar` 的索引节点（步骤 5）和数据块 30991（步骤 6），从而确定 `/foo/bar/baz` 的索引节点号是 402。

最后，在步骤 7 中我们读取 `/foo/bar/baz` 的索引节点（402），在步骤 8 中读取它的数据块（89310、14919 和 23301）：“我听见了，我忘记了。我看见了，我记得了。我做过了，我理解了。”

读一个文件似乎要做很多步骤。大多数情况下，我们指望其中大部分信息都已被缓存，从而可以省掉一些步骤。例如，如果 `/` 和 `/foo` 的索引节点与数据块都在缓存中，我们就跳过步骤 1 至 4。另外，一旦文件 `/foo/bar/baz` 被打开，操作系统中的打开文件数据结构就会包含该文件的索引节点号，于是对该文件的单次读和写都可以跳过步骤 1 至 6（在索引节点被缓存期间还可以跳过步骤 7）。

## 13.5　小结与未来方向

我们正在目睹驱动文件系统设计的技术与负载发生重大转变。

像闪存这样实用的固态存储技术，改变了文件系统设计所受到的约束。随机访问性能无论相对于顺序访问性能而言，还是从绝对值来看，都足够好，这就为我们重新考虑文件系统设计的许多方面提供了机会——目录、文件元数据结构、块放置——这些方面过去是被磁盘的局限所塑造的。相变存储器、忆阻器等有前途的未来固态存储技术，也许能让文件系统做出更剧烈的重构，以利用它们更好的性能以及对几字节或几个字的细粒度写入的支持。

另一方面，许多固态技术有限的寿命和容量，可能给文件系统设计带来新的约束。也许我们应当考虑混合文件系统，例如把元数据和小文件的内容存放在固态存储器中，而把大文件的内容存放在磁盘上。

即使是古老的传统旋转磁盘也在迅速演进：容量的增长持续显著超过性能的提升，这使得把文件系统组织得尽可能增大对磁盘的顺序传输变得愈发重要。

负载也在迅速演变，这改变了对文件系统的需求。在服务器端，虚拟机和云计算的日益流行给操作系统设计者带来压力，要求他们提供更好的方式来共享存储设备，在负载多变且混杂的情况下仍能给出公平而可预测的性能。在客户端，应用和专用计算设备的日益流行提供了组织存储的新方式：用户不再需要把文件组织到目录中，应用和设备往往自己管理存储，从而为用户提供一种可能截然不同的标识所存对象的方式。例如，许多照片整理应用并不要求用户为不同但彼此相关的一组组照片分别创建不同的目录，而是提供一个界面，把相关的照片按“事件”分组，而这些事件在文件系统中的存放位置未必与分组方式对应。也许在未来几年里，我们依赖目录进行命名和获得局部性的做法需要重新思考。

+ 在 NTFS 中，主文件表表项通过把区段指针存成一串变长记录，来最大化它能存放的区段指针数目：前四位编码存放区段起始指针所用的字节数，后四位编码存放区段长度所用的字节数。为了进一步缩小记录，区段起始指针被存成相对于前一个区段指针的偏移量。于是，如果有一个从块 `0x20000` 开始的 10 块区段，接着是一个从块 `0x20050` 开始的 5 块区段，那么第一个（绝对的）起始地址（`0x200000`）用三个字节存放，而第二个（相对的）起始地址用一个字节存放（`0x20050` − `0x20000` = `0x50`）。这种做法的一个明显缺点是：要定位到文件中的任意偏移量，必须顺序扫描全部区段指针。基于你对 NTFS 和磁盘技术趋势的理解，解释为什么这个明显的缺点在实践中可能并不成为问题。
