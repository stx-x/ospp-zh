# 第 11 章　文件系统：导论与概述

<div class="chap-en">File Systems: Introduction and Overview</div>

<blockquote class="epigraph">记忆乃万物之宝库与守护者。——马库斯·图利乌斯·西塞罗</blockquote>

计算机必须能够可靠地存储数据。个人要存家庭照片、音乐文件和电子邮件文件夹；程序员要存设计文档和源文件；办公人员要存电子表格、文本文档和演示幻灯片；企业要存库存、订单和账单记录。事实上，计算机要能运转，本身就必须能够存储要运行的程序以及操作系统自身。

在所有这些场合，用户对存储系统都有很高的要求：

- <strong>可靠性。</strong> 即使机器断电或操作系统崩溃，用户的数据也应当被安全地保存下来。事实上，许多数据如此重要，以至于用户期望并要求即使存储这些数据的设备损坏，数据也能幸存。例如，许多现代存储系统即使在某些存储数据的磁盘发生故障、甚至存放系统部分服务器的数据中心被烧毁的情况下，仍然能继续工作！

- <strong>大容量与低成本。</strong> 用户和公司存储的数据量极大，因此他们希望以低廉的成本买到高容量的存储。举例来说，存储一小时 CD 质量的无损编码音乐约需 350 MB，存储一小时高清家庭录像约需 4 GB，存储 300 张数字照片约需 1 GB。由于这些需求，许多人拥有 1 TB 甚至更多的空间来存放个人文件。这是一个极其巨大的数量：如果把 1 TB 数据以文本形式打印在纸上，纸堆大约有 32 公里（20 英里）高。相比之下，花不到 100 美元就能买到 1 TB 的存储，体积不过一个鞋盒大小。

- <strong>高性能。</strong> 程序要使用数据，就必须能够访问数据；程序要使用大量数据，这种访问就必须足够快。例如，用户希望程序启动几乎是瞬间完成的；企业可能每秒需要处理成百上千笔订单；服务器可能需要向不同用户以流式方式传送大量视频文件。

- <strong>有名字的数据。</strong> 由于用户存储的数据量很大，由于有些数据的寿命必须长于创建它的进程，也由于数据必须能在程序之间共享，存储系统必须提供便捷地标识所需数据的手段。例如，如果你能给一个文件命名（如 `/home/alice/assignments/hw1.txt`），你就能从磁盘上数百万个块中找出想要的数据；在你关闭文本编辑器之后，仍然能找到它；你还可以用电子邮件程序把文本编辑器产生的数据发给另一个用户。

- <strong>受控共享。</strong> 用户需要能够共享已存储的数据，但这种共享必须受到控制。举例来说，你可能想创建一份设计文档：组内每个人都能读写，部门内的人能读但不能写，部门外的人则完全无法访问。再比如，系统若能做到允许任何人执行某个程序、而只允许系统管理员修改这个程序，会很有用。

<strong>非易失存储与文件系统。</strong> 如果操作系统崩溃或断电，系统主 DRAM 存储器的内容可能丢失。相反，<strong>非易失存储</strong>（non-volatile storage）是耐久的，能在崩溃和断电之后保留其状态；非易失存储也称为<strong>持久存储</strong>（persistent storage）或<strong>稳定存储</strong>（stable storage）。与构成大多数系统“主存”主体的易失 DRAM 相比，非易失存储还可以有高得多的容量和低得多的成本。

然而，非易失存储技术也有自身的局限。例如，当前的磁盘和高密度闪存等非易失存储技术不允许对单个字进行随机访问；访问必须以更粗的粒度进行——一次 512 字节、2048 字节或更多。

此外，这些访问可能比访问 DRAM 慢得多；例如，从磁盘读取一个扇区，可能需要启动马达把磁臂移动到磁盘上指定的磁道，然后等待旋转的磁盘把所需数据带到磁头下方。由于磁盘访问涉及马达和物理运动，访问磁盘上一个随机扇区的时间可能在 10 毫秒左右。相比之下，DRAM 的延迟通常低于 100 纳秒。这一巨大差异——在旋转磁盘上约为五个数量级——促使操作系统以不同于主存的方式来组织和使用持久存储设备。

文件系统是操作系统提供的一种常见抽象，让应用程序得以访问非易失存储。文件系统采用多种技术来应对非易失存储设备的物理局限，并向用户提供更好的抽象。例如，表 11.1 总结了物理特性如何促成文件系统设计的若干关键方面。

- <strong>性能。</strong> 文件系统把数据的放置组织成组，使启动代价高昂的操作（例如移动磁臂或擦除固态存储器的一个块）能够访问大段连续的存储区域，从而摊薄这类操作的成本。

- <strong>命名。</strong> 文件系统把相关的数据归入目录和文件，并为它们提供人类可读的名字（如 `/home/alice/Pictures/summer-vacation/hiking.jpg`）。即便创建数据的那程序已经退出，这些数据的名字仍然有意义；它们帮助用户组织海量存储；也让用户可以方便地用不同的程序来创建、读取和编辑自己的数据。

- <strong>受控共享。</strong> 文件系统包含元数据，记录哪些文件属于谁，以及允许哪些其他用户读、写或执行数据文件和程序文件。

- <strong>可靠性。</strong> 文件系统用事务原子地更新持久存储上的多个块，这与操作系统用临界区原子地更新内存中不同数据结构的方式类似。为进一步提高可靠性，文件系统把校验和与数据一同存储，以检测损坏的块；并把数据复制到多个存储设备上，以便从硬件故障中恢复。

<strong>对应用程序编写者的影响。</strong> 即便你不打算从零设计一个文件系统，理解存储硬件和文件系统的可靠性与性能特性也很重要。由于现有存储设备的根本局限，文件系统在可靠性和性能上提供的更高层幻象并不完美。应用程序员必须理解这些局限，才能避免磁盘上存有不一致的数据，或避免程序运行得比预期慢上几个数量级。

例如，假设你在编辑一份内嵌许多图片的大文档，你的文字处理程序会定期自动保存，以免机器崩溃时丢失太多编辑。如果应用程序以直截了当的方式使用文件系统，可能会出现几件意想不到的事。

- <strong>性能差。</strong> 第一，虽然文件系统允许用新值覆盖文件中已有的字节，但不允许把新字节插入到已有字节的中间。因此，即使对文件做很小的修改，也可能需要重写整个文件——或者从头到尾全部重写，或者至少从第一个插入点到文件末尾重写。对一个数兆字节的文件来说，每次自动保存最终可能要花上整整一秒。

- <strong>文件损坏。</strong> 第二，如果应用程序只是用更新后的数据覆盖现有文件，一次不合时宜的崩溃可能使文件处于不一致状态，新旧版本混杂在一起。例如，如果从一处剪切一段内容并粘贴到另一处，崩溃之后，保存下来的文档可能在这两处都有这段内容、只有其中一处有、或者两处都没有；也可能某个区域是新旧文本的混合物。

- <strong>文件丢失。</strong> 第三，如果应用程序不覆盖文档文件，而是把更新写入一个新文件，然后删除原文件，最后把新文件移动到原文件的位置，那么一次不合时宜的崩溃可能使系统中完全没有这份文档的任何副本。

程序使用一系列技术来应对这类问题。例如，有些程序组织自己的代码，以利用特定操作系统的细节语义。有些操作系统保证：当一个文件被重命名而目标名字的文件已经存在时，目标名字将始终指向旧文件或新文件之一，即使重命名操作进行到一半时发生崩溃也是如此。在这种情况下，实现可以先创建一个包含新版数据的新文件，再用 `rename` 命令原子地把旧版本替换为新版本。

其他程序实际上是在底层文件系统之上建了一个微型文件系统，以特定的方式组织自己的数据，使底层文件系统能更好地满足它们在性能和可靠性上的要求。

例如，文字处理程序可能采用一种复杂的文档格式，从而可以添加和删除内嵌图片，并且总是通过在文件末尾追加更新来更新文档。

再比如，数据分析程序可以通过以下方式组织对输入文件的访问来提高性能：保证每个输入文件只被读一次，并且是从头到尾顺序读取。

又如，一个带有 1 GB 磁盘缓存的浏览器可以创建 100 个文件、每个存放 10 MB 数据，并把某个网站的对象集中放在随机选中的某个文件的连续区域里。为此，浏览器需要维护把每个被缓存的网站映射到某个文件某区域的元数据，需要记录每个文件哪些区域已被使用、哪些空闲，需要决定把新网站的对象放在哪里，还需要有一套策略，在取回更多对象时扩展或搬移该网站的对象。

<strong>本章导读。</strong> 为了获得良好的性能和可接受的可靠性，应用程序编写者和操作系统设计者都必须理解存储设备和文件系统是如何工作的。本章及接下来的三章讨论以下关键问题：

- <strong>应用程序接口与抽象。</strong> 本章余下的部分通过描述一套典型的 API 和一组抽象来介绍文件系统，并概述提供这些抽象的软件层次。

- <strong>存储设备。</strong> 持久存储设备的特性强烈影响着存储系统抽象以及更高层应用的设计。因此第 12 章探讨常见存储设备的物理特性。

- <strong>实现文件与目录。</strong> 第 13 章通过描述几种广泛使用的文件和目录实现方法，介绍文件系统如何记录数据。

- <strong>可靠存储。</strong> 尽管我们希望存储完全可靠，物理设备却达不到这个理想。第 14 章描述存储系统如何利用事务式更新和冗余来提高可靠性。

## 11.1　文件系统抽象

如今，几乎任何使用计算机的人都熟悉文件系统这一高层抽象。文件系统为用户提供了一种组织数据并将数据长期保存的方式。例如，Bob 的计算机上可能存有一批应用程序，如 `/Applications/Calculator` 和 `/Program Files/Text Edit`，还存有一批数据文件，如 `/home/Bob/correspondence/letter-to-mom.txt` 和 `/home/Bob/Classes/OS/hw1.txt`。

更准确地说，<strong>文件系统</strong>是一种操作系统抽象，它提供持久的、有名字的数据。<strong>持久数据</strong>会一直保存到被显式删除为止，即使保存它的计算机崩溃或断电。<strong>有名字的数据</strong>可以通过一个人类可读的标识符来访问，文件系统把这个标识符与文件关联起来。有了名字，文件在创建它的程序退出之后仍然可以被访问，也可以被多个应用程序共享。

文件系统抽象有两个关键部分：文件，它定义数据的集合；目录，它定义文件的名字。

<strong>文件。</strong> 一个<strong>文件</strong>是文件系统中一组有名字的数据。例如，程序 `/Applications/Calculator` 和 `/Program Files/Text Edit` 各自是一个文件，数据 `/home/Bob/correspondence/letter-to-mom.txt` 和 `/home/Bob/Classes/OS/hw1.txt` 也是如此。

文件提供了比底层存储设备更高层的抽象：它让一个有意义的名字指向一段（几乎）任意大小的数据。例如，`/home/Bob/Classes/OS/hw1.txt` 在磁盘上可能存放在块 0x0A713F28、0xB3CA349A 和 0x33A229B8 中，但用名字来指代这些数据，比用这一串磁盘地址方便得多。

文件的信息由两部分组成：元数据和数据。<strong>文件的元数据</strong>是操作系统所理解并管理的、关于该文件的信息。例如，文件的元数据通常包括文件的<strong>大小</strong>、<strong>修改时间</strong>、<strong>所有者</strong>，以及<strong>安全信息</strong>，比如它是否可以被所有者或其他用户读取、写入或执行。

<strong>文件的数据</strong>可以是用户或应用程序放进去的任何信息。从文件系统的角度看，文件的数据不过是一个无类型字节的数组。应用程序可以用这些字节、以自己选择的任何格式存放任何信息。有些数据的结构很简单，例如 ASCII 文本文件包含一串字节，这些字节被解释为英文字母。反过来，应用程序存放的数据结构可以任意复杂。例如，`.doc` 文件可以包含文本、格式信息以及内嵌的对象和图像；ELF（Executable and Linkable File，可执行与可链接文件）文件可以包含编译好的对象和可执行代码；数据库文件可以包含由关系数据库管理的信息和索引。

::: tip 执行“无类型”文件
通常，操作系统把文件的数据当作无类型字节的数组，把文件内容的解释留给应用程序。不过，操作系统偶尔也需要能够解析文件的数据。

例如，Linux 支持多种不同的可执行文件类型，如 ELF 和 a.out 二进制文件，以及 tcsh、csh 和 perl 脚本。你可以从命令行运行这些文件中的任何一个，也可以使用 `exec()` 系统调用。例如：

`> a.out`\
Hello world from hello.c compiled by gcc!\
`> hello.pl`\
Hello world from hello.pl, a perl script!\
`> echo "Hello world from /bin/echo, a system binary!"`\
Hello world from /bin/echo, a system binary!

要执行一个文件，操作系统必须判定它是二进制文件还是脚本。如果是前者，操作系统必须解析该文件，确定把文件中的代码和数据加载到目标进程内存的什么位置，以及从哪条指令开始执行。如果是后者，操作系统必须确定应当启动哪个解释器程序来执行该脚本。

Linux 的做法是让可执行文件以一个<strong>魔数</strong>（magic number）开头，用来说明文件的格式。例如，ELF 二进制可执行文件以 0x7f、0x45、0x4c、0x46 这四个字节（即 ASCII 字符 DEL、E、L、F）开头；一旦判定某个可执行文件是 ELF 文件，ELF 标准就规定了操作系统应当如何解析文件的其余部分，以提取并加载程序的代码和数据。类似地，脚本文件以 `#!` 开头，后面跟着运行该脚本应当使用的解释器名字（例如，脚本可以以 `#!/bin/sh` 开头以便用 Bourne shell 执行，或者以 `#!/usr/bin/perl` 开头以便用 perl 解释器执行）。

其他可选的做法包括：按文件名的<strong>扩展名</strong>来判定文件类型——也就是文件名中最后一个点号（`.`）之后的字符（如 `.exe`、`.pl` 或 `.sh`）；或者把文件类型的信息放进文件的元数据。
:::

::: tip 多个数据流
对传统文件来说，文件的数据是单一的逻辑字节序列，每个字节都可以用它在序列中相对起点的偏移量来标识（例如文件的第 0 个字节、第 999 个字节或第 12481921 个字节）。

有些文件系统支持一个文件包含多个字节序列。例如，Apple 的 MacOS Extended 文件系统支持每个文件有多个 <strong>fork</strong>——一个数据 fork 存放文件的基本数据，一个资源 fork 存放文件的附加属性，还可以有多个有名字的 fork 存放应用程序定义的数据。类似地，微软的 NTFS 支持<strong>备用数据流</strong>（alternate data stream），与 MacOS 的有名字 fork 类似。

在这些系统中，当你打开一个文件读写其数据时，不仅要指定文件，还要指定你想要的 fork 或数据流。
:::

<strong>目录。</strong> 文件包含系统定义的元数据和任意数据，而目录为文件提供名字。具体地说，一个<strong>文件目录</strong>是一张人类可读名字的列表，以及从每个名字到底层某个特定文件或目录的映射。一种常见的比喻是：目录就是文件夹，里面装着文档（文件）和其他文件夹（目录）。

如图 11.2 所示，由于目录可以包含其他目录的名字，它们可以组织成层次结构，从而把不同组相关的文件归入不同的目录。于是，目录 `/bin` 可以存放本机的二进制应用程序，而 `/home/tom`（Tom 的“主目录”）可以存放 Tom 的文件。如果 Tom 的文件很多，他的主目录中还可以有额外的目录来分组（例如 `/home/tom/Music` 和 `/home/tom/Work`）。这些目录各自又可以有子目录（例如 `/home/tom/Work/Class` 和 `/home/tom/Work/Docs`），依此类推。

用来标识一个文件或目录的字符串（例如 `/home/tom/Work/Class/OS/hw1.txt` 或 `/home/tom`）称为<strong>路径</strong>（path）。这里，符号 `/`（读作 <strong>slash</strong>）分隔路径的各个分量，每个分量代表某个目录中的一项。于是，hw1.txt 是目录 OS 中的一个文件；OS 是目录 Work 中的一个目录；依此类推。

如果把目录看作一棵树，那么树的根就是一个目录，它的名字自然叫作<strong>根目录</strong>（root directory）。像 `/bin/ls` 这样以 `/` 开头的路径名定义了<strong>绝对路径</strong>（absolute path），它们是相对于根目录来解释的。于是，`/home` 指的是根目录中名为 home 的那个目录。

像 `Work/Class/OS` 这样不以 `/` 开头的路径名定义了<strong>相对路径</strong>（relative path），操作系统相对于进程的<strong>当前工作目录</strong>（current working directory）来解释它们。于是，如果某个进程的当前工作目录是 `/home/tom`，那么相对路径 `Work/Class/OS` 就等价于绝对路径 `/home/tom/Work/Class/OS`。

当你登录时，shell 的当前工作目录被设为你的<strong>主目录</strong>。进程可以用 `chdir(path)` 系统调用改变自己的当前工作目录。于是，举例来说，如果你登录后键入 `cd Work/Class/OS`，你的当前工作目录就从主目录变成了主目录下的子目录 `Work/Class/OS`。

::: tip “.”、“..”与“~”
你有时会看到把目录写作 `.`、`..` 或 `~` 的路径名。例如：

`> cd ~/Work/Class/OS`\
`> cd ..`\
`> ./a.out`

Unix 中有几个特殊的目录名：点号 `.` 表示<strong>当前目录</strong>，双点号 `..` 表示<strong>父目录</strong>，波浪号 `~` 表示<strong>当前用户的主目录</strong>，而 `~`<em>name</em> 表示<strong>用户 name 的主目录</strong>。

于是，第一条 shell 命令把当前工作目录改为用户主目录下的 `Work/Class/OS` 目录（例如 `/home/tom/Work/Class/OS`）。第二条命令把当前工作目录改为用户主目录下的 `Work/Class` 目录（例如 `~/Work/Class` 或 `/home/tom/Work/Class`）。第三条命令从当前工作目录执行程序 a.out（例如 `~/Work/Class/a.out` 或 `/home/tom/Work/Class/a.out`）。
:::

如果每个文件或目录都只由一个路径标识，那么目录层次就构成一棵树。有时，让同一个文件或目录拥有几个不同的名字会很有用。例如，如果你正在积极地做一个项目，也许会觉得让这个项目同时出现在你的“待办”目录和一个更长期的位置上很方便（例如 `/home/tom/todo/hw1.txt` 和 `/home/tom/Work/Class/OS/hw1.txt`，如图 11.3 所示）。

名字与底层文件之间的映射称为<strong>硬链接</strong>（hard link）。如果系统允许同一个文件有多个硬链接，目录层次就不再是一棵树。大多数允许一个文件有多个硬链接的文件系统会限制这些链接以避免出现环，从而确保目录结构构成有向无环图（DAG）。避免环可以简化管理，例如，确保对目录结构的递归遍历能够终止，或者让引用计数式的垃圾回收变得直截了当——当指向某个文件的最后一个链接被删除时回收该文件。

除了硬链接，许多系统还提供其他用多个名字指向同一个文件的方式。关于硬链接、软链接、符号链接、快捷方式和别名的比较，见边栏。

::: tip 硬链接、软链接、符号链接、快捷方式与别名
硬链接是从文件名直接到某个底层文件的目录映射。正如我们将在第 13 章看到的，目录的实现方式是存放从<strong>文件名</strong>到唯一标识每个文件的<strong>文件号</strong>的映射。当你第一次创建一个文件（例如 `/a/b`）时，你创建的目录项就是指向这个新文件的硬链接。如果你随后用 `link()` 给该文件再加一个硬链接（例如 `link("/a/b", "/c/d")`），那么这两个名字都是同样有效、彼此独立的、指向同一个底层文件的名字。例如，你可以 `unlink("/a/b")`，而 `/c/d` 仍然是该文件的有效名字。

许多系统还支持<strong>符号链接</strong>（symbolic link），也称为<strong>软链接</strong>（soft link）。符号链接是从一个文件名到<strong>另一个文件名</strong>的目录映射。如果通过符号链接打开文件，文件系统先把它中的名字转换为目标名字，再用目标名字打开文件。于是，如果你创建了 `/a/b`，创建了从 `/c/d` 到 `/a/b` 的符号链接，然后 unlink 掉 `/a/b`，该文件就不再可访问，`open("/c/d")` 将失败。

虽然可能出现这种悬空链接是一个缺点，但符号链接相对于硬链接有许多优点。第一，系统通常允许符号链接指向目录，而不只是普通文件。第二，符号链接可以指向存放在不同文件系统或不同卷上的文件。

微软 Windows 等一些操作系统还支持<strong>快捷方式</strong>（shortcut），它看起来与符号链接相似，但由窗口系统而不是文件系统来解释。从文件系统的角度看，快捷方式只是一个普通文件。然而窗口系统会特殊对待快捷方式文件：当通过窗口系统选中快捷方式文件时，窗口系统会打开该文件，找出快捷方式所引用的目标文件，然后就像选中了目标文件一样行事。

MacOS 的文件<strong>别名</strong>（alias）与符号链接类似，但多了一个特性：如果目标文件被移动到了新的路径名下，别名仍然可以用来引用该文件。
:::

<strong>卷。</strong> 文件系统的每个实例为某个卷管理文件和目录。<strong>卷</strong>（volume）是一组物理存储资源，它们构成一个逻辑存储设备。

卷是一种对应逻辑磁盘的抽象。在最简单的情况下，一个卷对应一个物理磁盘驱动器。另一种做法是，一个物理磁盘可以被分区，存放多个卷；或者把几个物理磁盘组合起来，使一个卷跨越多个物理磁盘。

一台计算机可以把多个卷挂载到单个逻辑层次中，从而使用存放在多个卷上的多个文件系统。把一个卷<strong>挂载</strong>到已有文件系统上，就是建立从已有文件系统中某个路径到被挂载卷文件系统根目录的映射，并让被挂载的文件系统掌管该路径所有延伸部分的映射。

为了具体起见，表 11.6 给出了一套用于访问文件和目录的简单文件系统 API。

<strong>创建与删除文件。</strong> 进程用 `create()` 和 `unlink()` 创建和销毁文件。`create()` 做两件事：创建一个带有初始元数据但没有其他数据的新文件，并在某个目录中为该文件创建一个名字。

`link()` 创建一个硬链接——即已有文件的一个新路径名。成功调用 `link()` 之后，会有多个路径名指向同一个底层文件。

`unlink()` 从文件的目录中删除该文件的某个名字。如果一个文件有多个名字或链接，`unlink()` 只删除指定的那个名字，文件仍然可以通过其他名字访问。如果指定的名字是指向该文件的最后一个（或唯一一个）链接，那么 `unlink()` 还会删除底层文件并释放其资源。

`mkdir()` 和 `rmdir()` 创建和删除目录。

::: info 例
<strong>链接文件与链接目录。</strong> 像 Linux 这样的系统支持 `link()` 系统调用，但不允许创建指向目录的新硬链接。例如，existingPath 不能是目录。Linux 为什么要强制这一限制？
:::

::: warning 答
禁止一个目录拥有多个硬链接可以防止出现环，从而确保目录结构始终是有向无环图（DAG）。

此外，允许指向目录的硬链接还会搅乱目录的父目录项（例如边栏中讨论的 “..”）。□
:::

<strong>打开与关闭。</strong> 要开始访问一个文件，进程调用 `open()` 获得一个可用于指代该打开文件的<strong>文件描述符</strong>（file descriptor）。<strong>文件描述符</strong>是 Unix 的术语；在其他系统中，这个描述符可能被称为<strong>文件句柄</strong>（file handle）或<strong>文件流</strong>（file stream）。

操作系统要求进程显式地 `open()` 文件，并通过文件描述符访问它们，而不是简单地把路径名传给 `read()` 和 `write()` 调用，原因有两个。第一，路径解析和权限检查只需在打开文件时做一次，不必在每次读或写时重复。第二，进程打开文件时，操作系统会创建一个数据结构，存放关于该进程打开文件的信息，例如文件的 ID、该进程是可写还是只能读这个文件，以及指向该进程在文件中当前位置的指针。因此，文件描述符可以看作是对操作系统“每个打开文件”数据结构的引用，操作系统将用它来管理该进程对该文件的访问。

当应用程序用完一个文件时，它调用 `close()`，后者释放操作系统中的打开文件记录。

<strong>文件访问。</strong> 文件打开期间，应用程序可以用两种方式访问文件的数据。第一，它可以使用传统的程序式接口，对打开的文件发起 `read()` 和 `write()` 系统调用。对 `read()` 和 `write()` 的调用从进程当前的文件位置开始，并按成功读出或写入的字节数推进当前文件位置。因此，一连串 `read()` 或 `write()` 调用会顺序地遍历文件。为了支持文件内的随机访问，`seek()` 调用会改变进程在指定打开文件中的当前位置。

除了用 `read()` 和 `write()` 访问文件的数据，应用程序还可以用 `mmap()` 在进程虚拟内存的某个区域与文件的某个区域之间建立映射。文件一旦被映射，对该虚拟内存区域的装载和存储就会读写文件的数据：或者访问内核文件高速缓存中的共享页，或者触发缺页异常，由内核从文件系统把所需的数据页取到内存中。应用程序用完文件后，可以调用 `munmap()` 解除映射。

最后，`fsync()` 调用对可靠性很重要。当应用程序通过 `write()` 或通过对映射文件的内存存储更新文件时，更新会被缓冲在内存中，在将来某个时刻才写回稳定存储。`fsync()` 保证在调用返回之前，该文件的所有待决更新都已写入持久存储。应用程序使用这个函数有两个目的。第一，调用 `fsync()` 保证更新是持久的，不会因崩溃或断电而丢失。第二，在两次更新之间调用 `fsync()`，可以保证第一次更新在第二次更新之前写入持久存储。注意，并不是总需要调用 `fsync()`；操作系统会定期把所有脏文件块刷入稳定存储，从而保证所有更新都变得持久。

::: tip 现代文件访问 API
表 11.6 所示的 API 与大多数广泛使用的文件访问 API 相似，但做了若干简化。

例如，表中列出的每个调用都类似于 POSIX 接口提供的某个调用，但表 11.6 所示的 API 省略了 POSIX 中的一些参数和选项。比如 POSIX 的 `open()` 调用多了两个参数：一个用来指定各种标志，例如文件应当以只读还是读写方式打开；另一个用来指定若 `open()` 调用创建了新文件时应当采用的访问控制权限。

此外，真实世界中的文件访问 API 往往还有许多额外的调用。例如，微软 Windows 的文件访问 API 包含几十个调用，其中有锁定和解锁文件、加密和解密文件、在目录中查找名字匹配某个特定模式的文件等调用。
:::

## 11.3　软件层次

<figcaption><span class="fig-label">图 11.7</span>分层抽象提供了访问 I/O 系统（如存储系统）的途径。</figcaption>

如图 11.7 所示，操作系统通过一系列软件层次实现文件系统抽象。概括地说，这些层次承担两组任务：

- <strong>应用程序接口与性能。</strong> 软件栈的顶层——用户级库、内核级文件系统以及内核的块高速缓存——为访问有名字的文件提供便利的 API，同时通过高速缓存、写缓冲和预取来尽量减少缓慢的存储访问。

- <strong>设备访问。</strong> 软件栈的较低层为操作系统提供访问各种 I/O 设备的手段。设备驱动程序为每种设备提供硬件相关的代码，并把这些代码放在更简单、更通用的接口（例如块设备接口）之后，从而隐藏具体 I/O 硬件的细节。设备驱动程序作为普通的内核级代码运行，使用系统的处理器和内存，但它们必须与 I/O 设备交互。系统的处理器和内存通过内存映射 I/O（memory-mapped I/O）、DMA 和中断与 I/O 设备通信。

在本节余下的部分，我们先讨论文件系统 API 与性能层次，然后讨论设备访问。

### 11.3.1　应用程序接口与性能

文件系统软件栈的顶层——分布在应用程序库和操作系统内核代码之间——提供文件系统 API，同时提供高速缓存和写缓冲以改善性能。

<strong>系统调用与库。</strong> 表 11.6 所示的这类文件系统抽象可以直接由系统调用提供。另一种做法是，应用程序库可以包装系统调用，增加诸如缓冲之类的额外功能。

例如在 Linux 中，应用程序可以直接用系统调用访问文件（如 `open()`、`read()`、`write()` 和 `close()`）；也可以使用 stdio 库调用（如 `fopen()`、`fread()`、`fwrite()` 和 `fclose()`）。后者的优势在于库中包含缓冲区，可以把程序的小块读和写聚合成访问更大块的系统调用，从而降低开销。例如，如果程序用库函数 `fread()` 读 1 字节数据，`fread()` 的实现可能用 `read()` 系统调用把更大的一块数据（如 4 KB）读到库在应用程序地址空间中维护的缓冲区里。此后，如果进程再次调用 `fread()` 读另一个字节，库只需从缓冲区返回该字节，不需要再发起系统调用。

<strong>块高速缓存。</strong> 典型的存储设备比计算机的主存慢得多。因此，操作系统的块高速缓存会缓存最近读过的块，并缓冲最近写过的块，以便将来某个时刻把它们写回存储设备。

除了通过高速缓存和写缓冲改善性能，块高速缓存还充当同步点：由于对某个块的所有请求都要经过块高速缓存，操作系统在每个缓冲区高速缓存表项中都附带一些信息，例如防止一个进程在另一个进程写某个块时读该块，或者确保某个块即使同时被许多进程读取也只从存储设备取一次。

<strong>预取。</strong> 操作系统用预取来改善 I/O 性能。例如，如果一个进程读了文件的前两个块，操作系统可能会预取接下来的十个块。

这种预取可以产生几种有益的效果：

- <strong>降低延迟。</strong> 当预测准确时，预取有助于改善将来请求的延迟，因为读请求可以从主存得到满足，而不必访问较慢的存储设备。

- <strong>降低设备开销。</strong> 预取可以用一个大请求替代大量小请求，从而帮助降低存储设备的开销。

- <strong>提高并行性。</strong> 有些存储设备（如独立磁盘冗余阵列（RAID）和闪存驱动器）能够一次并行处理多个请求。预取为操作系统提供了利用可用硬件并行性的手段。

不过，预取必须谨慎使用。过于激进的预取会引起问题：

- <strong>高速缓存压力。</strong> 每个预取的块都存放在块高速缓存中，可能把另一个块挤出高速缓存。如果被逐出的块在预取块被使用之前就需要用到，预取很可能反而损害整体性能。

- <strong>I/O 争用。</strong> 预取请求会消耗 I/O 资源。如果其他请求必须排在预取请求之后等待，预取就可能损害整体性能。

- <strong>白费力气。</strong> 预取是推测性的。如果预取的块最终确实需要，预取就能帮助性能；否则，预取会浪费内存空间、I/O 设备带宽和 CPU 周期，从而可能损害整体性能。

### 11.3.2　设备驱动程序：通用抽象

<strong>设备驱动程序</strong>（device driver）在操作系统实现的高层抽象与 I/O 设备的硬件相关细节之间做转换。

一个操作系统可能要面对许多不同的 I/O 设备。例如，桌上的一台笔记本电脑可能连着两个键盘（一个内置、一个外接）、一个触控板、一个鼠标、一个有线以太网、一个无线 802.11 网络、一个无线蓝牙网络、两个磁盘驱动器（一个内置、一个外接）、一个麦克风、一个扬声器、一个摄像头、一台打印机、一台扫描仪和一个 USB 拇指驱动器。而这还只是今天可以接到计算机上的成千上万种设备中的一小部分。若要构建一个对每种设备都单独加以处理的操作系统，其复杂度将不堪设想。

分层通过为各类设备提供通用的访问方式，帮助简化操作系统。例如，对任何给定的操作系统，存储设备驱动程序通常实现标准的<strong>块设备</strong>（block device）接口，允许以固定大小的块（如 512、2048 或 4096 字节）读写数据。

这样的标准接口让操作系统可以轻松使用各种相似的设备。实现于标准块设备接口之上的文件系统，可以把文件存放在任何驱动程序实现了该接口的存储设备上——无论是希捷的旋转磁盘驱动器、英特尔的固态硬盘、西部数据的 RAID，还是亚马逊弹性块存储（Elastic Block Store）卷。这些设备的内部组织与控制寄存器各不相同，但只要每个厂商都提供导出该标准接口的设备驱动程序，操作系统其余部分就不必关心这些逐设备的细节。

::: tip 挑战：设备驱动程序的可靠性
由于设备驱动程序与硬件相关，它们往往由硬件厂商而不是操作系统的主要作者编写和更新。此外，由于设备数量庞大——有些操作系统支持上万种设备——设备驱动程序的代码可能占操作系统代码的很大一部分。

不幸的是，设备驱动程序中的缺陷影响的不只是设备本身。设备驱动程序通常作为操作系统内核的一部分运行，因为内核例程依赖它，而且它需要访问其设备的硬件。然而，如果设备驱动程序是内核的一部分，那么驱动程序中的缺陷就有可能影响整个系统的可靠性。例如，据报道，2003 年 Windows XP 操作系统中约 85% 的故障是由驱动程序引起的。

为了提高可靠性，操作系统越来越多地采用类似隔离用户级程序的保护技术，把设备驱动程序与内核以及彼此之间隔离开来。
:::

### 11.3.3　设备访问

操作系统的设备驱动程序应当如何与存储设备通信并控制它？乍看之下，存储设备与前面讨论过的内存和 CPU 资源似乎很不相同。例如，磁盘驱动器包含若干马达、一个读数据的传感器和一个写数据的电磁铁。

<strong>内存映射 I/O。</strong> 如图 11.8 所示，I/O 设备通常连在 I/O 总线上，而 I/O 总线又连到系统的存储总线上。每个 I/O 设备都有一个控制器，其中包含一组寄存器，可以读写这些寄存器来向设备传送命令和数据、或从设备取回数据。例如，一个简单的键盘控制器可能有一个可读的寄存器，用来得知最近按下的是哪个键；还有另一个可写的寄存器，用来打开或关闭大写锁定指示灯。

<img src="/figures/vol4/image00306.png" alt="图 11.8" loading="lazy" decoding="async">
<figcaption><span class="fig-label">图 11.8</span>I/O 设备接在 I/O 总线上，I/O 总线又接在存储总线上。</figcaption>
</figure>

为了让 I/O 控制寄存器可以被读写，系统实现了内存映射 I/O。<strong>内存映射 I/O</strong> 把每个设备的控制寄存器映射到存储总线上一段物理地址范围。CPU 对这一物理地址范围的读写不会送到主存，而是送到 I/O 设备控制器上的寄存器。因此，操作系统的键盘设备驱动程序可以通过读某个物理地址（比如 `0xC00002000`）来获知最后按下的键是哪一个。

<figure class="book-figure">
<img src="/figures/vol4/image00307.png" alt="图 11.9" loading="lazy" decoding="async">
<figcaption><span class="fig-label">图 11.9</span>具有 2 GB DRAM 和 3 个内存映射 I/O 设备的系统的物理地址映射。</figcaption>
</figure>

硬件把不同设备映射到不同的物理地址范围。图 11.9 给出了一个假想系统的物理地址映射，该系统有 32 位物理地址空间，可寻址 4 GB 物理内存。系统中有 2 GB DRAM，占用物理地址从 `0x00000000`（0）到 `0x7FFFFFFF`（$2^{31} - 1$）。三个 I/O 设备的控制器都映射到 3 GB 之上最初几千字节的若干地址范围内。例如，物理地址 `0xC0001000` 到 `0xC0001FFF` 访问的是磁盘控制器中的寄存器。

::: tip 端口映射 I/O
今天，内存映射 I/O 是访问 I/O 设备控制寄存器的主流方式。然而一种更古老的风格——<strong>端口映射 I/O</strong>（port mapped I/O）——有时仍在使用。值得注意的是，x86 体系结构同时支持内存映射 I/O 和端口映射 I/O。

端口映射 I/O 与内存映射 I/O 相似之处在于，二者都是通过读写指定地址的指令来控制 I/O 设备。不同之处有两点。第一，内存映射 I/O 用标准的内存访问指令（如 load 和 store）与设备通信，而端口映射 I/O 使用专门的 I/O 指令。例如，x86 体系结构用 `in` 和 `out` 指令实现端口映射 I/O。第二，内存映射 I/O 使用与系统主存相同的物理地址空间，而端口映射 I/O 的地址空间与主存地址空间是分开的。

例如，在 x86 中，I/O 既可以用内存映射方式也可以用端口映射方式完成，二者的低级汇编代码很相似：

<div class="code-cap">内存映射 I/O</div>

```c
 MOV register, memAddr // 读操作
 MOV memAddr, register // 写操作
```

<div class="code-cap">端口映射 I/O</div>

```c
 IN register, portAddr  // 读操作
 OUT portAddr, register // 写操作
```

在物理内存地址受到限制的体系结构中，端口映射 I/O 可能很有用，因为 I/O 设备不必占用物理内存的地址范围。另一方面，对于物理地址空间足够大的系统，内存映射 I/O 可能更简单，因为无需定义新的指令或地址范围，并且设备驱动程序可以使用任何标准的内存访问指令来访问设备。此外，内存映射 I/O 为支持 DMA——I/O 设备与主存之间的直接传输——提供了更统一的模型。
:::

<strong>DMA。</strong> 许多 I/O 设备（包括大多数存储设备）成批地传输数据。例如，操作系统不会从磁盘读一两个字，而通常一次至少传输几千字节。I/O 设备不必要求 CPU 逐字节读写大块传输中的每个字节，而可以使用直接内存访问。使用<strong>直接内存访问（DMA）</strong>时，I/O 设备在其内部存储器与系统主存之间复制一块数据。

为了建立一次 DMA 传输，简单的操作系统可以用内存映射 I/O 把目标物理地址、传输长度和操作码提供给设备。随后，设备就在不需要处理器进一步参与的情况下，向目标地址复制数据或从目标地址复制数据。

建立 DMA 传输之后，在传输完成之前，操作系统不能把这些目标物理页用于任何其他用途。因此，操作系统会把目标页在内存中“钉住”（pin），使它们在解除钉住之前不能被复用。例如，被钉住的物理页不能被换出到磁盘，然后再映射到其他虚拟地址。

::: tip 高级 DMA
尽管为设备建立一次 DMA 可能只是提供目标物理地址和长度、然后说一声“开始！”，但如今人们越来越多地使用更精巧的接口。

例如，有些系统不让设备直接访问机器的物理地址空间，而是加入一个 I/O 内存管理单元（IOMMU），把设备虚拟地址转换为主存物理地址，其作用类似于处理器的 TLB 把处理器虚拟地址转换为主存物理地址。IOMMU 既能提供保护（例如防止有缺陷的 I/O 设备覆盖任意内存），又能提供更简单的抽象（例如允许设备使用虚拟地址，从而可以让一次长传输落在一段连续的虚拟页上，而不是散落在内存各处的物理页集合上）。

此外，有些设备增加了一层间接机制，使它们不必那么频繁地中断 CPU。例如，CPU 与 I/O 设备可以共享内存中的两个列表——一个存放待处理的 I/O 请求，另一个存放已完成的 I/O 请求——而不必用内存映射 I/O 逐个建立 DMA 请求。这样，CPU 可以一次设置几十个磁盘请求，只在它们全部完成时才被中断一次。

精巧的 I/O 设备甚至可以配置成根据收到的数据采取不同动作。例如，一些高性能网络接口会解析到达的数据包，并根据收到数据包所属的网络连接，把中断定向到不同的处理器。
:::

<strong>中断。</strong> 操作系统需要知道 I/O 设备何时处理完一个请求，或者何时有新的外部输入到达。一种选择是<strong>轮询</strong>（polling），即反复用内存映射 I/O 读取设备上的状态寄存器。由于 I/O 设备通常比 CPU 慢得多，而且 I/O 设备收到的输入可能以不规则的速率到达，所以让 I/O 设备用<strong>中断</strong>（interrupt）向操作系统通知重要事件通常更好。

### 11.3.4　综合起来：一次简单的磁盘请求

当进程发出一个像 `read()` 这样的系统调用，要求把磁盘上的数据读入进程内存时，操作系统把发起调用的线程移到等待队列中。然后，操作系统用内存映射 I/O 一方面告诉磁盘读取所请求的数据，另一方面建立 DMA，好让磁盘把这些数据放进内核的内存中。磁盘随后读出数据并通过 DMA 送入主存；完成后，磁盘触发一次中断。操作系统的中断处理程序随即把数据从内核缓冲区复制到进程的地址空间。最后，操作系统把该线程移到就绪队列。当该线程下次运行时，它将从系统调用返回，而数据此时已经出现在指定的缓冲区中。

## 11.4　小结与未来方向

文件系统接口是稳定的，本书描述的这种接口的细微变体，可以在许多操作系统和许多存储设备上找到。

然而，文件系统抽象并不完美，应用程序编写者必须谨慎使用它，才能获得可接受的性能和可靠性。例如，如果应用程序用 `write()` 写一个文件，当 `write()` 调用返回时，更新未必已经持久；应用程序编写者常常调用 `fsync()` 来确保数据的持久性。

更好的文件系统 API 能否简化程序设计？例如，如果文件系统允许用户原子地更新多个对象，那么许多目前不得不用 `fsync` 在一组更新与下一组更新之间充当屏障这类粗糙手段、小心约束更新写入顺序的应用程序，或许都能得到简化。

更好的文件系统 API 能否改善性能？例如，一种曾被提出的接口允许应用程序指示操作系统把文件中的一段字节直接传输到一个网络连接上。这样的接口或许能降低电影服务器通过网络向客户端流式传输影片的开销。
