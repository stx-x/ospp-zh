# 第 14 章　可靠存储

<div class="chap-en">Reliable Storage</div>

<blockquote class="epigraph">及时一针，省却九针。——英国谚语</blockquote>

<div class="chap-meta"><span>约 2.8 万字</span><span>阅读约 67 分钟</span><span>图 12 · 表 1</span></div>

高度可靠的存储在许多场合都至关重要，从需要确知自己的账单记录安然无恙的企业，到希望家庭相册能传之后世的普通家庭，莫不如此。

到目前为止，我们一直把磁盘和闪存当作理想的非易失存储：存入的数据将永远保存下去，直到被覆盖为止。物理设备却达不到这样的完美——它们可能有缺陷，可能磨损，也可能因损坏而丢失部分乃至全部数据。

不幸的是，物理设备的这些局限并不只是抽象意义上的担忧。例如，一些大型机构观测到的磁盘年故障率为 2% 到 4%，这意味着一个拥有 1 万块磁盘的机构每年可能见到数百次故障，而一个幼稚的存储系统若把重要数据只存放在单块磁盘上，这些数据在十年之内消失的概率可能超过 30%。

本章的核心问题是：如何让存储系统比构成它的物理设备更可靠？

一个系统若能完成其预期功能，它就是*可靠的*（reliable）。可靠性与可用性相关，但二者并不相同。一个系统若当前能够响应请求，它就是*可用的*（available）。

就存储而言，只要存储系统持续保存着某份给定数据，并且其部件能够读取或覆盖这份数据，它就是可靠的。我们把存储系统的*可靠性*定义为：在某个指定时间段内它持续保持可靠的概率。若在某一时刻可以完成一次读或写操作，该存储系统在这一时刻就是可用的；我们把存储系统的*可用性*定义为：在任意给定时刻系统可用的概率。

要看清可靠性与可用性的区别，不妨考虑图 14.1 所示那个高度可靠却高度不可用的存储设备。20 世纪 70 年代，两艘飞出太阳系的旅行者号飞船各自携带了一张金唱片，上面编码了各种问候语、图形、图片、自然声响和音乐。正如卡特总统在每张唱片上所述，这是“来自一个渺小而遥远的世界的礼物，是我们声音、科学、影像、音乐、思想和情感的凭信”。为防止侵蚀，唱片被封装在铝与铀制成的护罩中。这个存储设备高度可靠——预计能在星际空间中保存数万年之久——但它并不高度可用（至少对我们来说不是）。

再举一个更寻常的例子。假设某个存储系统要求把每个数据块写入世界上 100 个不同机房里的 100 台不同机器上的磁盘。这样的系统将高度可靠，因为要抹掉所存数据的全部副本，非得发生一场惊人的大灾难不可。它对读操作也高度可用，因为有 100 个不同的位置可供读取。但它对写操作并不高度可用，因为只要 100 台机器中有一台不可用，新的写入就无法完成。

**两个问题。** 大体而言，存储系统必须应对两类可靠性威胁。

- **操作被中断。** 在一系列相关更新进行到一半时发生崩溃或断电，可能使已存数据处于不一致状态。例如，假设用户要求操作系统把一个文件从一个目录移到另一个目录：`> mv drafts/really-important.doc final/really-important.doc`。正如我们在第 13 章讨论过的，这样一次移动可能涉及许多底层操作：写 drafts 目录文件以删除 really-important.doc，更新 drafts 目录的最后修改时间，扩展 final 目录的文件以纳入另一个存储块来容纳 really-important.doc 的新目录项，把新的目录项写入该目录文件，更新文件系统的空闲空间位图以记录新分配的块现已占用，以及更新 final 目录的大小和最后修改时间。假设系统的电源在 drafts 目录的更新已存入非易失存储、而 final 目录的更新尚未存入时失效；在这种情况下，文件 really-important.doc 可能丢失。或者，假设操作系统在更新完 drafts 与 final 目录之后、更新文件系统空闲空间位图之前崩溃；在这种情况下，文件系统仍会把 final 目录中的新块视为空闲，并可能把这个块分配给另一个文件。于是存储设备上就会出现一个同时属于两个文件的块，针对其中一个文件的更新就可能破坏另一个文件的内容。

- **已存数据丢失。** 非易失存储介质的故障可能使先前存入的数据消失或损坏。这类故障可能影响单个块、整个存储设备，甚至成组的存储设备。例如，某个磁盘扇区若被污染驱动器腔体的颗粒划伤，就可能丢失；某个闪存单元若因邻近单元被大量读取而电荷受到扰动，就可能失去其内容；某块磁盘驱动器可能因轴承磨损使盘片振动过大、无法成功读写而彻底失效；而一组驱动器也可能因数据中心的一场火烧毁一排存储服务器而全部损失。

**两个方案。** 幸运的是，系统设计者已经针对这些问题发展出两套强有力的解决方案，本章余下的部分将分别讨论。

- **用事务实现原子更新。** 当系统需要对非易失存储做若干相关更新时，它可能希望状态被原子地修改：即使发生崩溃，状态也应当反映出全部更新或全部没有更新。事务（transaction）是提供非易失存储原子更新的基本技术。事务实现和使用起来都很简单，性能往往也不亚于、甚至优于临时拼凑的（ad hoc）方案。过去二十年中广泛使用的绝大多数文件系统都在内部使用了事务，许多应用程序也自行实现事务，以保持其持久状态一致。

- **用冗余应对介质故障。** 为应对数据丢失和损坏，存储系统使用若干形式的冗余，例如用校验和检测损坏的存储，用复制存储从丢失或损坏的扇区、磁盘中恢复。以可接受的低成本实现足够的冗余可能相当复杂。例如，一个广泛使用、模型简单的独立磁盘冗余阵列（RAID），所描绘的可靠性图景过于乐观，误差可达数个数量级。现代存储系统往往使用多级校验和（例如既在存储设备硬件中、又在文件系统软件中），包含足以挺过两次或更多硬件故障的冗余（例如为文件保留三份副本，或在 RAID 中使用两块奇偶校验盘），并依靠软件在故障发生后迅速检测、迅速修复（例如定期尝试读取全部已存数据的后台进程，以及设备失效时并行执行恢复的算法）。未能恰当运用这些技术的系统，其可靠性可能远低于预期。

## 14.1　事务：原子更新

当系统对非易失存储做了若干更新之后发生崩溃，其中一些更新可能已经存入并在崩溃中幸存，另一些则未必。由于崩溃可能毫无预警地发生，存储系统和应用程序的构造必须保证：无论崩溃发生在什么时候，系统的非易失存储都留在某种合理状态。

这个问题出现在许多场合。例如，若你在为一批应用程序安装更新时发生崩溃，恢复之后你希望自己能使用旧版本或新版本，而不是面对一堆互不兼容的程序拼成的大杂烩。例如，若你在把一个子目录从一个位置移到另一个位置时发生崩溃，恢复之后你希望看到数据在其中一个位置；如果这个子目录因为一次不合时宜的崩溃而消失，你就会（有理由地）对操作系统设计者感到恼火。最后，若银行正在把 100 美元从 Alice 的账户转到 Bob 的账户时发生崩溃，它希望确保：恢复之后，要么资金仍在 Alice 的账户里、且记录显示这笔转账尚待完成，要么资金已在 Bob 的账户里、且记录显示这笔转账已经完成。

这个问题与并发中的临界区问题颇为相似。两者都是要做若干更新，并且都不希望任何人观察到中间的不一致状态。此外，在前一种情形中我们无法控制其他线程何时来访问状态，在后一种情形中我们无法控制崩溃何时发生——我们必须设计出一种结构化的解决方案，对任何可能的执行都成立。解法也类似：我们希望让这组更新具有原子性。不过，由于我们处理的是非易失存储而非主存，实现原子性的技术在若干重要方面有所不同。

事务把原子更新的概念从内存扩展到稳定存储，使系统能够原子地更新多个持久数据结构。

### 14.1.1　临时性方案

直到 20 世纪 90 年代中期，许多文件系统都使用临时性的（ad hoc）办法来解决一致地更新多个磁盘上数据结构的问题。

例如，Unix 快速文件系统（FFS）会谨慎控制更新发往磁盘的顺序，使得若在一组更新进行到一半时发生崩溃，恢复期间扫描磁盘就能找出并修复不一致的数据结构。以创建新文件为例，FFS 会先更新空闲索引节点位图（free-inode bitmap），表明原先空闲的索引节点现已占用。在确认这项更新已落到磁盘上之后，它才初始化新文件的索引节点，清除所有直接、间接、双重间接及其他指针，把文件长度设为 0，并设置文件的所有者和访问控制列表。最后，一旦索引节点的更新安全落盘，文件系统才更新目录，使之包含新创建文件的目录项，把文件名映射到其索引节点。

若运行 FFS 的系统崩溃，重启时它会用一个名为 fsck（file system check，文件系统检查）的程序扫描文件系统的全部元数据（例如所有索引节点、所有目录和所有空闲空间位图），以确保所有元数据项彼此一致。举例来说，若 fsck 发现某个索引节点在空闲索引节点位图中被标记为*已分配*，却不出现在任何目录项中，它就可以推断：这个索引节点属于崩溃发生时正在创建（或正在删除）的某个文件。既然创建尚未完成、或删除已经开始，fsck 就可以把这个索引节点标记为空闲，从而撤销这个部分完成的创建（或完成这个部分完成的删除）。

其他文件系统操作也采用类似的推理。

这种“谨慎安排操作顺序、配合扫描与修复磁盘上数据结构”的做法一直很流行，直到 20 世纪 90 年代才基本被弃用。具体说来，这种做法有三个显著问题：

+ **推理复杂。** 这类似于试图只用原子读写来解决多线程同步问题：这种做法要求仔细推理所有可能的操作和所有可能的失效情形，以确保系统总能被恢复到一致状态。

+ **更新缓慢。** 为确保更新以某种便于分析系统状态的顺序存入，文件系统不得不在相互依赖的操作之间插入同步操作或屏障，从而减少了发往存储设备的请求流中的流水线程度或并行度。例如，在上面创建文件的例子中，为确保各项更新按要求的顺序落到磁盘，系统可能要耗费磁盘完整的三圈旋转来更新三个磁盘上的数据结构，即使这些数据结构彼此可能相距很近。

+ **恢复极慢。** 机器在崩溃后重启时，必须扫描其所有磁盘以查找不一致的元数据结构。在 20 世纪 70 年代和 80 年代，扫描大多数服务器磁盘上的数据结构只需几秒或几分钟。然而到 20 世纪 90 年代，对于拥有许多磁盘的大型服务器，这种扫描可能要花几十分钟到几个小时，而技术趋势表明扫描时间还会迅速变得更糟。

尽管前两点是这种做法的显著缺点，真正让大多数文件系统无法再依赖谨慎排序与 fsck 的却是第三点。20 世纪 80 年代末以来新建的文件系统几乎无一例外地采用了其他技术——主要是本节余下部分讨论的各种形式的事务。

::: tip fsck 仍在服役
尽管如今很少有文件系统在崩溃恢复时依赖扫描磁盘，但当磁盘上的数据结构因其他原因（例如软件缺陷或存储设备故障）而损坏时，fsck 及其他类似程序常常仍被当作“应急修复”手段使用。
:::

**应用层的做法。** 尽管现代文件系统往往在内部使用事务，一些标准的文件系统 API（如 POSIX API）却只提供较弱的抽象，迫使应用程序在想原子地施加一组更新时自行设法。许多程序使用应用层事务，但另一些程序仍沿用临时性方案。

例如，假设用户编辑了一个文本文件的若干处，然后想保存更新后的文档。这些编辑可能在文档的多个位置插入了文字，在另一些位置删除了文字，并把其余文字前移或后移——即使是在文档前部做一处很小的插入或删除，也可能波及文件的其余部分。

如果文本编辑器应用程序只是用内存中更新后的文件覆盖现有文件，一次不合时宜的崩溃就可能使文件处于无法理解的状态。操作系统和磁盘调度器可以选择任意顺序把更新后的块发往非易失存储，因此崩溃之后，文件可能是新旧块的任意混合，有些段落重复出现，有些段落则完全缺失。

为避免这个问题，文本编辑器可以利用 POSIX `rename` 操作的语义：它把名为 sourceName 的文件改名为 targetName。POSIX 保证：若名为 targetName 的文件已经存在，则 `rename` 从让 targetName 指向旧文件转为让它指向新文件的过程是原子的。（这一原子性保证可以由文件系统内部的事务提供，也可以通过临时性手段提供。）

因此，要更新一个已存在的文件 design.txt，文本编辑器先把更新写入一个新文件，例如临时文件 `#design.txt#`。然后它重命名这个临时文件，从而原子地替换先前存储的文件。

### 14.1.2　事务抽象

事务提供了一种原子地更新多份持久状态的办法。

例如，假设你正在更新一个网站，想把 `/server/live` 中现有的文档集合替换为你在 `/development/ready` 中新建的一组文档。你不希望用户在部分文档已更新、另一些尚未更新时看到中间步骤——他们可能遇到断掉的链接，也可能看到引用旧页面的新描述，或者反过来。像 Windows Vista 的 TxF（Transactional NTFS）这样的事务式文件系统提供了 API，让应用程序可以原子地施加所有这些更新，程序员可以写出图 14.2 那样的伪代码。

<div class="code-cap"><span class="code-label">图 14.2</span>使用事务式文件系统的伪代码。</div>

```c
ResultCode publish() {
    transactionID = beginTransaction();
    foreach file f in /development/ready that is not in /server/live {
        error = move f from /development/ready to /server/live;
        if (error) {
            rollbackTransaction(transactionID);
            return ROLLED_BACK;
        }
    }

    foreach file f in /server/live that is not in /development/ready {
        error = delete f;
        if (error) {
            rollbackTransaction(transactionID);
            return ROLLED_BACK;
        }
    }

    foreach file f in /development/ready that differs from /server/live {
        error = move f from /development/ready to /server/live;
        if (error) {
            rollbackTransaction(transactionID);
            return ROLLED_BACK;
        }
    }
    commitTransaction(transactionID);
    return COMMITTED;
}
```

注意，事务可以以两种方式之一结束：它可以*提交*（commit），即其全部更新都发生；也可以*回滚*（roll back），即其更新一个都不发生。

在这里，若事务提交，我们就能保证所有后续读取都会看到全部更新；而若它遇到错误并回滚，或在未提交也未回滚的情况下崩溃，那么事务之外的任何读取都看不到其中任何更新。

更准确地说，*事务*是一种执行一组更新的方式，同时提供以下*ACID 特性*：

- **原子性（Atomicity）。** 更新是“全有或全无”的。若事务*提交*，事务中的全部更新生效。若事务*回滚*，事务中的任何更新都不起作用。在上面的网站更新例子中，把更新放在一个事务里执行，就能保证：每一次更新只有在全部更新都已存储且可读时，才被存储且可读。

- **一致性（Consistency）。** 事务把系统从一个合法状态转移到另一个合法状态。系统状态上的不变式可以假定在事务开始时成立，并且必须在事务提交时成立。在上面的例子中，借助事务，我们可以维持这样的不变式：服务器上从一个文档指向另一个文档的每条链接都引用一个有效文件。

- **隔离性（Isolation）。** 每个事务看上去都是独自执行的，不受其他进行中事务的影响。即使多个事务并发执行，对任意一对事务 T 和 T′ 而言，看上去要么是 T 完全先于 T′ 执行，要么相反。把网站更新放在事务中执行，我们就能保证：每一次从网站读取的事务，看到的要么是旧的一组网页，要么是新的一组，而不是两者的混合。当然，若每次单独读取某个对象都处于自己的事务中，那么为拼装某个网页及其所含元素而进行的一系列读取，就仍可能看到旧网页与新元素的混合。如果把网络协议改成允许浏览器在一个事务中取回页面及其元素，我们就能保证用户看到的要么是旧页面及其元素，要么是新的。

- **持久性（Durability）。** 已提交事务对状态的修改必须在崩溃中幸存。事务一旦提交，要改变它产生的状态，唯一的办法就是另一个事务。在我们的网站更新例子中，系统在事务的全部更新都安全存入持久存储之前，绝不能从 `commitTransaction()` 调用返回。

**事务与临界区。** ACID 特性与临界区的性质密切相关。临界区提供了一种原子、一致、隔离但不持久地更新状态的办法。加入持久性要求，会显著改变我们实现原子更新的方式。

::: tip 术语之战
在操作系统中，我们以两种方式使用“一致性”（consistency）一词。在临界区和事务的语境中，“一致性”指的是系统的不变式得到维持（例如“我的数据结构一致吗？”）。在分布式存储机器和分布式系统的语境中，“一致性”指的是内存模型——更新以何种顺序对读取可见（例如“我的系统在不同高速缓存上的读取是顺序一致的吗？”）。

在可能引起混淆之处，我们将使用*事务一致性*或*内存模型一致性*这两个说法。
:::

### 14.1.3　实现事务

实现事务的难点在于：我们希望一组相关的写具有原子性，但对于磁盘和闪存这类持久存储硬件，原子操作只是单个扇区或单个页的写。因此，我们必须设计出一种办法，让一组相关的写在一次单扇区写发生时生效。

若系统只是开始原地更新数据结构，那么它在一组更新进行到一半时就容易受到崩溃的伤害：系统既没有完整的一套旧数据（可用于回滚），也没有完整的一套新数据（可用于提交），于是一次不合时宜的崩溃就可能迫使系统违反原子性。

作为替代，事务式系统可以把一个事务的全部*意图*（intentions）——即事务提交时将要做的更新——持久地存放在持久存储的某个独立位置。只有当全部意图都已存入、且事务提交之后，系统才应开始覆盖目标数据结构；若覆盖过程在中途被打断，那么在恢复时，系统可以利用持久存储的意图完成该事务的更新。

#### 重做日志

实现事务的一种常见而非常通用的方法是重做日志（redo logging）。*重做日志*用一份持久日志记录意图，并按四个阶段执行事务：

+ **准备（Prepare）。** 把所有计划中的更新追加到日志。这一步可以在事务开始提交时一次做完，也可以随时间逐步进行，即随着事务的执行把新的更新不断追加到日志。关键在于：在进入下一步之前，全部更新都必须已安全地存入日志。

+ **提交（Commit）。** 向日志追加一条提交记录，表明事务已经提交。当然，事务也可能回滚而不是提交。在这种情况下，可以在日志中写入一条回滚记录，表明该事务已被放弃。不过写不写回滚记录是可选的，因为只有当日志中出现提交记录时，事务才会被视为已提交。

+ **写回（Write-back）。** 一旦提交记录在日志中持久化，事务的全部更新就可以写入各自的目标位置，用新值替换旧值。

+ **垃圾收集（Garbage collect）。** 一旦事务的写回完成，它在日志中的记录就可以被垃圾收集。

步骤 2 中存放提交记录的那个扇区被成功存储的那一刻，就是*原子提交*（atomic commit）：在这一刻之前，事务可以安全地回滚；在这一刻之后，事务必须生效。

**恢复。** 如果系统在事务执行到一半时崩溃，它必须在处理新请求之前执行一段恢复例程。对重做日志而言，恢复例程很简单：顺序扫描日志，对每一类记录采取相应动作：

+ **某事务的更新记录。** 把这条记录加入为该事务计划执行的更新列表。

+ **某事务的提交记录。** 把该事务记录在日志中的全部更新写回到各自的目标位置。

+ **某事务的回滚记录。** 丢弃为该事务计划执行的更新列表。

到达日志末尾时，恢复过程丢弃那些在日志中没有提交记录的事务的所有更新记录。

**实现细节。** 有几项具体的技术与观察结论，对于让基于重做日志的事务获得良好性能与可靠性至关重要。

- **记录并发事务。** 尽管上例只展示了一个事务，但多个事务可能同时执行。在这种情形下，日志中的每条记录都必须标明它属于哪个事务。

- **异步写回。** 事务的第 3 步（*写回*）可以是异步的——一旦更新和提交都进入日志，写回就可以推迟到方便或高效的时候再执行。这种灵活性带来两点好处。第一，它使从事务调用提交到该调用返回之间的延迟最小：提交一旦追加到顺序日志，调用就可以返回。第二，写回的吞吐量更高，因为磁盘调度器可以成大批量地处理更新。有两件事限制了写回的最大延迟，但两者的约束都相对宽松。第一，写回延迟越大，意味着崩溃恢复可能耗时越长，因为可能有更多更新需要从日志中读出并应用。第二，日志要占用持久存储空间，而在某些情况下这一空间可能是受限的。

- **重复写回没问题。** 恢复期间写回的某些更新，可能在此次崩溃之前就已经写回过。例如在图 14.4 中，从持久日志头指针到易失日志头指针之间的所有记录都已写回，而两个日志头指针之间的部分记录可能也已写回。从重做日志中多次重新应用同一更新是没有问题的，因为这些更新是（而且必须是）*幂等的*（idempotent）——无论执行一次还是多次，效果都相同。例如，若某条日志记录说“把 42 写入 74 号扇区的每个字节”，那么这个值写入 74 号扇区一次、两次还是一百次都无关紧要。反过来，重做日志系统不能允许非幂等的记录，例如“把 74 号扇区每个字节的值加 42”。

- **恢复可以重启。** 如果恢复过程中又发生一次崩溃会怎样？系统重启后，只是重新开始恢复。日志中会被发现同样那串针对已提交事务的更新，同样那些写回会被发出。其中一些写回可能在此前那次崩溃之前、或在某次更早的恢复过程中已经完成，但重复执行它们不会带来任何问题。

- **垃圾收集的约束。** 一旦某个已提交事务的写回完成并持久存储，它在日志中占用的空间就可以回收。为具体起见，图 14.4 画出了一个事务日志，其中有一段正在使用的区域，有一段因只包含写回已完成的事务的记录而不再需要的区域，还有一段空闲区域。在这个例子中，系统的易失内存维护着指向日志头部和尾部的指针；新的事务记录被追加到日志尾部并缓存在易失内存中；一个写回进程异步地把已提交事务待完成的写回写入它们在持久存储中的最终位置；一个垃圾收集进程周期性地推进持久日志头指针，使恢复过程至少可以跳过一部分写回已完成的事务。

- **顺序至关重要。** 必须确保：事务的全部更新先于提交记录进入磁盘上的日志，提交记录先于任何写回进入磁盘，而全部写回先于该事务的日志记录被垃圾收集。在 Linux 中，应用程序可以调用 `sync()` 或 `fsync()`，要求操作系统把缓冲的写强制刷到磁盘。这些调用只有在被更新的块已安全存储之后才返回。在操作系统内部，一个请求可以带上 `BIO_RW_BARRIER` 标记，它告诉设备驱动程序和存储硬件：在带标记的请求被存储之前，必须确保之前的所有写都已存储，而其后的写一个都不得存储。

::: tip 撤销日志
尽管事务常常用重做日志来实现——把更新和提交写入日志，然后再把更新复制到它们的最终位置——但事务也可以用*撤销日志*（undo logging）来实现。

要更新一个对象，事务先把该对象的*旧*版本写入日志，然后把新版本写入它的最终存储位置。事务完成时，它只需把*提交*追加到日志。反之，若事务回滚，则通过把旧的对象版本写回其存储位置来撤销这些更新。

恢复过程对它在日志中发现的已提交事务不采取任何动作，但对未提交的事务则通过重写日志中保存的原始对象版本来撤销它们。

撤销日志允许在对象更新产生时就把它送往最终存储位置，但要求在事务提交之前这些更新必须已持久存储。这种模式与原地更新的做法相似，因此在某些情况下，给遗留系统加上撤销日志可能比加重做日志更容易。另一方面，对于磁盘这类顺序带宽远胜随机 I/O 性能的存储系统，撤销日志在事务提交之前可能需要更多的随机 I/O（有损延迟），而且由于它立即写入每个事务的更新，也就放弃了把大量事务更新成批写入、从而改善磁头调度的机会。

*撤销/重做日志*（undo/redo logging）在日志中同时保存对象的旧版本和新版本。这种组合使得被更新的对象可以在任何方便的时候写入最终存储位置，无论在事务提交之前还是之后。若事务回滚，任何被修改的对象都可以恢复到正确状态；若系统崩溃，任何已提交事务的更新都可以重做，任何未提交事务的更新都可以撤销。
:::

**重访隔离与并发。** 重做日志提供了一种让多项更新原子地持久化的机制，但如果有并发事务在共享状态上运行，我们还必须确保隔离性——每个事务看上去都必须单独执行，不受其他事务干扰。

在事务之间实现隔离的一种常见方法是*两阶段加锁*（two-phase locking），它把事务分成两个阶段。在*扩张*阶段，可以获取锁但不能释放锁；接着在*收缩*阶段，可以释放锁但不能获取锁。就事务而言，由于我们既要隔离性又要持久性，第二个阶段必须等到事务提交或回滚之后，这样其他事务就不会看到后来消失的更新。

正如我们在第 6 章讨论过的，两阶段加锁能保证一种很强的隔离性，称为可串行化。事务之间的*可串行化*（serializability）保证：程序的任何一次执行，其结果都等价于按某种顺序逐个处理事务的一次执行。因此，即使多个事务并发执行，它们能产生的结果也仅限于它们按某种顺序逐个执行时可能产生的结果。

尽管以任意顺序获取多把锁通常有死锁的危险，事务却提供了一个简单的解决办法：若一组事务发生死锁，可以强制其中一个或多个事务回滚、释放它们的锁，并在稍后重新开始。

::: tip 多版本并发控制
用锁来保证事务隔离性的另一种替代方案，是用多版本并发控制来保证。在*多版本并发控制*（multiversion concurrency control）中，对对象 x 的每次写都创建 x 的一个新版本，系统保留 x 的多个版本，并把每次读引向 x 的某个特定版本。通过保留对象的多个版本，系统可以让事务 A 读取一个已被事务 B 覆盖的 x 版本，即使 B 在串行化顺序上需要排在 A 之后。

有若干种多版本并发控制算法能够保证可串行化。一种简单的算法是多版本时间戳排序（multiversion timestamp ordering，MVTO）。MVTO 处理并发事务、保证可串行化，从不阻塞事务的读或写，但若它发现某个较晚事务的读（按 MVTO 正在实施的串行化调度）发生在某个较早事务（按串行化顺序）的写之前、因而没有观察到该写，就可能让事务回滚。

MVTO 为每个事务 T 分配一个逻辑时间戳。当 T 写对象 x 时，MVTO 创建 x 的一个新版本，并用 T 的时间戳 $t_{T}$ 标记它；当 T 读对象 y 时，MVTO 返回 y 的版本 $y_{v}$，它是在不超过 T 的时间戳的版本中时间戳最高的那个；MVTO 还会记录 $y_{v}$ 已被时间戳为 $t_{T}$ 的事务读过。最后，当 T 试图提交时，MVTO 会阻塞该提交，直到所有时间戳更小的事务都已提交或中止。

在三种情况下，MVTO 会让事务回滚，而不允许它提交。第一，若 MVTO 中止了某个事务，它会删除该事务写入的对象版本，并使所有读过这些版本的事务回滚。注意，读过某个版本的事务，其时间戳必定高于写该版本的事务，因此不需要让任何已提交事务回滚。

第二，若事务 T 写某个对象，而该对象已被较晚的事务 T′ 读过，且 T′ 观察到的是紧接 T 的写之前的那个版本，MVTO 就让 T 回滚。这样做的理由是：如果 T 提交，T′ 的读就必须返回 T 的写，但事实并非如此。

第三，若 MVTO 垃圾收集了旧版本，而事务 T 读取某个对象，该对象由较早事务所做的最后一次写已被垃圾收集，那么 MVTO 就让 T 回滚。
:::

::: tip 放宽隔离性
本书关注的是可串行化这一既强又相对简单的隔离要求：无论并发程度多高，系统都必须保证程序的任何一次执行结果都等价于按某个顺序逐个处理事务的一次执行。然而，强的隔离要求有时会迫使事务阻塞（例如在等待获取锁时）或回滚（例如在修复死锁、或在多版本并发控制下遇到“迟写”时）。

放宽隔离要求可以减少事务必须阻塞或回滚的情形，从而有效地允许更高的并发度。代价当然是对并发程序进行推理的复杂度可能上升，但已有若干种放宽的隔离语义被证明足够强，因而得到广泛使用。

例如，*快照隔离*（snapshot isolation）要求每个事务的读看上去都来自事务开始时对系统已提交数据所做的一份快照。每个事务的更新都被缓冲，直到事务提交时才由系统检查该事务的全部更新是否存在*写-写冲突*（write-write conflict）。若事务 T 在时刻 $t_(\text{start})$ 从快照中读到对象 o 并试图在时刻 $t_(\text{commit})$ 提交，而另一个事务 T′ 在 T 于 $t_(\text{start})$ 的读与 T 于 $t_(\text{commit})$ 的提交尝试之间提交了对 o 的更新，就发生了写-写冲突。若在 T 正要提交的任何对象上检测到写-写冲突，T 就回滚。

快照隔离弱于可串行化，因为每个事务的读在逻辑上发生于一个时刻，而它的写在逻辑上发生于另一个时刻。这种分离使得例如*写偏斜异常*（write skew anomaly）成为可能：一个事务读对象 x 而更新对象 y，一个并发事务读对象 y 而更新对象 x。若 x 与 y 之间存在某种约束，这一约束此时就可能被违反。例如，假设 x 与 y 表示两位经理分别分配给你做两项任务的工时，且约束为 $x + y \le 40$。经理 1 可能读到 $x = 15$、$y = 15$，试图再给任务 x 分配 10 小时的工作，并验证 $x + y = 25 + 15 \le 40$。与此同时，经理 2 可能读到 $x = 15$、$y = 15$，试图再给任务 y 分配 10 小时的工作，验证 $x + y = 15 + 25 \le 40$，并成功提交该更新，使 $y = 25$。最后，经理 1 也可能成功提交它的更新，使 $x = 25$，从而毁掉你的周末。
:::

**重做日志的性能。** 听起来重做日志比起简单地原地更新数据会带来显著的性能损失：重做日志把每次更新写两遍——先写日志，再写到最终存储位置。

情况并没有最初看上去那么糟。重做日志可以有极好的性能——常常优于原地更新——尤其是对小量写。有四个因素使重做日志得以高效实现：

- **日志更新是顺序的。** 由于日志更新是顺序的，追加到日志很快。对旋转磁盘，一旦写开始，大量更新可以作为一个顺序流写出，既不需要寻道，也没有旋转延迟。许多高性能系统专门拿出一块独立的磁盘用于记日志，使日志追加永远不需要寻道。对闪存，顺序更新通常明显快于随机更新，尽管优势没有这么显著。

- **写回是异步的。** 由于写回可以推迟到事务提交之后的某个时间，使用重做日志的事务可以有良好的响应时间（因为事务提交只需向日志追加一条提交记录），也可以有良好的吞吐量（因为成批的写回比必须立即发生的单次写或小批写调度起来更高效）。

- **所需的屏障或同步写更少。** 一些系统通过仔细安排数据结构更新的顺序来避免使用事务，以保证一旦发生崩溃，恢复过程能够扫描、识别并修复不一致的数据结构。然而这些技术往往需要大量屏障或同步写操作，从而减少了流水化或高效调度更新的机会。相比之下，事务需要的屏障相对很少：一次在更新已记入日志之后、提交记入日志之前；一次在提交记入日志之后、但事务被报告为成功之前（也在写回开始之前）；还有一次在事务的写回完成之后、但事务的日志项被垃圾收集之前。

- **成组提交。** *成组提交*（group commit）能进一步提高事务性能。成组提交把一组事务提交合并为一次日志写，以分摊发起写操作的开销（例如寻道与旋转延迟）。成组提交技术还可用来减少执行一组事务所需的屏障或同步操作次数。

::: info 例
**小量写事务的性能。** 假设你有一块 1 TB 的磁盘，每 10 毫秒旋转一圈，内圈磁道的最大持续盘面传输速率为 50 MB/s、外圈为 100 MB/s，平均寻道时间 5 毫秒、最小寻道时间 0.5 毫秒、最大寻道时间 10 毫秒。

考虑更新随机选取的 100 个 512 字节扇区；假定为安全起见这些更新必须有序（例如更新 i 必须在更新 i + 1 被应用之前就已写入磁盘）。

比较用简单的原地更新方式、以及用重做日志实现的事务完成这些更新的总时间。
:::

::: warning 答
采用简单的原地更新方式时，我们需要用 FIFO 调度来确保更新按序到达磁盘，因此每次更新的时间约为：

$$
\text{每次更新用时} &= \text{平均寻道时间} + 0.5 \text{旋转时间} + \text{传输时间} \
&= 5 \text{ms} + 5 \text{ms} + \text{传输时间}
$$

传输时间至多为 512/(50 × 10<sup>6</sup>) 秒，与其他各项相比可以忽略。于是，原地更新每请求约 **10 毫秒**，100 个请求约 **1 秒**。

对事务方式，我们先把这 100 次写追加到日志。保守起见，假定每次更新占用 2 个扇区（一个存数据，另一个存元数据，标明事务号和磁盘上的目标扇区）。于是，假定请求到达时磁头位于随机位置，记录这些请求所需的时间为：

$$
\text{写日志用时} &= \text{平均寻道时间} + 0.5 \text{旋转时间} + \text{传输时间} \
&= 5 \text{ms} + 5 \text{ms} + \text{传输时间} \
&= 5 \text{ms} + 5 \text{ms} + (200 \times 512)/(100 \times 10^{6}) \text{s} \
&= 11.0 \text{ms}
$$

接下来，我们需要把提交记录追加到该事务。如果磁盘硬件支持用屏障指令强制多个进行中的请求排序，操作系统可以把这一请求与那 100 次写一并发出。这里我们保守一些，假定系统要等事务主体中的那 100 次写都进入日志之后才发出提交的写。这样我们很可能必须等磁盘整整转一圈才能完成提交：*10 毫秒*。

最后，我们需要把这 100 次写写到它们在磁盘上的目标位置。与原地更新的情形不同，这里顺序无关紧要，因此可以更高效地调度并写出它们。估计这一时间需要工程判断，不同的人很可能给出不同的估计。在本例中，我们假定磁盘使用最短服务时间优先（SSTF）调度的一种变体：调度器考察下一条最近磁道上的 4 个请求，从中挑选从磁头当前位置算起预测（寻道时间 + 旋转延迟）最短的一个。由于调度器可以从 4 个请求中挑选，我们估计平均旋转延迟为四分之一圈，即 2.5 毫秒。这个估计可能偏保守，因为它忽略了一点：请求 i 总会把 4 个候选请求中若留到请求 i + 1 时在旋转上最远的那个排除掉。由于我们最初有 100 个请求，而且只考察最近磁道上的 4 个请求，最远的寻道应跨过磁盘的大约 4%，而到所考察那一组成员之一的平均寻道约为 2%。我们估计跨过磁盘 2% 到 4% 的寻道代价是最小寻道时间的两倍：1 毫秒。

把这些写回时间的估计合在一起，100 个扇区的写回大约需要：

$$
\text{每请求写回时间} &= \text{寻道时间} + \text{旋转延迟} \
&= 1.0 \text{ms} + 2.5 \text{ms} \
&= 3.5 \text{ms}
$$

于是 100 个请求共 350 毫秒。

把记日志、提交和写回的时间相加，得到：

$$
\text{总写入时间} &= \text{记日志时间} + \text{提交时间} + \text{写回时间} \
&= 11.0 \text{ms} + 10 \text{ms} + 350 \text{ms} \
&= 371 \text{ms}
$$

尽管它把数据写了两遍，而且提供了更强的原子更新语义，事务方式还是快了将近三倍。□
:::

::: info 例
对同样的两种方式，比较从发出这些请求的调用开始、到该调用因全部更新均已持久化而可以安全返回之间的响应时间延迟。
:::

::: warning 答
**原地更新**的用时与上面相同：**1 秒**。**事务方式**的用时是前两步——把更新记入日志、再把提交记入日志——之和：$10.24 \text{ms} + 10 \text{ms} = 20.24 \text{ms}$。□
:::

尽管使用重做日志的小量写实际上可能比原地更新方式获得性能优势，大量写却可能遭受显著的损失。

::: info 例
**大量写事务的性能。** 考虑与上例相同的磁盘和方式，比较 100 次写的总时间，但现在假定这 100 次写每个都更新一段随机选取的 1 MB 连续扇区。
:::

::: warning 答
对原地更新方式，每次更新的时间约为 **平均寻道时间 + 0.5 旋转时间 + 传输时间 = 5 毫秒 + 5 毫秒 + 传输时间**。我们假定平均传输的带宽为 75 MB/s——介于内圈与外圈磁道 50 MB/s 和 100 MB/s 的传输速率之间。于是估计平均传输时间为 100 MB/75 MB/s = 1.333 秒，从而每请求为 **0.005 秒 + 0.005 秒 + 1.333 秒 = 1.343 秒**，100 个请求为 **134.3 秒**。

对事务方式，我们的时间将是 **记日志时间 + 提交时间 + 写回时间**。

记日志方面，我们假定采用相当高效的元数据编码，使一次 100 MB 顺序更新的元数据大小与数据相比可以忽略。于是记录数据将耗时 **寻道时间 + 旋转延迟 + 传输时间 = 5 毫秒 + 5 毫秒 + 100 × 100 MB/100 MB/s = 0.005 秒 + 0.005 秒 + 100 秒 ≈ 100 秒**。

写提交记录又增加 10 毫秒，与上例相同。

最后，与上面一样，执行写回 **估计的调度寻道时间 + 估计的调度延迟 + 传输时间 = 1.0 毫秒 + 2.5 毫秒 + 100 MB/75 MB/s**，从而每请求共 **1.337 秒**，100 个请求为 **133.7 秒**。

把数据记日志、提交与写回的时间相加，**事务方式约需 233 秒**，而**原地更新方式约需 134 秒**。在这种情况下，事务确实带来了可观的代价，几乎使处理这些更新的总时间翻了一倍。□
:::

::: info 例
现在比较从发出这 100 次写的调用开始、到它可以安全返回之间的延迟。
:::

::: warning 答
在原地更新方式下，我们只有在全部写完之后才能返回；而在事务方式下，提交一完成就可以返回。因此两者相差无几：**原地更新 134 秒**，**事务 100 秒**。□
:::

减少大量写的事务开销的一个办法是增加一层间接：把大的数据对象写到磁盘的空闲区域，而不是写进循环日志。这样，日志中的更新只需是对该数据的引用，而不是数据本身。最后，在事务提交之后，通过更新原数据结构中的指针、使其指向新数据来完成写回。

### 14.1.4　事务与文件系统

文件系统在更新多个数据结构时必须保持内部一致性。例如，FFS 这样的文件系统在创建新文件时，可能需要更新该文件的索引节点、空闲索引节点位图、父目录、父目录的索引节点以及空闲空间位图。若这样一组更新执行到一半时发生崩溃，文件系统就可能处于不一致状态，比如说，新文件的索引节点已分配并初始化，却在父目录中没有对应的条目。

正如 14.1.1 节所讨论的，一些早期文件系统采用了临时凑合的方案，例如精心安排一系列写操作的顺序，以及在崩溃后重启时扫描磁盘、检测并修复不一致。然而这些方法存在复杂度高、更新慢的问题，而且——随着磁盘容量增长——崩溃恢复还慢得令人无法接受。

为解决这些问题，大多数现代文件系统使用事务。

**传统文件系统。** 通过*日志*（journaling）或*全日志*（logging），可以为 FFS、NTFS 这类原地更新的传统文件系统加上事务。

- **日志。** 日志文件系统通过事务来更新系统的元数据，但对用户文件的内容仍做原地更新。通过保护元数据更新，这类系统保证了其持久数据结构（例如对索引节点、位图、目录和间接块的更新）的一致性。日志文件系统先把元数据更新写入重做日志，然后提交，最后再写回它们最终所在的存储位置。对普通文件（非目录文件）内容的更新不记入日志，而是原地施加。这样就避免了把文件更新写两遍——对大的更新而言，写两遍可能代价高昂。另一方面，原地更新文件内容意味着日志文件系统在程序更新文件时提供的保证很少：若更新进行到一半时发生崩溃，文件可能最终处于不一致状态，一部分块已更新而另一部分没有。若使用日志文件系统的程序需要原子的多块更新，就得自己提供这种保证。

- **全日志。** 全日志文件系统则把所有对磁盘的更新——元数据和数据都包括——统统纳入事务。

今天，日志文件系统已很常见：微软的 NTFS、苹果的 HFS+，以及 Linux 的 XFS、JFS 和 ReiserFS 都使用日志；Linux 的 ext3 和 ext4 在默认配置下也使用日志。

全日志文件系统同样广泛可用，至少对 Linux 而言如此。特别是 Linux 的 ext3 和 ext4 文件系统可以配置成使用日志或全日志。

**写时复制文件系统。** 像开源系统 ZFS 这样的写时复制（copy-on-write）文件系统，从设计之初就以事务为目标。它们不原地覆盖数据；更新根索引节点或 ZFS 的 uberblock 是一个原子动作，由它提交一整组更新。

- **批量更新。** ZFS 不是逐条施加每个更新，而是先缓冲若干秒的更新，再把它们作为一个原子组写入稳定存储。批量处理带来两点好处。第一，它使系统能够把许多小的随机写转化为少量大的顺序写，从而改善大多数存储设备的性能，包括单个磁盘、RAID（独立磁盘冗余阵列），甚至某些闪存设备。

- **意图日志。** ZFS 通常先累积几秒钟的写，再执行一次大的批量更新，但有些应用需要立即得到保证：它的更新已安全存储到非易失介质上。例如，字处理软件的用户保存文件时，程序可能调用 `fsync()`，告诉文件系统确保更新已存入磁盘。强迫用户为了保存文件等上几秒钟是不可接受的。ZFS 的解决办法是 ZFS 意图日志（ZIL），它实质上是一个重做日志。ZIL 是由 ZFS 块构成的链表，这些块中含有的更新已被强制写到磁盘、但其所在的批量更新可能尚未存储。文件系统挂载时会重放 ZIL。ZFS 在 ZIL 的实现中包含若干优化。第一，默认情况下写操作会被缓冲，并在其批量更新中提交，而不写入 ZIL；只有被显式强制写入磁盘的写才会进入 ZIL。第二，ZIL 可以放在独立的专用记日志设备上；这样我们就可以用快速设备（例如闪存）承载 ZIL，而用较慢的大容量设备（例如磁盘）构成主存储池；若没有提供独立的 ZIL 设备，ZFS 就用主块池来存放 ZIL。最后，小数据写的内容被直接包含在 ZIL 的块中，而较大的写则把内容写到单独的块、由 ZIL 引用这些块；这样，随后的批量提交只需更新元数据、指向磁盘上已有的副本，从而避免重写那些大块。

## 14.2　错误检测与纠正

由于数据存储硬件并不完美，存储系统必须设计得能够检测并纠正错误。存储系统采用分层的做法：

- 存储硬件用校验和与设备级检查检测出许多失效，并用纠错码纠正少量的损坏

- 存储系统用 RAID 体系结构提供冗余，以重构单个设备丢失的数据

- 许多较新的文件系统还包含额外的端到端正确性检查

这些技术必不可少。几乎所有持久存储设备都带有内部冗余，以便在可接受的误码率下实现高存储密度。仅靠这种内部冗余是不够的。面向重要数据的存储系统会为纠错增加额外的冗余；近十年开发的、稍有影响的文件系统里，很难找到不包含更高层校验和的。

这些技术虽然必不可少且广泛使用，但在设计与使用它们时存在一些重大陷阱。在讨论中，我们会指出那些若处理不慎就会大幅降低可靠性的问题。

本节余下部分考察持久存储的错误检测与纠正：先看单个存储设备，再看 RAID 复制如何帮助容忍单个存储设备的失效，最后看许多较新文件系统中的端到端错误检测。

### 14.2.1　存储设备失效与缓解

存储硬件不断挑战物理学、材料科学与制造工艺的极限，以最大化存储容量和性能。这些激进的设计几乎没有留下误差余量，因此制造缺陷、污染或磨损都可能使已存储的位丢失。

单个旋转磁盘和闪存设备表现出两类失效。第一，孤立的磁盘扇区或闪存页可能丢失已有数据，或者退化到无法存储新数据。第二，整个设备可能失效，使其所有扇区或页都无法访问。下面我们依次讨论这两类失效，以理解上层技术需要应对的问题。

#### 扇区与页失效

当磁盘上一个或多个扇区上的数据丢失、而磁盘其余部分仍正常工作，就发生了磁盘*扇区失效*（sector failure）。*闪存页失效*（page failure）与之类似，只是发生在闪存页上。

存储设备用两种技术来缓解扇区或页失效：纠错码与重映射。

::: tip 扇区或页失效的成因
对旋转磁盘，永久性扇区失效可由多种故障引起，例如磁性涂层上因污染物从表面剥落而形成的凹坑、磁头把污染物拖过表面而在涂层上划出的划痕，以及涂抹在磁盘表面某段扇区上的机油。

暂时性扇区故障是指扇区中存储的数据被损坏，但仍能向该扇区成功写入新数据并从其中读出。其成因包括写干扰（write interference），即对一个磁道的写扰动了邻近磁道上存储的位，以及“高飞写”（high fly write），即磁头离盘面太远，产生的磁场太弱，无法被准确读出。

对闪存，永久性页失效可由制造缺陷引起，也可由磨损引起——某个页经历大量写/擦除周期后就会失效。

暂时性闪存失效可由以下原因引起：（i）写干扰错误，即给一位充电时也使附近的位被充电；（ii）读干扰错误，即反复读一个页会改变邻近页所存储的值；（iii）过编程错误，即写一个单元时使用了过高的电压，可能导致读或写不正确；（iv）数据保持错误，即电荷随时间从闪存单元泄漏出去或泄漏进来，改变其值。反复写/擦除造成的磨损会使设备更容易出现数据保持错误。
:::

**缓解手段：纠错码。** *纠错码*（error correcting code）应对的是扇区或页中部分位已损坏的失效。设备存储数据时，会用额外的冗余对数据编码。此后若读某个扇区或页时有少量位损坏，硬件会自动纠正错误，读操作成功完成。若损坏范围更大，那么读操作很可能失败并返回错误码。被告知设备已丢失数据并不完美，但总比设备悄悄返回错误的数据要好。

制造商在存储空间开销与纠错能力之间做权衡，以达到所宣称的可接受的扇区或页失效率；该指标通常表示为在遇到一个不可读扇区或页之前预期可读出的位数。2011 年，磁盘与闪存所标称的*不可恢复读错误*（non-recoverable read error）率通常在每读出 $10^{14}$ 至 $10^{16}$ 位出现一个扇区/页错误之间。不可恢复读错误率有时也称为*误码率*（bit error rate）。

**缓解手段：重映射。** 磁盘和闪存在制造时就带有一定数量的备用扇区或页，这样即使出现若干永久性扇区或页失效，也能通过把失效的扇区或页重映射到好的扇区或页，使设备继续工作。在把硬件交付用户之前，制造商会扫描设备，重映射因制造缺陷造成的坏扇区或坏页。此后若检测到新的永久性失效，操作系统或设备固件可以把失效的扇区或页重映射到好的扇区或页。

**陷阱。** 尽管设备的不可恢复读错误率规格很有帮助，设计者仍须避免若干常见陷阱：

- **假定不可恢复读错误率可以忽略。** 存储设备标称的错误率听起来很漂亮，但以今天存储的巨大容量而言，这些错误率是不可忽略的。例如，若你完整读出一块误码率为每 $10^{14}$ 位一个扇区的 2 TB 磁盘，那么遇到至少一个错误的可能性可能超过 10%。

- **假定不可恢复读错误率是常数。** 尽管设备可能只给出一个数字作为其不可恢复读错误率，但许多因素会影响这类错误实际出现的速率。某台设备的实际误码率可能取决于它的负载（例如某些故障可能由设备活动引起）、它的使用年限（例如某些故障可能随设备老化而更易发生），甚至取决于它的具体工作负载（例如某些扇区或页中的故障可能由对邻近扇区或页的读或写引起）。

- **假定各次失效相互独立。** 错误可能在时间或空间上相关联：在一个扇区发现错误，可能使你更有可能在邻近扇区也发现错误，或者更有可能不久后在另一个扇区发现故障。

- **假定错误率是均匀的。** 不可恢复读错误的各种成因的相对贡献，可能因型号不同而不同，也可能因同一型号的不同代次或不同生产批次而不同。例如，某型号磁盘的许多扇区读错误可能由污染物损伤其记录表面引起，而另一型号的大多数错误可能由写干扰引起——对一个磁道的写扰动了邻近磁道上存储的数据。前者的错误率可能随时间上升，而后者的错误率可能随其写/读比例上升而上升。失效率甚至在不同个体设备之间也有差异。如果你部署若干台外观完全相同的磁盘，其中一些可能一年中出现几十次不可恢复读错误，而另一些则运行得毫无瑕疵。

::: info 例
**不可恢复读错误。** 假设你笔记本电脑上那块几乎写满的 500 GB 磁盘刚刚停止工作。幸运的是，你在一块 500 GB 的 USB 硬盘上有最近的完整备份，其不可恢复读错误率为每读出 $10^{14}$ 位一个扇区。估计在把数据恢复到替换用的笔记本磁盘时，成功读出整块 USB 备份盘的概率。
:::

::: warning 答
我们需要读出 500 GB，因此预期的失效次数为

$$
500 \text{GB} \times 8 \times 10^{9} \text{位/GB} \times 10^(-14) \text{错误/位} = 0.04
$$

至少遇到一次失效的概率可能比这个值略低（因为扫描整块磁盘时我们可能遇到多次失效），但看来至少有百分之几的可能性使恢复无法完全成功。

我们也可以用稍有不同的方式处理这个问题：把不可恢复读错误率理解为每一位都有 $10^(-14)$ 的概率出错，并且各次失效相互独立（这两个假设都有点可疑，但用于粗略估计大概可以）。于是每一位正确的概率为 $1 - 10^(-14)$，成功读出所有位的概率为

$$
P_{S} = (1 - 10^(-14))^(8 \times 500 \times 10^{9}) = 0.9608
$$

按这种算法，我们估计在整盘读取备份盘的过程中遇到失效的可能性略低于 4%。

如边栏所述，这些计算忽略了一些重要因素，因此结果未必精确。但即便它们偏差达一个数量级，仍然可以合理地得出结论：不可恢复读错误率很可能是不可忽略的。□
:::

注意，少量扇区丢失的影响可能不大（例如备份软件除了一两个文件之外其余都恢复成功），也可能非常严重（例如一点数据都恢复不出来）。例如，若扇区失效损坏了根目录，相当一部分数据可能就此丢失。

#### 设备失效

当一台设备再也无法对磁盘的所有扇区提供读写服务时，就发生了*整盘失效*（full disk failure）；*整块闪存盘失效*（full flash drive failure）则是闪存设备上的对应情形。

::: tip 什么会导致整台设备失效？
磁盘失效可由多种故障引起，例如磁头损坏、电容失效或电涌损坏电子部件，或者机械磨损使磁头难以保持在磁道正上方。

闪存设备失效的常见原因包括磨损失效——失效的页多到设备没有备用页可用于重映射——以及设备电子部件的失效，例如电容损坏。
:::

当整台设备失效时，主机上的设备驱动程序会发现这一失效，对设备的读写会返回错误码，而不是（比如说）返回错误的数据。这种显式的失效通知很重要，因为它减少了纠正失效所需的跨设备冗余。

整机失效率通常用*年失效率*（annual failure rate）来表征，即每年预期失效的磁盘所占比例；也可以用它的倒数，即*平均无故障时间*（MTTF）来表征。2011 年，旋转磁盘标称的年失效率（或 MTTF）通常在 0.5%（$1.7 \times 10^{6}$ 小时）到 0.9%（$1 \times 10^{6}$ 小时）之间；闪存固态硬盘的标称失效率与之相近。

**陷阱。** 在考虑厂商标称的设备失效率时，存储系统设计者必须留意若干陷阱。

- **轻信标称失效率。** 针对若干大规模磁盘集群的研究发现，失效率存在显著差异。在这些研究中，许多系统的失效率达到 2%、4% 甚至更高，尽管其标称失效率不足 1%。这种差异部分可能源于厂商与用户对“失效”的定义不同，部分可能源于恶劣的现场条件，还有部分可能源于厂商用来估计 MTTF 的加速老化与预测技术的局限。

- **假定各次失效互不相关。** 来自实际部署系统的证据表明，当一处故障发生时，附近的其他设备也更可能在不久后失效。许多因素会造成这种相关性。例如，制造上的异常可能使一批磁盘不合规格，而批量采购磁盘的机构可能发现整批磁盘同时失效。再如，同一台机器或同一个机柜中的磁盘可能年龄相近，可能经历相似的环境压力与工作负载，也可能在相近的时间磨损失效。

- **把设备的 MTTF 与其使用寿命混为一谈。** 若一台设备的 MTTF 为一百万小时或更多，并不意味着它预期能用 100 年以上。磁盘的设计运行寿命是有限的，也许是 5 年。磁盘标称的年失效率（即 1/MTTF）只适用于磁盘的预期使用寿命期内。随着寿命临近终点，失效率可能因设备磨损而上升。

- **假定失效率恒定。** 一台设备在其生命周期内的失效率可能并不相同。有些设备表现出*磁盘早期失效*（disk infant mortality）：在使用的头几周里，潜伏的制造缺陷暴露出来，失效率可能高于正常水平。另一些设备则表现出*磁盘磨损失效*（disk wear out）：使用若干年之后失效率开始上升。

<figcaption><span class="fig-label">图 14.7</span>设备寿命的浴盆模型。</figcaption>

 理解早期失效与磨损失效的一个简单模型是图 14.7 所示的*浴盆模型*（bathtub model）。

- **忽视预警信号。** 有些设备失效毫无预兆，但另一些在失效之前，非致命异常的出现频率会不断上升。许多存储设备实现了*SMART（自我监测、分析与报告技术）*接口，它使操作系统能够监测读错误、扇区重映射、寻道定位不准、转速达不到目标值等事件，这些事件有助于预测失效。

- **假定各设备行为相同。** 不同型号的设备，甚至同一型号的不同代次，失效行为可能大相径庭。某一代次的失效率可能显著高于预期，而下一代次则可能显著低于预期。

::: info 例
**大型系统中的磁盘失效。** 假设你有一台系里的文件服务器，装有 100 块磁盘，每块的 MTTF 估计为 $1.5 \times 10^{6}$ 小时。估计这些磁盘中有一块失效所需的期望时间。为简单起见，假定每块磁盘的失效率恒定，且各磁盘独立失效。
:::

::: warning 答
若每块磁盘的 MTTF 为 $1.5 \times 10^{6}$ 小时，那么 100 块磁盘的失效速率是它的 100 倍，于是系统的 MTTF 为 $1.5 \times 10^{4}$ 小时。因此，尽管单块磁盘的年失效率为（1 次失效 / $1.5 \times 10^{6}$ 小时）× 24 小时/天 × 365 天/年 = 0.00585 次失效/年，这个 100 盘系统的年失效率却是 0.585，即 58.5%。□
:::

::: info 例
**陷阱。** 鉴于上面讨论的种种陷阱，上述计算更可能高估还是低估系统的失效率？
:::

::: warning 答
在上面列出的诸因素中，**轻信标称失效率**这一陷阱看来最为重要，它可能使我们显著*低估*系统的失效率。

该解法确实*假定了失效率恒定*。若这些磁盘很新或很旧，其失效率可能高于预期，这会使我们*低估*系统的失效率。

由于我们只关心平均速率，*相关性*这一陷阱大概与我们的分析关系不大。□
:::

::: tip 指数分布
如例中所示，当设备以恒定速率失效时，固定时间段内的失效事件数可以用泊松过程做数学建模，而相邻失效事件之间的间隔时间服从指数分布。

指数分布是*无记忆的*——既然失效事件的速率不随时间变化，那么距下一次失效事件的期望时间就总是相同的，无论当前是什么时刻，也无论距上次失效已经过了多久。因此，若一台设备的年失效率为 0.5，从而平均无故障时间为 2 年，而我们已让该设备无故障运行了一年，那么从当前时刻算起，距下一次失效的期望时间仍然是 2 年。

若随机变量 $T$ 表示相邻失效之间的时间，服从参数为 $\lambda$ 的指数分布，$\lambda$ 表示单位时间内的平均失效事件数，则概率密度函数 $f_{T} (t)$ 为：

$$
f_{T} (t) = \lambda e^(-\lambda t)
$$

平均无故障时间为 $\text{MTTF} = 1 \/ \lambda$。

指数分布具有若干便利的数学性质。例如，由于失效率恒定，平均无故障时间就是失效率的倒数；正因如此，在存储规格中于 MTTF 与年失效率之间换算才如此容易。又如，若给出了某一时段内的预期失效次数（例如每年 0.1 次），就很容易换算成另一时段的预期次数（例如每天 0.0003 次）。最后，若有 $k$ 个相互独立的失效过程，速率分别为 $lambda_{1}, lambda_{2}, dots.c, lambda_{k}$，那么总的失效函数——$k$ 类失效中任意一类发生的速率——为

$$
lambda_{\text{tot}} = lambda_{1} + lambda_{2} + dots.c + lambda_{k}
$$

而任意一类失效距下一次发生的平均时间为 $\text{MTTF}_{\text{tot}} = 1 \/ lambda_{\text{tot}}$。例如，若有 100 块磁盘，每块的 $\text{MTTF}_{\text{disk}} = 1.5 \times 10^{6}$ 小时，等价地说每块磁盘每年失效 0.00585 次，那么整个 100 盘系统每年失效 $100 \times 0.00585 = 0.585$ 次，等价地说该 100 盘系统的 $\text{MTTF}_{\text{100disks}} = 1.5 \times 10^{4}$ 小时。

**警告。** 指数分布在数学上如此便利，以至于人们忍不住在并不适用时也用它。请记住，真实系统中的失效可能彼此相关（即并不独立），也可能随时间变化（即并不恒定）。
:::

### 14.2.2　RAID：多盘冗余纠错

鉴于物理存储设备的种种局限，存储系统需要借助额外技术才能获得可接受的端到端可靠性。具体而言，存储系统并不试图造出完美可靠（且极其昂贵）的存储设备，而是使用独立磁盘冗余阵列（RAID），使得某台设备部分或全部失效时不会导致数据丢失。

#### 基本 RAID

*独立磁盘冗余阵列*（Redundant Array of Inexpensive Disks，RAID）是一种把数据冗余地分布到多块磁盘上、从而容忍单块磁盘失效的系统。请注意，RAID 一词传统上指冗余的*磁盘*；为简便起见，我们将在磁盘的语境下讨论 RAID。不过，这些原理同样适用于闪存盘等其他存储设备。

图 14.8 与图 14.9 展示了两种常见的 RAID 体系结构：镜像与轮转奇偶校验。

- **镜像。** 采用*镜像*（mirroring）的 RAID（也称 *RAID 1*）把每个数据块写入两块磁盘，并且可以从任意一块磁盘读出任意一个数据块，如图 14.8 所示。若其中一块磁盘发生扇区失效或整盘失效，数据也不会丢失，因为仍可从另一块磁盘读出数据。

- **轮转奇偶校验。** 采用*轮转奇偶校验*（rotating parity）的 RAID（也称 *RAID 5*）把若干数据块存放在若干块磁盘上，再用存放在另一块磁盘上的一个冗余块保护这些数据块，以此降低复制开销，如图 14.9 所示。具体来说，这种方法使用由 $G$ 块磁盘组成的组，把 $G - 1$ 个数据块分别写入不同的磁盘，把 1 个奇偶校验块写入剩下的那块磁盘。奇偶校验块的每一位由相应数据位的异或计算得出：

$$
\text{parity} = \text{data}_{0} xor \text{data}_{1} xor dots.c xor \text{data}_(G-1)
$$

 若其中一块磁盘发生扇区失效或整盘失效，丢失的数据块可以用其他磁盘上对应的数据块与奇偶校验块重构出来。注意，由于系统已经知道是哪块磁盘失效，奇偶校验足以用于纠错，而不只是检错。例如，若存放块 $\text{data}_{0}$ 的磁盘失效，该块可以通过计算奇偶校验块与其余数据块的异或来重构：

$$
\text{data}_{0} = \text{parity} xor \text{data}_{1} xor dots.c xor \text{data}_(G-1)
$$

 为使性能最大化，轮转奇偶校验 RAID 会精心组织其数据布局：让奇偶校验轮转，并对数据做条带化，以平衡并行性与顺序访问：

 - **轮转奇偶校验。** 由于只要任何一个数据块被更新，相应那一组块的奇偶校验就必须更新，因此平均而言奇偶校验块往往比数据块被访问得更频繁。为平衡负载，系统并不让 $G-1$ 块磁盘只存数据块、1 块磁盘只存奇偶校验块，而是让每块磁盘拿出其空间的 $1\/G$ 用于奇偶校验，负责存放 $1\/G$ 的奇偶校验块和 $(G - 1)\/G$ 的数据块。

 - **数据条带化。** 为在并行性与顺序访问效率之间取得平衡，先把若干连续块组成的一个*数据条*（strip）放在一块磁盘上，然后转到下一块磁盘放置下一个数据条。$G - 1$ 个数据条及其奇偶校验条合称一个*条带*（stripe）。通过条带化，大于一个块但小于一个数据条的请求只需一块磁盘寻道，然后读或写整段连续数据，而不必让多块磁盘各自寻道再读较小的连续段。反过来，RAID 也能并行处理间距更大的多个请求。

 把轮转奇偶校验与条带化结合起来，就得到图 14.9 所示的布局。

::: info 例
**更新采用轮转奇偶校验的 RAID。** 对图 14.9 中的轮转奇偶校验 RAID，假设你更新数据块 21。必须发生哪些磁盘 I/O 操作？
:::

::: warning 答
难点在于：我们不仅要更新数据块 21，还必须更新对应的奇偶校验块。由于数据块 21 是其数据条中的第 1 个块，而该数据条属于条带 1，所以我们需要更新条带 1 中奇偶校验条上的奇偶校验块 1（即图中的 *Parity (1,1,1)*）。

**更新数据和奇偶校验共需 4 次 I/O 操作。** **首先读出旧数据 $D_{21}$ 与奇偶校验 $P_(1,1,1)$**，从奇偶校验计算中“去掉”旧数据：$P_{\text{tmp}} = P_(1,1,1) xor D_{21}$。然后由新数据算出新的奇偶校验：$P'_(1,1,1) = P_{\text{tmp}} xor D'_{21}$。**最后，把新数据 $D'_{21}$ 与奇偶校验 $P'_(1,1,1)$** 分别写入磁盘 2 和磁盘 1。□
:::

::: tip 数据与奇偶校验的原子更新
实现 RAID 的一个难题是原子地更新数据与奇偶校验（或者在采用镜像的 RAID 中原子地更新两个数据块）。

设想图 14.9 中的 RAID 系统在更新块 21 的中途崩溃：磁盘 2 上的数据块已经更新，而磁盘 1 上的奇偶校验块尚未更新。此时若磁盘 2 失效，系统将为块 21 重构出错误的（旧的）数据。

若对镜像 RAID 的写操作被中断，情况可能更糟。由于读可以由任意一块磁盘服务，对不一致块的读有时会返回新值，有时会返回旧值。

**解决方案。** 解决（或不解决）原子更新问题通常有三种方案，外加一种“非方案”。

- **非易失写缓冲。** 硬件 RAID 系统常带有电池后备的写缓冲。只有更新已安全落盘，它才会从写缓冲中移除。RAID 的启动过程会确保崩溃或断电之后，写缓冲中的任何数据都被写入磁盘。

- **事务式更新。** RAID 系统可以用事务来原子地更新数据块与奇偶校验块。例如，Oracle 的 RAID-Z 把 RAID 条带化与 ZFS 文件系统结合起来，以避免原地覆盖数据，并原子地更新数据与奇偶校验。

- **恢复扫描。** 崩溃之后，系统可以扫描系统中的所有块，更新任何不一致的奇偶校验块。注意，在扫描完成之前，某些奇偶校验块可能仍不一致，此时若有磁盘失效，就可能重构出错误的数据。Linux 的 md（多设备）软件 RAID 驱动程序采用这种方法。

- **祈求好运。** 有些软件和硬件 RAID 实现并不保证崩溃之后数据块与奇偶校验块是同步的。买者自慎。
:::

采用轮转奇偶校验的 RAID 在小写操作上开销很高；而对于读操作和整条带写操作，其开销要小得多。

::: tip RAID 级别
一篇关于 RAID 的早期论文——David Patterson、Garth Gibson 与 Randy Katz 的 “A Case for Redundant Arrays of Inexpensive Disks (RAID)”，见 http://dl.acm.org/citation.cfm?id=50214 ——描述了一系列可能的 RAID 组织方式，并把它们命名为 RAID 0、RAID 1、RAID 2、RAID 3、RAID 4 和 RAID 5。其中若干级别是为了阐明关键概念，而非用于实际部署。

今天，这些变体中有三种被广泛使用：

- **RAID 0：JBOD。** RAID 级别 0 把数据分布到多块磁盘上，不带任何冗余。任何一块磁盘失效都会导致数据丢失。正因如此，RAID 这个词多少有些误导，这种组织方式常被称为 JBOD（Just a Bunch Of Disks，只是一堆磁盘）。

- **RAID 1：镜像。** RAID 级别 1 把完全相同的数据镜像到两块磁盘上。

- **RAID 5：轮转奇偶校验。** RAID 级别 5 把数据条带化到 $G$ 块磁盘上。一条带中的 $G - 1$ 块磁盘存放 $G-1$ 个不同的数据块，剩下的那块磁盘存放一个奇偶校验块。为平衡负载，为不同数据块存放奇偶校验块的角色在各磁盘之间轮转。

在 “Case for RAID” 这篇论文之后，又出现了新的组织方式，其中许多也按同样的思路命名。有些名称已成为标准。

- **RAID 6：双重冗余。** RAID 级别 6 与 RAID 级别 5 类似，但每组不是存放一个奇偶校验块，而是存放两个冗余块。这些块用里德-所罗门码等纠删码生成，只要至多失效两块磁盘，就能重构出全部原始数据。

- **RAID 10 与 RAID 50：嵌套 RAID。** RAID 10 与 RAID 50 最初称为 RAID 1+0 和 RAID 5+0。它们只是把 RAID 0 与 RAID 1 或 RAID 5 组合起来。例如，RAID 10 系统把成对的磁盘做镜像以获得冗余（RAID 1），把每一对镜像磁盘视为一块可靠的逻辑磁盘，然后在这些逻辑磁盘之间非冗余地条带化数据（RAID 0）。

人们还提出了许多别的 RAID 级别。在某些情况下，这些新的“级别”与其说关乎技术，不如说关乎营销。（“我们公司的 RAID 99+ 比你们公司那可怜的 RAID 14 强多了。”）无论如何，我们认为用来描述各种奇特 RAID 组织方式的这套命名相对而言并不重要；我们的讨论集中在镜像（RAID 1）、轮转奇偶校验（RAID 5）和双重冗余（RAID 6）上。其他组织方式都可以用这些方法的原理来分析。
:::

**恢复。** 在上述两种 RAID 布局中，若一块磁盘发生扇区失效，磁盘会在有人试图读该扇区时报错，并在必要时把损坏的扇区重映射到备用扇区。随后，RAID 系统从其他磁盘重构出丢失的扇区，并把它写回原来的磁盘。

若一块磁盘发生整盘失效，操作员会更换失效的磁盘，RAID 系统则从其他磁盘重构该磁盘的全部数据，并把这些数据写入替换磁盘。从磁盘失效到它被替换并重写完毕的平均时间，称为*平均修复时间*（MTTR）。

#### RAID 的可靠性

每组只配一块冗余磁盘的 RAID（例如镜像 RAID 或轮转奇偶校验 RAID）可能以三种方式丢失数据：两块磁盘整盘失效；一块磁盘整盘失效，同时其他磁盘上出现一个或多个扇区失效；多块磁盘上出现相互重叠的扇区失效。从当前时刻到其中某一事件发生之间的期望时间，称为*平均数据丢失时间*（MTTDL）。

**两块磁盘整盘失效。** 若两块磁盘失效，系统将无法重构出丢失的数据。

为体会这个问题可能有多严重，假设系统有 $N$ 块磁盘，每 $G$ 个块配一个奇偶校验块；并假设各磁盘独立失效，平均无故障时间为 MTTF，更换失效磁盘并恢复其数据的平均时间为 MTTR。

那么，当系统正常运行时，距第一次失效的期望时间为 $\text{MTTF} \/ N$。假定 MTTR 远小于 MTTF，这实质上是一场赛跑：必须在第二块磁盘失效之前更换磁盘并重构出它的数据。我们输掉这场赛跑、在修复完成之前就遭遇第二次失效的概率为 $\text{MTTF} \/ ((G - 1) \times \text{MTTR})$，由此得到多块磁盘整盘失效导致数据丢失的平均时间为

$$
\text{MTTDL}_{\text{two-full-disk}} = \text{MTTF}^{2} / (N \times (G - 1) \times \text{MTTR})
$$

::: info 例
**双盘失效的平均时间。** 假设你有 100 块磁盘，每 10 块编成一组，每 9 块存放数据块的磁盘配 1 块存放奇偶校验块的磁盘。假设各磁盘独立失效，单块磁盘的平均无故障时间为 $10^{6}$ 小时，失效磁盘的平均修复时间为 10 小时，估计因两块磁盘同时失效而导致数据丢失的期望平均时间。
:::

::: warning 答
由于假定失效独立发生且速率恒定，可以使用上面的公式：

$$
\text{MTTDL}_{\text{two-full-disk}} &= \text{MTTF}^{2} / (N \times (G - 1) \times \text{MTTR}) \ &= (10^{6} \text{ 小时})^{2} / (10^{2} \times 9 \times 10 \text{ 小时}) \ &\approx bold(10^{8} \text{ 小时})
$$

因此，在假定失效按预期速率独立发生、且不存在其他数据丢失来源的前提下，这种组织方式看来把平均数据丢失时间从约 100 年（单块磁盘）提高到了约 10000 年（90 块磁盘的数据加上 10 块磁盘的奇偶校验）。□
:::

**一块磁盘整盘失效加一处扇区失效。** 若一块或多块磁盘出现扇区失效，同时另一块磁盘整盘失效，RAID 系统就无法恢复它的全部数据。假定失效独立发生且速率恒定，则某一时段内丢失数据的概率可以估计为“发生磁盘失效的概率”乘以“读取重构失效磁盘数据所需的全部数据时失败的概率”：

$$
P_(\text{lostDataFromDiskAndSector}) &= P_(\text{DiskFailure}) \times P_(\text{RecoveryError}) \ &= (N / \text{MTTF}) \times P_(\text{fail_{recovery}_{read}})
$$

若由此得到的是某段时间内丢失数据的概率，或者等价地说，是数据丢失失效的速率，那么把这个式子取倒数，就得到平均数据丢失时间（MTTDL）。于是，我们可以用整盘失效之间的期望时间，除以“读取重构失效磁盘数据所需的全部数据时失败的概率”，来估计这种失效模式下的平均数据丢失时间。

$$
\text{MTTDL}_{\text{disk+sector}} = (\text{MTTF} / N) \times (1 / P_(\text{fail_{recovery}_{read}}))
$$

::: info 例
**磁盘失效加扇区失效的平均时间。** 假定在恢复过程中，潜伏扇区错误按每读 $10^{15}$ 位出现 1 次的速率被发现；并假定 100 块 1 TB 的磁盘每 10 块编成一组，每块磁盘的平均无故障时间为 $10^{6}$ 小时，则整盘失效与扇区失效共同导致数据丢失的期望平均时间是多少？
:::

::: warning 答
$$
\text{MTTDL}_{\text{disk+sector}} &= (\text{MTTF} / N) \times (1 / P_(\text{fail_{recovery}_{read}})) \ &= (10^{6} / 100) \times (1 / P_(\text{fail_{recovery}_{read}}))
$$

为估计 $P_(\text{fail_{recovery}_{read}})$，我们假定每一位独立失效，且被成功读出的概率为 $1 - 10^(-15)$。那么，从 9 块磁盘上各读出 1 TB 数据的成功概率为：

$
P_(“succeed_recovery_read”) &= P_(“succeed_bit_read”)^“number of bits” \
&= (1 - 10^(-15))^(9 “ 块磁盘” times 10^12 “ 字节/磁盘” times 8 “ 位/字节”) \
&approx 0.93
$

所以，恢复成功的概率约为 93%，恢复失败的概率为 7%。于是有

$$
\text{MTTDL}_{\text{disk+sector}} &= (10^{6} / 100) \times (1 / 0.07) \ &= bold(1.4 \times 10^{5} \text{ 小时})
$$

请注意，这个数据丢失速率远高于上面算出的双盘失效的速率。当然，各种失效模式各自的相对贡献取决于磁盘的 MTTF、容量和误码率，也取决于系统的 MTTR。□
:::

**共用同一份冗余的两个扇区同时失效。** 原则上，也可能因为不同磁盘上互相对应的扇区同时失效而丢失数据。不过，每块磁盘上有数十亿个互不相同的扇区，而每块磁盘上的潜伏失效数量很少，因此对大多数系统而言，这种失效模式的风险大概可以忽略不计。

**总体数据丢失率。** 若假定失效独立且失效率恒定，就可以把两种主要失效模式的失效率相加，以估计总的失效率：

$
“FailureRate”*(“indep+const”) &= “FailureRate”*(“two-full-disk”) + “FailureRate”_(“disk+sector”) \
&= 1/(“MTTDL”*(“two-full-disk”)) + 1/(“MTTDL”*(“disk+sector”)) \
&= (N (G - 1) “MTTR”)/(“MTTF”^2) + (N times P_(“fail_recovery_read”))/“MTTF” \
&= N/“MTTF” ((“MTTR”(G - 1))/“MTTF” + P_(“fail_recovery_read”))
$

因此，总失效率等于第一块磁盘失效的速率，乘以“组内第二块磁盘在修复完成之前失效”或“在读取各磁盘以重建失效磁盘的数据时遇到扇区错误”的速率。

我们把上面的量记作 $\text{FailureRate}_(\text{indep+const})$，以强调“失效独立”与“失效率恒定”这两个很强的假定。如前所述，在许多环境中失效很可能是彼此相关的，某些设备的失效率也可能随时间上升。这两个因素都可能使实际失效率显著高于预期。

::: info 例
**合并失效率。** 对前面几个例子中描述的系统（100 块磁盘，组大小为 10 的轮转奇偶校验，平均无故障时间 $10^{6}$ 小时，平均修复时间 10 小时，不可恢复读错误率为每 $10^{15}$ 位一个扇区），假定所有失效都相互独立，估计同时考虑双盘失效与“单盘失效加扇区失效”时的 MTTDL。
:::

::: warning 答
$
“FailureRate”*(“indep+const”) &= N/“MTTF” ((“MTTR”(G - 1))/“MTTF” + P*(“fail_recovery_read”)) \
&= (100 “ 块磁盘”)/(10^6 “ 小时”) ((10 “ 小时”)/(10^6 “ 小时”) + 0.0694) \
&= 1/(10^4 “ 小时”) (1/10^4 + 0.0694) \
&= 1/(10^4 “ 小时”) (0.0695) \
&= 6.95 times 10^(-6) “ 次故障”/“小时”
$

把失效率取倒数，就得到平均数据丢失时间：

$$
\text{MTTDL}_(\text{const+indep}) &= 1 / \text{FailureRate}_(\text{indep+const}) \ &= 1.44 \times 10^{5} \text{ 小时/次失效} \ &= bold(16.4) \text{ 年/次失效}
$$

□
:::

上面的例子中有两点特别值得注意。第一，就这些参数而言，数据丢失的主要原因很可能是单块磁盘失效，加上恢复期间遭遇不可恢复读错误。第二，就这些参数与这种配置而言，由此得到的每年 6% 的数据丢失概率，对许多环境来说可能无法接受。因此，系统采用各种技术来提高 RAID 系统的 MTTDL。

#### 提高 RAID 的可靠性

还能做些什么来进一步提高可靠性？大体上说有三件事：（1）增加冗余；（2）降低不可恢复读错误率；（3）缩短平均修复时间。这些方法在实际中都以各种组合被采用。

以下是一些常见的做法：

**用更多冗余磁盘增加冗余。** 系统不再为每一组只配一个冗余块（例如用两块互为镜像的磁盘，或为每个条带配一块奇偶校验盘），而是可以采用双重冗余（例如三份磁盘副本，或为每个条带配两块纠错盘）。在某些情况下，系统甚至可以使用更多冗余。例如，Google 文件系统（GFS）的设计目标是在数千块磁盘上提供高度可靠、高度可用的存储；默认情况下，GFS 把每个数据块存放在三块不同的磁盘上。

*双重冗余阵列*（dual redundancy array）使用里德-所罗门码等纠删码生成两个冗余块，从而保证即使一个条带内任意两处发生失效，数据仍能重构出来。这种方法有时称为 *RAID 6*。

具有双重冗余的系统可以比只有单重冗余的简单 RAID 可靠得多。在双重冗余下，最可能发生的数据丢失情形是：（a）三块磁盘整盘失效；（b）两块磁盘整盘失效，同时出现一个或多个不可恢复读错误。

若乐观地假定失效独立发生且速率恒定，则每个条带配两块冗余磁盘的系统，其总数据丢失率可能很低：

$
“FailureRate”_(“dual+indep+const”) &= N/“MTTF” \
&quad times (“MTTR”(G - 1))/“MTTF” \
&quad times (((“MTTR”(G - 2))/“MTTF”) + P_(“fail_recovery_read”))
$

这个数据丢失率比单奇偶校验的数据丢失率大约好 $\text{MTTF} \/ (\text{MTTR} \times (G - 1))$ 倍；对于 MTTF 超过一百万小时、MTTR 不足 10 小时、组大小为 10 块或更少磁盘的情形，双重奇偶校验把估计的失效率改善了约 1 万倍。

不过我们要强调，上述公式几乎可以肯定低估了真实系统可能的数据丢失率——真实系统可能遭遇相关失效、失效率随时间变化、实际失效率高于标称值，等等。

**用巡检降低不可恢复读错误。** 存储设备的扇区级错误率通常表示为一个单一的*不可恢复读速率*（non-recoverable read rate），暗示这个速率是恒定的。实际情况要复杂得多。视设备而定，错误可能随时间累积，而更繁重的工作负载可能加快错误累积的速度。

降低磁盘不可恢复读速率的一项重要技术是*巡检*（scrubbing）：定期读出磁盘的全部内容，发现存在不可恢复读错误的扇区，用 RAID 阵列中其余磁盘重构出丢失的数据，并尝试把重构出的数据写入可疑扇区再读回。若写入和读取都成功，说明错误由瞬时故障引起，磁盘继续使用该扇区；若该扇区仍然无法成功访问，说明错误是永久性的，系统就把该扇区重映射到一个备用扇区，并把重构出的数据写到那里。

**用更可靠的磁盘降低不可恢复读错误率。** 不同型号的磁盘所标称的不可恢复读错误率差别很大。尤其是 2011 年，许多面向笔记本电脑与个人计算机的磁盘标称每读 $10^{14}$ 位出现 1 次不可恢复读错误，而面向企业级服务器的磁盘往往存储密度较低，却能标称每读 $10^{16}$ 位才出现 1 次。这一两个数量级的改善，大大降低了 RAID 系统因整盘失效与恢复期间不可恢复读错误相叠加而丢失数据的概率。

**用热备盘缩短平均修复时间。** 有些系统配有“热备”磁盘驱动器，它们处于空闲状态，但已经插在服务器上，因此一旦服务器上的某块磁盘失效，热备盘就能自动启用，替换失效的磁盘。

注意，即使有热备盘，磁盘的平均修复时间仍受限于把重构数据写入磁盘所需的时间，而这个时间往往以小时计。例如，若有 1 TB 的磁盘，写入速度为 100 MB/s，则该磁盘的平均修复时间至少为 $10^{4}$ 秒——约 3 小时。实际中若达到的带宽低于此处的假设，修复时间还可能更长。

**用去聚簇缩短平均修复时间。** 容量从数百 GB 到数 TB 的磁盘，要把重构数据全部写满可能需要数小时。*去聚簇*（declustering）把一个失效磁盘的重构工作分摊到多块磁盘上。这样就能并行重构，从而加快重构速度、缩短 MTTR。

例如，Hadoop 文件系统（HDFS）是一个集群文件系统，它把每个数据块写入数百甚至数千块磁盘中的三块。它为每个块挑选的三块磁盘基本上是随机的。若有一块磁盘失效，它会把丢失的块近似随机地重新复制到其余磁盘上。若有 $N$ 块磁盘，每块带宽为 $B$，则总重构带宽可接近 $(N \/ 2) \times B$；例如有 1000 块带宽为 100 MB/s 的磁盘，重构带宽在理论上可接近 500 GB/s，从而能在几秒内重新复制一块 1 TB 磁盘上的数据。

实际中，重新复制会慢于这个数字，原因至少有三。第一，磁盘之外的资源（例如网络）可能成为恢复的瓶颈。第二，系统可能限制恢复速度，以免用户请求得不到资源。第三，若某台服务器崩溃、其磁盘变得无法访问，系统可能推迟启动恢复——希望服务器很快就能恢复——以免给系统增加额外负载。

#### 陷阱

在构建可靠的存储系统时，仅仅提供足以容忍目标数量失效的冗余是不够的。我们还需要考虑失效可能以何种方式发生（例如失效可能彼此相关），以及纠正失效需要付出什么代价（例如要成功读出大量其他数据）。具体来说，要注意下面这些陷阱：

- **假定失效互不相关。** 只要增加一两台冗余设备、再把各设备的 MTTF 相乘，就很容易算出漂亮的 MTTDL 数字。但我们上面推导出的那个简单公式只在失效互不相关时才成立。即使只有 1% 的相关失效概率，也会使估计值发生剧变。遗憾的是，相关性比率往往难以*先验地*估计，设计者有时只能留出相当大的安全余量，并希望这已经足够。

- **忽视潜伏错误带来的风险。** 常见的 RAID 可靠性分析只考虑整台设备失效，却不考虑不可恢复读失效。正如上文所见，不可恢复读错误会大大降低磁盘失效后成功恢复数据的概率。

- **不实施巡检。** 定期巡检磁盘以发现并纠正潜伏错误，可以显著降低数据丢失的风险。虽然合适的巡检频率难以*先验地*预测，但使用巡检的系统可以监测发现并纠正不可纠正读错误的速率，并用实测的速率来调整巡检频率。

- **没有备份。** 本节讨论的技术可以保护系统免受许多故障、但并非所有故障的影响。例如，大范围的相关失效（比如整栋楼被烧毁）、操作员失误（比如 `rm -r *`），或者软件缺陷，都可能损坏或删除存放在任意多台冗余设备上的数据。*备份*（backup）系统提供的存储与系统的主存储相互独立。理想情况下，这种独立既是物理上的，也是逻辑上的。*物理独立*意味着备份存储设备与主存储设备位于不同地点。例如，有些系统把数据复制到磁带，再把磁带存放在与主存储服务器不同的大楼里，以此实现物理独立；另一些系统把数据存到远程磁盘阵列（例如云备份与灾难恢复服务提供的阵列）来实现物理独立。*逻辑独立*意味着对备份系统的接口受到限制，以防数据被过早删除。例如，有些备份系统提供的接口允许用户读取*但不能写入*文件的旧版本（例如一小时前、两小时前、四小时前、一天前、一周前、一个月前和一年前的文件）。

::: tip 为真实系统建模
正文中用于估计系统平均数据丢失时间的公式，只在失效率恒定且失效互不相关时才适用。遗憾的是，实证研究常常观察到整盘失效之间、扇区级失效之间，以及扇区级失效与整盘失效之间的相关性；研究还常常发现失效率随磁盘年龄（使用时长）显著变化。遗憾的是，若失效率随时间变化，或者失效彼此相关，失效到达的分布就不再服从指数分布，数学处理也很快变得困难。

一种解决办法是用随机模拟来估计某段关注时间内数据丢失的概率。例如，我们可能想估计一个由 1000 块磁盘组成、每 10 块一组、采用轮转奇偶校验的系统在 10 年内丢失数据的概率。

为此，模拟需要跟踪哪些磁盘正常工作、哪些存在潜伏扇区错误、哪些已经发生整盘失效。状态之间的转移可以基于测量研究或现场数据，关键因素包括：（a）磁盘发生整盘失效的速率（可能取决于磁盘年龄、近期整盘失效的次数，或某块磁盘已经出现过的单扇区失效次数）；（b）扇区失效出现的速率（可能取决于磁盘年龄、磁盘的工作负载以及近期扇区失效的频度）；（c）磁盘失效后的修复时间；（d）巡检发现并修复一个扇区错误所需的期望时间。

要估计数据丢失的概率，就要反复对系统模拟十年，并统计系统进入“数据已丢失”状态的次数（即某一组出现两块磁盘整盘失效，或既有一块磁盘整盘失效、又有另一块磁盘上的扇区失效）。
:::

### 14.2.3　软件完整性校验

尽管存储设备本身带有扇区级或页级的校验和来检测数据损坏，近年来的许多文件系统还是对数据增加了额外的、更高层的校验和及其他完整性检查。

这些检查能捕获一批硬件级校验和可能漏掉的错误。例如，它们能检测出*野写*（wild write）或*丢写*（lost write）：操作系统软件、设备驱动程序软件或设备固件中的缺陷把一次写引向错误的块或页，或者未能完成本应完成的写。它们还能检测出罕见的 *ECC 漏检*（ECC false negative）——硬件级纠错码未能发现的多位数据损坏。

当软件完整性检查在读取某个块时失败、或在潜伏错误巡检过程中失败，系统就利用 RAID 中的冗余存储重构出丢失或损坏的块。

目前使用的软件完整性检查有两个例子：**块完整性元数据**与**文件系统指纹**。

**块完整性元数据。** 有些文件系统（例如 Network Appliance 的 WAFL 文件系统）带有*块完整性元数据*（block integrity metadata），使软件能够校验它读出的每一个块的结果。

如图 14.10 所示，WAFL 为每个 4 KB 数据块存放一个 64 字节的*数据完整性段*（data integrity segment，DIS）。DIS 中包含该数据块的校验和、该数据块的身份（例如它所属文件的 ID，以及该块在那个文件中的偏移量），以及 DIS 自身的校验和。

于是在读取一个块时，系统要做三项检查。第一，检查 DIS 的校验和。第二，验证块中的数据与块的数据完整性段中的校验和相符。第三，验证块的 DIS 中的身份与它本想读取的文件块相符。若这些检查全部通过，文件系统就可以确信它返回的是正确的数据；若有任何一项不通过，文件系统就可以从 RAID 中的冗余磁盘重构出所需的数据。

**文件系统指纹。** 有些文件系统（例如 Oracle 的 ZFS）带有*文件系统指纹*（file system fingerprint）：它以某种方式为整个文件系统提供一个校验和，使得在读写单个块时能够高效地检查并更新。

如图 14.11 所示，ZFS 的所有数据结构都组织成一棵块树，其根节点称为 uberblock。在树的每个内部节点上，对某个子节点的每个引用都既包含指向该子节点的指针，又包含该子节点的校验和。于是，对任意子树的引用都带有一个覆盖该子树全部内容的校验和，而 uberblock 持有的校验和则覆盖整个文件系统。

当 ZFS 读取数据（即树的叶子）或元数据（即树的内部节点）时，它沿指针自树顶向下找到要读的那个块，计算每个内部块或叶子块的校验和，并与随块引用一同存放的校验和比较。类似地，如图 14.11 所示，当 ZFS 写入一个块时，它会把从被更新块到 uberblock 路径上的引用全部更新，使每个引用都既包含新的校验和，又包含新的块指针（因为 ZFS 从不原地更新数据结构）。

::: tip 层层叠叠
如今，存放重要数据的存储系统往往不仅具备这些层次，还具备更多层次。企业与云存储系统把数据分布到若干地理上分散的站点，并可能对这些跨地域复制的数据施以高层校验和。在一个站点内部，它们可能借助某种实质上是分布式文件系统的机制，把数据复制到多台服务器上。在每台服务器上，这个分布式文件系统又可能用一个本地文件系统存放数据，而该本地文件系统对本地存放的数据施以文件系统级的校验和。而本地服务器所用的存储设备，则毫无例外地会检测、有时还会纠正低层错误。

尽管我们不详细讨论跨机器复制与跨地域复制，本章讲述的原理同样适用于这类系统。
:::

## 14.3　小结与未来方向

尽管单台存储设备内部带有纠错码，但要提供可靠程度可接受的存储，往往还需要额外的冗余来做检错与纠错。事实上在今天，把有价值的数据存放在单台设备上而不加某种 RAID 式冗余，几乎不可接受。同理，过去十年里设计的文件系统有许多——即便不是大多数——都带有软件检错机制，以捕获设备级硬件检查无法发现的数据损坏与数据丢失。

现在乃至将来，系统正越来越多地超越“在单台服务器的多块磁盘之间复制数据”，走向“在多台服务器之间分布式复制”。有时这些副本的布局能做到：即使发生严重的物理灾难，数据仍能得到保护。

例如，亚马逊的简单存储服务（Simple Storage Service，S3）让客户按月付费，把数据存放在亚马逊运营的服务器上。亚马逊称，该系统“设计上可在给定年份内为对象提供 99.999999999% 的持久性”。为提供如此高的可靠性，S3 把数据存放在多个数据中心，快速检测并修复丢失的冗余，并校验所存数据的校验和。

+ 假设我有一块图 14.14 所描述的磁盘，负载是对磁盘随机块的连续更新流。假定磁盘调度器使用 SCAN/电梯算法。
 - （a）若应用程序一次只发出一个请求，并等到该块已安全存到磁盘上再发出下一个请求，吞吐量是每秒多少个请求？
 - （b）若应用程序缓冲 100 MB 的写，把这 100 MB 的写作为一个批次发给磁盘，并等到这些写都已安全落盘再发出下一批 100 MB 的请求，吞吐量是每秒多少个请求？
 - （c）请设计一种方法，使这种负载获得良好性能。（务必说明写、读和崩溃恢复各是如何工作的。）
 - （d）请解释为什么即使发生崩溃，你的设计仍能保证 FIFO。
 - （e）估计你的方法的吞吐量，以每秒请求数计。

 假设我们必须保证：即使发生崩溃，第 $i$ 次更新只有在它之前的全部更新都能在崩溃恢复后被读到的情况下，才能在崩溃恢复后被某次读观察到。也就是说，更新具有 FIFO 性质——第 $i$ 次更新完成之前，第 $i+1$ 次更新不能“完成”。（1）请设计一种方法，使这种负载获得良好性能。（2）解释为什么即使发生崩溃，你的设计仍能保证 FIFO。（3）估计你的方法的吞吐量，以每秒请求数计。（为与本题前面的部分作对比，你的解法所需的主存缓冲空间不应显著超过 100 MB。）
