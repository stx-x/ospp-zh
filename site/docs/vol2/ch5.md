# 第 5 章　共享对象的同步访问

<div class="chap-en">Synchronizing Access to Shared Objects</div>

<blockquote class="epigraph">仅仅勤奋是不够的，蚂蚁也很勤奋。问题在于：我们勤奋为了什么？——<em>亨利·戴维·梭罗</em></blockquote>

多线程程序扩展了传统的单线程编程模型：每个线程都提供一条由我们所熟悉的指令构成的单一顺序执行流。如果一个程序含有作用于完全分离的内存子集的*独立线程*（independent threads），我们就可以分别对每个线程进行推理。在这种情况下，对独立线程的推理与对一系列彼此独立的单线程程序的推理几乎没有差别。

然而，大多数多线程程序同时具有*每线程状态*（per-thread state，例如线程的栈和寄存器）和*共享状态*（shared state，例如堆上的共享变量）。*协作线程*（cooperating threads）会读写共享状态。

共享状态之所以有用，是因为它让线程能够通信、协调工作和共享信息。例如，在第 4 章的地球可视化程序（Earth Visualizer）中，当一个线程从网络上下载完一幅详细图像后，它就把该图像数据与负责在屏幕上绘制新图像的渲染线程共享。

遗憾的是，当协作线程共享状态时，编写正确的多线程程序就变得困难得多。大多数程序员在推理程序时习惯于“顺序”思维。例如，我们常常把程序在执行一串指令时所经历的一系列状态当作一个序列来推理。然而，这种顺序推理模型在含协作线程的程序中并不成立，原因有三个：

+ **程序执行取决于线程访问共享状态时可能出现的交错方式。** 例如，若两个线程写同一个共享变量，一个写入值 1，另一个写入值 2，则该变量的最终值取决于哪个线程的写操作最后完成。这个例子虽然简单，问题却很严重，因为程序必须对*任意可能的交错*都正确。特别地，回顾一下：线程程序员不应对各线程的相对运行速度作任何假设。更糟的是，随着程序规模增大，可能的交错数目会组合爆炸。*在一个数百万行的程序里，我们如何对所有可能的线程动作交错进行推理？*

+ **程序执行可能是非确定性的。** 同一程序的多次运行可能产生不同结果。例如，调度器可能作出不同的调度决策，处理器可能以不同的频率运行，或者另一个并发运行的程序可能影响缓存命中率。甚至常见的调试手段——例如在调试器下运行程序、用 `-g` 选项而不是 `-O` 重新编译、或者加入一条 `printf`——也可能改变程序的行为。1998 年 ACM 图灵奖得主 Jim Gray 把这类“一检查就消失或改变行为”的缺陷称为*海森堡缺陷*（Heisenbugs）。多线程编程是海森堡缺陷的常见来源。相比之下，*玻尔缺陷*（Bohrbugs）是确定性的，通常也容易诊断得多。*我们如何调试那些行为在多次运行之间会发生变化的程序？*

+ **编译器和处理器硬件可能对指令重排序。** 现代编译器和硬件会重排序指令以提高性能。对单线程程序而言，这种重排序一般是不可见的；编译器和处理器会小心地保证单一指令序列内部（也就是一个线程内部）的依赖关系得到保持。然而，当多个线程通过访问共享变量相互作用时，重排序就可能变得可见。例如，考虑下面这段把 `q` 计算为 `p` 的函数值的代码：

```c
  // 线程 1
  p = someComputation();
  pInitialized = true;

  // 线程 2
  while(!pInitialized);
  q = anotherComputation(p);
```

 尽管看上去在调用 `anotherComputation(p)` 之前 `p` 总是已经初始化，事实却并非如此。为了最大化指令级并行度，硬件或编译器可能在计算 `p` 的过程完成之前就置 `pInitialized = true`，于是 `anotherComputation(p)` 可能用一个意外的值来计算。*当编译器和处理器硬件可能重排序一个线程的操作时，我们如何对线程交错进行推理？*

::: tip 为什么编译器与处理器硬件要重排序操作？
我们常常发现，学生对这样一件事感到困惑：编译器生成的代码，或处理器执行的代码，可能是对单线程正确、而在未加同步的多线程程序中不可预测的。

对编译器来说，问题很简单。现代处理器有很深的流水线；它们通过重叠一串指令的取指、译码、取数、算术运算和条件分支，同时执行许多条指令。处理器在必要时停顿——例如下一条指令需要上一条指令的结果时。现代编译器会重排序指令，以尽可能减少这类停顿，前提是重排序不改变程序的行为。

困难出现在编译器可以对代码作哪些假设上。如果代码是单线程的，分析相邻指令之间可能的依赖关系就要容易得多，从而可以做更多优化。相比之下，（未加同步的）多线程代码中的变量，随时可能被另一个线程读写。正如正文中的例子所示，一串看起来彼此无关的指令，其确切顺序可能影响程序的行为。为保持语义，指令重排序可能不再可行，结果就是更多的处理器停顿和更慢的代码执行。

只要程序员使用结构化同步来保护共享数据，编译器就可以在需要时重排序指令而不改变程序行为——前提是编译器不跨越同步操作重排序。反过来，如果一个编译器采取更保守的假设，认为所有内存都是共享的，那么即使在并不必要的时候，它也会生成缓慢的代码。

对处理器体系结构来说，问题同样出在性能上。某些优化只有在程序员使用结构化同步时才可行，否则不行。例如，现代处理器会缓冲内存写操作，使得内存写可以在后台进行的同时让指令继续执行。如果两条相邻指令向不同内存位置发出写操作，它们可以并行发生并按乱序完成。这种优化在单处理器上是安全的，但如果多个处理器在中间没有同步的情况下同时读写相同的位置，就可能不安全。有些处理器体系结构采取保守假设，认为优化在任何编程风格下都不应改变程序行为——在这种情况下，它们会停顿以避免重排序。另一些则采取更乐观的假设，认为程序员在使用结构化同步。为了让你的代码可移植，你应当假定编译器和硬件可以对指令重排序，但不会跨越同步操作。
:::

鉴于这些挑战，多线程代码可能引入微妙的、非确定性的、不可复现的缺陷。本章描述一种在多线程程序中共享状态的*结构化同步*（structured synchronization）方法。与其在程序中到处散布对共享状态的访问，并试图对线程访问以各种方式交错时会发生什么作*个案式*（ad hoc）推理，更好的做法是：(1) 把程序组织成便于对并发进行推理的结构；(2) 用一组标准的同步原语来控制对共享状态的访问。这种做法放弃了一些自由，但只要你始终遵循本章描述的规则，对含共享状态的程序进行推理就会简单得多。

本章第一部分详细阐述多线程程序员面临的挑战，以及在一般、无结构的情形下试图对所有可能的线程交错进行推理为什么危险。本章其余部分描述如何在多线程程序中组织共享对象，以便我们能够对它们进行推理。首先，我们把多线程程序的共享状态组织成一组*共享对象*（shared objects），由它们封装共享状态，并定义和限制状态的访问方式。其次，为了避免对共享对象内部状态变量的可能访问交错作*个案式*推理，我们描述共享对象如何用一小组*同步原语*（synchronization primitives）——锁与条件变量——来协调不同线程对其状态的访问。第三，为了简化对共享对象代码的推理，我们给出一组编写每个共享对象实现代码的*最佳实践*（best practices）。最后，我们深入讨论如何实现同步原语。

多线程编程素有“困难”之名。我们同意它需要小心，但本章提供了一组任何人都能遵循的简单规则，用来实现可被多个线程安全共享的对象。

## 5.1　挑战

本章从多线程编程的核心挑战讲起：多线程程序的执行取决于不同线程访问共享内存的交错方式，这使得推演和调试这类程序变得困难。特别是，协作线程的执行可能受到*竞态条件*（race condition）的影响。

### 5.1.1　竞态条件

*竞态条件*（race condition）指程序的行为取决于不同线程操作的交错顺序。实际上，各个线程在它们的操作之间展开一场赛跑，程序执行的结果取决于谁赢了这场比赛。

即使程序很简单，只要含有竞态条件（race condition），对它的推理也可能变得困难。为了体会这一点，我们来看三个极其简单的多线程程序。

**世界上最简单的协作线程程序。** 假设我们运行一个包含两个线程的程序，它们分别执行以下语句：

由于问题需要一系列罕见的事件组合才会出现，这台机器在几乎所有患者身上看起来都工作正常。从第一次事故到最后一次事故之间隔了好几年，在此期间，制造商一再坚称不可能发生过量照射，患者的伤害必定另有原因。直到同一家医院第二次发生同样的竞态条件，系统的设计缺陷才得以暴露。

### 5.1.2　原子操作

在反汇编上一个例子中的代码时，我们可以推演*原子操作*（atomic operation）——不可分割、不能与其它操作交错或被其拆分的操作。

在大多数现代体系结构上，把内存中一个 32 位字装入寄存器，或把一个 32 位字存入内存，都是原子操作。因此，前面的分析所讨论的是原子的装入与存储之间的交错。

反过来说，装入或存储并不总是原子操作。取决于硬件的实现方式，如果两个线程把 64 位浮点寄存器的值存到同一个内存地址，最终结果可能是第一个值、第二个值，也可能是两者的混合。

### 5.1.3　牛奶买多了

虽然原则上可以小心推演不同线程的原子加载与存储的各种可能交错，但这样做既繁琐又容易出错。稍后我们会给出一种更高层的线程同步抽象，但首先我们用一个叫做“牛奶买多了”（Too Much Milk）的简单问题，来说明使用原子加载与存储会遇到的困难。这个例子刻意取得很简单；现实中的并发程序往往复杂得多。即便如此，这个例子也足以说明，对共享状态的交错访问进行推演有多么困难。

牛奶买多了（Too Much Milk）问题描述的是两位合租一套公寓的室友，他们共用一台冰箱，并且——作为好室友——总是确保冰箱里备足牛奶。有这样负责任的室友，就可能出现下面这样的情形：

我们可以把每位室友建模为一个线程，把冰箱里牛奶的瓶数建模为内存中的一个变量。如果对共享状态唯一的原子操作就是对内存的原子装入与存储，那么牛奶买多了问题有没有一个解，既能保证*安全性*（safety，程序永远不会进入坏状态），又能保证*活性*（liveness，程序最终会进入好状态）？在这里，我们力求满足以下性质：

- **安全性：** 买牛奶的人永远不会多于一个。

- **活性：** 如果需要牛奶，最终会有人去买。

**警告：简化假设。** 本节的全部分析都假设指令严格按书写的顺序执行，也就是说，编译器和体系结构都不会对指令重排序。这一假设对于推理原子的装入与存储操作的先后顺序至关重要，但许多现代编译器和体系结构都会违反它，因此把这里介绍的分析方法用到你自己的程序上时必须极其小心。

**解法 1。** 基本想法是让室友在去商店之前，先在冰箱上留一张便条。要留下这张便条，最简单的做法——在我们这个可以对共享内存做原子装入与存储的编程模型下——就是在去买牛奶时设置一个标志，并在去买牛奶之前检查这个标志。每个线程可以执行如下代码：

```c
    if (milk==0) {       // 如果没有牛奶
        if (note==0) {   // 如果没有便条
            note = 1;    // 留下便条
            milk++;      // 买牛奶
            note = 0;    // 撕掉便条
        }
    }
```

不幸的是，这种实现可能破坏安全性。例如，第一个线程可能把代码执行到检查牛奶数量那一步（含这一步）之后被切换出去。然后，第二个线程可能跑完这整段代码并买了牛奶。最后，第一个线程被重新调度，看到 `note` 为零，于是留下便条、再买一份牛奶、再撕掉便条，系统里就剩下 `milk == 2`。

```c
    // 线程 A                      // 线程 B
    if (milk==0) {
                                     if (milk==0) {
                                         if (note==0) {
                                             note = 1;
                                             milk++;
                                             note = 0;
                                         }
                                     }

        if (note==0) {
            note = 1;
            milk++;
            note = 0;
        }
    }

                        Oh no!
```

这个“解法”反而把问题弄得更糟！上面的代码通常能正常工作，但当调度器恰好做出那个正确（或者说是错误）的动作时，它偶尔会失败。我们由此造出了一个海森堡 bug（Heisenbug），它会让程序偶尔以极难复现的方式失败（比如，很可能只有在评分人盯着看的时候，或者 CEO 在展会上演示新产品的时候）。

**解法 2。** 在解法 1 中，室友先检查便条，再设置便条。这就留下了一种可能：一位室友在通知另一位室友之前，就已经做出了买牛奶的决定。如果用两个变量来表示便条，室友就可以先留下自己的便条，再去检查对方的便条和牛奶数量，然后决定是否去买。例如，我们可以这样做：

<div class="code-cap">路径 A</div>

```c
 noteA = 1;         // 留下便条
 if (noteB==0) {    // 如果没有便条  A1
     if (milk==0) { // 如果没有牛奶  A2
         milk++;    // 买牛奶    A3
     }
 }
 noteA = 0;         // 撕掉便条 A
```

<div class="code-cap">路径 B</div>

```c
 noteB = 1;         // 留下便条
 if (noteA==0) {    // 如果没有便条  B1
     if (milk==0) { // 如果没有牛奶  B2
         milk++;    // 买牛奶    B3
     }              //             B4
 }                  //             B5
 noteB = 0;         // 撕掉便条
```

如果第一个线程执行路径 A 的代码，第二个线程执行路径 B 的代码，这个协议就是安全的；让每个线程在决定买牛奶之前先写下便条（“我可能会去买牛奶”），就确保了安全性：最多只有一个线程去买牛奶。

这个直觉虽然可靠，但若不枚举所有可能的交错方式，要证明安全性仍需格外小心。

**安全性证明。** 为了推出矛盾，假设该算法*并不*安全——A 和 B 都买了牛奶。考虑线程 A 位于标有 **A1** 的一行、且“把 `noteB` 从共享内存原子地装入 A 的寄存器”这一动作恰好发生的那一刻，两个变量（`noteB`、`milk`）处于什么状态。有三种情况需要考虑：

- **情况 1：**（`noteB = 1`，`milk` 为任意值）。这种状态与“线程 A 买了牛奶并到达 **A3**”的假设矛盾。

- **情况 2：**（`noteB = 0`，`milk > 0`）。在这个简单的程序里，性质 `milk > 0` 是一个*稳定性质*（stable property）——一旦它为真，就将永远为真。因此，如果 A 位于 **A1** 时 `milk > 0` 成立，A 在 **A2** 那一行的检查就会失败，A 就不会买牛奶，这与我们的假设矛盾。

- **情况 3：**（`noteB = 0`，`milk = 0`）。我们知道线程 B 此刻必定没有在执行 **B1**–**B5** 中的任何一行。我们还知道，从此刻起，`noteA == 1` 或 `milk > 0` 之中必有一个为真（`noteA` 或 `milk` 也是稳定性质）。这意味着 B 将来不可能买到牛奶（**B1** 或 **B2** 处的检查必有一个失败），这与“A 和 B 都买牛奶”的假设矛盾。

既然每种情况都与假设矛盾，该算法就是安全的。□

**活性。** 遗憾的是，解法 2 不能保证活性。特别是，两个线程可能都设置了自己的便条，都检查了对方的便条，然后都决定不去买牛奶。

这就把我们引向了解法 3。

**解法 3。** 解法 2 之所以安全，是因为只要对方*可能*去买牛奶，线程就会放弃去买。在解法 3 中，我们确保至少有一个线程在决定是否买牛奶之前，先弄清对方到底有没有买牛奶。具体做法如下：

<div class="code-cap">路径 A</div>

```c
 noteA = 1;         // 留下便条 A
 while (noteB==1) { // 等待便条 B 不存在
     ;              // 自旋
 }
 if (milk==0) {     // 如果没有牛奶 M
     milk++;        // 买牛奶
 }
 noteA = 0;         // 撕掉便条 A
```

<div class="code-cap">路径 B</div>

```c
 noteB = 1;          // 留下便条 B
 if (noteA==0) {     // 如果没有便条 A
     if (milk==0) {  // 如果没有牛奶
         milk++;     // 买牛奶
     }               //
 }                   //
 noteB = 0;          // 撕掉便条 B
```

我们可以用与证明解法 2 类似的论证来说明解法 3 是安全的。

为说明解法 3 具有活性，请注意代码路径 B 中没有循环，因此线程 B 最终一定会执行完所列出代码。最终 `noteB == 0` 会成立，并且一直成立。于是线程 A 最终一定会到达标有 **M** 的一行，并决定是否去买牛奶。如果它发现 `M == 1`，说明牛奶已经买过了；如果它发现 `M == 0`，它就会去买。无论哪种情况，活性性质——需要时会有人买牛奶——都得到了满足。

### 5.1.4　讨论

假设编译器和处理器按程序顺序执行指令，前面的证明表明：仅凭对共享内存的原子加载与存储操作，就有可能设计出既安全又活跃的“牛奶买多了”解法。虽然我们给出的解法只适用于两个室友的情形，但存在一个推广，称为 Peterson 算法，适用于任意固定数目 n 的线程。Peterson 算法的更多细节可以在别处找到（例如 `http://en.wikipedia.org/wiki/Peterson's_algorithm`）。

然而，我们对牛奶买多了问题的解法（以及类似的 Peterson 算法）并不令人十分满意：

- 这个解法*复杂*，需要仔细推理才能确信它确实可行。

- 这个解法*低效*。在牛奶买多了问题中，线程 A 在等待时是在*忙等*（busy-waiting），白白消耗 CPU 资源。在 Peterson 的推广解法中，全部 $n$ 个线程都可能忙等。在现代的抢占式多线程系统上，忙等尤其成问题，因为自旋的线程可能一直占着处理器，等待一个只有等到某个被抢占的线程重新被调度运行才可能发生的事件。

- 如果编译器或硬件对指令重排序，这个解法*可能失效*。这一局限可以通过*内存屏障*（memory barrier）来弥补（见边栏）。加入内存屏障会进一步提高算法的实现复杂度；而且屏障并不能解决刚刚提到的其他局限。

::: tip 内存屏障
假设你正在编写必须推理内存操作顺序的底层代码。在现代硬件和现代编译器上，怎样才能做到这一点？

*内存屏障*指令阻止编译器和硬件跨越屏障重排内存访问——屏障之前的访问不会被移到屏障之后，屏障之后的访问也不会被移到屏障之前。可以把内存屏障加进牛奶买多了问题的解法或 Peterson 算法，从而得到在现代机器上用现代编译器也能工作的代码。当然，这会让代码更加复杂。

如何发出内存屏障指令，取决于硬件和编译器的细节。一个很好的例子是 gcc 的内建函数 `__sync_synchronize()`：它告诉编译器不要跨越屏障重排内存访问，并发出底层硬件视为内存屏障的、与具体处理器相关的指令。
:::

### 5.1.5　更好的解法

下一节描述一种更好的方法，用于编写多个线程访问共享状态的程序。我们编写*共享对象*（shared object），由它们使用*同步对象*（synchronization object）来协调不同线程对共享状态的访问。

例如，假设我们有一个称为*锁*（lock）的原语，同一时刻只能有一个线程持有它。那么，通过为 Kitchen 对象定义一个带有如下方法的类，就可以解决牛奶买多了问题：

```c
    Kitchen::buyIfNeeded() {
        lock.acquire();
        if (milk == 0) {     // 如果没有牛奶
            milk++;          // 买牛奶
        }
        lock.release();
    }
```

在下一节概述管理同步的策略之后，我们将在 5.3 节和 5.4 节定义锁和条件变量（另一类同步对象）。

## 5.2　组织共享对象

<figure class="book-figure">
<img src="/figures/vol2/image00400.png" alt="图 5.1" loading="lazy" decoding="async">
<figcaption><span class="fig-label">图 5.1</span>在多线程程序中，线程彼此独立，并发地作用于共享对象。共享对象既包含共享状态，也包含同步变量，后者用于控制对共享状态的并发访问。</figcaption>
</figure>

数十年的工作发展出一种比只用原子加载与存储简单得多的多线程程序编写方法。这种方法把面向对象编程的模块性扩展到了多线程程序。如图 5.1 所示，多线程程序由*共享对象*和操作它们的一组线程构成。

*共享对象*（shared object）是可以被多个线程安全访问的对象。程序中的所有共享状态——包括在堆上分配的变量（例如用 `malloc` 或 `new` 分配的对象）以及静态的全局变量——都应当封装在一个或多个共享对象中。

用共享对象编程是对传统面向对象编程的扩展，在后者中，对象把实现细节隐藏在整洁的接口之后。同样，共享对象把同步多个线程动作的细节隐藏在整洁的接口之后。使用共享对象的线程只需理解接口，无需知道共享对象内部如何处理同步。

与普通对象一样，程序员可以根据应用的需要，为任意模块、接口和语义设计共享对象。每个共享对象的类都定义了一组供线程操作的公有方法。为了用这些共享对象组装出整个程序，每个线程执行一个“主循环”，而主循环是依据对共享对象公有方法的操作写成的。

由于共享对象封装了程序的共享状态，定义线程高层动作的主循环代码不必操心同步细节。于是，编程模型看起来与单线程代码的编程模型非常相似。

::: tip 共享对象、管程与语法糖
我们聚焦于*共享对象*，因为面向对象编程提供了一种思考共享状态的好方式：把共享状态隐藏在公有方法之后，这些方法为线程提供整洁的接口，并处理同步的细节。

尽管我们在讨论中使用面向对象的术语，这些思想同样适用于非面向对象的语言。例如，C++ 程序可能定义一个带有公有方法的共享对象类，而 C 程序则可能定义一个结构体，把同步变量和状态变量作为字段。精心设计的 C 程序不会把访问结构体字段的代码分散到各处，而是提供一组固定的函数来操作这些字段。

反过来说，有些编程语言对共享对象的支持比我们这里描述的还要多。当一门编程语言内置支持共享对象时，共享对象常被称为*管程*（monitor）。早期支持管程的语言包括 Brinch Hansen 的 Concurrent Pascal 和 Xerox PARC 的 Mesa；今天，Java 通过 `synchronized` 关键字支持管程。

我们认为，过程式语言、面向对象语言与内置支持管程的语言之间的差别，在很大程度上只是无关紧要的语法糖——它们不过是书写同一件事的不同方式。我们广义地使用“共享对象”或“管程”这两个词，指称一种概念性的方法：无论使用哪种具体的编程语言，都应当用它来管理并发。

在本书中，我们的代码和伪代码基于 C++ 语法。我们认为它提供了讲授共享对象（或管程）方法所需的恰当细节层次。我们更愿意用 C++ 而不是 Java 来教学，是因为我们希望明确展示锁和条件变量在哪里分配、在哪里访问，而不是依赖被语言内置的管程语法所隐藏的操作。反过来说，我们更愿意用 C++ 而不是 C，是因为我们认为 C++ 对面向对象编程的支持有助于你内化共享对象方法背后的哲学。
:::

### 5.2.1　实现共享对象

当然，在内部，共享对象必须处理同步的细节。如图 5.2 所示，共享对象是分层实现的。

<figure class="book-figure">
<img src="/figures/vol2/image00401.png" alt="图 5.2" loading="lazy" decoding="async">
<figcaption><span class="fig-label">图 5.2</span>多线程程序是用共享对象搭建起来的。共享对象则用同步变量和状态变量搭建。同步变量是用专门的处理器指令实现的，这些指令用于管理中断的递送，并以原子方式对内存单元做读-改-写。</figcaption>

- **共享对象层。** 与标准的面向对象编程一样，共享对象定义与具体应用相关的逻辑，并隐藏内部的实现细节。从外部看，它们的接口与你为单线程程序定义的接口相同。

- **同步变量层。** 共享对象并不直接用精心交错安排的原子装入和存储来实现，而是把*同步变量*作为成员变量包含进来。同步变量与其他对象一样存放在内存中，可以放进任何数据结构。*同步变量*是一种用于协调对共享状态的并发访问的数据结构。同步变量的接口和实现都必须仔细设计。特别地，我们用两类同步变量来构建共享对象：*锁*和*条件变量*；我们将在 5.3 节和 5.4 节定义它们，并说明如何构造它们。同步变量协调对*状态变量*的访问，而状态变量就是你在单线程编程中早已熟悉的普通成员变量（例如整数、字符串、数组和指针）。使用同步变量可以简化共享对象的实现。事实上，共享对象不仅在外观上与传统单线程对象相似，由于它们是用同步变量实现的，其内部实现也与单线程程序十分相似。

- **原子指令层。** 虽然上面的各层得益于此而拥有更简单的编程模型，但这种简化并不会一直延续到最底层——世界并不是由一只只乌龟驮着的。在内部，同步变量必须管理不同线程动作之间的交错。现代实现并不像我们在牛奶买多了问题中尝试的那样，用原子装入和存储来实现锁、条件变量这类同步变量，而是用*原子读-改-写指令*来构建它们。这些与具体处理器相关的指令，让一个线程在指令执行期间对某个内存单元拥有临时的独占、原子访问权。典型情况下，指令原子地读取一个内存单元，对该值做某种简单的算术运算，再把结果存回。硬件保证：其他任何线程访问同一内存单元的指令，要么完全发生在这条原子读-改-写指令之前，要么完全发生在它之后。

## 5.3　锁：互斥

**锁**（lock）是一种同步变量，它提供**互斥**（mutual exclusion）——当一个线程持有某把锁时，其他任何线程都不能持有它（也就是说，其他线程被**排斥**在外）。程序把每把锁与共享状态中的某个子集关联起来，并要求线程在访问这部分状态时必须持有这把锁。于是，同一时刻只有一个线程能够访问该共享状态。

互斥极大地简化了对程序的推理，因为一个线程可以在持有锁的期间执行任意一组操作，而在其他线程看来，这些操作**是原子的**。特别地，由于锁强制实施互斥、线程必须持有锁才能访问共享状态，其他线程不可能观察到中间状态；它们只能观察到锁被释放之后留下的状态。

::: info 例
**加锁以把多个操作归为一组。** 例如，考虑一个银行账户对象，它包含一个交易列表和一个总余额。要添加一笔新交易，我们先获取该账户的锁，把新交易追加到列表，读取旧余额，修改它，写回新余额，然后释放锁。要查询余额和最近的交易列表，我们先获取该账户的锁，从列表中读取最近的交易，读取余额，然后释放锁。这样使用锁，可以保证一次更新或查询在下一项开始之前完成；每次查询看到的始终是完整的最近交易集合。

归组的另一个例子是打印输出。如果没有锁，两个线程同时调用 `printf` 时，两条消息中的单个字符可能彼此交错，把意思弄得含混不清。因此，在现代多线程操作系统上，`printf` 会使用一把锁，确保每条消息中的那组字符作为一个整体打印出来。
:::

推理原子操作组之间的交错，比推理单个操作之间的交错要容易得多，原因有两点。第一，（显然）需要考虑的交错更少——在更粗的粒度上推理交错，可以减少需要考虑的情况数量本身。第二点，也是更重要的一点：我们可以让每个原子操作组对应程序的逻辑结构，从而针对**不变式**（invariant）而不是具体的**交错**进行推理。

具体来说，共享对象通常只用一把锁保护对象的全部状态：每个公有方法在入口处获取锁，在出口处释放锁。于是，推理共享类的代码与推理传统类的代码十分相似：我们假定在某个公有方法被调用时有一组不变式成立，并在该公有方法返回之前重新确立这些不变式。只要不变式定义得当，我们就可以独立地推理每个方法。

### 5.3.1　锁：API 与性质

锁通过提供两个方法来实现互斥：`Lock::acquire()` 与 `Lock::release()`。这两个方法定义如下：

- 锁可以处于两种状态之一：BUSY 或 FREE。

- 锁最初处于 FREE 状态。

- `Lock::acquire` 会一直等到锁变为 FREE，然后原子地把锁置为 BUSY。检查状态是否为 FREE 与把状态置为 BUSY，合起来是一个**原子操作**。即使多个线程同时尝试获取这把锁，也至多只有一个线程会成功：一个线程观察到锁是 FREE 并把它置为 BUSY，其他线程只会看到锁是 BUSY，然后等待。

- `Lock::release` 把锁置为 FREE。如果有正在等待的 `acquire` 操作，这一状态变化会使其中之一得以继续。

我们将在 5.7 节描述如何实现具有这些性质的锁。有了锁，解决牛奶买多了问题就变得轻而易举：两个线程都运行下面的代码：

```c
    lock.acquire();
    if (milk == 0) {     // 如果没有牛奶
        milk++;          // 买牛奶
    }
    lock.release();
```

**形式化性质。** 锁可以更精确地定义如下。如果某个线程从某把锁的 `acquire` 方法返回的次数，多于它从该锁的 `release` 方法返回的次数，我们就说该线程**持有这把锁**。如果某个线程已经调用了某把锁的 `acquire`，但尚未从这次调用返回，我们就说它**正在尝试获取**这把锁。

一把锁应当保证以下三条性质：

+ **互斥。** 至多只有一个线程持有该锁。

+ **进展性。** 如果没有线程持有该锁，而又有线程尝试获取它，那么最终会有某个线程成功获取到该锁。

+ **有界等待。** 如果线程 T 尝试获取某把锁，那么在其他线程成功获取该锁的次数上存在一个界，即在 T 成功之前，其他线程至多能成功获取该锁这么多次。

互斥是一条**安全性**（safety）性质，因为锁阻止一个以上的线程同时访问共享状态。

进展性与有界等待则是**活性**（liveness）性质。如果一把锁处于 FREE 状态，就必须有**某个**线程能够获取它；进一步说，任何**特定的**想要获取该锁的线程，最终都必须成功地获取到它。

这些定义听起来也许过于生硬，那是因为我们精心推敲过措辞，以避免引入微妙的边界情形。例如，如果持有锁的线程永不释放它，其他线程就无法取得进展，所以我们用成功的 `acquire` 操作来定义**有界等待**条件。

**警告：非性质——线程顺序。** 上面定义的**有界等待**性质保证一个线程最终会得到获取锁的机会，但它并不承诺等待中的线程按先进先出（FIFO）的顺序获取锁。你会遇到的大多数锁实现——例如 POSIX 线程中的锁——都不提供 FIFO 顺序。

### 5.3.2　案例研究：线程安全的有界队列

与标准的面向对象编程一样，每个共享对象都是某个类的一个实例，该类定义了类的状态以及作用于这些状态的方法。

类的状态既包括状态变量（例如整数、浮点数、字符串、数组和指针），也包括同步变量（例如锁）。类的构造函数每产生一个共享对象的实例，都会分配一把新锁，以及由该锁保护的状态变量的新实例。

**有界队列**（bounded queue）是一种对所能存放的元素数量设定了固定上限的队列。操作系统内核用有界队列来管理进程间通信、TCP 与 UDP 套接字以及 I/O 请求。由于内核运行在有限的物理内存中，内核必须设计成在有限资源下也能正常工作。例如，内核不会在生产者和消费者线程之间使用一个简单的、无限的缓冲区，而是使用大小有限的缓冲区，也就是有界队列。

**线程安全的有界队列**是可以在多个并发线程中安全调用的一种有界队列。图 5.3 给出了一种实现，它允许任意多个线程安全地向队列插入元素或从队列删除元素。如图 5.4 所示，一个程序可以分配多个这样的队列（例如 `queue1`、`queue2` 和 `queue3`），每个队列都包含自己的锁和状态变量。

<div class="code-cap"><span class="code-label">图 5.3</span>线程安全的有界队列。为便于实现，我们假定队列存放的是整数（而不是任意对象），并且存放的元素总数不大。</div>

```c
 // 线程安全队列接口

 const int MAX = 10;

 class TSQueue {
   // 同步变量
     Lock lock;

   // 状态变量
     int items[MAX];
     int front;
     int nextEmpty;

   public:
     TSQueue();
     ~TSQueue(){};
     bool tryInsert(int item);
     bool tryRemove(int *item);
 };

 // 把队列初始化为空
 // 锁置为可用。
 TSQueue::TSQueue() {
     front = nextEmpty = 0;
 }

 // 尝试插入数据项。若队列
 // 已满，返回 false；否则返回 true。
 bool
 TSQueue::tryInsert(int item) {
     bool success = false;

     lock.acquire();
     if ((nextEmpty - front) < MAX) {
         items[nextEmpty % MAX] = item;
         nextEmpty++;
         success = true;
     }
     lock.release();
     return success;
 }

 // 尝试取出数据项。若队列
 // 为空，返回 false；否则返回 true。
 bool
 TSQueue::tryRemove(int *item) {
     bool success = false;

     lock.acquire();
     if (front < nextEmpty) {
         *item = items[front % MAX];
         front++;
         success = true;
     }
     lock.release();
     return success;
 }
```

队列只存放固定数量 MAX 个元素。队列满时，插入请求返回错误；同样，队列空时，删除请求返回错误。5.4 节将说明**条件变量**如何让调用线程**等待**，而不是返回错误：插入时，线程一直等到队列中有空间存放该元素；删除时，线程一直等到队列中至少有一个元素可返回。

TSQueue 的实现定义了一个环形队列，数据存放在固定大小的数组 `items[MAX]` 中。状态变量 `front` 是队列中下一个将被删除的元素（如果有的话）；`nextEmpty` 是下一个新元素的位置（如果有的话）。为了让例子尽可能简单，队列中只能存放和取出 `int` 类型的元素，并且我们假定累计存放的元素总数可以用 64 位整数表示。

所有这些变量都与该对象的单线程版本完全一样。锁使得 `tryInsert` 与 `tryRemove` 能像单线程版本那样，原子地读写多个变量。

::: info 例
在刚获取锁的那一刻，TSQueue 满足哪些约束？在释放锁之前的那一刻，又有哪些约束成立？
:::

::: warning 答
由于锁强制实施互斥，而且线程修改状态变量时总是持有锁，所以在获取锁的那一刻，对象的状态变量必然处于以下两种情形之一：(i) 初始状态，或 (ii) 前一个线程释放锁时留下的状态。这些约束与使用有界队列的单线程代码完全相同：

- 曾经插入队列的元素总数为 `nextEmpty`。

- 曾经从队列删除的元素总数为 `front`。

- `front <= nextEmpty`

- 队列中当前的元素个数为 `nextEmpty - front`。

- `nextEmpty - front <= MAX`

锁的持有者在释放锁之前，总会重新确立这些约束。□
:::

::: info 例
如果不持有锁，这些约束还成立吗？
:::

::: warning 答
**不成立。** 直觉上似乎可以认为：如果这些约束在释放锁之前的那一刻成立，那么它们在释放锁之后的那一刻也必定成立。然而事实并非如此。在这段时间里，别的某个线程可能已经获取了锁，并且正在修改状态变量。一般说来，如果不持有锁，关于对象的状态变量就**什么都**不能说。□
:::

#### 临界区

**临界区**（critical section）是一段原子地访问共享状态的代码。只要保证线程在执行任何临界区时持有该对象的锁，就能保证每个临界区看起来都是原子地作用于其共享状态。`tryInsert` 与 `tryRemove` 两个方法中各有一个临界区。

有两点值得注意：

- 每个类都可以定义多个作用于该类所定义共享状态的方法，因此**每个类可以有多个临界区**。不过，对于类的每个实例（也就是每个对象），同一时刻只有一个线程持有该对象的锁，所以**对每个共享对象实例，同一时刻只有一个线程真正执行其中的临界区。** 对 TSQueue 类而言，如果一个线程调用 `queue1.tryInsert`，另一个线程调用 `queue1.tryRemove`，那么插入要么发生在删除之前，要么反过来。

- 一个程序可以创建**类的多个实例**。每个实例都是一个共享对象，而每个共享对象都有自己的锁。因此，不同的线程可能同时活跃在不同共享对象实例的临界区中。对 TSQueue 类而言，如果一个线程调用 `queue1.tryInsert`，另一个线程调用 `queue2.tryRemove`，第三个线程调用 `queue3.tryInsert`，那么这三个线程可能同时执行着作用于 TSQueue 类**不同实例**的临界区代码。

#### 使用共享对象

共享对象的分配方式与其他对象相同：可以用 `malloc` 和 `new` 从堆上动态分配，也可以在程序中声明静态变量，把它们静态地分配在全局内存中。

多个线程必须能够访问共享对象。如果共享对象是全局变量，那么线程代码可以用对象的全局名字来引用它，编译器会算出相应的地址。如果共享对象是动态分配的，那么每个使用该对象的线程都需要一个指向它的指针或引用。

把指向共享对象的指针交给线程，有两种常见做法：(1) 在创建线程时把指向该共享对象的指针传给线程；(2) 把共享对象的引用存放在其他共享对象（例如容器）中。例如，程序可以有一个全局的、共享的（而且是同步的！）哈希表，线程用它来存放和取回指向其他共享对象的引用。

图 5.5 展示了一个简单的程序：它创建三个队列，然后创建若干线程向这些队列插入元素；接着从每个队列删除 20 个元素，并打印删除得到的值。初始的主线程用 `new` 在堆上分配这些共享队列，并给每个工作线程一个指向其中一个共享队列的指针。

<div class="code-cap"><span class="code-label">图 5.5</span>这段代码创建三个 TSQueue 对象，然后向这些队列添加和删除一些元素。我们使用 <code>thread_create_p</code> 而不是 <code>thread_create</code>，以便把指向应当使用的队列的指针传给新创建的线程。</div>

```c
 // TSQueueMain.cc
 //   TSQueue 的测试代码。

 int main(int argc, char **argv) {
     TSQueue *queues[3];
     sthread_t workers[3];
     int i, j;

     // 启动工作线程执行插入。
     for (i = 0; i < 3; i++) {
         queues[i] = new TSQueue();
         thread_create_p(&workers[i],
                    putSome, queues[i]);
     }

     // 等一些数据项被放入。
     thread_join(workers[0]);

     // 从每个队列各取出 20 个数据项。
     for (i = 0; i < 3; i++) {
         printf("Queue %d:\n", i);
         testRemoval(&queues[i]);
     }
 }

 // 向队列插入 50 个数据项。
 void *putSome(void *p) {
     TSQueue *queue = (TSQueue *)p;
     int i;

     for (i = 0; i < 50; i++) {
         queue->tryInsert(i);
     }
     return NULL;
 }

 // 从队列取出 20 个数据项。
 void testRemoval(TSQueue *queue) {
     int i, item;

     for (i = 0; i < 20; j++) {
         if (queue->tryRemove(&item))
           printf("Removed %d\n", item);
         else
           printf("Nothing there.\n");
         }
     }
 }
```

**警告：把共享对象放在堆上，而不是栈上。** 虽然没有什么能阻止你把共享对象写成过程或方法中的自动变量，但你不应当写这样的程序。在过程调用期间，编译器把自动变量（有时被称为“局部变量”，这个叫法很有道理）分配在栈上。如果一个线程把指向自己某个自动变量的指针或引用传给另一个线程，随后又从分配该自动变量的过程返回，那么第二个线程手中的指针就指向第一个线程栈上的某块区域，而这块区域可能已被挪作他用。为了防止这种错误，少数带垃圾回收的语言（例如 Google 的 Go）会在自动数据可能被过程之外的代码引用时，自动把所有自动数据改为在堆上分配。

你也许想争辩说：对某个特定的程序而言，你知道在该过程与之共享某个对象的所有线程用完这个对象之前，该过程绝不会返回，因此共享该过程的某个局部变量是安全的。这种说法的问题在于，代码会随时间演变，从而引入一个危险而隐蔽的缺陷。在跨线程共享动态分配的变量时，最好养成这样的习惯：只共享来自堆的变量——绝不共享来自栈的变量。

## 5.4　条件变量：等待变化

条件变量（condition variable）提供了一种机制，让一个线程等待另一个线程采取某种动作。例如，在图 5.3 的线程安全队列例子中，当我们试图从空队列中取出一个元素时，与其返回一个错误，不如一直等到队列非空，然后总能返回一个元素。

类似地，Web 服务器可以等待新请求到达；字处理程序可以等待某个键被按下；气象模拟器的协调线程可以等待负责计算各地区温度的工作线程完成；或者，在我们的地球可视化程序例子中，负责渲染屏幕某一部分的线程可以等待用户命令，或等待新数据来更新视图。

在所有这些情形中，我们都希望一个线程等待某个动作改变系统状态，以便该线程能够继续推进。

<div class="code-cap"><span class="code-label">图 5.6</span>TSQueue::remove 的轮询式实现。代码在循环中反复重试，直到成功取出一个元素。</div>

```c
int
TSQueue::remove() {
    int item;
    bool success;

    do {
        success = tryRemove(&item);
    } until(success);
    return item;
}
```

一种让线程等待的办法是*轮询*（poll）——反复检查共享状态，看它是否已经改变。如图 5.6 所示，remove 的轮询式实现只需一个简单的包装，反复调用 tryRemove 直到它返回成功。遗憾的是，这种做法效率很低：等待的线程不停循环，也就是*忙等*（busy-wait），消耗处理器周期却不做有用的推进。更糟的是，忙等可能耽误其他线程的调度——而这些线程也许正是循环线程所等待的那一个。

::: tip 用 sleep 补救？
我们常常发现，学生想通过加入一段延迟来“修好”轮询式做法。例如，在图 5.6 中，我们可以在每次 tryRemove 调用失败后加一次 sleep 调用，让出处理器（比如）100 毫秒。这样，在等待线程等待期间，其他线程就可以运行。

这种做法有两个问题。第一，它虽然减轻了轮询的低效，却没有消除低效。挂起和调度一个线程会带来不小的开销，而含有许多轮询线程的程序仍会浪费大量资源。第二，周期性轮询会增加延迟。在地球可视化程序的例子中，如果等待键盘输入的线程在每次检查之间都要等 100 毫秒，应用会明显变得迟钝。

举一个极端的例子。本书作者之一曾让一位员工实现一个提供若干层处理的网络服务器，每一层都有一个线程，负责从上一层接收工作、把工作交给下一层。对该服务器所作的测量显示出令人吃惊的糟糕性能：我们预期每个请求只需几毫秒，结果每个请求要花上半秒多一点。好在性能差到这种地步，问题反而容易定位：各层之间通过很像 TSQueue 的有界队列传递工作，而队列的 remove 方法却是带 100 毫秒延迟的轮询循环。有五层这样的处理，服务器就变得无法使用了。幸好修法很简单：改用条件变量。
:::

### 5.4.1　条件变量的定义

*条件变量*是一种同步对象，它让线程能够高效地等待由某把锁保护的共享状态发生变化。条件变量有三个方法：

- **`CV::wait(Lock *lock)`。** 这个调用原子地*释放锁*并*挂起调用线程的执行*，把调用线程放入该条件变量的等待列表。之后，当调用线程被重新启用时，它会在从 `wait` 调用返回之前*重新获取锁*。

- **`CV::signal()`。** 这个调用从条件变量的等待列表中取下一个线程，并把它标记为可以运行（也就是把它放入调度器的就绪列表）。如果等待列表上没有线程，`signal` 不起作用。

- **`CV::broadcast()`。** 这个调用把条件变量等待列表上的所有线程都取下，并把它们标记为可以运行。如果等待列表上没有线程，`broadcast` 不起作用。

**警告：** 注意，条件变量的 `wait` 与 `signal` 不同于 UNIX 系统调用 wait 和 signal。这一命名虽不理想，却由来已久。在本书中，我们一律用“UNIX wait”和“UNIX signal”指称 UNIX 中的那两个调用，而用 `wait` 与 `signal` 简单指称条件变量的操作。

条件变量用来等待共享状态发生变化，而对共享状态的更新必须始终由锁来保护。因此，条件变量的 API 被设计成与锁协同工作。上述三个方法（`wait`、`signal` 和 `broadcast`）都只应在持有相应锁的情况下调用。

<div class="code-cap"><span class="code-label">图 5.7</span>用条件变量等待的设计模式（上）与唤醒等待者的设计模式（下）。由于许多临界区既需要等待又需要发信号，这两种设计模式常常合并写在同一个方法里。</div>

```c
SharedObject::someMethodThatWaits() {
    lock.acquire();

// 在此读和/或写共享状态。

    while (!testOnSharedState()) {
        cv.wait(&lock);
    }
    assert(testOnSharedState());

// 在此读和/或写共享状态。

    lock.release();
}

SharedObject::someMethodThatSignals() {
    lock.acquire();

// 在此读和/或写共享状态。

// 若状态发生了变化，且这种变化
// 可能让另一个线程取得
// 取得进展，就 signal（或 broadcast）。

    cv.signal();

    lock.release();
}
```

共享对象的标准设计模式是：一把锁，加上零个或多个条件变量。使用条件变量等待的方法如图 5.7 上半部分所示。在这段代码中，调用线程先获取锁，然后就可以读写该共享对象的状态变量。为了等到 testOnSharedState 成功，线程对共享对象的条件变量 cv 调用 `wait`。这一调用原子地把线程放入等待列表并释放锁，从而让其他线程可以进入临界区。一旦等待的线程被唤醒，它就重新获取锁，并从 `wait` 返回。此时管程可以安全地检查状态变量，看 testOnSharedState 是否成功。如果成功，管程就执行自己的任务，释放锁并返回。

图 5.7 下半部分给出与之配套的代码，用来唤醒等待的线程。只要一个线程对共享对象状态的修改使某个等待线程能够继续推进，它就必须通过条件变量向该等待线程发信号。

在条件变量上等待的线程必须在循环中检查对象的状态。条件变量的 `wait` 方法先释放锁（好让其他线程改变所关心的状态），然后再重新获取锁（以便再次检查该状态）。

同样，一个线程调用 `signal`（或 `broadcast`）的唯一理由，是它刚刚以可能引起某个等待线程关注的方式改变了共享状态。要修改共享状态，线程必须持有保护状态变量的锁，因此 `signal` 和 `broadcast` 也总是在持有锁时调用。

**讨论。** 条件变量的设计经过仔细推敲，目的是与锁和共享状态配合工作。条件变量的精确定义包含三条值得进一步说明的性质：

- 条件变量是*无记忆的*（memoryless）。除了一条等待线程的队列，条件变量本身没有任何内部状态。条件变量不需要自己的状态，因为它总是在带有自身状态的共享对象内部使用。如果当前没有线程在条件变量的等待列表上，`signal` 或 `broadcast` 就不起作用。除非线程持有锁、检查状态变量并发现需要等待，否则它不会调用 `wait`。因此，条件变量对先前的 `signal` 或 `broadcast` 调用没有“记忆”。在 `signal` 被调用之后，如果过一段时间另一个线程才调用 `wait`，它将阻塞到*下一次* `signal`（或 `broadcast`）被调用为止，而不管过去 `signal` 被调用过多少次。

- **`CV::wait` 原子地释放锁。** 线程总是在持有锁时调用 `wait`。`wait` 调用*原子地*释放锁，并把线程放入条件变量的等待列表。原子性保证了这样几件事之间没有间隙：检查共享对象的状态、决定等待、把等待线程加入条件变量的队列、以及释放锁以便其他线程访问共享对象。如果线程在调用 `wait` 之前先释放锁，就可能错过一次 signal 或 broadcast，从而永远等下去。考虑这种情况：线程 $T_{1}$ 检查了对象的状态，决定等待，于是它先释放锁，打算随后把自己放入条件变量的等待列表。就在这一刻，$T_{2}$ 抢占了 $T_{1}$。$T_{2}$ 获取锁，把对象的状态改成 $T_{1}$ 想要的样子，并调用 `signal`，但等待列表是空的，所以 `signal` 调用不起作用。最后，$T_{1}$ 再次运行，把自己放到等待列表上并挂起执行。缺少原子性意味着 $T_{1}$ 错过了这次 signal，如今在等待——而且可能永远等下去。一旦 `wait` 释放了锁，在它于一次 signal 之后重新获取锁之前，可能有任意多个线程运行过。在这段时间里，状态变量可能已经改变——事实上，它们几乎*必然*已经改变。代码不能因为某件事在 `wait` 被调用之前为真，就假定 `wait` 返回时它仍然为真。关于从 `wait` 返回，你唯一应当作的假设是：锁已被持有，并且在临界区开始处成立的常规不变式仍然成立。

- 当一个等待的线程通过 `signal` 或 `broadcast` 被重新启用时，*它可能不会立即运行*。等待的线程被重新启用时，只是被移到调度器的就绪队列，而且没有任何特殊优先级，调度器可能过一段时间才运行它。此外，该线程最终真正运行时，还必须重新获取锁，这意味着在 signal 发生之后、等待者重新获取锁之前，其他线程可能已经获取并释放过锁。因此，即使期望的谓词在 `signal` 或 `broadcast` 被调用时为真，到 `wait` 返回时它也可能不再为真。这看起来像是一个很小的易错窗口，但并发程序必须对*所有*可能的调度都正确。否则，程序可能只是有时失败、并非总是失败，这会让调试变得非常困难。关于这条性质背后的历史，参见讨论 Mesa 语义与 Hoare 语义的边栏。

**警告：** 以上几点对程序员有一个重要含义：`wait` *必须始终在循环内调用*。

由于 `wait` 会释放锁，也由于 `signal` 或 `broadcast` 与 `wait` 调用的返回之间没有原子性保证，所以无法保证所检查的状态仍然成立。因此，等待的线程必须始终在循环中等待，反复检查状态，直到期望的谓词成立。也就是说，设计模式应当是：

```c
    ...
    while (predicateOnStateVariables(...)) {
      wait(&lock);
    }
    ...
```

而不是：

```c
    ...
    if (predicateOnStateVariables(...)) {
        wait(&lock);
    }
    ...
```

条件变量之所以提出这一要求，有两个根本原因：简化实现，以及提高模块化程度。

- **简化实现。** 等待的线程被重新启用后可能不会立即运行。在它运行之前，其他线程可能访问共享状态，因此当 `wait` 最终真的返回时，期望的谓词可能已不再成立。这种行为简化了条件变量的实现，又不增加使用它的代码的复杂度。调度方面不需要特殊代码：`signal` 把被唤醒的线程放入就绪列表，由调度器决定何时运行它。同样，在 `wait` 结束时重新获取锁也不需要特殊代码：被唤醒的线程在重新被调度时调用 `acquire`。与任何获取锁的尝试一样，它可能立即成功，也可能因为其他线程先获取了锁而等待。有些实现甚至更进一步，警告说 `wait` 调用即使没有线程调用 `signal` 或 `broadcast` 也可能返回。因此，不仅状态上期望的谓词*可能已不再为真*，甚至可能*从来就没有为真过*。例如，Java 对条件变量的定义允许“虚假唤醒”（spurious wakeup）：在某个 Condition 上等待时，一般允许发生“虚假唤醒”，这是对底层平台语义的一种让步。这对大多数应用程序几乎没有实际影响，因为对 Condition 的等待总应当放在循环中进行，并测试所等待的状态谓词。实现可以自由地消除虚假唤醒的可能性，但建议应用程序员始终假定它们可能发生，因而始终在循环中等待。（引自 https://docs.oracle.com/javase/8/docs/api/）

- **提高模块化程度。** 在检查共享状态的循环中等待，使共享对象的代码更具模块性，因为只要看这个 `wait` 循环，就能推断线程何时会继续执行。特别是，要知道 `wait` 循环的后置条件，我们无需检查共享对象的其余代码，去弄清 `signal` 和 `broadcast` 在哪里被调用、为什么被调用。例如，在图 5.7 中，我们不必看任何其他代码，就能知道那句 `assert` 调用永远不会失败。在循环中等待不仅简化了等待代码的编写与推理，也简化了发信号代码的编写与推理。在错误的时机发信号，永远不会让不该继续的等待线程继续执行。`signal` 和 `broadcast` 可以看作一种*提示*：现在*也许*是继续推进的好时机；如果提示是错的，也不会造成任何损害。你随时可以把一个 `signal` 换成 `broadcast`，或者增加任意多个 `signal` 或 `broadcast` 调用，而不会改变共享对象的语义。避免多余的 `signal` 和 `broadcast` 调用可能影响性能，但不影响正确性。

**结论：** 考虑到实现方式的多样性以及模块化带来的好处，`wait` 必须始终在测试期望谓词的循环内调用。

::: tip Mesa 语义与 Hoare 语义
在现代条件变量中，`signal` 或 `broadcast` 把等待的线程从条件变量的等待列表移到就绪列表。之后，当这些线程被调度运行时，它们可能要在尝试重新获取锁的过程中阻塞一段时间。因此，现代条件变量实现的是通常所说的 *Mesa 语义*（Mesa semantics，得名于 Xerox PARC 的一种早期编程语言 Mesa，该语言实现了这种语义）。尽管有这个名称，Mesa 并不是第一个采用“Mesa”语义的系统；Brinch Hansen 早在五年前就提出了这种用法。不过，PARC 是第一个在非常大的操作系统中广泛使用 Mesa 语义的机构，这个名字也就沿用了下来。

C.A.R.“Tony”Hoare 为条件变量提出了另一种定义。在 *Hoare 语义*（Hoare semantics）下，当一个线程调用 `signal` 时，发信号线程的执行被挂起，锁的所有权立即转移给某个等待的线程，该线程的执行立即恢复。之后，当被恢复的线程释放锁时，锁的所有权回到发信号的线程，后者继续执行。

在 Hoare 语义下，发信号与恢复一个等待的线程是原子的，被唤醒的线程可以假定，自唤醒它的那次 signal 发出以来状态没有改变。在 Mesa 语义下，等待总是放在循环中进行：`while (predicate()) {cv.wait(&lock);}`。在 Hoare 语义下，等待可以用一个简单的条件语句完成：`if (predicate()) {cv.wait(&lock);}`。

Mesa 语义的使用要广泛得多，但有人认为，发信号与恢复等待线程的原子性，使 Hoare 语义下的程序更容易证明活性性质。如果我们知道有一个线程正在某个条件上等待，并且我们发出了一次 signal，那么就能确定，恢复并继续推进的是这个等待的线程，而不是某个后来才到达的线程。

本书作者坚定地站在 Mesa 语义一边。Mesa 在模块化上的优势大大简化了对对象核心安全性质的推理。对于我们最关心的那些性质（也就是“线程只在应当推进时才推进”这类安全性质），对于模块化至关重要的大型程序，Mesa 语义显然更可取。本章后面将说明如何在 Mesa 语义下实现 FIFO 排队，以应对活性至上的场合。

从实践上看，这场争论已经有了定论：几乎所有系统，包括 Java 和 POSIX，都使用 Mesa 语义。据我们所知，没有任何广泛使用的系统实现 Hoare 语义。假定较弱 Mesa 语义的程序员——总是写 `while (predicate())`——写出的程序在两种定义下都能工作。与发信号和调度的开销相比，在 `while` 循环中从 `wait` 返回时“额外”做一次谓词检查，其开销不太可能显著。作为程序员，按 Mesa 语义的假设来写代码不会出错。
:::

### 5.4.2　线程生命周期再讨论

第 4 章讨论了线程如何在 READY、WAITING 和 RUNNING 三种状态之间切换。这里我们更详细地解释 WAITING 状态。

一个处于 RUNNING 状态的线程调用 `wait`，就被置入 WAITING 状态。这通常是通过把该线程的线程控制块（TCB）从就绪列表移到条件变量的等待线程列表来实现的。之后，当某个处于 RUNNING 状态的线程对该条件变量调用 `signal` 或 `broadcast` 时，该条件变量等待列表上的线程控制块中有一个（若为 `signal`）或全部（若为 `broadcast`）被移到就绪列表。这使那些线程从 WAITING 状态变为 READY 状态。再过一段时间，调度器选择一个处于 READY 的线程，把它移到 RUNNING 状态并运行。最终，被发信号的线程得以运行。

锁的情况类似。对一个已被占用的锁调用 `acquire`，会把调用者置入 WAITING 状态，调用者的 TCB 被放到与该锁关联的一个等待 TCB 列表上。之后，当锁的持有者调用 `release` 时，一个等待的 TCB 被移到就绪列表，该线程转入 READY 状态。

注意，处于 RUNNING 或 READY 的线程，其状态存放在预先定义的“全局”位置：对 RUNNING 线程来说是 CPU，对 READY 线程来说是调度器的就绪线程列表。而处于 WAITING 的线程，其状态通常存放在某个“每锁”或“每条件变量”的等待线程队列上。于是，`signal`、`broadcast` 或 `release` 调用就能很容易地找到并重新启用该条件变量或该锁上等待着的线程。

<div class="code-cap"><span class="code-label">图 5.8</span>使用 Mesa 语义条件变量实现的线程安全阻塞有界队列。</div>

```c
class BBQ{
  // 同步变量
    Lock lock;
    CV itemAdded;
    CV itemRemoved;

  // 状态变量
    int items[MAX];
    int front;
    int nextEmpty;

  public:
    BBQ();
    ~BBQ() {};
    void insert(int item);
    int remove();
};

// 把队列初始化为空，
// 锁置为可用，
// 条件变量置为空。
BBQ::BBQ() {
    front = nextEmpty = 0;
}

// 等待，直到有空间，
// 然后插入数据项。
void
BBQ::insert(int item) {
    lock.acquire();
    while ((nextEmpty - front) == MAX) {
        itemRemoved.wait(&lock);
    }
    items[nextEmpty % MAX] = item;
    nextEmpty++;
    itemAdded.signal();
    lock.release();
}

// 等待，直到有数据项，
// 然后取出数据项。
int
BBQ::remove() {
    int item;

    lock.acquire();
    while (front == nextEmpty) {
        itemAdded.wait(&lock);
    }
    item = items[front % MAX];
    front++;
    itemRemoved.signal();
    lock.release();
    return item;
}
```

## 5.5　共享对象的设计与实现

多线程编程素有“困难”之名，但共享对象（shared object）为编写简单、安全的多线程程序提供了基础。本节给出一套方法，用来借助共享对象写出正确的多线程代码。

- 首先给出设计共享对象的高层方法：给定一个并发问题，应当从哪里着手？（5.5.1 节）

- 给出六条具体规则（也就是最佳实践），在编写多线程共享对象时应当始终遵守。（5.5.2 节）

- 描述 C、C++ 和 Java 代码中多线程编程的三个常见陷阱。（5.5.3 节）

我们的经验是：遵循这套方法和这些规则，你写出的代码不仅更可能正确，也更容易被他人阅读、理解和维护。

::: tip 论简单
贯穿本书的一个主题是：简单的抽象对于构建健壮、可靠的操作系统至关重要。操作系统把可靠性看得极重；一旦操作系统出错，计算机就会暂时无法使用，甚至更糟。然而，要想完整地测试某段多线程操作系统代码在所有可能条件和所有可能调度交错下都能正常工作，几乎是不可能的。这就迫使我们去设计那种第一次运行就正确的解法，而办法就是让代码保持简单。

对并发代码尤其如此：代码仅仅“能跑”是不够的，还必须简单到足以理解。我们常常看到学生在作业和考试的解答里写出盘根错节的并发代码。或许正因为这门课很难，学生便以为自己的解答也必须难以理解！这类解法有时确实能用，但更多时候，复杂性掩盖了设计缺陷。

即便你的代码在字面上是正确的，我们也希望你不要就此止步。你能轻松说清它*为什么*正确吗？如果不能，就再想一遍。哪怕这一次你能让代码跑通，日后也可能有别人要来修改它。并发代码若要长期可维护，下一位接手的人就必须能够读懂它。

然而在技术圈里，“简单”常常被当成贬损之词。有人可能会说：“这谁不会做啊！”言下之意是瞧不起你。我们站在对立面：简单的设计应当被视为褒奖。只有在绝对必要时才应引入复杂性。想想你的设计可能处于的三种状态（这份清单要感谢 John Ousterhout）：

- 代码简单到任何人都能看懂。如果有人这样对你说，恰当的反应是把它当作夸奖，并回答：“谢谢。”

- 代码复杂到只有作者本人能看懂。作为让自己显得不可替代的一种策略（毕竟，别人不理解代码就无法修复或改进它），这在短期内也许有用，但长期来看并不是好主意。你终究会想去做点新东西！

- 代码复杂到连作者本人都看不懂。并发代码经常落入这一类，而在我们看来，这完全没有必要。用本节介绍的规则，可以帮助你的代码落入第一类，而不是最后一类。
:::

当然，只编写单个共享对象是不够的。大多数程序都有多个共享对象，把它们组合起来时又会出现新的问题。但在尝试组合多个共享对象之前，我们必须确保每一个单独的对象都是正确的。第 6 章讨论程序使用多个共享对象时出现的问题。

### 5.5.1　高层方法

一个共享对象包含公有方法、私有方法、状态变量和同步变量；其中同步变量包括一把锁和一个或多个条件变量（condition variable）。在这个层面上，共享对象编程与标准的面向对象编程十分相似，区别只在于我们为每个共享对象增加了同步变量。这种相似是有意为之的：锁与条件变量的接口经过精心定义，使我们能够继续沿用那些熟悉的、用于编写和推理对象的技术。

因此，为一个共享对象设计类时，大多数高层设计难题与单线程编程中的类设计相同：

- 把问题分解为若干对象。

- 对每个对象：定义清晰的接口；确定合适的内部状态与不变式（invariant），以支撑该接口；用恰当的算法实现方法来操纵这些状态。

这些步骤需要创造力，也需要扎实的工程判断力与直觉。从单线程编程转向多线程编程，并不会让这些步骤难上多少。

与在单线程程序中实现一个类相比，共享对象在多线程情形下需要新增的步骤如下，它们相当直接：

1. 添加一把锁。

2. 添加获取与释放锁的代码。

3. 确定并添加条件变量。

4. 添加使用条件变量进行等待的循环。

5. 添加 `signal` 与 `broadcast` 调用。

我们依次讨论这些步骤。

除了这些相当机械的改动之外，其余代码的写法与单线程情形相同。

1. **添加一把锁。** 每个共享对象都需要一把锁作为成员变量，以强制对对象共享状态的互斥访问。本章聚焦于最简单的情形：每个共享对象恰好包含一把锁。第 6 章将讨论更高级的变体，例如一种“所有权”设计模式——通过更高层的程序结构，确保任一时刻至多只有一个线程拥有并可以访问某个对象，以此实现互斥。

2. **添加获取与释放锁的代码。** 所有访问对象共享状态——即在多个线程之间共享的任何状态——的代码，都必须持有该对象的锁。通常，对象的全部成员变量都属于共享状态。最简单也最常见的做法是：在每个公有方法的开头获取锁，在每个公有方法的末尾释放锁。这样做便于你检查代码，确认需要时锁总是被持有；这也意味着每个私有方法被调用时锁已经持有，无需再次获取。

 **警告**：你也许会想在某些方法中、或方法的某些部分中设法避免加锁。在你成为有经验的程序员，并对代码做过充分的性能剖析、确认这种“优化”能显著提升程序速度，*而且*完全理解编译器和体系结构的指令重排序所带来的危害之前，不要被这种“优化”诱惑。获取一把无争用的锁是相对廉价的操作；相比之下，推理内存访问的交错相当困难——而现代编译器与处理器所做的指令重排序只会让它更难。本节稍后将讨论一种常见（也被滥用）的“优化”——双重检查锁定（double-checked locking），使用它相当危险。

3. **确定并添加条件变量。** 如何确定一个共享对象需要哪些条件变量？一种系统化的方法是逐个考察每个方法，问自己：“这个方法在什么时候必须等待？”然后，把方法可能等待的每种情形映射到一个条件变量。一个类应当有多少个条件变量、每个条件变量代表什么，你有相当大的自由。一个好的选择是：方法每有一种必须等待的情形，就添加一个条件变量。

 **例：使用两个条件变量的阻塞有界队列。** 在阻塞有界队列的例子中，如果队列已满，`insert` 必须等到别的线程取走一项，因此我们创建了条件变量 itemRemoved；同样，如果队列为空，`remove` 必须等到别的线程插入一项，因此我们创建了条件变量 itemAdded。在这种情况下，创建两个条件变量是很自然的：itemAdded 用于等待队列中有项，itemRemoved 用于等待队列中有空位。

 不过，单个条件变量往往也够用。事实上，早期版本的 Java 为每个对象只定义一个条件变量，不允许程序员再分配额外的条件变量。采用这种做法时，任何因任何原因等待的线程都使用那一个条件变量；如果这个条件变量被因不同原因而等待的不同线程共用，那么任何要唤醒其他线程的线程都必须在该条件变量上 `broadcast`。

 **例：只用一个条件变量的阻塞有界队列。** 用单个条件变量（例如 somethingChanged）实现阻塞有界队列也是可行的，`insert` 与 `remove` 中的线程都可以在它上面等待。采用这种做法时，`insert` 和 `remove` 都需要用 `broadcast` 而不是 `signal`，才能确保正确的线程有机会运行。

 程序越复杂，这些取舍就越有意思。例如，设想一个 ResourceManager 类，允许调用线程请求对 $n$ 个不同资源中任意一个子集的独占访问。可以设想创建 $2^{n}$ 个条件变量，这样请求线程就可以在恰好代表它所需组合的条件变量上等待。然而，更简单的做法是只设一个条件变量，让所有请求线程都在其上等待，并在每次有资源被释放时对其 `broadcast`。视资源数量和预期等待线程数而定，这种更简单的做法甚至可能更高效。要点在于：一个共享对象该用多少个条件变量，并没有硬性规定。选择条件变量需要思考，对于同一个类，不同的设计者可能会用不同数目的条件变量。与许多其他设计决策一样，这取决于程序员的品味、判断与经验。问一句“这个方法在什么时候必须等待？”，将帮助你找到对自己而言最自然的、思考共享对象条件变量的方式。

4. **添加使用条件变量进行等待的循环。** 在你判定可能需要在返回前等待的每个方法中，加入一个 `while(...) {cv.wait()}` 循环。记住，每一次 `wait` 调用都必须包在一个测试相应谓词的 while 循环中。现代实现几乎无一例外地提供 Mesa 语义（Mesa semantics），并且常常允许虚假唤醒（spurious wakeup），即线程即使没有任何其他线程调用 `signal` 或 `broadcast`，也可能从 `wait` 返回。因此，线程在继续执行前必须总是检查条件。即使 `signal` 或 `broadcast` 调用发生时条件为真，等到被唤醒的线程真正恢复执行时，它也可能已经不为真了。

 **模块化的好处。** 如果你总是在 while 循环中等待，代码就会变得高度模块化。你只需看等待处的那段代码，就能在它继续执行时知道条件成立，*而无需*检查任何其他代码。即使对 `signal` 或 `broadcast` 的调用是错误的，也不会改变等待代码的行为。例如，看下面这段代码中的断言：

```c
   while (!workAvailable()) {
       cond.wait(&lock);
   }
   assert(workAvailable());
```

 我们通过局部检查就能知道该断言成立，*而完全不必了解任何调用 `signal` 或 `broadcast` 的代码*。在 while 循环中等待，也让 signal 与 broadcast 一侧的代码更健壮：多写一个 `signal`，或把一个 `signal` 改成 `broadcast`，都不会引入缺陷。

 **提示：自顶向下设计。** 开始写代码时，你可能已经知道某个方法需要包含一个等待循环，但还不确定谓词究竟应该是什么。这种情况下，一个有用的做法是先给执行该测试的私有方法起个名字（例如上例中的 workAvailable），稍后再写出该函数的定义。

5. **添加 `signal` 与 `broadcast` 调用。** 正如你必须决定方法在什么时候可以等待，你也必须决定方法在什么时候可以让其他等待的线程继续。通常很容易问一句：“调用这个方法能否让另一个线程继续？”如果答案是肯定的，就加上 `signal` 或 `broadcast` 调用。但该用哪一个？

 `CV::signal` 适用于以下情形：(1) 至多只有一个等待线程能够继续推进；(2) 在该条件变量上等待的任意一个线程都能继续推进。相反，`broadcast` 在以下情形下是必需的：(1) 可能有多个等待线程都能继续推进；(2) 不同线程在使用同一个条件变量等待不同的谓词，因此一部分等待线程能继续推进，另一部分则不能。

 **例：** 考虑前面描述的 $n$ 资源 ResourceManager 问题。对于只用一个条件变量的解法，每当有资源被释放，我们都必须在该条件变量上 `broadcast`。我们并不知道哪些线程能够继续推进，所以只能让它们全都去检查。如果改用 `signal`，那么收到 `signal` 的可能是“错误”的线程，而某个本可以继续推进的线程却仍然阻塞着。使用 `broadcast` 总是安全的：即使在 `signal` 就足够的情形下，最坏的结果也不过是所有等待线程都醒来、在 while 循环里检查条件，而只有一个线程继续走出循环。与 `signal` 相比，这会多消耗一些资源，但不会引入任何缺陷。

### 5.5.2　实现最佳实践

上面描述的是设计共享对象时应当遵循的基本思路。为了更具体一些，下面给出一组我们强烈建议你遵守的六条简单规则；它们是编写共享对象代码的一组“最佳实践”。

::: tip 编码规范、说教与布道
有些程序员反感编码规范。我们不明白他们的逻辑。对并发编程而言尤其如此：少数几个良好的设计模式已经经受住了时间的检验（也经受住了许多偏离这些模式的不幸之人的检验）。对并发编程来说，*调试是行不通的*。你必须依靠：(a) 写出正确的代码；(b) 写出你和别人都能读懂、理解的代码——不仅是现在，还包括日后代码不断变化之时。遵循我们给出的规则，有助于你写出正确、可读的代码。

在讲授多线程编程时，我们把本节描述的六条规则当作学生在课程中编写所有多线程代码时必须遵守的*编码规范*。我们说：“你离开这门课之后做什么，我们管不了；但在这门课上，任何违反这些规范的解法，按定义就是*错的*。”

事实上，我们对这些规则的信念如此之强，以至于其中一位作者在课堂上真的站到桌子上，把它们宣布为多线程编程的“六诫”：

1. 你当永远以同样的方式做事。

诸如此类。

这些规则的具体表述（以及呈现方式），来自我们数十次向数百名学生讲授多线程编程、并归纳常见错误的经验。我们发现，当我们坚持要求学生遵守这些规则时，绝大多数人都能轻松地为共享对象写出清晰、正确的代码。相反，在这门课早先的版本中，当我们把这些条目表述为“强烈建议”时，许多学生便无所适从，连最简单的共享对象也写不出来。

我们对学习多线程编程的人的建议是：把这些规则当作既定前提，严格照做一个学期左右，直到编写共享对象变得轻松为止。到那时，你很可能已经足够理解并发编程，可以自行决定是否继续遵守这些规则。

我们也相信，有经验的程序员同样能从严格遵守这些规则中获益。自从开始讲授这些规则，我们自己也约束自己遵守它们，除非有非常好的理由不这么做。我们发现例外情况很少。反过来说，每当我们发现自己想要偏离规则时，绝大多数情况下，强迫自己按规则重写代码后，代码都会变得更好。

这些规则也许显得主观（它们确实主观），但绝谈不上新鲜。三十多年前，Lampson 和 Redell 的论文《Experience with Processes and Monitors in Mesa》就给出过类似的建议（语气更为克制）。
:::

1. **一致的结构。** 第一条规则是一条元规则，是其他五条规则的基础：*遵循一致的结构。* 用干净、一致的结构编程总是有用的，但对共享对象而言，严格遵守久经考验的设计模式尤为重要。至少，即便一种方式并不天生优于另一种，每次都采用同一套策略也能：(1) 让你从细节中解放出来，专注于核心问题，因为标准做法的细节已经成了习惯；(2) 让后来者更容易审阅、维护和调试你的代码。（也会让*你*自己更容易维护和调试代码。）打个比方，电工在为不同用途选择导线颜色时遵循标准：白色是零线，黑色或红色是火线，铜色是地线。电工不必琢磨“嗯，今天腰带上白色线比黑色线多一点，地线该用白色还是黑色？”当她走进上个月布过线的房间，不必花时间回忆哪种颜色是哪种；当她走进一个从未见过的房间，也能立刻判断出线路在做什么，而无须一路追到配电盘。编码规范也有类似的好处。不过，对并发程序而言，证据表明我们所描述的那些抽象*确实*优于几乎所有其他做法。在你成为*非常*有经验的并发程序员之前，请利用前人的宝贵经验。等你成了并发高手，欢迎你去发明更好的捕鼠器。当然，偏离标准可以偷工减料，偶尔省下一两行输入；但你得花几分钟思考才能说服自己在每个具体场合都是对的（还得再花几分钟写注释，说服下一个看代码的人你是对的），而一旦错了，就要花几小时甚至几周去追查缺陷。实在不值得。

2. **始终用锁和条件变量进行同步。** 许多操作系统，如 Linux、Windows 和 MacOS，都提供多种同步原语。本章末尾将描述其中一种——信号量（semaphore），它在操作系统内核实现中尤其常用。与锁和条件变量相比，信号量同样强大：你可以用信号量构造条件变量，反之亦然。既然如此，为什么要选定一种而舍弃另一种？我们的建议是：你应当能够读懂和理解信号量，以便看懂遗留代码；但新代码只应使用锁和条件变量。几乎所有情况下，使用锁和条件变量的代码都比等价的信号量代码更清晰，因为它更“自文档化”。如果代码结构良好，每个同步动作在做什么都应当一目了然。诚然，有时信号量看起来与你要做的事情完美契合，因为你可以把对象的不变式精确映射到信号量的内部状态；例如，用信号量可以写出极其简洁的阻塞有界队列。但下个月代码改动之后会怎样？这种契合还能保持吗？为了保持一致与简单，请从两种风格中选一种并坚持下去。在我们看来，正确的选择是使用锁和条件变量。

3. **始终在方法开头获取锁，并在返回之前释放。** 这条规则延续了一致结构的原则：选定一种做事方式，并始终遵循。好处在于，同步按方法组织，读代码时很容易看出哪里持有锁、哪里没有。反过来说，如果 `acquire` 和 `release` 调用埋藏在方法中间，就很难快速检查和理解代码。退一步看，如果你能指出某段代码在逻辑上是一组需要持锁的动作，那么这一段大概就应该单独成为一个过程：它是一组逻辑上相关的动作。如果你发现自己想在过程中间获取锁，这通常是一个危险信号，提示你应当把正在考虑的那部分拆成单独的过程。我们每个人有时都会在该新建过程时偷懒。利用这个信号，结果会是更清晰的代码。

 这条规则有两个推论。第一，如果你的代码结构良好，所有共享数据都会封装在对象中，因而所有对共享数据的访问都由锁保护。由于编译器和处理器*从不*跨越锁操作重排指令，这条规则就保证了指令重排序不会成为你代码的隐患。第二，我们不时看到学生试图在一个过程中获取锁，在另一个过程中释放它，更糟的是，在完全不同的线程中释放。（一种流行的想法是：在父线程中获取锁，通过 thread_fork 传给子线程，让子线程启动后释放它。）*不要这样做。* 首先，这会让读代码的人很难判断哪些共享变量由哪把锁保护；而在过程开头获取、在末尾释放，哪些变量对应哪把锁就一目了然。虽然一些早期的线程系统允许传递锁，但大多数新设计的系统都禁止这样做。例如在 POSIX 中，由非加锁线程调用锁释放是“未定义”的。也就是说，它在某些系统上也许能工作，但不可移植。在 Java 中，这被完全禁止。

4. **始终在操作条件变量时持有锁。** 你在操作共享状态之后于条件变量上发出信号，是因为另一个线程正在循环中等待共享状态的某个测试变为真。条件变量离开共享状态就没有意义，而共享状态只应在持锁时访问。许多库强制执行这条规则——不持有相应的锁就不能调用条件变量方法。然而，有些运行时系统和库允许马虎行事，所以要小心。

5. **始终在 `while()` 循环中等待。** 模式应当永远写成 `while (predicateOnStateVariables(...)) { condition->wait(&lock); }`，而绝不能写成 `if (predicateOnStateVariables(...)) { wait(&lock); }`。这里，predicateOnStateVariables(...) 是检查当前对象的状态变量、以决定线程是否应当继续的代码。你也许会想：既然能从程序的全局结构推断出，尽管有 Mesa 语义，线程每次从 wait 返回时都可以继续，那么何不用 if 条件而不是 while 循环来守护 `wait` 调用？不要受这种诱惑。if 能用的场合 while 都能用，而 while 还能用在 if 不能用的场合。按照一致结构的原则，每次都采用同一种方式。此外还有三个问题。

 使用 if 会破坏模块化。在上面的例子中，要知道用 if 是否可行，你必须考虑程序的全局结构：有哪些线程、`signal` 在哪里调用，等等。问题在于，某个方法中代码的改动（比如增加一个 `signal`）可能会在另一个方法（`wait` 所在之处）中引发缺陷。使用 while 则是自文档化的；任何人都能看着这处 `wait`，确切知道线程何时可能继续。始终使用 while，会让你在放置 `signal` 的位置上获得极大的自由。事实上，`signal` 变成了一个提示——你可以在正确程序的任意位置添加 signal，程序依然正确。

 使用 if 会破坏可移植性。有些条件变量的实现允许虚假唤醒，有些则不允许。例如，Java 和 POSIX pthreads 库中的条件变量实现都允许在没有线程调用 `signal` 或 `broadcast` 的情况下从 `wait` 返回。

6. **（几乎）永远不要用 `thread_sleep`。** 许多线程库提供 `thread_sleep` 函数，使调用线程挂起一段墙钟时间。时间一到，该线程被放回调度器的就绪队列，可以再次运行。永远不要用 `thread_sleep` 让一个线程等待另一个线程完成某项任务。等待条件变为真，正确的做法是在条件变量上 `wait`。一般来说，只有当你想在某个特定的实时时刻执行动作时，`thread_sleep` 才适用，例如设定一个超时，用来判定远程服务器已无响应。如果你发现自己写出 `while(testOnObjectState()) {thread_sleep();}`，请把它当作一个危险信号：你很可能正在犯错。同样，如果线程必须等待对象状态改变，它应当在条件变量上 `wait`，而不是简单地调用 thread_yield。只有当某个*仍能继续推进*的低优先级线程想让高优先级线程运行时，才应使用 thread_yield。

### 5.5.3　三个陷阱

下面介绍三个常见的陷阱。第一个是双重检查锁定，它在 C、C++ 和 Java 等多种编程语言中都是问题。第二个和第三个陷阱是 Java 特有的。Java 是一门现代的类型安全语言，从诞生之初就支持线程。这种内建支持让 Java 中的多线程编程很方便。然而，这门语言的某些方面*过于*灵活，可能助长不良做法。我们在此指出这些陷阱。

1. **双重检查锁定。** 我们强烈建议：凡是访问对象成员变量的方法，都应在整个方法期间持有该共享对象的锁。程序员常常想省掉其中一些加锁与解锁操作。不幸的是，这类努力往往导致代码复杂、错误，或者两者兼有。为了说明其中的困难，来看*双重检查锁定*（double-checked locking）设计模式。它的典型例子是一个对象，在任何线程第一次需要它时才被分配并初始化。（这个例子和分析取自 Meyers 与 Alexandrescu 的《C++ and the Perils of Double-Checked Locking》，http://www.aristeia.com/Papers/DDJ_Jul_Aug_2004_revised.pdf）作为优秀的程序员，我们可以把这种延迟分配藏在对象 Singleton 内部，由它返回指向该对象的指针，必要时创建该对象。“优化”之处在于：如果对象尚未分配，就获取锁；如果对象已经存在，就避免获取锁。由于第一次检查与获取锁之间可能存在竞态条件，必须在锁内再次检查。

```c
   class Singleton {
   public:
       static Singleton* instance();
       Lock lock;
       ...
   private:
       static Singleton* pInstance;
   };

   Singleton* Singleton::pInstance = NULL;

   // 错误！不要这样写！
   Singleton* Singleton::instance() {
       if (pInstance == NULL) {
           lock.acquire();
           if (pInstance == NULL){
               pInstance = new Instance();
           }
           lock.release();
       }
       return pInstance;
   }
```

 尽管直觉上很吸引人，*这段代码是行不通的。* 问题在于语句 `pInstance = new Instance()` 并不是原子操作；事实上，它至少包含三步：为 Singleton 对象分配内存；运行构造函数以初始化该对象的内存；让 pInstance 指向这个新构造出来的对象。问题在于，现代编译器和硬件体系结构可以重排这些事件的顺序。于是，线程 1 可能先执行第一步、再执行第三步；随后线程 2 调用 instance，看到 pInstance 非空，便返回它，并在线程 1 完成初始化之前就开始使用这个对象。

 *讨论。* 这只是在试图省略锁时潜伏的危险的一个例子；这个教训适用于更广的范围。这个例子极其简单——不到 10 行代码，逻辑也非常简单——然而已发表的好些解法都是错的。正如 Meyers 和 Alexandrescu 指出的，一些使用临时变量和 volatile 关键字的诱人解法并不奏效。Bacon 等人的《The ’Double-Checked Locking is Broken’ Declaration》讨论了 Java 中的一系列非解法，见 http://www.cs.umd.edu/~pugh/java/memoryModel/DoubleCheckedLocking.html。这类优化风险很高，在实践中往往并不能带来显著的性能收益。大多数程序员不应考虑它们。即便是专家级程序员，也应当习惯性地坚持使用更简单的编程模式，比如我们讨论过的这些；只有当性能测量与剖析表明这类优化能显著提升整体性能时，才考虑双重检查锁定之类的做法。

2. **避免在方法中间定义 synchronized 块。** Java 为共享对象提供了语言级的内建支持。所有类都继承自基类 Object，而 Object 把一把锁和一个条件变量作为成员包含在内。任何方法声明都可以带上关键字 synchronized，表示在进入该方法时自动获取对象的锁，并在方法任何返回时自动释放。例如：

```c
   public synchronized foo() {
       // 做点什么；锁会自动获取/释放。
   }
```

 这种语法很有用——它遵循上面的第 2 条规则，并且让程序员不必操心细节，比如确保在每个可能的返回点（包括异常）之前释放锁。陷阱在于，Java 还允许在方法中间使用*同步块*（synchronized block）。例如：

```c
   public bar() {
       // 在不持有锁的情况下做点什么
       synchronized {
           // 在持有锁的情况下做点什么
       }
       // 在不持有锁的情况下做点什么
   }
```

 这种写法违反了 5.5.2 节的第 3 条规则，并带有那里列出的种种缺点。解决办法与上面讨论的相同：当你发现自己在 Java 方法中间想写一个同步块时，请把它当作一个强烈的提示——你应当定义一个单独的方法，更清晰地封装你识别出的那段逻辑。

3. **让共享状态类与线程类保持分离。** Java 定义了一个名为 Thread 的类，它实现了一个名为 Runnable 的接口；其他类可以实现该接口，从而被运行时系统当作线程对待。要编写表示线程“主循环”的代码，通常要么扩展 Thread 类，要么实现一个实现了 Runnable 的类。陷阱在于：在扩展 Thread 类（或编写实现 Runnable 的新类）时，你可能忍不住不仅放入线程的主循环，还放入要跨多个线程共享的状态，从而模糊了线程与共享对象之间的界限。这几乎总会造成混乱。例如，对于一个阻塞有界队列，除了为共享队列定义 BBQ 类、为线程定义 WorkerThread 类，你也可能忍不住把两者合并成一个类——例如一个带有关联工作线程的队列。如果这听起来让人糊涂，那它确实让人糊涂；但这是我们在学生代码中经常看到的陷阱。解决办法很简单：始终确保线程与共享对象定义在分开的类中。任何可被多个线程访问的状态、锁和条件变量，都绝不应出现在任何扩展 Thread 或实现 Runnable 的 Java 类中。

## 5.6　三个案例研究

学习如何编写并发程序，最好的办法就是动手实践。多线程编程是一项重要技能，我们预计，几乎每一位读这本书的人迟早都要编写许多多线程程序。为了帮助你起步，本节将逐一讲解几个例子。

### 5.6.1　读写锁

首先，我们实现一个*读写锁*（readers/writers lock）。与普通的互斥锁一样，读写锁（RWLock）保护共享数据。不过，它做了如下优化：为了获得最高的性能，RWLock 允许多个“读者”线程同时访问共享数据。只要没有线程在修改数据，任意多个线程都可以安全地同时读取共享数据。然而，在任一时刻只允许一个“写者”线程持有 RWLock。（“读者”线程只能读取，而“写者”线程既可以读*也可以*写数据结构。）当写者线程持有 RWLock 时，它可以安全地修改数据，因为该锁保证没有其他线程（无论读者还是写者）能同时持有这把锁。因此，互斥存在于任意写者与任意其他写者之间，也存在于任意写者与*读者集合*之间。

::: tip 为常见情形做优化
读写锁是计算机系统设计中的一条重要原则的实例：为常见情形做优化。性能优化常常有一个副作用，就是让代码变得更难理解和推理。更复杂的代码更容易出现缺陷，也更容易在添加新功能时引入新的缺陷。那么我们如何判断一项优化是否值得付出这些代价？

一种做法是对代码做性能剖析。然后，*并且只有在那之后*，再去优化那些频繁使用的代码路径。

就锁而言，使用普通的互斥锁显然更简单。只有在下面两个条件同时成立时，才适合把互斥锁换成读写锁：(i) 对互斥锁存在大量争用；(ii) 绝大多数访问都是只读的。换句话说，只有当这种替换能带来显著差别时，才适合使用它。
:::

读写锁在数据库中被广泛使用，用来支持更快的数据库搜索查询，同时支持不那么频繁的数据库更新。另一个常见用途是在操作系统内核内部：内核中的核心数据结构常常被许多线程读取，而更新很少发生。

为了把互斥锁推广为读写锁，我们实现一种新的共享对象 RWLock，由它守护对共享数据的访问并强制执行上述规则。RWLock 是用我们标准的同步构件——互斥锁与条件变量——实现的。

想要（原子地）读取共享数据的线程按如下方式执行：

```c
rwLock->startRead();
// 读取共享数据
rwLock->doneRead();
```

类似地，想要（原子地）写共享数据的线程执行如下代码：

```c
rwLock->startWrite();
// 读写共享数据
rwLock->doneWrite();
```

设计 RWLock 类时，我们首先定义它的接口（本例中接口已经定义好了）和它的共享状态。就状态而言，保留足够的数据以便精确刻画对象是有好处的；尤其在调试时，状态多比状态少要好。在这里，对象的行为完全由正在读或写的线程数、以及正在等待读或写的线程数刻画，因此我们选择用四个整数来记录这些值。图 5.9 给出了 RWLock 类的成员与接口。

<div class="code-cap"><span class="code-label">图 5.9</span>读写锁的接口与成员变量。</div>

```c
class RWLock{
  private:
    // 同步变量
    Lock lock;
    CV readGo;
    CV writeGo;

    // 状态变量
    int activeReaders;
    int activeWriters;
    int waitingReaders;
    int waitingWriters;

  public:
    RWLock();
    ~RWLock() {};
    void startRead();
    void doneRead();
    void startWrite();
    void doneWrite();

  private:
    bool readShouldWait();
    bool writeShouldWait();
};
```

接着，我们通过追问“方法在什么时候必须等待？”来添加同步变量。首先，我们添加一把互斥锁：只要另一个线程正在访问 RWLock 的状态变量，RWLock 的方法就必须等待。其次，我们注意到 startRead 或 startWrite 可能需要等待，于是为这两种情形各添加一个条件变量：readGo 与 writeGo。

RWLock::doneRead 与 doneWrite 不会等待（获取互斥锁除外）。因此，这两个方法不需要任何额外的条件变量。

现在我们可以实现 RWLock 了。图 5.10 给出完整的解法，我们将分几个简单的步骤把它展开。需要做的许多事情几乎是自动的。

- 由于我们总是在方法的开头与结尾获取/释放互斥锁（从不在中间获取或释放），因此可以在仔细考虑这些方法究竟做什么之前，就先在每个公有方法的开头和结尾写上获取与释放互斥锁的调用。此时，startRead 和 doneRead 是这样的：`void RWLock::startRead() { lock.acquire(); lock.release(); }` `void RWLock::doneRead() { lock.acquire(); lock.release(); }` RWLock::startWrite 与 RWLock::doneWrite 与此类似。

- 由于我们知道 startRead 和 startWrite 可能需要等待，可以在每个方法中间写一个 `while(...){wait(...);}` 循环。事实上，我们可以先插入一个稍后再定义的私有方法作为 while 循环的谓词（例如 readShouldWait 和 writeShouldWait），从而把细节推迟到以后再考虑。此时，startRead 是这样的：`void RWLock::startRead() { lock.acquire(); while (readShouldWait()) { readGo.Wait(&lock); } lock.release(); }` RWLock::StartWrite() 与此类似。

现在事情变得稍微复杂一些。我们可以添加代码来跟踪 activeReaders、activeWriters、waitingReaders 和 waitingWriters。由于我们在所有公有方法中都持有互斥锁，这件事很容易做。例如，一次 startRead 调用最初递增等待读者数；当线程越过 while 循环之后，等待读者数减一，而活动读者数加一。

当读或写结束时，等待中的线程可能变得可以继续。因此我们需要在 doneRead 和 doneWrite 中加入 `signal` 或 `broadcast` 调用。最简单的做法是在每个方法里对 readGo 和 writeGo 都做 `broadcast`，但这既低效，（以我们的口味而言）也不够清楚地表明这个类究竟如何工作。

相反，我们观察到：在 doneRead 中，一次读完成时有两种值得关注的情形：(a) 没有等待中的写，此时无需做任何事，因为这次读不会妨碍其他读继续进行；(b) 有等待中的写，并且这是最后一个活动读者，因此可以让一个写继续进行。在情形 (b) 中，我们使用 `signal`，因为至多只有一个写可以继续，而任何在条件变量上等待的写都可以继续。

startRead 和 doneRead 的代码现在完成了：

```c
// 等待，直到没有活跃或等待中的
// 写操作，然后继续。
void RWLock::startRead() {
    lock.acquire();
    waitingReaders++;
    while (readShouldWait()) {
        readGo.Wait(&lock);
    }
    waitingReaders--;
    activeReaders++;
    lock.release();
}

// 读取结束。若没有其他活跃的
// 读操作，写操作才可以继续。
void RWLock::doneRead() {
    lock.acquire();
    activeReaders--;
    if (activeReaders == 0
         && waitingWriters > 0) {
        writeGo.signal();
    }
    lock.release();
}
```

startWrite 和 doneWrite 的代码与此类似。对于 doneWrite，如果存在等待中的写，我们就在 writeGo 上 `signal`；否则，我们在 readGo 上 `broadcast`。

最后，我们需要定义 readShouldWait 和 writeShouldWait 这两个谓词。这里我们实现的是一个*写者优先*（writers preferred）的解法：只要有活动的或等待中的写者，读就应当等待；而写只在存在活动读者或活动写者时才等待。否则，源源不断的新读者可能使某个写请求饥饿，使它永远得不到服务。

```c
bool
RWLock::readShouldWait() {
  return (activeWriters > 0 || waitingWriters > 0);
}
```

writeShouldWait 的代码与此类似。

由于 readShouldWait 和 writeShouldWait 是私有方法，且总是从持有互斥锁的公有方法中调用，它们不需要获取该锁。

图 5.10 给出了完整代码。这个解法也许不合你的口味。你可能会决定使用更多或更少的条件变量，用不同的状态变量实现不同的不变式，或者改变调用 `signal` 或 `broadcast` 的时机。共享对象的做法正是在这些方面给了设计者自由。

<div class="code-cap"><span class="code-label">图 5.10</span>读写锁的一种实现。</div>

```c
// 等待，直到没有活跃或等待中的
// 写操作，然后继续。
void RWLock::startRead() {
    lock.acquire();
    waitingReaders++;
    while (readShouldWait()) {
        readGo.Wait(&lock);
    }
    waitingReaders--;
    activeReaders++;
    lock.release();
}

// 读取结束。若没有其他活跃的
// 读操作，写操作才可以继续。
void RWLock::doneRead() {
    lock.acquire();
    activeReaders--;
    if (activeReaders == 0
         && waitingWriters > 0) {
        writeGo.signal();
    }
    lock.release();
}

// 读操作需等待，只要有活跃或等待中的
// 写（“写者优先”）。
bool
RWLock::readShouldWait() {
    return (activeWriters > 0
             || waitingWriters > 0);
}

// 等待，直到没有活跃的读或
// 写，然后继续。
void RWLock::startWrite() {
    lock.acquire();
    waitingWriters++;
    while (writeShouldWait()) {
        writeGo.Wait(&lock);
    }
    waitingWriters--;
    activeWriters++;
    lock.release();
}

// 写入结束。等待中的写操作或
// 读操作可以继续。
void
RWLock::doneWrite() {
    lock.acquire();
    activeWriters--;
    assert(activeWriters == 0);
    if (waitingWriters > 0) {
        writeGo.signal();
    }
    else {
        readGo.broadcast();
    }
    lock.release();
}

// 写操作需等待活跃的读或写结束。
bool
RWLock::writeShouldWait() {
    return (activeWriters > 0
             || activeReaders > 0);
}
```

::: tip 单步调试与模型检验你的代码
假设你写了一些并发代码，想验证这个解法是否如你所愿地工作。有一件事你应当*始终*去做——无论代码是顺序的还是并发的——就是用调试器在各种输入下单步执行代码，验证程序逻辑确实在做你期望它做的事，以及变量确实取了你期望的值。

这对并发程序尤其有用。既然程序必须对任何可能的线程调度都正确，你就可以借助调试器考察线程以不同方式交错时会发生什么。你的程序逻辑是否仍然如你所愿地工作？

例如，对 RWLock 类，你可以：

- 启动一个读者。它会一路走到底吗？显然，它不应当等待，因为没有人持有锁，也没有写者。当它执行完 readDone 之后，状态变量是否回到了初始状态？

- 启动一个写者，并在它获取互斥锁之后启动一个读者。读者会等待这把锁吗？当写者执行完 startWrite 之后，读者会继续，然后等待写者调用 doneWrite 吗？此后读者会继续吗？

- 启动一个读者，接着一个写者，再接着另一个读者。如此等等。

我们鼓励你在本节的例子中都这样做。这些例子足够短，你可以手工执行，不过我们也提供了代码，供你在调试器中尝试。

一种更系统的方法叫作模型检验（model checking）。为了完整验证一个并发程序是否做到了它被设计要做的事，模型检验器会枚举所有可能的操作序列，并逐一尝试。由于即使对一个相当简单的程序，这也会产生几乎无穷多的可能测试，因此为了实用，模型检验必须缩减搜索空间。对于遵循我们准则的代码——用锁保护共享数据——指令的确切顺序不再重要。例如，抢占一个持有锁的线程对程序的行为没有影响。

相反，程序的行为取决于同步指令的序列：哪个线程先获取锁、哪个线程在条件变量上等待，如此等等。因此，模型检验器可以分两步进行：先验证不存在对共享数据的未加锁访问，然后枚举各种同步操作序列。即使如此，可能的组合数目仍可能大到无法承受，所以模型检验器通常会在某个时间限制内尽可能多地验证不同的交错方式。
:::

### 5.6.2　同步屏障

在数据并行编程中，正如第 4 章所解释的，计算在一个数据集上并行执行，每个线程处理数据的不同分区。当所有线程都完成自己的工作后，它们就可以在算法的下一个（数据并行）步骤中安全地使用彼此的结果。MapReduce 是数据并行编程的一个例子，但还有许多其他结构相同的系统。

为此，我们需要一种高效的方法来检查全部 n 个线程是否都完成了工作。这叫作*同步屏障*（synchronization barrier）。它只有一个操作：`checkin`。线程完成工作后调用 `checkin`；在*所有* n 个线程都调用过 `checkin` 之前，任何线程都不能从 `checkin` 返回。一旦所有线程都已调用过 `checkin`，就可以安全地使用上一步的结果。

请注意，同步屏障不同于本章前面定义的内存屏障。同步屏障由许多线程并发调用；屏障阻止任何线程继续，直到所有线程都到达屏障。内存屏障由单个线程调用，用来阻止该线程继续，直到屏障之前的所有内存操作都已完成并对其他线程可见。

用同步屏障实现 MapReduce 的代码可能如图 5.11 所示。

```text
Create n threads.
Create barrier.

Each thread executes map operation in parallel.
barrier.checkin();

Each thread sends data in parallel to reducers.
barrier.checkin();

barrier.checkin();
```

使用同步屏障的另一种替代方案是在每一步都创建 n 个线程；然后主线程可以对每个线程调用 thread_join 以确保其完成。这样做虽然正确，但可能低效。不仅每一步都要启动 n 个新线程，线程之间的工作划分每次也要重新做。数据并行计算中的每个线程常常可以在许多步骤中反复处理同一份数据，从而最大限度地利用硬件处理器缓存。

我们可以用前面描述读写锁时相同的方法，推导出同步屏障的实现。

- 我们创建一个 Barrier 类，其中有一把锁，用来保护它的内部状态变量：目前有多少线程已经调用过 `checkin`（count），以及我们预期有多少线程（numThreads）。

- 我们在 `checkin` 的开头 `acquire` 锁，在结尾 `release` 锁。

- 由于线程可能要在 `checkin` 中等待，我们需要一个条件变量 allCheckedIn。

- 我们把 `wait` 放在一个 while 循环中，检查是否全部 n 个线程都已调用过 `checkin`。

- 最后一个调用 `checkin` 的线程做一次 `broadcast`，唤醒所有等待者。

图 5.12 给出完整实现。注意，尽管信号意味着线程可以安全地退出 `checkin`，我们仍然使用 while 循环。使用 while 语句没有坏处，而且它能防范运行时库发出虚假唤醒（spurious wakeup）的可能。

<div class="code-cap"><span class="code-label">图 5.12</span>同步屏障的一个候选实现。在这个实现中，每个屏障实例只能安全地使用一次。</div>

```c
// 一次性同步屏障。
class Barrier{
  private:
    // 同步变量
    Lock lock;
    CV allCheckedIn;

    // 状态变量
    int numEntered;
    int numThreads;

  public:
    Barrier(int n);
    ~Barrier();
    void checkin();
};

Barrier::Barrier(int n) {
    numEntered = 0;
    numThreads = n;
}

// 在所有线程都
// 都调用 checkin 之后才会返回。
void
checkin() {
    lock.acquire();
    numEntered++;
    if (numEntered < numThreads) {
        while (numEntered < numThreads)
        allCheckedIn.wait(&lock);
    } else { // 最后调用 checkin 的线程
        allCheckedIn.broadcast();
    }
    lock.release();
}
```

设计很直接，但问题在于这个屏障只能使用一次。看出这一点的一种方式是：屏障的状态不会恢复到它被创建时所处的状态。实现可重用的屏障要微妙一些。

- *第一个*离开的线程（即唤醒其他线程的那个线程）不能重置状态，因为在其他线程醒来之前，它们还需要这个状态来判断应当退出 while 循环。

- *最后一个*离开屏障的线程也不能为下一轮重置状态，因为这里存在一种可能的竞态条件。假设某个线程在最后一个线程醒来并离开上一个屏障*之前*就完成了 `checkin`，并对下一个屏障调用了 `checkin`。此时，这个线程会发现已经有 n 个线程调用过 `checkin` 了（因为状态尚未被重置），于是它会以为自己“可以继续了！”

实现可重用屏障的一种简单办法是使用两个一次性屏障。第一个屏障确保所有线程都已调用过 `checkin`，第二个屏障确保所有线程都已从 allCheckedIn.wait 中醒来。第 n 个离开的线程可以安全地重置 numCheckedIn；第 n 个调用 `checkin` 的线程可以安全地重置 numLeaving。图 5.13 给出结果。

<div class="code-cap"><span class="code-label">图 5.13</span>可重用的同步屏障的实现。</div>

```c
// 可重复使用的同步屏障。
class Barrier{
  private:
    // 同步变量
    Lock lock;
    CV allCheckedIn;
    CV allLeaving;

    // 状态变量
    int numEntered;
    int numLeaving;
    int numThreads;

  public:
    Barrier(int n);
    ~Barrier();
    void checkin();
};

Barrier::Barrier(int n) {
    numEntered = 0;
    numLeaving = 0;
    numThreads = n;
}

// 在所有线程都
// 都调用 checkin 之后才会返回。
void
checkin() {
    lock.acquire();
    numEntered++;
    if (numEntered < numThreads) {
        while (numEntered < numThreads)
        allCheckedIn.wait(&lock);
    } else {
    // allLeaving.wait 中没有线程
        numLeaving = 0;
        allCheckedIn.broadcast();
    }
    numLeaving++;
    if (numLeaving < numThreads) {
        while (numLeaving < numThreads)
        allLeaving.wait(&lock);
    } else {
    // allCheckedIn.wait 中没有线程
        numEntered = 0;
        allLeaving.broadcast();
    }
    lock.release();
}
```

### 5.6.3　FIFO 阻塞有界队列

假定条件变量采用 Mesa 语义，我们在图 5.8 中给出的线程安全阻塞有界队列实现并不保证免于饥饿。例如，某个线程可能调用 remove，并因为队列为空而在 while 循环中等待。如果每当另一个线程向队列插入一项时，都有一个*不同的*线程调用 remove、获取锁、发现队列非空，并在等待线程恢复运行之前就把该项取走，那么饥饿就会发生。

通常，饥饿并不是问题。例如，如果我们有一个线程向队列中放入条目，而有 n 个等价的工作线程从队列中取出条目，那么哪个工作线程先执行可能无关紧要。即使饥饿确实是个问题，只要对 insert 和 remove 的调用不频繁，或者缓冲区很少为空或很少为满，每个线程都极有可能取得进展。

然而，假设我们确实需要一个能保证所有线程都有进展的线程安全有界缓冲区。我们可以把这一活性约束更形式化地定义为：

- **免于饥饿。** 如果一个线程在 insert 中等待，那么可以保证在有限次 remove 调用完成之后它能继续运行，反之亦然。

- **先进先出（FIFO）。** 一个更强的约束是队列先进先出，即 FIFO。第 n 个在 remove 中获取锁的线程，取到的是第 n 个在 insert 中获取锁的线程所插入的条目。

在 Hoare 语义下，只要 `signal` 唤醒的是等待最久的线程，图 5.8 中的实现就是 FIFO 的，因而也是免于饥饿的。

这里我们考虑一个相关的问题：能否用 Mesa 语义实现一个免于饥饿的、或者 FIFO 的有界缓冲区？我们需要确保当一个线程向某个等待者发出信号时，由那个正在等待的线程（而不是任何其他线程）来取走条目。

<div class="code-cap"><span class="code-label">图 5.14</span>用 Mesa 语义实现的 FIFO 阻塞有界缓冲区。ConditionQueue 是由条件变量构成的链表。</div>

```c
ConditionQueue insertQueue;
ConditionQueue removeQueue;
int numRemoveCalled = 0; // # of times remove has been called
int numInsertCalled = 0; // # of times insert has been called

int
FIFOBBQ::remove() {
    int item;
    int myPosition;
    CV *myCV, *nextWaiter;

    lock.acquire();

    myPosition = numRemoveCalled++;
    mycv = new CV;  // 创建一个新的条件变量用于等待。
    removeQueue.append(myCV);

// 即使被唤醒，也要等到轮到自己。
    while (front < myPosition || front == nextEmpty) {
        mycv->Wait(&lock);
    }

    delete self;    // 这个条件变量不再需要了。
    item = items[front % size];
    front++;

// 如果有线程在 insert 中等待，唤醒下一个。
    nextWaiter = insertQueue.removeFromFront();
    if (nextWaiter != NULL)
        nextWaiter->Signal(&lock);
    lock.release();
    return item;
}
```

做到这一点的最简单办法是为每个正在等待的线程创建一个条件变量。这样，你就能精确地决定该唤醒哪个线程！你也许会担心这样做浪费空间，但在现代计算机系统中，一个条件变量（或一把锁）只占 DRAM 的几个字；与每个线程所需的其他存储相比，它很小。

解法的要点如下：

- 为每个等待者创建一个条件变量。

- 按 FIFO 顺序把条件变量放入一个队列。

- 信号唤醒位于队列前端的线程。

- 小心虚假唤醒！

我们在图 5.14 中给出 FIFOBBQ::remove 的一种实现；insert 与此类似。

如果我们希望队列后进先出（LIFO）而不是先进先出，或者希望按某种优先级顺序唤醒线程，这个实现也很容易扩展。而在 Hoare 语义下，这就不那么容易了；我们需要为每种不同的排队规则提供不同的条件变量实现，而不能把这件事留给那少数几种确实在意具体顺序的应用自行处理。

## 5.7　同步对象的实现

我们已经描述了锁与条件变量，并说明了如何在共享对象中使用它们；接下来讨论如何实现这些重要的构件（building block）。

回顾第 4 章：线程既可以在内核中实现，也可以在用户级实现。我们先说明如何为内核线程实现同步；本节末尾再讨论为了让这些抽象也支持用户级线程，需要做哪些改动。

锁与条件变量都有状态。对锁而言，状态就是锁本身的状态（FREE 或 BUSY），再加上一个队列，其中存放零个或多个等待锁变为 FREE 的线程。对条件变量而言，状态就是等待被发信号的线程队列。无论哪种情况，难点都在于原子地修改这些数据结构。

“牛奶买多了”的讨论表明，只用内存读、写来实现原子动作既复杂又昂贵。因此，现代实现使用更强大的硬件原语（hardware primitive），让我们能够原子地读取、修改和写入一部分状态。我们用到两种硬件原语：

- **关闭中断。** 在单处理器上，只要关闭这颗处理器上的中断，就能让一段指令序列成为原子的。

- **原子的读-修改-写指令。** 在多处理器上，关闭中断不足以提供原子性。于是体系结构提供专门的指令，原子地读取并更新内存中的一个字。相对于每颗处理器上的指令，这些指令都是全局原子的。

这两种原语同时也都充当内存屏障（memory barrier）：它们告诉编译器与硬件，所有先前的指令都必须在原子指令执行之前完成。

### 5.7.1　用关中断实现单处理器锁

在单处理器上，只要一个线程的某条指令序列中间不发生上下文切换，这个序列对其他线程而言就是原子的。因此，在单处理器上，线程只要在该序列执行期间关闭中断（并避免调用可能触发上下文切换的线程库函数），就能让一串动作成为原子动作。

由此可以得到一种在单处理器上实现锁的方法——做法很简单，限制却很严重：

```c
Lock::acquire() { disableInterrupts(); }

Lock::release() { enableInterrupts(); }
```

这种实现确实提供了锁所必需的互斥性质。有些单处理器内核就采用这种简单的做法，但它不足以作为锁的一般实现。如果锁所保护的代码序列运行很久，中断就会关闭那么久。这会阻止其他线程运行，也会让系统无法及时响应用户输入或其他实时任务。此外，这种做法可以用于内核，因为内核里的代码（大概）都经过仔细编写、可信地快速释放锁；但我们不能让不可信的用户级代码在关闭中断的情况下运行，否则一个恶意或有缺陷的程序就能独占处理器。

### 5.7.2　实现单处理器队列锁

更通用的方案基于这样一个观察：如果锁处于 BUSY，那么在锁变为空闲之前，让正在获取锁的线程继续运行毫无意义。此时应当切换到下一个就绪线程。

这种实现会短暂关闭中断以保护锁的数据结构，但一旦线程取得了锁、或者判定锁处于 BUSY，就立即重新打开中断。图 5.15 所示的 Lock 实现说明了这种做法。如果线程尝试获取锁时锁处于 BUSY，该线程就把自己的 TCB 移入这把锁的等待列表。随后线程挂起自己，并切换到下一个可运行的线程。suspend 调用不会返回，直到该线程被放回就绪列表，例如直到某个线程调用 Lock::release。

<div class="code-cap"><span class="code-label">图 5.15</span>单处理器队列锁的伪代码。临时关闭中断，使对实现该锁的数据结构的访问具有原子性。suspend(oldTCB, newTCB) 把当前线程切换到下一个将要运行的线程；只有等其他线程调用 release 并把它移回就绪列表之后，它才会返回。</div>

```c
 class Lock {
   private:
     int value = FREE;
     Queue waiting;
   public:
     void acquire();
     void release();
 }

 Lock::acquire() {
     TCB *chosenTCB;

     disableInterrupts();
     if (value == BUSY) {
         waiting.add(runningThread);
         runningThread->state = WAITING;
         chosenTCB = readyList.remove();
         thread_switch(runningThread,
                       chosenTCB);
         runningThread->state = RUNNING;
     } else {
         value = BUSY;
     }
     enableInterrupts();
 }

 Lock::release() {
 // 下一个持有锁的线程
     TCB *next;

     disableInterrupts();
     if (waiting.notEmpty()) {
     // 把一个 TCB 从等待队列
     // 移到就绪队列
         next = waiting.remove();
         next->state = READY;
         readyList.add(next);
     } else {
         value = FREE;
     }
     enableInterrupts();
 }
```

在我们的实现里，如果有线程正在等待这把锁，release 调用就不会把 value 置为 FREE，而是让 value 保持 BUSY。被唤醒的线程保证就是下一个执行临界区的线程。这样的安排确保了免于饥饿。

**警告**：这一优化只适用于本实现。锁的使用者不应对等待线程获取锁的次序作任何假设。

::: info 例
在 Lock::acquire 中，调用 thread_switch 时中断是关闭的。那么由谁来重新打开中断？
:::

::: warning 答
**由下一个运行的线程重新打开中断。** 具体来说，大多数线程系统的实现都维持这样一条不变式：线程在执行上下文切换之前总是先关闭中断。因此，一个线程在经历上下文切换后再次运行时，中断总是处于关闭状态。所以，线程从上下文切换返回时，必须重新打开中断。例如，图 5.15 中的 Lock::acquire 代码在返回之前重新打开中断；第 4 章中的 yield 实现在上下文切换之前关闭中断，切换之后再重新打开。□
:::

### 5.7.3　实现多处理器自旋锁

然而在多处理器上，关闭中断是不够的。即使在一颗处理器上关闭了中断，其他线程仍在并发运行。一颗处理器上线程的操作，会与其他处理器上线程的操作交错进行。

既然关闭中断不够，大多数处理器体系结构就提供*原子的读-修改-写指令*来支持同步。这类指令能把一个值从内存位置读入寄存器、修改该值，并把修改后的值写回内存，而相对于其他处理器上的所有指令，整个过程是原子的。

::: tip 读-修改-写指令是如何实现的
讲到这里，学生常常会问：处理器硬件是如何实现 test-and-set 这类原子指令的？如果每颗处理器都有自己的缓存，那么是什么阻止两颗处理器同时读取并更新同一个位置？完整的解释超出了本书的范围，不过硬件所用的机制与缓存一致性（cache coherence）所用的机制是同一套。

处理器缓存中的每个条目都有一个状态：*独占*（exclusive）或*只读*（read-only）。只要还有其他处理器缓存了该数据，它在所有缓存中就都必须是*只读*的。要修改一个共享内存位置，处理器必须持有该数据的*独占*副本；其他任何缓存都不得持有副本。否则，一颗处理器可能读到某个位置已经过期的值，而另一颗处理器早已更新了它。要读写某个正以*独占*状态存放在其他缓存中的位置，处理器需要从那个缓存取回最新的值。

读-修改-写指令正是借助这一机制实现的。执行这类指令时，硬件先取得该内存的*独占*副本，并使其他所有缓存中的副本失效。然后指令在本地副本上执行；指令完成后，其他处理器才可以取回最新的值来读取结果。
:::

举例来说，有些体系结构提供*测试并设置*（test-and-set）指令，它原子地把一个值从内存读入寄存器，并把 1 写入该内存位置。

<div class="code-cap"><span class="code-label">图 5.16</span>用 test-and-set 实现的多处理器自旋锁。</div>

```c
 class SpinLock {
   private:
     int value = 0; // 0 = FREE; 1 = BUSY

   public:
     void acquire() {
         while (test_and_set(&value)) // 当 BUSY 时
             ; // 自旋
     }

     void release() {
         value = 0;
         memory_barrier();
     }
 }
```

图 5.16 用 test_and_set 实现了一把锁。这把锁之所以称为*自旋锁*（spinlock），是因为等待一把 BUSY 锁的线程会在一个紧凑的循环里“自旋”（忙等），直到其他线程释放该锁。如果锁被长时间持有，这种做法的效率不高。不过，对于那些只被短期持有（即持有时间比一次上下文切换还短）的锁，自旋锁是合适的。

::: tip 中断处理程序与自旋锁
只要中断处理程序要访问共享数据，这份数据就必须用自旋锁而不是队列锁来保护。正如第 2 章和第 4 章所解释的，中断处理程序不是线程：它必须不阻塞地运行到结束，这样硬件才能递交下一个中断。若使用队列锁，中断处理程序开始运行时锁可能正被持有，这会使中断处理程序无法正确工作。

任何线程只要要获取中断处理程序中使用的自旋锁，就*必须*先关闭中断。否则，如果中断恰好在不巧的时刻到达，就可能导致死锁。处理程序可能永远自旋，等待一把被它所中断的那个线程持有的锁。此时多半只能重启系统才能解决问题。

为了避免这类错误，大多数操作系统都让中断处理程序保持极其简单。例如，许多中断处理程序只是唤醒一个线程，由该线程去做管理 I/O 设备的繁重工作。唤醒线程需要互斥地访问就绪列表，而就绪列表由一把自旋锁保护，凡是使用这把锁，都必须先关闭中断。
:::

### 5.7.4　实现多处理器队列锁

我们常常需要支持长度不一的临界区。例如，我们可能想要一个通用解法，它不对持有锁的方法的运行时间作任何假设。

<div class="code-cap"><span class="code-label">图 5.17</span>多处理器队列锁的伪代码。调度器和锁都用自旋锁保护各自的内建数据结构。任何线程在锁处于 BUSY 时尝试获取锁，都会被放入队列，留待以后唤醒。这里需要格外小心，防止等待线程在完成 thread_switch 之前就被放回就绪列表。</div>

```c
 class Lock {
    private:
      int value = FREE;
      SpinLock spinLock;
      Queue waiting;
    public:
      void acquire();
      void release();
 }

 Lock::acquire() {
     spinLock.acquire();
     if (value != FREE) {
         waiting.add(runningThread);
         scheduler.suspend(&spinLock);
        // 调度器释放 spinLock
     } else {
         value = BUSY;
         spinLock.release();
     }
 }

 void Lock::release() {
     TCB *next;

     spinLock.acquire();
     if (waiting.notEmpty()) {
         next = waiting.remove();
         scheduler.makeReady(next);
     } else {
         value = FREE;
     }
     spinLock.release();
 }

 class Scheduler {
   private:
     Queue readyList;
     SpinLock schedulerSpinLock;
   public:
     void suspend(SpinLock *lock);
     void makeReady(Thread *thread);
 }

 void
 Scheduler::suspend(SpinLock *lock) {
     TCB *chosenTCB;

     disableInterrupts();
     schedulerSpinLock.acquire();
     lock->release();
     runningThread->state = WAITING;
     chosenTCB = readyList.getNextThread();
     thread_switch(runningThread,
                   chosenTCB);
     runningThread->state = RUNNING;
     schedulerSpinLock.release();
     enableInterrupts();
 }

 void
 Scheduler::makeReady(TCB *thread) {
     disableInterrupts();
     schedulerSpinLock.acquire();
     readyList.add(thread);
     thread->state = READY;
     schedulerSpinLock.release();
     enableInterrupts();
 }
```

在多处理器上，我们无法完全消除忙等，但可以把它降到最低。如前所述，调度器的就绪列表需要一把自旋锁。调度器持有这把自旋锁只持续几条指令；而且，如果就绪列表的自旋锁处于 BUSY，那么尝试切换到另一个线程也没有意义，因为那同样需要访问就绪列表。

为了减少就绪列表自旋锁上的争用，我们用*另一把*自旋锁来保护每把锁的内部状态。线程一旦持有某把锁的自旋锁，就可以检查和更新这把锁的状态。如果锁是 FREE，线程就设置其值并释放自旋锁。如果锁是 BUSY，则需要做更多工作：把当前线程放入该锁的等待列表，挂起当前线程，并切换到新线程。

不过，如图 5.17 所示，这里的顺序必须非常小心。在多处理器上挂起一个线程，需要先关闭中断，以确保线程在持有就绪列表自旋锁期间不会被抢占。然后获取就绪列表自旋锁，*只有到这时*，才可以安全地释放该锁的自旋锁并切换到新线程。就绪列表自旋锁由下一个运行的线程释放。否则，另一颗处理器上的某个线程可能在等待线程完成上下文切换之前，就把它放回就绪列表（并让它开始运行）。

之后，当锁被释放时，如果有线程正在等待这把锁，就把其中一个从锁的等待列表移到调度器的就绪列表。

::: info 例
如果我们在调用 suspend 之前就释放了锁的自旋锁，可能会发生什么？
:::

::: warning 答
问题的关键在于：我们要确保正在获取锁的线程先完成自我挂起，之后释放锁的线程才会尝试重新调度它。如果让 makeReady 在 suspend 之前运行，makeReady 会把正在获取锁的线程标记为 READY，但随后 suspend 又把这个线程的状态改成 WAITING。于是该线程就永远卡在 WAITING 状态。由于这种执行顺序极少出现，问题会极难定位。□
:::

**注意**：在图 5.17 的实现中，随着处理器数量增加，这唯一一把调度器自旋锁可能成为瓶颈。因此，正如第 6 章将要解释的，大多数系统为每颗处理器各设一个就绪列表，每个列表由不同的自旋锁保护。这样，不同处理器就可以同时向不同的列表加入线程或从中取出线程。通常，处于 WAITING 的线程会被放到它此前处于 RUNNING 状态的那颗处理器的就绪列表上；这能改善缓存性能，因为该处理器的缓存中可能还留有该线程上次运行时用到的代码和数据。把线程放回同一个就绪列表，还能防止其他处理器在线程完成上下文切换之前就运行它。一旦线程变为 READY，任何空闲处理器都可以运行它：获取它所在就绪列表的自旋锁，把它取出，再释放自旋锁。

### 5.7.5　案例研究：Linux 2.6 内核互斥锁

我们以 Linux 2.6 内核为例，说明锁在实践中是如何实现的。Linux 的代码与我们上面描述的做法十分接近，只是它*针对常见情形做了优化*。

在 Linux 中，大多数锁在大多数时候都是 FREE 的。而且，即使某把锁处于 BUSY，也很可能没有其他线程在等它。反之，如果锁经常处于 BUSY、或者有长长的线程队列在等它，那就意味着任何需要这把锁的线程通常都得等待，从而拖慢系统。

Linux 的锁实现正是利用了这一点：在线程获取锁时无需等待、以及释放锁时无需唤醒线程的情形下，提供一条极快的快路径。其他所有情形则走一条慢路径，与图 5.17 类似。

此外，为获取一把 FREE 的锁、以及释放一把没有等待者的锁提供快路径，对下面将要讨论的用户级线程库同样重要。

为了优化常见情形的路径，Linux 利用了 x86 的硬件特性。x86 支持许多种不同的读-修改-写指令，包括原子减一（从内存位置减 1，并返回先前的值）、原子加一、原子交换（把内存位置的值与寄存器中的值互换）以及原子 test-and-set。

关键思路是：设计锁的数据结构，使得在快路径上获取和释放锁时，*不必*先获取自旋锁，也不必关闭中断。慢路径则确实需要获取自旋锁。锁的值不是二值的，而是一个整数计数，共有三种状态：

```c
    struct mutex {
        /* 1: unlocked, 0: locked, negative: locked, possible waiters */
        atomic_t          count;
        spinlock_t        wait_lock;
        struct list_head  wait_list;
    };
```

Linux 的锁获取代码是一个宏（以避免在快路径上发生过程调用），展开后是一小段指令。decl 指令前面的 x86 lock 前缀告诉处理器：这条指令应当原子地执行。

```c
        lock decl (%eax)  // 对内存单元的原子减一
                          // %eax 中的地址是 lock->count 的指针
        jns 1f            // 若无符号（值为 0）则跳转
        call slowpath_acquire
    1:
```

如果锁原本是 FREE，那么只用两条指令就取得了锁；如果锁原本是 BUSY，代码会让 count 保持小于 0，并调用另一个例程处理慢路径。慢路径关闭抢占、获取自旋锁、把线程放入锁的等待队列，然后重新检查在此期间锁是否已被释放。为此，它使用了原子交换指令：

```c
    for (;;) {
        /*
         * Lets try to take the lock again - this is needed even if
         * we get here for the first time (shortly after failing to
         * acquire the lock), to make sure that we get a wakeup once
         * it’s unlocked. Later on, if we sleep, this is the
         * operation that gives us the lock. We xchg it to -1, so
         * that when we release the lock, we properly wake up the
         * other waiters:
         */
        if (atomic_xchg(&lock->count, -1) == 1)
            break;

        /* didn’t get the lock, go to sleep: */
        ...
    }
```

如果成功，就取得了锁。如果失败，线程释放自旋锁并切换到下一个就绪线程。当线程从 suspend 返回时，与图 5.17 的情形不同，锁可能已经不是 FREE，因此线程必须再试一次。

最终，线程跳出循环，这意味着它找到了一个锁处于 FREE 的时刻（`lock->count = 1`），并在这个时刻把锁置为“已加锁、可能有等待者”的状态（即令 `count = -1`）。此时线程已持有锁，随后它做清理：若没有其他等待者，就把 `count` 重置为 0。

```c
    /* set it to 0 if there are no waiters left: */
    if (list_empty(&lock->wait_list))
        atomic_set(&lock->count, 0);
```

然后它释放自旋锁并重新允许抢占。

释放时，如果锁的值为 0（即锁没有等待者），快路径就是两条内联指令。

```c
        lock incl (%eax)     // 原子加一
        jg 1f        // 若新值为 1 则跳转
        call slowpath_release
    1:
```

在慢路径上，count 原本为负。加一指令执行后，锁仍保持 BUSY。接着，线程获取自旋锁，把 count 置为 FREE，并唤醒一个等待线程。

```c
    spin_lock_mutex(&lock->wait_lock, flags);
        /*
         * Unlock lock here
         */
    atomic_set(&lock->count, 1);
    if (!list_empty(&lock->wait_list)) {
        struct mutex_waiter *waiter =
            list_entry(lock->wait_list.next,
                struct mutex_waiter, list);
        wake_up_process(waiter->task);
    }
    spin_unlock_mutex(&lock->wait_lock, flags);
```

注意，这个函数总是把 count 置为 1，即使还有等待线程也是如此。因此，可能有新线程插进来，在快路径上取得这把锁，并把 count 置为 0。在这种情况下，等待线程仍然会被唤醒；等它最终运行时，上面那个主循环会把 count 置为 -1。

这个例子说明，获取和释放一把锁可以很便宜。程序员有时会费尽心思，试图在特定情形下避免获取锁。然而，这类情形下的推理可能很微妙，而省掉本该有的锁是危险的。在争用很少的情况下，避免用锁不太可能显著提升性能，因此通常更好的做法是保持简单，依靠锁来保证访问共享状态时的互斥。

### 5.7.6　实现条件变量

我们可以用与实现锁类似的办法来实现条件变量，只有一处简化：由于调用 `wait`、`signal` 或 `broadcast` 时总是持有锁，我们已经互斥地访问了条件等待队列。与锁的情形一样，这里需要小心，防止等待线程在完成上下文切换之前就被放回就绪列表；做法是在释放管程锁*之前*先获取调度器自旋锁。另一个线程可能获取了管程锁并开始向等待线程发信号，但它在上下文切换之后调度器锁被释放之前，无法完成这次信号。

<div class="code-cap"><span class="code-label">图 5.18</span>条件变量实现的伪代码。suspend 与 makeReady 的定义见图 5.17。</div>

```c
 class CV {
   private:
     Queue waiting;
   public:
     void wait(Lock *lock);
     void signal();
     void broadcast();
 }

 // 管程锁由当前线程持有。
 void CV::wait(Lock *lock) {
     assert(lock.isHeld());
     waiting.add(myTCB);
     // 切换到新线程并释放锁。
     scheduler.suspend(&lock);
     lock->acquire();
 }

 // 管程锁由当前线程持有。
 void CV::signal() {
     if (waiting.notEmpty()) {
         thread = waiting.remove();
         scheduler.makeReady(thread);
     }
 }

 void CV::broadcast() {
     while (waiting.notEmpty()) {
         thread = waiting.remove();
         scheduler.makeReady(thread);
     }
 }
```

图 5.18 给出了一个采用 Mesa 语义的实现——当我们向一个等待线程发信号时，该线程变为 READY，但它可能不会立即运行，而且必须重新获取管程锁。很可能有另一个线程先取得管程锁，并在等待线程从 CV::wait 返回之前，改变由该锁保护的状态。

### 5.7.7　实现应用级同步

前面的讨论集中在为内核线程实现锁与条件变量。在那种情况下，一切（代码、共享状态、锁的数据结构、线程控制块以及就绪列表）都在内核内存中，所有线程都在内核态运行。幸运的是，虽然有些细节会变，但当我们为运行在用户级的线程实现锁与条件变量时，同样的基本做法依然可行。

回顾第 4 章：支持应用级并发有两种方式——通过系统调用访问内核的线程操作，或者使用用户级线程调度器。

**内核管理的线程。** 在内核管理的线程中，内核向进程提供线程，并管理线程就绪列表。内核调度器需要知道线程何时在等待某把锁或某个条件变量，以便挂起该线程并切换到下一个就绪线程。

最简单的情形是：把锁与条件变量的数据结构（包括等待列表）放在内核地址空间中。对同步对象的每次方法调用都转换为一次系统调用。这样，前面描述的内核级锁与条件变量的实现就可以基本不加改动地使用。

更精巧的做法是把锁的状态与实现拆成快路径和慢路径，类似于上面介绍的 Linux 锁。例如，每把锁有两个数据结构：(i) 进程的地址空间里存放类似 count 字段的东西；(ii) 内核中存放自旋锁和 `wait_list` 队列。

于是，获取一把 FREE 的锁、或释放一把没有等待线程的锁，在用户级只需几条指令，不涉及系统调用。慢路径仍然需要系统调用（例如等待线程需要挂起执行时）。实现的细节我们留给读者作为练习。

**用户管理的线程。** 在完全运行于用户级的线程库中，库会创建多个内核线程充当虚拟处理器，再把用户级线程多路复用到这些虚拟处理器上。这种情况与内核线程类似，只不过是在进程的地址空间内运行，而不是在内核的地址空间内。具体来说，代码、共享状态、锁与条件变量的数据结构、线程控制块以及就绪列表，都位于进程的地址空间。

唯一重要的改动与关闭中断有关。显然，用户级线程包无法关闭系统级的中断；内核不可能允许一个不可信的进程关闭中断从而可能永远运行下去。

幸运的是，线程库只需要屏蔽来自操作系统的上调（upcall）；上调用于触发线程抢占以及用户级调度器中的其他操作，如果它们在线程库修改调度器数据结构时发生，就可能造成不一致。大多数现代操作系统都提供了一种办法，可以暂时屏蔽上调，然后在安全的时候再递交这些上调。只要确保用户级调度器与上调处理程序不会同时运行，上面介绍的快路径互斥锁实现在这里同样可用。

## 5.8　信号量：弊大于利

<blockquote class="book-quote">

“在系统构想阶段就逐渐发现，我们以两种完全不同的方式使用信号量。这种差别如此显著，以致回过头看，人们不禁要问：把这两种方式说成是对同一组原语的运用，是否真的公平。一方面，我们把信号量用于互斥；另一方面，则是私有信号量。”（摘自 Dijkstra《The structure of the ’THE’-Multiprogramming System》，*Communications of the ACM*，第 11 卷第 5 期，1968 年 5 月。）

</blockquote>

本书的重点是使用锁与条件变量来构造共享对象，以实现同步。然而多年来，人们提出了许多不同的同步原语，包括通信顺序进程（communicating sequential processes）、事件投递（event delivery）、消息传递（message passing）等等。重要的是要认识到：这些机制都不比使用锁与条件变量更强大；采用其中任何一种范式的程序，都可以通过直截了当的变换改写为管程。

有一种同步机制值得详细讨论，因为它至今仍被广泛使用，那就是**信号量**（semaphore）。信号量由 Dijkstra 提出，用于在 THE 操作系统中提供同步；THE 系统（以及在它之上取得的其他诸多进展）探索了在操作系统设计中以结构化方式使用并发的途径。

信号量的定义如下：

- 信号量有一个非负的取值。

- 创建信号量时，它的值可以初始化为任意非负整数。

- `Semaphore::P()` 等待，直到值大于 0；然后原子地把值减 1 并返回。

- `Semaphore::V()` 原子地把值加 1。如果有线程正在 P 中等待，就使其中一个线程被唤醒，于是它对 P 的调用得以成功地把值减 1 并返回。

- 不允许对信号量施加其他操作；特别地，任何线程都不能直接读取信号量的当前值。

请注意，`Semaphore::P` 是一个原子操作：观察到值为正的那次读取，与把值减 1 的那次更新是原子的。因此，即使多个线程并发调用 P，信号量的值也永远不会为负。

同样，如果在有线程于 P 中等待时发生 V，那么 V 的递增与 P 的递减是原子的：没有其他线程能观察到递增后的值，而在 P 中等待的线程则保证能把值减 1 并返回。

有了这一定义，信号量既可以用于互斥（像锁那样），也可以用于一般的等待——等待另一个线程完成某件事（有点像条件变量）。

要把信号量用作互斥锁，把它初始化为 1。此时，`Semaphore::P` 等价于 `Lock::acquire`，`Semaphore::V` 等价于 `Lock::release`。

把信号量用于更一般的等待则更棘手。理解信号量的一个好类比是 `thread_join`。使用 `thread_join` 时，事件的确切顺序无关紧要：如果被分叉的线程在父线程调用 `thread_join` 之前就已结束，那么该调用会立即返回；反之，如果父线程先调用 `thread_join`，它就会一直等到该线程结束，然后返回。

信号量的 P 和 V 也可以设置成类似的行为。通常（但并不总是）把信号量初始化为 0。这样，每次调用 `Semaphore::P` 都是在等待对应的线程调用 V；如果 V 先被调用，P 就立即返回。

困难出现在需要把共享状态（因而需要互斥）与一般等待协调起来的时候。乍看起来，`Semaphore::P` *类似于* `CV::wait(&lock)`，`Semaphore::V` *类似于* `CV::signal`。然而两者有重要差别。第一，`CV::wait(&lock)` 会原子地释放管程锁，因此你可以安全地检查共享对象的状态，然后原子地挂起执行。

相比之下，`Semaphore::P` 并**不**释放与之关联的互斥锁。通常，锁在调用 P 之前就被释放；否则，在该线程恢复运行之前，其他线程都无法访问共享状态。在这种情况下，程序员必须精心构造程序，才能让它正确工作。第二，条件变量是无状态的，而信号量有状态。如果没有线程在等待，调用 `CV::signal` 毫无效果，而调用 `Semaphore::V` 会把值加 1。这会使下一次 `Semaphore::P` 无需阻塞就能继续。

**“信号量弊大于利”。** 我们的观点是：用锁与条件变量编程优于用信号量编程。出于两个理由，我们建议你始终使用上述这些同步变量来编写代码。

第一，把锁与条件变量分成两个类，能让代码更好地自我说明，也更容易阅读。正如 Dijkstra 的引文所指出的，这里需要两种不同的抽象；通过显式的类型区分，让每个同步变量的角色一目了然，代码就更清楚。例如，如果获取锁与释放锁的调用没有与用于一般等待的 P、V 调用混在一起，那么验证每一次加锁都配有一次解锁就容易得多。

第二，把无状态的条件变量绑定到一把锁上，是比信号量更好的通用等待抽象。把条件变量绑定到锁之后，我们可以方便地在对象状态的任意谓词上等待。相反，信号量依赖程序员把对象的状态小心地映射为信号量的值，使得“在 P 中是等待还是继续”这一决定完全可以只依据该值作出，既不必持有锁，也不必检查共享对象状态的其余部分。

尽管我们不建议用信号量编写新代码，但基于信号量的代码并不罕见，在操作系统中尤其如此。因此，理解信号量的语义、能够阅读并理解他人编写的基于信号量的代码，是很重要的。

::: tip 中断处理程序中的信号量
有一种情形下，信号量优于条件变量和锁：在 I/O 设备与等待 I/O 完成的线程之间同步通信。通常，硬件通过一个共享的内存数据结构与设备驱动程序通信。这个数据结构会被硬件和内核并发读写，但这种共享访问无法用软件锁来协调。于是，硬件与设备驱动程序改用精心设计的原子内存操作。

如果硬件设备需要关注（例如一个需要处理的网络报文到达了，或者一个磁盘请求已经完成），硬件就更新共享数据结构，并启动一个中断处理程序。中断处理程序往往很简单：它只是唤醒一个正在等待的线程，然后返回。为此，人们也许会考虑使用条件变量，并在不持有锁的情况下调用 `signal`（这有时被称为*裸通知*（naked notify））。遗憾的是，这里有一个角落情形：假设操作系统线程先检查数据结构，发现当前没有工作需要做，并且正要调用条件变量上的 `wait`。就在此时，硬件把新的工作写入数据结构，并触发中断处理程序调用 `signal`。由于该线程尚未调用 `wait`，这个 `signal` 没有产生任何效果。于是，当线程调用 `wait` 时，信号早已发生，线程便一直等待下去——可能等很久。

一个常见的解决办法是让设备中断改用信号量。由于信号量是有状态的，无论线程先调用 P 还是中断处理程序先调用 V，结果都一样：V 不会丢失。
:::

为帮助说明信号量与条件变量的差别，我们考察四种用信号量实现条件变量的候选方案。

::: info 例
假设你在一个只提供信号量的操作系统上编写并发应用软件。下面的代码是否正确实现了条件变量？

```c
void CV::wait(Lock *lock) {
    lock->release();
    semaphore.P();
    lock->acquire();
}

void CV::signal() {
    semaphore.V();
}
```
:::

::: warning 答
**不。条件变量是无状态的，而信号量是有状态的。** 我们可以用一个反例来说明这种差别。

如果一个线程调用 `signal` 而无人等待，会发生什么？什么也不会发生。如果另一个线程稍后调用 `wait` 呢？该线程会等待。

相比之下，考虑信号量的情形。如果一个线程调用 V 而无人等待，会发生什么？信号量的值被加 1。如果某个线程稍后调用 P 呢？信号量的值被减 1，该线程继续执行。

换句话说，P 与 V 是可交换的：无论它们以何种顺序发生，结果都相同。条件变量则不可交换：`wait` 要等到下一次 `signal` 才会返回。这正是访问条件变量时必须持有锁的原因——使用条件变量的代码需要访问共享状态变量，才能完成它的工作。

对条件变量而言，如果一个线程在无人等待时调用了 `signal` 一千次，下一次 `wait` 仍会睡眠。而用上面的代码，接下来一千个调用 `wait` 的线程都会立即返回。□
:::

::: info 例
那么下面的代码呢？

```c
void CV::wait(Lock *lock) {
    lock->release();
    semaphore.P();
    lock->acquire();
}

void CV::signal() {
  if (!semaphore.queueEmpty())
      semaphore.V();
}
```
:::

::: warning 答
**更接近了，但仍然不对。** 首先，信号量的定义不允许信号量的使用者查看信号量队列的内容。但更重要的是，这里存在竞态条件。锁一旦被释放，其他线程就可能插进来，获取锁并调用 `signal`，而等待线程还没来得及调用 P。在这种情况下，队列是空的，等待者因此永远不会退出 while 循环。

而 `CV::wait` 的定义是：释放锁与线程进入睡眠必须原子地完成。□
:::

::: info 例
那么下面的代码呢？

```c
void CV::wait(Lock *lock) {
    waitQueue.append(myTCB);
    lock->release();
    semaphore.P();
    lock->acquire();
}

void CV::signal() {
    if (!waitQueue.isEmpty())
        semaphore.V();
}
```
:::

::: warning 答
**非常接近，但仍然不对。** 这里仍然存在竞态条件。假设一个线程调用 `wait` 并释放了锁，随后另一个线程获取锁并调用 `signal`。对条件变量而言，等待者应当被唤醒；但用上面的实现，可能有第三个线程抢先获取锁、调用 `wait`，并在第一个等待者有机会运行之前就把信号量的值减掉。

对某些程序来说，这种差别不会表现出来；但对另一些程序，它可能引发问题。□
:::

::: info 例
有可能用信号量实现条件变量吗？
:::

::: warning 答
**可以，使用我们为实现 FIFO 有界缓冲区而勾勒的技术：为每个等待者创建一个信号量，然后精确地唤醒正确的那个等待者。** 这个解法由 Andrew Birrell 提出，用于在 Microsoft Windows 原生支持条件变量之前，在其上实现条件变量。

```c

// 线程。
void CV::wait(Lock *lock) {
    semaphore = new Semaphore(0);
    waitQueue.Append(semaphore);
    lock.release();
    semaphore.P();
    lock.acquire();
}

// 如果有等待者，唤醒其中一个。
void CV::signal() {
    if (!waitQueue.isEmpty()) {
        semaphore = queue.Remove();
        semaphore.V();
    }
}
```

□

## 5.9　小结与未来方向

本章倡导用系统化、结构化的方法来编写在线程之间共享状态的多线程代码。这种方法——用锁与条件变量管理对共享对象的并发访问——经受住了时间的检验。使用共享对象来推理多线程程序，要比试图推理单条加载、存储指令可能的各种交错方式简单得多。此外，遵循系统化的方法，还能让他人有可能阅读、理解、维护和修改我们编写的多线程代码。

本章讨论了以下内容：

- **竞态条件。** 编写使用共享数据的多线程代码所面临的根本挑战在于：程序的行为可能取决于各线程所执行操作的确切顺序。这种非确定性的行为很难推理、复现和调试。

- **锁与条件变量。** 两种有用的同步抽象是提供互斥的锁，以及用于等待共享状态发生变化的条件变量。

- **编写共享对象的方法。** 使用锁与条件变量，我们勾勒了为协调对共享对象的访问而编写正确同步代码的一系列步骤。在我们的课堂上，遵循这一方法已被证明对学生大有帮助，因为它降低了设计出错的可能性。

- **同步的实现。** 借助硬件对原子读-改-写指令的支持，以及在必要时临时推迟硬件中断的能力，可以高效地实现锁与条件变量。特别地，我们展示了获取和释放无争用锁的开销可以低至四条指令。

- **信号量。** 信号量是锁与条件变量的一种被广泛实现的替代方案，它在管理硬件 I/O 中断方面具有建设性的作用。

简而言之，本章定义了一套核心技能，几乎任何程序员在今后十年乃至更长的时间里都会反复用到。

但这还不是故事的全部。正如下一章将要讨论的，复杂系统往往包含许多共享对象和线程。这带来了新的挑战：对跨越多个共享对象的操作进行同步；避免死锁——即一组线程都在等待彼此做某件事；以及在大量线程争用同一个对象时尽可能提高性能。

### 5.9.1　历史注记

一旦研究者接受了用线程显式管理并发的必要性，挑战就变成了如何最好地协调多线程对共享数据的访问。当时人们提出了大量不同的抽象，并且花了一些时间才弄清各种方法各自的优缺点。

管程——也就是用锁与条件变量来管理共享数据结构——于 20 世纪 70 年代初由 Tony Hoare [83] 和 Per Brinch Hansen [75] 分别在各自的论文中提出。管程的一个早期优势是能够对多线程代码的性质作形式化证明；例如，在 Hoare 式的条件变量语义下，任何在 `signal` 之前一刻对共享对象成立的断言，在从 `wait` 返回之后一刻仍然成立。正如我们在“牛奶过多”一例中所见，没有显式同步时，推理并发执行可能相当困难。

到 20 世纪 80 年代初，Xerox PARC 已经造出了第一台个人计算机 Alto，它的全部系统软件都是用线程（当时称为轻量级进程）和管程编写的。本章介绍的方法就源自那个项目 [98]。这种做法在当时有多么激进，几乎怎么形容都不为过；那个年代几乎所有广泛使用的操作系统（包括 UNIX）都是用信号量构建的。

另一条研究路线主张彻底禁止线程访问共享数据，以此消除竞态条件。数据不再共享，而是全部归单个线程私有；这样一来就永远不需要锁。这条路线的一个早期例子是通信顺序进程（CSP），同样由 Tony Hoare 提出 [84]。Google 用于并发 Web 编程的 Go 语言是一门现代语言，同时支持管程和 CSP 风格的编程。在 CSP 和 Go 中，一个线程若需要对另一个线程的数据执行操作，就向它发送一条消息；接收线程可以用结果回复，或者按数据流的风格把结果转发给另一个线程。

当时，关于消息传递与共享内存哪一种才是更好的并发编程模型，曾有过相当激烈而广泛的争论；这场争论在很大程度上被 Lauer 和 Needham [101] 的一个简单观察所化解：任何使用管程的程序都可以通过一种简单的变换改写成 CSP，反之亦然。在管程锁的保护下执行一个过程，等价于在 CSP 中处理一条消息；实际上，管程在持有锁期间是单线程的。因此，选择哪一种风格在很大程度上是品味与惯例的问题，而大多数程序员选择了线程与管程。
