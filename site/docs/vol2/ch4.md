<div class="chap-en">Concurrency and Threads</div>
<blockquote class="epigraph">众人拾柴火焰高。——<em>约翰·海伍德（1546）</em></blockquote>

在计算机之外的真实世界里，不同的活动常常同时进行。五位爵士乐手各自演奏乐器，同时又在互相应和；一辆车向北行驶，另一辆向南行驶；药物分子的某一部分被细胞受体吸引，而另一部分被排斥；一台人形机器人一边行走，一边举起手臂、转动头部；你从《纽约时报》网站上读一篇文章，另一个人正在读另一篇；母亲节这天，数百万人同时拨打长途电话。

我们用*并发*（concurrency）一词来指称可以同时发生的多个活动。真实世界是并发的；在计算机内部，现代计算机同样是并发的。例如，一台高端服务器可能带有十几颗处理器、10 块磁盘和 4 个网络接口；一台工作站可能带有十几个活跃的 I/O 设备，包括显示器、键盘、鼠标、摄像头、麦克风、扬声器、无线网卡、有线网卡、打印机、扫描仪和磁盘驱动器。今天，就连手机也往往配备多核处理器。

正确地管理并发是操作系统开发者面临的关键挑战。为了管理硬件资源、为用户提供及时的响应，并同时运行多个应用程序，操作系统需要一种有条理的方式来跟踪它必须完成的各种活动。在接下来的几章里，我们将给出表达和管理并发的一组抽象。这些抽象在商用操作系统中被广泛使用，因为它们降低了实现复杂度、提高了系统可靠性，也改善了性能。

并发同样是许多应用开发者关心的问题。虽然我们要讨论的这些抽象最初是为了让操作系统代码更容易写对，但它们如今在应用程序中已得到广泛使用：

- 网络服务必须能够同时处理来自客户端的多个请求；一个一次只能处理一个搜索请求的 Google，或者一个一次只允许购买一本书的 Amazon，用处都会小得多。

- 今天的大多数应用程序都有用户界面；要让用户获得良好的响应，同时又要执行应用逻辑，采用结构化的并发方法会容易得多。

- 并行程序需要把工作映射到多个处理器上，才能获得多核体系结构带来的性能收益。

- 数据管理系统需要借助并发来掩盖磁盘和网络操作的延迟。

从程序员的角度看，按顺序思考远比同时跟踪许多活动容易。例如，在读或写一个过程的代码时，你可以确定初始状态和一组前置条件，逐条推演每条语句如何改变状态，并由此确定后置条件。可是，当几十个事件同时发生时，你又如何写出正确的程序呢？

关键的思想是：把一个并发程序——也就是含有许多同时进行的活动的程序——写成一组顺序的执行流，即*线程*（thread），它们以非常精确的方式相互作用并共享结果。线程让我们可以定义一组并发运行的任务，而每个任务的代码仍然是顺序的。每个线程都表现得好像拥有自己的专用处理器，如图 4.1 所示。我们在后面会看到，使用线程抽象往往还需要程序员编写额外的代码，来协调多个线程对共享数据结构的访问；这个话题将在第 5 章详细讨论。

线程抽象让程序员可以按需创建任意多个线程，而不必操心物理处理器究竟有多少个，也不必操心在每一时刻究竟是哪个处理器在执行什么。当然，线程只是一种抽象：物理硬件的处理器数量是有限的（而且可能只有一个！）。操作系统的职责，就是在物理硬件相当有限的情况下，提供“虚拟处理器几乎无穷多”的假象。它通过透明地挂起和恢复线程来维持这一假象，使得任一时刻只有一部分线程真正在运行。

本章将定义线程抽象，说明程序员如何使用这一抽象，并解释操作系统如何在一组有限的处理器之上实现线程。第 5 章说明当线程操作共享数据时如何协调它们，第 6 章讨论用线程编程时的一些高级问题。第 7 章讨论策略问题：当需要运行的东西多于可用的处理器时，操作系统应当如何选择*下一个*运行哪个线程。

## 4.1　线程的使用场景

线程抽象背后的直觉很简单：在程序中，我们可以把每个并发任务表示为一个*线程*。每个线程都提供了与传统编程模型类似的顺序执行抽象。事实上，我们可以把传统程序看作*单线程的*（single-threaded）——指令一条接一条地执行，程序只有一个逻辑步骤序列：依次执行语句、迭代循环、调用并从过程返回。

*多线程程序*是同一基本编程模型的推广。每个线程在执行语句、循环迭代、过程调用与返回时，都遵循单一的操作序列。区别在于，一个程序现在可以同时有若干个这样的线程在运行。

那么，什么时候适合在同一个程序内使用多个线程？线程在操作系统代码和应用代码中都已广泛使用，从这些经验中可以归纳出几个常见的主题。我们通过较为详细地描述一个应用来说明这些主题，看看它是如何、又为什么借助线程的。

### 4.1.1　使用线程的四个理由

用线程来表达和管理并发，有如下几个优点：

- **程序结构：表达逻辑上并发的任务。** 程序常常要与真实世界中带有并发活动的应用打交道，或者去模拟这类应用。线程让你可以把每个并发任务写成一个独立的线程，从而表达应用固有的并发性。在地球可视化程序中，线程让不同的活动——刷新屏幕、取回更多数据、接收新的用户输入——同时进行。举例来说，为了在重绘屏幕、收发网络报文的同时还能接收鼠标输入，物理处理器必须在这些任务之间分配时间。人们当然可以设想手写一个把这些活动交织起来的程序（例如先画几个像素，然后检查用户是否移动了鼠标，再检查网络上是否到达了新的图像数据……），但使用线程会大大简化并发代码。另一个例子是地球可视化程序的服务器端。服务器要管理大量客户端的请求，每个客户端关注地球上不同的位置。由于这些客户端很可能接在各种不同的接入链路技术上（例如从拨号上网到千兆以太网），如果每个请求都必须处理完毕服务器才能开始下一个，所有人的速度都会被拖慢。为每个客户端创建一个独立的线程后，该客户端所需的计算和网络通信就可以与其他客户端交错进行，而不影响程序的逻辑结构。这种“每个客户端一个服务器线程”的设计模式很常见；例如流行的 Apache Web 服务器会在客户端首次连接时为其分配一个线程。

- **响应性：把工作移到后台执行。** 为了提高用户响应性和性能，一种常见的设计模式是创建线程在后台完成工作，而不让用户等待结果。这样，无论用户请求多么复杂，用户界面都能对后续命令保持响应。例如在 Web 浏览器中，即使（或者说尤其）下载的页面极其庞大，或者页面中的脚本要执行很久，取消按钮也应当继续有效。这是怎么做到的？许多应用都有一个循环：取一条用户命令，执行它，再取下一条命令。然而，如果某些命令执行起来很慢，那么一个把所有事情都顺序执行的应用程序，在完成上一条命令之前就无法检查下一个操作。为了让界面保持响应，我们可以用线程把每条命令拆成两部分：凡是能立即完成的部分都放在主事件循环里做，剩下的部分交给另一个线程在后台完成。在地球可视化程序中，我们就用线程把应用逻辑中计算量大的部分——渲染显示——移出了主循环。操作系统内核大量使用线程来保持响应性。许多操作系统的设计原则是让常见情形足够快。例如，写文件时，操作系统把被修改的数据放入内核缓冲区，随即返回应用程序；在后台，内核另有一个线程把这些修改过的数据刷写到磁盘。再比如读文件：内核可以有一个线程，设法预测接下来可能被读取的块（例如应用程序正在从头到尾读取一个大文件），并在应用请求之前就把这些块从磁盘取入内存。

- **性能：利用多个处理器。** 程序可以在多处理器上用线程并行地完成工作；它们可以用更少的时间完成同样的工作，或者在同样的时间内完成更多的工作。今天，一台服务器可能有十几颗处理器；台式机或笔记本电脑可能包含八个处理器核；就连大多数智能手机也是多核机器。展望未来，摩尔定律使每个系统的处理器数量很可能继续增加。用线程实现并行的一个好处是，线程数不必与硬件处理器的数量精确匹配。操作系统会透明地切换哪个线程在哪个处理器上运行。对于一台 8 处理器机器，你可以把地球可视化应用并行化：把渲染屏幕上不同区域这一繁重工作分给六个线程。于是操作系统可以让这六个渲染线程在六个处理器上运行，同时让另外各种线程在两个剩余处理器上运行——更新屏幕上的导航控件、构造从远端服务器取回更多图像所需的网络报文，以及解析应答报文。

- **性能：管理 I/O 设备。** 计算机必须通过 I/O 设备与外部世界交互，才能做有用的工作。把任务作为独立的线程来运行后，当一个任务在等待 I/O 时，处理器可以推进另一个任务。处理器与 I/O 之间的并发有两方面好处。第一，处理器通常比与它交互的 I/O 系统快得多，因此在 I/O 期间让处理器空转，会浪费它的大部分能力。例如，从磁盘读取的延迟可达数十毫秒，这足以让现代处理器执行一千多万条指令。在请求一个磁盘块之后，操作系统可以切换到另一个程序，或同一程序中的另一个线程，直到磁盘操作完成、原线程可以恢复为止。第二，I/O 提供了计算机与外部实体交互的途径，例如用户敲击键盘，或者远程计算机发来网络报文。这类 I/O 事件的到达是不可预测的，因此处理器必须能够在处理其他任务的同时，仍然快速响应这些外部事件。在地球可视化应用中，流畅的用户界面至关重要，但大部分图像存放在远程服务器上，只在需要时才取回。当用户改变位置时，应用先下载该位置的一幅小的低分辨率视图，从而提供流畅的体验；在用一个线程渲染这些图像的同时，另一个线程并行地取回分辨率越来越高的图像，渲染线程便可以在高分辨率图像到达时更新视图。

::: tip 线程与进程
第 2 章把进程描述为“在受限权限下执行一个程序”。线程则是程序中一条独立的指令序列。要理解这两个概念的关系，最好的办法也许是看不同的操作系统如何以不同方式把它们组合起来：

- **每个进程一个线程。** 简单的单线程应用只有一条从头到尾执行的指令序列。操作系统内核以用户态运行这些指令，从而限制对特权操作或系统内存的访问。进程通过系统调用，请求内核替它执行特权操作。

- **每个进程多个线程。** 另一种做法是：程序由若干个并发线程构成，每个线程都在该进程的受限权限之内执行。任一时刻，进程的线程中可能只有一部分在运行，其余处于挂起状态。进程中的任何线程都可以向内核发起系统调用，这会使该线程阻塞到调用返回为止，但其他线程仍可继续运行。同样，当处理器收到 I/O 中断时，它会抢占某个正在运行的线程，以便内核运行中断处理程序；处理程序结束后，内核再恢复该线程。

- **多个单线程进程。** 就在二十年前，许多操作系统还只支持多个进程，而每个进程只有一个线程。然而在内核看来，每个进程都像一个线程：一条独立的指令序列，有时在内核中执行，有时在用户级执行。例如在多处理器上，如果多个进程同时发起系统调用，内核实际上就有多个线程在内核态并发执行。

- **多个内核线程。** 为了管理复杂性、把工作移到后台、利用并行性并掩盖 I/O 延迟，操作系统内核本身也能从使用多个线程中获益。此时，每个内核线程都以内核权限运行：它可以执行特权指令、访问系统内存，并直接向 I/O 设备发出命令。操作系统内核为自身的使用实现了线程抽象。

由于线程如此有用，几乎所有现代操作系统都同时支持“每个进程多个线程”和“多个内核线程”。
:::

## 4.2　线程抽象

至此，我们已经描述了线程是什么、为什么有用。在继续深入之前，我们必须更精确地定义线程抽象及其性质。

*线程*是*一条单独的执行序列*，它代表*一个可以独立调度的任务*。

- **单独的执行序列。** 每个线程执行一串指令——赋值、条件、循环、过程调用等等——与我们所熟悉的顺序编程模型完全一样。

- **可以独立调度的任务。** 操作系统可以在任意时刻运行、挂起或恢复一个线程。

### 4.2.1　运行、挂起与恢复线程

线程提供了“处理器数量无穷多”的假象。操作系统如何实现这一假象？它必须执行来自每个线程的指令，使每个线程都取得进展；但底层硬件只有数量有限的处理器，甚至可能只有一个！

为了把任意一组线程映射到一组固定的处理器上，操作系统提供了一个*线程调度器*（thread scheduler），它可以在正在运行的线程与已经就绪但尚未运行的线程之间切换。例如在图 4.1 中，调度器可以把线程 1 从处理器 1 上挂起、放入就绪线程的列表，然后把线程 5 从就绪列表移出、在处理器 1 上恢复运行。

线程之间的切换对每个线程中正在执行的代码是透明的。这一抽象让每个线程看起来都是一条单一的执行流；这意味着程序员只需关注线程内部指令的顺序，而不必关心这条序列是否、以及何时会被（暂时）挂起，以便让另一个线程运行。

于是，线程提供的执行模型是：*每个线程都在一个专用的虚拟处理器上运行，其速度不可预测且不断变化*。从线程代码的角度看，每条指令似乎都紧接在前一条之后立即执行。然而调度器可能在某条指令与下一条之间挂起线程，稍后再恢复它。这就好像线程所运行的处理器有时会变得非常慢。

::: tip 协作式多线程与抢占式多线程
尽管大多数线程系统都包含一个（至少在原则上）可以在任意时刻运行任意线程的调度器，有些系统提供的却是*协作式线程*（cooperative threads）抽象。在这类系统中，线程一直运行而不被打断，直到它显式地把处理器的控制权让给另一个线程。协作式多线程的一个优点是对线程间交错的掌控更强。例如，在大多数协作式多线程系统中，同一时刻只有一个线程在运行，因此当某个线程运行时，不会有别的线程来运行并改变系统状态。

遗憾的是，协作式多线程也有明显的缺点。例如，一个长时间运行的线程可能独占处理器，使其它线程饥饿，令系统的用户界面变得迟缓甚至失去响应。此外，现代多处理器机器同时运行多个线程，因此即便采用协作式多线程，仍然必须推敲线程之间可能的相互作用。所以，尽管协作式多线程曾用于一些重要的系统（包括 Apple MacOS 操作系统的早期版本），今天已较少使用。

本书所描述的另一种方案有时称为*抢占式多线程*（preemptive multi-threading），因为正在运行的线程可以在任意时刻被切换。本书凡使用“多线程”一词，除特别说明外，均指抢占式多线程。
:::

### 4.2.2　为什么是“不可预测的速度”？

要求程序员假设线程的虚拟处理器以不可预测的速度运行、并且与其它线程的任何交错都有可能发生，这看起来也许有些奇怪。既然某些交错比另一些更可能发生，程序员难道不应该加以利用吗？

线程编程模型采纳这一假设，是为了给程序员提供一个推理正确性的准绳。多线程程序不应当假设一个线程与另一个线程速度相同（或更快、更慢），也不应当试图依据线程的相对执行速度来协调它们；相反，多线程程序不应对线程调度器的行为作任何假设。相应地，内核的调度决策——何时把线程分配到某个处理器、何时为了另一个线程而抢占它——也就可以在不担心是否影响程序正确性的前提下作出。

如果线程彼此完全独立，不共享内存或其它资源，那么执行顺序无关紧要——任何一种调度产生的输出都与其它调度相同。然而大多数多线程程序都要共享数据结构。这时，正如第 5 章所述，程序员必须使用显式的同步，以确保无论不同线程的指令如何交错，程序都是正确的。

即使我们可以忽略调度问题——例如处理器比线程还多，每个线程都分到自己的物理处理器——物理现实仍然是：不同线程的相对执行速度会受到它们无法控制的因素的显著影响。一个极端的例子是，程序员可能在单步调试一个线程，而其它线程正在别的处理器上全速运行。如果程序员还想弄懂并发程序的行为，程序的正确性就不能依赖于究竟哪些线程正在被观察。

执行速度的波动在正常运行中同样存在。一旦发生缓存缺失，访问内存可能使处理器停顿数百甚至数千个周期。其它因素还包括：调度器抢占线程的频繁程度、机器上有多少颗物理处理器、缓存有多大、内存有多快、节能固件如何调整处理器的时钟频率、有哪些网络报文到达、以及从用户那里收到什么输入。一个程序中不同线程的执行速度很难预测，会随硬件不同而变化，甚至在同一硬件上每次运行都不相同。因此，我们必须通过显式同步来协调线程的行为，而不是试图去推断它们的相对速度。

::: info 例
内核的中断处理程序是一个线程吗？
:::

::: warning 答
**不是。中断处理程序不是线程。** 内核中断处理程序与线程有某些相似之处：它也是一条从头到尾执行的指令序列。但是，中断处理程序不能被独立调度：它由硬件 I/O 事件触发，而不是由内核中的线程调度器决定。一旦开始，中断处理程序就会一直运行到结束，除非被另一个（更高优先级的）中断抢占。□
:::

图 4.5 给出了一个使用线程的简单 API。这一简化的 API 基于 POSIX 标准的 pthreads API，但为简单起见省略了一些 POSIX 选项和错误处理。大多数其它线程包都与之十分相似；如果你学会了用这个 API 编程，就会发现用大多数标准线程 API 写代码都很容易。

理解这套简单线程 API 的一个好办法，是把它看成为**异步过程调用**（asynchronous procedure call）提供了一种手段。普通的过程调用把一组参数传给函数，立即在调用者的栈上运行该函数，函数完成后带着结果把控制权交还调用者。异步过程调用则把“调用”与“返回”分开：借助 thread_create，调用者启动函数，但与普通过程调用不同，调用者会与被调用的函数并发地继续执行。稍后，调用者可以（用 thread_join）等待该函数完成。

在第 3 章中，我们在 UNIX 进程抽象里见过类似的概念。thread_create 类似于 UNIX 进程的 fork 与 exec，而 thread_join 类似于 UNIX 进程的 wait。UNIX 的 fork 创建一个新进程，它与调用 fork 的进程并发运行；UNIX 的 exec 让该进程运行一个特定的程序；UNIX 的 wait 则让调用进程挂起执行，直到新进程结束。

### 4.3.1　一个多线程的 Hello World

<div class="code-cap"><span class="code-label">图 4.6</span>使用简单线程 API 的多线程程序示例，它打印十次“Hello”。图中还给出该程序某一次运行的输出。</div>

```c
#include <stdio.h>
#include "thread.h"

static void go(int n);

#define NTHREADS 10
static thread_t threads[NTHREADS];

int main(int argc, char **argv) {
    int i;
    long exitValue;

    for (i = 0; i < NTHREADS; i++){
        thread_create(&(threads[i]), &go, i);
    }
    for (i = 0; i < NTHREADS; i++){
        exitValue = thread_join(threads[i]);
        printf("Thread %d returned with %ld\n",
                        i, exitValue);
    }
    printf("Main thread done.\n");
    return 0;
}

void go(int n) {
    printf("Hello from thread %d\n", n);
    thread_exit(100 + n);
    // Not reached
}
```

为了说明简单线程 API 的用法，图 4.6 给出了一个用 ’C’ 语言编写的非常简单的多线程程序。main 函数用 `thread_create` 创建了 10 个线程。有意思的是第二个和第三个参数。

```text

Hello from thread 3
Hello from thread 4

Hello from thread 5

Hello from thread 6

Hello from thread 9

Thread 3 returned 103
Thread 4 returned 104

Thread 6 returned 106
Thread 7 returned 107
Thread 8 returned 108

```

- 第二个参数 go 是一个函数指针——新创建的线程应当从这里开始执行。

- 第三个参数 i 被传给该函数。

因此，thread_create 初始化第 i 个线程的状态，使它准备好以参数 i 调用函数 go。

当调度器运行第 i 个线程时，该线程以值 i 为参数运行函数 go，并打印 Hello from thread i。随后，线程通过调用 thread_exit 返回值（i + 100）。这次调用把指定的值存入 thread_t 对象的一个字段，以便 thread_join 能够取回它。

main 函数用 thread_join 等待它创建的每一个线程。每当一个线程结束，main 中的代码就读出该线程的退出值并打印它。

::: info 例
为什么线程 2 的“Hello”消息可能在线程 5 的“Hello”消息**之后**打印，尽管线程 2 先于线程 5 创建？
:::

::: warning 答
**创建线程与调度线程是两个独立的操作。** 尽管线程通常按创建顺序被调度，但这一点并无保证。此外，即使线程 2 在线程 5 之前开始运行，它也可能在到达 printf 调用之前被抢占。

更确切地说，程序员唯一能作的假设是：每个线程都在自己的虚拟处理器上以不可预测的速度运行。任何交错都是可能的。□
:::

::: info 例
为什么线程 2 的“Thread returned”消息必须在线程 5 的“Thread returned”消息之前打印？
:::

::: warning 答
由于线程在速度不可预测的虚拟处理器上运行，线程结束的先后顺序是不确定的。然而，**主线程是按线程创建的顺序检查线程是否结束的。** 只有当线程 i 的 thread_join 返回之后，它才会为线程 i+1 调用 thread_join。□
:::

::: info 例
当线程 5 打印“Hello”时，系统中可能存在的线程数的**最小值**和**最大值**各是多少？
:::

::: warning 答
程序启动时，一个主线程开始运行 main。该线程创建 NTHREADS = 10 个线程。这些线程都可能在 5 号线程打印“Hello”之前运行完毕。因此，**最小值是两个线程**——主线程与 5 号线程。另一方面，也可能 10 个线程全部已经创建，而 5 号线程是第一个运行的线程。因此，**最大值是 11 个线程。** □
:::

### 4.3.2　分叉-汇合并行

尽管图 4.5 中的接口很简单，它却异常强大。许多多线程应用可以只用这些线程操作、无需任何额外的同步来设计。利用*分叉-汇合并行*（fork-join parallelism），线程可以创建子线程去执行工作（“分叉”，即 `thread_create`），并等待它们的结果（“汇合”，即 `thread_join`）。只要数据 (a) 在子线程开始之前由父线程写入，或者 (b) 由子线程写入、并在汇合之后由父线程读取，就可以在线程之间安全地共享。

如果遵守了这些共享方面的限制，每个线程都将独立地、确定性地执行，不受任何其他并发执行线程的行为影响。把线程多路复用到处理器上，除了影响性能之外没有别的作用。

<div class="code-cap"><span class="code-label">图 4.7</span>用多个线程并行地把一块连续的内存区域清零的例程。为了向子线程传递两个参数（指向缓冲区的指针和缓冲区的长度），程序传递一个指向保存这两个参数的 struct 的指针。</div>

```c
// To pass two arguments, we need a struct to hold them.
typedef struct bzeroparams {
    unsigned char *buffer;
    int length;
};

#define NTHREADS 10

void go (struct bzeroparams *p) {
    memset(p->buffer, 0, p->length);
}

// Zero a block of memory using multiple threads.
void blockzero (unsigned char *p, int length) {
    int i;
    thread_t threads[NTHREADS];
    struct bzeroparams params[NTHREADS];

// For simplicity, assumes length is divisible by NTHREADS.
    assert((length % NTHREADS) == 0);
    for (i = 0; i < NTHREADS; i++) {
        params[i].buffer = p + i * length/NTHREADS;
        params[i].length = length/NTHREADS;
        thread_create_p(&(threads[i]), &go, &params[i]);
    }
    for (i = 0; i < NTHREADS; i++) {
        thread_join(threads[i]);
    }
}
```

::: info 例
**并行块清零。** 操作系统里分叉-汇合并行的一个简单例子，是把一块连续内存清零的过程。为了防止无意的数据泄漏，每当一个进程退出时，操作系统都必须把曾分配给该退出进程的内存清零。否则，新进程可能被重新分配到这段内存，从而得以读取其中可能敏感的数据。例如，操作系统的远程登录程序可能暂时把用户的密码存放在内存中，而下一个使用同一段物理内存的进程，可能是另一个怀有恶意的用户启动的内存扫描程序。
:::

对于一个大的进程来说，把清零函数并行化是合理的。在现代计算机上，把 1 GB 内存清零大约需要 50 毫秒；相比之下，创建并启动一个新线程只需要几十微秒。

图 4.7 给出了用分叉-汇合并行实现的一个并行清零函数的代码。多线程的 blockzero 创建一组线程，并把内存区域的互不相交的一部分分配给每个线程；当所有线程都完成工作后，该区域就被清零了。

在实践中，操作系统常常会创建一个线程在后台运行 blockzero。退出进程的内存并不需要立即清除，等到真正需要这段内存时——也就是创建下一个进程时——再清除即可。

为了利用这种灵活性，操作系统可以创建一组低优先级的线程来运行 blockzero。内核随即可以返回，继续运行应用程序的代码。稍后，当需要这段内存时，内核可以调用 thread_join。如果到那时清零已经完成，join 会立即返回；否则，它将等到这段内存可以安全使用为止。

## 4.4　线程的数据结构与生命周期

正如我们所见，每个线程代表一条顺序的执行流。操作系统通过透明地挂起和恢复线程，营造出每个线程都运行在自己的虚拟处理器上的假象。要让这一假象成立，操作系统必须精确地保存和恢复线程的状态。然而，由于线程要么运行在进程中、要么运行在内核中，还存在*共享的*状态——在把处理器从一个线程切换到另一个线程时，这部分状态无需保存或恢复。

因此，要理解操作系统如何实现线程抽象，我们必须同时定义每线程的状态（per-thread state）以及线程之间共享的状态。然后才能描述线程的生命周期——操作系统如何创建、启动、停止和删除线程，以提供这一抽象。

### 4.4.1　每线程状态与线程控制块（TCB）

操作系统需要一个数据结构来表示线程的状态；在这一点上线程与其它对象并无二致。这个数据结构称为*线程控制块*（thread control block, TCB）。操作系统每创建一个线程，就为它创建一个 TCB。

线程控制块保存两类每线程的信息：

+ 线程正在进行的计算的状态。

+ 关于该线程、用于管理该线程的元数据。

**每线程的计算状态。** 为了创建多个线程，并能够按需启动和停止每个线程，操作系统必须在线程控制块（TCB）中为每个线程当前的运算状态分配空间：一个指向该线程的栈的指针，以及一份它的处理器寄存器的副本。

- **栈。** 线程的栈与单线程计算所用的栈相同——它存放该线程当前正在运行的各层嵌套过程所需的信息。例如，若线程调用 foo()，foo() 调用 bar()，bar() 又调用 bas()，那么栈上会包含这三个过程各自的**栈帧**；每个栈帧包含该过程使用的局部变量、调用该过程时传入的参数，以及过程结束时应当跳转到的返回地址。由于在任一时刻，不同线程可能处于其顺序计算的不同状态——每个线程可能处在不同过程的不同位置，而这些过程又是从不同的外层过程嵌套中以不同的参数调用的——所以每个线程都需要自己的栈。创建新线程时，操作系统为它分配一个新栈，并把指向该栈的指针存入该线程的 TCB。

- **处理器寄存器的副本。** 处理器的寄存器不仅包括用于存放正在进行的计算中间值的通用寄存器，还包括专用寄存器，例如指令指针和栈指针。为了能够挂起一个线程、运行另一个线程、稍后再恢复原来的线程，操作系统需要有一个地方，在该线程不活跃运行时存放它的寄存器。在某些系统中，被停止线程的通用寄存器存放在栈顶，TCB 中只保存一个指向栈的指针。在另一些系统中，TCB 中包含存放全部处理器寄存器副本的空间。

::: tip 栈要多大？
线程系统在实现上有一个问题：应当为每个线程分配多大的栈？栈随着过程的调用与返回而增长和收缩。栈的大小必须足以容纳线程生存期内所需的最深嵌套层次。当有数百或数千个线程时，分配的栈若超过最小需要量，就可能造成浪费。

大多数现代操作系统把内核栈分配在物理内存中，因而空间十分宝贵。不过，内核中过程嵌套的最大深度通常很小。因此，内核通常为每个线程栈分配一个很小的固定大小区域，例如在 Intel x86 上的 Linux 中默认为 8 KB。内核之所以能保持在这个界限之内，靠的是一条重要的内核编码约定：缓冲区与数据结构总是分配在堆上，而从不作为过程的局部变量。尽管大多数编程语言允许把任意数据结构定义为过程的局部变量或“自动”变量——在过程开始时分配、在过程退出时释放——但当栈的大小有限时，这样做会带来问题。

用户级栈分配在虚拟内存中，因此对空间约束的要求不那么紧。在单线程进程中，栈位于地址空间的顶端，几乎可以不受限制地增长。为了捕捉程序错误，大多数操作系统会在用户程序的栈增长得过大过快时触发错误，因为这通常意味着无界递归，而不是程序员的本意。

在多线程的用户应用程序中，不可能让每个栈都无约束地增长。尽管某些编程语言（例如 Google 的 Go）会按需自动增长栈，但这样做仍然不常见。POSIX 允许默认栈大小取决于具体的库（例如在台式机上较大，在智能手机上较小）。正如一份 POSIX 线程教程不无揶揄地所说：“超出默认栈限制是很容易发生的，通常的结果是：程序终止和/或数据被损坏。”[10] 大多数实现试图在程序超过默认栈限制时检测出来，办法是在栈的最顶端和最底端放入一个已知的值作为警戒。这些警戒值可以在每次上下文切换时检查；如果值发生了变化，线程很可能就超出了自己的栈。

为了支持应用的可移植性，POSIX 线程标准允许用户把默认栈大小重新定义为某个特定程序正确执行所需的任何值。本书配套的线程库把默认栈大小设为 1 MB。只要你采纳内核的做法、从不把大的数据对象放在栈上，这个大小几乎肯定是够用的。
:::

**每线程的元数据。** TCB 中还包含**每线程的元数据**——用于管理该线程的信息。例如，每个线程可能有一个线程 ID、调度优先级和状态（例如，该线程是在等待某个事件，还是已准备好被放到某个处理器上运行）。

### 4.4.2　共享状态

与为每个线程分配的每线程状态相对，有些状态是在同一进程中运行的各线程之间、或在操作系统内核内*共享*的（图 4.8）。特别是，程序*代码*由进程内的所有线程共享，尽管每个线程可能在代码的不同位置执行。此外，静态分配的*全局变量*和动态分配的*堆变量*可以存储所有线程都能访问的信息。

::: tip 其他每线程状态：线程局部变量
除了与单线程情形下的执行状态相对应的每线程状态之外，有些系统还包含额外的**线程局部变量**（thread-local variables）。这些变量与全局变量相似，其作用域跨越不同的过程；不同之处在于，每个线程都有自己的一份副本。

考虑下面这些例子：

- **Errno。** 在 UNIX 中，系统调用的返回值被有意保持得很简单。例如，UNIX 的 read 系统调用要么返回读取的字节数（成功时），要么返回 -1（出错时）。应用程序常常需要关于错误原因的更多信息（例如权限错误、磁盘离线等）。为此，内核在应用程序的内存中设置一个变量 errno，保存最近一次系统调用的诊断码。由于 UNIX 最初每个进程只有一个线程，这里并无混淆：errno 指的是该进程最近一次系统调用。然而在多线程程序中，多个线程可以并发地执行系统调用。为了不必为多线程环境重新定义整个 UNIX 系统调用接口，errno 现在是一个宏，它映射到一个线程局部变量，其中保存该线程最近一次系统调用的错误码。

- **堆的内部实现。** 虽然程序的堆在逻辑上是共享的——一个线程在堆上分配一个对象、再把指向该对象的指针传给另一个线程，这是允许的——但出于性能原因，堆可能会在内部把自己的空间细分为每线程的区域。细分堆的好处是多个线程可以各自同时分配对象而互不干扰。此外，把同一线程使用的对象从同一内存区域分配，还能提高缓存命中率。为了实现这些优化，堆的每个细分区域都有线程局部变量，用来记录该线程局部堆的哪些部分正在使用、哪些部分空闲，等等。于是，分配新内存的代码（例如 malloc 和 new）被写成使用这些线程局部数据结构，并且只有当局部堆为空时才从共享堆中取内存。

线程局部变量常常很有用，但为简单起见，我们余下的讨论只把 TCB、寄存器和栈作为每线程状态的核心组成部分来关注。
:::

**警告：** 尽管每线程的状态与共享的状态之间存在着重要的逻辑划分，操作系统通常并不强制实施这一划分。没有什么能阻止一个有缺陷的线程去访问另一个线程的（概念上私有的）每线程状态。在一个线程中向错误的指针写入，可能破坏另一个线程的栈。或者，粗心的程序员可能把指向某个线程栈上局部变量的指针传给另一个线程，使第二个线程得到一个指向栈上位置的指针，而该位置的内容会随着第一个线程调用和返回各个过程而变化。又或者，第一个线程在交出指向自己栈上某个变量的指针之后就退出了；堆会把那段内存重新分配给一个毫不相干的用途。由于这些缺陷可能取决于线程执行的具体交错方式，它们极难定位和修正。

因此，为了避免出现意外的行为，在编写多线程程序时，重要的是弄清哪些变量被设计为跨线程共享（全局变量、堆上的对象），哪些被设计为私有（局部变量/自动变量）。

**INIT（初始）。** 创建线程会把线程置入 INIT 状态，并为它分配和初始化每线程的数据结构。这些工作完成之后，创建线程的代码就把该线程加入*就绪列表*（ready list），从而把线程置入 READY 状态。就绪列表是所有可运行、正在等待轮到自己使用处理器的线程的集合。在实践中，正如第 7 章所讨论的，就绪列表实际上并不是一个“列表”；操作系统通常使用更复杂的数据结构（例如优先级队列）来跟踪可运行的线程。尽管如此，按照惯例，我们仍将继续称它为就绪列表。

**READY（就绪）。** 处于 READY 状态的线程可以被运行，但当前并未运行。它的 TCB 位于就绪列表上，其寄存器的值保存在 TCB 中。调度器可以在任何时刻把线程的寄存器值从 TCB 复制到某个处理器的寄存器中，从而使线程从 READY 转入 RUNNING。

**RUNNING（运行）。** 处于 RUNNING 状态的线程正在某个处理器上运行。此时，它的寄存器值存放在处理器上，而不是存放在 TCB 中。处于 RUNNING 的线程可以通过两种方式转入 READY 状态：

- 调度器可以抢占正在运行的线程，把它移到 READY 状态，具体做法是：(1) 把该线程的寄存器保存到它的 TCB 中；(2) 切换处理器，让它运行就绪列表上的下一个线程。
- 正在运行的线程可以通过调用 `yield`（例如线程库中的 `thread_yield`）自愿让出处理器，从 RUNNING 转入 READY。

注意，线程可以在 READY 与 RUNNING 之间往返转换许多次。由于操作系统精确地保存和恢复线程的寄存器，这些转换只影响线程执行的速度。

**警告：** 按照本书的约定，处于 RUNNING 的线程不在就绪列表上；就绪列表只存放处于 READY 而非 RUNNING 的线程。不过，有些操作系统（例如 Linux）采用另一种约定：位于就绪列表最前面的那个线程就是 RUNNING 线程。只要始终如一地使用，两种约定是等价的。

**WAITING（等待）。** 处于 WAITING 状态的线程正在等待某个事件。调度器可以把处于 READY 状态的线程转入 RUNNING 状态，而处于 WAITING 状态的线程则不能运行，直到另一个线程的某个动作把它从 WAITING 转入 READY。

图 4.6 中的 `threadHello` 程序给出了一个处于 WAITING 状态的线程的例子。主线程在创建了各个子线程之后，必须等待它们完成，办法是对每个子线程调用一次 `thread_join`。如果在调用 join 时某个子线程尚未结束，主线程就从 RUNNING 转入 WAITING，直到该子线程退出。

线程在等待某个事件期间无法取得进展，因此运行它没有用处。这时，TCB 既不会被继续用于运行该线程，也不会被放进调度器的就绪列表，而是存放在与所等事件相关联的某个*同步变量*（synchronization variable）的*等待列表*（waiting list）上。当所需的事件发生时，操作系统把该 TCB 从同步变量的等待列表移到调度器的就绪列表，从而把线程从 WAITING 转入 READY。我们将在第 5 章描述同步变量。

**FINISHED（结束）。** 处于 FINISHED 状态的线程再也不会运行。系统可以释放它的部分或全部状态以供他用，不过也可能把 TCB 放入*结束列表*（finished list），在一段时间内保留该线程的某些残余。例如，`thread_exit` 调用让线程可以经由 `thread_join` 把自己的退出值传给父线程。最终，当线程的状态不再需要时（例如其退出值已被 join 调用读走），系统就可以删除并回收该线程的状态。

理解这些状态的一个办法，是考察线程的 TCB 与寄存器分别存放在哪里，如表 4.10 所示。例如，所有处于 READY 状态的线程，其 TCB 都在就绪列表上，寄存器都在 TCB 中。所有处于 RUNNING 状态的线程，其 TCB 都在运行列表（running list）上，寄存器值都在硬件寄存器中。而所有处于 WAITING 状态的线程，其 TCB 都在各个同步变量的等待列表上。

::: tip 空闲线程
如果系统有 k 个处理器，大多数操作系统会确保恰好有 k 个处于 RUNNING 的线程：它为每个处理器保留一个低优先级的*空闲线程*（idle thread），以便在没有别的线程可运行时使用。

在旧式机器上，空闲线程会在一个紧凑的循环中空转，什么也不做。

今天，空闲线程仍然在循环中空转，但为了省电，它在每次迭代时都把处理器置入低功耗睡眠模式。在睡眠模式下，处理器停止执行指令，直到发生硬件中断。随后，处理器被唤醒，以常规方式处理该中断——保存当前正在运行的线程（即空闲线程）的状态，并运行处理程序。处理程序运行结束后，某个等待该 I/O 事件的线程可能已经变为 READY。如果是这样，调度器接下来就运行那个线程；否则，空闲线程恢复执行，再次把处理器置入睡眠。

在虚拟机中运行操作系统时，拥有一个低功耗的空闲线程同样有帮助。显然，空闲的操作系统若占用本可以更好地供同一系统中其他虚拟机使用的处理周期，是低效的。把处理器置入睡眠模式是一条特权指令，因此如果操作系统运行在虚拟机内部，硬件会陷入宿主内核（host kernel）。宿主内核随后就可以切换到另一台虚拟机。
:::

::: info 例
对图 4.6 中的 `threadHello` 程序，当针对线程 i 调用 `thread_join` 返回时，线程 i 处于什么状态？
:::

::: warning 答
当 join 返回时，线程 i 已经运行完毕并退出。运行时系统把退出值保存在 TCB 中，并把 TCB 移到结束列表（以便父线程能够找到它的退出值）。**因此该线程处于 FINISHED 状态。** □
:::

::: info 例
对 `threadHello` 程序，在*单处理器*（uniprocessor）上，主线程进入 READY 状态的次数最少是多少、最多是多少？
:::

::: warning 答
主线程刚被创建时，必须进入 READY 状态；否则它永远不会被调度。在单处理器上，为了让子线程得以运行，它还必须让出处理器（例如由于时间片用完，或者在 `thread_join` 中）。此后，子线程可以在主线程被重新调度之前全部运行完毕。一旦子线程结束，主线程就可以一直运行到完成。因此，**最少是两次。**

**最多则（近乎）无限次。** 正在运行的线程可以被抢占并重新调度许多次，而不影响执行的正确性。在极端情况下，甚至可以设想线程在每执行完一条指令之后就被抢占！□
:::

::: tip 我的 TCB 在哪里？
实现上一个相当棘手的问题是：如何找到当前线程的 TCB。线程库出于多种原因需要访问当前 TCB，例如改变线程的优先级，或者访问线程局部的变量。

人们可能认为找到 TCB 很简单：只要把一个指向 TCB 的指针存放在全局变量里即可。然而要记得，同一进程中运行的每个线程使用的代码完全相同，因此每个线程都会在完全相同的位置查找 TCB。在单处理器上，这种做法可行：全局变量可以保存当前 TCB 的值，库在切换线程时更新该值。

然而，在多处理器上这种做法行不通。有些系统（例如 Intel x86）在硬件上支持读取当前处理器的 ID。在这类系统中，线程库可以维护一个全局的指针数组，第 i 个表项指向运行在第 i 个处理器上的线程的 TCB。正在运行的线程于是可以先查出自己的处理器 ID，再在数组中找到对应的表项，从而找到自己的 TCB。

对于没有这一特性的系统，还有另一种办法：栈指针总是每个线程独有的。线程库可以把指向线程 TCB 的指针存放在栈的最底部、过程帧的下面。（有些系统更进一步，把整个 TCB 放在栈底。）只要线程栈按固定的块边界对齐，就可以通过对当前栈指针的低位做掩码，定位到指向当前 TCB 的指针。
:::

## 4.6　实现内核线程

到目前为止，我们已经描述了线程的基本数据结构与操作。现在我们来描述如何实现它们。实现的具体方式因上下文而异：

- **内核线程。** 最简单的情形是在操作系统内核内部实现线程，让它们共享一个或多个物理处理器。*内核线程*（kernel thread）执行内核代码、修改内核数据结构。今天几乎所有商用操作系统都支持内核线程。

- **内核线程与单线程进程。** 一个支持内核线程的操作系统可能同时运行一些单线程的用户进程。如图 4.11 所示，这些进程可以发起系统调用，并在内核中与内核线程并发执行。

- **用内核线程实现多线程进程。** 大多数操作系统提供一组库例程和系统调用，让应用程序可以在单个用户级进程内使用多个线程。图 4.12 说明了这种情形。这些线程执行用户代码、访问用户级数据结构；它们也会向操作系统内核发起系统调用，为此需要一个内核中断栈，就像普通的单线程进程一样。

- **用户级线程。** 为了避免每次线程操作都发起系统调用，有些系统支持这样一种模型：用户级的线程操作——创建、让出、汇合、退出，以及第 5 章描述的同步例程——完全在用户级库中实现，不调用内核。

### 4.6.1　创建线程

<div class="code-cap"><span class="code-label">图 4.13</span>创建线程的伪代码。初始化栈的具体做法，以及向初始函数传递参数的约定，都与机器相关。在 Intel x86 体系结构上，栈从高地址开始向下增长，参数通过栈传递；在其他系统上，栈可能向上增长，参数也可能通过寄存器传递。图 4.14 给出了 <code>thread_dummySwitchFrame</code> 的伪代码。</div>

```c
 // func is a pointer to a procedure the thread will run.
 // arg is the argument to be passed to that procedure.
 void
 thread_create(thread_t *thread, void (*func)(int), int arg) {
     // Allocate TCB and stack
     TCB *tcb = new TCB();

     thread->tcb = tcb;
     tcb->stack_size = INITIAL_STACK_SIZE;
     tcb->stack = new Stack(INITIAL_STACK_SIZE);

     // Initialize registers so that when thread is resumed, it will start running at
     // stub.  The stack starts at the top of the allocated region and grows down.
     tcb->sp = tcb->stack + INITIAL_STACK_SIZE;
     tcb->pc = stub;

     // Create a stack frame by pushing stub’s arguments and start address
     // onto the stack: func, arg
     *(tcb->sp) = arg;
     tcb->sp--;
     *(tcb->sp) = func;
     tcb->sp--;

     // Create another stack frame so that thread_switch works correctly.
     // This routine is explained later in the chapter.
     thread_dummySwitchFrame(tcb);

     tcb->state = READY;
     readyList.add(tcb);    // Put tcb on ready list
 }

 void
 stub(void (*func)(int), int arg) {
     (*func)(arg);           // Execute the function func()
     thread_exit(0);         // If func() does not call exit,  call it here.
 }
```

图 4.13 给出了分配新线程的伪代码。`thread_create` 的目标是发起一次异步过程调用：以 `arg` 为实参调用 `func`。当该线程运行时，它将与调用线程并发地执行 `func(arg)`。

创建一个线程分三步：

+ **分配每线程状态。** 线程构造函数的第一步，是为该线程的每线程状态分配空间，即 TCB 和栈。前面已经提到，TCB 是线程系统用来管理线程的数据结构；栈是一块内存区域，用来存放与正在执行的过程有关的数据，它像其他数据结构一样在内存中分配。

+ **初始化每线程状态。** 为了初始化 TCB，线程构造函数把新线程的寄存器设置为线程开始 RUNNING 时所需的值。当我们为该线程分配处理器时，希望它开始运行 `func(arg)`。不过，构造函数并不让线程从 `func` 开始，而是让它从一个哑函数 `stub` 开始，再由 `stub` 调用 `func`。之所以要多这一层，是因为 `func` 过程可能直接返回而不调用 `thread_exit`。没有 `stub` 的话，`func` 就会返回到栈顶存放的那个随机位置去！有了 `stub`，`func` 返回到 `stub`，再由 `stub` 调用 `thread_exit` 结束该线程。为了让线程从 `stub` 的开头开始运行，线程构造函数把栈布置成“`stub` 刚刚被普通代码调用”的样子；具体做法取决于机器的调用约定。在伪代码中，我们把 `stub` 的两个参数 `func` 和 `arg` 压入栈。线程开始运行时，`stub` 中的代码就会像普通过程那样访问自己的参数。此外，我们还在栈上压入一个供 `thread_switch` 使用的哑栈帧；这一细节留到讨论线程切换的实现时再解释。

+ **把 TCB 放入就绪队列。** 创建线程的最后一步，是把线程状态置为 READY，并把新的 TCB 放入就绪队列，使该线程可以被调度。

### 4.6.2　删除线程

当线程调用 `thread_exit` 时，删除线程分两步进行：

- 把线程从就绪队列中移除，使它再也不会运行。

- 释放为该线程分配的每线程状态。

这看起来很简单，却有一个重要的微妙之处：如果线程把自己从就绪队列中移除，并释放自己的每线程状态，程序就可能出错。举例来说，如果线程把自己从就绪队列中移除，但在它完成状态释放之前发生了一次中断，就会造成内存泄漏：该线程再也不会被恢复运行，它的状态也就永远不会被释放。

更糟的是，假设线程释放的是自己的状态，会怎样？如果没有栈，该线程还能把 `thread_exit` 中的代码执行完吗？如果正在运行的线程的栈刚被释放就发生中断，又会怎样？如果上下文切换代码试图保存当前线程的状态，它就会写入已被释放的内存，甚至可能写入另一个处理器重新分配给其他数据结构的存储区。结果可能是内存被破坏，而具体表现取决于事件的确切顺序。不用说，这样的缺陷极难定位。

幸运的是，有一个简单的解决办法：线程永远不删除自己的状态，而由别的线程来删除。退出时，线程转入 FINISHED 状态，把它的 TCB 从就绪队列移到*已完成*（finished）线程的链表上，调度器永远不会运行这个链表上的线程。随后该线程可以安全地切换到就绪队列中的下一个线程。一旦已完成的线程不再运行，再由*另一个*线程释放它的状态就是安全的。

### 4.6.3　线程上下文切换

为了支持多个线程，我们还需要一种机制，来切换哪些线程处于 RUNNING、哪些处于 READY。

*线程上下文切换*（thread context switch）挂起当前正在运行的线程，恢复另一个线程的执行。切换时，它把当前线程的寄存器保存到该线程的 TCB 和栈中，再把新线程的寄存器从它的 TCB 和栈恢复到处理器中。

我们需要回答几个问题：

- 什么会触发上下文切换？

- 自愿的上下文切换（例如调用 `thread_yield`）是如何工作的？

- 非自愿的上下文切换与自愿的切换有何不同？

- 调度器接下来应当选择哪个线程运行？

我们依次讨论这些问题，但把最后一个留到第 7 章。本章讨论的*机制*（mechanism），无论调度器在选择线程时采用何种*策略*（policy），都能工作。

::: tip 机制与策略分离
把机制与策略分离，是操作系统设计中一条有用且被广泛采用的原则。当机制与策略被干净地分开时，就更容易引入新的策略，使系统针对新的负载或新的技术得到优化。

例如，线程上下文切换这一抽象就把机制（如何在线程之间切换）与策略（运行哪个线程）干净地分开了，因此无论采用什么策略，机制都能工作。有的系统可以选择简单的做法（例如先进先出调度）；另一些系统则可以针对自己的目标优化调度（例如用周期性的调度器为媒体设备平滑地运行实时多媒体流，用轮转调度器为服务器兼顾响应时间与吞吐量，或者用优先级调度器把大部分资源都投入到智能手机上那个可见的应用）。

我们将在本书中多次看到这一原则。例如，线程同步机制无论采用何种调度策略都能工作；用于定位文件块的文件元数据机制，无论采用何种策略决定文件块在磁盘上的放置位置都能工作；用于把虚拟地址映射为物理地址的页转换机制，无论操作系统为各个进程分配哪些物理页都能工作。
:::

**什么会触发内核线程的上下文切换？** 线程上下文切换可以由自愿的线程库调用触发，也可以由非自愿的中断或处理器异常触发。

- **自愿的。** 线程可以调用某个会触发上下文切换的线程库函数。例如，大多数线程库提供 `thread_yield` 调用，让当前运行的线程自愿把处理器让给就绪队列中的下一个线程。同样，`thread_join` 和 `thread_exit` 调用会挂起当前线程的执行，转而运行另一个线程。

- **非自愿的。** *中断*或*处理器异常*可能调用中断处理程序。中断硬件保存正在运行的线程的状态，并执行处理程序的代码。处理程序可以判定应当运行另一个线程，然后切换到它；反之，如果当前线程应当继续运行，处理程序就恢复被中断线程的状态并继续执行。例如，许多线程系统被设计成保证任何线程都无法独占处理器。为此，它们设置一个硬件定时器，周期性地中断处理器（例如每隔几毫秒）。定时器中断处理程序保存正在运行的线程的状态，选择另一个线程，并把它的状态恢复到处理器中运行。其他 I/O 硬件事件（例如按下键盘按键、网络报文到达、磁盘操作完成）也会调用中断处理程序。在这些情形下，处理程序同样会保存当前运行线程的状态以便稍后恢复，然后执行处理程序的代码；处理完毕后，它要么恢复当前线程的状态，要么切换到新线程。如果该 I/O 事件把一个优先级高于先前运行线程的线程放到了就绪队列上，就会运行这个新线程。

无论哪种情况，线程系统都必须保存当前的处理器状态，使当前线程恢复执行时，*从该线程自己的角度看*，除了时间流逝之外，那个事件仿佛从未发生过。这就提供了“线程在一个速度不可预测且不断变化的虚拟处理器上执行”这一抽象。

为简单起见，我们不希望在执行一次自愿切换的过程中再发生一次非自愿的切换。在两个线程之间切换时，需要暂时推迟中断，直到切换完成，以免造成混乱。处理器提供了用于推迟和重新允许中断的特权指令，下面的实现就利用了它们。

::: tip 线程切换时为什么必须关中断？
我们对 `thread_yield` 的实现，会把该过程执行期间可能发生的任何中断都推迟到让出操作完成之后。这看起来似乎没有必要：毕竟，即使线程上下文切换被打断，切换的状态也会保存在栈上。最终内核会重新调度该线程、恢复它的状态，并完成这次线程切换。

然而，可能出现一种微妙的不一致。假设一个低优先级线程（例如空闲线程）正要自愿切换到某个高优先级线程。它把高优先级线程从就绪队列中取出，而恰在这一刻发生了一次中断。假设该中断把一个中优先级线程从 WAITING 移到 READY。由于从表面上看处理器仍在运行低优先级线程，中断处理程序就立即切换到新线程。于是高优先级线程陷入了悬置状态！它已经就绪，却要等到低优先级线程被重新调度之后才能运行；而那可能很久之后才会发生。

当然，这种事件顺序不会经常出现，但一旦出现，就很难定位和调试。
:::

**自愿的内核线程上下文切换。** 自愿切换比较容易理解，所以我们从这里开始。图 4.14 给出了 Intel x86 硬件体系结构上一个简单的 `thread_yield` 实现的伪代码。线程调用 `thread_yield`，自愿把处理器让给另一个线程。调用线程的寄存器被复制到它的 TCB 和栈中，稍后当调度器选中它时再恢复运行。

<div class="code-cap"><span class="code-label">图 4.14</span>Intel x86 体系结构上 <code>thread_switch</code> 与 <code>thread_yield</code> 的伪代码。注意，如果没有其他线程可运行，<code>thread_yield</code> 就是一个空操作；否则它保存旧线程的状态并恢复新线程的状态。当旧线程被重新调度时，它从 <code>thread_switch</code> 返回，作为运行线程继续执行。</div>

```c
 // We enter as oldThread, but we return as newThread.
 // Returns with newThread’s registers and stack.
 void thread_switch(oldThreadTCB, newThreadTCB) {
     pushad;                  // Push general register values onto the old stack.
     oldThreadTCB->sp = %esp; // Save the old thread’s stack pointer.
     %esp = newThreadTCB->sp; // Switch to the new stack.
     popad;            // Pop register values from the new stack.
     return;
 }

 void thread_yield() {
     TCB *chosenTCB, *finishedTCB;

     // Prevent an interrupt from stopping us in the middle of a switch.
     disableInterrupts();

     // Choose another TCB from the ready list.
     chosenTCB = readyList.getNextThread();
     if (chosenTCB == NULL) {
         // Nothing else to run, so go back to running the original thread.
     } else {
         // Move running thread onto the ready list.
         runningThread->state = ready;
         readyList.add(runningThread);
         thread_switch(runningThread, chosenTCB); // Switch to the new thread.
         runningThread->state = running;
     }

     // Delete any threads on the finished list.
     while ((finishedTCB = finishedList->getNextThread()) != NULL) {
         delete finishedTCB->stack;
         delete finishedTCB;
     }
     enableInterrupts();
 }

 // thread_create must put a dummy frame at the top of its stack:
 // the return PC and space for pushad to have stored a copy of the registers.
 // This way, when someone switches to a newly created thread,
 // the last two lines of thread_switch work correctly.
 void thread_dummySwitchFrame(newThread) {
     *(tcb->sp) = stub;      // Return to the beginning of stub.
     tcb->sp--;
     tcb->sp -= SizeOfPopad;
 }
```

`thread_yield` 的伪代码首先关中断，以防线程系统同时尝试进行两次上下文切换。接着，伪代码从就绪队列中取出下一个要运行的线程（如果有），并切换到这个线程。

`thread_switch` 的代码看起来可能有点绕，因为它是在旧线程的上下文中被调用，却在新线程的上下文中结束。为了做到这一点，`thread_switch` 把寄存器的状态保存到栈上，并把栈指针保存到 TCB；然后它切换到新线程的栈，从新栈恢复新线程的状态，并返回到新栈上保存的程序计数器所指的地方。

一个蹊跷之处在于，返回位置可能并不是 `thread_yield`！返回的是新线程先前正在做的事情。例如，新线程可能一直在 `thread_join` 中处于 WAITING，现在变成 READY 可以运行了；它可能调用过 `thread_yield`；也可能是一个刚刚开始运行的新创建线程。

关键的一点是：任何导致线程让出或阻塞的例程，都必须以同样的方式调用 `thread_switch`。同样，为了创建新线程，`thread_create` 必须把新线程的栈布置成仿佛它刚好在执行第一条指令之前被挂起。这样，如果新创建的线程是下一个要运行的线程，那么线程就可以调用 `thread_yield`、切换到新创建的线程、切换到它的栈指针、从栈上弹出寄存器值，并“返回”到新线程——尽管新线程从头到尾都没有调用过 `switch`。

::: info 例
假设两个线程各自循环，每次迭代都调用 `thread_yield`。

```c
    go() {
        while(1) {
            thread_yield();
        }
    }
```

:::

**图 4.15 给出了这种交错：** `thread_yield` 由一个线程调用，却在另一个线程中返回。`thread_yield` 通过操纵栈和程序计数器来在线程之间切换，有意违背了编译器通常遵循的过程调用约定。

::: tip 零线程内核
内核既可以是单线程的，也可以是多线程的；实际上，内核还可以完全没有自己的线程——也就是零线程内核！事实上，这种设计曾经相当常见 [107]。

回想第 2 章描述的那种简单的操作系统图景。一旦系统完成引导、初始化了设备驱动程序，并启动了若干用户级进程（例如登录 shell），内核所做的其他一切就都是事件驱动的，即都是为响应中断、处理器异常或系统调用而做的。

在这样一个简单的操作系统中，不需要用“内核线程”或“内核线程控制块”来跟踪正在进行中的计算。相反，当发生中断、陷入或异常时，栈指针被置为中断栈的基址，指令指针被置为处理程序的地址。接着处理程序开始执行，并要么立即返回到被中断的用户级进程，要么挂起该用户级进程并“返回”到另一个用户级进程。无论哪种情况，下一个事件（中断、处理器异常或系统调用）都会让这一过程重新开始。
:::

**非自愿的内核线程上下文切换。** 第 2 章解释了当中断、异常或陷入打断正在运行的用户级进程时会发生什么：硬件与软件协同工作，保存被中断进程的状态、运行内核的处理程序，然后恢复被中断进程的状态。

当中断或陷入引发内核中两个线程之间的切换时，机制几乎完全相同。第 2 章描述的三个步骤略有修改（*改动之处以斜体标出*）：

+ **保存状态。** 保存当前正在运行的*线程*的寄存器，使处理程序能够运行代码而不干扰被中断的*线程*。中断或异常发生时，硬件保存一部分状态；处理程序运行时，软件保存其余状态。

+ **运行内核的处理程序。** 运行内核的处理程序代码，处理中断或异常。*由于我们已经处于内核态，这一步不需要从用户态切换到内核态。我们也不需要把栈指针改为内核中断栈的基址，而只需从当前栈指针开始，把保存的状态或处理程序的变量压入当前栈。*

+ **恢复状态。** 恢复*下一个就绪线程*的寄存器，使该线程能够从上次离开的地方继续运行。

简而言之，把内核线程之间的切换与用户态下发生的一次转移相比：(1) 不需要切换模式（因而也不需要切换栈）；(2) 处理程序可以恢复就绪队列上的任意线程，而不必总是恢复刚刚被挂起的那个线程或进程。

**实现细节。** 在大多数处理器体系结构上，从中断处理程序内部切换到下一个线程，有一种简单（但低效）的办法：在处理程序返回之前调用 `thread_switch`。正如我们已经看到的，`thread_switch` 保存当前线程（也就是中断处理程序）的状态，并切换到新的内核线程。当原来的线程恢复运行时，它会从 `thread_switch` 返回，随即从栈上弹出中断上下文，在被中断的位置继续执行。

大多数系统（例如 Linux）会做一点小优化，以提高中断处理的性能。被中断线程的状态其实已经保存在栈上，只不过采用的是中断硬件规定的格式。如果我们修改 `thread_switch`，让它完全按照中断硬件的方式保存和恢复寄存器，那么从中断返回与恢复一个线程就成了同一个动作：两者都是从栈上弹出中断帧，以恢复下一个要运行的线程。

例如，为了与 x86 的中断硬件兼容，`thread_switch` 的软件实现会模拟硬件的情形：在调用 `pushad` 保存通用寄存器之前，先保存返回的指令指针和 eflags 寄存器。切换到新栈之后，它调用 `iret` 来恢复新线程——无论新线程是被硬件事件挂起的，还是被软件调用挂起的。

## 4.7　把内核线程与单线程用户进程结合起来

前面的图 4.11 展示了一个既有内核线程、又有单线程用户进程的系统。进程是指令的顺序执行，因此每个用户级进程都包含该进程的线程。然而，进程不只是线程，因为它还拥有自己的地址空间：进程 1 有自己的内存视图、自己的代码、自己的堆和自己的全局变量，与进程 2（以及内核）的都不同。

由于进程包含的不只是一个线程，每个进程的进程控制块（PCB）需要比内核线程的线程控制块（TCB）保存更多信息。与 TCB 一样，单线程进程的 PCB 必须在该进程的线程未运行时保存处理器寄存器。除此之外，PCB 还保存有关该进程地址空间的信息；当从一个进程切换到另一个进程时，操作系统不仅要改变寄存器状态，还必须改变虚拟内存映射。

由于 PCB 与 TCB 各自代表一个线程，内核的就绪队列里可以同时混有进程的 PCB 和内核线程的 TCB。调度器选择下一个要运行的线程时，这两种都可以选。无论是在内核线程之间切换，还是在进程的线程与内核线程之间切换，线程切换的做法几乎完全相同：两种情况下都要保存当前正在运行的线程的状态，再恢复下一个要运行的线程的状态。

正如第 2 章所述，大多数操作系统为每个进程专设一个内核中断栈。这样一来，当进程需要执行系统调用，或者发生中断、处理器异常时，硬件会陷入内核，保存用户级的处理器状态，并开始在内核中的某个特定处理程序处运行。一旦进入内核，进程的线程就表现得与内核线程完全一样——它可以创建线程（或其他进程）、可以阻塞（例如在 UNIX 的进程等待中，或在等待 I/O 时），甚至可以退出。在内核中运行时，该进程可能被定时器中断或 I/O 事件抢占，让更高优先级的进程或内核线程取而代之。被抢占进程的 PCB 和内核栈中，既保存着它当前的内核状态，也保存着该进程发起系统调用时保存的用户级状态。

在内核中，我们可以用 `thread_switch` 恢复一个进程。不过，当系统调用或中断处理完毕、要恢复用户级进程的执行时，我们必须把它的状态精确地恢复到先前的样子：寄存器中是正确的值，运行在用户态，虚拟内存映射恰当，如此等等。

一个重要的细节是：许多处理器体系结构为用户级代码准备了额外的协处理器状态，例如浮点寄存器。通常，操作系统内核并不使用浮点运算。因此，内核在两个内核线程之间切换时无需保存这些寄存器，但在两个进程之间切换时就必须保存并恢复它们。

::: tip 一点小差别
你也许注意到，第 2 章讲到的模式切换会让 x86 硬件在启动处理程序之前，不只保存指令指针和 eflags 寄存器，还要保存被中断进程的**栈指针**。因为在模式切换时，硬件要把栈指针改为内核的中断栈，所以它必须保存原来的用户级栈指针。

与此相反，从内核线程转入内核处理程序时，硬件并不切换栈。处理程序就在当前栈上运行，而不是在一个单独的中断栈上运行。因此硬件无需保存原来的栈指针；处理程序只是随其他寄存器一起，在 `pushad` 指令中保存栈指针。

于是，x86 硬件从内核线程转入内核处理程序时的行为，与进行模式切换时略有不同：

- **进入处理程序。** 发生中断或异常时，如果处理器（通过检查 eflags 寄存器）发现自己已经处于内核态，它就只是把指令指针和 eflags 寄存器（而不包括栈指针）压入现有的栈。反之，如果硬件发现这次是从用户态切换到内核态，处理器还会把栈指针改为中断栈的基址，并把原来的栈指针连同指令指针和 eflags 寄存器一起压入新栈。

- **从处理程序返回。** 执行 `iret` 指令时，它会同时检查当前的 eflags 寄存器和栈上那个将用来恢复先前 eflags 寄存器的值。如果两者的模式位相同，`iret` 就只弹出指令指针和 eflags 寄存器，继续使用当前的栈。反之，如果模式位不同，`iret` 不仅会弹出指令指针和 eflags 寄存器，还会弹出保存的栈指针，从而把处理器的栈指针切换到所保存的那个值。
:::

## 4.8　实现多线程进程

到目前为止，我们描述了如何在操作系统内核内实现多个线程。当然，我们还希望能够运行用户程序。由于许多用户程序是单线程的，我们先从如何把内核线程与单线程进程结合起来这一简单情形入手，然后再讨论实现*多线程进程*（multi-threaded process，即拥有多个线程的进程）的各种方式。所有广泛使用的现代操作系统都同时支持内核线程和多线程进程。Java 这类编程语言，以及 POSIX 和 simple threads 这类标准库接口，都利用操作系统的这一支持，向程序员提供线程抽象。

### 4.8.1　用内核线程实现多线程进程

支持每个进程多个线程的最简单办法，是使用我们已经描述过的内核线程实现。当内核线程创建、删除、挂起或恢复线程时，它可以用一次简单的过程调用完成。当用户级线程访问线程库做同样的事情时，它则通过系统调用，请求内核代为执行该操作。

正如前面图 4.12 所示，进程中的一个线程拥有：

- 一个用户级栈，用于执行用户代码。

- 一个内核中断栈，用于该线程发起系统调用、引发处理器异常或被中断时使用。

- 一个内核 TCB，用于保存和恢复每线程的状态。

要创建一个线程，用户库先为该线程分配一个用户级栈，然后发起一次进入内核的系统调用。内核分配 TCB 和中断栈，并把该线程的状态布置成：它将在用户级栈上、从所请求的过程的起点开始执行。内核需要把指向该 TCB 的指针存入进程控制块；如果进程退出，内核必须终止该进程中仍在运行的其他线程。

创建线程之后，内核把新线程放入就绪队列，让它像其他线程一样被调度，并向用户程序返回一个唯一的标识符，供其在引用新建的线程时使用（例如用于 join）。

线程的 join、yield 与 exit 也是如此：都是通过调用进入内核来执行所请求的功能。

### 4.8.2　在没有内核支持的情况下实现用户级线程

也可以把线程实现为一个完全位于用户级的库，而不需要操作系统的任何支持。早期的线程库之所以采用这种纯用户级方案，原因很简单：当时几乎没有操作系统支持多线程进程。即便在操作系统对线程的支持普及之后，纯用户级线程有时仍被用来最小化对特定操作系统的依赖、最大化可移植性；例如，Sun 的 Java 虚拟机（JVM）最早的实现采用的就是所谓*绿色线程*（green threads）——一种纯用户级的线程实现。

基本思路很简单。线程库把它的全部数据结构都建立在进程内部：TCB、就绪队列、已完成队列和等待队列，都只是进程地址空间里的数据结构。于是，对线程库的调用就只是过程调用，这与在多线程内核内部实现同样这些函数的方式颇为类似。

在操作系统内核看来，使用绿色线程（green thread）的多线程应用就是一个普通的单线程进程。整个进程可以发起系统调用、可以被分时调度，等等。与内核线程不同的是，当一个使用绿色线程的进程被分时调度时，整个进程连同它的所有线程都会被挂起。

绿色线程的一个局限是：操作系统内核并不知道用户级就绪队列的状态。如果应用发起了一个因等待 I/O 而阻塞的系统调用，内核就无法改为运行另一个用户级线程。同样，在多处理器上，内核也无法把同一进程内运行的不同线程放到不同处理器上运行。

**抢占式用户级线程。** 不过，在大多数操作系统上，是可以为同一进程内执行的用户级线程实现抢占的。正如第 2 章所讨论的，大多数操作系统提供一种上调机制，用来向进程投递异步事件通知；在 UNIX 上，这类机制称为信号处理程序。典型的事件或信号包括用户按下“Escape”，或者在 UNIX 上按下“Control-C”；这通知应用应当尝试干净地退出。另一类常见事件是表示实际时间已流逝的定时器中断。为了投递一个事件，内核先挂起该进程的执行，然后让它在用户代码指定的处理程序处恢复运行，该处理程序通常运行在一个单独的上调栈或信号栈上。

要为某个进程 P 实现抢占式多线程，做法如下。

+ 用户级线程库发起一次系统调用，向内核注册一个定时器信号处理程序和一个信号栈。

+ 硬件定时器中断发生时，硬件保存 P 的寄存器状态，并运行内核的处理程序。

+ 内核的处理程序并不恢复 P 的寄存器状态、让 P 从被中断处继续运行，而是把 P 保存的寄存器复制到 P 的信号栈上。

+ 内核让 P 在信号栈上已注册的信号处理程序处恢复执行。

+ 信号处理程序把被抢占的用户级线程的处理器状态，从信号栈复制到该线程的 TCB 中。

+ 信号处理程序选出下一个要运行的线程，重新允许信号处理程序（相当于重新允许中断），并把新线程的状态从它的 TCB 恢复到处理器中，以（刚）存放在信号栈上的状态继续执行。

这种做法把中断和处理器异常虚拟化了，使用户级进程所看到的图景，与内核在这些事件发生时所看到的图景非常相似。

### 4.8.3　在内核支持下实现用户级线程

今天，大多数程序使用内核支持的线程，而不是纯用户级线程。主要操作系统都以标准抽象的形式支持线程，因此可移植性问题已不像从前那样突出。

不过，各类系统更多采用一种混合模型，试图把用户级线程那种轻量的性能以及对调度的应用级控制结合起来，同时保留内核线程的许多优点。

**混合式线程汇合。** 在某些情况下，线程库可以避免转入内核。例如，`thread_join` 不必总是发起系统调用来等待目标线程结束，而可以由 `thread_exit` 把自己的退出值存入进程地址空间中的某个数据结构。这样一来，如果对 `thread_join` 的调用发生在目标线程已经退出之后，它就可以立刻返回该值，无需发起系统调用。然而，如果对 `thread_join` 的调用先于 `thread_exit`，那就需要一次系统调用，以便转入 WAITING 状态，让其他线程得以运行。进一步的优化是：在多处理器上，`thread_join` 有时适宜在进入内核之前先自旋几微秒，寄希望于另一个线程在此期间结束。

**每处理器内核线程。** 绿色线程的思路也可以改造成能在多处理器上工作的形式。对许多并行科学计算应用来说，创建和同步线程的开销是头等大事，因此那种大多数线程操作都要陷入内核的做法代价高得无法接受。于是，线程库把用户级线程多路复用到内核线程之上，其方式与内核把内核线程多路复用到物理处理器之上完全相同。

应用启动时，用户级线程库为宿主机上的每颗处理器各创建一个内核线程。只要系统上没有其他活动，内核就会为每个这样的线程分配一颗处理器。每个内核线程并行地执行用户级调度器：从用户级就绪队列中取出下一个线程并运行它。由于线程调度决策发生在用户级，它们可以很灵活，也可以针对具体应用定制；例如在并行图算法中，程序员可以根据图的其他部分的计算结果，调整各个线程的优先级。

当然，这些系统中仍然存在绿色线程的大部分缺点：

- 每当用户级线程调用进入内核时，承载它的内核线程就会阻塞。这使线程库无法在此期间把另一个用户级线程放到那颗处理器上运行。

- 每当内核把一个内核线程分时挂起时，该内核线程当时正在运行的用户级线程也随之被挂起。在内核线程恢复之前，线程库无法恢复那个线程。

**调度器激活。** 为了解决这些问题，一些操作系统增加了对用户级线程的显式支持。其中一种模型称为*调度器激活*（scheduler activations），最近在 Windows 中得到了实现。在这种做法中，凡有可能影响用户级线程系统的内核事件，都会通知（或激活）用户级线程调度器。例如，如果一个线程在系统调用中阻塞，激活机制会告知用户级调度器：应当另选一个线程在那颗处理器上运行。调度器激活类似于上调或信号，区别在于它不返回内核，而是直接在用户级完成线程的挂起与恢复。

有多种操作会触发调度器激活上调：

+ **增加虚拟处理器的数量。** 程序启动时会收到一次激活，告知它已被分配一颗虚拟处理器：这次激活运行主线程，以及此后可能创建的其他线程。要给程序再分配一颗虚拟处理器，内核会在那颗新的处理器上再发起一次激活上调；用户级调度器便可以从就绪队列中取出一个等待中的线程并运行它。

+ **减少虚拟处理器的数量。** 当内核抢占一颗虚拟处理器（例如要把这颗处理器让给另一个进程）时，内核会在分配给该并行程序的其他某颗处理器上发起一次上调。线程系统随即可以把被抢占的用户级线程移到就绪队列上，好让另一颗处理器运行它。

+ **转入 WAITING。** 当用户级线程在内核中因等待 I/O 而阻塞时，内核同样会发起一次上调，通知用户级调度器需要采取行动，例如在等待 I/O 完成期间另选一个线程来运行。

+ **从 WAITING 转入 READY。** I/O 完成后，内核发起一次上调，通知调度器那个被挂起的线程可以恢复了。

+ **从 RUNNING 转入空闲。** 当一次用户级激活发现就绪队列为空（即它已无工作可做）时，它可以发起一次进入内核的系统调用，把这颗虚拟处理器交还给内核，供其他进程使用。

这样一来，大多数线程管理函数——`thread_create`、`thread_yield`、`thread_exit` 和 `thread_join`，以及第 5 章描述的同步函数——都在进程内部以过程调用的方式实现。与此同时，用户级线程系统始终确切知道自己被分配了多少颗虚拟处理器，并完全掌控这些处理器上运行什么。

## 4.9　其他抽象

虽然线程是表达和管理并发的常用方式，但它并不是唯一的方式。本节描述两种流行的替代方案，每种都面向不同的应用领域：

- **异步 I/O 与事件驱动编程。** 异步 I/O 与事件机制让单线程程序能够把 I/O 与计算、以及 I/O 与 I/O 重叠起来，从而应对高延迟的 I/O 设备。

- **数据并行编程。** 在数据并行编程中，所有处理器对数据集的不同部分并行地执行相同的指令。

无论哪种情况，目标都是相似的：用确定性的顺序模型取代多线程的复杂性，使程序员更容易理解和调试程序。

### 4.9.1　异步 I/O 与事件驱动编程

*异步 I/O*（asynchronous I/O）是一种让单线程进程能够同时发出多个并发 I/O 请求的机制。进程通过系统调用发出 I/O 请求，但该调用立即返回，不等待结果。稍后，操作系统以下列方式之一把结果提供给进程：(1) 调用信号处理程序；(2) 把结果放入进程内存中的一个队列；或 (3) 把结果保存在内核内存中，直到进程再次发起系统调用将其取回。

异步 I/O 的一个典型用法，是把同一进程内的磁盘读取与其他计算重叠起来。从磁盘读取可能需要数十毫秒。在 Linux 中，进程不必发起一个会一直阻塞到所请求的数据从磁盘读出为止的 `read` 系统调用，而可以发起 `aio_read`（异步 I/O 读）系统调用；该调用告诉操作系统启动磁盘读取，然后立即返回。稍后，进程可以调用 `aio_error` 判断磁盘读取是否已经完成，并调用 `aio_return` 取回读取的结果，如图 4.16 所示。

<img src="/figures/vol2/image00396.png" alt="图 4.16" loading="lazy">
<figcaption><span class="fig-label">图 4.16</span>Linux 上的异步文件读取。应用程序调用 <code>aio_read</code> 启动读取；磁盘读取初始化之后，该系统调用立即返回。随后应用程序可以在磁盘完成所请求操作的同时做其他处理。操作完成时，磁盘中断处理器，从而使内核的磁盘中断处理程序运行。应用程序在任意时刻都可以向内核询问磁盘读取的结果是否已经可用，然后用 <code>aio_return</code> 取回结果。</figcaption>

有一种常见的设计模式，让单个线程通过等待不同的 I/O 事件，把多个受 I/O 限制的任务交织起来。考虑一个有 10 个活跃客户端的 Web 服务器。与其为每个客户端创建一个线程、让每个线程在各自的网络连接上做阻塞式读取，另一种办法是让服务器只用一个线程，依次处理来自*任意*客户端的下一个到达的报文。

为此，服务器调用 `select`，它会阻塞到 10 条网络连接中*任意一条*有数据可读为止。`select` 返回时，会给出一个有数据可读的连接列表。于是该线程就可以从这些连接读取数据，并且知道读取一定会立即返回。处理完数据后，线程再次调用 `select`，等待下一批数据到达。图 4.17 说明了这一设计模式。

异步 I/O 让许多并发的操作系统请求能够各自推进。这种做法催生了一种*事件驱动编程*（event-driven programming）模式：一个线程在一个循环中反复执行，每次迭代取出并处理下一个 I/O 事件。为了处理每个事件，线程通常为每个任务维护一个*续延*（continuation），即一个记录该任务当前状态与下一步动作的数据结构。

举例来说，处理一个 Web 请求可能涉及一系列 I/O 步骤：(a) 建立网络连接，(b) 从该网络连接读取请求，(c) 从磁盘读取被请求的数据，(d) 把被请求的数据写入该网络连接。如果单个线程同时处理来自多个不同客户端的请求，它就必须记录每个客户端在这条序列中走到了哪一步。

进一步说，网络可能把一个客户端的请求分成若干报文，因此服务器需要多次调用 `read` 才能拼出完整的报文。服务器可能同时在为多个客户端做这种请求拼装，因此它需要为每个客户端维护若干变量（例如请求缓冲区、期望的字节数、目前已收到的字节数）。当新报文到达时，线程用该网络连接的端口号判断是哪个客户端发来的请求，并根据这个端口号（客户端标识）取出相应客户端的那些变量，然后就可以处理数据了。

#### 事件驱动编程与线程的比较

虽然表面上不同，但无论采用异步 I/O 加事件驱动编程，还是同步 I/O 加线程，重叠 I/O 在本质上是同一回事。两种情况下，程序都会阻塞到下一个任务可以推进为止，恢复该任务的状态，执行该任务的下一步，并保存任务的状态直至它能再走一步。区别在于：(1) 状态是保存在续延（continuation）还是 TCB 中；(2) 状态的保存与恢复是由应用显式完成，还是由线程系统自动完成。

考虑一个简单的服务器：它把来自若干客户端的到达数据收集到一组按客户端划分的缓冲区中。事件驱动版本与“每客户端一线程”版本的伪代码十分相似：

```text
 // Event-driven
 Hashtable<Buffer*> *hash;

 while(1) {
     connection = use select() to find a
                  readable connection ID
     buffer = hash.remove(connection);
     got = read(connection, tmpBuf,
                            TMP_SIZE);
     buffer->append(tmpBuf, got);
     buffer = hash.put(connection,
                       buffer);
 }
```

```text
 // Thread-per-client
 Buffer *b;

 while(1) {
     got = read(connection, tmpBuf,
                          TMP_SIZE);
     buffer->append(tmpBuf, got);
 }
```

这两个程序运行时，系统所做的工作几乎相同，如图 4.18 所示。在事件驱动的版本中，代码用 `select` 判断接下来应当取哪一条连接上的报文；在线程版本中，当某个线程的数据到达时，内核会透明地调度该线程。

两种情况下需要维护的状态也相似。在事件驱动的版本中，应用程序维护一张哈希表，表中保存每个客户端的缓冲区状态；每当有报文到达某个客户端时，服务器都必须查一次表，找出对应的缓冲区。在“每客户端一线程”的版本中，每个线程只有一个缓冲区，而由操作系统记录不同线程的状态。

为了比较这两种做法，不妨再回顾一下 4.1 节中线程的几种使用场景：

- **性能：应对高延迟的 I/O 设备。** 两种做法——事件驱动和线程——都能把 I/O 与计算重叠起来。哪一种性能更好？过去普遍的看法是，事件驱动方式明显更快，理由有两点。第一，这种方式的空间开销和上下文切换开销可能更低：线程系统必须使用通用代码，为每个线程的状态分配一个栈，并在每次上下文切换时保存和恢复所有寄存器；而事件驱动方式允许程序员只分配、只保存/恢复每个任务真正需要的那部分状态。第二，过去有些操作系统对线程系统的实现效率低或不可扩展，因此每个进程不能创建太多线程。今天，这一比较就没有那么明确了。许多系统的内存很大，为每个任务分配一个线程栈的代价已不那么要紧。例如，在内存为 1 GB 的机器上创建 1000 个线程、每个线程栈 8 KB，占用不到机器内存的 1%。此外，如今大多数操作系统都有高效且可扩展的线程库。例如，Linux 2.4 内核在进程拥有大量线程时性能很差，Linux 2.6 则改造了线程系统，提高了可扩展性与绝对性能。零散的经验证据显示，两种做法之间的性能差距已大大缩小。对某些应用而言，高度优化的线程管理代码加上同步 I/O 路径，其表现可以超过优化不足的应用程序代码加上异步 I/O 路径。在多数情况下，性能差异小到使其他因素（例如代码的简洁性和易维护性）比原始性能更为重要。如果性能对某个应用至关重要，那么一如既往，在做决定之前，仔细的基准测试是无可替代的。

- **性能：利用多个处理器。** 事件驱动方式本身并不能帮助程序利用多个处理器。在实践中，事件驱动方式与线程方式常常结合使用：一个使用 $n$ 个处理器的程序可以有 $n$ 个线程，每个线程都用事件驱动模式，在每个处理器上把多个受 I/O 限制的任务多路复用起来。

- **响应性：把工作移到后台执行。** 当任务通常都比较短暂时，事件驱动编程可能很有效；而当任务兼有前台和后台成分时，线程往往更方便。事件驱动模型也能适用于这种情形，代价是编码复杂度有所增加，例如把长任务切成较小的片段，并在有更高优先级的工作待处理时显式地保存这些片段的状态。

- **程序结构：表达逻辑上并发的任务。** 只要存在两种可行的编程风格，就必然各自都有坚定的拥护者。这里也不例外：一些事件驱动编程的拥护者认为，线程共享数据时所需的同步使线程比事件更复杂；线程的拥护者则认为，比起必须显式地把计算的状态保存在续延中，线程提供了一种更自然的方式来表达程序的控制流。

在我们看来，仍然存在两种风格都合适的场合，我们自己写程序时也两种风格都用。话虽如此，对大多数 I/O 密集型的程序，线程更可取：它们通常更自然、效率也还算不错，并且在多处理器上运行时更简单。

### 4.9.2　数据并行编程

另一个重要的应用领域是并行计算。关于用线程还是用其它模型来表达和管理并行性更为有效，一直存在争论。

一种流行的模型是*数据并行编程*（data parallel programming），也称为 SIMD（单指令多数据）编程或*整体同步并行编程*（bulk synchronous parallel programming）。在这种模型中，程序员描述一个作用于整个数据集的计算，让它在同一时刻并行地施加于相互独立的数据元素之上。对每个数据项的处理都必须全部完成，才能进入下一步；一个处理器只能在其后的某个步骤中使用另一个处理器产生的结果。因此，程序的行为是确定性的。工作不由程序员划分给各个线程，而由运行时系统决定如何把这种并行工作映射到硬件的各个处理器上。

例如，取前面图 4.7 中并行地把一个缓冲区清零的例子，把一个含 $N$ 个元素的数组清零的数据并行程序，可以简单到只需：

```text
    forall i in 0:N-1
        array[i] = 0;
```

运行时系统会把数组划分给各个处理器，并行地执行该计算。当然，运行时系统本身也可能是用线程实现的，但这对程序员是不可见的。

大规模数据分析任务常常采用数据并行编程。例如，Hadoop 是一个开源系统，能够处理和分析分布在数百甚至数千台服务器上的数 TB 数据。它对每个数据元素施加一个任意的计算，例如根据引用某个网页的页面此前的流行度估计，更新该网页的流行度。Hadoop 对所有网页反复并行地施加该计算，直到每个网页的流行度都收敛为止。搜索引擎随后就可以利用这些结果，决定在响应搜索查询时应当返回哪些页面。

另一个例子是 SQL（结构化查询语言）。SQL 是访问数据库的标准语言，程序员在其中指定要执行的数据库查询，而由数据库把该查询映射为低层的线程操作和磁盘操作。

多媒体流（例如音频、视频和图形）往往包含大量数据，并且要对这些数据反复执行相似的操作，因此数据并行编程常被用于媒体处理；支持这类并行处理的专用硬件也很常见。由于针对高度规整的数据并行程序做了优化，GPU（图形处理器）能够提供高得多的数据处理速率。例如，在 2013 年，一块中端的 Radeon 7850 GPU 能达到 1.69 TFLOPS（每秒 1.69 万亿次双精度浮点运算）；作为对比，一颗 Intel i7 3960 CPU（一款高端的六核通用处理器）只能达到 0.19 双精度 TFLOPS。

目前有相当多的努力投入到通用 GPU（GPGPU）的开发和使用上——这类 GPU 能更好地支持范围更广的程序。哪些类别的程序适合用 GPGPU、哪些仍然需要更传统的 CPU 体系结构，目前还不清楚；但对那些能够移植到约束更强的 GPGPU 编程模型上的程序来说，性能提升可能是巨大的。

## 4.10　小结与未来方向

并发无处不在——不仅大多数智能手机、服务器、台式机、笔记本电脑和平板电脑都有多个核，而且用户已经习惯于界面随时保持响应，I/O 延迟相对于计算机的指令周期时间已变得极其巨大，服务器也必须能够处理大量同时到达的请求。

尽管线程并不是解决这些问题的唯一方案，但它是一种通用技术，可以应用于范围广泛的并发问题。在我们看来，多线程编程是每一位专业程序员都必须掌握的技能。

本章讨论了以下内容：

- **线程抽象。** 线程是一组并发活动，其中每一个都以不可预测的速度顺序执行。

- **一个简单的线程 API。** 线程库无论是供操作系统内核使用，还是供应用程序代码使用，都提供执行异步过程调用的能力。

- **线程的实现。** 任何抢占式多线程实现的核心，都是保存一个线程的状态、恢复另一个线程的状态的能力。线程系统记录所有当前未运行的线程所保存的状态，并按需在线程的 READY 与 RUNNING 状态之间切换。多线程的实现既可以放在内核中，也可以放在用户级，取决于系统的目标。在我们看来，未来大多数系统都会同时拥有一个用于管理操作系统内部并发的内核级线程系统，以及一个用于在应用层表达并行性的轻量级线程系统。

- **其他抽象。** 在两个重要领域中，存在着切实可行的线程替代方案：面向服务器的事件驱动编程，以及面向多处理器的数据并行编程。

技术趋势表明，并发编程的重要性只会与日俱增。几十年来，计算机体系结构设计者一直能够使单个处理器核运行得越来越快；如今我们已到达这样一个阶段：单个核的性能趋于平缓，进一步的加速必须来自并行处理。

用于表达和管理并行性的最佳编程模型仍是一个活跃的研究领域，但看来线程在未来几十年里很可能仍是一个重要的选项。

### 4.10.1　历史注记

20 世纪 60 年代商用操作系统极端的工程复杂性和层出不穷的缺陷，促使研究者去寻找替代方案。这段经历的一个直接产物就是现代软件工程：通过对特性清单的严格管控、模块测试、断言等手段，系统地管理复杂的实现任务。

另一个后果是把线程用于管理并发。计算机科学史上最有影响的论文之一，是 Dijkstra 对其 THE 系统的描述 [48]。Dijkstra 主张把操作系统构造为一系列分层的抽象，每一层都由相互通信的线程实现。不到十年，研究界就接受了这一主张。Xerox PARC 在 20 世纪 70 年代末建造 Alto 时，其操作系统就是从零开始用线程构造的。Alto 展示了我们今天在个人计算机上习以为常的大部分技术：位图显示、菜单、窗口、鼠标、以太网和电子邮件。本书关于线程编程的许多论述，都基于该项目的经验 [98]。

然而，线程在商业上的广泛采用花了长得多的时间。到 20 世纪 90 年代初，客户端-服务器计算的普及促成了若干重要的商用操作系统从零开始用线程编写，包括 Microsoft 的 Windows NT、SUN Microsystems 的 Solaris 以及 Linux。客户端操作系统随后跟上；到 20 世纪 90 年代末，随着 Apple 推出 OS X，所有主流商用操作系统都建立在多线程之上。大约在同一时期，线程库的接口开始标准化，起点是 1995 年的 POSIX。同样，Java 等现代编程语言在设计时就包含了用于创建和同步线程的构造。

并行处理日益重要，促成了非常轻量的用户级线程实现的出现，因为如果不能提升性能，把应用并行化就没有多少意义。到 90 年代初，人们提出了调度器激活，把用户级线程与内核线程结合起来 [2]。

即便如此，“线程是否比各种替代方案更好的编程模型”这一话题仍然活跃 [159]。若干知名的操作系统研究者主张，普通程序员几乎永远不应当使用线程，原因是：(a) 编写正确的多线程程序实在太难；(b) 线程常被用于的大多数事情，都可以用其他更安全的方式完成 [129, 160]。这些论点值得理解——即便你并不同意，它们也指出了使用线程时务必避开的陷阱。
