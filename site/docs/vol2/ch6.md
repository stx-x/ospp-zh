# 第 6 章　多对象同步

<div class="chap-en">Multi-Object Synchronization</div>

<blockquote class="epigraph">当两列火车在交叉口相向而行时，双方都应完全停住；在对方驶离之前，任何一方都不得重新启动。——<em>堪萨斯州法律，20 世纪初</em></blockquote>

上一章讲述了编写并发程序的一个关键构件：如何设计一个可在多个线程之间共享的对象。本章需要再向前走一步：当程序变得更复杂，含有多个共享对象和多把锁时，会发生什么？要回答这个问题，我们必须对共享对象之间的相互作用进行推理。

在这一语境下，会出现若干需要考虑的问题：

- **多处理器性能。** 由于提升单颗 CPU 性能越来越困难，现代计算机的处理器数量不断增加。共享对象的设计会对多处理器性能产生很大影响。例如，一把保护被频繁访问的共享对象的锁可能成为瓶颈，因为同一时刻只有一个线程能持有该锁。

- **正确性。** 出于性能上的考虑，设计者常常重新设计自己的数据结构以提高并发度。把单个共享对象拆成一组各自带有自己的锁的相关对象，可以改善性能。然而这同时也带来了正确性问题。对于含有多个共享对象的程序，我们面临的问题与推理原子加载和原子存储时面临的问题类似：即使对某个共享对象的每一次单独操作都是原子的，我们仍然必须推理跨对象的多条操作序列之间的相互作用。

- **死锁。** 为了便于推理跨多个对象的操作行为，一种做法是同时持有多把锁。这种做法带来了死锁的可能，即线程在一个环中永久地互相等待。

没有任何一套现成的配方总能解决这些挑战。具体来说，目前的技术有两个基本局限。第一，它们都涉及工程上的权衡。有些方案通用，但复杂或昂贵；有些方案简单，但速度慢；还有些方案既简单又廉价，但并不通用。第二，许多方案本质上是**非模块化的**：为了理解或限制不同模块之间如何交互，必须对系统的全局结构和模块的内部实现细节进行推理。

**本章导读：**

- **多处理器锁性能。** 我们能否预测一把锁何时会在多处理器上成为瓶颈？（6.1 节）

- **锁的设计模式。** 如果锁成了瓶颈，能否重构程序来缓解问题？（6.2 节）

- **锁争用。** 如果重构之后锁仍然是瓶颈，又该怎么办？（6.3 节）

- **多对象原子性。** 我们如何让跨多个对象的一串操作对其他线程表现为原子的？（6.4 节）

- **死锁。** 多线程程序中的死锁由什么引起？有哪些办法可以防止死锁或打破死锁？（6.5 节）

- **非阻塞同步。** 在复杂的多对象程序中，有没有办法彻底消除锁？（6.6 节）

## 6.1　多处理器锁性能

对于带有数十个处理器的现代多核体系结构，客户端-服务器应用往往具有充足的并行度。每个独立的客户端请求都可以由一个运行在不同处理器上的不同线程来处理，这称为*请求并行度*（request parallelism）。同样，服务器操作系统通常也具有充足的并行度——含有大量线程的应用可以并发地向内核发起大量系统调用。

然而，即便请求并行度充足，性能往往仍然令人失望。一旦为了让服务器应用能够并发处理请求而给它加上锁和条件变量，在 50 路多处理器上的吞吐量可能只比在单处理器上略快一点。这通常有三个原因：

+ **加锁。** 锁意味着互斥——同一时刻只有一个线程能持有该锁。因此，对共享对象的访问会限制并行度。

+ **共享数据的通信。** 依据处理器所需的数据是否已经在其缓存中，现代处理器的性能可能相差十倍（甚至更多）。现代处理器设计有大容量缓存，使处理器所需的几乎全部数据都已经存放在缓存中。在单处理器上，处理器很少需要等待。然而在多处理器上，情况就不同了。由锁保护的共享数据往往需要从一个缓存复制到另一个缓存。共享数据通常位于最后持有该锁的那个处理器的缓存中，而它又恰恰是下一个将要获取该锁的处理器所需要的。与单处理器相比，搬移数据会显著拖慢临界区的性能。

+ **伪共享。** 还有一个复杂因素：硬件以固定的粒度跟踪共享数据，通常以 32 或 64 字节的缓存项为单位。这降低了硬件管理的开销，但如果多个共享行为不同的数据结构恰好落在同一个缓存项中，就会引起性能问题。这称为*伪共享*（false sharing）。

幸运的是，通过精心设计共享对象，可以减轻这些影响。不过我们要提醒：在通过细致的测量证明必须采用更复杂的设计才能达到性能目标之前，应让共享对象的设计保持简单。

::: tip Linux 内核锁机制的演进
最早的 Linux 版本只能运行在单处理器机器上。为了让 Linux 能在多处理器上运行，2.0 版引入了大内核锁（Big Kernel Lock，BKL）——一把保护内核所有共享数据结构的单一锁。BKL 使内核得以在多处理器机器上工作，但可扩展性和性能都受到限制。于是，随着时间的推移，不同的子系统和不同的数据结构各自有了自己的锁，从而无需持有 BKL 即可访问。

到 2.6 版时，Linux 已经过高度优化，可以在多处理器机器上良好运行。它现在拥有数千把不同的锁，研究人员也已在 48 处理器的机器上展示了多种基准测试的可扩展性。不过，BKL 仍在少数——大多是不太关键的性能部分——Linux 内核中继续使用，例如 reboot 系统调用、一些较老的文件系统以及一些设备驱动程序。
:::

为说明这些概念，考虑一个带有近期取回页面之内存缓存的 Web 服务器。直接从内存返回一个页面，通常比从头重新生成它更快。例如，选举之夜 Google 可能收到大量关于选举结果的搜索，在这种情况下，把通用搜索的全部工作都做一遍就几乎没有必要了。

为实现网页缓存，服务器可以有一个共享数据结构，例如以搜索词为键的哈希表，在页面存在时指向该缓存页面。哈希表在处理客户端请求的线程之间共享，因此需要一把锁。每当某个线程生成了一个缓存中不存在的新页面时，就更新该哈希表。代码还可能标记最近被取回的页面，以便让它们优先留在内存中，而让那些不那么频繁出现的请求退居其次。

这一设计中的一个重要问题是：哈希表上的那把单锁是否会显著限制服务器的并行度？我们怎样才能判断共享对象上的锁是否会成为问题？

一种简便的做法是：先假设程序其余部分都可以完美并行化——换句话说，唯一的限制因素是同一时刻只能有一个线程持有那把共享锁——由此推导出并行程序性能的一个上界。

::: info 例
假设平均而言，Web 服务器把每个请求 5% 的时间用于访问和操纵其近期使用网页的哈希表。如果该哈希表由一把锁保护，那么最大可能的吞吐量增益是多少？
:::

::: warning 答
花在临界区里的时间本质上是串行的。如果我们假设服务器的其余所有部分都可以完美并行化，那么无论使用多少个处理器，最大加速比都是**20 倍**。□
:::

正如前面提到的，还有一个复杂因素：在多处理器上取回共享数据可能耗时多得多，因为数据很可能不在处理器缓存中。如果程序中持有锁的那一部分在多处理器上比在单处理器上更慢，那么吞吐量的潜在增益就会受到严重限制。

我们可以用一个简单的实验来研究缓存行为对多处理器性能的影响。该实验只用于说明问题；它并不意图反映程序的正常行为，而是作为一种隔离硬件对使用共享对象的代码性能之影响的方法。

假设我们建立一个含一千个共享对象的数组，其中每个对象是一个由自旋锁保护的简单整数计数器。（我们使用自旋锁而不是锁，是为了避免把上下文切换的时间计入测量。）程序遍历该数组。对每个元素，它获取锁、递增计数器、释放锁。我们把这一循环重复一千次，以提高测量精度。

考虑以下几种情形：

- **一个线程，一个数组。** 当一个线程遍历数组、依次递增每个计数器时，该测试给出获取并释放一组无争用锁所需的时间。

- **两个线程，两个数组。** 当两个线程遍历彼此不相交的数组时，得到的是并行完成工作时的性能下降程度。在大多数体系结构上，并行执行几乎没有或完全没有性能下降。

- **两个线程，一个数组。** 当两个线程遍历*同一个*数组时，每把锁先由一个在某个处理器上运行的线程获取，随后不久又由另一个在不同处理器上运行的线程获取。因此，这一情形体现了在处理器之间搬移共享对象数据所带来的额外开销。

- **两个线程，一个数组中的交替元素。** 为度量伪共享的影响，可以让一个线程遍历数组并获取奇数项，让另一个线程遍历数组并获取偶数项。如果伪共享没有任何影响，这一情形就应当与“两个数组”的情形完全相同——两个线程从不使用同一份数据。

## 6.2　锁的设计模式

接下来我们讨论一组方法，它们可以减轻加锁对多处理器性能的影响。通常，最佳做法是从简单开始：每个共享对象只用一把锁。如果对象的接口设计得当，那么可以先把系统建起来，等性能测量找出瓶颈之后，再重构它的实现来提高并发度和性能。可以遵循的格言是：“从一个能工作的系统变成一个能工作且快速的系统，比从一个快速的系统变成一个快速且能工作的系统更容易。”

必要时，可以用下面四种设计模式来提高并发度：

- **细粒度加锁。** 把对象的状态划分成若干不同的子集，每个子集由不同的锁保护。

- **每处理器数据结构。** 划分对象的状态，使全部或大部分访问都由运行在同一处理器上的线程完成。

- **所有权设计模式。** 把共享对象从共享容器中取出，使只有单个线程能够读或修改该对象。

- **分阶段体系结构。** 把系统划分为多个阶段，使只有各阶段内部的线程才能访问该阶段的共享数据。

### 6.2.1　细粒度加锁

减少共享锁争用的一种简单而广泛使用的做法，是把共享对象的状态划分成若干不同的子集，每个子集由自己的锁保护。这称为*细粒度加锁*（fine-grained locking）。

上文讨论的 Web 服务器缓存就是一例。缓存可以用一张共享哈希表来存放和查找最近使用过的网页；由于哈希表是共享的，它需要一把锁来提供互斥。在每个哈希表方法的开头和结尾都要获取并释放这把锁，这些方法是：put(key, value)、value = get(key) 以及 value = remove(key)。

如果单把锁限制了性能，另一种选择是每个哈希桶配一把锁。各方法在访问任何散列到桶 b 的记录之前，先获取桶 b 的锁。只要桶的数量足够多，且没有哪个桶承担了请求中很大的比例，不同的线程就可以并行地使用和更新这张哈希表。

然而，天下没有免费的午餐。把对象的状态划分成由不同锁保护的不同部分，可能显著增加对象的复杂度。假设我们要实现一张哈希表，其哈希桶的数量随所存对象数量的增加而增长。如果只有一把锁，这很容易做到。可是，如果采用细粒度加锁呢？设计就变得复杂了，因为有些方法（如 put 和 get）只作用于一个桶，而另一些方法（如 resize）要跨多个桶操作。

可以有以下几种解决方案：

+ **引入读写锁。** 假设我们为哈希表的整体结构（例如桶的数量和桶数组）设一把读写锁，并为每个桶设一把互斥锁。一次只作用于一个桶的方法，如 put 和 get，以读模式获取表的读写锁，同时获取相关桶的互斥锁。改变表结构的方法，如 resize，必须以写模式获取读写锁；读写锁保证在表被调整大小期间，其他任何线程都不能使用这张哈希表。

+ **获取每一把锁。** 改变哈希表结构的方法，如 resize，必须先遍历每一个桶、获取它的锁，然后才能继续。一旦 resize 持有了每个桶的锁，就可以保证没有其他线程正在并发地访问或修改这张哈希表。

+ **划分哈希键空间。** 另一种方案是把哈希键空间划分为 r 个区域，为每个区域设一把互斥锁，并允许每个区域在负载变重时独立调整大小。于是 get、put 和 resizeRegion 各自获取相关区域的互斥锁。

哪种方案最好？这一点并不显然。第一种方案简单，看起来允许很高的并发度，但即便以读模式获取读写锁，开销也可能很大。例如，我们在第 5 章给出过一个读写锁的实现，其中获取只读锁需要在入口和出口各获取一次互斥锁。对底层互斥锁的访问可能成为瓶颈。

第二种方案使 resize 的代价高昂，但如果 resize 是很少发生的操作，这也许可以接受。第三种方案在 get/put 的并发度与 resize 的代价之间取得平衡，但它更复杂，而且可能需要调整分组数量才能获得良好的性能。

此外，随着实现变得更复杂，这些权衡也可能发生变化。例如，为了在适当的时机触发 resize，我们可能还需要维护一个额外的 nObjects 计数，记录哈希表当前存放的对象数，因此无论采用哪种加锁方案，都必须扩展它来覆盖这项信息。

::: info 例
如何用细粒度加锁来减少 malloc/free 或 new/delete 中保护共享内存堆的那把锁的争用？
:::

::: warning 答
**一种做法是把堆划分成若干独立的内存区域，每块区域配自己的锁。** 例如，单处理器上一种快速的堆实现使用 n 个桶，其中第 i 个桶存放大小为 $2^{i}$ 的块，并服务大小在 $2^(i-1) + 1$ 到 $2^{i}$ 之间的请求。如果第 i 个桶中没有空闲块，就从下一个更大的桶 i + 1 中取一块，一分为二。采用细粒度加锁时，可以给每个桶配一把自己的锁。□
:::

### 6.2.2　每处理器数据结构

与细粒度加锁相关的一种技术，是按机器上的处理器数量来划分共享数据结构。例如，与其用一张存放缓存页的共享哈希表，另一种设计是使用 N 张独立的哈希表，其中 N 是处理器的数量。每个线程根据自己当前运行所在的处理器来选用哈希表。每张哈希表仍然需要自己的锁，以防某个线程在操作途中被上下文切换，但在常见情形下，只有运行在同一处理器上的线程才会争用同一把锁。

这种做法常常与每处理器的就绪队列结合使用，从而保证每个线程每次被上下文切换后都优先运行在同一个处理器上，进一步提高执行速度。

这种方法的一个优点是硬件缓存行为更好；正如上一节所见，必须在处理器之间传递的共享数据会拖慢临界区的执行。当然，缺点在于哈希表现在被划分开了，于是某个网页可能缓存在一个处理器的哈希表里，却要在另一个处理器上使用。这究竟是不是一项性能收益，取决于减少共享数据通信所带来的好处与缓存有效性下降之间的相对影响。

::: info 例
如何用每处理器数据结构来减少内存堆的争用？在什么条件下这种做法效果良好？
:::

::: warning 答
**可以把堆划分成 N 块独立的内存区域，每个处理器一块。** 对 malloc/new 的调用使用本地的堆；free/delete 则把数据归还到它当初被分配的那个堆。**只要满足以下两个条件，这种做法就能表现良好：(i) 堆之间的再平衡很少发生；(ii) 大多数被分配的数据都由获取它的线程释放。** □
:::

### 6.2.3　所有权设计模式

在大型多线程程序中，一种常见的同步技术是*所有权设计模式*（ownership design pattern）。在这种模式中，线程把一个对象从容器中取出，此后就可以在不持有锁的情况下访问该对象：程序结构保证任一时刻至多只有一个线程拥有该对象。

举个例子，一个网页可以包含多个对象，包括 HTML 框架、样式表和图像。考虑一个多线程 Web 浏览器，它把处理划分为三个阶段：通过网络接收对象、解析对象、渲染对象（见图 6.2）。第一阶段为每个网络连接设一个线程；其余阶段有若干个工作线程，每个线程一次处理一个对象。

阶段之间的工作队列负责协调对象的所有权。队列中的对象没有被任何线程访问。当 *解析* 阶段的一个工作线程从该阶段的工作队列中取出一个对象时，它就拥有了该对象，并对它拥有独占访问权。该线程解析完对象后，把它放入第二个队列，并停止访问它。随后，*渲染* 阶段的一个工作线程把它从第二个队列中取出，获得对它的独占访问权，以便把它渲染到屏幕上。

::: info 例
如何用所有权设计模式来减少内存堆的争用？
:::

::: warning 答
所有权可以看作每处理器数据结构的推广；与其每个处理器一个堆，**不如每个线程一个堆。** 只要分配内存的线程同时也是释放内存的线程，该线程就可以在没有锁的情况下安全地使用自己的堆，只在本地堆空间用完时才回到全局堆。□
:::

::: tip 可交换的接口设计
类和接口的设计常常会以某些方式约束实现，使其不得不加锁。UNIX API 就是一例。与大多数操作系统一样，UNIX 的 open 系统调用返回一个文件句柄，供后续对该文件的操作使用；同一个系统调用也用于初始化网络套接字。open 调用使操作系统能够分配内部数据结构，以跟踪文件或网络套接字的当前状态，更一般地说，跟踪哪些文件和套接字正在被使用。

UNIX 还规定，每一次相继的 open 调用都返回下一个整数文件句柄；正如第 3 章所见，UNIX shell 在把 stdin 和 stdout 重定向到文件或管道时就使用了这一特性。

UNIX API 的这一设计带来的一个后果是，open 的实现需要一把锁。对早期的 UNIX 系统来说，这不成问题，但现代多线程 Web 服务器要打开数量极其庞大的网络套接字和文件。由于 API 的语义，open 的实现无法使用细粒度加锁或每处理器数据结构。

在可能的情况下，更好的选择是把 API 设计成*可交换的*（commutative）：两次调用的结果相同，与哪一次调用先发生无关。例如，如果实现可以返回任意一个唯一的整数作为文件句柄，而不是返回紧接着的下一个整数，那么它就可以从一个每处理器的打开文件句柄桶中分配。这样，实现只有在分配 stdin 和 stdout 之类的特定句柄这种特殊情形下才需要加锁。
:::

### 6.2.4　分阶段体系结构

<figcaption><span class="fig-label">图 6.3</span>一个简单 Web 服务器的分阶段体系结构。</figcaption>

如图 6.3 所示，*分阶段体系结构*（staged architecture）模式把系统划分为多个子系统，称为阶段。每个阶段包含该阶段私有的状态，以及一组（一个或多个）作用于该状态的工作线程。不同阶段之间通过向共享的生产者-消费者队列发送消息来相互通信。每个工作线程反复地从本阶段的入站队列中取出下一条消息并加以处理，处理过程中可能为其他阶段的队列产生一条或多条消息。

图 6.3 给出了一个简单 Web 服务器的分阶段体系结构：第一个 *连接*（connect）阶段用一个线程建立网络连接，并把每个连接传递给第二个 *读取并解析* 阶段。

*读取并解析* 阶段有若干个线程，每个线程反复地从入站队列中取出一个连接、从该连接读取请求、解析请求以确定请求的是哪个网页，并检查该网页是否已经被缓存。

假设该网页尚未被缓存。如果请求的是静态网页（例如一个 HTML 文件），*读取并解析* 阶段就把请求和连接传递给 *读取静态页* 阶段，由该阶段的一个线程从磁盘读取指定的页面。否则，*读取并解析* 阶段就把请求和连接传递给 *生成动态页* 阶段，由该阶段的一个线程运行一个程序，针对该请求动态生成页面。

一旦页面被取回或生成，页面和连接就被传递给 *发送页面* 阶段，由该阶段的一个线程通过该连接把页面发送出去。

分阶段体系结构的关键性质是：每个阶段的状态对该阶段是私有的。这改善了模块化，使人们更容易分别对每个阶段、以及对阶段之间的交互进行推理。

作为模块化好处的一个例子，考虑一个由不同团队、甚至不同公司分别生产不同阶段的系统。每个阶段几乎可以独立地设计和测试，把各个阶段组合到一起时，系统很可能按预期工作。例如，一个网站使用一家公司的 Web 服务器和另一家公司的数据库、并让两者通过消息通信，这是常见的做法。

另一个好处是缓存局部性更好。只作用于系统状态一部分的线程，其缓存行为可能优于要访问所有阶段状态的线程。另一方面，对某些工作负载而言，与在同一个处理器上完成一个请求的全部处理相比，把请求从一个阶段传到另一个阶段反而可能损害缓存行为。

还要注意，为了获得良好的性能，每个阶段中的处理量必须足够大，才能摊薄收发消息的开销。

每个阶段恰好只有一个线程这一特殊情形，就是第 4 章所述的*事件驱动编程*（event-driven programming）。在事件驱动编程中，一个阶段内部没有并发，因此不需要加锁。每条消息相对于该阶段的状态都是原子地处理的。

分阶段体系结构的一个难题是如何应对过载。系统的吞吐量受最慢阶段的吞吐量限制。如果系统过载，最慢的阶段就会落后，它的工作队列就会增长。取决于系统的实现方式，可能发生两种糟糕的情况。第一，队列可能无限增长，消耗越来越多的内存，直到系统的内存堆被耗尽。第二，如果队列被限制为有限大小，那么一旦达到该大小，较早的阶段就必须要么丢弃为过载阶段准备的工作，要么阻塞直到队列有空位。注意，如果它们阻塞，那么背压就会把较早阶段的吞吐量限制到瓶颈阶段的吞吐量，它们的队列又可能随之开始增长。

一种解决方案是动态改变每个阶段的线程数。如果某个阶段的入站队列在增长，程序就可以把处理资源向它倾斜：减少负载较轻阶段的线程数，为落后的阶段增加更多线程。

## 6.3　锁争用

有时，即便已经用上了上一节介绍的各种方法，在多处理器上，加锁仍可能成为取得良好性能的瓶颈。例如，对哈希表采用细粒度加锁时，如果某个桶里存放着一个特别热门的条目——比如 Justin Bieber 的缓存页面——那么这个桶上的锁就可能成为争用的来源。

本节讨论锁抽象的另外两种实现，它们对已经成为瓶颈的锁表现更好：

- **MCS 锁。** MCS 是一种自旋锁实现，针对存在大量等待线程的情形做了优化。

- **RCU 锁。** RCU 是一种读写锁实现，针对读操作远多于写操作的情形做了优化。RCU 降低了读者的开销，代价是提高了写者的开销。更重要的是，RCU 的语义与普通读写锁有所不同，这就要求锁的使用者自己理解它的危险之处。

这两种方法虽然都在现代操作系统内核中使用，但我们要提醒：它们都不是万能药。只有当性能剖析（profiling）表明某把锁确实是争用的来源、而且没有其他可选方案时，才应当使用它们。

### 6.3.1　MCS 锁

回顾一下，第 5 章介绍的锁实现是针对“锁通常处于 FREE 状态”这一常见情形调优的。那么，当锁通常处于 BUSY 状态时，有没有高效的锁实现呢？

遗憾的是，获取和释放锁的开销会随争用该锁的线程数急剧**增加**。对一把被争用的锁而言，这又会进一步增加等待该锁的线程数。再回顾一下前面用过的那个例子：一把自旋锁保护一个共享计数器。

```c
    void Counter::Increment() {
        while (test_and_set(&lock)) // while BUSY
            ; // spin
        value++;
        lock = FREE;
        memory_barrier();
    }
```

即使有许多线程试图递增同一个计数器，同一时刻也只有一个线程能执行临界区，其余线程必须排队等候。正如前面观察到的，由于计数器的值必须从一个持锁者传递给下一个持锁者，同一个临界区在多处理器上执行所需的时间会明显长于在单处理器上。

<img src="/figures/vol2/image00405.png" alt="图 6.4" loading="lazy">
<figcaption><span class="fig-label">图 6.4</span>三种锁替代实现的额外开销随争用该锁的处理器数量的变化：（a）测试并设置，（b）测试并测试并设置，（c）MCS。测量在 64 核 AMD Opteron 6262 上进行。曲线不平滑是真实系统测量的典型特征。</figcaption>

然而，存在多个等待线程时，情况还要更糟。受自旋锁保护的临界区的执行时间，会随自旋处理器数量的增加而线性增长。图 6.4 展示了这一效应。问题在于，处理器在执行一条原子的读-改-写指令之前，硬件必须先取得对该内存位置的独占访问权；其他任何读-改-写指令都只能发生在它之前或之后。

因此，如果若干处理器同时执行自旋循环，它们都会试图取得对锁所在内存位置的独占访问权。清除锁的存储指令同样需要独占访问，而硬件无法知道应当让释放锁的操作优先于那些“查看锁是否空闲”的竞争请求。

人们可能会想：在试图用测试并设置获取锁之前，先检查一下锁是否空闲，应该会有所帮助。这种做法称为**测试并测试并设置**（test and test-and-set）：

```c
 void Counter::Increment() {
     while (lock == BUSY || test_and_set(&lock)) // while BUSY
         ; // spin
     value++;
     lock = FREE;
     memory_barrier();
 }
```

然而事实证明，这并没有用。锁被释放时，锁的新值 FREE 必须传递给其他正在等待的处理器。在现代系统上，每个处理器都要各自把该数据取入自己的缓存。最终会有一个处理器取到新值并获取到锁。如果临界区不太长，其他处理器此时仍然忙于取新值、试图获取锁，这反而妨碍释放锁的操作完成。

一种做法是根据线程已经等待的时间长短来调整轮询的频率。更具可扩展性的方案，是为每个等待线程分配一个独立的内存位置，让它在那个位置上自旋。释放锁时，只把**一个**线程对应的标志置位，告诉它就是下一个获得锁的线程。

这一思想最广为人知的实现称为 MCS 锁，名称取自其作者 Mellor-Crummey 与 Scott 的姓氏首字母。MCS 锁利用了大多数现代多处理器体系结构都支持的原子读-改-写指令——**比较并交换**（compare-and-swap）。比较并交换检查某个内存位置的值，若旧值未发生变化，就换入一个新值。

<div class="code-cap"><span class="code-label">图 6.5</span>MCS 队列锁的伪代码。每个等待线程都在自己的线程控制块（TCB，即 myTCB）中的独立内存位置上自旋。compare-and-swap 操作原子地把该 TCB 插入队列尾部。</div>

```c
 class MCSLock {
   private:
     Queue *tail = NULL;
 }

 MCSLock::release() {

     if (compare_and_swap(&tail,
                     myTCB, NULL)) {

         // If tail == myTCB, no one is
         // waiting. MCSLock is now free.

     } else {
         // Someone is waiting.
         while (myTCB->next == NULL)
             ; // spin until next is set

         // Tell next thread to proceed.
         myTCB->next->needToWait = FALSE;
     }
 }

 MCSLock::acquire() {
     Queue *oldTail = tail;

     myTCB->next = NULL;
     while (!compare_and_swap(&tail,
                   oldTail, &myTCB)) {

         // Try again if someone else
         // changed tail in the meantime.

         oldTail = tail;
     }

     // If oldTail == NULL, lock acquired.
     if (oldTail != NULL) {
         // Need to wait.
         myTCB->needToWait = TRUE;
         memory_barrier();
         oldTail->next = myTCB;
         while (myTCB->needToWait)
             ; //spin
     }
 }
```

<img src="/figures/vol2/image00406.png" alt="图 6.6" loading="lazy">
<figcaption><span class="fig-label">图 6.6</span>MCS 队列锁的行为。初始时（a），tail 为 NULL，表示锁处于 FREE 状态。为获取锁（b），线程 A 原子地把 tail 设为指向 A 的 TCB。随后线程 B 与 C 通过（原子地）把自己加入队尾来排队（c）和（d），然后各自在自己的 TCB 的 needToWait 标志上自旋。线程 A 清除 B 的 needToWait 标志，把锁交给 B（e）；B 清除 C 的 needToWait 标志，把锁交给 C（f）。若没有其他线程在等待——即 tail 仍指向 C 的 TCB——C 就把 tail 设回 NULL，释放锁（a）。</figcaption>
</figure>

用比较并交换可以构建一个等待线程队列，而不需要另外的自旋锁。等待线程原子地把自己加到队列的**尾部**，然后在自己的队列项中的一个标志上自旋。线程释放锁时，把下一个队列项中的标志置位，通知那个线程轮到它了。图 6.5 给出了实现，图 6.6 演示了算法实际运行的情形。

由于队列中的每个线程都在自己的队列项上自旋，锁可以沿队列高效地从一处传到另一处。当然，建立队列本身有开销，因此除非有大量等待线程，MCS 锁的效率不如普通自旋锁。

### 6.3.2　读-复制-更新（RCU）

**读-复制-更新**（RCU）为“频繁读取、偶尔更新”的数据结构提供高性能的同步。特别地，RCU 优化了读路径，即便有大量并发读者，同步开销也极低。不过，写操作可能被延迟很长时间——在某些实现中长达数十毫秒。

#### 为什么不使用读写锁？

标准的读写锁不适合某些以读为主的工作负载。回顾一下：这类锁允许任意数量的读者并发地处于活动状态，但一旦有写者在活动，其他任何写者或读者都不能活动。

问题出在存在大量并发读、而每个临界区又很短的时候。每次读取之前，读者必须以读模式获取读写锁，读完再释放。无论进入还是退出，读者都必须更新读写锁同步对象中的某些状态。即便只有读者，这个同步对象也可能成为瓶颈。这就限制了读者进入临界区的速率，因为它们只能一个一个地获取锁。对于长度不足几千个周期的临界区，对于有几十个线程同时读取同一个共享对象的程序，标准读写锁会限制性能。

虽然可以用 MCS 锁来实现这个读写锁同步对象，从而减轻锁争用的一些影响，但这改变不了读写锁控制结构固有的串行访问。

#### RCU 的方法

并发读如何访问一个同时可能被写入的数据结构，而又不必在每次读取时更新某个同步变量的状态？

为应对这一挑战，RCU 锁保留了读写锁的基本结构：读者（以及写者）在临界区前后分别调用 RCU 锁的获取与释放，以读模式（或写模式）进入和退出。RCU 锁对标准接口做了三处重要改动：

+ **受限的更新。** 使用 RCU 时，写线程必须以一次原子的内存写入，把它的修改**发布**到共享数据结构上。通常的做法是更新单个指针，下面我们用 RCU 更新一个共享链表来说明这一点。受限的更新乍看之下似乎会严重限制 RCU 所能支持的数据结构操作类型，其实不然。一种常见的模式是：写线程先复制出一份复杂数据结构（或其中一部分）的**副本**，修改副本，然后把指向副本的指针发布到一个共享位置，供新的读者访问。

+ **多个并发版本。** RCU 允许任意数量的只读临界区与这次更新同时进行。这些只读临界区看到的可能是数据结构的旧版本，也可能是新版本。

+ **与线程调度器集成。** 更新发生时，可能仍有读者在进行中，因此共享对象必须保留其状态的多个版本，以保证旧版本在所有读者访问完毕之前不被释放。从更新被发布，到最后一名读者用完旧版本，这段时间称为**宽限期**（grace period）。RCU 锁利用线程调度器提供的信息来判断宽限期何时结束。

```c
 typedef struct ElementS{
   int key;
   int value;
   struct ElementS *next;
 } Element;

 class RCUList {
   private:
     RCULock rcuLock;
     Element *head;
   public:
     bool search(int key, int *value);
     void insert(Element *item, value);
     bool remove(int key);
 };

 bool
 RCUList::search(int key, int *valuep) {
     bool result = FALSE;
     Element *current;

     rcuLock.readLock();
     current = head;
     for (current = head; current != NULL;
                 current = current->next) {
         if (current->key == key) {
             *valuep = current->value;
             result = TRUE;
             break;
         }
     }
     rcuLock.readUnlock();
     return result;
 }
```

图 6.10 与图 6.11 展示了如何用 RCU 锁实现一个链表，使它可以被许多读者并发访问，同时由一个写者更新。

链表数据结构由一个 RCU 锁和一个指向表头的指针组成。链表中的每个表项有两个数据字段——key 与 value——以及一个指向链表中下一条记录的指针。

search 方法是只读的：在用 readLock 注册之后，它沿链表向下扫描，直到找到 key 匹配的元素。如果找到了该元素，方法通过参数返回其 value 字段，然后返回 TRUE；否则方法返回 FALSE，表示没有找到匹配的记录。

更新链表的方法则要微妙一些。它们都被安排成：只需更新一个指针，就足以把链表的新版本发布给读者。特别重要的是，insert 必须**先**初始化数据结构，**再**更新表头指针，从而让新元素对读者可见。
:::

```c
 void
 RCUList::insert(int key,
                    int value) {
     Element *item;

     // One write at a time.
     rcuLock.writeLock();

     // Initialize item.
     item = (Element*)
          malloc(sizeof(Element));
     item->key = key;
     item->value = value;
     item->next = head;

     // Atomically update list.
     rcuLock.publish(&head, item);

     // Allow other writes
     // to proceed.
     rcuLock.writeUnlock();

     // Wait until no reader
     // has old version.
     rcuLock.synchronize();
 }

 bool
 RCUList::remove(int key) {
     bool found = FALSE;
     Element *prev, *current;

     // One write at a time.
     rcuLock.WriteLock();
     for (prev = NULL, current = head;
             current != NULL; prev = current,
             current = current->next) {
         if (current->key == key) {
             found = TRUE;

             // Publish update to readers
             if (prev == NULL) {
                 rcuLock.publish(&head,
                           current->next);
             } else {
                 rcuLock.publish(&(prev->next),
                           current->next);
             }
             break;
         }
     }

     // Allow other writes to proceed.
     rcuLock.writeUnlock();

     // Wait until no reader has old version.
     if (found) {
         rcuLock.synchronize();
         free(current);
     }
     return found;
 }
```

#### 实现 RCU

实现 RCU 时的核心目标，是尽量降低读临界区的代价：系统必须允许任意数量的并发读者。反过来说，写操作可以具有很高的**延迟**。具体而言，宽限期可能很长：从更新被发布，到系统能够保证没有读者仍在使用旧版本，其间可能长达数十毫秒。即便如此，写的**开销**——每次写所需的 CPU 时间——也应当保持在适度水平。

达成这些目标的一种常用技术，是把 RCU 的实现与线程调度器的实现结合起来。这与上一章介绍的读写锁形成对照：读写锁对线程调度器不作任何假设，但必须精确跟踪任一时刻有多少读者处于活动状态。

具体说来，我们要介绍的这个实现向调度器提出两点要求：(1) 只读临界区在完成之前不被打断；(2) 每当某个处理器上的线程被打断时，调度器就更新该处理器对应的 RCU 状态。这样一来，一次写完成之后，RCULock::Synchronize 只需等待所有处理器至少被打断一次。到那时，就可以确定对象的旧版本处于**静止**（quiescent）状态——没有线程还能访问旧版本（改变它的那个写者除外）。

<div class="code-cap"><span class="code-label">图 6.12</span>一个基于静止状态的 RCU 实现。代码假定自旋锁的获取/释放与中断的开启/关闭都会触发内存屏障。致谢：这段伪代码基于 Paul McKenney 在 “Is Parallel Programming Hard, And, If So, What Can be Done About It?” 中的实现。</div>

```c
 class RCULock{
   private:
   // Global state
     Spinlock globalSpin;
     long globalCounter;
   // One per processor
     DEFINE_PER_PROCESSOR(
        static long, quiescentCount);

   // Per-lock state
     Spinlock writerSpin;

   // Public API omitted
 }

 void RCULock::ReadLock() {
     disableInterrupts();
 }

 void RCULock::ReadUnlock() {
     enableInterrupts();
 }

 // Called by scheduler
 void RCULock::QuiescentState(){
     memory_barrier();
     PER_PROC_VAR(quiescentCount) =
                     globalCounter;
     memory_barrier();
 }

 void RCULock::writeLock() {
     writerSpin.acquire();
 }

 void RCULock::writeUnlock() {
     writerSpin.release();
 }

 void RCULock::publish (void **pp1,
                          void *p2){
     memory_barrier();
     *pp1 = p2;
     memory_barrier();
 }

 void
 RCULock::synchronize() {
     int p, c;

     globalSpin.acquire();
     c = ++globalCounter;
     globalSpin.release();

     FOREACH_PROCESSOR(p) {
         while((PER_PROC_VAR(
           quiescentCount, p) - c) < 0) {
             // release CPU for 10ms
             sleep(10);
         }
     }
 }
```

图 6.12 给出了一个基于静止状态的 RCU 实现。首先注意，readLock 与 readUnlock 的开销很小：它们不更新任何状态，只是确保读操作不被打断。RCU::writeLock 与 writeUnlock 的开销也很小：它们获取并释放一把自旋锁，以保证每个 RCULock 上同一时刻至多有一个写操作可以进行。

RCU::publish 同样简单。它先执行一次内存屏障，使对共享对象的所有修改都在指针更新之前完成；接着更新指针，然后再执行一次内存屏障，让其他处理器能看到这次更新。

RCU::synchronize 与 quiescentState 协同工作，确保 synchronize 返回时，所有线程都必定已经用完了对象的旧版本。RCU::synchronize 递增一个全局计数器，然后等待所有处理器的 quiescentCount 追上该计数器的新值。每当某个处理器被打断时，调度器就调用 RCU::quiescentState，把该处理器的 quiescentCount 更新为当前的 globalCounter。因此，一旦每个处理器上的 quiescentCount 都不小于 c，synchronize 就知道不可能再有读者观察到旧版本了。

## 6.4　多对象原子性

一旦程序中出现了多个共享对象，跨对象的交互就不仅变得必要，也变得棘手。例如，设想一个存储银行账户的系统。一种合理的设计选择，是让每位客户的账户成为一个带锁的共享对象（互斥锁或读写锁，如第 5 章所述）。然而，考虑如下从账户 A 向账户 B 转账 $100 的操作：

```c
A->subtract(100);
B->add(100);
```

尽管每一个单独的动作都是原子的，这一串动作却不是。于是可能出现这样的情况：A 告诉 B 钱已经汇出，而钱尚未进入 B 的账户。

同样，设想一位银行经理想要回答一个问题：“这家银行一共有多少钱？”如果经理的程序只是逐个读取每个账户，那么这个计算就可能漏掉或重复计算在账户之间“在途”的钱，例如 A 到 B 的这笔转账。

这些例子说明了一类普遍的问题：只要程序中含有多个共享对象，它就会出现。即使对象保证每个方法都原子地执行，不同线程的*操作序列*仍然可能交错。管理多把锁的同样问题，也适用于一个对象内部的细粒度加锁。

### 6.4.1　谨慎的类设计

有时，可以通过谨慎的类设计与接口设计来解决这个问题。这既包括单个对象的设计（例如规定清晰、暴露恰当抽象的接口），也包括这些对象如何交互的整体结构（例如把系统体系结构组织成定义良好的层次）。

举例来说，如果用带 readNote 与 writeNote 两个方法的 Note 对象、以及带 checkForMilk 与 addMilk 两个方法的 Fridge 对象去求解“牛奶过多”问题（Too Much Milk），你也会遇到同样的麻烦。若没有相当可观的编程功夫，这些单独操作的原子性并不足以保证得到期望的行为。

另一方面，如果我们重构这些对象，得到：

```c
Fridge::checkforMilkAndSetNoteIfNeeded();
Fridge::addMilk();
```

那么问题就变得直截了当。

这条建议也许显得显而易见：当然，无论单线程代码还是多线程代码，你都应当力求优雅的设计。尽管如此，我们仍要强调：你在接口、抽象和软件体系结构上所做的选择，可能极大地影响设计的复杂度乃至可行性。

### 6.4.2　全部获取/全部释放

不过，更好的接口设计也有其局限。有时，出于程序结构或更高并发度的需要，必须使用多把锁。那么，是否存在一种通用技术，可以执行一组需要多把锁的操作，使这组操作整体看起来是原子的？为表述清楚起见，我们把一组操作称为一个*请求*（request）。

一种做法称为*全部获取/全部释放*（acquire-all/release-all）：在处理请求中的整个操作集合期间，凡是在任何时刻可能用到的锁，都统统获取。然后，一旦线程拿到了它可能需要的全部锁，它就可以执行这个请求，最后再释放这些锁。

::: info 例
考虑一张每个哈希桶配一把锁的哈希表。要把一个条目从一个桶移到另一个桶，哈希表提供了 changeKey(item, k1, k2) 操作。采用全部获取/全部释放，这个函数可以这样实现：先获取 k1 和 k2 两把锁，然后在 k1 下删除该条目、在 k2 下插入该条目，最后释放两把锁。
:::

全部获取/全部释放允许相当高的并发度。当各个请求触及的是由不同锁保护、彼此不相交的状态子集时，它们可以并行推进。

这种方法的一个关键性质，是请求之间的*可串行化*（serializability）：任何程序执行的结果，都等价于把各个请求按某种顺序逐个处理所得的执行结果。可串行化使人们可以*仿佛*每个任务都单独执行那样，去推理多步骤的任务。

如图 6.13 所示，访问不相交数据的请求可以并行推进。其结果与系统先执行其中一个请求、再执行另一个请求（或者反过来）相同。反之，如果两个请求触及相同的数据，那么“所有锁在开始时获取、在结束时释放”这一点就蕴含着：一个请求会在另一个请求开始之前完成。

使用这一做法的难点之一，是在开始处理请求之前就确切知道这个请求会用到哪些锁。一种可能的解决办法是保守地多获取一些锁（例如获取某个请求*可能*需要的所有锁），但这也许很难判定。不先执行请求，我们怎么能知道需要哪些锁呢？

### 6.4.3　两阶段加锁

*两阶段加锁*（two-phase locking）对全部获取/全部释放模式作了改进，以解决这一顾虑。它不在处理请求之前获取全部锁，而是可以按每个操作的需要去获取锁。不过，在请求所需的全部锁都获取到之前，不释放任何锁。大多数实现则干脆在请求结束时释放全部锁。

两阶段加锁避免了事先知道要抓哪些锁的需要。因此，程序可以避免获取用不到的锁，也可能不必把锁持有那么久。

::: info 例
对于采用每桶一把锁的哈希表，changeKey(item, k1, k2) 函数可以这样实现：获取 k1 的锁，用键 k1 删除该条目，获取 k2 的锁，用键 k2 插入该条目，然后释放两把锁。
:::

与全部获取/全部释放一样，两阶段加锁是可串行化的。如果两个请求的数据不相交，它们就是可交换的，因而可串行化。否则，两个请求之间必定存在某些重叠的数据，由一个或多个锁保护。只要一个请求执行完成，它必定在释放其中任何一把锁之前，就已经获取了所有这些锁，并对重叠数据完成了修改。因此，任何与之重叠的请求，对重叠数据的读取或修改必定完全发生在另一个请求之前或之后。

然而，与全部获取/全部释放不同，两阶段加锁在某些情况下会导致死锁，这便是下一节的主题。

::: info 例
假设一个线程开始执行 changeKey(item, k1, k2)，与此同时另一个线程试图把另一个条目沿相反方向从 k2 移到 k1。如果第一个线程获取了 k1 的锁，第二个线程获取了 k2 的锁，那么两者都无法继续推进。
:::

## 6.5　死锁

构造复杂的多线程程序时面临的一个挑战，是死锁的可能性。*死锁*（deadlock）是一组线程之间形成的等待环，其中每个线程都在等待环中另一个线程采取某个动作。

死锁可能出现在许多不同场合，其中最简单的一种是*相互递归加锁*（mutually recursive locking），如下面的代码片段所示：

```c
// Thread A

lock1.acquire();
lock2.acquire();
lock2.release();
lock1.release();
```

```c
// Thread B

lock2.acquire();
lock1.acquire();
lock1.release();
lock2.release();
```

假设两个带互斥锁的共享对象在持有各自锁的情况下可以相互调用。当一个线程持有第一个对象的锁、另一个线程持有第二个对象的锁时，就可能发生死锁。如果第一个线程在仍然持有自己的锁时调用第二个对象，它就需要等待第二个对象的锁。如果另一个线程反过来做同样的事，两者都无法取得进展。

两把锁加一个条件变量也会让我们陷入死锁，如下所示：

```c
// Thread A

lock1.acquire();
...
lock2.acquire();
while (need to wait) {
    cv.wait(&lock2);
}
...
lock2.release();
...
lock1.release();
```

```c
// Thread B

lock1.acquire();
...
lock2.acquire();
...
cv.signal();
lock2.release();
...
lock1.release();
```

在*嵌套等待*（nested waiting）中，一个共享对象在持有第一个对象锁的情况下调用另一个共享对象，然后在一个条件变量上等待。CV::wait 会释放第二个对象的锁，但不释放第一个。如果那个能够向该条件变量发信号的线程需要第一把锁才能取得进展，就会导致死锁。

死锁问题远不止涉及锁和条件变量。只要一个线程在等待某个事件，而该事件因为存在“等待第一个线程所持有的资源”的环而无法发生，就可能出现死锁。正如上面的例子，资源可以是锁，但也可以是任何一种稀缺量：内存、处理时间、磁盘块，或者缓冲区中的空间。

假设我们有两个有界缓冲区（bounded buffer），一个线程把请求放入其中一个缓冲区，并从另一个缓冲区取出响应。如果另一个线程反过来做，就可能导致死锁。

```c
// Thread A

buffer1.put();
buffer1.put();
...
buffer2.get();
buffer2.get();
```

```c
// Thread B

buffer2.put();
buffer2.put();
...
buffer1.get();
buffer1.get();
```

如果缓冲区几乎满了，两个线程都需要等待出现空位，于是双方都无法到达“可以从另一个缓冲区取出数据”这一步，从而无法让对方取得进展。

导致死锁的稀缺资源甚至可以是一根筷子。哲学家就餐问题（Dining Philosophers）是说明死锁的挑战与解决之道的经典案例，图 6.15 给出了一个例子。圆桌周围交替摆放着 n 个盘子和 n 根筷子。坐在盘子前的哲学家需要两根筷子才能进餐。假设每位哲学家都按这样的顺序行动：拿起左边的筷子，拿起右边的筷子，进餐，然后放下两根筷子。如果每位哲学家都这样做，就可能出现死锁：每位哲学家都拿起了左边的筷子，却可能卡在等待右边的哲学家放下筷子上。

注意，相互递归加锁等价于 n = 2 的哲学家就餐问题。

- **死锁的必要条件。** 死锁的发生需要哪些条件？

- **预防死锁。** 可以用哪些技术来预防死锁？

- **用银行家算法避免死锁。** 银行家算法是一种通用的机制，它利用“将来可能需要哪些资源”的知识来预防死锁。

- **检测并从死锁中恢复。** 有些系统不预防死锁，而是在死锁发生之后进行修复。我们如何检测死锁，然后恢复？

### 6.5.1　死锁与饥饿

死锁与饥饿都属于活性问题。在*饥饿*（starvation）中，一个线程在不确定长的时间内无法取得进展。死锁是饥饿的一种形式，但条件更强：一组线程构成一个环，其中没有线程能取得进展，因为每个线程都在等待环中另一个线程采取行动。因此，死锁蕴含饥饿（对哲学家们来说，是字面意义上的饥饿），但饥饿不蕴含死锁。

例如，回忆 5.6.1 节讨论的读者/写者例子。写者只有在有读者或写者活跃时才等待。在我们给出的写者优先方案中，如果新写者到达得足够频繁，正在等待的读者就可能饥饿；同样，如果有读者活跃，而新的读者在最后一个活跃读者完成之前到达并变为活跃，正在等待的写者也可能饥饿。注意，这种饥饿并不是死锁，因为不存在环。等待的读者在等活跃的写者结束，等待的写者在等活跃的读者结束，但没有任何活跃线程在等待某个正在等待的读者或写者。

一个系统可能遭受死锁或饥饿，并不意味着它一定会。如果在某些情形下某个线程可能饥饿，就说该系统*可能饥饿*（subject to starvation）；如果一组线程在某些情形下可能死锁，就说该系统*可能死锁*（subject to deadlock）。这里，影响是否发生死锁或饥饿的情形可以包括很多因素，例如：调度器所做的选择、正在运行的线程数、系统所处理的负载或请求序列、哪些线程在争抢锁时获胜，以及当信号或广播发生时哪些线程以什么顺序被唤醒。

一个可能饥饿或可能死锁的系统，可能在许多次、甚至大多数次运行中都是活的，只在特定负载或“不走运”的交错下才饥饿或死锁。例如，在相互递归加锁中，只有两个线程几乎同时获得外层锁时才会死锁。在哲学家就餐问题中，哲学家们可能成功地吃了很久，才碰上导致死锁的不走运事件序列。同样，在读者/写者例子中，只要写操作的速率保持在某个阈值以下，写者优先方案就会让一部分读操作完成。

由于测试未必能发现死锁问题，因此重要的是在设计上就构造出无死锁的系统。

### 6.5.2　死锁的必要条件

死锁的发生有四个必要条件。了解这些条件对设计解决方案很有用：只要能阻止其中任何一个条件，就能消除死锁的可能性。

+ **有界资源。** 能同时使用某个资源的线程数量是有限的。

+ **不可抢占。** 线程一旦获得某个资源，其所有权就不能被收回，除非该线程主动释放。

+ **持有并等待。** 线程在等待另一个资源时持有某个资源。这个条件有时称为*多重独立请求*（multiple independent requests），因为当一个线程先获得一个资源、再试图获取另一个资源时就会出现。

+ **循环等待。** 存在一组正在等待的线程，其中每个线程都在等待另一个线程所持有的资源。

假设我们有 5 位哲学家围坐在一张有 5 根筷子的桌旁，但筷子不用时放在桌子中央的托盘里。我们可能处于图 6.17 所示的状态：哲学家 1 有两根筷子，哲学家 2、3、4 各有一根筷子并且都在等另一根筷子，而哲学家 5 一根也没有。在这个状态中，我们有有界资源（5 根筷子）、不可抢占（我们不能强行从饥饿的哲学家手中夺走筷子）、持有并等待（哲学家 2、3、4 都持有筷子并等待另一根），以及循环等待（哲学家 2、3、4 各自都在等待另一位哲学家所持有的资源）。然而我们并没有死锁。哲学家 1 最终会放下它的两根筷子，例如这可能使哲学家 2 和 3 得以进餐并放下筷子；这又会使哲学家 4 和 5 得以进餐。

尽管图 6.17 所示的系统当前并未死锁，它仍然*可能死锁*。例如，如果哲学家 1 归还两根筷子，哲学家 5 拿起一根，哲学家 1 又拿起另一根，系统就会死锁。

### 6.5.3　预防死锁

预防死锁可能很有挑战性。例如，考虑一个有 A、B、C 三个资源以及两个访问它们的线程的系统。线程 1 依次获取 A、C、B，线程 2 依次获取 B、C、A。下面的序列可能导致死锁：

我们怎样才能避免这个死锁？死锁的循环等待出现在到达第 5 步时，但我们的命运早在之前就已注定。具体地说，一旦完成第 2 步、线程 2 获得了 B，死锁就不可避免了。要预防死锁，我们必须在第 2 步就意识到它将在第 5 步发生。一旦第 1 步完成、线程 1 获得了 A，我们就不能让线程 2 完成第 2 步并获取 B，否则死锁随之而来。

这个例子说明，对任意程序而言，预防死锁可以采取三种途径之一：

+ **利用或限制程序的行为。** 通常我们可以改变程序的行为，阻止死锁的四个必要条件之一，从而消除死锁的可能性。在上面的例子中，我们可以改变程序，使它从不在持有 C 的时候等待 B，从而消除死锁。

+ **预测未来。** 如果我们能知道线程可能或将会做什么，就可以让线程在走向可能的死锁*之前*先等待（例如线程 2 可以在上面的第 2 步等待），从而避免死锁。

+ **检测并恢复。** 另一种选择是允许线程恢复或“撤销”那些把系统带入死锁的动作；在上面的例子中，当线程 2 发现自己陷入死锁时，它可以回退到较早的状态来恢复。

我们将在本小节和接下来的两个小节中讨论这三种方案。

6.5.2 节列出了死锁的四个必要条件。这些条件之所以有用，是因为它们提示了预防死锁的途径：如果系统的结构能够阻止至少一个条件，系统就不可能死锁。结合具体系统的情形来考虑这些条件，往往能指出可行的死锁预防策略。下面我们讨论一些常用的方法。

**有界资源：提供足够的资源。** 确保无死锁的一种办法，是准备足够的资源来满足所有线程的需求。一个简单的例子是往哲学家就餐问题的桌子中央再加一根筷子；这就足以消除死锁的可能性。另一个例子是：线程实现常常在线程控制块（TCB）中预留空间，以便把线程插入等待链表或就绪链表。理论上当然可以只在需要时才为链表项动态分配空间，但那可能使系统恰好在最糟糕的时刻耗尽内存，从而导致死锁。

**不可抢占：抢占资源。** 另一种技术是允许运行时系统强行收回线程所持有的资源。例如，操作系统可以把一个正在运行的进程的一页内存复制到磁盘上，从而抢占这一页，以免应用程序在获取内存页时死锁。

**持有并等待：调用模块外部代码时释放锁。** 对于各有自己锁的嵌套模块，在内层模块中等待条件变量可能导致嵌套等待死锁。一种解决办法是重构模块代码，使调用其它模块时不持有任何锁。例如，只要程序不依赖于那三步原子地发生，我们就可以把左边的代码改成右边的代码：

```c
Module::foo() {
    lock.acquire();
    doSomeStuff();
    otherModule->bar();
    doOtherStuff();
    lock.release();
}

Module::doSomeStuff() {
    x = x + 1;
}

Module::doOtherStuff() {
    y = y - 2;
}
```

```c
Module::foo() {
    doSomeStuff();
    otherModule->bar();
    doOtherStuff();
}

Module::doSomeStuff() {
    lock.acquire();
    x = x + 1;
    lock.release();
}

Module::doOtherStuff() {
    lock.acquire();
    y = y - 2;
    lock.release();
}
```

::: tip 死锁与内核分页
早期操作系统常运行在主存非常有限的机器上。为了应对这一点——至少可以追溯到 Multics 时代——内核的一部分（代码和数据）可以被换出到磁盘以节省空间。之后需要这些代码和数据时，再把它们调入主存，同时换出内核中当前未使用的另一部分。

使这一机制可行的挑战在于死锁。用于换入或换出内核部分内容的代码，以及它在任何可能的执行路径上可能触及的任何代码或数据，都必须常驻内存。如果没有非常严格的模块分层，就很容易漏掉某个依赖，而它在少数情况下会触发潜伏的死锁。通常唯一可能的补救办法就是重启系统。

由于这种做法固有的复杂性，大多数现代操作系统让全部内核代码和几乎所有数据结构常驻内存；唯一的例外是，有些内核仍然会换出用于应用虚拟内存的页表，这个话题我们将在第 9 章讨论。
:::

理论上，只要在调用模块外部代码时总是释放锁，就可以消除嵌套管程带来的死锁风险。在实践中，这样做很可能相当繁琐：不仅需要额外的代码来获取和释放锁，还需要额外的思考，才能把一个跨一系列动作持锁的原子方法，改造成若干个各自获取并释放锁的原子方法。因此，程序员常常采取一种明显不模块化、也确实不尽如人意的做法：考虑被调用的外部模块是否可能等待某个依赖于外层管程锁的东西。如果这种等待不太可能，就可以在持有外层锁的情况下发起调用。

**循环等待：锁排序。** 许多系统采用的一种方法是，为锁确定一个顺序，并且只按该顺序获取锁。

例如，C 语言的 printf 会获取一把锁，以确保打印出的消息是原子的，而不会与其它线程的输出混在一起。由于等待这把锁不会导致循环等待，因此在持有大多数内核锁时都可以安全地调用 printf。

对于一个带每桶锁的哈希表，以及一个把项从一个桶移到另一个桶的操作 changeKeys(item, k1, k2)，我们可以通过总是先获取编号较小的桶的锁、再获取编号较大的桶的锁来避免死锁。这样就防止了循环等待，因为一个线程只会等待持有更高编号锁的线程。那些线程也可能在等待，但只会等待编号更高的锁，依此类推。

同样，如果哲学家们不是总先拿左边的筷子再拿右边的，而是把筷子从 1 到 n 编号、总是先拿编号较小的筷子再拿编号较大的，我们就能消除哲学家就餐问题中的死锁。

### 6.5.4　用银行家算法避免死锁

消除“持有并等待”的一种通用技术是：等到所有需要的资源都可用，然后在操作开始时把它们原子地一次获取，而不是随着操作推进逐步获取。我们前面在“全部获取/全部释放”中见过这一点；只要实现是原子地获取全部锁而不是逐个获取，它就不会死锁。另一个例子是：哲学家可以等到相邻的两根筷子都可用，然后同时把它们拿起来。

当然，线程可能并不确切知道自己完成工作到底需要哪些资源，但它仍然可以获取自己*可能*需要的全部资源。考虑一个为手机设计的操作系统，其中内存受限，并且不能通过把内存复制到磁盘上来抢占。与其让应用按需请求更多内存，我们不如让每个应用申报自己的最大内存需求，并在它启动时分配这么多内存。

这种做法的缺点包括：影响程序的模块化；应用难以准确估计自己的最坏情况需求；以及在常见情形下分配了远超必要的资源所带来的开销。

Dijkstra 提出银行家算法（Banker's Algorithm），是为了改进“全部获取”的性能。尽管很少有系统完整地使用它，我们仍然讨论它，因为该算法的简化版本很常见。银行家算法还揭示了*安全*状态与*不安全*状态之间的区别，以及死锁的发生往往如何取决于系统的负载和操作序列。

在银行家算法中，线程在开始一项任务时申报自己的最大资源需求，但随后在任务运行过程中逐步获取和释放这些资源。运行时系统会推迟批准某些请求，以确保系统永不发生死锁。

该算法背后的洞见是：一个可能死锁的系统并不一定会死锁——对某些请求交错，它会死锁；对另一些交错，它不会。通过推迟处理某些资源请求，系统可以避开那些可能导致死锁的交错。

<img src="/figures/vol2/image00414.png" alt="图 6.18" loading="lazy">
<figcaption><span class="fig-label">图 6.18</span>进程可以处于安全、不安全或死锁状态。虚线表示一个线程所经历的一系列状态——有些是安全的，有些是不安全的，最终状态是死锁。</figcaption>
</figure>

一个容易死锁的系统可以处于三种状态之一：*安全状态*、*不安全状态*和*死锁状态*（见图 6.18）。

- 在*安全状态*中，对任何可能的资源请求序列，都至少存在一个处理这些请求的*安全序列*，最终能够成功批准所有挂起的和将来的请求。

- 在*不安全状态*中，至少存在一个将来的资源请求序列，无论尝试哪种处理顺序都会导致死锁。

- 在*死锁状态*中，系统至少存在一个死锁。

处于安全状态的系统掌握着自己的命运：对任何负载，它都可以通过推迟处理某些请求来避免死锁。具体来说，银行家算法会推迟任何使系统从安全状态转入不安全状态的请求。一旦系统进入不安全状态，它可能就无法避免死锁了。

注意，不安全状态并不总会导致死锁。处于不安全状态的系统可能保持在该状态，也可能回到安全状态，这取决于资源请求与完成的特定交错。然而，只要系统仍处于不安全状态，一个糟糕的负载或不走运的请求调度就可能迫使它死锁。

银行家算法使系统保持在安全状态。该算法基于一个松散的类比：一个小镇银行家拥有一个在某一时刻最多可贷出的总额（total），以及若干家企业，第 i 家企业有一个信用额度 max[i]。随着各个项目的开始与结束，企业借入并偿还一定数额的钱，因此第 i 家企业的未偿贷款额总是在 0 与 max[i] 之间。如果一家企业在信用额度内的所有请求都得到批准，它最终会达到所有当前项目都已完成的状态，贷款余额回到零。

一个保守的银行家可能只发放信用额度，直到其总和不超过银行家手头可用的资金总额。这种做法类似于*全部获取*或*提供足够的资源*。它保证系统保持在安全状态。所有获得信用额度的企业最终都会完成它们的项目。

然而，更激进的银行家可以发放更多信用，只要银行能够履行对每家企业的承诺——也就是说，在第 i 家企业提出请求时能够提供 max[i] 的贷款。该算法假设银行被允许*推迟*增加贷款额的请求。例如，银行可能把某份文书弄丢几个小时、几天或几周。

通过推迟贷款请求，银行保持在安全状态——所谓安全状态，是指存在至少一个放贷序列，使每家企业 i 最终都能得到它的最大贷款额 max[i]、完成项目并还清全部贷款。银行随后可以用这些还款批准其它企业挂起的贷款。

// Invariant: the system is in a safe state.
ResourceMgr::Request(int resourceID, int threadID) {
    lock.Acquire();
    assert(isSafe());
    while (!wouldBeSafe(resourceID, threadID)) {
        cv.Wait(&lock);
    }
    alloc[resourceID][threadID]++;
    avail[resourceID]--;
    assert(isSafe());
    lock.Release();
}

<div class="code-cap"><span class="code-label">图 6.21</span>银行家算法中用于检验下一个状态是否安全的伪代码。如果不安全，系统就推迟，直到它变为安全。</div>

```c
// A state is safe iff there exists a safe sequence of grants that are sufficient
// to allow all threads to eventually receive their maximum resource needs.

bool
ResourceMgr::isSafe() {
    int j;
    int toBeAvail[] = copy avail[];
    int need[][] = max[][] - alloc[][];  // need[i][j] is initialized to
                                         // max[i][j] - alloc[i][j]
    bool finish[] = [false, false, false, ...]; // finish[j] is true
                                         // if thread j is guaranteed to finish

    while (true) {
        j = any threadID such that:
             (finish[j] == false) && forall i: need[i][j] <= toBeAvail[i];
        if (no such j exists) {
            if (forall j: finish[j] == true) {
                return true;
            } else {
                return false;
            }
        } else {  // Thread j will eventually finish and return its
                  // current allocation to the pool.
            finish[j] = true;
            forall i:  toBeAvail[i] = toBeAvail[i] + alloc[i][j];
        }
    }
}

// Hypothetically grant request and see if resulting state is safe.

bool
ResourceMgr::wouldBeSafe(int resourceID, int threadID) {
    bool result = false;

    avail[resourceID]--;
    alloc[resourceID][threadID]++;
    if (isSafe()) {
        result = true;
    }
    avail[resourceID]++;
    alloc[resourceID][threadID]--;
    return result;
}
```

高层思想很简单：当一个请求到达时，先等到批准它是安全的，再批准它。如图 6.19 所示，我们可以通过跟踪以下信息来实现这一高层做法：(i) 每种资源当前分配给每个线程的数量，(ii) 每个线程可能的最大分配量，(iii) 当前可用、未分配的资源集合。

图 6.21 给出了如何检验一个状态是否安全。回忆一下，如果一个状态存在某种线程执行序列，使每个线程都能获得其最大资源需求、完成工作并释放资源，那么它就是安全的。我们先看当前空闲资源是否足以让某个线程完成。如果是，那么该线程持有的资源最终会归还系统。接着，我们看当前空闲资源加上第一步所确定线程持有的资源，是否足以让另一个线程完成；如果是，第二个线程的资源最终也会归还系统。在按某个特定顺序服务请求的前提下，我们继续这一过程，直到找出所有保证能完成的线程。如果这个集合包含所有线程，该状态就是安全的。

### 6.5.5　检测并从死锁中恢复

有些系统不预防死锁，而是允许死锁发生，并在出现时从中恢复。

为什么要允许死锁发生？有时，要对系统的数据和工作负载施加足够强的结构、以保证永不发生死锁，是很困难或代价很高的。如果死锁很少见，为什么要在常见情况下为预防它付出开销？

要让这种做法可行，我们需要：(i) 一种在死锁发生时从中恢复的办法，最好对用户的目标造成尽可能小的损害；(ii) 一种检测死锁的办法，使我们知道何时调用恢复机制。我们先讨论恢复，因为它为理解实现检测时的取舍提供了背景。

#### 从死锁中恢复

死锁一旦发生，从中恢复很有挑战性。死锁意味着某些线程持有资源并等待其它资源，而进展已不可能。

由于这些资源按定义是不可收回的，强行从部分或全部死锁线程那里拿走资源并不是理想的解决办法。举个简单的例子：如果一个进程是某个死锁的一部分，有些操作系统会让用户选择杀死该进程并释放它的资源。这听起来很激烈，但如果一个死锁的进程无法取得任何进展，杀死它并不会让用户的处境差多少。

然而，在我们讨论过的基于锁的共享对象编程抽象之下，杀死某个进程中的所有线程可能是危险的。如果一个死锁的线程持有某个共享内核对象的锁，杀死该线程并把锁标记为空闲，可能使内核对象处于不一致状态。

因此，我们需要某种系统化的办法，在所需的某个资源不可用时进行恢复。针对这个问题，人们发展出两种广泛使用的做法：

- **不依赖该资源继续执行。** Web 服务常常被设计成能够容忍资源不可用。Web 领域的一条经验法则是：如果网站的延迟变得太长——无论出于什么原因——相当一部分客户就会放弃，转投别处。问题究竟是硬件故障、软件故障还是死锁，其实并不重要。网站必须被设计成能够快速回应用户，不管问题是什么类型。Amazon 的网站就是这种设计范式的良好例子。它被设计成一组相互咬合的模块，其中任何单个模块都可能因故障而离线。因此，网站的所有其它部分都必须设计成能在某个所需资源不可用时应付过去。例如，正常情况下 Amazon 的软件会在完成订单之前检查库存，确认商品有货。但是，如果死锁或故障使库存服务器延迟响应超过某个阈值，前端 Web 服务器就会放弃等待，完成订单，然后把一项后台检查排入队列，以确认该商品确实在库存中。如果商品实际上没有货（例如因为在此期间被别的客户买走了），就向客户发送一封致歉信。只要这种情况不经常发生，它就可能比让客户等待更好，尤其是在死锁的情形下——那里的等待可能是无限期的。由于死锁很少见且难以测试，这要求整个程序在编码上保持纪律，系统地处理错误情况。

- **乐观并发控制。** 事务也可以用来避免死锁。乐观并发控制（optimistic concurrency control）让事务并行执行而不锁住任何数据，但只有当该事务访问过的对象自事务开始以来都没有被修改时，才允许它提交；否则，事务必须中止并重试。要用乐观并发控制实现事务，每个事务要记录自己读取和更新了哪些对象的哪些版本。所有更新都施加在本地副本上，然后在事务提交之前，系统核实该事务访问过的对象在此期间都没有被修改；如果有冲突，事务必须中止。当然，提交一个事务可能使其它正在进行的事务失效（那些使用了本事务修改过的数据的事务）。这些冲突会在较晚的事务试图提交时被发现。当不同的事务通常使用数据的不同子集时，乐观并发控制效果很好。在这些情况下，这种做法不仅消除了死锁，还最大化了并发度，因为线程不必等待锁。另一方面，如果存在许多相互冲突的并发事务，反复回滚并重新执行事务会增加开销。

- **事务：回滚与重试。** 一种更通用的技术使用*事务*（transaction）；事务提供了一种安全机制，可以收回分配给某个线程的资源。我们将在第 14 章详细讨论事务；它们在数据库和文件系统中都被广泛使用。对于死锁恢复，事务提供两项重要服务：

 **线程回滚。** 事务确保从线程收回锁不会使系统的对象处于不一致状态；我们改为回滚，也就是撤销死锁线程的动作，回到一个干净的状态。为解开死锁，我们可以选择一个或多个牺牲线程（victim thread），停止它们，撤销它们的动作，让其它线程继续。

 **线程重启。** 一旦死锁被打破、其它线程完成了部分或全部工作，就重启牺牲线程。当这些线程完成时，系统的行为就像是牺牲线程从未引起死锁，而只是执行被推迟了。

 事务定义了回滚与重启的安全点。每个事务都有 beginTransaction 和 endTransaction 语句；回滚会撤销一路回到 beginTransaction 的所有修改。回滚之后，线程可以安全地在 beginTransaction 处重新开始。事务的一个关键特性是，在事务完成之前，不允许其它线程看到该事务的结果。这样一来，如果事务所做的修改因死锁而需要回滚，就只有那一个线程受影响。这可以通过两阶段加锁来实现，前提是在事务完成之后才释放锁。如果事务成功，它*提交*（commit），事务的锁被释放，事务对共享状态的修改对其它线程可见。然而，如果事务没能到达它的 endTransaction 语句（例如因为死锁，或因为发生了其它异常），事务就*中止*（abort）。系统可以把该事务修改过的所有状态重置为事务开始时的样子。支持这种做法的一种方式是，为每个事务修改过的所有状态保留一份初值副本；事务提交时可以丢弃这份副本。

 如果一个事务系统发生死锁，系统可以中止一个或多个死锁的事务。中止这些事务，会把系统状态回滚到“这些事务从未开始”时的样子，并释放被中止事务的锁和其它资源。如果中止所选定的事务释放了足够的资源，死锁就被打破，剩下的事务可以继续；如果不够，系统可以再中止额外的事务。

 事务系统中随之而来的一个问题是*哪个*线程应当被中止、哪些线程应当被允许继续。一个重要的考虑是活性。对最老的事务给予优先级，可以保证进展并避免饥饿。这样，当系统需要中止某个事务时，它可以中止*最年轻*的那个。这保证了*某个*事务（例如最老的那个）最终会完成；被中止的事务最终会成为最老的，因此它也会完成。这种做法的一个例子是*伤害等待*（wound wait）。在伤害等待中，一个较年轻的事务可以等待一个较老的事务所持有的资源，较老的事务最终会完成并释放该资源，因此不会导致死锁。但是，如果一个较老的事务需要等待一个较年轻的事务所持有的资源，该资源就被抢占，较年轻的事务被中止并重启。

#### 检测死锁

一旦我们有了从死锁中恢复的通用办法，就需要一种判断死锁是否已经发生的办法，以便知道何时触发恢复。一个重要的考虑是，检测机制可以是保守的：只要我们*可能*处于死锁状态，它就可以触发修复。这种做法有误报的风险：一个并未死锁的线程被错误地判定为死锁。取决于修复操作的开销，有时使用更简单的检测机制、即使偶尔误报，也会更高效。

例如，程序可以选择只等待很短时间（或者根本不等待）就宣布需要恢复。我们前面在 Amazon 网站的设计中见过一个例子。另一个例子是旧式的电路交换电话网：一次呼叫在沿途的一系列交换机上预留一条电路。如果连接建立过程在某一跳找不到空闲电路，它不会去等下一跳的电路变为空闲，而是取消这次连接尝试，并给用户一条错误信息：“所有电路都忙，请稍后再拨。”

一个现代的类似物是互联网。当一台路由器过载、数据包缓冲区用尽时，它干脆丢弃到达的数据包。另一种做法是让每台路由器在确认下一台路由器有空间之前一直等待发送——这种做法可能导致死锁。精确判断是否发生了死锁，其开销会超过直接丢弃并重发一些数据包。

有多种方法可以更精确地识别死锁。

如果只有若干资源，且每个资源在同一时间只能被一个线程持有（例如一台打印机、一个键盘、一个音箱，或若干把互斥锁），那么我们可以通过分析一个简单的图来检测死锁。在图 6.22 左边的图中，每个线程和每个资源都用一个节点表示。如果资源*被*某个线程*拥有*，就有一条有向边从资源指向该线程；如果某个线程*等待*该资源，就有一条有向边从该线程指向资源。存在死锁，当且仅当这样的图中存在环。

如果某些资源有多个实例，我们就把有 k 个可互换实例的资源（例如 k 台相同的打印机）表示为一个带 k 个连接点的节点。图 6.22 右边的图说明了这一点。此时，环是死锁的必要条件，但不是充分条件。

Coffman、Elphick 和 Shoshani 在 1971 年描述的另一种方案，是 Dijkstra 银行家算法的一个变体。在这个算法中，我们假设不再知道 max[][]，因此无法判断当前状态是否安全，也无法判断某个将来的请求序列是否会迫使系统死锁。但是，我们可以考察当前的资源集合、已批准的请求和挂起的请求，并问：假设不再有新的请求到来、且所有线程最终都会完成，当前这批请求是否有可能最终得到满足。如果是，就没有死锁（尽管我们可能处于不安全状态）；否则就有死锁。

<div class="code-cap"><span class="code-label">图 6.23</span>Coffman 等人提出的死锁检测。该算法与图 6.21 所示银行家算法的 isSafe() 检测类似。</div>

```c
// A state is safe iff there exists a safe sequence of grants that would allow
// all threads to eventually receive their maximum resource needs.
//
// avail[] holds free resource count
// alloc[][] holds current allocation
// request[][] holds currently-blocked requests
bool
ResourceMgr::isDeadlocked() {
    int j;
    int toBeAvail[] = copy avail[];
    bool finish[] = [false, false, false, ...]; // finish[j] is true if thread
                                                // j is guaranteed to finish

    while(true) {
        j = any threadID such that (finish[j] == false) &&
                                (forall i: request[i][j] <= toBeAvail[i]);
        if (no such j exists) {
            if (forall j: finish[j] == true) {
                return false;
            } else {
                return true;
            }
        } else {
            // Thread j *may* eventually finish and
            // return its current allocation to the pool.
            finish[j] = true;
            forall i: toBeAvail[i] = toBeAvail[i] + alloc[i][j];
        }
    }
}
```

图 6.23 给出了 isDeadlocked 方法的伪代码，它是图 6.21 中银行家算法所用 isSafe 方法的一个变体。

人们或许希望，我们可以通过问“满足当前请求会不会使我们进入死锁状态？”并阻塞任何会导致这种情况的请求，来避免死锁。Coffman 等人的算法强调：死锁不仅取决于批准了哪些请求，也取决于有哪些请求正在等待。触发死锁（“循环等待”）的那个请求将是一个等待的请求，而不是一个被批准的请求。

## 6.6　非阻塞同步

第 5 章描述了同步的一个核心抽象——共享对象，每个对象配一把锁。在绝大多数情况下，这一抽象都足以支撑多线程程序的构建。然而，随着并发程序变得越发复杂，锁争用、跨越多个对象的操作其语义，以及死锁等问题都可能出现。更糟的是，这些问题的解决方案往往要求我们牺牲模块化；例如，要判断某个特定程序是否会死锁，就得详细理解各个共享对象的实现之间如何相互作用。

一些研究者提出了一个激进的问题：编写复杂的并发程序时，不用锁会不会更好？取消加锁，就可以把锁争用和死锁从设计考虑中消除，从而促成更加模块化的程序结构。然而，这些技术用起来可能*复杂得多*。迄今为止，无锁的并发实现只用于少数由专家级程序员编写的、精心设计的运行时库模块。我们之所以勾勒这些思想，是因为随着每台计算机上处理器数量的持续增长，它们有可能变得更为重要。

今天，确实需要采用这些方法的场合很少见。只有已经掌握了基于锁的基本方法的经验丰富的程序员，才应考虑这些高级技术。你们中的许多人也许永远不需要用到它们。如果你确实想尝试，请格外小心：测量系统的性能，确认这些技术带来了显著的收益；并向可信赖的同行寻求额外的评审，以帮助确保代码按预期工作。

程序员常常假定获取锁是一项昂贵的操作，因而试图在整个程序中减少加锁。而过早优化最可能的结果，是一个有缺陷、难以维护、并不比干净利落的实现更快，而且讽刺的是，比架构清晰的程序更难调优的程序。在大多数平台上，获取或释放锁都是一个经过高度优化的原语——获取一把无争用的锁往往几乎不花代价。如果出现了争用，那多半说明你确实需要这把锁！

在 6.3 节中，我们看到了一个不用锁实现同步的例子。读-复制-更新（RCU）允许读操作在不获取锁、也不更新共享同步状态的情况下继续进行，但它仍然要求更新操作获取锁。如果持有锁的线程被中断、因缺陷而停止推进，或者陷入死锁，其他线程就可能被拖延很长——也许是无限长——的一段时间。

我们完全可以构造出对读操作和写操作都完全*非阻塞*的数据结构。所谓非阻塞方法，是指从不要求一个线程等待另一个线程完成其操作的方法。获取锁则是一种阻塞操作：一旦持有锁的线程停住、被延迟或死锁，其他所有线程都必须等它退出临界区。

更形式化地说，*无等待数据结构*（wait-free data structure）是这样一种结构：它保证每个线程都能取得进展——无论在该结构中执行的其他线程处于什么状态、以多快的速度执行，每个方法都能在有限步内完成。*无锁数据结构*（lock-free data structure）则只保证某个线程能取得进展：总有某个方法能在有限步内完成。

无等待与无锁数据结构的常见构件，是大多数现代处理器上都提供的原子比较并交换（compare-and-swap）指令。我们在 6.3 节 MCS 锁的实现中已略有体会。在那里，我们用比较并交换把线程原子地追加到等待线程的链表上，*而无需事先获取锁*。

无等待与无锁数据结构把这一思想运用得更为普遍，从而彻底消除锁的使用。例如，无锁哈希表可以构造为一个由指向各哈希桶的指针组成的数组：

- **查找。** 查找操作解引用该指针，并检查相应的桶。

- **更新。** 要更新一个桶，线程先分配该桶的一份新副本，然后用比较并交换，当且仅当该指针在此期间没有被改动过时，原子地替换它。如果两个线程同时试图更新同一个桶（例如添加一个新条目），则一个成功，另一个必须重试。

对于更复杂的数据结构，其逻辑可能复杂得多；因此，设计高效的无等待与无锁数据结构仍然是专家的领域。尽管如此，人们已经为种类广泛的数据结构设计出了非阻塞算法，包括先进先出（FIFO）队列、双端队列、后进先出（LIFO）栈、集合和平衡树。其中若干实现可以在 Java 虚拟机运行时库中找到。

此外，人们也投入了相当多的精力研究如何自动构造无等待与无锁数据结构。例如，采用乐观并发控制（optimistic concurrency control）的事务，为实现无锁应用提供了一种非常灵活的做法。回忆一下，乐观并发控制让事务在不锁定其所访问数据的情况下推进；如果在提交时发现它所访问的某些数据在此期间已被改动，该事务就中止。大多数现代数据库都采用某种形式的乐观并发控制，为磁盘上的数据结构提供原子的、容错的更新。

::: info 例
乐观并发控制是无锁的、无等待的，还是两者兼有？
:::

::: warning 答
**要看出乐观并发控制是无锁的**，考虑两个同时执行的冲突事务。先提交的那个成功，第二个必须中止并重试。**如果一种实现采用创伤等待（wound wait）或其他机制来限制一个事务成功提交所需的重试次数，那么它就是无等待的。** □
:::

沿着这一思路，*软件事务内存*（software transactional memory，STM）是一种有希望的做法，可以为内存中的数据结构提供通用的事务支持。遗憾的是，STM 事务的代价往往显著高于传统的临界区；原因在于它需要维护用于检查依赖关系的状态，还需要维护另一份状态——在无冲突时据以更新对象，在检测到冲突时据以回滚对象。STM 的开销能否降低到可以更广泛使用的程度，仍是一个悬而未决的问题。在可以使用 STM 的场合，它提供了一种组合不同模块的方式，而不必操心锁争用或死锁。

## 6.7　小结与未来方向

高级同步技术应当谨慎对待。你的首要目标应当是构造出一个能工作的程序，哪怕这意味着在一个数据结构、甚至整个程序的外围套上“一把大锁”。

除非你**确信**确有必要，否则要抵制把事情搞得更复杂的诱惑。怎样才能确信？不要猜，去测量系统的性能。测量程序及其各子系统在“修改前”和“修改后”的性能，不仅能帮助你为手头的程序作出正确的决策，还能帮助你为将来编写的程序培养良好的直觉。

在设计过程的早期就花时间，为程序建立清晰的结构。考虑到多对象同步的问题常常会模糊模块边界，拥有一个能让你推理程序各部分如何交互的总体结构至关重要。要力争做到严格的模块分层或层级结构。这样的程序更容易实现无死锁，也更容易测试。

尽管性能很重要，但通常更容易的做法是：先从一个清晰、简单、正确的设计开始，测量它以找出瓶颈，然后优化这些瓶颈；相比之下，从一个复杂的设计出发去调整其性能要难得多，更不用说去修它的缺陷了。

在本章中，我们给出了一组用于管理复杂的、多对象并发程序的概念性工具和技术。我们讨论了：估计锁对多处理器性能的影响；减少锁争用的设计模式；针对高争用锁的实现技术，如 MCS 和 RCU；在同一对象的多个操作之间、或跨对象实现原子性的策略；以及死锁预防与恢复的算法。

然而，编写并发程序仍然复杂得令人沮丧。我们认为，未来工作的一个重要方向将是开发更好的工具来管理和降低这种复杂性。过去十年间，新一代工具发展起来，通过自动识别测试覆盖率、内存泄漏、已释放内存的再次使用、缓冲区溢出和错误的指针运算，帮助程序员提高软件的可靠性。

把这种做法推广到并发程序上是一项重大的挑战。一条有希望的途径是利用自动工具检测内存竞态；一个编写良好的程序，在不持有保护相应数据结构的锁时，不应对共享内存进行任何读或写。一旦证明程序不存在竞态，就可以用模型检验（model checking）系统地测试共享对象在一切可能的线程交错下都能正确工作。
